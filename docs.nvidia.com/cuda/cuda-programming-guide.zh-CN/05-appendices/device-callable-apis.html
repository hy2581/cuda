5.6. 设备端可调用 API 与内建函数#

本章包含可从 CUDA 内核和设备代码调用的 API 和内在函数的参考材料和 API 文档。

5.6.1. 内存屏障原语接口#

原语 API 是一个类似 C 的接口 cuda::barrier 功能。这些原语可通过包含 <cuda_awbarrier_primitives.h> 头文件。

5.6.1.1. 数据类型#

typedef /* 实施定义 */ __mbarrier_t;
typedef /* 实施定义 */ __mbarrier_token_t;

5.6.1.2. 内存屏障原语 API#

uint32_t __mbarrier_maximum_count();
void __mbarrier_init(__mbarrier_t* bar, uint32_t expected_count);

  • bar 必须是一个指向 __shared__ memory.

  • expected_count <= __mbarrier_maximum_count()

  • Initialize *bar 当前和下一阶段的预计到达人数 expected_count.

void __mbarrier_inval(__mbarrier_t* bar);

  • bar 必须是指向驻留在共享内存中的屏障对象的指针。

  • 无效 *bar 在重新利用相应的共享内存之前需要。

__mbarrier_token_t __mbarrier_arrive(__mbarrier_t* bar);

  • 初始化 *bar 必须在此调用之前发生。

  • 待处理计数不得为零。

  • 以原子方式减少屏障当前阶段的待处理计数。

  • 返回与递减之前的屏障状态相关联的到达令牌。

__mbarrier_token_t __mbarrier_arrive_and_drop(__mbarrier_t* bar);

  • 初始化 *bar 必须在此调用之前发生。

  • 待处理计数不得为零。

  • 以原子方式减少屏障当前阶段的待处理计数和下一阶段的预期计数。

  • 返回与递减之前的屏障状态相关联的到达令牌。

bool __mbarrier_test_wait(__mbarrier_t* bar, __mbarrier_token_t token);

  • token 必须与前一个阶段或当前阶段相关联 *bar.

  • 如果 token 与 *bar 的前一个阶段相关联，则返回 true；否则返回 false。

bool __mbarrier_test_wait_parity(__mbarrier_t* bar, bool phase_parity);

  • phase_parity 必须指示当前阶段或前一阶段的奇偶校验 *bar。值为 true 对应于奇数相且值为 false 对应于偶数相。

  • 如果 phase_parity 表示 *bar 前一阶段的整数奇偶校验，则返回 true；否则返回 false。

bool __mbarrier_try_wait(__mbarrier_t* bar, __mbarrier_token_t token, uint32_t max_sleep_nanosec);

  • token 必须与前一个阶段或当前阶段相关联 *bar.

  • 如果 token 与 *bar 的前一个阶段相关联，则返回 true。否则，执行线程可能会被挂起。当指定阶段完成时，挂起的线程恢复执行（返回 true），或在该阶段完成之前根据系统相关的时间限制提前恢复（返回 false）。

  • max_sleep_nanosec 指定可用于时间限制而不是系统相关限制的时间限制（以纳秒为单位）。

bool __mbarrier_try_wait_parity(__mbarrier_t* bar, bool phase_parity, uint32_t max_sleep_nanosec);

  • phase_parity 必须指示当前阶段或前一阶段的奇偶校验 *bar。 值为 true 对应于奇数相且值为 false 对应于偶数相。

  • 如果 phase_parity 表示 *bar 前一阶段的整数奇偶校验，则返回 true。否则，执行线程可能会被挂起。当指定阶段完成时，挂起的线程恢复执行（返回 true），或在该阶段完成之前根据系统相关的时间限制提前恢复（返回 false）。

  • max_sleep_nanosec 指定可用于时间限制而不是系统相关限制的时间限制（以纳秒为单位）。

5.6.2. 管道原语接口#

管道原语为可用功能提供类似 C 的接口 <cuda/pipeline>。管道原语接口可通过包含 <cuda_pipeline.h> 标头。在不兼容 ISO C++ 2011 的情况下进行编译时，请包含 <cuda_pipeline_primitives.h> 头文件。

注

管道原语 API 仅支持跟踪从全局内存到具有特定大小和对齐要求的共享内存的异步副本。它提供了与 cuda::pipeline 对象与 cuda::thread_scope_thread.

5.6.2.1. memcpy_async 原语#

void __pipeline_memcpy_async(void* __restrict__ dst_shared,
                             const void* __restrict__ src_global,
                             size_t size_and_align,
                             size_t zfill=0);

  • 请求提交以下操作进行异步评估：

    size_t i = 0;
for (; i < size_and_align - zfill; ++i) ((char*)dst_shared)[i] = ((char*)src_global)[i]; /* copy */
for (; i < size_and_align; ++i) ((char*)dst_shared)[i] = 0; /* 零填充 */

  • Requirements:

    • dst_shared 必须是指向共享内存目标的指针 memcpy_async.

    • src_global 必须是指向全局内存源的指针 memcpy_async.

    • size_and_align 必须是 4、8 或 16。

    • zfill <= size_and_align.

    • size_and_align 必须是对齐的 dst_shared 或 src_global.

  • 对于任何线程来说，在等待之前修改源内存或观察目标内存都是竞争条件。 memcpy_async 操作来完成。提交之间 memcpy_async 操作并等待其完成，以下任何操作都会引入竞争条件：

    • 加载自 dst_shared.

    • 存储至 dst_shared 或 src_global.

    • 应用原子更新 dst_shared 或 src_global.

5.6.2.2. 提交原语#

void __pipeline_commit();

  • 提交提交 memcpy_async 作为当前批次添加到管道。

5.6.2.3. 等待原语#

void __pipeline_wait_prior(size_t N);

  • 令 {0, 1, 2, ..., L} 是与调用相关的索引序列 __pipeline_commit() 通过给定的线程。

  • 等待批次完成 至少 直至并包括 L-N.

5.6.2.4. 到达屏障原语#

void __pipeline_arrive_on(__mbarrier_t* bar);

  • bar 指向共享内存中的屏障。

  • 将屏障到达计数增加 1，当在此调用之前排序的所有 memcpy_async 操作完成时，到达计数将减少 1，因此对到达计数的净影响为零。用户有责任确保到达计数的增量不超过 __mbarrier_maximum_count().

5.6.3. 合作组API#

5.6.3.1. cooperative_groups.h#

5.6.3.1.1. 类 thread_block#

任何 CUDA 程序员都已经熟悉一组特定的线程：线程块。合作组扩展引入了一种新的数据类型， thread_block，在内核中明确表示这个概念。

class thread_block;

通过构建：

thread_block g = this_thread_block();

公共会员功能：

static void sync()：同步组中命名的线程，相当于 g.barrier_wait(g.barrier_arrive())

thread_block::arrival_token barrier_arrive()：到达thread_block屏障，返回需要传入的token barrier_wait().

void barrier_wait(thread_block::arrival_token&& t): 等等 thread_block 屏障，获取从返回的到达令牌 barrier_arrive() 作为右值引用。

static unsigned int thread_rank(): 调用线程在 [0, num_threads) 内的排名

static dim3 group_index()：启动网格内块的 3 维索引

static dim3 thread_index()：已启动块内线程的 3 维索引

static dim3 dim_threads()：启动块的尺寸（以线程为单位）

static unsigned int num_threads()：组内线程总数

旧成员函数（别名）：

static unsigned int size()：组中线程总数（别名为 num_threads())

static dim3 group_dim()：启动块的尺寸（别名 dim_threads())

示例：

// / 将全局整数加载到共享内存中
__global__ void kernel(int *globalInput) {
    __shared__ int x;
    thread_block g = this_thread_block();
    // 在线程块中选择一个领导者
    if (g.thread_rank() == 0) {
        // 从全局加载到共享以供所有线程使用
        x = (*globalInput);
    }
    // 将数据加载到共享内存后，想要同步
    // 如果线程块中的所有线程都需要查看它
    g.sync(); // 相当于 __syncthreads();
}

注意： 组中的所有线程都必须参与集体操作，否则行为是未定义的。

相关： thread_block 数据类型派生自更通用的 thread_group 数据类型，可用于表示更广泛的组类。

5.6.3.1.4. 类 thread_block_tile#

平铺组的模板化版本，其中模板参数用于指定平铺的大小 - 在编译时已知这一点，就有可能实现更优化的执行。

template <unsigned int Size, typename ParentT = void>
class thread_block_tile;

通过构建：

template <unsigned int Size, typename ParentT>
_CG_QUALIFIER thread_block_tile<Size, ParentT> tiled_partition(const ParentT& g)

Size 必须是 2 的幂且小于或等于 1024。注释部分描述了在计算能力 7.5 或更低的硬件上创建大小大于 32 的切片所需的额外步骤。

ParentT 是划分该组的父类型。它是自动推断的，但 void 值会将此信息存储在组句柄中而不是类型中。

公共会员功能：

void sync() const：同步组中命名的线程

unsigned long long num_threads() const：组内线程总数

unsigned long long thread_rank() const: 调用线程在 [0, num_threads) 内的排名

unsigned long long meta_group_size() const：返回父组分区时创建的组数。

unsigned long long meta_group_rank() const：从父组划分的分块集中的组的线性排名（受meta_group_size限制）

T shfl(T var, unsigned int src_rank) const: 参考 warp shuffle功能, 注意：对于大于 32 的大小，组中的所有线程都必须指定相同的 src_rank，否则行为未定义。

T shfl_up(T var, int delta) const: 参考 warp shuffle功能，仅适用于小于或等于 32 的尺寸。

T shfl_down(T var, int delta) const: 参考 warp shuffle功能，仅适用于小于或等于 32 的尺寸。

T shfl_xor(T var, int delta) const: 参考 warp shuffle功能，仅适用于小于或等于 32 的尺寸。

int any(int predicate) const: 参考 warp 投票功能

int all(int predicate) const: 参考 warp 投票功能

unsigned int ballot(int predicate) const: 参考 warp 投票功能，仅适用于小于或等于 32 的尺寸。

unsigned int match_any(T val) const: 参考 warp 匹配函数，仅适用于小于或等于 32 的尺寸。

unsigned int match_all(T val, int &pred) const: 参考 warp 匹配函数，仅适用于小于或等于 32 的尺寸。

旧成员函数（别名）：

unsigned long long size() const：组中线程总数（别名为 num_threads())

注意：

  • thread_block_tile 这里使用模板化数据结构，组的大小被传递给 tiled_partition 作为模板参数而不是实参进行调用。

  • shfl, shfl_up, shfl_down, and shfl_xor 使用 C++11 或更高版本编译时，函数接受任何类型的对象。这意味着只要满足以下约束，就可以对非整数类型进行洗牌：

    • 符合普通可复制的条件，即 is_trivially_copyable<T>::value == true

    • sizeof(T) <= 32 对于尺寸小于或等于 32 的分块， sizeof(T) <= 8 对于较大的分块

  • 在计算能力为 7.5 或更低的硬件上，大小大于 32 的分块需要为其保留少量内存。这可以使用以下方法完成 cooperative_groups::block_tile_memory 必须驻留在共享内存或全局内存中的结构模板。

    template <unsigned int MaxBlockSize = 1024>
struct block_tile_memory;

    MaxBlockSize 指定当前线程块中的最大线程数。该参数可用于在只以较小线程数启动的内核中，尽量减少 block_tile_memory 的共享内存用量。

    随后需要将此 block_tile_memory 传入 cooperative_groups::this_thread_block，从而允许得到的 thread_block 被划分为大小大于 32 的分块。接受 block_tile_memory 参数的 this_thread_block 重载是一个集体操作，必须由 thread_block 中的所有线程调用。

    block_tile_memory 可以在计算能力 8.0 或更高版本的硬件上使用，以便能够编写针对多种不同计算能力的一个源代码。在不需要的情况下，在共享内存中实例化时，它不应消耗内存。

示例：

// / 以下代码将创建两组平铺组，大小分别为 32 和 4：
// / 后者将出处编码在类型中，而第一个将其存储在句柄中
thread_block block = this_thread_block();
thread_block_tile<32> tile32 = tiled_partition<32>(block);
thread_block_tile<4, thread_block> tile4 = tiled_partition<4>(block);

// / 以下代码将在所有计算功能上创建大小为 128 的图块。
// 在计算能力 8.0 或更高版本上可以省略 /block_tile_memory。
__global__ void kernel(...) {
    // 为 thread_block_tile 使用保留共享内存，
    // 指定块大小最多为 256 个线程。
    __shared__ block_tile_memory<256> shared;
    thread_block thb = this_thread_block(shared);

    // 使用 128 个线程创建图块。
    auto tile = tiled_partition<128>(thb);

    // ...
}

5.6.3.1.5. 类合并组#

在 CUDA 的 SIMT 架构中，在硬件级别，多处理器以 32 个线程为一组执行线程（称为 warps）。如果应用程序代码中存在数据相关的条件分支，使得 warp 内的线程出现分歧，则 warp 会串行执行每个分支，从而禁用不在该路径上的线程。路径上保持活动状态的线程称为合并的线程。协作组具有发现和创建包含所有合并线程的组的功能。

通过构建组句柄 coalesced_threads() 是机会主义的。它返回该时间点的活动线程集，并且不保证返回哪些线程（只要它们是活动的）或者它们将在整个执行过程中保持合并（它们将被带回到一起以执行集体，但之后可能会再次发散）。

class coalesced_group;

通过构建：

coalesced_group active = coalesced_threads();

公共会员功能：

void sync() const：同步组中命名的线程

unsigned long long num_threads() const：组内线程总数

unsigned long long thread_rank() const: 调用线程在 [0, num_threads) 内的排名

unsigned long long meta_group_size() const：返回父组分区时创建的组数。例如，如果该组是通过查询活动线程集创建的 coalesced_threads() 的价值 meta_group_size() 将是 1。

unsigned long long meta_group_rank() const：从父组划分的分块集中的组的线性排名（受meta_group_size限制）。如果该组是通过查询活动线程集创建的，例如 coalesced_threads() 的价值 meta_group_rank() 永远是0。

T shfl(T var, unsigned int src_rank) const: 参考 warp shuffle功能

T shfl_up(T var, int delta) const: 参考 warp shuffle功能

T shfl_down(T var, int delta) const: 参考 warp shuffle功能

int any(int predicate) const: 参考 warp 投票功能

int all(int predicate) const: 参考 warp 投票功能

unsigned int ballot(int predicate) const: 参考 warp 投票功能

unsigned int match_any(T val) const: 参考 warp 匹配函数

unsigned int match_all(T val, int &pred) const: 参考 warp 匹配函数

旧成员函数（别名）：

注意：

5.6.3.2. cooperative_groups/async.h#

5.6.3.2.1. memcpy_async#

memcpy_async 是一个组范围的集体 memcpy，它利用硬件加速支持从全局内存到共享内存的非阻塞内存事务。给定一组在组中命名的线程， memcpy_async 将通过单个管道阶段移动指定数量的字节或输入类型的元素。此外，为了在使用时获得最佳性能 memcpy_async API，共享内存和全局内存都需要 16 字节对齐。需要注意的是，虽然在一般情况下这是一个 memcpy，但只有当源是全局内存并且目标是共享内存并且两者都可以通过 16、8 或 4 字节对齐来寻址时，它才是异步的。异步复制的数据只能在调用 wait 或 wait_prior 之后读取，这表明相应的阶段已完成将数据移动到共享内存。

必须等待所有未完成的请求可能会失去一些灵活性（但会变得简单）。为了有效地重叠数据传输和执行，能够启动一个 N+1memcpy_async 等待并根据请求进行操作时请求 N。为此，请使用 memcpy_async 并使用基于集体阶段的等待 wait_prior API。参见 等待和 wait_prior 了解更多详情。

执行复制 “形状”字节.

// / 此示例从全局内存中流式传输 elementsPerThreadBlock 的数据
// / 放入一个有限大小的共享内存 (elementsInShared) 块中进行操作。
#include <cooperative_groups.h>
#include <cooperative_groups/memcpy_async.h>

__global__ void kernel(int* global_data) {
    cg::thread_block tb = cg::this_thread_block();

    const size_t elementsInShared = 128;

5.6.3.2.2. wait 或 wait_prior#

template <typename TyGroup>
void wait(TyGroup & group);

template <unsigned int NumStages, typename TyGroup>
void wait_prior(TyGroup & group);

wait 或 wait_prior 集体允许等待 memcpy_async 副本完成。 wait 阻止调用线程，直到完成所有先前的副本。 wait_prior 允许最新的 NumStages 仍未完成并等待所有先前的请求。所以与 N 请求的总副本数，它会等到第一个 N-NumStages 已完成，最后 NumStages 可能仍在进行中。两者都 wait 或 wait_prior 将同步指定组。

代码生成要求： 计算能力最低 5.0，异步计算能力 8.0，C++11

cooperative_groups/memcpy_async.h 需要包含标题。

示例：

// / 此示例从全局内存中流式传输 elementsPerThreadBlock 的数据
// / 放入一个有限大小的共享内存 (elementsInShared) 块中进行操作
// / 多个（两个）阶段。随着第 N 阶段的开始，我们可以在第 N-1 阶段等待并进行操作。
#include <cooperative_groups.h>
#include <cooperative_groups/memcpy_async.h>

namespace cg = cooperative_groups;

__global__ void kernel(int* global_data) {
    cg::thread_block tb = cg::this_thread_block();
    const size_t elementsPerThreadBlock = 16 * 1024 + 64;
    const size_t elementsInShared = 128;
    __align__(16) __shared__ int local_smem[2][elementsInShared];
    int stage = 0;
    // 首先启动一个额外的请求
    size_t copy_count = elementsInShared;
    size_t index = copy_count;
    cg::memcpy_async(tb, local_smem[stage], elementsInShared, global_data, elementsPerThreadBlock - index);
    while (index < elementsPerThreadBlock) {
        // 现在我们开始下一个请求......
        cg::memcpy_async(tb, local_smem[stage ^ 1], elementsInShared, global_data + index, elementsPerThreadBlock - index);
        // ...但我们等待前面的一个
        cg::wait_prior<1>(tb);

        // 它现在可用，我们可以在此处使用 local_smem[stage]
        // (...)
        //

        // 计算下一次迭代实际复制的数据量。
        copy_count = min(elementsInShared, elementsPerThreadBlock - index);
        index += copy_count;

        // 这里可能需要 cg::sync(tb) ，具体取决于是否
        // 使用 local_smem[stage] 完成的工作可以释放线程以继续竞争或不继续竞争
        // 换行至下一阶段
        stage ^= 1;
    }
    cg::wait(tb);
    // 最后的local_smem[stage]可以在这里处理
}

// 仅当数据通过 test_fn 谓词时才将输入数据放入输出
template<typename Group, typename Data, typename TyFn>
__device__ int stream_compaction(Group &g, Data *input, int count, TyFn&& test_fn, Data *output) {
    int per_thread = count / g.num_threads();
    int thread_start = min(g.thread_rank() * per_thread, count);
    int my_count = min(per_thread, count - thread_start);

    // 从我的输入部分获取所有传递的项目
    // 进入阵列的传染部分并对它们进行计数。
    int i = thread_start;
    while (i < my_count + thread_start) {
        if (test_fn(input[i])) {
            i++;
        }
        else {
            my_count--;
            input[i] = input[my_count + thread_start];
        }
    }

    // 扫描每个线程的计数以计算我的开始
    // 输出中的索引
    int my_idx = cg::exclusive_scan(g, my_count);

    for (i = 0; i < my_count; ++i) {
        output[my_idx + i] = input[thread_start + i];
    }
    // 返回输出中的项目总数
    return g.shfl(my_idx + my_count, g.num_threads() - 1);
}

    return tile.thread_rank() % 2 + 1;
}

__device__ int my_thread_data(int i) {
    return i;

    __shared__ cuda::atomic<int, cuda::thread_scope_block> buffer_used;

    auto block = cg::this_thread_block();

    for (int i = 0 ; i < buf_needed ; ++i) {
        buffer[buf_offset + i] = my_thread_data(i);

}

5.6.3.6.1. barrier_arrive 或 barrier_wait#

T::arrival_token T::barrier_arrive();
void T::barrier_wait(T::arrival_token&&);

barrier_arrive 或 barrier_wait 成员函数提供了类似的同步API cuda::barrier （阅读更多）。协作组自动初始化组屏障，但到达和等待操作由于这些操作的集体性质而具有额外的限制：组中的所有线程必须每个阶段到达并等待屏障一次。 当 barrier_arrive 与组一起调用，调用任何集体操作或与该组的另一个屏障到达的结果是不确定的，直到观察到屏障阶段完成为止 barrier_wait 打电话。线程被阻塞于 barrier_wait 可能会在其他线程调用之前从同步中释放 barrier_wait，但仅在组中的所有线程调用之后 barrier_arrive。 团体类型 T 可以是以下任意一个 隐性群体。这允许线程在到达之后和等待同步解决之前执行独立的工作，从而隐藏一些同步延迟。 barrier_arrive 返回一个 arrival_token 必须传入相应的对象 barrier_wait。令牌以这种方式消耗，不能用于其他用途 barrier_wait call.

Barrier_arrive 和 Barrier_wait 用于跨集群同步共享内存的初始化的示例：

#include <cooperative_groups.h>

using namespace cooperative_groups;

void __device__ init_shared_data(const thread_block& block, int *data);
void __device__ local_processing(const thread_block& block);
void __device__ process_shared_data(const thread_block& block, int *data);

__global__ void cluster_kernel() {
    extern __shared__ int array[];
    auto cluster = this_cluster();
    auto block   = this_thread_block();

    // 使用此线程块来初始化一些共享状态
    init_shared_data(block, &array[0]);

    auto token = cluster.barrier_arrive(); // 让其他块知道该块正在运行并且数据已初始化

    // 进行一些本地处理以隐藏同步延迟
    local_processing(block);

    // 从集群中的下一个块映射共享内存中的数据
    int *dsmem = cluster.map_shared_rank(&array[0], (cluster.block_rank() + 1) % cluster.num_blocks());

    // 在访问 dsmem 之前，确保集群中的所有其他块正在运行并初始化共享数据
    cluster.barrier_wait(std::move(token));

    // 消耗分布式共享内存中的数据
    process_shared_data(block, dsmem);
    cluster.sync();
}

5.6.3.6.2.1. 电网同步#

在引入协作组之前，CUDA 编程模型仅允许在内核完成边界处的线程块之间进行同步。内核边界带有隐式的状态失效，以及潜在的性能影响。

例如，在某些用例中，应用程序具有大量小内核，每个内核代表处理管道中的一个阶段。当前 CUDA 编程模型需要这些内核的存在，以确保在一个管道阶段上运行的线程块在下一管道阶段上运行的线程块准备好使用数据之前已生成数据。在这种情况下，提供全局线程间块同步的能力将允许应用程序重构为具有持久线程块，这些线程块能够在给定阶段完成时在设备上同步。

要从内核内部跨网格同步，您只需使用 grid.sync() function:

grid_group grid = this_grid();
grid.sync();

当启动内核时，有必要使用，而不是 <<<...>>> 执行配置语法， cudaLaunchCooperativeKernel CUDA 运行时启动 API 或 CUDA driver equivalent.

5.6.4. CUDA 设备运行时#

CUDA 设备运行时是内核代码中可用的 API，它提供了许多与主机上的 CUDA 运行时 API 相同的功能。这些 API 最常在以下环境中使用 CUDA 动态并行性 和 设备图启动.

5.6.4.1. 在 CUDA 代码中包含设备运行时 API#

5.6.4.2.2.1. 内存声明#
5.6.4.2.2.1.1. 设备和常量内存#

在文件范围内声明的内存 __device__ 或 __constant__ 使用设备运行时时，内存空间说明符的行为相同。所有内核都可以读取或写入设备变量，无论内核最初是由主机还是设备运行时启动。同样地，所有内核都将具有相同的视图 __constant__s 如在模块范围内声明的那样。

5.6.4.2.2.1.2. 纹理和表面#

设备运行时不允许从设备代码中创建或销毁纹理或表面对象。从主机创建的纹理和表面对象可以在设备上自由使用和传递。无论在何处创建，动态创建的纹理对象始终有效，并且可以从父内核传递给子内核。

注

设备运行时不支持从设备启动的内核中的旧模块范围（即计算能力 2.0 或 Fermi 样式）纹理和表面。模块范围（传统）纹理可以从主机创建并在设备代码中使用，就像任何内核一样，但只能由顶级内核（即从主机启动的内核）使用。

5.6.4.2.2.1.3. 共享内存变量声明#

在 CUDA C++ 中，共享内存可以声明为静态大小的文件范围或函数范围的变量，也可以声明为 extern 变量的大小由内核调用者在运行时通过启动配置参数确定。两种类型的声明在设备运行时均有效。

__global__ void permute(int n, int *data) {
   extern __shared__ int smem[];
   if (n <= 1)
       return;

   smem[threadIdx.x] = data[threadIdx.x];
   __syncthreads();

   permute_data(smem, n);
   __syncthreads();

   // 写回 GMEM，因为我们无法将 SMEM 传给孩子。
   data[threadIdx.x] = smem[threadIdx.x];
   __syncthreads();

   if (threadIdx.x == 0) {
       permute<<< 1, 256, n/2*sizeof(int) >>>(n/2, data);
       permute<<< 1, 256, n/2*sizeof(int) >>>(n/2, data+n/2);
   }
}

void host_launch(int *data) {
    permute<<< 1, 256, 256*sizeof(int) >>>(256, data);
}
5.6.4.2.2.1.4. 常量内存#

不能从设备修改常量。它们只能从主机修改，但是当存在在其生命周期内的任何点访问该常量的并发网格时，从主机修改常量的行为是未定义的。

5.6.4.2.2.1.5. 符号地址#

设备端符号（即那些标记为 __device__）可以简单地通过以下方式从内核中引用 & 运算符，因为所有全局范围的设备变量都位于内核的可见地址空间中。这也适用于 __constant__ 符号，尽管在这种情况下指针将引用只读数据。

由于设备端符号可以直接引用，那些引用符号的 CUDA 运行时 API（例如， cudaMemcpyToSymbol() 或 cudaGetSymbolAddress()) 是不必要的，并且不受设备运行时支持。这意味着即使在子内核启动之前，也无法在正在运行的内核中更改常量数据，作为参考 __constant__ 空间是只读的。

5.6.4.3. SM Id 和 Warp Id#

请注意，在 PTX 中 %smid 或 %warpid 被定义为易失值。设备运行时可以将线程块重新调度到不同的 SM 上，以便更有效地管理资源。因此，依赖于 %smid 或 %warpid 在线程或线程块的生命周期内保持不变。

5.6.4.7. API 错误和启动失败#

与 CUDA 运行时一样，任何函数都可能返回错误代码。最后返回的错误代码会被记录并可以通过 cudaGetLastError() 打电话。每个线程都会记录错误，以便每个线程都可以识别它生成的最新错误。错误代码类型为 cudaError_t.

与主机端启动类似，设备端启动可能会因多种原因（无效参数等）而失败。用户必须调用 cudaGetLastError() 确定启动是否生成错误，但是启动后没有错误并不意味着子内核成功完成。

对于设备端异常，例如访问无效地址，子网格中的错误将返回给主机。

5.6.4.8. 设备运行时流#

CUDA 设备运行时公开特殊的命名流，这些流为从设备启动的内核和图形提供特定的行为。与设备图启动相关的命名流记录在 设备启动。另外两个可用于 CUDA 设备运行时中的内核和 memcpy 操作的命名流是 cudaStreamTailLaunch 或 cudaStreamTailLaunch。本节记录了这些命名流的具体行为。

命名和未命名（NULL）流都可以从设备运行时获得。流句柄可能不会传递到父网格或子网格。换句话说，流应该被视为创建它的网格私有的。

设备不支持主机端 NULL 流的跨流屏障语义（详细信息请参见下文）。为了保持与主机运行时的语义兼容性，所有设备流必须使用 cudaStreamCreateWithFlags() API，通过 cudaStreamNonBlocking 标志。的 cudaStreamCreate() API 在 CUDA 设备运行时中不可用。

As cudaStreamSynchronize() 或 cudaStreamQuery() 设备运行时不支持。内核启动到 cudaStreamTailLaunch 当应用程序需要知道流启动的子内核已完成时，应使用流。

5.6.4.8.1. 隐式（NULL）流#

在主机程序中，未命名（NULL）流具有与其他流的附加屏障同步语义（请参阅 阻塞流和非阻塞流以及默认流 了解详情）。设备运行时提供一个隐式的、未命名的流，在线程块中的所有线程之间共享，但所有命名流都必须使用 cudaStreamNonBlocking 标志，启动到 NULL 流中的工作不会插入对任何其他流（包括其他线程块的 NULL 流）中待处理工作的隐式依赖关系。

5.6.4.8.2. 即发即忘流#

即发即忘命名流 (cudaStreamFireAndForget）允许用户以更少的样板启动即发即忘的工作，并且没有流跟踪开销。它在功能上与每次启动创建一个新流并启动到该流中相同，但速度更快。

即发即忘启动会立即安排启动，而不依赖于先前启动的网格的完成情况。除了通过父网格末尾的隐式同步之外，任何其他网格启动都不能依赖于即发即弃启动的完成。因此，在父网格的即发即弃工作完成之前，尾部启动或父网格流中的下一个网格不会启动。

// 在这个例子中，C2的启动不会等待C1的完成
__global__ void P( ... ) {
   C1<<< ... , cudaStreamFireAndForget >>>( ... );
   C2<<< ... , cudaStreamFireAndForget >>>( ... );
}

即发即弃流不能用于记录或等待事件。尝试这样做会导致 cudaErrorInvalidValue。编译时不支持即发即弃流 CUDA_FORCE_CDP1_IF_SUPPORTED 定义的。使用即发即弃流需要在 64 位模式下进行编译。

5.6.4.8.3. 尾部发射流#

尾部启动名为stream (cudaStreamTailLaunch）允许网格在完成后安排新网格的启动。应该可以使用尾部发射来实现与尾部发射相同的功能 cudaDeviceSynchronize() 在大多数情况下。

每个网格都有自己的尾部发射流。网格启动的所有非尾部启动工作在尾部流启动之前都会隐式同步。 IE。直到父网格以及父网格向普通流或每线程或即发即弃流启动的所有工作完成后，父网格的尾部启动才会启动。如果两个网格被启动到同一个网格的尾部启动流，则后面的网格不会启动，直到前面的网格及其所有后代工作完成为止。

// 在此示例中，C2 仅在 C1 完成后启动。
__global__ void P( ... ) {
   C1<<< ... , cudaStreamTailLaunch >>>( ... );
   C2<<< ... , cudaStreamTailLaunch >>>( ... );
}

在父级网格完成所有工作之前，启动到尾部启动流中的网格不会启动，包括父级在所有非尾部启动流中启动的所有其他网格（及其后代），包括尾部启动后执行或启动的工作。

// 在此示例中，C 仅在 X、F 和 P 全部完成后才会启动。
__global__ void P( ... ) {
   C<<< ... , cudaStreamTailLaunch >>>( ... );
   X<<< ... , cudaStreamPerThread >>>( ... );
   F<<< ... , cudaStreamFireAndForget >>>( ... )
}

在父网格的尾部启动工作完成之前，不会启动父网格流中的下一个网格。换句话说，尾部启动流的行为就好像它被插入到其父网格和其父网格流中的下一个网格之间。

// 在此示例中，P2 仅在 C 完成后启动。
__global__ void P1( ... ) {
   C<<< ... , cudaStreamTailLaunch >>>( ... );
}

__global__ void P2( ... ) {
}

int main ( ... ) {
   ...
   P1<<< ... >>>( ... );
   P2<<< ... >>>( ... );
   ...
}

每个网格仅获得一个尾部发射流。要尾部启动并发网格，可以像下面的示例一样完成。

// 在此示例中，C1 和 C2 将在 P 完成后同时启动
__global__ void T( ... ) {
   C1<<< ... , cudaStreamFireAndForget >>>( ... );
   C2<<< ... , cudaStreamFireAndForget >>>( ... );
}

__global__ void P( ... ) {
   ...
   T<<< ... , cudaStreamTailLaunch >>>( ... );
}

尾部启动流不能用于记录或等待事件。尝试这样做会导致 cudaErrorInvalidValue。编译时不支持尾部启动流 CUDA_FORCE_CDP1_IF_SUPPORTED 定义的。尾部启动流的使用要求编译为 64 位模式。

5.6.4.9. ECC 错误#

CUDA 内核中的代码无法获得 ECC 错误通知。一旦整个启动树完成，主机端就会报告 ECC 错误。执行嵌套程序期间出现的任何 ECC 错误都将生成异常或继续执行（取决于错误和配置）。
