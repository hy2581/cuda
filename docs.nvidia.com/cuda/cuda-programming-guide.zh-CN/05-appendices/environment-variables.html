5.2. CUDA 环境变量#

以下部分列出了 CUDA 环境变量。与多进程服务 (MPS) 相关的内容记录在 GPU部署与管理指南.

5.2.1. 设备枚举和属性#

5.2.1.1. CUDA_VISIBLE_DEVICES#

环境变量控制哪些 GPU 设备对 CUDA 应用程序可见以及它们的枚举顺序。

  • 如果未设置该变量，则所有 GPU 设备均可见。

  • 如果该变量设置为空字符串，则没有 GPU 设备可见。

可能的值：以逗号分隔的 GPU 标识符序列。

GPU 标识符提供为：

  • 整数索引：这些对应于系统中 GPU 的序号，由下式确定 nvidia-smi，从0开始。例如设置 CUDA_VISIBLE_DEVICES=2,1 使设备 0 不可见，并在设备 1 之前枚举设备 2。

    • 如果遇到无效索引，则仅可见列表中索引出现在无效索引之前的设备。例如，设置 CUDA_VISIBLE_DEVICES=0,2,-1,1 使设备 0 和 2 可见，而设备 1 不可见，因为它出现在无效索引之后 -1.

  • GPU UUID 字符串：这些应遵循与给出的格式相同的格式 nvidia-smi -L，例如 GPU-8932f937-d72c-4106-c12f-20bd9faed9f6。然而，为了方便起见，允许使用缩写形式；只需从 GPU UUID 的开头指定足够的数字即可唯一标识目标系统中的该 GPU。例如， CUDA_VISIBLE_DEVICES=GPU-8932f937 可能是引用上述 GPU UUID 的有效方法，假设系统中没有其他 GPU 共享此前缀。

  • 多实例 GPU (MIG) support: MIG-<GPU-UUID>/<GPU instance ID>/<compute instance ID>。例如， MIG-GPU-8932f937-d72c-4106-c12f-20bd9faed9f6/1/2。仅支持单个 MIG 实例枚举。

返回的设备计数 cudaGetDeviceCount() API 仅包含可见设备，因此使用整数设备标识符的 CUDA API 仅支持 [0，可见设备计数 - 1] 范围内的序数。 GPU 设备的枚举顺序决定序数值。例如，与 CUDA_VISIBLE_DEVICES=2,1, 呼叫 cudaSetDevice(0) 会将设备 2 设置为当前设备，因为它首先被枚举并分配序数 0。 cudaGetDevice(&device_ordinal) 之后还将设置 device_ordinal 为 0，对应设备 2。

warp:

nvidia-smi -L # 获取 GPU UUID 列表
CUDA_VISIBLE_DEVICES=0,1
CUDA_VISIBLE_DEVICES=GPU-8932f937-d72c-4106-c12f-20bd9faed9f6
CUDA_VISIBLE_DEVICES=MIG-GPU-8932f937-d72c-4106-c12f-20bd9faed9f6/1/2

5.2.1.2. CUDA_DEVICE_ORDER#

环境变量控制 CUDA 枚举可用设备的顺序。

可能的值:

  • FASTEST_FIRST：使用简单的启发式（默认）从最快到最慢的方式枚举可用设备。

  • PCI_BUS_ID：可用的设备按 PCI 总线 ID 按升序排列。 PCI 总线 ID 可以通过以下方式获取 nvidia-smi --query-gpu=name,pci.bus_id.

warp:

CUDA_DEVICE_ORDER=FASTEST_FIRST
CUDA_DEVICE_ORDER=PCI_BUS_ID
nvidia-smi --query-gpu=name,pci.bus_id # 获取 PCI 总线 ID 列表

5.2.1.3. CUDA_MANAGED_FORCE_DEVICE_ALLOC#

环境变量如何改变 统一内存 物理存储在多 GPU 系统中。

可能的值：数值，零或非零。

  • 非零值：强制驱动程序使用设备内存进行物理存储。支持托管内存的进程中使用的所有设备都必须是对等兼容的。否则， cudaErrorInvalidDevice 被返回。

  • 0：默认行为。

warp:

CUDA_MANAGED_FORCE_DEVICE_ALLOC=0
CUDA_MANAGED_FORCE_DEVICE_ALLOC=1 # 强制设备内存

5.2.2. 即时编译#

5.2.2.1. CUDA_CACHE_DISABLE#

环境变量控制磁盘上的行为 即时 (JIT) 编译 缓存。 禁用 JIT 缓存会在每次执行 CUDA 应用程序时强制 PTX 对其进行 CUBIN 编译，除非在二进制文件中找到正在运行的架构的 CUBIN 代码。

禁用 JIT 缓存会增加应用程序在初始执行期间的加载时间。但是，它对于减少应用程序的磁盘空间以及诊断驱动程序版本或构建标志之间的差异非常有用。

可能的值:

  • 1：禁用 PTX JIT 缓存。

  • 0：启用 PTX JIT 缓存（默认）。

warp:

CUDA_CACHE_DISABLE=1 # 禁用缓存
CUDA_CACHE_DISABLE=0 # 启用缓存

5.2.2.2. CUDA_CACHE_PATH#

环境变量指定了目录路径 即时 (JIT) 编译 cache.

可能的值：缓存目录的绝对路径（具有适当的访问权限）。默认值为：

  • 在 Windows 上， %APPDATA%\NVIDIA\ComputeCache

  • 在Linux上， ~/.nv/ComputeCache

warp:

CUDA_CACHE_PATH=~/tmp

5.2.2.3. CUDA_CACHE_MAXSIZE#

环境变量指定 即时 (JIT) 编译 缓存大小（以字节为单位）。超过此大小的二进制文件不会被缓存。如果需要，旧的二进制文件将从缓存中逐出，为新的二进制文件腾出空间。

可能的值：字节数。默认值为：

  • 在桌面/服务器平台上， 1073741824 （1 GiB）

  • 在嵌入式平台上， 268435456 (256 MiB)

4294967296 (4 GiB) 是最大大小。

warp:

CUDA_CACHE_MAXSIZE=268435456 # 256 MiB

5.2.2.4. CUDA_FORCE_PTX_JIT 或 CUDA_FORCE_JIT#

环境变量指示 CUDA 驱动程序忽略应用程序中嵌入的任何 CUBIN 并执行 即时 (JIT) 编译 而是嵌入的 PTX 代码。

强制 JIT 编译会增加应用程序在初始执行期间的加载时间。但是，它可用于验证 PTX 代码是否嵌入到应用程序中以及其即时编译是否正常运行。 这确保了 向前兼容性 与未来的架构。

CUDA_FORCE_PTX_JIT overrides CUDA_FORCE_JIT.

可能的值:

  • 1：强制 PTX JIT 编译。

  • 0：默认行为。

warp:

CUDA_FORCE_PTX_JIT=1

5.2.2.5. CUDA_DISABLE_PTX_JIT 或 CUDA_DISABLE_JIT#

环境变量禁用 即时 (JIT) 编译 嵌入式 PTX 代码并使用应用程序中嵌入的兼容 CUBIN。

如果内核没有嵌入的二进制代码，或者嵌入的二进制代码是为不兼容的体系结构编译的，则内核将无法加载。这些环境变量可用于验证应用程序是否具有为每个内核生成的兼容 CUBIN 代码。请参阅 二进制兼容性 部分了解更多详细信息。

CUDA_DISABLE_PTX_JIT overrides CUDA_DISABLE_JIT.

可能的值:

  • 1：禁用 PTX JIT 编译。

  • 0：默认行为。

warp:

CUDA_DISABLE_PTX_JIT=1

5.2.2.6. CUDA_FORCE_PRELOAD_LIBRARIES#

环境变量会影响所需库的预加载 NVVM 和 即时 (JIT) 编译.

可能的值:

  • 1：这会强制驱动程序预加载所需的库 NVVM 和 即时 (JIT) 编译 在初始化期间。这会增加内存占用以及 CUDA 驱动程序初始化所需的时间。设置此环境变量对于避免涉及多个线程的某些死锁情况是必要的。

  • 0：默认行为。

warp:

CUDA_FORCE_PRELOAD_LIBRARIES=1

5.2.3. 执行#

5.2.3.1. CUDA_LAUNCH_BLOCKING#

环境变量指定是否禁用或启用异步内核启动。

禁用异步执行会导致执行速度变慢，但对于调试很有用。它强制 GPU 工作从 CPU 的角度同步运行。这允许在触发 CUDA API 错误的确切 API 调用时观察到 CUDA API 错误，而不是在执行后期。同步执行对于调试目的很有用。

可能的值:

  • 1：禁用异步执行。

  • 0：异步执行（默认）。

warp:

CUDA_LAUNCH_BLOCKING=1

5.2.3.2. CUDA_DEVICE_MAX_CONNECTIONS#

环境变量控制并发计算和复制引擎连接（工作队列）的数量，将两者设置为指定值。 如果独立的 GPU 任务（即从不同 CUDA 流启动的内核或复制操作）映射到同一工作队列，则会创建错误的依赖关系，这可能导致 GPU 工作序列化，因为使用相同的底层资源。 为了减少这种错误依赖关系的可能性，建议通过此环境变量控制的工作队列计数大于或等于每个上下文的活动 CUDA 流的数量。

设置此环境变量还会修改复制连接的数量，除非通过显式设置 CUDA_DEVICE_MAX_COPY_CONNECTIONS 环境变量。

可能的值: 1 或 32 连接数，默认为 8 （假设没有 MPS）

warp:

CUDA_DEVICE_MAX_CONNECTIONS=16

5.2.3.3. CUDA_DEVICE_MAX_COPY_CONNECTIONS#

环境变量控制复制操作中涉及的并发复制连接（工作队列）的数量。 它仅影响以下设备 计算能力 8.0及以上。

CUDA_DEVICE_MAX_COPY_CONNECTIONS 覆盖通过设置的复制连接的值 CUDA_DEVICE_MAX_CONNECTIONS，如果两者都设置了。

可能的值: 1 或 32 连接数，默认为 8 （假设没有 MPS）

warp:

CUDA_DEVICE_MAX_COPY_CONNECTIONS=16

5.2.3.4. CUDA_SCALE_LAUNCH_QUEUES#

该环境变量指定可用于启动工作的队列（命令缓冲区）大小的比例因子，即可以在设备上排队的待处理内核或主机/设备复制操作的总数。

可能的值: 0.25x, 0.5x, 2x, 4x

  • 除以下以外的任何值 0.25x, 0.5x, 2x 或 4x 被解释为 1x.

warp:

CUDA_SCALE_LAUNCH_QUEUES=2x

5.2.3.5. CUDA_GRAPHS_USE_NODE_PRIORITY#

环境变量控制 CUDA 图相对于它从启动它的流继承的流优先级的执行优先级。

CUDA_GRAPHS_USE_NODE_PRIORITY 覆盖 cudaGraphInstantiateFlagUseNodePriority 图实例化上的标志。

可能的值:

  • 0：继承图形启动到的流的优先级（默认）。

  • 1：尊重每个节点的启动优先级。 CUDA 运行时将节点级优先级视为准备运行的图形节点的调度提示。

warp:

CUDA_GRAPHS_USE_NODE_PRIORITY=1

5.2.3.6. CUDA_DEVICE_WAITS_ON_EXCEPTION#

环境变量控制发生异常（错误）时 CUDA 应用程序的行为。

启用后，当发生设备端异常时，CUDA 应用程序将停止并等待，从而允许调试器，例如 cuda-gdb，在进程退出或继续之前附加以检查实时 GPU 状态。

可能的值:

  • 0：默认行为。

  • 1：设备异常时停止。

warp:

CUDA_DEVICE_WAITS_ON_EXCEPTION=1

5.2.3.7. CUDA_DEVICE_DEFAULT_PERSISTING_L2_CACHE_PERCENTAGE_LIMIT#

该环境变量控制 GPU L2 缓存的默认“预留”部分，保留用于 持久访问，表示为 L2 大小的百分比。

它与支持持久 L2 缓存的 GPU 相关，特别是具有 计算能力 使用时8.0或更高 CUDA 多进程服务 (MPS)。必须在启动 CUDA MPS Control Daemon 之前（即运行之前）设置环境变量 nvidia-cuda-mps-control -d command.

可能的值：0 到 100 之间的百分比值，默认为 0。

warp:

CUDA_DEVICE_DEFAULT_PERSISTING_L2_CACHE_PERCENTAGE_LIMIT=25 # 25%

5.2.3.8. CUDA_DISABLE_PERF_BOOST#

在 Linux 主机上，将此环境变量设置为 1 可防止提升设备性能状态，而是可以根据各种启发法隐式选择 pstate。 此选项可潜在地用于降低功耗，但由于动态性能状态选择，在某些情况下可能会导致更高的延迟。

warp:

CUDA_DISABLE_PERF_BOOST=1 # perf boost 已禁用，仅限 Linux。
CUDA_DISABLE_PERF_BOOST=0 # 默认行为

5.2.3.9. CUDA_AUTO_BOOST [[deprecated]]#

环境变量影响 GPU 时钟“自动提升”行为，即动态时钟提升。 它覆盖了“自动增强”选项 nvidia-smi 工具，即 nvidia-smi --auto-boost-default=0.

注

此环境变量已弃用。强烈建议使用 nvidia-smi --applications-clocks=<memory,graphics> 或 NVML API 而不是 CUDA_AUTO_BOOST 环境变量。

5.2.4. 模块加载#

5.2.4.1. CUDA_MODULE_LOADING#

环境变量会影响 CUDA 运行时加载模块的方式，特别是它初始化设备代码的方式。

可能的值:

  • DEFAULT：默认行为，相当于 LAZY.

  • LAZY：特定内核的加载被延迟，直到 CUDA 函数句柄为止， CUfunc，使用提取 cuModuleGetFunction() 或 cuKernelGetFunction() API 调用。在这种情况下，当加载 CUBIN 中的第一个内核或访问 CUBIN 中的第一个变量时，会加载来自 CUBIN 的数据。

    • 驱动程序在第一次调用内核时加载所需的代码；后续调用不会产生额外的开销。这减少了启动时间和 GPU 内存占用。

  • EAGER：在程序初始化时完全加载 CUDA 模块和内核。 CUBIN、FATBIN 或 PTX 文件中的所有内核和数据都完全加载到相应的 cuModuleLoad* 或 cuLibraryLoad* 驱动程序 API 调用。

    • 更高的启动时间和 GPU 内存占用。内核启动开销是可以预测的。

warp:

CUDA_MODULE_LOADING=EAGER
CUDA_MODULE_LOADING=LAZY

5.2.4.2. CUDA_MODULE_DATA_LOADING#

环境变量会影响 CUDA 运行时加载与模块关联的数据的方式。

这是对以内核为中心的设置的补充 CUDA_MODULE_LOADING。该环境变量不影响 LAZY 或 EAGER 加载内核。 数据加载行为继承自 CUDA_MODULE_LOADING 如果这个环境变量没有设置。

可能的值:

  • DEFAULT：默认行为，相当于 LAZY.

  • LAZY：模块数据的加载被延迟到CUDA函数句柄为止， CUfunc，为必填项。在这种情况下，当加载 CUBIN 中的第一个内核或访问 CUBIN 中的第一个变量时，会加载来自 CUBIN 的数据。

    • 延迟数据加载可能需要上下文同步，这会减慢并发执行速度。

  • EAGER：CUBIN、FATBIN 或 PTX 文件中的所有数据都完全加载到相应的 cuModuleLoad* 或 cuLibraryLoad* API 调用。

warp:

CUDA_MODULE_DATA_LOADING=EAGER

5.2.4.3. CUDA_BINARY_LOADER_THREAD_COUNT#

设置加载设备二进制文件时要使用的 CPU 线程数。当设置为 0 时，使用的 CPU 线程数设置为默认值 1。

可能的值:

  • 要使用的整数线程数。默认为 0，即使用 1 个线程。

warp:

CUDA_BINARY_LOADER_THREAD_COUNT=4

5.2.5. CUDA错误日志管理#

5.2.5.1. CUDA_LOG_FILE#

环境变量指定描述性错误日志消息发生时将打印的位置 对于返回错误的受支持 CUDA API 调用。

例如，如果尝试启动具有无效网格配置的内核，例如 kernel<<<1, dim3(1,1,128)>>>(...)，该内核将无法启动并且 cudaGetLastError() 将返回一个泛型 invalid configuration argument error.
如果 CUDA_LOG_FILE 设置环境变量后，用户可以在日志中看到以下描述性错误消息： [CUDA][E] Block Dimensions (1,1,128) include one or more values that exceed the device limit of (1024,1024,64) 并轻松确定块的指定 z 维度无效。参见 错误日志管理 了解更多详情。

可能的值: stdout, stderr，或有效的文件路径（具有适当的访问权限）

warp:

CUDA_LOG_FILE=stdout
CUDA_LOG_FILE=/tmp/dbg_cuda_log
