5.4.1.2.1. __shared__ 内存#

__shared__ 内存变量可以具有在编译时确定的静态大小，也可以具有在内核启动时确定的动态大小。请参阅 内核配置 有关在运行时指定共享内存大小的详细信息，请参阅部分。

共享内存限制：

  • 具有动态大小的变量必须声明为外部数组或指针。

  • 具有静态大小的变量不能在其声明中初始化。

下面的例子说明了如何声明和大小 __shared__ variables:

extern __shared__ char dynamic_smem_pointer[];
// 外部 __shared__ char* 动态_smem_pointer;替代语法

__global__ void kernel() { // 或 __device__ 函数
    __shared__ int smem_var1[4];                  // 静态尺寸
    auto smem_var2 = (int*) dynamic_smem_pointer; // 动态尺寸
}

int main() {
    size_t shared_memory_size = 16;
    kernel<<<1, 1, shared_memory_size>>>();
    cudaDeviceSynchronize();
}

5.4.1.2.2. __managed__ 内存#

__managed__ 变量有以下限制：

  • 的地址 __managed__ 变量不是常量表达式。

  • A __managed__ 变量不得具有引用类型 T&.

  • a 的地址或值 __managed__ 当 CUDA 运行时可能不处于有效状态时，不应使用变量，包括以下情况：

    • 在静态/动态初始化或销毁对象时 static 或 thread_local 储存期限。

    • 在之后执行的代码中 exit() 已被调用。例如，一个函数标记为 __attribute__((destructor)).

    • 在 CUDA 运行时可能未初始化时执行的代码中。例如，一个函数标记为 __attribute__((constructor)).

  • A __managed__ 变量不能用作无括号的 id 表达式参数 decltype() expression.

  • __managed__ 变量具有与指定的相同的连贯性和一致性行为 动态分配的托管内存.

  • 另请参阅以下限制： 局部变量.

以下是合法和非法使用的示例 __managed__ variables:

#include <cassert>

__device__ __managed__ int global_var = 10; // OK

int* ptr = &global_var;                     // 错误：在静态初始化中使用托管变量

struct MyStruct1 {
    int field;
    MyStruct1() : field(global_var) {};
};

struct MyStruct2 {
    ~MyStruct2() { global_var = 10; }
};

MyStruct1 temp1; // 错误：在动态初始化中使用托管变量

MyStruct2 temp2; // 错误：在析构函数中使用托管变量
                 // 具有静态存储持续时间的对象

__device__ __managed__ const int const_var = 10;         // 错误：const 限定类型

__device__ __managed__ int&      reference = global_var; // 错误：引用类型

template <int* Addr>
struct MyStruct3 {};

MyStruct3<&global_var> temp;     // 错误：托管变量的地址不是常量表达式

__global__ void kernel(int* ptr) {
    assert(ptr == &global_var);  // OK
    global_var = 20;             // OK
}

int main() {
    int* ptr = &global_var;      // OK
    kernel<<<1, 1>>>(ptr);
    cudaDeviceSynchronize();
    global_var++;                // OK
    decltype(global_var) var1;   // 错误：托管变量用作 decltype 的无括号参数

    decltype((global_var)) var2; // OK
}

5.4.1.3. 内联说明符#

以下说明符可用于控制内联 __host__ 或 __device__ functions:

  • __noinline__: 指示 nvcc 不要内联该函数。

  • __forceinline__： 力量 nvcc 将函数内联到单个翻译单元中。

  • __inline_hint__：使用时启用跨翻译单元的积极内联 链接时间优化.

这些说明符是互斥的。

5.4.1.4. __restrict__ 指针#

nvcc 通过以下方式支持受限指针 __restrict__ keyword.

当两个或多个指针引用重叠的内存区域时，就会发生指针别名。这可能会抑制代码重新排序和公共子表达式消除等优化。

限制限定指针是程序员的一个承诺，即在指针的生命周期内，它指向的内存只能通过该指针访问。这允许编译器执行更积极的优化。

  • 所有访问设备函数的线程仅从中读取；或

  • 最多有一个线程对其进行写入，并且没有其他线程从中读取。

以下示例说明了别名问题，并演示了使用受限指针如何帮助编译器减少指令数量：

__device__
void device_function(const float* a, const float* b, float* c) {
    c[0] = a[0] * b[0];
    c[1] = a[0] * b[0];
    c[2] = a[0] * b[0] * a[1];
    c[3] = a[0] * a[1];
    c[4] = a[0] * b[0];
    c[5] = b[0];
    ...
}

因为指针 a, b, 和 c 可能是别名，任何直写 c 可以修改的元素 a 或 b。为了保证功能正确性，编译器无法加载 a[0] 或 b[0] 存入寄存器，将它们相乘，并将结果存储在两个寄存器中 c[0] 或 c[1]。这是因为如果以下情况，结果将与抽象执行模型不同： a[0] 或 c[0] 都在同一个地点。编译器无法利用公共子表达式。同样，编译器无法重新排序计算 c[4] 的计算 c[0] 或 c[1] 因为前面的写入 c[3] 可以改变计算的输入 c[4].

通过声明 a, b, 和 c 作为受限指针，程序员通知编译器这些指针没有别名。这意味着写入 c 永远不会覆盖的元素 a 或 b。这将函数原型更改如下：

__device__
void device_function(const float* __restrict__ a, const float* __restrict__ b, float* __restrict__ c);

请注意，必须限制所有指针参数才能使编译器优化器有效。随着添加 __restrict__ 关键字，编译器可以随意重新排序和执行公共子表达式消除，同时保持与抽象执行模型相同的功能。

__device__
void device_function(const float* __restrict__ a, const float* __restrict__ b, float* __restrict__ c) {
    float t0 = a[0];
    float t1 = b[0];
    float t2 = t0 * t1;
    float t3 = a[1];
    c[0]     = t2;
    c[1]     = t2;
    c[4]     = t2;
    c[2]     = t2 * t3;
    c[3]     = t0 * t3;
    c[5]     = t1;
    ...
}

请参阅示例 编译器资源管理器.

结果是减少了内存访问和计算的数量，并通过缓存负载和寄存器中的公共子表达式带来的寄存器压力的增加来平衡。

由于寄存器压力是许多 CUDA 代码中的一个关键问题，因此使用受限指针会减少占用，从而对性能产生负面影响。

访问 __global__ function const 指针标记为 __restrict__ 被编译为只读缓存加载，类似于 PTX ld.global.nc 或 __ldg() 低级加载和存储函数 instructions.

__global__
void kernel1(const float* in, float* out) {
    *out = *in; // PTX：ld.global
}

__global__
void kernel2(const float* __restrict__ in, float* out) {
    *out = *in;  // PTX：ld.global.nc
}

请参阅示例 编译器资源管理器.

5.4.1.5. __grid_constant__ 参数#

注释一个 __global__ 函数参数与 __grid_constant__ 防止编译器创建参数的每线程副本。相反，网格中的所有线程将通过单个地址访问参数，这可以提高性能。

__grid_constant__ 参数具有以下属性：

  • 它具有内核的生命周期。

  • 它是单个内核私有的，这意味着来自其他网格（包括子网格）的线程无法访问该对象。

  • 内核中的所有线程都看到相同的地址。

  • 它是只读的。修改一个 __grid_constant__ 对象或其任何子对象，包括 mutable 成员，是未定义的行为。

Requirements:

  • 内核参数注释为 __grid_constant__ 必须有 const- 限定的非引用类型。

  • 所有函数声明必须与任何一致 __grid_constant__ parameters.

  • 函数模板特化必须与主模板声明相匹配 __grid_constant__ parameters.

  • 函数模板实例化还必须与主模板声明相匹配 __grid_constant__ parameters.

示例：

struct MyStruct {
    int         x;
    mutable int y;
};

__device__ void external_function(const MyStruct&);

__global__ void kernel(const __grid_constant__ MyStruct s) {
    // s.x++； // 编译错误：试图修改只读内存
    // y++； // 未定义行为：尝试修改只读内存

    // 编译器不会创建“s”的每线程本地副本：
    external_function(s);
}

请参阅示例 编译器资源管理器.

5.4.2.1. 主机编译器类型扩展#

只要主机编译器支持，CUDA 就允许使用非标准算术类型。支持以下类型：

  • 128位整数类型 __int128.

    • 当主机编译器定义了 Linux 上支持 __SIZEOF_INT128__ macro.

  • 128 位浮点类型 __float128 或 _Float128 可在计算能力 10.0 及更高版本的 GPU 设备上使用。的常数表达式 __float128 编译器可以以较低精度的浮点表示形式处理类型。

  • _Complex types 仅在主机代码中受支持。

5.4.2.2. 内置变量#

用于指定和检索沿 x、y 和 z 维度的网格和块的内核配置的值是类型 dim3。用于获取块和线程索引的变量是类型 uint3。两者都 dim3 或 uint3 是由三个无符号值组成的简单结构，名为 x, y, 和 z。在 C++11 及更高版本中，所有组件的默认值 dim3 is 1.

内置设备专用变量：

  • dim3 gridDim：包含网格的维度，即沿 x、y 和 z 维度的线程块数量。

  • dim3 blockDim：包含线程块的维度，即沿 x、y 和 z 维度的线程数。

  • uint3 blockIdx：包含网格内沿 x、y 和 z 维度的块索引。

  • uint3 threadIdx：包含块内沿 x、y 和 z 维度的线程索引。

  • int warpSize：运行时值，定义为warp 中的线程数，通常 32。另请参阅 Warp 与 SIMT 用于定义warp。

任何呼叫 __global__ 函数必须指定一个 执行配置 为了那个电话。此执行配置定义了将用于在设备上执行功能的网格和块的尺寸，以及相关联的 stream.

执行配置是通过在表格中插入表达式来指定的 <<<grid_dim, block_dim, dynamic_smem_bytes, stream>>> 位于函数名称和带括号的参数列表之间，其中：

  • grid_dim 属于类型 dim3 并指定网格的尺寸和大小，使得 grid_dim.x * grid_dim.y * grid_dim.z 等于正在启动的区块数量；

  • block_dim 属于类型 dim3 并指定每个块的尺寸和大小，使得 block_dim.x * block_dim.y * block_dim.z 等于每个块的线程数；

  • dynamic_smem_bytes 是一个可选的 size_t 默认为零的参数。它指定除了静态分配的内存之外，为此调用每个块动态分配的共享内存中的字节数。该内存被使用 extern __shared__ 数组（参见 __共享__内存).

  • stream 属于类型 cudaStream_t （指针）并指定关联的流。 stream 是一个可选参数，默认为 NULL.

以下示例显示了内核函数的声明和调用：

__global__ void kernel(float* parameter);

kernel<<<grid_dim, block_dim, dynamic_smem_bytes>>>(parameter);

执行配置的参数在实际函数的参数之前进行评估。

函数调用失败，如果 grid_dim 或 block_dim 超出了设备允许的最大尺寸，如中指定的 计算能力，或者如果 dynamic_smem_bytes 大于考虑静态分配内存后的可用共享内存。

5.4.3.1. 线程块簇#

计算能力 9.0 及更高版本允许用户指定编译时线程块簇尺寸，以便内核可以使用 簇层次结构 在CUDA 中。编译时簇维度可以使用以下方式指定 __cluster_dims__ 属性具有以下语法： __cluster_dims__([x, [y, [z]]])。下面的示例显示 X 维度上的编译时簇大小为 2，Y 和 Z 维度上的编译时簇大小为 1。

__global__ void __cluster_dims__(2, 1, 1) kernel(float* parameter);

默认形式为 __cluster_dims__() 指定内核将作为网格集群启动。如果未指定集群维度，用户可以在启动时指定。未能在启动时指定维度将导致启动时错误。

线程块簇的尺寸也可以在运行时指定，并且可以使用以下命令启动带有簇的内核 cudaLaunchKernelEx API。此 API 采用类型的配置参数 cudaLaunchConfig_t、内核函数指针和内核参数。下面的示例显示了运行时内核配置。

__global__ void kernel(float parameter1, int parameter2) {}

int main() {
    cudaLaunchConfig_t config = {0};
    // 网格维度不受集群启动影响，仍然枚举
    // 使用块的数量。
    // 网格尺寸应该是簇大小的倍数。
    config.gridDim          = dim3{4};  // 4块
    config.blockDim         = dim3{32}; // 每块 32 个线程
    config.dynamicSmemBytes = 1024;     // 1 KB

    cudaLaunchAttribute attribute[1];
    attribute[0].id               = cudaLaunchAttributeClusterDimension;
    attribute[0].val.clusterDim.x = 2; // X 维度上的簇大小
    attribute[0].val.clusterDim.y = 1;
    attribute[0].val.clusterDim.z = 1;
    config.attrs    = attribute;
    config.numAttrs = 1;

    float parameter1 = 3.0f;
    int   parameter2 = 4;
    cudaLaunchKernelEx(&config, kernel, parameter1, parameter2);
}

5.4.3.2. 发射范围#

正如在 内核启动和占用 部分，使用更少的寄存器允许更多线程和线程块驻留在多处理器上，从而提高性能。

因此，编译器使用启发式方法来最小化寄存器的使用，同时保持 寄存器溢出 并将指令数降至最低。应用程序可以选择通过以使用指定的启动边界的形式向编译器提供附加信息来帮助这些启发式方法 __launch_bounds__() a 的定义中的限定符 __global__ function:

__global__ void
__launch_bounds__(maxThreadsPerBlock, minBlocksPerMultiprocessor, maxBlocksPerCluster)
MyKernel(...) {
    ...
}

  • maxThreadsPerBlock 指定应用程序启动时每块的最大线程数 MyKernel();它编译为 .maxntid PTX 指令。

  • minBlocksPerMultiprocessor 是可选的，指定每个多处理器所需的最小驻留块数；它编译为 .minnctapersm PTX 指令。

  • maxBlocksPerCluster 是可选的，指定应用程序启动时每个集群所需的最大线程块数 MyKernel();它编译为 .maxclusterrank PTX 指令。

如果指定了启动边界，编译器首先得出上限， L，关于内核应使用的寄存器的数量。这确保了 minBlocksPerMultiprocessor 块（或单个块，如果 minBlocksPerMultiprocessor 未指定）的 maxThreadsPerBlock 线程可以驻留在多处理器上。请参阅 occupancy 内核使用的寄存器数量与每个块分配的寄存器数量之间关系的部分。然后编译器优化寄存器的使用，如下所示：

  • 如果初始寄存器使用量超过 L，编译器会减少它，直到它小于或等于 L。这通常会导致本地内存使用量增加和/或指令数量增加。

  • 如果初始寄存器使用率低于 L

    • If maxThreadsPerBlock 已指定，但是 minBlocksPerMultiprocessor 不是，编译器使用 maxThreadsPerBlock 确定寄存器使用阈值之间的转换 n 或 n + 1 居民区。当少使用一个寄存器为额外的常驻块腾出空间时，就会发生这种情况。然后，编译器应用与未指定启动边界时类似的启发式方法。

    • 如果两者都 minBlocksPerMultiprocessor 或 maxThreadsPerBlock 被指定，编译器可能会增加寄存器的使用最多 L 以减少指令数量并更好地隐藏单线程指令的延迟。

如果执行以下命令，内核将无法启动：

  • 每个块的线程数超过其启动限制 maxThreadsPerBlock.

  • 每个集群的线程块数量多于其启动限制 maxBlocksPerCluster.

CUDA 内核所需的每线程资源可能会以不期望的方式限制最大块大小。为了保持与未来硬件和工具包的前向兼容性，并确保至少一个线程块可以在流式多处理器上运行，开发人员应包含单个参数 __launch_bounds__(maxThreadsPerBlock) 它指定内核启动时的最大块大小。否则可能会导致“启动时请求的资源过多”错误。提供两个参数版本 __launch_bounds__(maxThreadsPerBlock,minBlocksPerMultiprocessor) 在某些情况下可以提高性能。最佳价值 minBlocksPerMultiprocessor 应通过对每个内核的详细分析来确定。

内核的最佳启动范围通常会因主要架构修订而有所不同。以下代码示例说明了如何在设备代码中使用 __CUDA_ARCH__ macro.

#define THREADS_PER_BLOCK  256

#if __CUDA_ARCH__ >= 900
    #define MY_KERNEL_MAX_THREADS  (2 * THREADS_PER_BLOCK)
    #define MY_KERNEL_MIN_BLOCKS   3
#else
    #define MY_KERNEL_MAX_THREADS  THREADS_PER_BLOCK
    #define MY_KERNEL_MIN_BLOCKS   2
#endif

__global__ void
__launch_bounds__(MY_KERNEL_MAX_THREADS, MY_KERNEL_MIN_BLOCKS)
MyKernel(...) {
    ...
}

When MyKernel 使用每个块的最大线程数进行调用，该最大数被指定为 __launch_bounds__()，很容易使用 MY_KERNEL_MAX_THREADS 作为执行配置中每个块的线程数：

// 主机代码
MyKernel<<<blocksPerGrid, MY_KERNEL_MAX_THREADS>>>(...);

然而，这是行不通的，因为 __CUDA_ARCH__ 主机代码中未定义，如 执行空间说明符 部分。因此， MyKernel 将以每块 256 个线程启动。应确定每个块的线程数：

  • 在编译时使用不依赖于的宏或常量 __CUDA_ARCH__，例如

    // 主机代码
MyKernel<<<blocksPerGrid, THREADS_PER_BLOCK>>>(...);

  • 或者在运行时基于计算能力

    // 主机代码
cudaGetDeviceProperties(&deviceProp, device);
int threadsPerBlock = (deviceProp.major >= 9) ? 2 * THREADS_PER_BLOCK : THREADS_PER_BLOCK;
MyKernel<<<blocksPerGrid, threadsPerBlock>>>(...);

5.4.4. 同步原语#

5.4.4.1. 线程块同步函数#

void __syncthreads();
int  __syncthreads_count(int predicate);
int  __syncthreads_and(int predicate);
int  __syncthreads_or(int predicate);

内在函数协调同一块内线程之间的通信。当块中的线程访问共享或全局内存中的相同地址时，可能会发生先读后写、先写后读或先写后写危险。通过在此类访问之间同步线程可以避免这些危险。

内在函数具有以下语义：

  • __syncthreads*() 等待，直到线程块中所有未退出的线程同时到达相同的位置 __syncthreads*() 程序中的内部调用或退出。

  • __syncthreads*() 提供参与线程之间的内存排序：调用 __syncthreads*() 内在函数强烈发生在之前（参见 C++ 规范 [intro.races]) 任何参与线程都不会被阻塞或退出。

下面的例子展示了如何使用 __syncthreads() 同步线程块内的线程并安全地对线程之间共享的数组的元素求和：

// 假设 blockDim.x 是 128
__global__ void example_syncthreads(int* input_data, int* output_data) {
    __shared__ int shared_data[128];
    // 每个线程写入“shared_data”的不同元素：
    shared_data[threadIdx.x] = input_data[threadIdx.x];

    // 所有线程同步，保证对“shared_data”的所有写入都是有序的 
    // 在任何线程从“__syncthreads()”解除阻塞之前：
    __syncthreads();

    // 单个线程安全地读取“shared_data”：
    if (threadIdx.x == 0) {
        int sum = 0;
        for (int i = 0; i < blockDim.x; ++i) {
            sum += shared_data[i];
        }
        output_data[blockIdx.x] = sum;
    }
}

__syncthreads*() 条件代码中允许使用内在函数，但前提是条件在整个线程块中统一计算。否则，执行可能会挂起或产生意想不到的副作用。

以下示例演示了有效的行为：

// 假设 blockDim.x 是 128
__global__ void syncthreads_valid_behavior(int* input_data, int* output_data) {
    __shared__ int shared_data[128];
    shared_data[threadIdx.x] = input_data[threadIdx.x];
    if (blockIdx.x > 0) { // 所有块线程的正确、统一条件
        __syncthreads();
        output_data[threadIdx.x] = shared_data[128 - threadIdx.x];
    }
}

而以下示例表现出无效行为，例如内核挂起或未定义的行为：

// 假设 blockDim.x 是 128
__global__ void syncthreads_invalid_behavior1(int* input_data, int* output_data) {
    __shared__ int shared_data[256];
    shared_data[threadIdx.x] = input_data[threadIdx.x];
    if (threadIdx.x > 0) { // 错误的、不统一的条件
        __syncthreads();   // 未定义的行为
        output_data[threadIdx.x] = shared_data[128 - threadIdx.x];
    }
}

// 假设 blockDim.x 是 128
__global__ void syncthreads_invalid_behavior2(int* input_data, int* output_data) {
    __shared__ int shared_data[256];
    shared_data[threadIdx.x] = input_data[threadIdx.x];
    for (int i = 0; i < blockDim.x; ++i) {
        if (i == threadIdx.x) { // 错误的、不统一的条件
            __syncthreads();    // 未定义的行为
        }
    }
    output_data[threadIdx.x] = shared_data[128 - threadIdx.x];
}

__syncthreads() 带谓词的变体:

int __syncthreads_count(int predicate);

与 __syncthreads() 不同之处在于它对块中所有未退出的线程计算谓词，并返回谓词计算结果为非零值的线程数。

int __syncthreads_and(int predicate);

与 __syncthreads() 不同之处在于它评估块中所有未退出线程的谓词。当且仅当所有谓词的计算结果都为非零值时，它才返回非零值。

int __syncthreads_or(int predicate);

与 __syncthreads() 不同之处在于它评估块中所有未退出线程的谓词。当且仅当谓词计算出其中一个或多个非零值时，它才返回非零值。

5.4.4.2. warp 同步函数#

void __syncwarp(unsigned mask = 0xFFFFFFFF);

内在函数 __syncwarp() 协调同一经束内线程之间的通信。当 warp 中的某些线程访问共享或全局内存中的相同地址时，可能会发生潜在的先读后写、先写后读或先写后写危险。通过同步这些访问之间的线程可以避免这些数据危险。

Calling __syncwarp(mask) 在命名为 warp 的参与线程之间提供内存排序 mask: 调用 __syncwarp(mask) 强烈地发生在之前（参见 C++ 规范 [intro.races]）任何命名的warp mask 解除等待或退出的阻塞。

这些功能受 Warp __sync 内在约束.

下面的例子演示了如何使用 __syncwarp() 同步warp 中的线程以安全地访问共享内存数组：

__global__ void example_syncwarp(int* input_data, int* output_data) {
    if (threadIdx.x < warpSize) {
        __shared__ int shared_data[warpSize];
        shared_data[threadIdx.x] = input_data[threadIdx.x];

        __syncwarp(); // 相当于 __syncwarp(0xFFFFFFFF)
        if (threadIdx.x == 0)
            output_data[0] = shared_data[1];
    }
}

5.4.4.3. 内存栅栏功能#

CUDA 编程模型假设弱有序内存模型。换句话说，CUDA 线程将数据写入共享内存、全局内存、页锁定主机内存或对等设备内存的顺序不一定是另一个 CUDA 或主机线程观察正在写入的数据的顺序。在没有内存围栏或同步的情况下读取或写入同一内​​存位置会导致未定义的行为。

在下面的示例中，线程 1 执行 writeXY()，当线程 2 执行时 readXY().

__device__ int X = 1, Y = 2;

__device__ void writeXY() {
    X = 10;
    Y = 20;
}

__device__ void readXY() {
    int B = Y;
    int A = X;
}

两个线程同时读取和写入相同的内存位置， X 或 Y。任何数据竞争都会导致未定义的行为并且没有定义的语义。因此，所得值 A 或 B 可以是任何东西。

内存栅栏和同步功能强制执行 顺序一致的顺序 内存访问。这些功能的不同之处在于 线程范围 其中强制执行顺序，但独立于访问的内存空间，包括共享内存、全局内存、页锁定主机内存和对等设备的内存。

Hint

建议使用 cuda::atomic_thread_fence 由提供 libcu++ 出于安全和便携性原因，只要有可能。

块级内存栅栏

// <cuda/atomic> 标头
cuda::atomic_thread_fence(cuda::memory_order_seq_cst, cuda::thread_scope_block);

确保：

  • 在调用之前，调用线程对所有内存进行的所有写入 cuda::atomic_thread_fence() 调用线程块中的所有线程都会观察到发生在调用线程之后对所有内存进行的所有写入之前 cuda::atomic_thread_fence();

  • 在调用之前，调用线程对所有内存进行的所有读取 cuda::atomic_thread_fence() 在调用之后，在调用线程对所有内存进行的所有读取之前排序 cuda::atomic_thread_fence().

void __threadfence_block();

确保：

  • 在调用之前，调用线程对所有内存进行的所有写入 __threadfence_block() 调用线程块中的所有线程都会观察到发生在调用线程之后对所有内存进行的所有写入之前 __threadfence_block();

  • 在调用之前，调用线程对所有内存进行的所有读取 __threadfence_block() 在调用之后，在调用线程对所有内存进行的所有读取之前排序 __threadfence_block().

确保：

  • 调用后，调用线程不会写入所有内存 cuda::atomic_thread_fence() 设备中的任何线程都会观察到在调用线程之前对所有内存进行任何写入之前发生的情况 cuda::atomic_thread_fence().

void __threadfence();

确保：

  • 调用后，调用线程不会写入所有内存 __threadfence() 设备中的任何线程都会观察到在调用线程之前对所有内存进行任何写入之前发生的情况 __threadfence().

系统级内存栅栏

cuda::atomic_thread_fence(cuda::memory_order_seq_cst, cuda::thread_scope_system);

确保：

  • 在调用之前，调用线程对所有内存进行的所有写入 cuda::atomic_thread_fence() 设备中的所有线程、主机线程和对等设备中的所有线程都会观察到，在调用线程之后对所有内存进行所有写入之前发生 cuda::atomic_thread_fence().

void __threadfence_system();

确保：

  • 在调用之前，调用线程对所有内存进行的所有写入 __threadfence_system() 设备中的所有线程、主机线程和对等设备中的所有线程都会观察到，在调用线程之后对所有内存进行所有写入之前发生 __threadfence_system().

在前面的代码示例中，我们可以在代码中插入内存栅栏，如下所示：

#include <cuda/atomic>

__device__ int X = 1, Y = 2;

__device__ void writeXY() {
    X = 10;
    cuda::atomic_thread_fence(cuda::memory_order_seq_cst, cuda::thread_scope_device);
    Y = 20;
}

__device__ void readXY() {
    int B = Y;
    cuda::atomic_thread_fence(cuda::memory_order_seq_cst, cuda::thread_scope_device);
    int A = X;
}

__device__ int X = 1, Y = 2;

__device__ void writeXY() {
    X = 10;
    __threadfence();
    Y = 20;
}

__device__ void readXY() {
    int B = Y;
    __threadfence();
    int A = X;
}

对于此代码，可以观察到以下结果：

  • A 等于 1 且 B 等于2，即 readXY() 之前执行过 writeXY(),

  • A 等于 10 且 B 等于20，即 writeXY() 之前执行过 readXY().

  • A 等于 10 且 B 等于2。

  • 案例中 A 是 1 并且 B 是 20 是不可能的，因为内存栅栏确保写入 X 在写入之前可见 Y.

如果线程1和线程2属于同一个块，那么使用块级栅栏就足够了。如果线程 1 和 2 不属于同一块，则如果它们是来自同一设备的 CUDA 线程，则必须使用设备级栅栏；如果它们是来自两个不同设备的 CUDA 线程，则必须使用系统级栅栏。

  • 每个块首先对数组的一个子集求和，并将结果存储在全局内存中。

  • 当所有块完成后，最后一个块从全局内存中读取这些部分和中的每一个，并将它们加在一起以获得最终结果。

注

内存栅栏仅影响内存操作的执行顺序；它不保证这些操作对其他线程的可见性。

在下面的代码示例中，内存操作的可见性 result 通过将变量声明为来确保变量 volatile。有关更多详细信息，请参阅 volatile-限定变量 一节。

#include <cuda/atomic>

__device__ int count = 0;

__global__ void sum(const float*    array,
                    int             N,
                    volatile float* result) {
    __shared__ bool isLastBlockDone;
    // 每个块对输入数组的一个子集求和。
    float partialSum = calculatePartialSum(array, N);

    if (threadIdx.x == 0) {
        // 每个块的线程 0 将部分和存储到全局内存中。
        // 编译器将使用绕过 L1 缓存的存储操作
        // 因为“结果”变量被声明为易失性的。
        // 这确保了最后一个块的线程将读取正确的
        // 由所有其他块计算的部分总和。
        result[blockIdx.x] = partialSum;

        // 线程 0 确保“count”变量的增量为
        // 仅在部分和写入全局内存后执行。
        cuda::atomic_thread_fence(cuda::memory_order_seq_cst, cuda::thread_scope_device);

        // 线程 0 发出信号表示它已完成。
        int count_old = atomicInc(&count, gridDim.x);

        // 线程 0 确定其块是否是要完成的最后一个块。
        isLastBlockDone = (count_old == (gridDim.x - 1));
    }
    // 同步以确保每个线程读取正确的值
    // 是最后一个块完成。
    __syncthreads();

    if (isLastBlockDone) {
        // 最后一个块对 result[0 .. gridDim.x-1] 中存储的部分和进行求和
        float totalSum = calculateTotalSum(result);

        if (threadIdx.x == 0) {
            // 最后一个块的线程 0 将总和存储到全局内存中，并且
            // 重置计数变量，以便下一个内核调用起作用
            // 正确地。
            result[0] = totalSum;
            count     = 0;
        }
    }
}

5.4.5. 原子函数#

原子函数对共享数据执行读取-修改-写入操作，使它们看起来像是一步执行的。原子性确保每个操作要么完全完成，要么根本不完成，从而为所有参与线程提供一致的数据视图。

CUDA 通过四种方式提供原子函数：

扩展 CUDA C++ 原子函数， cuda::atomic 和 cuda::atomic_ref.

  • 它们在主机和设备代码中都是允许的。

  • 他们遵循 C++ 标准原子操作 semantics.

  • 它们允许指定 线程范围 的原子操作。

标准 C++ 原子函数， cuda::std::atomic 和 cuda::std::atomic_ref.

  • 它们在主机和设备代码中都是允许的。

  • 他们遵循 C++ 标准原子操作 semantics.

  • 他们不允许指定 线程范围 的原子操作。

Compiler 内置原子函数, __nv_atomic_<op>().

  • 它们自 CUDA 12.8 起可用。

  • 它们仅允许在设备代码中使用。

  • 他们遵循 C++ 标准原子内存顺序 semantics.

  • 它们允许指定 线程范围 的原子操作。

  • 它们具有相同的内存排序语义 C++ 标准原子操作.

  • 它们支持以下允许的数据类型的子集 cuda::std::atomic 和 cuda::std::atomic_ref，128 位数据类型除外。

遗留原子函数, atomic<Op>().

  • 它们仅允许在设备代码中使用。

  • 他们只支持 memory_order_relaxed C++ 原子内存语义.

  • 它们允许指定 线程范围 原子操作作为函数名称的一部分。

  • Unlike 内置原子函数，遗留原子函数仅保证原子性，不会引入同步点（栅栏）。

  • 它们支持以下允许的数据类型的子集 内置原子函数。原子 add 操作支持其他数据类型。

Hint

使用 扩展 CUDA C++ 原子函数 由提供 libcu++ 出于效率、安全性和便携性的考虑，建议使用。

5.4.5.1. 遗留原子函数#

传统原子函数对存储在全局或共享内存中的 32 位、64 位或 128 位字执行原子读-修改-写操作。例如， atomicAdd() 函数读取全局或共享内存中特定地址的字，向其添加一个数字，然后将结果写回同一地址。

  • 原子函数只能在设备函数中使用。

  • 对于矢量类型，例如 __half2, __nv_bfloat162, float2, 和 float4，对向量的每个元素执行读-修改-写操作。不保证整个向量在单次访问中是原子的。

本节中描述的原子函数有一个 内存排序 和 cuda::std::memory_order_relaxed 并且仅在特定的情况下是原子的 线程范围:

  • 例如，不带后缀的原子 API atomicAdd, 在范围内是原子的 cuda::thread_scope_device.

  • 原子 API 具有 _block 后缀，例如 atomicAdd_block, 在范围内是原子的 cuda::thread_scope_block.

  • 原子 API 具有 _system 后缀，例如 atomicAdd_system, 在范围内是原子的 cuda::thread_scope_system 如果他们遇到特定的 conditions.

以下示例显示 CPU 和 GPU 以原子方式更新地址处的整数值 addr:

#include <cuda_runtime.h>

__global__ void atomicAdd_kernel(int* addr) {
    atomicAdd_system(addr, 10);
}

void test_atomicAdd(int device_id) {
    int* addr;
    cudaMallocManaged(&addr, 4);
    *addr = 0;

    cudaDeviceProp deviceProp;
    cudaGetDeviceProperties(&deviceProp, device_id);
    if (deviceProp.concurrentManagedAccess != 1) {
        return; // 设备无法与 CPU 同时一致地访问托管内存
    }

    atomicAdd_kernel<<<...>>>(addr);
    __sync_fetch_and_add(addr, 10);  // CPU原子操作
}

请注意，任何原子操作都可以基于 atomicCAS() （比较和交换）。例如， atomicAdd() 对于单精度浮点数可以如下实现：

#include <cuda/memory>
#include <cuda/std/bit>

__device__ float customAtomicAdd(float* d_ptr, float value) {
    volatile unsigned* d_ptr_unsigned = reinterpret_cast<unsigned*>(d_ptr);
    unsigned  old_value      = *d_ptr_unsigned;
    unsigned  assumed;
    do {
        assumed                          = old_value;
        float    assumed_float           = cuda::std::bit_cast<float>(assumed);
        float    expected_value          = assumed_float + value;
        unsigned expected_value_unsigned = cuda::std::bit_cast<unsigned>(expected_value);
        old_value                        = atomicCAS(d_ptr_unsigned, assumed, expected_value_unsigned);
    // 注意：使用整数比较以避免 NaN 时挂起（因为 NaN != NaN）
    } while (assumed != old_value);
    return cuda::std::bit_cast<float>(old_value);
}

5.4.5.2. 内置原子函数#

CUDA 12.8 及更高版本支持用于原子操作的 CUDA 编译器内置函数，遵循与 C++ 标准原子操作 和 CUDA 线程范围。函数如下 GNU 的原子内置函数签名 带有线程范围的额外参数。

nvcc 定义宏 __CUDACC_DEVICE_ATOMIC_BUILTINS__ 当支持内置原子函数时。

下面列出了原始枚举器 内存顺序 和 线程范围，它们被用作 order 或 scope 内置原子函数的参数：

// 原子内存顺序
enum {
   __NV_ATOMIC_RELAXED,
   __NV_ATOMIC_CONSUME,
   __NV_ATOMIC_ACQUIRE,
   __NV_ATOMIC_RELEASE,
   __NV_ATOMIC_ACQ_REL,
   __NV_ATOMIC_SEQ_CST
};

// 线程范围
enum {
   __NV_THREAD_SCOPE_THREAD,
   __NV_THREAD_SCOPE_BLOCK,
   __NV_THREAD_SCOPE_CLUSTER,
   __NV_THREAD_SCOPE_DEVICE,
   __NV_THREAD_SCOPE_SYSTEM
};

  • 内存顺序对应 C++标准原子操作的内存顺序.

  • 线程作用域如下 cuda::thread_scope definition.

  • __NV_ATOMIC_CONSUME 目前内存顺序是使用更强的实现的 __NV_ATOMIC_ACQUIRE 内存顺序。

  • __NV_THREAD_SCOPE_THREAD 线程作用域目前使用更广泛的实现 __NV_THREAD_SCOPE_BLOCK 线程范围。

示例：

__device__ T __nv_atomic_load_n(T*  pointer,
                                int memory_order,
                                int thread_scope = __NV_THREAD_SCOPE_SYSTEM);

原子内置函数有以下限制：

  • 它们只能在设备功能中使用。

  • 它们不能在本地内存上操作。

  • 无法获取这些函数的地址。

  • order 或 scope 参数必须是整数；它们不能是变量。

  • 线程范围 __NV_THREAD_SCOPE_CLUSTER 受架构支持 sm_90 和更高。

不支持的情况示例：

     unsigned u1 = 1, u2 = 2;
     __nv_atomic_load(&u1, &u2, __NV_ATOMIC_RELAXED, __NV_THREAD_SCOPE_SYSTEM);
 }

 // 不允许应用于本地内存
__device__ void foo() {
   unsigned a = 1, b;
   __nv_atomic_load(&a, &b, __NV_ATOMIC_RELAXED, __NV_THREAD_SCOPE_SYSTEM);
}

 // 无法获取函数地址。
 template<void *F = __nv_atomic_load_n>
 class X {
     void *f = F; // 无法获取函数地址。
 };

     int a;
 public:
     __device__ Y(int *b): a(__nv_atomic_load_n(b, __NV_ATOMIC_RELAXED)) {}
 };

5.4.6.1. warp 活动掩码#

unsigned __activemask();

该函数返回一个 32 位整数掩码，表示调用 warp 中所有当前活动的线程。如果warp 中的第 N 个通道处于活动状态，则设置第 N 位 __activemask() 被称为。 非活动线程 在返回的掩码中用 0 位表示。已退出程序的线程始终标记为不活动。

warp

__activemask() 不能用于确定哪些warp 通道执行给定的分支。此函数旨在用于机会性warp 级编程，并且仅提供warp 内活动线程的即时快照。

    // 无效：“at_least_one”的值是不确定的
    // 并且在执行之间可能会有所不同。

5.4.6.2. warp 投票功能#

int      __all_sync   (unsigned mask, int predicate);
int      __any_sync   (unsigned mask, int predicate);
unsigned __ballot_sync(unsigned mask, int predicate);

warp vote 函数启用给定的线程 warp 执行缩减和广播操作。这些函数接受一个整数 predicate 作为warp 中每个未退出线程的输入，并将这些值与零进行比较。然后将比较结果合并（简化） 活动线程 通过以下方式之一来控制 warp，向每个参与线程广播单个返回值：

__all_sync(unsigned mask, predicate):

Evaluates predicate 对于所有未退出的线程 mask 并返回非零如果 predicate 所有这些的评估结果都为非零。

__any_sync(unsigned mask, predicate):

Evaluates predicate 对于所有未退出的线程 mask 并返回非零如果 predicate 其中一个或多个的计算结果为非零。

__ballot_sync(unsigned mask, predicate):

Evaluates predicate 对于所有未退出的线程 mask 并返回一个整数，其第 N 位被设置，如果 predicate 对于 warp 的第 N 个线程，计算结果为非零，并且第 N 个线程处于活动状态。否则，第 N 位为零。

warp

5.4.6.5. warp shuffle功能#

Hint

建议使用 libcu++ cuda::device::warp_shuffle() 作为通用且更安全的替代品 __shfl_sync() 或 __shfl_<op>_sync() intrinsics.

T __shfl_sync     (unsigned mask, T value, int      src通道,  int width=warpSize);
T __shfl_up_sync  (unsigned mask, T value, unsigned delta,    int width=warpSize);
T __shfl_down_sync(unsigned mask, T value, unsigned delta,    int width=warpSize);
T __shfl_xor_sync (unsigned mask, T value, int      laneMask, int width=warpSize);

Warp shuffle 函数在未退出的线程之间交换值 warp 不使用共享内存。

__shfl_sync()：从索引通道直接复制。

内在函数返回的值 value 由其ID由以下给出的线程持有 src通道.

  • If width 小于 warpSize，那么warp 的每个子部分都表现为一个单独的实体，其起始逻辑通道 ID 为 0。

  • If src通道 超出范围 [0, width - 1]，结果对应于所持有的值 src通道 % width，它位于同一小节内。

__shfl_up_sync()：从 ID 低于调用方 ID 的通道复制。

内在函数通过减去来计算源通道 ID delta 来自调用方的通道 ID。的价值 value 返回结果通道 ID 所持有的内容：实际上， value warp向上移动 delta.

  • If width 小于 warpSize，那么warp 的每个子部分都表现为一个单独的实体，其起始逻辑通道 ID 为 0。

  • 源通道索引不会环绕的值 width，所以较低的 delta 通道将保持不变。

__shfl_down_sync()：从 ID 高于调用方 ID 的通道复制。

内在函数通过添加来计算源通道 ID delta 到调用方的通道 ID。的价值 value 返回结果通道 ID 所持有的内容：这具有移位的效果 value warp向下 delta.

  • If width 小于 warpSize，那么warp 的每个子部分都表现为一个单独的实体，其起始逻辑通道 ID 为 0。

  • 至于 __shfl_up_sync()，源通道的 ID 号不会环绕宽度值，因此上部 delta 通道实际上将保持不变。

__shfl_xor_sync()：根据自己通道 ID 的按位异或从通道复制。

内在函数通过对调用者的通道 ID 执行按位异或来计算源通道 ID laneMask： 的值 value 返回结果通道 ID 所保存的内容。该模式实现了蝴蝶寻址模式，用于树缩减和广播。

  • If width 小于 warpSize，那么每组 width 连续的线程能够访问较早组中的元素。但是，如果它们尝试访问后面的线程组中的元素，则它们自己的值 value 将被退回。

T 可以是：

  • int, unsigned, long, unsigned long, long long, unsigned long long, float 或 double.

  • __half 或 __half2 与 cuda_fp16.h 包括标题。

  • __nv_bfloat16 或 __nv_bfloat162 与 cuda_bf16.h 包括标题。

线程只能从积极参与内在函数的另一个线程读取数据。如果目标线程是 inactive，检索到的值未定义。

width 必须是范围内的二的幂 [1, warpSize]，即 1、2、4、8、16 或 32。其他值将产生未定义的结果。

这些功能受 Warp __sync 内在约束.

有效的 warp shuffle 用法示例：

int data   = ...

    int result2 = __shfl_sync(0xb1111, data, 1);

// 通道 [16 - 31] 从通道 16 获取“数据”

5.4.6.6. Warp __sync 内在约束#

全部warp __sync 内在函数，例如：

  • __shfl_sync, __shfl_up_sync, __shfl_down_sync, __shfl_xor_sync

  • __match_any_sync, __match_all_sync

  • __reduce_add_sync, __reduce_min_sync, __reduce_max_sync, __reduce_and_sync, __reduce_or_sync, __reduce_xor_sync

  • __syncwarp

使用 mask 参数来指示哪些warp 线程参与调用。该参数确保硬件执行内在函数之前正确收敛。

中的每一位 mask 对应于线程的通道 ID (threadIdx.x % warpSize）。内在等待，直到所有未退出的warp 线程指定 mask 接听电话。
为了正确执行，必须满足以下约束：

  • 每个调用线程必须在 mask.

  • 每个非调用线程必须将其相应位设置为零 mask。退出的线程将被忽略。

  • 中指定的所有未退出线程 mask 必须以相同的方式执行内在函数 mask 值。

  • Warp 线程可能会同时调用不同的内在函数 mask 值，前提是掩码不相交。即使在发散的控制流中，这种条件也是有效的。

warp行为 __sync 函数无效，例如内核挂起或未定义，如果：

  • 调用线程中未指定 mask.

  • 指定的非退出线程 mask 无法最终退出或在同一程序点使用相同的内容调用内在函数 mask 值。

  • 在条件代码中，所有条件必须在指定的所有非退出线程中进行相同的评估 mask.

注

当所有 warp 线程都参与调用时，即当 mask 设置为 0xFFFFFFFF.

有效的warp 内在函数用法示例：

__global__ void valid_examples() {
    if (threadIdx.x < 4) {        // 线程 0、1、2、3 处于活动状态
        __all_sync(0b1111, pred); // 正确，线程 0、1、2、3 参与调用
    }

    if (threadIdx.x == 0)
        return; // exit
    // 正确，所有未退出的线程都参与调用
    __all_sync(0xFFFFFFFF, pred);
}

Disjoint mask examples:

5.4.7. CUDA 特定宏#

5.4.7.1. __CUDA_ARCH__#

宏观 __CUDA_ARCH__ 代表 虚拟架构 正在为其编译代码的 NVIDIA GPU 的名称。其值可能与设备的实际计算能力不同。该宏允许编写专门针对特定 GPU 架构的代码路径，这可能是获得最佳性能或使用特定于架构的功能和指令所必需的。该宏还可用于区分主机代码和设备代码。

__CUDA_ARCH__ 仅在设备代码中定义，即在 __device__, __host__ __device__, 和 __global__ 功能。宏的值与 nvcc option compute_<version>，与关系 __CUDA_ARCH__ = <version> * 10.

示例：

nvcc --generate-code arch=compute_80,code=sm_90 prog.cu

defines __CUDA_ARCH__ as 800.

__CUDA_ARCH__ Constraints

1. 以下实体的类型签名不应取决于是否 __CUDA_ARCH__ 是定义的，也不取决于它的值。

  • __global__ 函数和函数模板。

  • __device__ 或 __constant__ variables.

  • 纹理和表面。

示例：

#if !defined(__CUDA_ARCH__)
    typedef int my_type;
#else
    typedef double my_type;
#endif

__device__ my_type my_var;           // 错误：my_var 的类型取决于 __CUDA_ARCH__

__global__ void kernel(my_type in) { // 错误：内核的类型取决于 __CUDA_ARCH__
    ...
}

2. 如果一个 __global__ 函数模板是从主机实例化并启动的，那么它必须使用相同的模板参数实例化，无论是否 __CUDA_ARCH__ 被定义或其值。

示例：

__device__ int result;

template <typename T>
__global__ void kernel(T in) {
    result = in;
}

__host__ __device__ void host_device_function(void) {
#if !defined(__CUDA_ARCH__)
    kernel<<<1, 1>>>(1); // 错误：仅“kernel<int>”实例化
                            // 当 __CUDA_ARCH__ 未定义时！
#endif
}

int main(void) {
    host_device_function();
    cudaDeviceSynchronize();
    return 0;
}

3. 在单独编译模式下，具有外部链接的函数或变量定义的存在或不存在不应取决于 __CUDA_ARCH__ 或关于它的价值。

示例：

#if !defined(__CUDA_ARCH__)
    void host_function(void) {} // 错误：host_function() 的定义
                                // 仅在 __CUDA_ARCH__ 时出现
                                // 未定义
#endif

4. 在单独编译中，预处理器宏 __CUDA_ARCH__ 不得在标头中使用以防止对象具有不同的行为。或者，所有对象必须针对同一虚拟架构进行编译。如果在标头中定义了弱函数或模板函数，并且其行为取决于 __CUDA_ARCH__，那么如果这些对象针对不同的计算架构进行编译，则不同对象中的该函数的实例可能会发生冲突。

例如，如果一个头文件 a.h contains:

template<typename T>
__device__ T* get_ptr() {
#if __CUDA_ARCH__ == 900
    return nullptr; /* 没有地址 */
#else
    __shared__ T arr[256];
    return arr;
#endif
}

那么如果 a.cu 或 b.cu 两者都包括 a.h 并实例化 get_ptr() 对于同一类型，并且 b.cu 期望非NULL 地址，并编译为：

nvcc -arch=compute_70 -dc a.cu
nvcc -arch=compute_80 -dc b.cu
nvcc -arch=sm_80 a.o b.o

链接时只会使用 ``get_ptr()`` 函数的一个版本，因此行为取决于所选择的版本。为避免此问题，``a.cu`` 和 ``b.cu`` 必须针对相同的计算架构编译，或者不应在共享头文件函数中使用 ``__CUDA_ARCH__``。

编译器不保证将为不支持的用途生成诊断信息 __CUDA_ARCH__ 如上所述。

5.4.7.2. __CUDA_ARCH_SPECIFIC__ 或 __CUDA_ARCH_FAMILY_SPECIFIC__#

宏 __CUDA_ARCH_SPECIFIC__ 或 __CUDA_ARCH_FAMILY_SPECIFIC__ 定义为识别 GPU 设备 architecture- 和 family- 分别具有具体特征。参见 功能集编译器目标 部分了解更多信息。

类似于 __CUDA_ARCH__, __CUDA_ARCH_SPECIFIC__ 或 __CUDA_ARCH_FAMILY_SPECIFIC__ 仅在设备代码中定义，即在 __device__, __host__ __device__, 和 __global__ 函数中定义。这些宏与 nvcc 选项 compute_<version>a 或 compute_<version>f 一起使用。

nvcc --generate-code arch=compute_100a,code=sm_100a prog.cu

  • __CUDA_ARCH__ == 1000.

  • __CUDA_ARCH_SPECIFIC__ == 1000.

  • __CUDA_ARCH_FAMILY_SPECIFIC__ == 1000.

nvcc --generate-code arch=compute_100f,code=sm_103f prog.cu

  • __CUDA_ARCH__ == 1000.

  • __CUDA_ARCH_FAMILY_SPECIFIC__ == 1000.

  • __CUDA_ARCH_SPECIFIC__ 没有定义。

nvcc -arch=sm_100 prog.cu

  • __CUDA_ARCH__ == 1000.

  • __CUDA_ARCH_FAMILY_SPECIFIC__ 没有定义。

  • __CUDA_ARCH_SPECIFIC__ 没有定义。

nvcc -arch=sm_100a prog.cu
# 相当于：
nvcc --generate-code arch=sm_100a,compute_100,compute_100a prog.cu

  • __CUDA_ARCH__ == 1000.

  • __CUDA_ARCH_FAMILY_SPECIFIC__ 没有定义。

  • __CUDA_ARCH_SPECIFIC__ == 1000 或 __CUDA_ARCH_SPECIFIC__ 未定义的都生成。

5.4.8.1. 地址空间谓词函数#

Hint

建议使用 cuda::device::is_address_from() 或 cuda::device::is_object_from() 提供的功能 libcu++ 作为地址空间谓词内在函数的可移植且更安全的替代方案。

5.4.8.2. 地址空间转换函数#

CUDA 指针 (T*）可以访问对象，无论对象存储在何处。例如，一个 int* 可以访问 int 对象是否驻留在全局内存或共享内存中。

地址空间转换函数用于在通用地址和特定地址空间中的地址之间进行转换。 当编译器无法确定指针的地址空间时（例如，跨越翻译单元或与 PTX 指令交互时），这些函数非常有用。

__device__ size_t __cvta_generic_to_global  (const void* ptr); // PTX：cvta.to.global
__device__ size_t __cvta_generic_to_shared  (const void* ptr); // PTX：cvta.to.shared
__device__ size_t __cvta_generic_to_constant(const void* ptr); // PTX：cvta.to.const
__device__ size_t __cvta_generic_to_local   (const void* ptr); // PTX：cvta.to.local

__device__ void* __cvta_global_to_generic  (size_t raw_ptr); // PTX：cvta.global
__device__ void* __cvta_shared_to_generic  (size_t raw_ptr); // PTX：cvta.共享
__device__ void* __cvta_constant_to_generic(size_t raw_ptr); // PTX：cvta.const
__device__ void* __cvta_local_to_generic   (size_t raw_ptr); // PTX：cvta.local

作为与 PTX 指令互操作的示例， ld.shared.s32 r0, [ptr]; PTX 指令期望 ptr 引用共享内存地址空间。 一个 CUDA 程序 int* 指向对象的指针 __shared__ 内存需要将此指针转换为共享地址空间，然后通过调用将其传递给 PTX 指令 __cvta_generic_to_shared 如下：

__shared__ int smem_var;
smem_var        = 42;
size_t smem_ptr = __cvta_generic_to_shared(&smem_var);
int    output;
asm volatile("ld.shared.s32 %0, [%1];" : "=r"(output) : "l"(smem_ptr) : "memory");
assert(output == 42);

利用这些地址表示的常见优化是通过利用共享空间、本地空间和常量空间的地址范围小于 32 位这一事实来减少数据结构大小，这允许存储 32 位地址而不是 64 位指针并保存寄存器。此外，32 位算术比 64 位算术更快。 要获取这些地址的 32 位整数表示形式，请通过从无符号 64 位整数转换为无符号 32 位整数，将 64 位值截断为 32 位：

__shared__ int smem_var;
uint32_t       smem_ptr_32bit = static_cast<uint32_t>(__cvta_generic_to_shared(&smem_var));

要从此类 32 位表示恢复通用地址，请将地址零扩展回无符号 64 位整数，然后调用相应的地址空间转换函数：

size_t smem_ptr_64bit = static_cast<size_t>(smem_ptr_32bit); // 零扩展至 64 位
void*  generic_ptr    = __cvta_shared_to_generic(smem_ptr_64bit);
assert(generic_ptr == &smem_var);

Hint

陷阱操作可以通过调用 __trap() 来自任何设备线程的函数。

5.4.8.5. __nanosleep()#

__device__ void __nanosleep(unsigned nanoseconds);

功能 __nanosleep(ns) 将线程挂起大约睡眠持续时间 ns 纳秒。最长睡眠持续时间约为一毫秒。

示例：

以下代码实现了具有指数退避的互斥锁。

__device__ void mutex_lock(unsigned* mutex) {
    unsigned ns = 8;
    while (atomicCAS(mutex, 0, 1) == 1) {
        __nanosleep(ns);
        if (ns < 256) {
            ns *= 2;
        }
    }
}

__device__ void mutex_unlock(unsigned *mutex) {
    atomicExch(mutex, 0);
}

5.4.8.6. 动态编程扩展 (DPX) 指令#

比较函数：

  • 三个参数。语义： max(a, b, c), min(a, b, c).

     int __vimax3_s32  (     int,      int,      int);
unsigned __vimax3_s16x2(unsigned, unsigned, unsigned);
unsigned __vimax3_u32  (unsigned, unsigned, unsigned);
unsigned __vimax3_u16x2(unsigned, unsigned, unsigned);

     int __vimin3_s32  (     int,      int,      int);

unsigned __vimin3_u32  (unsigned, unsigned, unsigned);
unsigned __vimin3_u16x2(unsigned, unsigned, unsigned);

  • 两个参数，带有 ReLU。语义： max(a, b, 0), max(min(a, b), 0).

     int __vimax_s32_relu  (     int,      int);
unsigned __vimax_s16x2_relu(unsigned, unsigned);

     int __vimin_s32_relu  (     int,      int);
unsigned __vimin_s16x2_relu(unsigned, unsigned);

  • 三个参数，带有ReLU。语义： max(a, b, c, 0), max(min(a, b, c), 0).

     int __vimin3_s32_relu  (     int,      int,      int);
unsigned __vimin3_s16x2_relu(unsigned, unsigned, unsigned);

  • 两个参数，还返回哪个参数更小/更大：

     int __vibmax_s32  (     int,      int, bool* pred);
unsigned __vibmax_u32  (unsigned, unsigned, bool* pred);
unsigned __vibmax_s16x2(unsigned, unsigned, bool* pred);
unsigned __vibmax_u16x2(unsigned, unsigned, bool* pred);

     int __vibmin_s32  (     int,      int, bool* pred);
unsigned __vibmin_u32  (unsigned, unsigned, bool* pred);
unsigned __vibmin_s16x2(unsigned, unsigned, bool* pred);
unsigned __vibmin_u16x2(unsigned, unsigned, bool* pred);

融合加法和最小值/最大值：

  • 三个参数，将（第一个+第二个）与第三个进行比较。语义： max(a + b, c), min(a + b, c)

     int __viaddmax_s32  (     int,     int,       int);
unsigned __viaddmax_s16x2(unsigned, unsigned, unsigned);
unsigned __viaddmax_u32  (unsigned, unsigned, unsigned);
unsigned __viaddmax_u16x2(unsigned, unsigned, unsigned);

     int __viaddmin_s32  (     int,     int,       int);
unsigned __viaddmin_s16x2(unsigned, unsigned, unsigned);
unsigned __viaddmin_u32  (unsigned, unsigned, unsigned);
unsigned __viaddmin_u16x2(unsigned, unsigned, unsigned);

  • 三个参数，使用 ReLU，将（第一个 + 第二个）与第三个和零进行比较。语义： max(a + b, c, 0), max(min(a + b, c), 0)

     int __viaddmax_s32_relu  (     int,      int,      int);
unsigned __viaddmax_s16x2_relu(unsigned, unsigned, unsigned);

     int __viaddmin_s32_relu  (     int,      int,      int);
unsigned __viaddmin_s16x2_relu(unsigned, unsigned, unsigned);

这些指令是硬件加速的或软件模拟的，具体取决于计算能力。参见 算术指令 计算能力要求部分。

完整的 API 可以在以下位置找到 CUDA 数学 API 文档.

DPX 是一个非常有用的工具，用于实现动态规划算法，例如基因组学中的 Smith-Waterman 和 Needleman-Wunsch 算法以及路线优化中的 Floyd-Warshall 算法。

三个有符号 32 位整数的最大值，使用 ReLU：

int a           = -15;
int b           = 8;
int c           = 5;
int max_value_0 = __vimax3_s32_relu(a, b, c); // max(-15, 8, 5, 0) = 8
int d           = -2;
int e           = -4;
int max_value_1 = __vimax3_s32_relu(a, d, e); // max(-15, -2, -4, 0) = 0

两个 32 位有符号整数、另一个 32 位有符号整数和一个零之和的最小值 (ReLU)：

int a           = -5;
int b           = 6;
int c           = -2;
int max_value_0 = __viaddmax_s32_relu(a, b, c); // 最大值(-5 + 6, -2, 0) = 最大值(1, -2, 0) = 1
int d           = 4;
int max_value_1 = __viaddmax_s32_relu(a, d, c); // 最大值(-5 + 4, -2, 0) = 最大值(-1, -2, 0) = 0

unsigned a = 9;
unsigned b = 6;
bool     smaller_value;
unsigned min_value = __vibmin_u32(a, b, &smaller_value); // min_value 为 6，smaller_value 为 true

三对无符号 16 位整数的最大值：

unsigned a         = 0x00050002;
unsigned b         = 0x00070004;
unsigned c         = 0x00020006;
unsigned max_value = __vimax3_u16x2(a, b, c); // max(5, 7, 2) 和 max(2, 4, 6)，因此 max_value 为 0x00070006

5.4.9. 编译器优化提示#

编译器优化提示用附加信息装饰代码，以帮助编译器优化生成的代码。

  • 内置函数在设备代码中始终可用。

  • 主机代码支持取决于主机编译器。

5.4.9.1. #pragma unroll#

默认情况下，编译器会展开具有已知行程计数的小循环。然而， #pragma unroll 指令可用于控制任何给定循环的展开。该伪指令必须紧邻循环之前放置，并且仅适用于该循环。

可以选择跟随整型常量表达式。以下是整型常量表达式的情况：

  • 如果不存在，则在其行程计数恒定的情况下，循环将完全展开。

  • 如果评估为 0 或 1，循环将不会展开。

  • 如果是非正整数或大于 INT_MAX，该编译指示将被忽略，并发出警告。

示例：

struct MyStruct {
    static constexpr int value = 4;
};

inline constexpr int Count = 4;

__device__ void foo(int* p1, int* p2) {
    // 未指定参数，循环将完全展开
    #pragma unroll
    for (int i = 0; i < 12; ++i)
        p1[i] += p2[i] * 2;

    // 展开值 = 5
    #pragma unroll (Count + 1)
    for (int i = 0; i < 12; ++i)
        p1[i] += p2[i] * 4;

    // 展开值 = 1，禁用循环展开
    #pragma unroll 1
    for (int i = 0; i < 12; ++i)
        p1[i] += p2[i] * 8;

    // 展开值 = 4
    #pragma unroll (MyStruct::value)
    for (int i = 0; i < 12; ++i)
        p1[i] += p2[i] * 16;

    // 负值，pragma unroll 被忽略
    #pragma unroll -1
    for (int i = 0; i < 12; ++i)
        p1[i] += p2[i] * 2;
}

请参阅示例 编译器资源管理器.

5.4.9.2. __builtin_assume_aligned()#

Hint

建议使用 cuda::std::assume_aligned() 提供的功能 libcu++ (C++参考）作为内置函数的便携式且更安全的替代方案。

void* __builtin_assume_aligned(const void* ptr, size_t align)
void* __builtin_assume_aligned(const void* ptr, size_t align, <integral type> offset)

内置函数使编译器能够假设返回的指针至少对齐 align bytes.

  • 三参数版本使编译器能够假设 (char*) ptr - offset 至少对齐到 align bytes.

align 必须是 2 的幂和整数文字。

示例：

void* res1 = __builtin_assume_aligned(ptr, 32);    // 编译器可以假设“res1”至少是 32 字节对齐的
void* res2 = __builtin_assume_aligned(ptr, 32, 8); // 编译器可以假设 'res2 = (char*) ptr - 8' 至少是 32 字节对齐的

5.4.9.3. __builtin_assume() 或 __assume()#

void __builtin_assume(bool predicate)
void __assume        (bool predicate) // 仅适用于 Microsoft 编译器

内置函数使编译器能够假设布尔参数为 true。如果参数在运行时为 false，则行为未定义。请注意，如果参数有副作用，则行为是未指定的。

示例：

__device__ bool is_greater_than_zero(int value) {
    return value > 0;
}

__device__ bool f(int value) {
    __builtin_assume(value > 0);
    return is_greater_than_zero(value); // 返回 true，不评估条件
}

5.4.9.4. __builtin_expect()#

long __builtin_expect(long input, long expected)

内置函数告诉编译器 input 预计等于 expected，并返回值 input。它通常用于向编译器提供分支预测信息。 它的行为类似于 C++20 [[likely]] 或 [[unlikely]] attributes.

示例：

// 向编译器表明可能是“var == 0”
if (__builtin_expect(var, 0))
    doit();

5.4.9.5. __builtin_unreachable()#

void __builtin_unreachable(void)

内置函数告诉编译器控制流永远不会到达调用该函数的点。如果控制流在运行时确实达到了这一点，则程序具有未定义的行为。

此函数对于避免生成无法访问的分支的代码以及禁用对无法访问的代码的编译器警告非常有用。

示例：

// 向编译器表明永远不会达到默认的 case 标签。
switch (in) {
    case 1:  return 4;
    case 2:  return 10;
    default: __builtin_unreachable();
}

5.4.9.6. 自定义 ABI 指令#

#pragma nv_abi 指令使应用程序能够编译在 单独编译 模式来实现类似于的性能 整个程序编译 通过保留函数使用的寄存器数量。

使用此编译指示的语法如下，其中 EXPR 指任何整型常量表达式：

#pragma nv_abi preserve_n_data(EXPR) preserve_n_control(EXPR)

  • 接下来的论点 #pragma nv_abi 是可选的并且可以按任何顺序提供；然而，至少需要一个参数。

  • preserve_n 参数限制函数调用期间保留的寄存器数量：

    • preserve_n_data(EXPR) 限制数据寄存器的数量。

    • preserve_n_control(EXPR) 限制控制寄存器的数量。

#pragma nv_abi 指令可以紧邻设备函数声明或定义之前放置。

#pragma nv_abi preserve_n_data(16)
__device__ void dev_func();

#pragma nv_abi preserve_n_data(16) preserve_n_control(8)
__device__ int dev_func() {
    return 0;
}

或者，可以将其直接放置在设备函数内的 C++ 表达式语句内的间接函数调用之前。请注意，虽然支持对自由函数的间接函数调用，但不支持对函数引用或类成员函数的间接调用。

__device__ int dev_func1();

struct MyStruct {
    __device__ int member_func2();
};

__device__ void test() {
    auto* dev_func_ptr = &dev_func1; // 类型： int (*)(void)
    #pragma nv_abi preserve_n_control(8)
    int v1 = dev_func_ptr();         // 正确，间接调用

    #pragma nv_abi preserve_n_control(8)
    int v2 = dev_func1();            // 错误，直接调用；该编译指示没有效果
                                     // dev_func1 的类型为：int(void)

    auto& dev_func_ref = &dev_func1; // 类型：int (&)(void)
    #pragma nv_abi preserve_n_control(8)
    int v3 = dev_func_ref();         // 错误，调用参考
                                     // 该编译指示没有效果

    auto member_function_ptr = &MyStruct::member_func2; // 类型： int (MyStruct::*)(void)
    #pragma nv_abi preserve_n_control(8)
    int v4 = member_function_ptr();  // 错误，间接调用成员函数
                                     // 该编译指示没有效果
}

当应用于设备函数的声明或定义时，编译指示会修改对该函数的任何调用的自定义 ABI 属性。当放置在间接函数调用站点时，它仅影响该特定调用的 ABI 属性。请注意，编译指示仅在放置在调用站点时影响间接函数调用；它对直接函数调用没有影响。

#pragma nv_abi preserve_n_control(8)
__device__ int dev_func3();

__device__ int dev_func4();

__device__ void test() {
    int v1 = dev_func3();            // 正确，编译指示影响直接调用

    auto* dev_func_ptr = &dev_func4; // 类型： int (*)(void)
    #pragma nv_abi preserve_n_control(8)
    int v2 = dev_func_ptr();         // 正确，编译指示影响间接调用

    int v3 = dev_func_ptr();         // 错误，该编译指示没有效果
}

请注意，如果函数声明的编译指示参数与其相应的定义不匹配，则程序是格式错误的。

5.4.10.1. 断言#

void assert(int expression);

assert() 宏停止内核执行如果 expression 等于零。如果程序在调试器中运行，则会触发断点，从而允许使用调试器检查设备的当前状态。否则，每个线程 expression 等于 0 在通过与主机同步后将消息打印到 stderr cudaDeviceSynchronize(), cudaStreamSynchronize(), or cudaEventSynchronize()。该消息的格式如下：

<filename>:<line number>:<function>:
block: [blockIdx.x,blockIdx.y,blockIdx.z],
thread: [threadIdx.x,threadIdx.y,threadIdx.z]
Assertion `<expression>` failed.

内核的执行被中止，在主机程序中引发中断。的 assert() 宏会导致 CUDA 上下文损坏，导致任何后续 CUDA 调用或内核调用失败 cudaErrorAssert.

内核执行不受影响，如果 expression 与零不同。

例如，源文件中的以下程序 test.cu

#include <assert.h>

 __global__ void testAssert(void) {
     int is_one        = 1;
     int should_be_one = 0;

     // 这不会有任何影响
     assert(is_one);

     // 这将停止内核执行
     assert(should_be_one);
 }

 int main(void) {
     testAssert<<<1,1>>>();
     cudaDeviceSynchronize();
     return 0;
 }

将输出：

test.cu:11: void testAssert(): block: [0,0,0], thread: [0,0,0] Assertion `should_be_one` failed.

断言旨在用于调试目的。由于它们会影响性能，因此建议在生产代码中禁用它们。可以通过定义在编译时禁用它们 NDEBUG 包含之前的预处理器宏 assert.h 或 <cassert>，或者通过使用编译器标志 -DNDEBUG。注意表达式不应该有副作用；否则，禁用断言将影响代码的功能。

以下编译指示可用于管理引发特定诊断消息时触发的错误的严重性。

#pragma nv_diag_error

#pragma nv_diag_suppress 177 // “已声明但从未引用”

    int i = 0;
}

#pragma nv_diag_default 177
void bar() {
    int i = 0;
}

以下编译指示可用于保存和恢复当前诊断编译指示状态：

#pragma nv_diagnostic push
#pragma nv_diagnostic pop

示例：

#pragma nv_diag_suppress 177 // “已声明但从未引用”

    int i = 0;
}

#pragma nv_diagnostic pop
void bar() {
    int i = 0; // 提出警告
}

5.4.11.2. 交替浮点#

Tensor Core 支持计算能力 8.0 及更高版本的设备上的替代类型浮点运算。

__nv_bfloat16

此数据格式是替代的 fp16 格式，其范围与 f32 相同，但精度降低（7 位）。您可以直接使用此数据格式 __nv_bfloat16 类型可用于 cuda_bf16.h。矩阵片段与 __nv_bfloat16 数据类型需要由以下累加器组成 float 类型。支持的形状和操作与 __half.

tf32

该数据格式是 Tensor Core 支持的特殊浮点格式，其范围与 f32 相同，但精度降低（>=10 位）。该格式的内部布局是实现定义的。要在 WMMA 运算中使用此浮点格式，必须手动将输入矩阵转换为 tf32 精度。

为了促进转换，一个新的内在 __float_to_tf32 提供。虽然内在函数的输入和输出参数是 float 类型，输出将是 tf32 数字上。这种新精度仅适用于张量核心，如果与其他核心混合使用 float类型运算，结果的精度和范围将是未定义的。

一旦输入矩阵（matrix_a 或 matrix_b) 转换为 tf32 精度，a 的组合 fragment 或 precision::tf32 精度和数据类型 float 或 load_matrix_sync 将利用这一新功能。两个累加器片段必须具有 float 数据类型。唯一支持的矩阵大小是 16x16x8 (m-n-k)。

片段的元素表示为 float，因此映射为 element_type<T> 或 storage_element_type<T> is:

5.4.11.4. 子字节操作#

子字节 WMMA 运算提供了一种访问 Tensor Core 的低精度功能的方法。它们被视为预览功能，即它们的数据结构和 API 可能会发生变化，并且可能与未来版本不兼容。此功能可通过 nvcuda::wmma::experimental namespace:

namespace experimental {
    namespace precision {
        struct u4; // 4 位无符号
        struct s4; // 4 位有符号

   }
    enum bmmaBitOp {
        bmmaBitOpXOR = 1, // 最小compute_75

5.4.11.5. 限制#

对于每个主要和次要设备架构，张量核心所需的特殊格式可能不同。由于线程仅保存整个矩阵的一个片段（不透明的架构特定的 ABI 数据结构），这使得情况变得更加复杂，开发人员不允许假设各个参数如何映射到参与矩阵乘法累加的寄存器。

由于片段是特定于体系结构的，因此如果函数已针对不同的链接兼容体系结构进行编译并链接在一起到同一设备可执行文件中，则将它们从函数 A 传递到函数 B 是不安全的。在这种情况下，片段的大小和布局将特定于一种体系结构，而在另一种体系结构中使用 WMMA API 将导致不正确的结果或潜在的损坏。

sm_70 和 sm_75 是两个链路兼容架构的示例，其中片段的布局不同。

fragA.cu: void foo() { wmma::fragment<...> mat_a; bar(&mat_a); }
fragB.cu: void bar(wmma::fragment<...> *mat_a) { // 对 mat_a 进行操作 }

// sm_70 片段布局
$> nvcc -dc -arch=compute_70 -code=sm_70 fragA.cu -o fragA.o
// sm_75片段布局
$> nvcc -dc -arch=compute_75 -code=sm_75 fragB.cu -o fragB.o
// 将两者联系在一起
$> nvcc -dlink -arch=sm_75 fragA.o fragB.o -o frag.o

这种未定义的行为在编译时和运行时工具也可能无法检测到，因此需要格外小心以确保片段的布局一致。当与为不同的链接兼容架构构建并期望传递 WMMA 片段的遗留库链接时，最有可能出现这种链接危险。

请注意，在弱链接的情况下（例如，CUDA C++ 内联函数），链接器可以选择任何可用的函数定义，这可能会导致编译单元之间的隐式传递。

为了避免此类问题，矩阵应始终存储到内存中，以便通过外部接口（例如， wmma::store_matrix_sync(dst, …);）然后它可以安全地传递给 bar() 作为指针类型 [例如 float *dst].

请注意，由于 sm_70 可以在 sm_75 上运行，因此上面的示例 sm_75 代码可以更改为 sm_70 并在 sm_75 上正确运行。但是，当与其他 sm_75 单独编译的二进制文件链接时，建议在应用程序中包含 sm_75 本机代码。

5.4.11.7. warp#

以下代码在单个 warp 中实现 16x16x16 矩阵乘法。

#include <mma.h>
using namespace nvcuda;

__global__ void wmma_ker(half *a, half *b, float *c) {
   // 声明片段
   wmma::fragment<wmma::matrix_a, 16, 16, 16, half, wmma::col_major> a_frag;
   wmma::fragment<wmma::matrix_b, 16, 16, 16, half, wmma::row_major> b_frag;
   wmma::fragment<wmma::accumulator, 16, 16, 16, float> c_frag;

   // 将输出初始化为零
   wmma::fill_fragment(c_frag, 0.0f);

   // 加载输入
   wmma::load_matrix_sync(a_frag, a, 16);
   wmma::load_matrix_sync(b_frag, b, 16);

   // 执行矩阵乘法
   wmma::mma_sync(c_frag, a_frag, b_frag, c_frag);

   // 存储输出
   wmma::store_matrix_sync(c, c_frag, 16, wmma::mem_row_major);
}
