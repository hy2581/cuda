3.1. 高级 CUDA API 与特性#

本节将介绍更高级的 CUDA API 和功能的使用。这些主题涵盖的技术或功能通常不需要 CUDA 内核修改，但仍然可以从主机端影响应用程序级行为，包括 GPU 工作执行和性能以及 CPU 端性能。

3.1.1. cudaLaunchKernelEx#

当 三重 V 形符号 在第一个版本中引入了 内核配置 内核只有四个可编程参数： - 线程块尺寸 - 网格尺寸 - 动态共享内存（可选，如果未指定则为 0） - 流（如果未指定则使用默认流）

某些 CUDA 功能可以受益于内核启动时提供的附加属性和提示。这 cudaLaunchKernelEx 使程序能够通过以下方式设置上述执行配置参数 cudaLaunchConfig_t 结构。 此外， cudaLaunchConfig_t 结构允许程序传入零个或多个 cudaLaunchAttributes 控制或建议内核启动的其他参数。例如， cudaLaunchAttributePreferredSharedMemoryCarveout 本章稍后讨论（参见 配置 L1/共享内存平衡) 指定使用 cudaLaunchKernelEx。的 cudaLaunchAttributeClusterDimension 本章稍后讨论的属性用于指定内核启动所需的簇大小。

支持的属性及其含义的完整列表在 CUDA 运行时 API 参考文档.

3.1.2. 启动集群：#

线程块簇前面几节介绍的线程块组织是计算能力 9.0 及更高版本中可用的可选级别，它使应用程序能够保证集群的线程块在单个 GPC 上同时执行。这使得比单个 SM 中的线程组更大的线程组能够交换数据并相互同步。

Section 第2.1.10.1节 展示了如何使用三重 V 形符号来指定和启动使用集群的内核。在本节中， __cluster_dims__ 注释用于指定必须用于启动内核的集群的尺寸。当使用三重 V 形符号时，簇的大小是隐式确定的。

3.1.2.1. 使用 cudaLaunchKernelEx 启动集群#

Unlike 使用具有三重 V 形符号的集群启动内核，线程块簇的大小可以在每次启动的基础上进行配置。下面的代码示例展示了如何使用以下命令启动集群内核 cudaLaunchKernelEx.

// 内核定义
// 内核没有附加编译时属性
__global__ void cluster_kernel(float *input, float* output)
{

}

int main()
{
    float *input, *output;
    dim3 threadsPerBlock(16, 16);
    dim3 numBlocks(N / threadsPerBlock.x, N / threadsPerBlock.y);

    // 具有运行时集群大小的内核调用
    {
        cudaLaunchConfig_t config = {0};
        // 网格维度不受集群启动影响，仍然枚举
        // 使用块数。
        // 网格尺寸应该是簇大小的倍数。
        config.gridDim = numBlocks;
        config.blockDim = threadsPerBlock;

        cudaLaunchAttribute attribute[1];
        attribute[0].id = cudaLaunchAttributeClusterDimension;
        attribute[0].val.clusterDim.x = 2; // X 维度上的簇大小
        attribute[0].val.clusterDim.y = 1;
        attribute[0].val.clusterDim.z = 1;
        config.attrs = attribute;
        config.numAttrs = 1;

        cudaLaunchKernelEx(&config, cluster_kernel, input, output);
    }
}

有两个 cudaLaunchAttribute 与线程块簇相关的类型： cudaLaunchAttributeClusterDimension 或 cudaLaunchAttributePreferredClusterDimension.

属性 ID cudaLaunchAttributeClusterDimension 指定执行集群所需的维度。该属性的值， clusterDim, 是一个 3 维值。网格的相应维度（x、y 和 z）必须能被指定簇维度的相应维度整除。设置此项类似于使用 __cluster_dims__ 编译时内核定义上的属性，如下所示 使用三重 V 形符号的集群启动，但可以在运行时针对同一内核的不同启动进行更改。

在计算能力为 10.0 及更高的 GPU 上，另一个属性 id cudaLaunchAttributePreferredClusterDimension 允许应用程序额外指定集群的首选维度。首选维度必须是由指定的最小簇维度的整数倍 __cluster_dims__ 内核上的属性或 cudaLaunchAttributeClusterDimension 归因于 cudaLaunchKernelEx。也就是说，除了首选簇尺寸之外，还必须指定最小簇尺寸。网格的相应维度（x、y 和 z）必须能被指定的首选簇维度的相应维度整除。

所有线程块将在至少具有最小簇尺寸的簇中执行。在可能的情况下，将使用首选维度的集群，但并非所有集群都保证以首选维度执行。所有线程块都将在具有最小或首选集群维度的集群中执行。使用首选簇维度的内核必须编写为在最小或首选簇维度中正确运行。

3.1.2.2. 块作为簇#

当内核定义为 __cluster_dims__ 注解中，网格中的簇数是隐式的，可以通过将网格的大小除以指定的簇大小来计算。

__cluster_dims__((2, 2, 2)) __global__ void foo();

// 8x8x8 集群，每个集群有 2x2x2 线程块。
foo<<<dim3(16, 16, 16), dim3(1024, 1, 1)>>>();

在上面的示例中，内核作为 16x16x16 线程块的网格启动，这意味着使用 8x8x8 集群的网格。

内核也可以使用 __block_size__ 注释，它指定定义内核时所需的块大小和簇大小。使用此注释时，三重 V 形启动将成为集群而不是线程块的网格维度，如下所示。

// 每个块有多少个线程以及每个集群有多少个块的实现细节
// 作为内核的一个属性来处理。
__block_size__((1024, 1, 1), (2, 2, 2)) __global__ void foo();

// 8x8x8 簇。
foo<<<dim3(8, 8, 8)>>>();

__block_size__ 需要两个字段，每个字段都是 3 个元素的元组。第一个元组表示块维度和第二个簇大小。第二个元组假设为 (1,1,1) 如果没有通过。要指定流，必须通过 1 或 0 作为第二个和第三个参数 <<<>>> 最后是流。传递其他值将导致未定义的行为。

请注意，第二个元组是非法的 __block_size__ 或 __cluster_dims__ 同时指定。使用也是违法的 __block_size__ 与一个空的 __cluster_dims__。当第二个元组 __block_size__ 被指定，这意味着“块作为簇”被启用，并且编译器将识别其中的第一个参数 <<<>>> 作为簇的数量而不是线程块的数量。

3.1.3. 有关直播和活动的更多信息#

CUDA 流 介绍了 CUDA 流的基础知识。默认情况下，在给定 CUDA 流上提交的操作是序列化的：只有前一个操作完成后才能开始执行。唯一的例外是最近添加的 程序化依赖启动和同步 功能。拥有多个 CUDA 流是实现并发执行的一种方法；另一种方法是使用 CUDA 图形。这两种方法也可以结合起来。

在不同 CUDA 流上提交的工作 may 在特定情况下并发执行，例如，如果没有事件依赖、如果没有隐式同步、如果有足够的资源等。

如果在不同 CUDA 流之间提交对 NULL 流的任何 CUDA 操作，则来自不同 CUDA 流的独立操作不能同时运行，除非这些流是非阻塞 CUDA 流。这些是使用以下命令创建的流 cudaStreamCreateWithFlags() 运行时 API 与 cudaStreamNonBlocking 标志。为了提高 GPU 并发工作执行的潜力，建议用户创建非阻塞 CUDA 流。

还建议用户选择足以解决其问题的最不通用的同步选项。 例如，如果要求 CPU 等待（阻止）特定 CUDA 流上的所有工作完成， 使用 cudaStreamSynchronize() 对于该流最好是 cudaDeviceSynchronize()，因为后者将不必要地等待设备的所有 CUDA 流上的 GPU 工作完成。 如果要求CPU等待而不阻塞，那么使用 cudaStreamQuery() 并在轮询循环中检查其返回值可能更可取。

使用CUDA事件也可以实现类似的同步效果（CUDA 活动），例如，通过在该流上记录事件并调用 cudaEventSynchronize() 以阻塞方式等待在该事件中捕获的工作完成。 同样，这比使用更可取且更集中 cudaDeviceSynchronize()。 呼唤 cudaEventQuery() 并检查其返回值（例如，在轮询循环中）将是一种非阻塞替代方案。

如果此操作发生在应用程序的关键路径中，则显式同步方法的选择尤其重要。 表4 提供各种同步选项的高级摘要 与主人。

对于同步，即表达 CUDA 流之间的依赖关系，建议使用非定时 CUDA 事件，如中所述 CUDA 活动。 用户可以调用 cudaStreamWaitEvent() 强制未来在特定流上提交的操作等待先前记录的事件（例如，在另一个流上）的完成。 请注意，对于等待或查询事件的任何 CUDA API，用户有责任确保 cudaEventRecord API 已被调用， 作为未记录的事件将始终返回成功。

默认情况下，CUDA 事件携带计时信息，因为它们可用于 cudaEventElapsedTime() API 调用。 然而，仅用于表达跨流的依赖关系的 CUDA 事件不需要计时信息。 对于这种情况，建议创建禁用计时信息的事件以提高性能。这可以使用 cudaEventCreateWithFlags() 应用程序编程接口 与 cudaEventDisableTiming 标志。

3.1.3.1. 流优先级#

流的相对优先级可以在创建时指定 cudaStreamCreateWithPriority()。允许的优先级范围，按[最高优先级，最低优先级]排序，可以使用以下命令获得 cudaDeviceGetStreamPriorityRange() 功能。在运行时，GPU 调度程序利用流优先级来确定任务执行顺序，但这些优先级仅作为提示而不是保证。选择要启动的工作时，高优先级流中的待处理任务优先于低优先级流中的待处理任务。高优先级任务不会抢占已经运行的低优先级任务。 GPU 在任务执行期间不会重新评估工作队列，并且增加流的优先级不会中断正在进行的工作。流优先级会影响任务执行，而无需强制执行严格的排序，因此用户可以利用流优先级来影响任务执行，而无需依赖严格的排序保证。

以下代码示例获取当前设备允许的优先级范围，并创建两个具有最高和最低可用优先级的非阻塞 CUDA 流。

// 获取该设备的流优先级范围
int leastPriority, greatestPriority;
cudaDeviceGetStreamPriorityRange(&leastPriority, &greatestPriority);

// 创建具有最高和最低可用优先级的流
cudaStream_t st_high, st_low;
cudaStreamCreateWithPriority(&st_high, cudaStreamNonBlocking, greatestPriority));
cudaStreamCreateWithPriority(&st_low, cudaStreamNonBlocking, leastPriority);

3.1.3.2. 显式同步#

如前所述，流可以通过多种方式与其他流同步。下面提供了不同粒度级别的常用方法： - cudaDeviceSynchronize() 等待直到所有主机线程的所有流中的所有先前命令都完成。 - cudaStreamSynchronize()将流作为参数并等待，直到给定流中的所有先前命令都完成。它可用于将主机与特定流同步，从而允许其他流继续在设备上执行。 - cudaStreamWaitEvent()接受一个流和一个事件作为参数（参见 CUDA 活动 事件的描述）并使所有命令在调用后添加到给定流 cudaStreamWaitEvent()延迟执行直到给定事件完成。 - cudaStreamQuery()为应用程序提供了一种方法来了解流中所有前面的命令是否已完成。

3.1.3.3. 隐式同步#

如果主机线程在来自不同流的两个命令之间发出以下任一操作，则它们不能同时运行：

  • 页锁定主机内存分配

  • 设备内存分配

  • 设备内存集

  • 两个地址之间的内存复制到同一设备内存

  • 任何 CUDA 命令到 NULL 流

  • L1/共享内存配置之间的切换

需要依赖性检查的操作包括与正在检查的启动相同的流中的任何其他命令 以及任何致电 cudaStreamQuery() 在那条流上。因此，应用程序应遵循这些指南来改进 它们并发内核执行的潜力：

  • 所有独立操作应在相关操作之前发出，

  • 任何类型的同步都应尽可能延迟。

3.1.4. 程序化依赖内核启动#

正如我们之前讨论的，CUDA Streams 的语义是内核按顺序执行。这样，如果我们有两个连续的内核，其中第二个内核依赖于第一个内核的结果，那么程序员可以放心地知道，当第二个内核开始执行时，相关数据将可用。然而，可能的情况是，第一个内核可以将后续内核所依赖的数据写入全局内存，并且它仍然有更多的工作要做。同样，依赖的第二内核在需要来自第一内核的数据之前可能有一些独立的工作。在这种情况下，两个内核的执行可能会部分重叠（假设硬件资源可用）。重叠也可能会重叠第二个内核的启动开销。除了硬件资源的可用性之外，能够实现的重叠程度还取决于内核的具体结构，例如

  • 第一个内核在执行过程中何时完成第二个内核所依赖的工作？

  • 第二个内核在执行过程中何时开始处理来自第一个内核的数据？

由于这在很大程度上取决于所讨论的特定内核，因此很难完全自动化，因此 CUDA 提供了一种机制来允许应用程序开发人员指定两个内核之间的同步点。这是通过称为“编程相关内核启动”的技术来完成的。情况如下图所示。

PDL 具有三个主要组成部分。

  1. 第一个内核（所谓的 主内核）需要调用一个特殊的函数来表明它已经完成了后续依赖内核（也称为 二级内核）将需要。这是通过调用函数来完成的 cudaTriggerProgrammaticLaunchCompletion().

  2. 反过来，依赖的辅助内核需要指示它已经完成了独立于主内核的工作部分，并且它现在正在等待主内核完成它所依赖的工作。这是通过函数完成的 cudaGridDependencySynchronize().

  3. 第二个内核需要使用特殊属性启动 cudaLaunchAttributeProgrammaticStreamSerialization 以其 programmaticStreamSerializationAllowed 字段设置为“1”。

以下代码片段显示了如何完成此操作的示例。

清单 3 具有两个内核的程序化依赖内核启动示例#
__global__ void primary_kernel() {
    // 启动辅助内核之前应完成的初始工作

    // 触发二级内核
    cudaTriggerProgrammaticLaunchCompletion();

    // 可以与辅助内核重合的工作
}

__global__ void secondary_kernel()
{
    // 初始化、独立工作等

    // 将阻塞，直到辅助内核依赖的所有主内核都已完成
    // 完成并将结果刷新到全局内存
    cudaGridDependencySynchronize();

    // 依赖工作
}

// 使用特殊属性启动辅助内核

// 设置属性
cudaLaunchAttribute attribute[1];
attribute[0].id = cudaLaunchAttributeProgrammaticStreamSerialization;
attribute[0].val.programmaticStreamSerializationAllowed = 1;

// 在内核启动配置中设置属性
 cudaLaunchConfig_t config = {0};

// 基础启动配置
config.gridDim = grid_dim;
config.blockDim = block_dim;
config.dynamicSmemBytes= 0;
config.stream = stream;

// 为 PDL 添加特殊属性
config.attrs = attribute;
config.numAttrs = 1;

// 启动主内核
primary_kernel<<<grid_dim, block_dim, 0, stream>>>();

// 使用配置启动辅助（依赖）内核
// 属性
cudaLaunchKernelEx(&config, secondary_kernel);

3.1.5. 批量内存传输#

CUDA 开发中的常见模式是使用批处理技术。通过批处理，我们粗略地表示我们将多个（通常较小的）任务组合在一起形成一个（通常较大的）操作。批次中的成分不一定全部相同，尽管它们通常是相同的。这个想法的一个例子是 cuBLAS 提供的批量矩阵乘法运算。

一般来说，与 CUDA 图形和 PDL 一样，批处理的目的是减少与单独分派各个批处理任务相关的开销。就内存传输而言，启动内存传输可能会产生一些 CPU 和驱动程序开销。此外，常规 cudaMemcpyAsync() 当前形式的功能不一定能为驾驶员提供足够的信息来优化传输，例如有关源和目的地的提示。在 Tegra 平台上，可以选择使用 SM 或复制引擎 (CE) 来执行传输。当前的选择是由驱动程序中的启发式指定的。这可能很重要，因为使用 SM 可能会导致更快的传输，但它会限制一些可用的计算能力。另一方面，使用 CE 可能会导致传输速度变慢，但总体应用程序性能更高，因为它使 SM 可以自由地执行其他工作。

这些考虑激发了设计的动机 cudaMemcpyBatchAsync() 函数（及其相关函数 cudaMemcpyBatch3DAsync()）。 这些函数允许优化批量内存传输。除了源和目标指针列表之外，该 API 还使用内存复制属性来指定排序期望，并提示源和目标位置，以及是否愿意将传输与计算重叠（目前仅在具有 CE 的 Tegra 平台上支持这一功能）。

让我们首先考虑从固定主机内存到固定设备内存的简单批量数据传输的最简单情况

清单 4 从固定主机内存到固定设备内存的同质批量内存传输示例#
std::vector<void *> srcs(batch_size);
std::vector<void *> dsts(batch_size);
std::vector<void *> sizes(batch_size);

// 分配源缓冲区和目标缓冲区
// 使用流编号进行初始化
for (size_t i = 0; i < batch_size; i++) {
    cudaMallocHost(&srcs[i], sizes[i]);
    cudaMalloc(&dsts[i], sizes[i]);
    cudaMemsetAsync(srcs[i], sizes[i], stream);
}

// 设置该批次副本的属性
cudaMemcpyAttributes attrs = {};
attrs.srcAccessOrder = cudaMemcpySrcAccessOrderStream;

// 批次中的所有副本都具有相同的副本属性。
size_t attrsIdxs = 0;  // 属性索引

// 启动批量内存传输
cudaMemcpyBatchAsync(&dsts[0], &srcs[0], &sizes[0], batch_size,
    &attrs, &attrsIdxs, 1 /* 属性数 */, nullptr /* 失败IDx */, stream);

前几个参数 cudaMemcpyBatchAsync() 函数看起来立即有意义。它们由包含源指针和目标指针以及传输大小的数组组成。每个数组必须有“batch_size”元素。新的信息来自属性。该函数需要一个指向属性数组的指针以及相应的属性索引数组。原则上，也可以传递一个数组 size_t 在这个数组中，可以记录失败传输的索引，但是传递一个失败的索引是安全的 nullptr 在这种情况下，故障指数将不会被记录。

转向属性，在这种情况下，传输是同构的。所以我们只使用一个属性，该属性将应用于 所有转账。这是由 attrIndex 参数。原则上这可以是一个数组。元素 i 该数组包含第一个传输的索引 i应用属性数组的第 -th 元素。 在这种情况下， attrIndex 被视为单个元素数组，值“0”表示 attribute[0] 将适用于索引为 0 及以上的所有传输，换句话说，所有传输。

最后，我们注意到我们已经设置了 srcAccessOrder 归因于 cudaMemcpySrcAccessOrderStream。这意味着将按常规流顺序访问源数据。换句话说，memcpy 将阻塞，直到处理来自任何这些源指针和目标指针的数据的先前内核完成。

在下一个示例中，我们将考虑异构批量传输的更复杂的情况。

清单 5 使用一些临时主机内存到固定设备内存的异构批量内存传输示例#
std::vector<void *> srcs(batch_size);
std::vector<void *> dsts(batch_size);
std::vector<void *> sizes(batch_size);

// 分配 src 和 dst 缓冲区
for (size_t i = 0; i < batch_size - 10; i++) {
    cudaMallocHost(&srcs[i], sizes[i]);
    cudaMalloc(&dsts[i], sizes[i]);
}

int buffer[10];

for (size_t i = batch_size - 10; i < batch_size; i++) {
    srcs[i] = &buffer[10 - (batch_size - i];
    cudaMalloc(&dsts[i], sizes[i]);
}

// 设置该批次副本的属性
cudaMemcpyAttributes attrs[2] = {};
attrs[0].srcAccessOrder = cudaMemcpySrcAccessOrderStream;
attrs[1].srcAccessOrder = cudaMemcpySrcAccessOrderDuringApiCall;

size_t attrsIdxs[2];
attrsIdxs[0] = 0;
attrsIdxs[1] = batch_size - 10;

// 启动批量内存传输
cudaMemcpyBatchAsync(&dsts[0], &srcs[0], &sizes[0], batch_size,
    &attrs, &attrsIdxs, 2 /* 属性数 */, nullptr /* 失败IDx */, stream);

这里我们有两种传输方式： batch_size-10 从固定主机内存传输到固定设备内存， 10 次从主机阵列到固定设备内存的传输。此外， buffer 数组不仅存在于主机上，而且只存在于当前作用域中——它的地址就是所谓的 临时指针。 API 调用完成后（异步），该指针可能无效。要使用此类临时指针执行复制， srcAccessOrder 属性中必须设置为 cudaMemcpySrcAccessOrderDuringApiCall.

我们现在有两个属性，第一个属性适用于索引从 0 开始且小于 batch_size-10。第二个适用于所有索引起始于 batch_size-10 并且小于 batch_size.

如果不是分配 buffer 堆栈中的数组，我们使用以下方法从堆中分配了它 malloc 数据将不再是短暂的。它在指针被显式释放之前一直有效。在这种情况下，如何暂存副本的最佳选择将取决于系统是否具有硬件管理的内存或通过地址转换对主机内存进行一致的 GPU 访问，在这种情况下，最好使用流排序，或者是否没有，在这种情况下，立即暂存传输最有意义。在这种情况下，应该使用该值 cudaMemcpyAccessOrderAny 为 srcAccessOrder 的属性。

cudaMemcpyBatchAsync 函数还允许程序员提供有关源位置和目标位置的提示。这是通过设置来完成的 srcLocation 或 dstLocation 的领域 cudaMemcpyAttributes 结构。的 srcLocation``and ``dstLocation 字段都是类型 cudaMemLocation 这是一个包含位置类型和位置 ID 的结构。这是一样的 cudaMemLocation 使用时可用于向运行时提供预取提示的结构 cudaMemPrefetchAsync()。我们在下面的代码示例中说明了如何设置从设备传输到主机的特定 NUMA 节点的提示：

清单 6 设置源和目标位置提示的示例#
// 分配源缓冲区和目标缓冲区
std::vector<void *> srcs(batch_size);
std::vector<void *> dsts(batch_size);
std::vector<void *> sizes(batch_size);

// 我们将使用 cudaMemLocation 结构提供位置提示
// 设备device_id
cudaMemLocation srcLoc = {cudaMemLocationTypeDevice, dev_id};

// 具有 numa 节点 numa_id 的主机
cudaMemLocation dstLoc = {cudaMemLocationTypeHostNuma, numa_id};

// 分配 src 和 dst 缓冲区
for (size_t i = 0; i < batch_size; i++) {
    cudaMallocManaged(&srcs[i], sizes[i]);
    cudaMallocManaged(&dsts[i], sizes[i]);

    cudaMemPrefetchAsync(srcs[i], sizes[i], srcLoc, 0, stream);
    cudaMemPrefetchAsync(dsts[i], sizes[i], dstLoc, 0, stream);
    cudaMemsetAsync(srcs[i], sizes[i], stream);
}

// 设置该批次副本的属性
cudaMemcpyAttributes attrs = {};

// 这些是托管内存指针，因此流顺序是合适的
attrs.srcAccessOrder = cudaMemcpySrcAccessOrderStream;

// 现在我们可以在此处指定位置提示。
attrs.srcLocHint = srcLoc;
attrs.dstlocHint = dstLoc;

// 批次中的所有副本都具有相同的副本属性。
size_t attrsIdxs = 0;

// 启动批量内存传输
cudaMemcpyBatchAsync(&dsts[0], &srcs[0], &sizes[0], batch_size,
    &attrs, &attrsIdxs, 1 /* 属性数 */, nullptr /* 失败IDx */, stream);

最后要介绍的是用于暗示我们是否要使用 SM 还是 CE 进行传输的标志。 该字段是 cudaMemcpyAttributesflags::flags 可能的值为：

  • cudaMemcpyFlagDefault – 默认行为

  • cudaMemcpyFlagPreferOverlapWithCompute – 这暗示系统应该更喜欢使用 CE 来进行与计算重叠的传输。该标志在非 Tegra 平台上会被忽略

综上所述，关于“cudaMemcpyBatchAsync”的要点如下：

  • cudaMemcpyBatchAsync 函数（及其 3D 变体）允许程序员指定一批内存传输，从而允许分摊传输设置开销。

  • 除了源和目标指针以及传输大小之外，该函数还可以采用一个或多个内存复制属性，这些属性提供有关正在传输的内存类型和源指针的相应流排序行为的信息、有关源和目标位置的提示，以及是否更愿意将传输与计算重叠（如果可能）或是否使用 SM 进行传输的提示。

  • 鉴于上述信息，运行时可以尝试最大程度地优化传输。

3.1.6. 环境变量#

CUDA提供了各种环境变量（参见 第 5.2 节），这会影响执行和性能。 如果没有显式设置它们，CUDA 会为它们使用合理的默认值，但是 根据具体情况可能需要进行特殊处理，例如出于调试目的或提高性能。

例如，增加 CUDA_DEVICE_MAX_CONNECTIONS 环境变量可能是必要的，以减少以下可能性 由于错误的依赖关系，来自不同 CUDA 流的独立工作被序列化。当以下情况时可能会引入这种错误的依赖关系： 使用相同的底层资源。 建议从使用默认值开始，并且仅在出现性能问题（例如，独立的意外序列化）时探索此环境变量的影响 跨 CUDA 流工作不能归因于其他因素（例如缺乏可用的 SM 资源）。 值得注意的是，对于 MPS，该环境变量具有不同的（较低的）默认值。

同样，设置 CUDA_MODULE_LOADING 环境变量为 EAGER 可能更可取 对于延迟敏感的应用程序，为了转移所有开销 由于模块加载到应用程序初始化阶段并超出其关键阶段。当前默认模式是延迟模块加载。 在这种默认模式下，可以实现与急切模块加载类似的效果 通过在应用程序的初始化阶段添加各种内核的“预热”调用，以强制模块加载更快发生。

请参考 CUDA 环境变量 有关各种 CUDA 环境变量的更多详细信息。 建议您将环境变量设置为新值 before 您启动应用程序；尝试在您的应用程序中设置它们 可能没有效果。
