3.1. 高级 CUDA API 与特性#

本节介绍更高级的 CUDA API 与特性的用法。这些主题通常不需要修改 CUDA 内核，但仍可从主机端影响应用级行为，包括 GPU 工作的执行方式与性能，以及 CPU 端性能。

3.1.1. cudaLaunchKernelEx#

早期 CUDA 引入 三尖括号语法 时，一个内核的 执行配置 只有四个可编程参数：线程块维度、网格维度、动态共享内存大小（可选，未指定时为 0）以及流（未指定时使用默认流）。

某些 CUDA 特性可受益于内核启动时附带的额外属性和提示。cudaLaunchKernelEx 允许程序通过 cudaLaunchConfig_t 结构设置上述执行配置参数。此外，cudaLaunchConfig_t 结构还允许程序传入零个或多个 cudaLaunchAttributes，用于控制或建议内核启动的其他参数。例如，本章后面讨论的 cudaLaunchAttributePreferredSharedMemoryCarveout（见 配置 L1/共享内存平衡）就是通过 cudaLaunchKernelEx 指定的。稍后还会讨论 cudaLaunchAttributeClusterDimension 属性，它用于指定内核启动所需的簇大小。

受支持属性及其含义的完整列表见 CUDA Runtime API 参考文档。

3.1.2. 启动簇#

前面几节介绍过 线程块簇。它是计算能力 9.0 及更高版本中可用的可选线程块组织层级，可让应用保证同一簇内的线程块在单个 GPC 上同时执行。这样，规模大于单个 SM 所能容纳的线程组也能交换数据并相互同步。

第 2.1.10.1 节 展示了如何使用三尖括号语法指定并启动使用簇的内核。在该示例中，__cluster_dims__ 注解用于指定启动内核时必须使用的簇维度。使用三尖括号语法时，簇大小是隐式确定的。

3.1.2.1. 使用 cudaLaunchKernelEx 启动簇#

与 使用三尖括号语法启动簇内核 不同，线程块簇的大小可以按每次启动分别配置。下面的代码示例展示了如何使用 cudaLaunchKernelEx 启动簇内核。

// 内核定义
// 内核没有附加编译时属性
__global__ void cluster_kernel(float *input, float* output)
{

}

int main()
{
    float *input, *output;
    dim3 threadsPerBlock(16, 16);
    dim3 numBlocks(N / threadsPerBlock.x, N / threadsPerBlock.y);

    // 使用运行时簇大小的内核调用
    {
        cudaLaunchConfig_t config = {0};
        // 网格维度不受簇启动影响，仍按线程块数量枚举。
        // 网格尺寸应该是簇大小的倍数。
        config.gridDim = numBlocks;
        config.blockDim = threadsPerBlock;

        cudaLaunchAttribute attribute[1];
        attribute[0].id = cudaLaunchAttributeClusterDimension;
        attribute[0].val.clusterDim.x = 2; // X 维度上的簇大小
        attribute[0].val.clusterDim.y = 1;
        attribute[0].val.clusterDim.z = 1;
        config.attrs = attribute;
        config.numAttrs = 1;

        cudaLaunchKernelEx(&config, cluster_kernel, input, output);
    }
}

与线程块簇相关的 cudaLaunchAttribute 类型有两个：cudaLaunchAttributeClusterDimension 和 cudaLaunchAttributePreferredClusterDimension。

属性 ID cudaLaunchAttributeClusterDimension 指定执行簇所需的维度。该属性的值 clusterDim 是一个三维值。网格在 x、y、z 各维上的大小，必须能被指定簇维度的对应维度整除。设置该属性类似于在编译时对内核定义使用 __cluster_dims__ 属性（见 使用三尖括号语法启动簇），但它可以在运行时针对同一内核的不同启动进行调整。

在计算能力 10.0 及更高的 GPU 上，另一个属性 ID cudaLaunchAttributePreferredClusterDimension 允许应用程序额外指定簇的首选维度。首选维度必须是最小簇维度的整数倍；最小簇维度可由内核上的 __cluster_dims__ 属性指定，也可由传给 cudaLaunchKernelEx 的 cudaLaunchAttributeClusterDimension 属性指定。换言之，除了首选簇维度外，还必须指定最小簇维度。网格在 x、y、z 各维上的大小，也必须能被指定首选簇维度的对应维度整除。

所有线程块都会在至少具备最小簇维度的簇中执行。在条件允许时会使用首选维度的簇，但并不保证所有簇都按首选维度执行。所有线程块都会在最小簇维度或首选簇维度的簇中执行。使用首选簇维度的内核，必须写成在最小或首选簇维度下都能正确运行。

3.1.2.2. 块作为簇#

当内核使用 __cluster_dims__ 注解定义时，网格中的簇数是隐式的，可由网格大小除以指定簇大小得到。

__cluster_dims__((2, 2, 2)) __global__ void foo();

// 8x8x8 个簇，每个簇包含 2x2x2 个线程块。
foo<<<dim3(16, 16, 16), dim3(1024, 1, 1)>>>();

在上面的示例中，内核以 16x16x16 个线程块组成的网格启动，这意味着实际使用的是 8x8x8 个簇组成的网格。

内核也可以使用 __block_size__ 注解，在定义内核时同时指定所需线程块大小和簇大小。使用该注解时，三尖括号启动中的网格维度表示簇数量，而不是线程块数量，如下所示。

// 每个线程块有多少线程、每个簇有多少线程块，
// 都作为内核属性处理。
__block_size__((1024, 1, 1), (2, 2, 2)) __global__ void foo();

// 8x8x8 簇。
foo<<<dim3(8, 8, 8)>>>();

__block_size__ 需要两个字段，每个字段都是包含 3 个元素的元组。第一个元组表示线程块维度，第二个元组表示簇大小；如果未传入第二个元组，则假定为 (1,1,1)。若要指定流，必须在 <<<>>> 中把第二、第三个参数分别传为 1 和 0，最后再传入流。传递其他值会导致未定义行为。

需要注意，不能同时指定 __block_size__ 的第二个元组和 __cluster_dims__。将 __block_size__ 与空的 __cluster_dims__ 一起使用也是非法的。当指定了 __block_size__ 的第二个元组时，就表示启用了“块作为簇”，编译器会把 <<<>>> 中的第一个参数识别为簇数量，而不是线程块数量。

3.1.3. 关于流和事件的更多内容#

CUDA 流 已介绍 CUDA 流的基础知识。默认情况下，提交到同一个 CUDA 流的操作会串行执行：前一个操作完成后，下一个操作才能开始。唯一例外是较新的 程序化依赖启动和同步 特性。使用多个 CUDA 流是实现并发执行的一种方法；另一种方法是使用 CUDA 图。两种方法也可以结合使用。

提交到不同 CUDA 流的工作在特定条件下可能并发执行，例如没有事件依赖、没有隐式同步且资源足够时。

如果在来自不同 CUDA 流的独立操作之间，向 NULL 流提交了任何 CUDA 操作，那么这些独立操作不能并发运行，除非相关流是非阻塞 CUDA 流。非阻塞流可通过 cudaStreamCreateWithFlags() Runtime API 搭配 cudaStreamNonBlocking 标志创建。为了提高 GPU 工作并发执行的可能性，建议用户创建非阻塞 CUDA 流。

还建议用户选择足以解决问题的最窄同步选项。例如，如果需要 CPU 等待（阻塞）某个特定 CUDA 流上的所有工作完成，那么对该流使用 cudaStreamSynchronize() 通常优于 cudaDeviceSynchronize()，因为后者会不必要地等待该设备所有 CUDA 流上的 GPU 工作完成。如果需要 CPU 等待但不阻塞，则可以使用 cudaStreamQuery() 并在轮询循环中检查其返回值。

使用 CUDA 事件也可以实现类似的同步效果（见 CUDA 事件）。例如，可以在某个流上记录事件，然后调用 cudaEventSynchronize()，以阻塞方式等待该事件捕获的工作完成。同样，这比使用 cudaDeviceSynchronize() 更集中、更合适。调用 cudaEventQuery() 并检查其返回值（例如在轮询循环中）则是一种非阻塞替代方案。

如果同步操作位于应用程序关键路径上，显式同步方法的选择尤其重要。表 4 从较高层次总结了与主机同步的各种选项。

对于用于表达 CUDA 流之间依赖关系的同步，建议使用非计时 CUDA 事件，如 CUDA 事件 中所述。用户可以调用 cudaStreamWaitEvent()，强制之后提交到某个流的操作等待先前记录的事件完成，例如等待另一个流上的事件。需要注意，对于任何等待或查询事件的 CUDA API，用户都必须确保已经调用过 cudaEventRecord()；未记录的事件始终会返回成功。

默认情况下，CUDA 事件会携带计时信息，因为它们可用于 cudaEventElapsedTime() API 调用。但如果事件只用于表达跨流依赖，就不需要计时信息。此时建议创建禁用计时的事件以提升性能，可通过 cudaEventCreateWithFlags() API 搭配 cudaEventDisableTiming 标志实现。

3.1.3.1. 流优先级#

流的相对优先级可以在创建时通过 cudaStreamCreateWithPriority() 指定。允许的优先级范围按 [最高优先级，最低优先级] 排列，可通过 cudaDeviceGetStreamPriorityRange() 查询。运行时，GPU 调度器会利用流优先级决定任务执行顺序，但优先级只是提示而非保证。选择要启动的工作时，高优先级流中的待处理任务会优先于低优先级流中的待处理任务；但高优先级任务不会抢占已经运行的低优先级任务。GPU 在任务执行期间不会重新评估工作队列，提高某个流的优先级也不会中断正在执行的工作。流优先级会影响任务执行，但不强制严格排序，因此用户可以用它影响调度，而不应依赖它提供严格顺序保证。

以下代码示例获取当前设备允许的优先级范围，并创建两个具有最高和最低可用优先级的非阻塞 CUDA 流。

// 获取该设备的流优先级范围
int leastPriority, greatestPriority;
cudaDeviceGetStreamPriorityRange(&leastPriority, &greatestPriority);

// 创建具有最高和最低可用优先级的流
cudaStream_t st_high, st_low;
cudaStreamCreateWithPriority(&st_high, cudaStreamNonBlocking, greatestPriority));
cudaStreamCreateWithPriority(&st_low, cudaStreamNonBlocking, leastPriority);

3.1.3.2. 显式同步#

如前所述，流可以通过多种方式与其他流同步。不同粒度下的常用方法包括：

  • cudaDeviceSynchronize()：等待所有主机线程的所有流中此前提交的命令全部完成。

  • cudaStreamSynchronize()：接收一个流作为参数，并等待该流中此前提交的命令全部完成。它可用于让主机与特定流同步，同时允许其他流继续在设备上执行。

  • cudaStreamWaitEvent()：接收一个流和一个事件作为参数（事件说明见 CUDA 事件），并让调用之后添加到该流的所有命令延迟执行，直到给定事件完成。

  • cudaStreamQuery()：让应用程序查询流中此前的命令是否都已完成。

3.1.3.3. 隐式同步#

如果主机线程在来自不同流的两个命令之间发出以下任一操作，则它们不能同时运行：

  • 页锁定主机内存分配

  • 设备内存分配

  • 设备内存集

  • 两个地址之间的内存复制到同一设备内存

  • 任何 CUDA 命令到 NULL 流

  • L1/共享内存配置之间的切换

需要依赖性检查的操作包括与正在检查的启动相同的流中的任何其他命令 以及任何致电 cudaStreamQuery() 在那条流上。因此，应用程序应遵循这些指南来改进 它们并发内核执行的潜力：

  • 所有独立操作应在相关操作之前发出，

  • 任何类型的同步都应尽可能延迟。

3.1.4. 程序化依赖内核启动#

如前所述，CUDA 流的语义要求内核按顺序执行。这样，如果有两个连续内核，且第二个内核依赖第一个内核的结果，程序员就可以确信：当第二个内核开始执行时，它所依赖的数据已经可用。不过，有些情况下，第一个内核已经把后续内核依赖的数据写入全局内存，但自己仍有其他工作要做；同样，依赖它的第二个内核在真正需要这些数据之前，也可能有一段独立工作可先执行。在这种情况下，只要硬件资源可用，两个内核的执行就可能部分重叠；这种重叠还可以覆盖第二个内核的启动开销。除硬件资源外，能重叠到什么程度还取决于内核本身的结构，例如：

  • 第一个内核在执行到何处时完成第二个内核所依赖的工作？

  • 第二个内核在执行到何处时开始处理来自第一个内核的数据？

由于这些信息高度依赖具体内核，完全自动化很困难，因此 CUDA 提供了一种机制，允许应用开发者显式指定两个内核之间的同步点。这项技术称为“程序化依赖内核启动”（Programmatic Dependent Kernel Launch，PDL）。下图展示了这种情况。

PDL 包含三个主要组成部分。

  1. 第一个内核（即 主内核）需要调用一个特殊函数，表明它已经完成后续依赖内核（也称 辅助内核）所需的全部工作。这通过调用 cudaTriggerProgrammaticLaunchCompletion() 完成。

  2. 相应地，依赖主内核的辅助内核需要表明：它已经执行到不再有独立于主内核的工作可做，接下来要等待主内核完成它依赖的那部分工作。这通过 cudaGridDependencySynchronize() 完成。

  3. 第二个内核需要使用特殊属性 cudaLaunchAttributeProgrammaticStreamSerialization 启动，并将其 programmaticStreamSerializationAllowed 字段设置为 1。

下面的代码片段展示了如何完成这一过程。

清单 3 具有两个内核的程序化依赖内核启动示例#
__global__ void primary_kernel() {
    // 启动辅助内核之前应完成的初始工作

    // 触发二级内核
    cudaTriggerProgrammaticLaunchCompletion();

    // 可以与辅助内核重叠执行的工作
}

__global__ void secondary_kernel()
{
    // 初始化、独立工作等

    // 将阻塞，直到辅助内核依赖的所有主内核都已完成
    // 完成并将结果刷新到全局内存
    cudaGridDependencySynchronize();

    // 依赖工作
}

// 使用特殊属性启动辅助内核

// 设置属性
cudaLaunchAttribute attribute[1];
attribute[0].id = cudaLaunchAttributeProgrammaticStreamSerialization;
attribute[0].val.programmaticStreamSerializationAllowed = 1;

// 在内核启动配置中设置属性
 cudaLaunchConfig_t config = {0};

// 基础启动配置
config.gridDim = grid_dim;
config.blockDim = block_dim;
config.dynamicSmemBytes= 0;
config.stream = stream;

// 为 PDL 添加特殊属性
config.attrs = attribute;
config.numAttrs = 1;

// 启动主内核
primary_kernel<<<grid_dim, block_dim, 0, stream>>>();

// 使用配置启动辅助（依赖）内核
// 属性
cudaLaunchKernelEx(&config, secondary_kernel);

3.1.5. 批量内存传输#

CUDA 开发中常见的一种模式是批处理。所谓批处理，大致是把多个通常较小的任务组合成一个通常较大的操作。批次中的组成项不一定完全相同，虽然实践中它们往往相同。cuBLAS 提供的批量矩阵乘法就是这种思路的一个例子。

一般来说，与 CUDA 图和 PDL 类似，批处理的目标是减少逐个派发批内任务所产生的开销。对于内存传输，启动一次传输可能会带来 CPU 与驱动开销。此外，常规 cudaMemcpyAsync() 当前形式未必能向驱动提供足够信息来优化传输，例如源位置和目标位置提示。在 Tegra 平台上，传输可以选择由 SM 或复制引擎（CE）执行；当前选择由驱动中的启发式规则决定。这一点可能很重要：使用 SM 可能让传输更快，但会占用部分可用计算能力；使用 CE 可能让传输变慢，但能释放 SM 执行其他工作，从而带来更高的整体应用性能。

这些考虑促成了 cudaMemcpyBatchAsync() 及相关函数 cudaMemcpyBatch3DAsync() 的设计。这些函数允许优化批量内存传输。除了源指针列表和目标指针列表外，该 API 还使用内存复制属性来指定排序期望，并给出源位置、目标位置以及是否愿意让传输与计算重叠等提示；其中与计算重叠的提示目前仅在配备 CE 的 Tegra 平台上受支持。

先考虑最简单的情况：从页锁定主机内存到设备内存的一批简单数据传输。

清单 4 从页锁定主机内存到固定设备内存的同构批量内存传输示例#
std::vector<void *> srcs(batch_size);
std::vector<void *> dsts(batch_size);
std::vector<void *> sizes(batch_size);

// 分配源缓冲区和目标缓冲区
// 使用流编号进行初始化
for (size_t i = 0; i < batch_size; i++) {
    cudaMallocHost(&srcs[i], sizes[i]);
    cudaMalloc(&dsts[i], sizes[i]);
    cudaMemsetAsync(srcs[i], sizes[i], stream);
}

// 设置该批次副本的属性
cudaMemcpyAttributes attrs = {};
attrs.srcAccessOrder = cudaMemcpySrcAccessOrderStream;

// 批次中的所有复制都使用相同的复制属性。
size_t attrsIdxs = 0;  // 属性索引

// 启动批量内存传输
cudaMemcpyBatchAsync(&dsts[0], &srcs[0], &sizes[0], batch_size,
    &attrs, &attrsIdxs, 1 /* 属性数量 */, nullptr /* 失败索引 */, stream);

cudaMemcpyBatchAsync() 的前几个参数较容易理解：它们分别是源指针数组、目标指针数组以及传输大小数组。每个数组都必须包含 batch_size 个元素。新的信息来自属性。该函数需要一个指向属性数组的指针，以及对应的属性索引数组。原则上，也可以传入一个 size_t 数组来记录失败传输的索引；如果不需要记录失败索引，传入 nullptr 是安全的，此时不会记录失败索引。

再看属性。本例中的传输是同构的，因此只使用一个属性，并让它适用于所有传输。这由 attrIndex 参数控制。原则上，该参数可以是一个数组；数组元素 i 表示从哪个传输索引开始使用属性数组中的第 i 个元素。本例中，attrIndex 被视为只有一个元素且值为 0 的数组，表示 attribute[0] 会应用于索引 0 及之后的所有传输，也就是全部传输。

最后，示例将 srcAccessOrder 属性设置为 cudaMemcpySrcAccessOrderStream。这表示源数据将按常规流顺序访问。换言之，memcpy 会阻塞，直到此前处理这些源指针或目标指针数据的内核完成。

在下一个示例中，我们将考虑异构批量传输的更复杂的情况。

清单 5 包含部分临时主机内存到固定设备内存传输的异构批量内存传输示例#
std::vector<void *> srcs(batch_size);
std::vector<void *> dsts(batch_size);
std::vector<void *> sizes(batch_size);

// 分配 src 和 dst 缓冲区
for (size_t i = 0; i < batch_size - 10; i++) {
    cudaMallocHost(&srcs[i], sizes[i]);
    cudaMalloc(&dsts[i], sizes[i]);
}

int buffer[10];

for (size_t i = batch_size - 10; i < batch_size; i++) {
    srcs[i] = &buffer[10 - (batch_size - i];
    cudaMalloc(&dsts[i], sizes[i]);
}

// 设置该批次副本的属性
cudaMemcpyAttributes attrs[2] = {};
attrs[0].srcAccessOrder = cudaMemcpySrcAccessOrderStream;
attrs[1].srcAccessOrder = cudaMemcpySrcAccessOrderDuringApiCall;

size_t attrsIdxs[2];
attrsIdxs[0] = 0;
attrsIdxs[1] = batch_size - 10;

// 启动批量内存传输
cudaMemcpyBatchAsync(&dsts[0], &srcs[0], &sizes[0], batch_size,
    &attrs, &attrsIdxs, 2 /* 属性数量 */, nullptr /* 失败索引 */, stream);

这里有两类传输：前 batch_size-10 次是从页锁定主机内存到固定设备内存的传输，后 10 次是从主机数组到固定设备内存的传输。此外，buffer 数组不仅位于主机端，而且只在当前作用域内存在；它的地址就是所谓的临时指针。异步 API 调用返回后，该指针可能已经失效。要使用这类临时指针执行复制，必须将 srcAccessOrder 属性设置为 cudaMemcpySrcAccessOrderDuringApiCall。

现在有两个属性。第一个属性适用于从 0 开始且小于 batch_size-10 的索引；第二个属性适用于从 batch_size-10 开始且小于 batch_size 的所有索引。

如果 buffer 不是栈上数组，而是通过 malloc 从堆上分配，那么数据就不再是临时的；在显式释放指针之前，它一直有效。在这种情况下，如何暂存复制的最佳选择取决于系统特性：如果系统具有硬件管理内存，或通过地址转换对主机内存提供一致的 GPU 访问，那么最好使用流排序；否则，立即暂存传输通常最合理。此时应将 srcAccessOrder 属性设为 cudaMemcpyAccessOrderAny。

cudaMemcpyBatchAsync 函数还允许程序员提供源位置和目标位置提示。这通过设置 cudaMemcpyAttributes 结构中的 srcLocation 或 dstLocation 字段完成。srcLocation 和 dstLocation 字段类型都是 cudaMemLocation，该结构包含位置类型和位置 ID。这与使用 cudaMemPrefetchAsync() 向运行时提供预取提示时使用的 cudaMemLocation 结构相同。下面的代码示例展示了如何为从设备传输到主机端特定 NUMA 节点设置提示：

清单 6 设置源和目标位置提示的示例#
// 分配源缓冲区和目标缓冲区
std::vector<void *> srcs(batch_size);
std::vector<void *> dsts(batch_size);
std::vector<void *> sizes(batch_size);

// 我们将使用 cudaMemLocation 结构提供位置提示
// 设备device_id
cudaMemLocation srcLoc = {cudaMemLocationTypeDevice, dev_id};

// 具有 numa 节点 numa_id 的主机
cudaMemLocation dstLoc = {cudaMemLocationTypeHostNuma, numa_id};

// 分配 src 和 dst 缓冲区
for (size_t i = 0; i < batch_size; i++) {
    cudaMallocManaged(&srcs[i], sizes[i]);
    cudaMallocManaged(&dsts[i], sizes[i]);

    cudaMemPrefetchAsync(srcs[i], sizes[i], srcLoc, 0, stream);
    cudaMemPrefetchAsync(dsts[i], sizes[i], dstLoc, 0, stream);
    cudaMemsetAsync(srcs[i], sizes[i], stream);
}

// 设置该批次副本的属性
cudaMemcpyAttributes attrs = {};

// 这些是托管内存指针，因此流顺序是合适的
attrs.srcAccessOrder = cudaMemcpySrcAccessOrderStream;

// 现在我们可以在此处指定位置提示。
attrs.srcLocHint = srcLoc;
attrs.dstlocHint = dstLoc;

// 批次中的所有复制都使用相同的复制属性。
size_t attrsIdxs = 0;

// 启动批量内存传输
cudaMemcpyBatchAsync(&dsts[0], &srcs[0], &sizes[0], batch_size,
    &attrs, &attrsIdxs, 1 /* 属性数量 */, nullptr /* 失败索引 */, stream);

最后一个要介绍的是用于提示传输应使用 SM 还是 CE 的标志。该字段是 cudaMemcpyAttributes::flags，可能的取值包括：

  • cudaMemcpyFlagDefault：默认行为。

  • cudaMemcpyFlagPreferOverlapWithCompute：提示系统优先使用 CE 执行可与计算重叠的传输。该标志在非 Tegra 平台上会被忽略。

综上，关于 cudaMemcpyBatchAsync 的要点如下：

  • cudaMemcpyBatchAsync 函数及其 3D 变体允许程序员指定一批内存传输，从而摊薄传输设置开销。

  • 除源指针、目标指针和传输大小外，该函数还可接收一个或多个内存复制属性。这些属性可提供正在传输的内存类型、源指针对应的流排序行为、源位置与目标位置提示，以及在可能时是否更倾向让传输与计算重叠，或是否使用 SM 执行传输等信息。

  • 基于上述信息，运行时可以尝试尽可能优化传输。

3.1.6. 环境变量#

CUDA 提供了多种环境变量（见 第 5.2 节），这些变量会影响执行行为和性能。若未显式设置，CUDA 会使用合理默认值；但在调试或性能调优等场景下，可能需要根据具体情况进行专门设置。

例如，可能需要增大 CUDA_DEVICE_MAX_CONNECTIONS 环境变量，以降低不同 CUDA 流中的独立工作因伪依赖而被串行化的可能性。当多个流使用相同底层资源时，可能引入这类伪依赖。建议从默认值开始；只有在出现性能问题（例如跨 CUDA 流的独立工作发生意外串行化），且该问题无法归因于其他因素（如可用 SM 资源不足）时，再探索该环境变量的影响。需要注意的是，对于 MPS，该环境变量有不同且更低的默认值。

类似地，对于延迟敏感型应用，将 CUDA_MODULE_LOADING 环境变量设为 EAGER 可能更合适，这样可把模块加载开销转移到应用初始化阶段，避免出现在关键路径上。当前默认模式是延迟模块加载。在默认模式下，也可以通过在应用初始化阶段对各个内核执行“预热”调用，强制模块更早加载，从而获得类似 eager 模块加载的效果。

关于各种 CUDA 环境变量的更多细节，请参见 CUDA 环境变量。建议在启动应用程序之前设置环境变量的新值；尝试在应用程序内部设置它们可能不会生效。
