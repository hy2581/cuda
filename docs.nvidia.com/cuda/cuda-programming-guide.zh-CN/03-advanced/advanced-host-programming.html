3.1. 高级 CUDA API 与特性#

本节介绍更高级的 CUDA API 与特性。这些主题通常不需要修改 CUDA 内核代码，但仍可从主机侧影响应用层行为，包括 GPU 工作的执行与性能，以及 CPU 侧性能。

3.1.1. cudaLaunchKernelEx#

当最初版本引入三重尖括号语法时，内核的执行配置仅有四个可编程参数： - 线程块维度 - 网格维度 - 动态共享内存（可选，未指定时为 0） - 流（未指定时使用默认流）

某些 CUDA 特性可受益于内核启动时提供的额外属性与提示。cudaLaunchKernelEx 允许程序通过 cudaLaunchConfig_t 结构设置上述执行配置参数。此外，cudaLaunchConfig_t 还允许传入 0 个或多个 cudaLaunchAttributes，用于控制或建议其他启动参数。例如，本章稍后讨论的 cudaLaunchAttributePreferredSharedMemoryCarveout（见配置 L1/共享内存平衡）就是通过 cudaLaunchKernelEx 指定的。本章后文还会介绍 cudaLaunchAttributeClusterDimension 属性，用于指定期望的集群大小。

受支持属性及其含义的完整列表，请参见 CUDA Runtime API 参考文档。

3.1.2. 启动集群：#

前文介绍的线程块集群，是在计算能力 9.0 及以上可用的可选线程块组织层级。它使应用能够保证同一集群内的线程块在单个 GPC 上同时执行，从而让超过单个 SM 可容纳规模的更大线程组进行数据交换与同步。

第 2.1.10.1 节展示了如何使用三重尖括号语法指定并启动使用集群的 kernel。其中通过 __cluster_dims__ 注解来指定启动该 kernel 时必须使用的集群维度。使用三重尖括号语法时，集群大小是隐式确定的。

3.1.2.1. 使用 cudaLaunchKernelEx 启动集群#

不同于使用三重尖括号语法启动集群内核，线程块集群大小可按“每次启动”进行配置。下面代码示例展示了如何使用 cudaLaunchKernelEx 启动集群 kernel。

// Kernel definition
// No compile time attribute attached to the kernel
__global__ void cluster_kernel(float *input, float* output)
{

}

int main()
{
    float *input, *output;
    dim3 threadsPerBlock(16, 16);
    dim3 numBlocks(N / threadsPerBlock.x, N / threadsPerBlock.y);

    // Kernel invocation with runtime cluster size
    {
        cudaLaunchConfig_t config = {0};
        // The grid dimension is not affected by cluster launch, and is still enumerated
        // using number of blocks.
        // The grid dimension should be a multiple of cluster size.
        config.gridDim = numBlocks;
        config.blockDim = threadsPerBlock;

        cudaLaunchAttribute attribute[1];
        attribute[0].id = cudaLaunchAttributeClusterDimension;
        attribute[0].val.clusterDim.x = 2; // Cluster size in X-dimension
        attribute[0].val.clusterDim.y = 1;
        attribute[0].val.clusterDim.z = 1;
        config.attrs = attribute;
        config.numAttrs = 1;

        cudaLaunchKernelEx(&config, cluster_kernel, input, output);
    }
}

与线程块集群相关的 cudaLaunchAttribute 类型有两个：cudaLaunchAttributeClusterDimension 与 cudaLaunchAttributePreferredClusterDimension。

属性 id cudaLaunchAttributeClusterDimension 用于指定执行集群时所需维度。其取值 clusterDim 是一个三维值。网格对应维度（x、y、z）必须分别能被所设集群维度整除。该设置类似于在编译期于 kernel 定义处使用 __cluster_dims__（见三重尖括号中的集群启动），但它可以在运行时针对同一 kernel 的不同启动进行调整。

在计算能力 10.0 及以上 GPU 上，还可使用属性 id cudaLaunchAttributePreferredClusterDimension 额外指定集群的“首选维度”。首选维度必须是通过 kernel 的 __cluster_dims__ 或传给 cudaLaunchKernelEx 的 cudaLaunchAttributeClusterDimension 所指定“最小集群维度”的整数倍。也就是说，除了首选维度外，必须先指定最小集群维度。网格对应维度（x、y、z）还必须分别能被首选集群维度整除。

所有线程块都会在不小于最小集群维度的集群中执行。条件允许时会使用首选维度的集群，但不保证所有集群都按首选维度执行。线程块最终会在“最小维度”或“首选维度”两者之一的集群中运行。因此，使用首选集群维度的 kernels 必须在这两种维度下都能正确运行。

3.1.2.2. 将线程块视为集群#

当 kernel 使用 __cluster_dims__ 注解定义时，网格中的集群数是隐式的，可由网格大小除以指定集群大小得到。

__cluster_dims__((2, 2, 2)) __global__ void foo();

// 8x8x8 clusters each with 2x2x2 thread blocks.
foo<<<dim3(16, 16, 16), dim3(1024, 1, 1)>>>();

在上例中，kernel 以 16x16x16 线程块网格启动，这意味着实际使用的是 8x8x8 的集群网格。

kernel 还可使用 __block_size__ 注解，在定义时同时指定所需线程块大小与集群大小。使用该注解后，三重尖括号启动中的网格维度表示“集群数”而非“线程块数”，如下所示。

// Implementation detail of how many threads per block and blocks per cluster
// is handled as an attribute of the kernel.
__block_size__((1024, 1, 1), (2, 2, 2)) __global__ void foo();

// 8x8x8 clusters.
foo<<<dim3(8, 8, 8)>>>();

__block_size__ 需要两个字段，二者均为 3 元组。第一个元组表示线程块维度，第二个表示集群大小。若未传第二个元组，则默认为 (1,1,1)。若要指定 stream，需要在 <<<>>> 中将第二、第三参数设为 1 与 0，最后再传入 stream。传入其他值会导致未定义行为。

注意：不能同时指定 __block_size__ 的第二个元组与 __cluster_dims__；也不能在 __cluster_dims__ 为空时使用 __block_size__。当指定了 __block_size__ 的第二个元组时，意味着启用了“将线程块视为集群”，编译器会把 <<<>>> 内第一个参数解释为集群数而非线程块数。

3.1.3. 关于流与事件的更多内容#

CUDA 流一节介绍了 CUDA 流的基础。默认情况下，提交到同一 CUDA 流上的操作是串行的：前一个未完成，后一个不会开始。唯一例外是新近加入的程序化依赖启动与同步特性。启用并发执行的一种方式是使用多个 CUDA 流；另一种方式是使用 CUDA 图。两种方式也可结合使用。

提交到不同 CUDA 流上的工作在特定条件下可能并发执行，例如：不存在事件依赖、没有隐式同步、且资源充足等。

来自不同 CUDA 流的独立操作之间，如果夹入了任何提交到 NULL 流的 CUDA 操作，通常不能并发运行；除非这些流是非阻塞 CUDA 流。非阻塞流通过运行时 API cudaStreamCreateWithFlags() 并指定 cudaStreamNonBlocking 标志创建。为提升 GPU 并发执行潜力，建议用户创建非阻塞 CUDA 流。

还建议用户选择“足够满足问题需求且最不泛化”的同步选项。 例如，如果需求是让 CPU 等待（阻塞）某个特定 CUDA 流上的所有工作完成， 那么对该流调用 cudaStreamSynchronize() 会优于 cudaDeviceSynchronize()，因为后者会不必要地等待设备上所有 CUDA 流的 GPU 工作。 若需求是让 CPU 非阻塞等待，则可在轮询循环中调用 cudaStreamQuery() 并检查其返回值。

类似的同步效果也可通过 CUDA 事件（CUDA Events）实现，例如在该流上记录事件并调用 cudaEventSynchronize() 以阻塞方式等待该事件所覆盖工作完成。 同样，这比使用 cudaDeviceSynchronize() 更聚焦、也更推荐。 而调用 cudaEventQuery() 并检查返回值（例如在轮询循环中）则是非阻塞替代方案。

如果该同步操作位于应用关键路径，显式同步方法的选择尤为重要。 表 4 对与主机之间的多种同步选项做了高层总结。

在 CUDA 流之间做同步（即表达依赖关系）时，建议使用非计时事件，具体见 CUDA 事件。 用户可调用 cudaStreamWaitEvent()，让某个特定流上后续提交的操作等待此前已记录事件（例如其他流上的事件）完成。 请注意：对于任何等待或查询事件的 CUDA API，用户有责任确保已先调用 cudaEventRecord； 未记录的事件总会返回 success。

CUDA 事件默认携带计时信息，因为它们可用于 cudaEventElapsedTime()。 但若事件仅用于表达流间依赖，则不需要计时信息。 在这种情况下，为提升性能，建议创建“禁用计时”的事件。这可通过 cudaEventCreateWithFlags() 并指定 cudaEventDisableTiming 标志实现。

3.1.3.1. 流优先级#

可在创建流时通过 cudaStreamCreateWithPriority() 指定流的相对优先级。允许优先级范围（按 [最高优先级, 最低优先级] 排序）可通过 cudaDeviceGetStreamPriorityRange() 获取。运行时 GPU 调度器会利用流优先级决定任务执行顺序，但这些优先级是提示而非保证。选择待启动工作时，高优先级流中的待执行任务优先于低优先级流中的任务。高优先级任务不会抢占已在运行的低优先级任务。GPU 在任务执行中不会重新评估工作队列，提高流优先级也不会打断正在执行的工作。流优先级可影响执行，但不强制严格顺序；用户应将其作为调度倾向，而非严格顺序保证。

下面代码示例获取当前设备允许的优先级范围，并创建两个非阻塞 CUDA 流，分别使用可用的最高与最低优先级。

// get the range of stream priorities for this device
int leastPriority, greatestPriority;
cudaDeviceGetStreamPriorityRange(&leastPriority, &greatestPriority);

// create streams with highest and lowest available priorities
cudaStream_t st_high, st_low;
cudaStreamCreateWithPriority(&st_high, cudaStreamNonBlocking, greatestPriority));
cudaStreamCreateWithPriority(&st_low, cudaStreamNonBlocking, leastPriority);

3.1.3.2. 显式同步#

如前所述，流与流之间可通过多种方式同步。按粒度不同，常见方法如下： - cudaDeviceSynchronize()：等待所有主机线程的所有流中、此前提交的命令全部完成。 - cudaStreamSynchronize()：以某个流为参数，等待该流中此前提交的命令完成。可用于仅同步主机与特定流，同时让设备上的其他流继续执行。 - cudaStreamWaitEvent()：以流和事件为参数（事件见CUDA 事件），使该调用后加入该流的所有命令延迟执行，直到给定事件完成。 - cudaStreamQuery()：用于查询某个流中此前命令是否已全部完成。

3.1.3.3. 隐式同步#

若主机线程在两条不同流的两条命令之间插入以下任一操作，这两条命令将无法并发运行：

  • 分配页锁定（pinned）主机内存

  • 分配设备内存

  • 设备内存置值（memset）

  • 在同一设备内存上的两地址间执行内存拷贝

  • 向 NULL 流提交任意 CUDA 命令

  • 切换 L1/共享内存配置

需要进行依赖检查的操作包括：与被检查 launch 同一流中的其他任意命令，以及在该流上对 cudaStreamQuery() 的任何调用。因此，为提升 kernel 并发执行潜力，应用应遵循以下准则：

  • 先提交所有独立操作，再提交依赖操作；

  • 尽可能推迟任何形式的同步。

3.1.4. 编程式依赖内核启动#

如前所述，CUDA 流的语义决定了 kernels 按顺序执行。这样当两个 kernel 连续执行且第二个依赖第一个结果时，程序员可以确信：第二个 kernel 开始执行时，其依赖数据已经就绪。但在某些情况下，第一个 kernel 可能已经把后续 kernel 依赖的数据写入全局内存，却仍有其他工作未完成；同样，第二个依赖 kernel 在真正使用这些数据前也可能有一部分独立工作可先执行。此时（在硬件资源允许的前提下）可让两个 kernel 的执行部分重叠，这种重叠还可覆盖第二个 kernel 的部分启动开销。除硬件资源可用性外，可实现的重叠程度还取决于 kernel 的具体结构，例如：

  • 第一个 kernel 在执行到何时完成了第二个 kernel 所依赖的工作？

  • 第二个 kernel 在执行到何时开始处理来自第一个 kernel 的数据？

由于这高度依赖具体 kernel，很难完全自动化；因此 CUDA 提供了机制，允许应用开发者显式指定两个 kernel 之间的同步点。这一技术称为“编程式依赖内核启动（PDL）”。下图展示了该情形。

PDL 主要包含三个组成部分：

  1. 第一个 kernel（即 primary kernel）需要调用一个特殊函数，表明“后续依赖 kernel（即 secondary kernel）所需的数据/工作”已就绪。通过调用 cudaTriggerProgrammaticLaunchCompletion() 实现。

  2. 随后，依赖的 secondary kernel 需要表明自己已执行到“与 primary kernel 无关”的部分，并开始等待 primary kernel 完成其所依赖工作。通过 cudaGridDependencySynchronize() 实现。

  3. 第二个 kernel 启动时需要附带特殊属性 cudaLaunchAttributeProgrammaticStreamSerialization，并将其 programmaticStreamSerializationAllowed 字段设为 ‘1’。

下面代码片段展示了实现方式示例。

Listing 3 Example of 编程式依赖内核启动 with two Kernels#
__global__ void primary_kernel() {
    // Initial work that should finish before starting secondary kernel

    // Trigger the secondary kernel
    cudaTriggerProgrammaticLaunchCompletion();

    // Work that can coincide with the secondary kernel
}

__global__ void secondary_kernel()
{
    // Initialization, Independent work, etc.

    // Will block until all primary kernels the secondary kernel is dependent on have
    // completed and flushed results to global memory
    cudaGridDependencySynchronize();

    // Dependent work
}

// Launch the secondary kernel with the special attribute

// Set Up the attribute
cudaLaunchAttribute attribute[1];
attribute[0].id = cudaLaunchAttributeProgrammaticStreamSerialization;
attribute[0].val.programmaticStreamSerializationAllowed = 1;

// Set the attribute in a kernel launch configuration
 cudaLaunchConfig_t config = {0};

// Base launch configuration
config.gridDim = grid_dim;
config.blockDim = block_dim;
config.dynamicSmemBytes= 0;
config.stream = stream;

// Add special attribute for PDL
config.attrs = attribute;
config.numAttrs = 1;

// Launch primary kernel
primary_kernel<<<grid_dim, block_dim, 0, stream>>>();

// Launch secondary (dependent) kernel using the configuration with
// the attribute
cudaLaunchKernelEx(&config, secondary_kernel);

3.1.5. 批量内存传输#

CUDA 开发中的常见模式是“批处理（batching）”。所谓批处理，是将若干（通常较小）任务打包为一次（通常更大）操作。批内各组件不一定完全相同，尽管在实践中常常相似。cuBLAS 提供的批量矩阵乘法就是典型示例。

与 CUDA 图和 PDL 类似，批处理的目标是降低将批内任务逐个分发带来的额外开销。就内存传输而言，单次传输启动会产生一定 CPU 与驱动开销。并且当前形态的常规 cudaMemcpyAsync() 不一定为驱动提供足够信息来优化传输（例如源/目的位置提示）。在 Tegra 平台上，可选择用 SM 或拷贝引擎（CE）执行传输，当前由驱动启发式决定。该选择很关键：使用 SM 可能传输更快，但会占用部分计算能力；使用 CE 可能传输更慢，但因释放了 SM 去做其他工作，整体应用性能可能更高。

基于上述考虑，设计了 cudaMemcpyBatchAsync()（及其同类 cudaMemcpyBatch3DAsync()）。这些函数允许对批量内存传输进行优化。除源/目的指针列表外，API 还通过内存拷贝属性描述顺序预期、源/目的位置提示，以及是否偏好“传输与计算重叠”（当前仅 Tegra + CE 支持）。

先看最简单情形：从页锁定主机内存到页锁定设备内存的简单批量传输。

Listing 4 Example of Homogeneous Batched Memory Transfer from Pinned Host Memory to Pinned Device Memory#
std::vector<void *> srcs(batch_size);
std::vector<void *> dsts(batch_size);
std::vector<void *> sizes(batch_size);

// Allocate the source and destination buffers
// initialize with the stream number
for (size_t i = 0; i < batch_size; i++) {
    cudaMallocHost(&srcs[i], sizes[i]);
    cudaMalloc(&dsts[i], sizes[i]);
    cudaMemsetAsync(srcs[i], sizes[i], stream);
}

// Setup attributes for this batch of copies
cudaMemcpyAttributes attrs = {};
attrs.srcAccessOrder = cudaMemcpySrcAccessOrderStream;

// All copies in the batch have same copy attributes.
size_t attrsIdxs = 0;  // Index of the attributes

// Launch the batched memory transfer
cudaMemcpyBatchAsync(&dsts[0], &srcs[0], &sizes[0], batch_size,
    &attrs, &attrsIdxs, 1 /*numAttrs*/, nullptr /*failIdx*/, stream);

cudaMemcpyBatchAsync() 的前几个参数直观易懂：分别是源指针数组、目标指针数组以及传输大小数组，每个数组都需包含 batch_size 个元素。新增信息来自属性：函数需要属性数组指针及其对应的属性索引数组。原则上还可传入一个 size_t 数组记录失败传输的索引；若传 nullptr 也安全，只是不会记录失败索引。

再看属性：此例中的传输是同质的，因此只用一个属性并应用于全部传输。其作用范围由 attrIndex 控制。原则上它可以是数组，数组第 i 个元素表示“属性数组第 i 项”开始生效的首个传输索引。本例将 attrIndex 视为单元素数组，值为 ‘0’，表示 attribute[0] 对索引 0 及之后的所有传输生效，即覆盖全部传输。

最后，本例将 srcAccessOrder 设为 cudaMemcpySrcAccessOrderStream，表示源数据按常规流顺序访问。换言之，memcpy 会阻塞，直到此前处理这些源/目标指针对应数据的 kernel 完成。

下一个示例展示更复杂的异质批量传输场景。

Listing 5 Example of Heterogeneous Batched Memory Transfer using some Ephemeral Host Memory to Pinned Device Memory#
std::vector<void *> srcs(batch_size);
std::vector<void *> dsts(batch_size);
std::vector<void *> sizes(batch_size);

// Allocate the src and dst buffers
for (size_t i = 0; i < batch_size - 10; i++) {
    cudaMallocHost(&srcs[i], sizes[i]);
    cudaMalloc(&dsts[i], sizes[i]);
}

int buffer[10];

for (size_t i = batch_size - 10; i < batch_size; i++) {
    srcs[i] = &buffer[10 - (batch_size - i];
    cudaMalloc(&dsts[i], sizes[i]);
}

// Setup attributes for this batch of copies
cudaMemcpyAttributes attrs[2] = {};
attrs[0].srcAccessOrder = cudaMemcpySrcAccessOrderStream;
attrs[1].srcAccessOrder = cudaMemcpySrcAccessOrderDuringApiCall;

size_t attrsIdxs[2];
attrsIdxs[0] = 0;
attrsIdxs[1] = batch_size - 10;

// Launch the batched memory transfer
cudaMemcpyBatchAsync(&dsts[0], &srcs[0], &sizes[0], batch_size,
    &attrs, &attrsIdxs, 2 /*numAttrs*/, nullptr /*failIdx*/, stream);

这里有两类传输：batch_size-10 次从页锁定主机内存到页锁定设备内存，以及 10 次从主机数组到页锁定设备内存。并且 buffer 数组不仅位于主机端，还只在当前作用域内存在——其地址属于所谓 ephemeral pointer（短生命周期指针）。由于 API 为异步调用，该指针在调用返回后可能失效。对这类指针做拷贝时，属性中的 srcAccessOrder 必须设为 cudaMemcpySrcAccessOrderDuringApiCall。

此时我们有两个属性：第一个作用于索引从 0 到小于 batch_size-10 的传输；第二个作用于索引从 batch_size-10 到小于 batch_size 的传输。

如果 buffer 不是栈上分配而是用 malloc 在堆上分配，则其数据不再是 ephemeral，会一直有效直到显式释放指针。此时最佳分阶段策略取决于系统是否具备硬件托管内存，或能否通过地址转换实现 GPU 对主机内存的一致访问：若具备，宜采用流顺序；若不具备，则立即分阶段传输更合理。在这种场景下，属性的 srcAccessOrder 应使用 cudaMemcpyAccessOrderAny。

cudaMemcpyBatchAsync 还允许程序员提供源与目标位置提示。方法是在 cudaMemcpyAttributes 结构中设置 srcLocation 与 dstLocation 字段。这两个字段均为 cudaMemLocation 类型，其中包含位置类型与位置 ID。该结构与 cudaMemPrefetchAsync() 使用的预取位置提示结构相同。下面代码示例展示了如何为“从设备传到主机特定 NUMA 节点”设置提示。

Listing 6 Example of Setting Source and Destination Location Hints#
// Allocate the source and destination buffers
std::vector<void *> srcs(batch_size);
std::vector<void *> dsts(batch_size);
std::vector<void *> sizes(batch_size);

// cudaMemLocation structures we will use tp provide location hints
// Device device_id
cudaMemLocation srcLoc = {cudaMemLocationTypeDevice, dev_id};

// Host with numa Node numa_id
cudaMemLocation dstLoc = {cudaMemLocationTypeHostNuma, numa_id};

// Allocate the src and dst buffers
for (size_t i = 0; i < batch_size; i++) {
    cudaMallocManaged(&srcs[i], sizes[i]);
    cudaMallocManaged(&dsts[i], sizes[i]);

    cudaMemPrefetchAsync(srcs[i], sizes[i], srcLoc, 0, stream);
    cudaMemPrefetchAsync(dsts[i], sizes[i], dstLoc, 0, stream);
    cudaMemsetAsync(srcs[i], sizes[i], stream);
}

// Setup attributes for this batch of copies
cudaMemcpyAttributes attrs = {};

// These are managed memory pointers so Stream Order is appropriate
attrs.srcAccessOrder = cudaMemcpySrcAccessOrderStream;

// Now we can specify the location hints here.
attrs.srcLocHint = srcLoc;
attrs.dstlocHint = dstLoc;

// All copies in the batch have same copy attributes.
size_t attrsIdxs = 0;

// Launch the batched memory transfer
cudaMemcpyBatchAsync(&dsts[0], &srcs[0], &sizes[0], batch_size,
    &attrs, &attrsIdxs, 1 /*numAttrs*/, nullptr /*failIdx*/, stream);

最后要说明的是：可通过标志位提示传输更倾向使用 SM 还是 CE。 对应字段为 cudaMemcpyAttributesflags::flags，可取值如下：

  • cudaMemcpyFlagDefault - 默认行为

  • cudaMemcpyFlagPreferOverlapWithCompute - 提示系统优先使用 CE 来让传输与计算重叠。该标志在非 Tegra 平台会被忽略。

总结来说，关于 cudaMemcpyBatchAsync 的要点如下：

  • cudaMemcpyBatchAsync（及其 3D 变体）允许一次指定一批内存传输，从而摊销传输初始化开销。

  • 除源/目标指针和传输大小外，函数还能接收一个或多个拷贝属性，用于描述传输内存类型、源指针对应的流顺序行为、源/目标位置提示，以及是否偏好传输与计算重叠（若可行）或使用 SM 执行传输。

  • 有了上述信息，运行时即可尽可能对传输进行最大化优化。

3.1.6. 环境变量#

CUDA 提供了多种环境变量（见第 5.2 节），会影响执行行为与性能。 若未显式设置，CUDA 会采用合理默认值；但在某些场景下（如调试或性能优化）可能需要按具体情况做特殊配置。

例如，适当提高 CUDA_DEVICE_MAX_CONNECTIONS 的值，可能有助于降低不同 CUDA 流中的独立工作因“伪依赖”而被串行化的概率。此类伪依赖可能在复用同一底层资源时出现。 建议先使用默认值，只有在出现性能问题时再评估该环境变量的影响（例如跨流独立工作出现意外串行化，且不能归因于 SM 资源不足等因素）。 还需注意：在 MPS 场景下，该变量默认值不同（且更低）。

同样，对于延迟敏感型应用，将 CUDA_MODULE_LOADING 设为 EAGER 往往更合适，可把模块加载开销前移到应用初始化阶段，避开关键路径。当前默认模式是懒加载。 在默认懒加载模式下，也可通过在初始化阶段增加各类 kernel 的“预热”调用，促使模块更早加载，从而达到类似 eager 的效果。

关于各 CUDA 环境变量的更多细节，请参考 CUDA 环境变量。 建议在启动应用之前设置这些环境变量；在应用内部尝试设置，可能不会生效。
