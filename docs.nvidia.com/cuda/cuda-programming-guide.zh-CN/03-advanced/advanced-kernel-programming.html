3.2. 高级内核编程#

本章将先更深入地介绍 NVIDIA GPU 的硬件模型，然后引入 CUDA 内核代码中用于提升内核性能的一些高级特性。本章还将介绍与线程作用域、异步执行及其相关同步原语有关的概念。这些概念性讨论为理解内核代码中的高级性能特性提供必要基础。

其中部分特性的详细说明位于本指南下一部分对应的专题章节中。

  • Advanced synchronization primitives introduced in this chapter, are covered completely in Section 4.9 and Section 4.10.

  • Asynchronous data copies, including the tensor memory accelerator (TMA), are introduced in this chapter and covered completely in Section 4.11.

3.2.1. 使用 PTX#

Parallel Thread Execution（PTX）是 CUDA 用于抽象底层硬件 ISA 的虚拟机指令集架构，已在 第 1.3.3 节介绍。直接编写 PTX 属于非常高级的优化技术，对大多数开发者并非必需，应视作最后手段。不过，在某些场景中，直接编写 PTX 所提供的细粒度控制确实能带来性能提升。这类场景通常出现在应用中对性能极其敏感的关键路径上，哪怕提升零点几个百分点也有明显价值。全部 PTX 指令可见 PTX ISA 文档。

cuda::ptx namespace

在代码中直接使用 PTX 的一种方式是使用来自 libcu++ 的 cuda::ptx 命名空间。该命名空间提供可直接映射到 PTX 指令的 C++ 函数，从而简化在 C++ 应用中的使用。更多信息请参考 cuda::ptx 命名空间文档。

Inline PTX

在代码中引入 PTX 的另一种方式是使用内联 PTX。该方法在对应文档中有详细说明，它与在 CPU 上编写汇编代码非常相似。

3.2.2. 硬件实现#

流式多处理器（SM，参见GPU 硬件模型）被设计用于并发执行数百个线程。为管理如此大量线程，SM 采用了一种称为 Single-Instruction, Multiple-Thread（SIMT）的并行计算模型，见SIMT 执行模型。其指令采用流水线执行，同时利用单线程内的指令级并行与硬件同时多线程带来的大规模线程级并行（见硬件多线程）。与 CPU 核心不同，SM 按顺序发射指令，不进行分支预测或推测执行。

SIMT 执行模型与硬件多线程这两节描述了各类设备通用的 SM 架构特性。不同计算能力设备的具体差异见计算能力。

NVIDIA GPU 架构采用小端（little-endian）表示。

3.2.2.1. SIMT 执行模型#

每个 SM 都会以 32 个并行线程为一组（称为 warp）来创建、管理、调度和执行线程。组成同一 warp 的线程虽然从相同程序地址同时起步，但它们拥有各自的指令地址计数器与寄存器状态，因此可独立分支并独立执行。术语 warp 源于织造技术（早期并行线程技术）。half-warp 指一个 warp 的前半或后半；quarter-warp 指其四分之一（第一、第二、第三或第四象限）。

一个 warp 在同一时刻执行一条共同指令，因此当 32 个线程执行路径一致时效率最高。若 warp 内线程因数据相关分支而发生分歧，warp 会依次执行各分支路径，并在执行某一路径时屏蔽不在该路径上的线程。分支分歧仅发生在单个 warp 内；不同 warp 无论执行相同还是不同代码路径，彼此都可独立执行。

SIMT 架构与 SIMD（Single Instruction, Multiple Data）向量组织相似，二者都由一条指令控制多个处理单元。关键区别在于：SIMD 会将向量宽度显式暴露给软件，而 SIMT 指令描述的是“单个线程”的执行与分支行为。与 SIMD 向量机相比，SIMT 既支持为独立标量线程编写线程级并行代码，也支持为协同线程编写数据并行代码。就正确性而言，开发者可基本忽略 SIMT 细节；但若尽量避免 warp 内线程分歧，通常能获得显著性能提升。这类似缓存行：为保证正确性可不关心其大小，但要追求峰值性能时必须在代码结构中纳入考虑。反之，在向量架构中，软件需要手动将加载合并为向量并自行处理分歧。

3.2.2.1.1. 独立线程调度#

在计算能力低于 7.0 的 GPU 上，warp 采用单一程序计数器（由 32 个线程共享）并配合活动掩码指示活动线程。因此，同一 warp 中处于不同分歧路径或执行状态的线程无法彼此发信号或交换数据；对于依赖锁/互斥量保护细粒度共享数据的算法，可能因竞争线程所在 warp 不同而产生死锁。

在计算能力 7.0 及以上 GPU 上，独立线程调度允许线程间充分并发，而不受 warp 绑定。独立线程调度下，GPU 为每个线程维护执行状态（包括程序计数器和调用栈），并可按线程粒度让出执行，以更高效利用资源或让某线程等待其他线程产出数据。调度优化器会决定如何把同一 warp 中活动线程组合成 SIMT 执行单元。该机制在保持既有 NVIDIA GPU 的 SIMT 高吞吐同时，提供了更高灵活性：线程可在子 warp 粒度发生分歧并重新汇合。

独立线程调度可能破坏依赖旧架构“隐式 warp 同步”语义的代码。所谓 warp-synchronous 代码，假设同一 warp 内线程在每条指令上严格锁步执行；而在可子 warp 粒度分歧与重汇合后，这一假设不再可靠，可能导致实际参与执行代码的线程集合与预期不一致。所有面向 CC 7.0 之前 GPU 编写的 warp 同步代码（如无需显式同步的 warp 内归约）都应复查兼容性。建议开发者使用 __syncwarp() 进行显式同步，以确保在各代 GPU 上行为正确。

注意

warp 中参与当前指令执行的线程称为 active（活动）线程；未参与当前指令的线程称为 inactive（非活动/被禁用）线程。线程变为非活动可能有多种原因，例如：比同 warp 其他线程更早退出、走到了与当前 warp 执行路径不同的分支，或属于线程数不是 warp 大小整数倍的线程块中“尾部剩余线程”。

若 warp 执行的非原子指令中，多个线程写入同一全局内存或共享内存地址，则该地址上发生的串行写入次数会随设备计算能力不同而变化。但对所有计算能力而言，最终由哪个线程完成最后一次写入都是未定义的。

若 warp 执行原子指令时，多个线程对同一全局内存地址执行读-改-写，则每次读-改-写都会发生且彼此串行化，但发生顺序未定义。

3.2.2.2. 硬件多线程#

当 SM 被分配一个或多个线程块执行时，会先将其划分为多个 warp，并由 warp scheduler 调度执行。线程块到 warp 的划分方式固定不变：每个 warp 都包含线程 ID 连续递增的一组线程，第一个 warp 含线程 0。关于线程 ID 与线程块内索引的对应关系，参见线程层次结构。

一个线程块中的 warp 总数定义如下：

\(\text{ceil}\left( \frac{T}{W_{size}}, 1 \right)\)

  • T 为每个线程块中的线程数；

  • Wsize 为 warp 大小，取值为 32；

  • ceil(x, y) 表示将 x 向上取整到最接近的 y 的整数倍。

SM 在整个 warp 生命周期内都将该 warp 的执行上下文（程序计数器、寄存器等）保存在片上，因此在 warp 间切换几乎没有开销。每个指令发射周期，warp 调度器会选择一个“其下一条指令已就绪”的 warp（即该 warp 的活动线程），并向这些线程发射指令。

每个 SM 都有一组 32 位寄存器（按 warp 划分）以及一块按线程块划分的共享内存。对于给定内核，在某个 SM 上可同时驻留并并发处理的线程块/warp 数量，取决于内核使用的寄存器与共享内存规模，以及 SM 可用的寄存器与共享内存总量；此外每个 SM 还受线程块与 warp 驻留数量上限约束。这些上限及资源容量都由设备计算能力决定，详见计算能力。若每个 SM 资源不足以至少容纳一个线程块，内核将启动失败。每个线程块分配到的寄存器与共享内存总量，可通过占用率章节中的多种方法确定。

3.2.2.3. 异步执行特性#

新一代 NVIDIA GPU 引入了异步执行能力，以便在 GPU 内部实现数据搬运、计算与同步之间更充分的重叠。这些能力允许从 GPU 代码发起的某些操作，相对于同一线程块内其他 GPU 代码异步执行。注意，这不同于第 2.3 节所述的 CUDA 异步 API；后者是让 GPU 内核启动或内存操作彼此异步，或相对 CPU 异步。

计算能力 8.0（NVIDIA Ampere 架构）引入了“全局内存到共享内存”的硬件加速异步数据拷贝与异步屏障（参见 NVIDIA A100 Tensor Core GPU Architecture）。

计算能力 9.0（NVIDIA Hopper 架构）进一步扩展了异步执行特性，引入张量内存加速器（TMA）单元，可在全局内存与共享内存之间双向传输大块数据和多维张量，同时支持异步事务屏障与异步矩阵乘加操作（详情见 Hopper Architecture in Depth）。

CUDA 提供了可在设备代码中由线程调用的 API 来使用这些特性。异步编程模型定义了异步操作相对于 CUDA 线程的行为语义。

异步操作指：由某个 CUDA 线程发起，但像由另一个线程执行那样异步运行的操作；该“执行者”称为 async thread。在结构正确的程序中，会有一个或多个 CUDA 线程与该异步操作进行同步。发起异步操作的 CUDA 线程不必是参与同步的线程之一，但 async thread 始终与其发起线程关联。

异步操作会通过某种同步对象来发出“完成”信号，该对象可以是 barrier 或 pipeline。这些同步对象详见高级同步原语，它们在异步内存操作中的作用见异步数据拷贝。

3.2.2.3.1. 异步线程与异步代理#

异步操作的内存访问方式可能与常规操作不同。为区分这些访问模式，CUDA 引入了 async thread、generic proxy 与 async proxy 概念。常规 load/store 通过 generic proxy 执行。某些异步指令（如 LDGSTS、STAS/REDAS）可建模为“在 generic proxy 中运行的 async thread”；另一些异步指令（如 TMA 批量异步拷贝及部分张量核操作 tcgen05.*、wgmma.mma_async.*）则建模为“在 async proxy 中运行的 async thread”。

在 generic proxy 中运行的 async thread：当异步操作被发起时，它会关联到一个 async thread，该线程不同于发起该操作的 CUDA 线程。对同一地址而言，异步操作之前的 generic proxy（常规）load/store 保证先于该异步操作发生；但其后的常规 load/store 不保证维持顺序，因此在 async thread 完成前可能产生竞争条件。

在 async proxy 中运行的 async thread：当异步操作被发起时，它会关联到一个 async thread，该线程不同于发起该操作的 CUDA 线程。对同一地址而言，异步操作之前和之后的常规 load/store 都不保证顺序。需要使用 proxy fence 在不同 proxy 间进行同步，以确保内存顺序正确。使用张量内存加速器（TMA）一节展示了如何使用 proxy fence 来保证 TMA 异步拷贝的正确性。

关于这些概念的更多细节，请参阅 PTX ISA 文档。

3.2.3. 线程作用域#

CUDA 线程构成了线程层次结构，正确且高性能地编写 CUDA 内核都离不开这一级层次。在该层次中，内存操作的可见性与同步范围并不统一。为表达这种差异，CUDA 编程模型引入了线程作用域概念。线程作用域用于定义：某线程的 load/store 可被哪些线程观察到，以及哪些线程可通过原子操作、屏障等同步原语互相同步。每种作用域在内存层次中都对应一个一致性点。

3.2.4. 高级同步原语#

本节介绍三类同步原语：

  • 作用域原子操作：将 C++ 内存顺序与 CUDA 线程作用域结合，使线程能在 block、cluster、device 或 system 作用域内安全通信（见线程作用域）。

  • 异步屏障：将同步拆分为到达（arrival）与等待（wait）阶段，可用于跟踪异步操作进度。

  • 流水线：用于分阶段组织工作并协调多缓冲生产者-消费者模式，常用于让计算与异步数据拷贝重叠执行。

3.2.4.1. 作用域原子操作#

第 5.4.5 节概述了 CUDA 中可用的原子函数。本节聚焦支持C++ 标准原子内存语义的作用域原子操作，可通过 libcu++ 库或编译器内建函数使用。作用域原子操作可在 CUDA 线程层次的合适层级实现高效同步，从而在复杂并行算法中兼顾正确性与性能。

3.2.4.1.1. 线程作用域与内存顺序#

作用域原子操作结合了两个关键概念：

  • 线程作用域（Thread Scope）：定义哪些线程能够观察到该原子操作的效果（见线程作用域）。

  • 内存顺序（Memory Ordering）：定义其相对其他内存操作的顺序约束（见C++ 标准原子内存语义）。

#include <cuda/atomic>

__global__ void block_scoped_counter() {
    // Shared atomic counter visible only within this block
    __shared__ cuda::atomic<int, cuda::thread_scope_block> counter;

    // Initialize counter (only one thread should do this)
    if (threadIdx.x == 0) {
        counter.store(0, cuda::memory_order_relaxed);
    }
    __syncthreads();

    // All threads in block atomically increment
    int old_value = counter.fetch_add(1, cuda::memory_order_relaxed);

    // Use old_value...
}

__global__ void block_scoped_counter() {
    // Shared counter visible only within this block
    __shared__ int counter;

    // Initialize counter (only one thread should do this)
    if (threadIdx.x == 0) {
        __nv_atomic_store_n(&counter, 0,
                            __NV_ATOMIC_RELAXED,
                            __NV_THREAD_SCOPE_BLOCK);
    }
    __syncthreads();

    // All threads in block atomically increment
    int old_value = __nv_atomic_fetch_add(&counter, 1,
                                          __NV_ATOMIC_RELAXED,
                                          __NV_THREAD_SCOPE_BLOCK);

    // Use old_value...
}

此示例实现了一个块作用域原子计数器，用于展示作用域原子操作的基本概念：

  • 共享变量：通过 __shared__ 内存让块内所有线程共享一个计数器。

  • 原子类型声明：cuda::atomic<int, cuda::thread_scope_block> 创建一个块级可见的原子整数。

  • 单线程初始化：仅线程 0 初始化计数器，避免初始化阶段的竞争条件。

  • 块级同步：__syncthreads() 确保所有线程在继续执行前都可见初始化后的计数器。

  • 原子递增：每个线程原子地递增计数器，并获取递增前的值。

这里选择 cuda::memory_order_relaxed，因为仅需原子性（不可分割的读-改-写），而不需要不同内存位置之间的顺序约束。对于这种简单计数场景，递增顺序不影响正确性。

对于生产者-消费者模式，acquire-release 语义可保证正确顺序：

__global__ void producer_consumer() {
    __shared__ int data;
    __shared__ cuda::atomic<bool, cuda::thread_scope_block> ready;

    if (threadIdx.x == 0) {
        // Producer: write data then signal ready
        data = 42;
        ready.store(true, cuda::memory_order_release);  // Release ensures data write is visible
    } else {
        // Consumer: wait for ready signal then read data
        while (!ready.load(cuda::memory_order_acquire)) {  // Acquire ensures data read sees the write
            // spin wait
        }
        int value = data;
        // Process value...
    }
}

__global__ void producer_consumer() {
    __shared__ int data;
    __shared__ bool ready; // Only ready flag needs atomic operations

    if (threadIdx.x == 0) {
        // Producer: write data then signal ready
        data = 42;
        __nv_atomic_store_n(&ready, true,
                            __NV_ATOMIC_RELEASE,
                            __NV_THREAD_SCOPE_BLOCK);  // Release ensures data write is visible
    } else {
        // Consumer: wait for ready signal then read data
        while (!__nv_atomic_load_n(&ready,
                                   __NV_ATOMIC_ACQUIRE,
                                   __NV_THREAD_SCOPE_BLOCK)) {  // Acquire ensures data read sees the write
            // spin wait
        }
        int value = data;
        // Process value...
    }
}

3.2.4.1.2. 性能注意事项#

  • 尽量使用最窄作用域：块作用域原子操作通常远快于系统作用域原子操作。

  • 优先使用较弱顺序：仅在保证正确性确有必要时才使用更强顺序。

  • 关注内存位置：共享内存原子操作通常比全局内存原子操作更快。

3.2.4.2. 异步屏障#

异步屏障与典型的单阶段屏障（__syncthreads()）不同：线程声明自己到达屏障（arrival）与等待其他线程到达（wait）是分离的两个动作。这种分离允许线程在等待期间执行与屏障无关的额外工作，从而提高执行效率。异步屏障既可用于 CUDA 线程中的生产者-消费者模式，也可通过“拷贝完成即到达屏障（arrive on）”的方式支持内存层次内的异步数据拷贝。

异步屏障可用于计算能力 7.0 及以上设备。计算能力 8.0 及以上设备还为共享内存中的异步屏障提供硬件加速，并显著提升同步粒度：可对线程块内任意子集的 CUDA 线程进行硬件加速同步。更早架构仅能在整 warp（__syncwarp()）或整块（__syncthreads()）层级加速同步。

CUDA 编程模型通过 cuda::std::barrier 提供异步屏障，它是 libcu++ 中符合 ISO C++ 的屏障实现。除实现 std::barrier 外，库还提供 CUDA 专用扩展，可选择屏障线程作用域以提升性能，并暴露更底层的 cuda::ptx API。cuda::barrier 可通过 friend 函数 cuda::device::barrier_native_handle() 获取本机句柄并传给 cuda::ptx 函数，从而与 cuda::ptx 互操作。CUDA 还提供了线程块作用域、驻留于共享内存中的异步屏障 primitives API。

同步的时间拆分

如果不使用异步 arrive-wait 屏障，线程块内同步通常通过 __syncthreads() 完成；在使用 Cooperative Groups 时，则可使用 block.sync()。

#include <cooperative_groups.h>

__global__ void simple_sync(int iteration_count) {
    auto block = cooperative_groups::this_thread_block();

    for (int i = 0; i < iteration_count; ++i) {
        /* code before arrive */

         // Wait for all threads to arrive here.
        block.sync();

        /* code after wait */
    }
}

在线程同步点（block.sync()）处，线程会被阻塞，直到所有线程都到达该点。此外，同步点之前发生的内存更新，保证在线程块内所有线程越过该点后可见。

该模式包含三个阶段：

  • 同步之前的代码执行内存更新，这些更新会在同步之后被读取。

  • 同步点。

  • 同步之后的代码可见同步之前发生的内存更新。

若改用异步屏障，则时间拆分同步模式如下。

#include <cuda/barrier>
#include <cooperative_groups.h>

__device__ void compute(float *data, int iteration);

__global__ void split_arrive_wait(int iteration_count, float *data)
{
  using barrier_t = cuda::barrier<cuda::thread_scope_block>;
  __shared__ barrier_t bar;
  auto block = cooperative_groups::this_thread_block();

  if (block.thread_rank() == 0)
  {
    // Initialize barrier with expected arrival count.
    init(&bar, block.size());
  }
  block.sync();

  for (int i = 0; i < iteration_count; ++i)
  {
    /* code before arrive */

    // This thread arrives. Arrival does not block a thread.
    barrier_t::arrival_token token = bar.arrive();

    compute(data, i);

    // Wait for all threads participating in the barrier to complete bar.arrive().
    bar.wait(std::move(token));

    /* code after wait */
  }
}

#include <cuda/ptx>
#include <cooperative_groups.h>

__device__ void compute(float *data, int iteration);

__global__ void split_arrive_wait(int iteration_count, float *data)
{
  __shared__ uint64_t bar;
  auto block = cooperative_groups::this_thread_block();

  if (block.thread_rank() == 0)
  {
    // Initialize barrier with expected arrival count.
    cuda::ptx::mbarrier_init(&bar, block.size());
  }
  block.sync();

  for (int i = 0; i < iteration_count; ++i)
  {
    /* code before arrive */

    // This thread arrives. Arrival does not block a thread.
    uint64_t token = cuda::ptx::mbarrier_arrive(&bar);

    compute(data, i);

    // Wait for all threads participating in the barrier to complete mbarrier_arrive().
    while(!cuda::ptx::mbarrier_try_wait(&bar, token)) {}

    /* code after wait */
  }
}

#include <cuda_awbarrier_primitives.h>
#include <cooperative_groups.h>

__device__ void compute(float *data, int iteration);

__global__ void split_arrive_wait(int iteration_count, float *data)
{
  __shared__ __mbarrier_t bar;
  auto block = cooperative_groups::this_thread_block();

  if (block.thread_rank() == 0)
  {
    // Initialize barrier with expected arrival count.
    __mbarrier_init(&bar, block.size());
  }
  block.sync();

  for (int i = 0; i < iteration_count; ++i)
  {
    /* code before arrive */

    // This thread arrives. Arrival does not block a thread.
    __mbarrier_token_t token = __mbarrier_arrive(&bar);

    compute(data, i);

    // Wait for all threads participating in the barrier to complete __mbarrier_arrive().
    while(!__mbarrier_try_wait(&bar, token, 1000)) {}

    /* code after wait */
  }
}

在该模式中，同步点被拆分为 arrive 点（bar.arrive()）与 wait 点（bar.wait(std::move(token))）。线程首次调用 bar.arrive() 时开始参与 cuda::barrier。当线程调用 bar.wait(std::move(token)) 时，会阻塞直到参与线程完成期望次数的 bar.arrive()（该期望值由 init() 的 expected arrival count 参数给定）。参与线程在 bar.arrive() 之前发生的内存更新，保证在其调用 bar.wait(std::move(token)) 后可见。注意，调用 bar.arrive() 本身不会阻塞线程；线程可继续执行其他不依赖于“其他参与线程在其 bar.arrive() 之前更新”的工作。

arrive and wait 模式包含五个阶段：

  • arrive之前的代码执行内存更新，这些更新会在 wait之后被读取。

  • 带隐式内存栅栏的 arrive 点（即等价于 cuda::atomic_thread_fence(cuda::memory_order_seq_cst, cuda::thread_scope_block)）。

  • arrive 与 wait之间的代码。

  • wait 点。

  • wait之后的代码可见 arrive之前执行的更新。

关于异步屏障的完整使用指南，请参见 异步屏障。

3.2.4.3. 流水线#

CUDA 编程模型提供了 pipeline 同步对象，用作将异步内存拷贝编排为多阶段的协调机制，便于实现双缓冲或多缓冲的生产者-消费者模式。pipeline 是一个具有 head 与 tail 的双端队列，按先进先出（FIFO）顺序处理工作。生产者线程向 pipeline 的 head 提交工作，消费者线程从 tail 拉取工作。

流水线能力可通过 libcu++ 中的 cuda::pipeline API 使用，也可通过primitives API使用。下表说明了两类 API 的主要功能。

cuda::pipeline API

说明

producer_acquire

获取 pipeline 内部队列中的一个可用阶段。

producer_commit

在当前已获取阶段上，提交自调用 producer_acquire 之后发起的异步操作。

consumer_wait

等待 pipeline 中最老阶段的异步操作完成。

consumer_release

将 pipeline 最老阶段释放回 pipeline 对象以便复用；释放后的阶段可再次被生产者获取。

原语 API

说明

__pipeline_memcpy_async

请求将一次从全局内存到共享内存的拷贝提交为异步执行。

__pipeline_commit

在 pipeline 当前阶段提交该调用之前发起的异步操作。

__pipeline_wait_prior(N)

等待 pipeline 中除最近 N 次提交外的所有异步操作完成。

cuda::pipeline API 接口更丰富、限制更少；而原语 API 仅支持跟踪从全局内存到共享内存的异步拷贝，并要求特定的大小与对齐条件。原语 API 的能力等价于一个 cuda::thread_scope_thread 作用域的 cuda::pipeline 对象。

更详细的使用模式与示例请参见 流水线。

3.2.5. 异步数据拷贝#

在内存层次中高效移动数据，是实现高性能 GPU 计算的基础。传统同步内存操作会让线程在数据传输期间空等。GPU 虽可借助并行性天然隐藏内存延迟（即在内存操作完成期间，SM 切换去执行其他 warp），但即便如此，内存延迟仍可能成为内存带宽利用率和计算资源效率的瓶颈。为解决这些瓶颈，现代 GPU 架构提供了硬件加速的异步数据拷贝机制，使数据传输可独立推进，同时线程继续执行其他工作。

异步数据拷贝通过将“发起传输”与“等待传输完成”解耦，实现计算与数据移动重叠。这样线程可在内存延迟期间执行有用工作，从而提升整体吞吐与资源利用率。

注意

本节的概念与原理与前文异步执行一章相近，但那一章主要讨论 kernel 执行与 cudaMemcpyAsync 等内存传输的异步行为，可视作应用不同组件之间的异步。

本节所述异步是指：在不阻塞 GPU 线程的前提下，实现 GPU DRAM（即全局内存）与 SM 上内存（如共享内存或张量内存）之间的数据传输。这属于单次 kernel 启动内部的异步。

要理解异步拷贝为何能提升性能，可以先看一种常见的 GPU 计算模式。CUDA 应用常采用复制并计算（copy and compute）模式：

  • 从全局内存取数，

  • 将数据写入共享内存，并且

  • 在共享内存数据上执行计算，并可能将结果写回全局内存。

该模式的复制阶段通常写作 shared[local_idx] = global[global_idx]。这种从全局内存到共享内存的复制会被编译器展开为：先从全局内存读入寄存器，再由寄存器写入共享内存。

当该模式出现在迭代算法中时，每个线程块都需要在 shared[local_idx] = global[global_idx] 赋值后进行同步，以保证计算阶段开始前共享内存写入已全部完成。计算阶段结束后还需再次同步，防止在所有线程完成计算前就覆盖共享内存。下方代码示例展示了这一模式。

#include <cooperative_groups.h>

__device__ void compute(int* global_out, int const* shared_in) {
    // Computes using all values of current batch from shared memory.
    // Stores this thread's result back to global memory.
}

__global__ void without_async_copy(int* global_out, int const* global_in, size_t size, size_t batch_sz) {
  auto grid = cooperative_groups::this_grid();
  auto block = cooperative_groups::this_thread_block();
  assert(size == batch_sz * grid.size()); // Exposition: input size fits batch_sz * grid_size

  extern __shared__ int shared[]; // block.size() * sizeof(int) bytes

  size_t local_idx = block.thread_rank();

  for (size_t batch = 0; batch < batch_sz; ++batch) {
    // Compute the index of the current batch for this block in global memory.
    size_t block_batch_idx = block.group_index().x * block.size() + grid.size() * batch;
    size_t global_idx = block_batch_idx + threadIdx.x;
    shared[local_idx] = global_in[global_idx];

    // Wait for all copies to complete.
    block.sync();

    // Compute and write result to global memory.
    compute(global_out + block_batch_idx, shared);

    // Wait for compute using shared memory to finish.
    block.sync();
  }
}

使用异步数据拷贝后，从全局内存到共享内存的数据移动可异步执行，从而在等待数据到达期间更高效地利用 SM。

#include <cooperative_groups.h>
#include <cooperative_groups/memcpy_async.h>

__device__ void compute(int* global_out, int const* shared_in) {
    // Computes using all values of current batch from shared memory.
    // Stores this thread's result back to global memory.
}

__global__ void with_async_copy(int* global_out, int const* global_in, size_t size, size_t batch_sz) {
  auto grid = cooperative_groups::this_grid();
  auto block = cooperative_groups::this_thread_block();
  assert(size == batch_sz * grid.size()); // Exposition: input size fits batch_sz * grid_size

  extern __shared__ int shared[]; // block.size() * sizeof(int) bytes

  size_t local_idx = block.thread_rank();

  for (size_t batch = 0; batch < batch_sz; ++batch) {
    // Compute the index of the current batch for this block in global memory.
    size_t block_batch_idx = block.group_index().x * block.size() + grid.size() * batch;

    // Whole thread-group cooperatively copies whole batch to shared memory.
    cooperative_groups::memcpy_async(block, shared, global_in + block_batch_idx, block.size());

    // Compute on different data while waiting.

    // Wait for all copies to complete.
    cooperative_groups::wait(block);

    // Compute and write result to global memory.
    compute(global_out + block_batch_idx, shared);

    // Wait for compute using shared memory to finish.
    block.sync();
  }
}

cooperative_groups::memcpy_async 会把 block.size() 个元素从全局内存复制到 shared 数据区。该操作可视为由“另一线程”执行，并在复制完成后与当前线程对 cooperative_groups::wait 的调用同步。在复制完成前修改全局数据，或读写共享数据，都会引入数据竞争。

该示例展示了所有异步拷贝操作背后的核心思想：将内存传输的发起与完成解耦，使线程可在后台搬运数据时执行其他工作。CUDA 编程模型提供了多套 API 来使用这一能力，包括 Cooperative Groups 与 libcu++ 中的 memcpy_async，以及更底层的 cuda::ptx 与原语 API。这些 API 语义相近：都将对象从源复制到目标，行为可视为由另一线程执行，并在复制完成后通过不同机制进行同步。

现代 GPU 架构为异步数据搬运提供了多种硬件机制。

  • LDGSTS（计算能力 8.0+）支持从全局内存到共享内存的高效小规模异步传输。

  • 张量内存加速器（TMA，计算能力 9.0+）扩展了上述能力，提供针对大规模多维数据传输优化的批量异步拷贝操作。

  • STAS 指令（计算能力 9.0+）支持在 cluster 内从寄存器到分布式共享内存的小规模异步传输。

这些机制支持不同的数据路径、传输规模与对齐要求，使开发者可针对具体数据访问模式选择最合适的方法。下表概览了 GPU 内异步拷贝支持的数据路径。

3.2.6. Configuring L1/Shared Memory Balance#

As mentioned in L1 data cache, the L1 and shared memory on an SM use the same physical resource, known as the unified data cache. On most architectures, if a kernel uses little or no shared memory, the unified data cache can be configured to provide the maximal amount of L1 cache allowed by the architecture.

The unified data cache reserved for shared memory is configurable on a per-kernel basis. An application can set the carveout, or preferred shared memory capacity, with the cudaFuncSetAttribute function called before the kernel is launched.

cudaFuncSetAttribute(kernel_name, cudaFuncAttributePreferredSharedMemoryCarveout, carveout);

The application can set the carveout as an integer percentage of the maximum supported shared memory capacity of that architecture. In addition to an integer percentage, three convenience enums are provided as carveout values.

  • cudaSharedmemCarveoutDefault

  • cudaSharedmemCarveoutMaxL1

  • cudaSharedmemCarveoutMaxShared

The maximum supported shared memory and the supported carveout sizes vary by architecture; see Shared Memory Capacity per Compute Capability for details.

Where a chosen integer percentage carveout does not map exactly to a supported shared memory capacity, the next larger capacity is used. For example, for devices of compute capability 12.0, which have a maximum shared memory capacity of 100KB, setting the carveout to 50% will result in 64KB of shared memory, not 50KB, because devices of compute capability 12.0 support shared memory sizes of 0, 8, 16, 32, 64, and 100.

The function passed to cudaFuncSetAttribute must be declared with the __global__ specifier. cudaFuncSetAttribute is interpreted by the driver as a hint, and the driver may choose a different carveout size if required to execute the kernel.

注意

Another CUDA API, cudaFuncSetCacheConfig, also allows an application to adjust the balance between L1 and shared memory for a kernel. However, this API set a hard requirements on shared/L1 balance for kernel launch. As a result, interleaving kernels with different shared memory configurations would needlessly serialize launches behind shared memory reconfigurations. cudaFuncSetAttribute is preferred because driver may choose a different configuration if required to execute the function or to avoid thrashing.

Kernels relying on shared memory allocations over 48 KB per block are architecture-specific. As such they must use dynamic shared memory rather than statically-sized arrays and require an explicit opt-in using cudaFuncSetAttribute as follows.

// Device code
__global__ void MyKernel(...)
{
  extern __shared__ float buffer[];
  ...
}

// Host code
int maxbytes = 98304; // 96 KB
cudaFuncSetAttribute(MyKernel, cudaFuncAttributeMaxDynamicSharedMemorySize, maxbytes);
MyKernel <<<gridDim, blockDim, maxbytes>>>(...);
