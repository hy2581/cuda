3.2. 高级内核编程#

本章将首先深入探讨 NVIDIA GPU 的硬件模型，然后介绍 CUDA 内核代码中旨在提高内核性能的一些更高级的功能。本章将介绍一些与线程作用域、异步执行以及相关同步原语相关的概念。这些概念性讨论为内核代码中可用的一些高级性能特性提供了必要的基础。

本编程指南下一部分中专门介绍这些功能的章节中包含对其中一些功能的详细描述。

  • 高级同步原语 本章中介绍的内容完全涵盖在 第 4.9 节 和 第 4.10 节.

  • 异步数据复制，包括张量内存加速器（TMA），在本章中进行了介绍，并在 第 4.11 节.

3.2.1. 使用 PTX#

并行线程执行 (PTX)，CUDA 用于抽象硬件 ISA 的虚拟机指令集架构 (ISA)，在 第1.3.3节。直接在 PTX 中编写代码是一种非常先进的优化技术，对于大多数开发人员来说并不是必需的，应将其视为最后的工具。然而，在某些情况下，通过直接写入 PTX 实现的细粒度控制可以提高特定应用程序的性能。这些情况通常发生在应用程序中对性能非常敏感的部分，其中性能改进的每一分之一都会带来显着的好处。所有可用的 PTX 指令都在 PTX ISA 文档.

cuda::ptx namespace

直接在代码中使用 PTX 的一种方法是使用 cuda::ptx 命名空间来自 libcu++。此命名空间提供直接映射到 PTX 指令的 C++ 函数，从而简化了它们在 C++ 应用程序中的使用。欲了解更多信息，请参阅 cuda::ptx 命名空间 documentation.

内联 PTX

在代码中包含 PTX 的另一种方法是使用内联 PTX。该方法在相应的 documentation。这与在 CPU 上编写汇编代码非常相似。

3.2.2. 硬件实现#

流式多处理器或 SM（参见 GPU硬件模型）旨在同时执行数百个线程。为了管理如此大量的线程，它采用了一种独特的并行计算模型，称为 单指令、多线程, or SIMT，即描述于 SIMT执行模型。这些指令是流水线式的，利用单个线程内的指令级并行性，以及通过同步硬件多线程实现广泛的线程级并行性，详细信息请参见 硬件多线程。与 CPU 内核不同，SM 按顺序发出指令，并且不执行分支预测或推测执行。

Sections SIMT执行模型 和 硬件多线程 描述所有设备共有的 SM 架构特征。部分 计算能力 提供不同计算能力的设备的具体信息。

NVIDIA GPU 架构使用小端表示法。

3.2.2.1. SIMT执行模型#

每个 SM 以 32 个并行线程为一组创建、管理、调度和执行线程，称为 warps。构成warp 的各个线程在同一程序地址处一起启动，但它们具有自己的指令地址计数器和寄存器状态，因此可以自由地独立分支和执行。术语 warp 起源于编织，这是第一个并行线程技术。一个 half-warp 是warp 的前半部分或后半部分。一个 quarter-warp 是warp 的第一、第二、第三或第四四分之一。

Warp 一次执行一条公共指令，因此当 Warp 的所有 32 个线程都同意其执行路径时，即可实现最高效率。如果 warp 的线程通过依赖于数据的条件分支发生分歧，则 warp 会执行所采用的每个分支路径，从而禁用不在该路径上的线程。分支发散仅发生在warp 内；不同的 warp 独立执行，无论它们执行的是公共还是不相交的代码路径。

SIMT 架构类似于 SIMD（单指令、多数据）向量组织，因为单指令控制多个处理元素。一个关键的区别是 SIMD 向量组织向软件公开 SIMD 宽度，而 SIMT 指令指定单个线程的执行和分支行为。与 SIMD 向量机相比，SIMT 使程序员能够为独立的标量线程编写线程级并行代码，以及为协调线程编写数据并行代码。为了正确性，程序员基本上可以忽略 SIMT 行为；然而，通过注意代码很少需要线程束中的线程发散，可以实现显着的性能改进。实际上，这类似于缓存行的作用：在设计正确性时可以安全地忽略缓存行大小，但在设计峰值性能时必须在代码结构中考虑缓存行大小。另一方面，矢量架构需要软件将负载合并为矢量并手动管理差异。

3.2.2.1.1. 独立线程调度#

在计算能力低于 7.0 的 GPU 上，warp 使用在 warp 中的所有 32 个线程之间共享的单个程序计数器以及指定 warp 的活动线程的活动掩码。因此，来自不同区域或不同执行状态的同一warp 的线程无法相互发送信号或交换数据，并且需要细粒度共享由锁或互斥锁保护的数据的算法可能会导致死锁，具体取决于竞争线程来自哪个warp。

在计算能力7.0及更高版本的GPU中， 独立线程调度 允许线程之间完全并发，无论warp如何。通过独立线程调度，GPU 可以维护每个线程的执行状态，包括程序计数器和调用堆栈，并且可以按线程粒度生成执行，以便更好地利用执行资源或允许一个线程等待另一个线程生成数据。调度优化器确定如何将来自同一 warp 的活动线程分组到 SIMT 单元中。这保留了之前 NVIDIA GPU 中 SIMT 执行的高吞吐量，但具有更大的灵活性：线程现在可以在子warp粒度上发散和重新收敛。

独立线程调度可以破坏依赖于以前 GPU 架构的隐式warp 同步行为的代码。 Warp-synchronous 代码假设同一 warp 中的线程在每条指令上都以锁步方式执行，但线程在子 warp 粒度上发散和重新收敛的能力使这种假设无效。这可能会导致参与执行代码的线程集与预期不同。应重新审查为 CC 7.0 之前的 GPU 开发的任何warp 同步代码（例如无同步的内部warp 归约），以确保兼容性。开发人员应该使用显式同步此类代码 __syncwarp() 确保所有 GPU 代的正确行为。

注

参与当前指令的 warp 线程称为 active 线程，而不在当前指令上的线程是 inactive （已禁用）。线程可能由于多种原因而处于不活动状态，包括比其warp 中的其他线程更早退出、采用了与warp当前执行的分支路径不同的分支路径，或者是线程数不是warp大小的倍数的块的最后一个线程。

如果由 warp 执行的非原子指令从该 warp 的多个线程写入全局或共享内存中的同一位置，则该位置发生的序列化写入次数可能会有所不同，具体取决于设备的计算能力。但是，对于所有计算功能，哪个线程执行最终写入是未定义的。

如果一个 atomic 由 warp 执行的指令会为该 warp 的多个线程读取、修改和写入全局内存中的同一位置，对该位置的每次读/修改/写入都会发生，并且它们都是序列化的，但它们发生的顺序是未定义的。

3.2.2.2. 硬件多线程#

当 SM 被给予一个或多个线程块来执行时，它会将它们划分为 warp，并且每个 warp 都由一个线程调度执行 warp调度程序。块被划分为warp 的方式始终是相同的；每个 warp 包含连续的、递增的线程 ID，第一个 warp 包含线程 0。 线程层次结构 描述线程 ID 如何与块中的线程索引相关。

块中的warp总数定义如下：

\(\text{ceil}\left(\frac{T}{W_{size}}, 1 \right)\)

  • T 是每个块的线程数，

  • Wsize 是warp大小，等于 32，

  • ceil(x, y) 等于 x 四舍五入到最接近的 y 倍数。

SM 处理的每个 warp 的执行上下文（程序计数器、寄存器等）在整个 warp 的生命周期内都在片上维护。因此，warp之间的切换不会产生任何成本。在每个指令发出周期，warp 调度程序都会选择一个 warp，其中的线程准备好执行其下一条指令（活动线程 warp）并向这些线程发出指令。

每个 SM 都有一组 32 位寄存器，它们在 warp 之间划分，以及一个 共享内存 它在线程块之间划分。对于给定内核，可以驻留在 SM 上并同时处理的块和 warp 的数量取决于内核使用的寄存器和共享内存的数量，以及 SM 上可用的寄存器和共享内存的数量。每个 SM 的驻留块和 warp 也有最大数量。这些限制以及 SM 上可用的寄存器和共享内存的数量取决于设备的计算能力，并在 计算能力。如果每个 SM 没有足够的可用资源来处理至少一个块，则内核将无法启动。为块分配的寄存器和共享内存的总数可以通过以下几种方式确定： Occupancy 一节。

3.2.2.3. 异步执行特性#

最近几代 NVIDIA GPU 已包含异步执行功能，以允许 GPU 内的数据移动、计算和同步有更多重叠。这些功能使得从 GPU 代码调用的某些操作能够与同一线程块中的其他 GPU 代码异步执行。这种异步执行不应与中讨论的异步 CUDA API 相混淆。 第2.3节，这使得 GPU 内核启动或内存操作能够彼此异步操作或与 CPU 异步操作。

计算能力 8.0（NVIDIA Ampere GPU 架构）引入了从全局到共享内存的硬件加速异步数据复制和异步屏障（请参阅 NVIDIA A100 张量核心 GPU 架构 ).

计算能力 9.0（NVIDIA Hopper GPU 架构）扩展了异步执行功能 张量内存加速器 (TMA) 单元，它可以将大数据块和多维张量从全局内存传输到共享内存，反之亦然，异步事务屏障和异步矩阵乘法累加运算（请参阅 深入了解 Hopper 架构 博客文章了解详细信息。）。

CUDA 提供了 API，线程可以从设备代码调用这些 API 来使用这些功能。异步编程模型定义了与 CUDA 线程相关的异步操作的行为。

异步操作是由 CUDA 线程发起的操作，但像另一个线程一样异步执行，我们将其称为 异步线程。在格式良好的程序中，一个或多个 CUDA 线程与异步操作同步。启动异步操作的 CUDA 线程不需要位于同步线程中。异步线程始终与启动操作的 CUDA 线程关联。

异步操作使用同步对象来表示其完成，该对象可以是屏障或管道。这些同步对象在中详细解释 高级同步原语，它们在执行异步内存操作中的作用在 异步数据复制.

3.2.2.3.1. 异步线程和异步代理#

异步操作访问内存的方式可能与常规操作不同。为了区分这些不同的内存访问方法，CUDA 引入了 异步线程, a 通用代理，和一个 异步代理。正常操作（加载和存储）通过通用代理。一些异步指令，例如 LDGSTS 和 STAS/REDAS，使用在通用代理中操作的异步线程进行建模。其他异步指令，例如使用 TMA 的批量异步复制和一些张量核心操作（tcgen05.*、wgmma.mma_async.*），是使用异步代理中操作的异步线程进行建模的。

在通用代理中运行的异步线程。当发起异步操作时，它会与异步线程关联，该异步线程与发起操作的 CUDA 线程不同。 Preceding 保证在异步操作之前对通用代理（正常）加载和存储到同一地址进行排序。然而， subsequent 正常加载和存储到同一地址不能保证维持其顺序，可能会导致竞争条件，直到异步线程完成。

在异步代理中运行的异步线程。当发起异步操作时，它会与异步线程关联，该异步线程与发起操作的 CUDA 线程不同。 之前和之后 正常加载和存储到同一地址不能保证保持其顺序。需要代理栅栏来跨不同代理同步它们，以确保正确的内存排序。部分 使用张量内存加速器（TMA） 演示使用代理栅栏来确保使用 TMA 执行异步复制时的正确性。

有关这些概念的更多详细信息，请参阅 PTX ISA documentation.

3.2.3. 线程范围#

CUDA 线程形成一个 线程层次结构，并且使用此层次结构对于编写正确且高性能的 CUDA 内核至关重要。在此层次结构中，内存操作的可见性和同步范围可能会有所不同。为了解决这种不均匀性，CUDA 编程模型引入了概念 线程范围。线程作用域定义了哪些线程可以观察线程的加载和存储，并指定哪些线程可以使用原子操作和屏障等同步原语相互同步。每个作用域在内存层次结构中都有一个关联的一致性点。

3.2.4. 高级同步原语#

本节介绍三个同步原语系列：

  • 范围原子，它将 C++ 内存排序与 CUDA 线程范围配对，以在块、集群、设备或系统范围内跨线程安全地进行通信（请参阅 线程范围).

  • 异步屏障，它将同步分为到达和等待阶段，并且可用于跟踪异步操作的进度。

  • 流水线，它分阶段工作并协调多缓冲区生产者-消费者模式，通常用于与以下内容重叠计算 异步数据复制.

3.2.4.1. 范围原子#

第 5.4.5 节 概述了 CUDA 中可用的原子函数。在本节中，我们将重点关注 scoped 支持的原子 C++ 标准原子内存 语义，可通过 libcu++ 库或通过编译器内置函数。作用域原子提供了在 CUDA 线程层次结构的适当级别上进行高效同步的工具，从而实现复杂并行算法的正确性和性能。

3.2.4.1.1. 线程作用域和内存排序#

范围原子结合了两个关键概念：

  • 线程范围：定义哪些线程可以观察原子操作的效果（参见 线程范围).

  • 内存排序：定义相对于其他内存操作的排序约束（参见 C++ 标准原子内存语义).

#include <cuda/atomic>

__global__ void block_scoped_counter() {
    // 共享原子计数器仅在此块内可见
    __shared__ cuda::atomic<int, cuda::thread_scope_block> counter;

    // 初始化计数器（只有一个线程应该执行此操作）
    if (threadIdx.x == 0) {
        counter.store(0, cuda::memory_order_relaxed);
    }
    __syncthreads();

    // 块中的所有线程以原子方式递增
    int old_value = counter.fetch_add(1, cuda::memory_order_relaxed);

    // 使用旧值...
}

__global__ void block_scoped_counter() {
    // 共享计数器仅在此块内可见
    __shared__ int counter;

    // 初始化计数器（只有一个线程应该执行此操作）
    if (threadIdx.x == 0) {
        __nv_atomic_store_n(&counter, 0,
                            __NV_ATOMIC_RELAXED,
                            __NV_THREAD_SCOPE_BLOCK);
    }
    __syncthreads();

    // 块中的所有线程以原子方式递增
    int old_value = __nv_atomic_fetch_add(&counter, 1,
                                          __NV_ATOMIC_RELAXED,
                                          __NV_THREAD_SCOPE_BLOCK);

    // 使用旧值...
}

这个例子实现了一个 块范围原子计数器 这演示了作用域原子的基本概念：

  • 共享变量：单个计数器在块中的所有线程之间共享，使用 __shared__ memory.

  • 原子类型声明: cuda::atomic<int, cuda::thread_scope_block> 创建具有块级可见性的原子整数。

  • 单次初始化：只有线程 0 初始化计数器以防止设置过程中出现竞争情况。

  • 块同步: __syncthreads() 确保所有线程在继续之前都能看到初始化的计数器。

  • 原子增量：每个线程自动递增计数器并接收先前的值。

cuda::memory_order_relaxed 这里选择 是因为我们只需要原子性（不可分割的读-修改-写），而无需不同内存位置之间的排序约束。由于这是一个简单的计数操作，因此增量的顺序对于正确性并不重要。

对于生产者-消费者模式，获取-释放语义确保正确的排序：

__global__ void producer_consumer() {
    __shared__ int data;
    __shared__ cuda::atomic<bool, cuda::thread_scope_block> ready;

    if (threadIdx.x == 0) {
        // 生产者：写入数据然后发出就绪信号
        data = 42;
        ready.store(true, cuda::memory_order_release);  // Release保证数据写入可见
    } else {
        // 消费者：等待就绪信号然后读取数据
        while (!ready.load(cuda::memory_order_acquire)) {  // 获取确保数据读取可看到写入
            // 旋转等待
        }
        int value = data;
        // 过程值...
    }
}

__global__ void producer_consumer() {
    __shared__ int data;
    __shared__ bool ready; // 只有就绪标志需要原子操作

    if (threadIdx.x == 0) {
        // 生产者：写入数据然后发出就绪信号
        data = 42;
        __nv_atomic_store_n(&ready, true,
                            __NV_ATOMIC_RELEASE,
                            __NV_THREAD_SCOPE_BLOCK);  // Release保证数据写入可见
    } else {
        // 消费者：等待就绪信号然后读取数据
        while (!__nv_atomic_load_n(&ready,
                                   __NV_ATOMIC_ACQUIRE,
                                   __NV_THREAD_SCOPE_BLOCK)) {  // 获取确保数据读取可看到写入
            // 旋转等待
        }
        int value = data;
        // 过程值...
    }
}

3.2.4.1.2. 性能考虑因素#

  • 使用尽可能窄的范围：块范围的原子比系统范围的原子快得多。

  • 更喜欢较弱的订单：仅在需要正确性时才使用更强的排序。

  • 考虑内存位置：共享内存原子比全局内存原子更快。

3.2.4.2. 异步屏障#

异步屏障不同于典型的单级屏障（__syncthreads()），因为线程通知它已到达屏障（“到达”）与等待其他线程到达屏障的操作（“等待”）是分开的。这种分离允许线程执行与屏障无关的附加操作，从而提高执行效率，从而更有效地利用等待时间。异步屏障可用于通过 CUDA 线程实现生产者-消费者模式，或者通过在完成时让复制操作向屏障发出信号（“到达”）来启用内存层次结构内的异步数据复制。

异步屏障可在计算能力 7.0 或更高版本的设备上使用。计算能力 8.0 或更高的设备通过允许块内 CUDA 线程的任何子集的硬件加速同步，为共享内存中的异步屏障提供硬件加速，并在同步粒度方面取得显着进步。以前的架构只能加速整个warp 的同步（__syncwarp()) 或整块 (__syncthreads()）水平。

CUDA 编程模型通过以下方式提供异步屏障 cuda::std::barrier，一个符合 ISO C++ 的屏障，可用于 libcu++ 图书馆。除了实施 std::barrier，该库提供了 CUDA 特定的扩展来选择屏障的线程范围以提高性能并公开较低级别的 cuda::ptx API。一个 cuda::barrier 可以与 cuda::ptx 通过使用 friend function cuda::device::barrier_native_handle() 检索屏障的本机句柄并将其传递给 cuda::ptx 功能。 CUDA还提供了 原语API 用于线程块范围内共享内存中的异步屏障。

如果没有异步到达等待屏障，线程块内的同步可以通过以下方式实现： __syncthreads() 或 block.sync() 使用时 合作团体.

#include <cooperative_groups.h>

__global__ void simple_sync(int iteration_count) {
    auto block = cooperative_groups::this_thread_block();

    for (int i = 0; i < iteration_count; ++i) {
        /* 到达前的代码 */

         // 等待所有线程到达这里。
        block.sync();

        /* 等待后的代码 */
    }
}

线程在同步点（block.sync()）直到所有线程都到达同步点。此外，保证同步点之前发生的内存更新对于同步点之后的块中的所有线程都是可见的。

该模式分为三个阶段：

  • Code before 同步执行将被读取的内存更新 after 同步。

  • 同步点。

  • Code after 同步，可以看到发生的内存更新 before 同步。

使用异步屏障代替，时间分割同步模式如下。

#include <cuda/barrier>
#include <cooperative_groups.h>

__device__ void compute(float *data, int iteration);

__global__ void split_arrive_wait(int iteration_count, float *data)
{
  using barrier_t = cuda::barrier<cuda::thread_scope_block>;
  __shared__ barrier_t bar;
  auto block = cooperative_groups::this_thread_block();

  if (block.thread_rank() == 0)
  {
    // 使用预期到达计数初始化障碍。
    init(&bar, block.size());
  }
  block.sync();

  for (int i = 0; i < iteration_count; ++i)
  {
    /* 到达前的代码 */

    // 该线程到达。到达不会阻塞线程。
    barrier_t::arrival_token token = bar.arrive();

    compute(data, i);

    // 等待参与屏障的所有线程完成 bar.arrive()。
    bar.wait(std::move(token));

    /* 等待后的代码 */
  }
}

#include <cuda/ptx>
#include <cooperative_groups.h>

__device__ void compute(float *data, int iteration);

__global__ void split_arrive_wait(int iteration_count, float *data)
{
  __shared__ uint64_t bar;
  auto block = cooperative_groups::this_thread_block();

  if (block.thread_rank() == 0)
  {
    // 使用预期到达计数初始化障碍。
    cuda::ptx::mbarrier_init(&bar, block.size());
  }
  block.sync();

  for (int i = 0; i < iteration_count; ++i)
  {
    /* 到达前的代码 */

    // 该线程到达。到达不会阻塞线程。
    uint64_t token = cuda::ptx::mbarrier_arrive(&bar);

    compute(data, i);

    // 等待参与屏障的所有线程完成 mbarrier_arrive()。
    while(!cuda::ptx::mbarrier_try_wait(&bar, token)) {}

    /* 等待后的代码 */
  }
}

#include <cuda_awbarrier_primitives.h>
#include <cooperative_groups.h>

__device__ void compute(float *data, int iteration);

__global__ void split_arrive_wait(int iteration_count, float *data)
{
  __shared__ __mbarrier_t bar;
  auto block = cooperative_groups::this_thread_block();

  if (block.thread_rank() == 0)
  {
    // 使用预期到达计数初始化障碍。
    __mbarrier_init(&bar, block.size());
  }
  block.sync();

  for (int i = 0; i < iteration_count; ++i)
  {
    /* 到达前的代码 */

    // 该线程到达。到达不会阻塞线程。
    __mbarrier_token_t token = __mbarrier_arrive(&bar);

    compute(data, i);

    // 等待参与屏障的所有线程完成 __mbarrier_arrive()。
    while(!__mbarrier_try_wait(&bar, token, 1000)) {}

    /* 等待后的代码 */
  }
}

在此模式中，同步点被分为到达点 (bar.arrive()）和一个等待点（bar.wait(std::move(token))）。一个线程开始参与一个 cuda::barrier 第一次致电 bar.arrive()。当一个线程调用 bar.wait(std::move(token)) 它将被阻塞，直到参与线程完成 bar.arrive() 预期次数，这是传递给的预期到达计数参数 init()。在参与线程调用之前发生的内存更新 bar.arrive() 保证在调用后对参与线程可见 bar.wait(std::move(token))。请注意，调用 bar.arrive() 不会阻塞线程，它可以继续执行其他工作，这些工作不依赖于其他参与线程调用之前发生的内存更新 bar.arrive().

到达并等待 模式有五个阶段：

  • Code before 到达执行将被读取的内存更新 after 等待。

  • 到达具有隐式内存栅栏的点（即，相当于 cuda::atomic_thread_fence(cuda::memory_order_seq_cst, cuda::thread_scope_block)).

  • Code between 到达并等待。

  • 等待点。

  • Code after 等待，可以看到已执行的更新 before 到达。

有关如何使用异步屏障的综合指南，请参阅 异步屏障.

3.2.4.3. 流水线#

CUDA 编程模型提供管道同步对象作为协调机制，将异步内存副本排序为多个阶段，从而促进双或多缓冲生产者-消费者模式的实现。管道是一个双端队列 head 和一个 tail 以先进先出 (FIFO) 顺序处理工作。生产者线程将工作提交到管道的头部，而消费者线程从管道的尾部提取工作。

管道暴露在外 cuda::pipeline API 在 libcu++ 图书馆，以及通过 原语API。下表描述了两个 API 的主要功能。

获取管道内部队列中的可用阶段。

producer_commit

提交之后发出的异步操作 producer_acquire 调用当前获取的管道阶段。

consumer_wait

等待管道最旧阶段中的异步操作完成。

consumer_release

将管道最旧的阶段释放给管道对象以供重用。然后，制作人可以获取已发布的舞台。

cuda::pipeline API 具有更丰富的接口和更少的限制，而原语 API 仅支持跟踪从全局内存到具有特定大小和对齐要求的共享内存的异步副本。原语 API 提供与 cuda::pipeline 对象与 cuda::thread_scope_thread.

有关详细的使用模式和示例，请参阅 流水线.

3.2.5. 异步数据复制#

内存层次结构内的高效数据移动是实现 GPU 计算高性能的基础。传统的同步内存操作迫使线程在数据传输期间等待空闲。 GPU 本质上通过并行性隐藏内存延迟。也就是说，当内存操作完成时，SM 切换到执行另一个 warp。即使通过并行性隐藏了这种延迟，内存延迟仍然有可能成为内存带宽利用率和计算资源效率的瓶颈。为了解决这些瓶颈，现代 GPU 架构提供了硬件加速的异步数据复制机制，允许内存传输独立进行，同时线程继续执行其他工作。

异步数据复制通过将内存传输的启动与等待其完成分离来实现计算与数据移动的重叠。这样，线程可以在内存延迟期间执行有用的工作，从而提高总体吞吐量和资源利用率。

注

虽然本节的概念和原则与前面章节中讨论的类似 异步执行，该章涵盖了内核的异步执行和内存传输，例如由 cudaMemcpyAsync。这可以被认为是应用程序不同组件的异步。

本节中描述的异步是指能够在 GPU 的 DRAM（即全局内存）和 on-SM 内存（例如共享内存或张量内存）之间传输数据，而不会阻塞 GPU 线程。这是单个内核启动执行中的异步。

要了解异步副本如何提高性能，检查常见的 GPU 计算模式会很有帮助。 CUDA 应用程序通常采用 复制和计算 模式：

  • 从全局内存中获取数据，

  • 将数据存储到共享内存，以及

  • 对共享内存数据执行计算，并可能将结果写回全局内存。

copy 该模式的阶段通常表示为 shared[local_idx] = global[global_idx]。编译器将这种全局到共享内存的复制扩展为从全局内存读取到寄存器，然后从寄存器写入共享内存。

当这种模式出现在迭代算法中时，每个线程块都需要在迭代算法之后进行同步。 shared[local_idx] = global[global_idx] 分配，以确保在计算阶段开始之前完成对共享内存的所有写入。线程块还需要在计算阶段之后再次同步，以防止在所有线程完成计算之前覆盖共享内存。下面的代码片段说明了这种模式。

#include <cooperative_groups.h>

__device__ void compute(int* global_out, int const* shared_in) {
    // 使用共享内存中当前批次的所有值进行计算。
    // 将该线程的结果存储回全局内存。
}

__global__ void without_async_copy(int* global_out, int const* global_in, size_t size, size_t batch_sz) {
  auto grid = cooperative_groups::this_grid();
  auto block = cooperative_groups::this_thread_block();
  assert(size == batch_sz * grid.size()); // 说明：输入大小适合batch_sz * grid_size

  extern __shared__ int shared[]; // block.size() * sizeof(int) 字节

  size_t local_idx = block.thread_rank();

  for (size_t batch = 0; batch < batch_sz; ++batch) {
    // 计算全局内存中该块的当前批次的索引。
    size_t block_batch_idx = block.group_index().x * block.size() + grid.size() * batch;
    size_t global_idx = block_batch_idx + threadIdx.x;
    shared[local_idx] = global_in[global_idx];

    // 等待所有副本完成。
    block.sync();

    // 计算并将结果写入全局内存。
    compute(global_out + block_batch_idx, shared);

    // 等待使用共享内存的计算完成。
    block.sync();
  }
}

通过异步数据复制，可以异步完成从全局内存到共享内存的数据移动，以便在等待数据到达时更有效地使用 SM。

#include <cooperative_groups.h>
#include <cooperative_groups/memcpy_async.h>

__device__ void compute(int* global_out, int const* shared_in) {
    // 使用共享内存中当前批次的所有值进行计算。
    // 将该线程的结果存储回全局内存。
}

__global__ void with_async_copy(int* global_out, int const* global_in, size_t size, size_t batch_sz) {
  auto grid = cooperative_groups::this_grid();
  auto block = cooperative_groups::this_thread_block();
  assert(size == batch_sz * grid.size()); // 说明：输入大小适合batch_sz * grid_size

  extern __shared__ int shared[]; // block.size() * sizeof(int) 字节

  size_t local_idx = block.thread_rank();

  for (size_t batch = 0; batch < batch_sz; ++batch) {
    // 计算全局内存中该块的当前批次的索引。
    size_t block_batch_idx = block.group_index().x * block.size() + grid.size() * batch;

    // 整个线程组协作地将整个批次复制到共享内存。
    cooperative_groups::memcpy_async(block, shared, global_in + block_batch_idx, block.size());

    // 等待时计算不同的数据。

    // 等待所有副本完成。
    cooperative_groups::wait(block);

    // 计算并将结果写入全局内存。
    compute(global_out + block_batch_idx, shared);

    // 等待使用共享内存的计算完成。
    block.sync();
  }
}

cooperative_groups::memcpy_async 函数副本 block.size() 元素从全局内存到 shared 数据。此操作的发生就像由另一个线程执行一样，该线程与当前线程的调用同步 cooperative_groups::wait 复制完成后。在复制操作完成之前，修改全局数据或读取或写入共享数据会引入数据竞争。

此示例说明了所有异步复制操作背后的基本概念：它们将内存传输启动与完成分离，允许线程在数据在后台移动时执行其他工作。 CUDA 编程模型提供了多个 API 来访问这些功能，包括 memcpy_async 可用的功能 合作团体 和 libcu++ 图书馆以及较低级别的 cuda::ptx 和原语 API。这些 API 共享相似的语义：它们将对象从源复制到目标，就好像由另一个线程执行一样，在复制完成后，可以使用不同的完成机制进行同步。

现代 GPU 架构为异步数据移动提供了多种硬件机制。

  • LDGSTS（计算能力 8.0+）允许从全局内存到共享内存的高效小规模异步传输。

  • 张量内存加速器（TMA，计算能力 9.0+）扩展了这些功能，提供针对大型多维数据传输优化的批量异步复制操作

  • STAS 指令（计算能力 9.0+）支持从寄存器到集群内分布式共享内存的小规模异步传输。

这些机制支持不同的数据路径、传输大小和对齐要求，允许开发人员为其特定的数据访问模式选择最合适的方法。下表概述了 GPU 内异步副本支持的数据路径。

3.2.6. 配置 L1/共享内存平衡#

正如中提到的 一级数据缓存，SM上的L1和共享内存使用相同的物理资源，称为统一数据缓存。在大多数架构上，如果内核使用很少或不使用共享内存，则可以将统一数据缓存配置为提供架构允许的最大数量的 L1 缓存。

为共享内存保留的统一数据缓存可在每个内核的基础上进行配置。 应用程序可以设置 carveout，或首选共享内存容量，与 cudaFuncSetAttribute 在内核启动之前调用的函数。

cudaFuncSetAttribute(kernel_name, cudaFuncAttributePreferredSharedMemoryCarveout, carveout);

应用程序可以设置 carveout 作为该架构支持的最大共享内存容量的整数百分比。 除了整数百分比之外，还提供了三个方便的枚举作为剥离值。

  • cudaSharedmemCarveoutDefault

  • cudaSharedmemCarveoutMaxL1

  • cudaSharedmemCarveoutMaxShared

支持的最大共享内存和支持的剥离大小因架构而异；看到 每个计算能力的共享内存容量 了解详情。

如果所选的整数百分比剥离未准确映射到支持的共享内存容量，则使用下一个更大的容量。 例如，对于计算能力 12.0 的设备（最大共享内存容量为 100KB），将剥离设置为 50% 将导致共享内存为 64KB，而不是 50KB，因为计算能力 12.0 的设备支持的共享内存大小为 0、8、16、32、64 和 100。

该函数传递给 cudaFuncSetAttribute 必须与 __global__ specifier. cudaFuncSetAttribute 被驱动程序解释为提示，并且如果需要执行内核，驱动程序可以选择不同的剥离大小。

注

另一个 CUDA API， cudaFuncSetCacheConfig，还允许应用程序调整内核的 L1 和共享内存之间的平衡。然而，该 API 对内核启动的共享/L1 平衡提出了硬性要求。因此，将内核与不同的共享内存配置交错是不必要的 序列化发射 共享内存重新配置的背后。 cudaFuncSetAttribute 是首选，因为如果需要执行该功能或避免抖动，驱动程序可以选择不同的配置。

依赖于每块超过 48 KB 共享内存分配的内核是特定于体系结构的。 因此他们必须使用 动态共享内存 而不是静态大小的数组，并且需要显式选择使用 cudaFuncSetAttribute 如下。

// 设备代码
__global__ void MyKernel(...)
{
  extern __shared__ float buffer[];
  ...
}

// 主机代码
int maxbytes = 98304; // 96 KB
cudaFuncSetAttribute(MyKernel, cudaFuncAttributeMaxDynamicSharedMemorySize, maxbytes);
MyKernel <<<gridDim, blockDim, maxbytes>>>(...);
