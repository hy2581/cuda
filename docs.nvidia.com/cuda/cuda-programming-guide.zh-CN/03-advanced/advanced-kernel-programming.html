3.2. 高级内核编程#

本章首先更深入地介绍 NVIDIA GPU 的硬件模型，然后介绍 CUDA 内核代码中用于提升内核性能的一些高级特性。本章还会说明与线程作用域、异步执行以及相关同步原语有关的概念。这些概念性内容为内核代码中可用的若干高级性能特性奠定必要基础。

本编程指南下一部分中有专门章节，对其中一些特性做更完整的说明。

  • 本章介绍的 高级同步原语，会在 第 4.9 节 和 第 4.10 节 中完整介绍。

  • 本章介绍的 异步数据拷贝（包括张量内存加速器 TMA），会在 第 4.11 节 中完整介绍。

3.2.1. 使用 PTX#

并行线程执行（Parallel Thread Execution，PTX）是 CUDA 用来抽象硬件 ISA 的虚拟机指令集架构（ISA），已在 第 1.3.3 节 中介绍。直接编写 PTX 代码是一种非常高级的优化技术，大多数开发者并不需要，应当将其视为最后手段。不过，在某些场景下，直接编写 PTX 带来的细粒度控制可以提高特定应用的性能。这些场景通常位于应用中对性能极其敏感的部分，哪怕不到百分之一的性能提升也有明显价值。所有可用的 PTX 指令都列在 PTX ISA 文档 中。

cuda::ptx 命名空间

在代码中直接使用 PTX 的一种方法，是使用 libcu++ 提供的 cuda::ptx 命名空间。该命名空间提供了直接映射到 PTX 指令的 C++ 函数，使其更容易在 C++ 应用中使用。更多信息请参阅 cuda::ptx 命名空间 文档。

内联 PTX

另一种在代码中包含 PTX 的方法是使用内联 PTX。相应的 文档 对这种方法做了详细说明。它与在 CPU 上编写汇编代码非常相似。

3.2.2. 硬件实现#

流式多处理器（Streaming Multiprocessor，SM；参见 GPU 硬件模型）设计用于并发执行数百个线程。为了管理如此多的线程，SM 使用一种独特的并行计算模型，称为 单指令、多线程（Single-Instruction, Multiple-Thread，SIMT），该模型会在 SIMT 执行模型 中说明。指令以流水线方式执行，既利用单个线程内的指令级并行性，也通过同步硬件多线程利用大量线程级并行性，详见 硬件多线程。与 CPU 核心不同，SM 按顺序发射指令，不执行分支预测或推测执行。

SIMT 执行模型 和 硬件多线程 两节描述所有设备共有的 SM 架构特性。计算能力 一节提供不同计算能力设备的具体信息。

NVIDIA GPU 架构使用小端表示法。

3.2.2.1. SIMT 执行模型#

每个 SM 都以 32 个并行线程为一组来创建、管理、调度和执行线程，这样的一组线程称为 warp。组成同一 warp 的各个线程会从相同的程序地址一起开始执行，但每个线程都有自己的指令地址计数器和寄存器状态，因此可以自由地独立分支和执行。术语 warp 源自织造，也是最早的并行线程技术名称。half-warp 指 warp 的前半部分或后半部分；quarter-warp 指 warp 的第一、第二、第三或第四个四分之一部分。

一个 warp 每次执行一条共同指令，因此当 warp 中全部 32 个线程采用相同执行路径时，效率最高。如果一个 warp 中的线程因数据相关的条件分支而发生发散，warp 会依次执行被采用的各个分支路径，并禁用不在当前路径上的线程。分支发散只发生在 warp 内部；不同 warp 会独立执行，无论它们执行的是相同代码路径还是不同代码路径。

SIMT 架构与 SIMD（单指令、多数据）向量组织相似，因为单条指令会控制多个处理元素。关键区别在于，SIMD 向量组织会将 SIMD 宽度暴露给软件，而 SIMT 指令描述的是单个线程的执行和分支行为。与 SIMD 向量机相比，SIMT 允许程序员为独立的标量线程编写线程级并行代码，也能为协同工作的线程编写数据并行代码。为了保证正确性，程序员基本上可以忽略 SIMT 行为；但如果在代码结构上尽量避免同一 warp 内线程发散，就能获得显著的性能提升。实践中，这与缓存行的作用类似：为了正确性设计程序时可以安全地忽略缓存行大小，但为了峰值性能设计程序时就必须在代码结构中考虑它。另一方面，向量架构要求软件将加载合并成向量，并手动管理发散。

3.2.2.1.1. 独立线程调度#

在计算能力低于 7.0 的 GPU 上，一个 warp 使用由其中全部 32 个线程共享的单个程序计数器，并配有一个活动掩码来标识该 warp 中的活动线程。因此，同一 warp 中处于发散区域或不同执行状态的线程无法相互发信号或交换数据；需要通过锁或互斥量保护细粒度共享数据的算法，可能会因竞争线程所属的 warp 不同而导致死锁。

在计算能力 7.0 及更高版本的 GPU 中，独立线程调度 允许线程之间实现完全并发，不受 warp 边界限制。采用独立线程调度时，GPU 会为每个线程维护执行状态，包括程序计数器和调用栈，并能以线程为粒度让出执行，以便更充分地利用执行资源，或让一个线程等待另一个线程产生数据。调度优化器会决定如何把同一 warp 中的活动线程重新组合成 SIMT 单元。这样既保留了早期 NVIDIA GPU 中 SIMT 执行的高吞吐量，又提供了更大的灵活性：线程现在可以在小于 warp 的粒度上发散并重新汇合。

独立线程调度可能破坏依赖旧 GPU 架构隐式 warp 同步行为的代码。warp 同步 代码假设同一 warp 中的线程在每条指令处都锁步执行，但线程可以在子 warp 粒度上发散并重新汇合后，这种假设不再成立。这可能导致实际参与执行的线程集合与预期不同。任何为 CC 7.0 之前 GPU 编写的 warp 同步代码（例如不显式同步的 warp 内归约）都应重新检查以确保兼容性。开发者应使用 __syncwarp() 显式同步这类代码，以保证其在所有 GPU 世代上行为正确。

注

参与当前指令的 warp 线程称为 活动 线程，而不参与当前指令的线程称为 非活动（被禁用）线程。线程可能因多种原因处于非活动状态，例如比同一 warp 中的其他线程更早退出、采用了不同于当前 warp 正在执行路径的分支路径，或者它们位于线程数不是 warp 大小整数倍的线程块末尾。

如果一个 warp 执行的非原子指令让该 warp 中多个线程写入全局内存或共享内存中的同一位置，那么写入该位置时发生的序列化写入次数可能因设备计算能力而异。不过，对所有计算能力而言，最终由哪个线程完成写入都是未定义的。

如果一个 warp 执行的 原子 指令让该 warp 中多个线程对全局内存中的同一位置执行读取、修改和写入，那么针对该位置的每一次读/改/写都会发生，并且都会被序列化，但它们发生的顺序未定义。

3.2.2.2. 硬件多线程#

当 SM 接收到一个或多个待执行线程块时，它会把这些线程块划分为 warp，并由 warp 调度器 调度每个 warp 执行。线程块划分为 warp 的方式始终相同：每个 warp 包含线程 ID 连续递增的一组线程，第一个 warp 包含线程 0。线程层次结构 说明了线程 ID 与线程块内线程索引之间的关系。

线程块中的 warp 总数定义如下：

\(\text{ceil}\left(\frac{T}{W_{size}}, 1 \right)\)

  • T 是每个块的线程数，

  • Wsize 是 warp 大小，等于 32，

  • ceil(x, y) 表示将 x 向上舍入到最接近的 y 的倍数。

SM 处理的每个 warp 的执行上下文（程序计数器、寄存器等）都会在该 warp 的整个生命周期内保留在片上。因此，在 warp 之间切换没有开销。在每个指令发射周期，warp 调度器会选择一个已有线程准备好执行下一条指令的 warp（即该 warp 的 活动线程），并向这些线程发射该指令。

每个 SM 都有一组 32 位寄存器，会在各个 warp 之间分配；还有一块 共享内存，会在线程块之间分配。对于给定内核，能够驻留在 SM 上并被并发处理的线程块数和 warp 数，取决于该内核使用的寄存器和共享内存数量，以及 SM 上可用的寄存器和共享内存数量。每个 SM 还存在驻留线程块数和驻留 warp 数的上限。这些限制以及 SM 上可用的寄存器和共享内存容量，都取决于设备的计算能力，具体见 计算能力。如果每个 SM 的可用资源不足以处理至少一个线程块，内核启动会失败。分配给一个线程块的寄存器和共享内存总量，可通过 占用率 一节记录的几种方式确定。

3.2.2.3. 异步执行特性#

近几代 NVIDIA GPU 已引入异步执行特性，使 GPU 内部的数据移动、计算和同步能够更多地重叠。这些特性允许从 GPU 代码调用的某些操作，相对于同一线程块中的其他 GPU 代码异步执行。这里的异步执行不应与 第 2.3 节 中讨论的异步 CUDA API 混淆；后者让 GPU 内核启动或内存操作能够彼此异步，或相对于 CPU 异步。

计算能力 8.0（NVIDIA Ampere GPU 架构）引入了从全局内存到共享内存的硬件加速异步数据拷贝，以及异步屏障（参见 NVIDIA A100 Tensor Core GPU 架构）。

计算能力 9.0（NVIDIA Hopper GPU 架构）通过 张量内存加速器（TMA） 单元扩展了异步执行特性。TMA 可以在全局内存和共享内存之间双向传输大块数据和多维张量；Hopper 还引入了异步事务屏障以及异步矩阵乘加运算（详情见 Hopper 架构深度解析 博客文章）。

CUDA 提供了可由设备代码中的线程调用的 API 来使用这些特性。异步编程模型定义了异步操作相对于 CUDA 线程的行为。

异步操作由 CUDA 线程发起，但会像由另一个线程执行一样异步运行；这里将这个执行实体称为 异步线程。在格式良好的程序中，一个或多个 CUDA 线程会与异步操作同步。发起异步操作的 CUDA 线程不一定是执行同步的线程之一。异步线程始终与发起该操作的 CUDA 线程相关联。

异步操作使用同步对象来表示自身完成；该同步对象可以是屏障，也可以是流水线。这些同步对象会在 高级同步原语 中详细说明，它们在异步内存操作中的作用则会在 异步数据拷贝 中演示。

3.2.2.3.1. 异步线程和异步代理#

异步操作访问内存的方式可能不同于常规操作。为了区分这些不同的内存访问方式，CUDA 引入了 异步线程、通用代理 和 异步代理 等概念。普通操作（加载和存储）会经过通用代理。一些异步指令，例如 LDGSTS 和 STAS/REDAS，会被建模为在通用代理中运行的异步线程。其他异步指令，例如使用 TMA 的批量异步拷贝以及一些张量核心操作（tcgen05.*、wgmma.mma_async.*），会被建模为在异步代理中运行的异步线程。

在通用代理中运行的异步线程。发起异步操作时，该操作会与一个异步线程关联；这个异步线程不同于发起操作的 CUDA 线程。对同一地址而言，异步操作之前的通用代理（普通）加载和存储保证排在该异步操作之前。不过，在异步线程完成之前，同一地址上的后续普通加载和存储并不保证保持相应顺序，因此可能产生竞争条件。

在异步代理中运行的异步线程。发起异步操作时，该操作会与一个异步线程关联；这个异步线程不同于发起操作的 CUDA 线程。对同一地址而言，异步操作之前和之后的普通加载和存储都不保证保持相应顺序。需要使用代理栅栏在不同代理之间进行同步，才能确保正确的内存排序。使用张量内存加速器（TMA） 一节演示了在使用 TMA 执行异步拷贝时，如何通过代理栅栏保证正确性。

有关这些概念的更多细节，请参阅 PTX ISA 文档。

3.2.3. 线程作用域#

CUDA 线程构成一个 线程层次结构，合理使用这一层次结构对于编写正确且高性能的 CUDA 内核至关重要。在该层次结构中，内存操作的可见性和同步作用域可能不同。为表达这种非均匀性，CUDA 编程模型引入了 线程作用域 概念。线程作用域定义哪些线程可以观察某个线程的加载和存储，并指定哪些线程可以通过原子操作、屏障等同步原语彼此同步。每个作用域在内存层次结构中都有一个关联的一致性点。

3.2.4. 高级同步原语#

本节介绍三个同步原语系列：

  • 作用域原子，它将 C++ 内存排序与 CUDA 线程作用域配合使用，以便在块、簇、设备或系统作用域内跨线程安全通信（参见 线程作用域）。

  • 异步屏障，它将同步分为到达和等待阶段，并且可用于跟踪异步操作的进度。

  • 流水线，它对工作进行分阶段处理，并协调多缓冲区生产者-消费者模式，常用于将计算与 异步数据拷贝 重叠。

3.2.4.1. 作用域原子#

第 5.4.5 节 概述了 CUDA 中可用的原子函数。本节重点介绍支持 C++ 标准原子内存 语义的 作用域 原子；它们可通过 libcu++ 库或编译器内置函数使用。作用域原子提供了在 CUDA 线程层次结构适当层级进行高效同步的工具，使复杂并行算法能够兼顾正确性和性能。

3.2.4.1.1. 线程作用域和内存排序#

作用域原子结合了两个关键概念：

  • 线程作用域：定义哪些线程可以观察原子操作的效果（参见 线程作用域）。

  • 内存排序：定义相对于其他内存操作的排序约束（参见 C++ 标准原子内存语义）。

#include <cuda/atomic>

__global__ void block_scoped_counter() {
    // 共享原子计数器仅在此块内可见
    __shared__ cuda::atomic<int, cuda::thread_scope_block> counter;

    // 初始化计数器（只有一个线程应该执行此操作）
    if (threadIdx.x == 0) {
        counter.store(0, cuda::memory_order_relaxed);
    }
    __syncthreads();

    // 块中的所有线程以原子方式递增
    int old_value = counter.fetch_add(1, cuda::memory_order_relaxed);

    // 使用旧值...
}

__global__ void block_scoped_counter() {
    // 共享计数器仅在此块内可见
    __shared__ int counter;

    // 初始化计数器（只有一个线程应该执行此操作）
    if (threadIdx.x == 0) {
        __nv_atomic_store_n(&counter, 0,
                            __NV_ATOMIC_RELAXED,
                            __NV_THREAD_SCOPE_BLOCK);
    }
    __syncthreads();

    // 块中的所有线程以原子方式递增
    int old_value = __nv_atomic_fetch_add(&counter, 1,
                                          __NV_ATOMIC_RELAXED,
                                          __NV_THREAD_SCOPE_BLOCK);

    // 使用旧值...
}

这个示例实现了一个 块作用域原子计数器，演示了作用域原子的基本概念：

  • 共享变量：使用 __shared__ 内存在块中的所有线程之间共享单个计数器。

  • 原子类型声明：cuda::atomic<int, cuda::thread_scope_block> 创建一个具有块级可见性的原子整数。

  • 单次初始化：只有线程 0 初始化计数器以防止设置过程中出现竞争情况。

  • 块同步: __syncthreads() 确保所有线程在继续之前都能看到初始化的计数器。

  • 原子递增：每个线程以原子方式递增计数器，并取得递增前的值。

这里选择 cuda::memory_order_relaxed，是因为我们只需要原子性（不可分割的读-改-写），而不需要不同内存位置之间的排序约束。由于这是简单计数操作，递增发生的顺序并不影响正确性。

对于生产者-消费者模式，获取-释放语义确保正确的排序：

__global__ void producer_consumer() {
    __shared__ int data;
    __shared__ cuda::atomic<bool, cuda::thread_scope_block> ready;

    if (threadIdx.x == 0) {
        // 生产者：写入数据然后发出就绪信号
        data = 42;
        ready.store(true, cuda::memory_order_release);  // release 确保数据写入可见
    } else {
        // 消费者：等待就绪信号然后读取数据
        while (!ready.load(cuda::memory_order_acquire)) {  // acquire 确保读取能看到数据写入
            // 旋转等待
        }
        int value = data;
        // 处理 value...
    }
}

__global__ void producer_consumer() {
    __shared__ int data;
    __shared__ bool ready; // 只有就绪标志需要原子操作

    if (threadIdx.x == 0) {
        // 生产者：写入数据然后发出就绪信号
        data = 42;
        __nv_atomic_store_n(&ready, true,
                            __NV_ATOMIC_RELEASE,
                            __NV_THREAD_SCOPE_BLOCK);  // release 确保数据写入可见
    } else {
        // 消费者：等待就绪信号然后读取数据
        while (!__nv_atomic_load_n(&ready,
                                   __NV_ATOMIC_ACQUIRE,
                                   __NV_THREAD_SCOPE_BLOCK)) {  // acquire 确保读取能看到数据写入
            // 旋转等待
        }
        int value = data;
        // 处理 value...
    }
}

3.2.4.1.2. 性能考虑因素#

  • 使用尽可能窄的作用域：块作用域原子比系统作用域原子快得多。

  • 优先使用较弱的内存顺序：只有在正确性需要时才使用更强的排序。

  • 考虑内存位置：共享内存原子比全局内存原子更快。

3.2.4.2. 异步屏障#

异步屏障不同于典型的单阶段屏障（__syncthreads()）：线程通知自己已经到达屏障的操作（“到达”），与等待其他线程到达屏障的操作（“等待”）是分离的。这种分离允许线程执行不依赖该屏障的额外工作，更有效地利用等待时间，从而提升执行效率。异步屏障可用于通过 CUDA 线程实现生产者-消费者模式，也可用于内存层次结构内的异步数据拷贝：拷贝操作完成时向屏障发出“到达”信号。

异步屏障可在计算能力 7.0 或更高版本的设备上使用。计算能力 8.0 或更高的设备为共享内存中的异步屏障提供硬件加速，允许硬件加速同步线程块内任意 CUDA 线程子集，在同步粒度方面取得了显著进步。早期架构只能在整个 warp（__syncwarp()）或整个线程块（__syncthreads()）级别提供加速同步。

CUDA 编程模型通过 cuda::std::barrier 提供异步屏障，这是一个符合 ISO C++ 的屏障，可在 libcu++ 库中使用。除了实现 std::barrier 之外，该库还提供 CUDA 专用扩展，用于选择屏障的线程作用域以提升性能，并公开更底层的 cuda::ptx API。通过 friend 函数 cuda::device::barrier_native_handle() 取回屏障的原生句柄，并将其传给 cuda::ptx 函数，即可把 cuda::barrier 与 cuda::ptx 搭配使用。CUDA 还为线程块作用域内、共享内存中的异步屏障提供了 原语 API。

同步的时间分割

如果不使用异步到达/等待屏障，线程块内同步可以通过 __syncthreads() 实现；使用 协作组 时，也可以通过 block.sync() 实现。

#include <cooperative_groups.h>

__global__ void simple_sync(int iteration_count) {
    auto block = cooperative_groups::this_thread_block();

    for (int i = 0; i < iteration_count; ++i) {
        /* 到达前的代码 */

         // 等待所有线程到达这里。
        block.sync();

        /* 等待后的代码 */
    }
}

线程会在同步点（block.sync()）阻塞，直到所有线程都到达该同步点。此外，同步点之前发生的内存更新，保证在同步点之后对该线程块中的所有线程可见。

该模式分为三个阶段：

  • 同步 之前 的代码执行内存更新，这些更新会在同步 之后 被读取。

  • 同步点。

  • 同步 之后 的代码，可以看到同步 之前 发生的内存更新。

使用异步屏障代替，时间分割同步模式如下。

#include <cuda/barrier>
#include <cooperative_groups.h>

__device__ void compute(float *data, int iteration);

__global__ void split_arrive_wait(int iteration_count, float *data)
{
  using barrier_t = cuda::barrier<cuda::thread_scope_block>;
  __shared__ barrier_t bar;
  auto block = cooperative_groups::this_thread_block();

  if (block.thread_rank() == 0)
  {
    // 使用预期到达计数初始化屏障。
    init(&bar, block.size());
  }
  block.sync();

  for (int i = 0; i < iteration_count; ++i)
  {
    /* 到达前的代码 */

    // 该线程到达。到达不会阻塞线程。
    barrier_t::arrival_token token = bar.arrive();

    compute(data, i);

    // 等待参与屏障的所有线程完成 bar.arrive()。
    bar.wait(std::move(token));

    /* 等待后的代码 */
  }
}

#include <cuda/ptx>
#include <cooperative_groups.h>

__device__ void compute(float *data, int iteration);

__global__ void split_arrive_wait(int iteration_count, float *data)
{
  __shared__ uint64_t bar;
  auto block = cooperative_groups::this_thread_block();

  if (block.thread_rank() == 0)
  {
    // 使用预期到达计数初始化屏障。
    cuda::ptx::mbarrier_init(&bar, block.size());
  }
  block.sync();

  for (int i = 0; i < iteration_count; ++i)
  {
    /* 到达前的代码 */

    // 该线程到达。到达不会阻塞线程。
    uint64_t token = cuda::ptx::mbarrier_arrive(&bar);

    compute(data, i);

    // 等待参与屏障的所有线程完成 mbarrier_arrive()。
    while(!cuda::ptx::mbarrier_try_wait(&bar, token)) {}

    /* 等待后的代码 */
  }
}

#include <cuda_awbarrier_primitives.h>
#include <cooperative_groups.h>

__device__ void compute(float *data, int iteration);

__global__ void split_arrive_wait(int iteration_count, float *data)
{
  __shared__ __mbarrier_t bar;
  auto block = cooperative_groups::this_thread_block();

  if (block.thread_rank() == 0)
  {
    // 使用预期到达计数初始化屏障。
    __mbarrier_init(&bar, block.size());
  }
  block.sync();

  for (int i = 0; i < iteration_count; ++i)
  {
    /* 到达前的代码 */

    // 该线程到达。到达不会阻塞线程。
    __mbarrier_token_t token = __mbarrier_arrive(&bar);

    compute(data, i);

    // 等待参与屏障的所有线程完成 __mbarrier_arrive()。
    while(!__mbarrier_try_wait(&bar, token, 1000)) {}

    /* 等待后的代码 */
  }
}

在这种模式中，同步点被拆分为到达点（bar.arrive()）和等待点（bar.wait(std::move(token))）。线程第一次调用 bar.arrive() 时，就开始参与该 cuda::barrier。当线程调用 bar.wait(std::move(token)) 时，它会阻塞，直到参与线程完成预期次数的 bar.arrive() 调用；该预期次数就是传给 init() 的预期到达计数参数。参与线程调用 bar.arrive() 之前发生的内存更新，保证在它们调用 bar.wait(std::move(token)) 之后对参与线程可见。注意，调用 bar.arrive() 不会阻塞线程；线程可以继续执行其他工作，只要这些工作不依赖于其他参与线程在调用 bar.arrive() 之前发生的内存更新。

到达并等待 模式有五个阶段：

  • 到达 之前 的代码执行内存更新，这些更新会在等待 之后 被读取。

  • 带隐式内存栅栏的到达点（也就是等价于 cuda::atomic_thread_fence(cuda::memory_order_seq_cst, cuda::thread_scope_block)）。

  • 到达与等待 之间 的代码。

  • 等待点。

  • 等待 之后 的代码，可以看到到达 之前 已执行的更新。

有关异步屏障用法的完整指南，请参阅 异步屏障。

3.2.4.3. 流水线#

CUDA 编程模型提供流水线同步对象，作为将异步内存拷贝组织成多个阶段的协调机制，从而便于实现双缓冲或多缓冲的生产者-消费者模式。流水线是一个带有 head 和 tail 的双端队列，按先进先出（FIFO）顺序处理工作。生产者线程把工作提交到流水线头部，消费者线程则从流水线尾部取出工作。

流水线可通过 libcu++ 库中的 cuda::pipeline API 使用，也可通过 原语 API 使用。下表描述了这两类 API 的主要功能。

cuda::pipeline API

说明

producer_acquire

获取管道内部队列中的可用阶段。

producer_commit

提交在 producer_acquire 调用之后、针对当前已获取流水线阶段发出的异步操作。

consumer_wait

等待管道最旧阶段中的异步操作完成。

consumer_release

把流水线中最旧的阶段释放回流水线对象以便重用。释放后的阶段随后可由生产者获取。

原语 API

说明

__pipeline_memcpy_async

请求提交一次从全局内存到共享内存的内存拷贝，以便异步执行。

__pipeline_commit

提交在当前流水线阶段、该调用之前发出的异步操作。

__pipeline_wait_prior(N)

等待除最近 N 次提交之外，所有提交到流水线的异步操作完成。

cuda::pipeline API 的接口更丰富、限制更少；原语 API 则只支持跟踪从全局内存到共享内存的异步拷贝，并且有特定大小和对齐要求。原语 API 提供的功能等价于线程作用域为 cuda::thread_scope_thread 的 cuda::pipeline 对象。

有关详细使用模式和示例，请参阅 流水线。

3.2.5. 异步数据拷贝#

在内存层次结构内高效移动数据，是 GPU 计算获得高性能的基础。传统同步内存操作会迫使线程在数据传输期间空闲等待。GPU 本身通过并行性隐藏内存延迟，也就是在内存操作完成期间让 SM 切换去执行另一个 warp。即便如此，内存延迟仍可能在内存带宽利用率和计算资源效率两方面成为瓶颈。为解决这些瓶颈，现代 GPU 架构提供了硬件加速的异步数据拷贝机制，使内存传输可以独立推进，同时线程继续执行其他工作。

异步数据拷贝将内存传输的发起与等待其完成解耦，从而让计算与数据移动重叠。这样，线程可以在内存延迟期间执行有用工作，提高总体吞吐量和资源利用率。

注

虽然本节背后的概念和原则，与前面 异步执行 一章讨论的内容相似，但该章讨论的是内核和内存传输（例如通过 cudaMemcpyAsync 发起的传输）的异步执行。这可以看作应用程序不同组件之间的异步。

本节所说的异步，是指在不阻塞 GPU 线程的情况下，在 GPU DRAM（即全局内存）与 SM 内存（例如共享内存或张量内存）之间传输数据。这是单个内核启动执行过程内部的异步。

要理解异步拷贝如何提升性能，考察一种常见的 GPU 计算模式会很有帮助。CUDA 应用通常采用 拷贝并计算 模式：

  • 从全局内存中获取数据，

  • 把数据存储到共享内存，并且

  • 对共享内存中的数据执行计算，并可能把结果写回全局内存。

该模式中的 拷贝 阶段通常写作 shared[local_idx] = global[global_idx]。编译器会把这种从全局内存到共享内存的拷贝展开为：先从全局内存读取到寄存器，再从寄存器写入共享内存。

当这种模式出现在迭代算法中时，每个线程块都需要在 shared[local_idx] = global[global_idx] 赋值之后同步，以确保计算阶段开始前，所有对共享内存的写入都已完成。线程块还需要在计算阶段之后再次同步，以防止所有线程完成计算前共享内存被覆盖。下面的代码片段说明了这种模式。

#include <cooperative_groups.h>

__device__ void compute(int* global_out, int const* shared_in) {
    // 使用共享内存中当前批次的所有值进行计算。
    // 将该线程的结果存储回全局内存。
}

__global__ void without_async_copy(int* global_out, int const* global_in, size_t size, size_t batch_sz) {
  auto grid = cooperative_groups::this_grid();
  auto block = cooperative_groups::this_thread_block();
  assert(size == batch_sz * grid.size()); // 说明：输入大小适合 batch_sz * grid_size

  extern __shared__ int shared[]; // block.size() * sizeof(int) 字节

  size_t local_idx = block.thread_rank();

  for (size_t batch = 0; batch < batch_sz; ++batch) {
    // 计算全局内存中该块的当前批次的索引。
    size_t block_batch_idx = block.group_index().x * block.size() + grid.size() * batch;
    size_t global_idx = block_batch_idx + threadIdx.x;
    shared[local_idx] = global_in[global_idx];

    // 等待所有拷贝完成。
    block.sync();

    // 计算并将结果写入全局内存。
    compute(global_out + block_batch_idx, shared);

    // 等待使用共享内存的计算完成。
    block.sync();
  }
}

借助异步数据拷贝，可以异步完成从全局内存到共享内存的数据移动，使 SM 在等待数据到达期间得到更高效的利用。

#include <cooperative_groups.h>
#include <cooperative_groups/memcpy_async.h>

__device__ void compute(int* global_out, int const* shared_in) {
    // 使用共享内存中当前批次的所有值进行计算。
    // 将该线程的结果存储回全局内存。
}

__global__ void with_async_copy(int* global_out, int const* global_in, size_t size, size_t batch_sz) {
  auto grid = cooperative_groups::this_grid();
  auto block = cooperative_groups::this_thread_block();
  assert(size == batch_sz * grid.size()); // 说明：输入大小适合 batch_sz * grid_size

  extern __shared__ int shared[]; // block.size() * sizeof(int) 字节

  size_t local_idx = block.thread_rank();

  for (size_t batch = 0; batch < batch_sz; ++batch) {
    // 计算全局内存中该块的当前批次的索引。
    size_t block_batch_idx = block.group_index().x * block.size() + grid.size() * batch;

    // 整个线程组协作地将整个批次拷贝到共享内存。
    cooperative_groups::memcpy_async(block, shared, global_in + block_batch_idx, block.size());

    // 等待时计算不同的数据。

    // 等待所有拷贝完成。
    cooperative_groups::wait(block);

    // 计算并将结果写入全局内存。
    compute(global_out + block_batch_idx, shared);

    // 等待使用共享内存的计算完成。
    block.sync();
  }
}

cooperative_groups::memcpy_async 函数会把 block.size() 个元素从全局内存拷贝到 shared 数据。该操作表现得像由另一个线程执行，并在拷贝完成后，与当前线程对 cooperative_groups::wait 的调用同步。在拷贝操作完成之前，修改全局数据，或读取、写入共享数据，都会引入数据竞争。

这个示例说明了所有异步拷贝操作背后的基本概念：它们将内存传输的发起与完成解耦，使线程能够在数据后台移动时执行其他工作。CUDA 编程模型提供了多个 API 来访问这些功能，包括 协作组 和 libcu++ 库中的 memcpy_async 函数，以及更底层的 cuda::ptx 和原语 API。这些 API 语义相似：它们像由另一个线程执行一样，把对象从源复制到目标；拷贝完成后，可以使用不同的完成机制与其同步。

现代 GPU 架构为异步数据移动提供了多种硬件机制。

  • LDGSTS（计算能力 8.0+）允许从全局内存到共享内存的高效小规模异步传输。

  • 张量内存加速器（TMA，计算能力 9.0+）扩展了这些功能，提供针对大型多维数据传输优化的批量异步拷贝操作。

  • STAS 指令（计算能力 9.0+）支持从寄存器到簇内分布式共享内存的小规模异步传输。

这些机制支持不同的数据路径、传输大小和对齐要求，允许开发者为特定数据访问模式选择最合适的方法。下表概述了 GPU 内异步拷贝支持的数据路径。

3.2.6. 配置 L1/共享内存平衡#

如 L1 数据缓存 中所述，SM 上的 L1 与共享内存使用同一份物理资源，称为统一数据缓存。在大多数架构上，如果内核很少使用或不使用共享内存，就可以把统一数据缓存配置为提供该架构允许的最大 L1 缓存容量。

统一数据缓存中为共享内存保留的部分，可以按内核配置。应用程序可以在启动内核之前调用 cudaFuncSetAttribute，设置 carveout，也就是首选共享内存容量。

cudaFuncSetAttribute(kernel_name, cudaFuncAttributePreferredSharedMemoryCarveout, carveout);

应用程序可以把 carveout 设为该架构支持的最大共享内存容量的整数百分比。除了整数百分比之外，还提供了三个便捷枚举值作为 carveout 取值。

  • cudaSharedmemCarveoutDefault

  • cudaSharedmemCarveoutMaxL1

  • cudaSharedmemCarveoutMaxShared

支持的最大共享内存容量和支持的 carveout 大小因架构而异；详情请参阅 每个计算能力的共享内存容量。

如果所选整数百分比 carveout 不能准确映射到某个受支持的共享内存容量，则会使用下一个更大的容量。例如，对于计算能力 12.0 的设备，其最大共享内存容量为 100KB；将 carveout 设为 50% 会得到 64KB 共享内存，而不是 50KB，因为计算能力 12.0 的设备支持的共享内存大小为 0、8、16、32、64 和 100。

传给 cudaFuncSetAttribute 的函数必须使用 __global__ 说明符声明。cudaFuncSetAttribute 会被驱动程序解释为提示；如果执行内核需要，驱动程序可以选择不同的 carveout 大小。

注

另一个 CUDA API cudaFuncSetCacheConfig 也允许应用程序调整某个内核的 L1 与共享内存之间的平衡。不过，该 API 会对内核启动时的共享内存/L1 平衡提出硬性要求。因此，如果交错启动采用不同共享内存配置的内核，就可能因为共享内存重新配置而不必要地 序列化启动。更推荐使用 cudaFuncSetAttribute，因为在执行该函数需要或为避免配置抖动时，驱动程序可以选择不同配置。

依赖每个线程块超过 48 KB 共享内存分配的内核是架构相关的。因此，它们必须使用 动态共享内存，而不是静态大小数组，并且需要像下面这样使用 cudaFuncSetAttribute 显式选择启用。

// 设备代码
__global__ void MyKernel(...)
{
  extern __shared__ float buffer[];
  ...
}

// 主机代码
int maxbytes = 98304; // 96 KB
cudaFuncSetAttribute(MyKernel, cudaFuncAttributeMaxDynamicSharedMemorySize, maxbytes);
MyKernel <<<gridDim, blockDim, maxbytes>>>(...);
