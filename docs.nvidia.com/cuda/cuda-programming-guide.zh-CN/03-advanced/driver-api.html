3.3. CUDA 驱动程序 API#

本指南的前面部分介绍了 CUDA 运行时。正如中提到的 CUDA 运行时 API 和 CUDA 驱动程序 API，CUDA 运行时是在较低级别的 CUDA 驱动程序 API 之上编写的。本节介绍 CUDA 运行时和驱动程序 API 之间的一些差异，以及如何混合它们。大多数应用程序无需与 CUDA 驱动程序 API 交互即可以全部性能运行。不过，驱动程序 API 中有时会早于运行时 API 提供新接口，以及一些高级接口，例如 虚拟内存管理，仅在驱动程序 API 中公开。

驱动程序API是在 cuda 动态库（cuda.dll 或 cuda.so) 在安装设备驱动程序期间将其复制到系统上。它的所有入口点都以 cu 为前缀。

它是一个基于句柄的命令式 API：大多数对象由不透明的句柄引用，这些句柄可以指定给函数来操作对象。

驱动程序 API 中可用的对象总结如下 表6.

驱动程序 API 必须初始化 cuInit() 在调用驱动程序 API 中的任何函数之前。然后必须创建一个 CUDA 上下文，该上下文附加到特定设备并成为调用主机线程的当前上下文，详细信息请参见 上下文.

在 CUDA 上下文中，内核由主机代码显式加载为 PTX 或二进制对象，如中所述 模块。因此，用 C++ 编写的内核必须单独编译为 PTX 或二进制对象。内核是使用 API 入口点启动的，如中所述 内核执行.

任何想要在未来设备架构上运行的应用程序都必须加载 PTX，不是二进制代码。这是因为二进制代码是特定于体系结构的，因此与未来的体系结构不兼容，而 PTX 代码在加载时由设备驱动程序编译为二进制代码。

这是示例的主机代码 Kernels 使用驱动程序API编写：

int main()
{
    int N = ...;
    size_t size = N * sizeof(float);

    // 在主机内存中分配输入向量 h_A 和 h_B
    float* h_A = (float*)malloc(size);
    float* h_B = (float*)malloc(size);

    // 初始化输入向量
    ...

    // 初始化
    cuInit(0);

    // 获取支持CUDA的设备数量
    int deviceCount = 0;
    cuDeviceGetCount(&deviceCount);
    if (deviceCount == 0) {
        printf("There is no device supporting CUDA.\n");
        exit (0);
    }

    // 获取设备0的句柄
    CUdevice cuDevice;
    cuDeviceGet(&cuDevice, 0);

    // 创建上下文
    CUcontext cuContext;
    cuCtxCreate(&cuContext, 0, cuDevice);

    // 从二进制文件创建模块
    CUmodule cuModule;
    cuModuleLoad(&cuModule, "VecAdd.ptx");

    // 在设备内存中分配向量
    CUdeviceptr d_A;
    cuMemAlloc(&d_A, size);
    CUdeviceptr d_B;
    cuMemAlloc(&d_B, size);
    CUdeviceptr d_C;
    cuMemAlloc(&d_C, size);

    // 将向量从主机内存复制到设备内存
    cuMemcpyHtoD(d_A, h_A, size);
    cuMemcpyHtoD(d_B, h_B, size);

    // 从模块获取函数句柄
    CUfunction vecAdd;
    cuModuleGetFunction(&vecAdd, cuModule, "VecAdd");

    // 调用内核
    int threadsPerBlock = 256;
    int blocksPerGrid =
            (N + threadsPerBlock - 1) / threadsPerBlock;
    void* args[] = { &d_A, &d_B, &d_C, &N };
    cuLaunchKernel(vecAdd,
                   blocksPerGrid, 1, 1, threadsPerBlock, 1, 1,
                   0, 0, args, 0);

    ...
}

完整代码可以在 vectorAddDrv CUDA 示例。

3.3.1. 上下文#

CUDA 上下文类似于 CPU 进程。驱动程序 API 中执行的所有资源和操作都封装在 CUDA 上下文中，当上下文被破坏时，系统会自动清理这些资源。除了模块和纹理或表面引用等对象之外，每个上下文都有自己独特的地址空间。结果， CUdeviceptr 来自不同上下文的值引用不同的内存位置。

主机线程一次可能只有一个当前设备上下文。当创建上下文时 cuCtxCreate()，它成为调用主机线程的当前线程。在上下文中运行的 CUDA 函数（大多数不涉及设备枚举或上下文管理的函数）将返回 CUDA_ERROR_INVALID_CONTEXT 如果有效上下文不是线程的当前上下文。

每个主机线程都有一个当前上下文堆栈。 cuCtxCreate() 将新上下文推入堆栈顶部。 cuCtxPopCurrent() 可以调用以将上下文与主机线程分离。然后，上下文是“浮动的”，并且可以作为任何主机线程的当前上下文推送。 cuCtxPopCurrent() 还恢复先前的当前上下文（如果有）。

还为每个上下文维护使用计数。 cuCtxCreate() 创建一个使用计数为 1 的上下文。 cuCtxAttach() 增加使用计数并 cuCtxDetach() 减少它。当调用时使用计数变为 0 时，上下文将被销毁 cuCtxDetach() 或 cuCtxDestroy().

驱动程序 API 可与运行时互操作，并且可以访问主上下文（请参阅 运行时初始化）由运行时从驱动程序 API 通过管理 cuDevicePrimaryCtxRetain().

使用计数促进了在相同上下文中运行的第三方编写的代码之间的互操作性。例如，如果加载三个库以使用相同的上下文，则每个库都会调用 cuCtxAttach() 增加使用计数并 cuCtxDetach() 当库使用完上下文后减少使用计数。对于大多数库，应用程序应该在加载或初始化库之前创建一个上下文；这样，应用程序可以使用自己的启发式方法创建上下文，而库只需对传递给它的上下文进行操作即可。希望创建自己的上下文的库（他们的 API 客户端可能不知道，他们可能已经或可能没有创建自己的上下文）将使用 cuCtxPushCurrent() 或 cuCtxPopCurrent() 如下图所示。

3.3.2. 模块#

模块是设备代码和数据的动态可加载包，类似于 Windows 中的 DLL，由 nvcc 输出（请参阅 与 NVCC 编译）。所有符号的名称（包括函数、全局变量以及纹理或表面引用）均在模块范围内维护，以便独立第三方编写的模块可以在同一 CUDA 上下文中进行互操作。

此代码示例加载模块并检索某个内核的句柄：

CUmodule cuModule;
cuModuleLoad(&cuModule, "myModule.ptx");
CUfunction myKernel;
cuModuleGetFunction(&myKernel, cuModule, "MyKernel");

此代码示例从 PTX 代码编译并加载新模块并解析编译错误：

#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[3];
void* values[3];
char* PTXCode = "some PTX code";
char error_log[BUFFER_SIZE];
int err;
options[0] = CU_JIT_ERROR_LOG_BUFFER;
values[0]  = (void*)error_log;
options[1] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[1]  = (void*)BUFFER_SIZE;
options[2] = CU_JIT_TARGET_FROM_CUCONTEXT;
values[2]  = 0;
err = cuModuleLoadDataEx(&cuModule, PTXCode, 3, options, values);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);

此代码示例从多个 PTX 代码编译、链接和加载新模块，并解析链接和编译错误：

#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[6];
void* values[6];
float walltime;
char error_log[BUFFER_SIZE], info_log[BUFFER_SIZE];
char* PTXCode0 = "some PTX code";
char* PTXCode1 = "some other PTX code";
CUlinkState linkState;
int err;
void* cubin;
size_t cubinSize;
options[0] = CU_JIT_WALL_TIME;
values[0] = (void*)&walltime;
options[1] = CU_JIT_INFO_LOG_BUFFER;
values[1] = (void*)info_log;
options[2] = CU_JIT_INFO_LOG_BUFFER_SIZE_BYTES;
values[2] = (void*)BUFFER_SIZE;
options[3] = CU_JIT_ERROR_LOG_BUFFER;
values[3] = (void*)error_log;
options[4] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[4] = (void*)BUFFER_SIZE;
options[5] = CU_JIT_LOG_VERBOSE;
values[5] = (void*)1;
cuLinkCreate(6, options, values, &linkState);
err = cuLinkAddData(linkState, CU_JIT_INPUT_PTX,
                    (void*)PTXCode0, strlen(PTXCode0) + 1, 0, 0, 0, 0);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);
err = cuLinkAddData(linkState, CU_JIT_INPUT_PTX,
                    (void*)PTXCode1, strlen(PTXCode1) + 1, 0, 0, 0, 0);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);
cuLinkComplete(linkState, &cubin, &cubinSize);
printf("Link completed in %fms. Linker Output:\n%s\n", walltime, info_log);
cuModuleLoadData(cuModule, cubin);
cuLinkDestroy(linkState);

通过使用多线程可以加速模块链接/加载过程的某些部分，包括加载 cubin 时。此代码示例使用 CU_JIT_BINARY_LOADER_THREAD_COUNT 以加快模块加载速度。

#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[3];
void* values[3];
char* cubinCode = "some cubin code";
char error_log[BUFFER_SIZE];
int err;
options[0] = CU_JIT_ERROR_LOG_BUFFER;
values[0]  = (void*)error_log;
options[1] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[1]  = (void*)BUFFER_SIZE;
options[2] = CU_JIT_BINARY_LOADER_THREAD_COUNT;
values[2]  = 0; // 使用与机器上的 CPU 数量一样多的线程
err = cuModuleLoadDataEx(&cuModule, cubinCode, 3, options, values);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);

完整代码可以在 ptxjit CUDA 示例。

3.3.3. 内核执行#

cuLaunchKernel() 使用给定的执行配置启动内核。

参数可以作为指针数组传递（紧邻最后一个参数） cuLaunchKernel()）其中第 n 个指针对应于第 n 个参数并指向从中复制参数的内存区域，或者作为额外选项之一（最后一个参数 cuLaunchKernel()).

当参数作为额外选项传递时（CU_LAUNCH_PARAM_BUFFER_POINTER 选项），它们作为指向单个缓冲区的指针传递，其中参数被假定通过匹配设备代码中每个参数类型的对齐要求而相对于彼此正确偏移。

内置向量类型的设备代码中的对齐要求列于 表 42。对于所有其他基本类型，设备代码中的对齐要求与主机代码中的对齐要求相匹配，因此可以使用以下方式获得 __alignof()。唯一的例外是主机编译器对齐时 double 或 long long （和 long 在 64 位系统上）在一个字边界上而不是在两个字边界上（例如，使用 gcc的编译标志 -mno-align-double）因为在设备代码中这些类型总是在两个字边界上对齐。

CUdeviceptr 是一个整数，但是代表一个指针，所以它的对齐要求是 __alignof(void*).

以下代码示例使用宏 (ALIGN_UP()）调整每个参数的偏移量以满足其对齐要求和另一个宏（ADD_TO_PARAM_BUFFER()) 将每个参数添加到传递给的参数缓冲区中 CU_LAUNCH_PARAM_BUFFER_POINTER option.

#define ALIGN_UP(offset, alignment) \
      (offset) = ((offset) + (alignment) - 1) & ~((alignment) - 1)

char paramBuffer[1024];
size_t paramBufferSize = 0;

#define ADD_TO_PARAM_BUFFER(value, alignment)                   \
    do {                                                        \
        paramBufferSize = ALIGN_UP(paramBufferSize, alignment); \
        memcpy(paramBuffer + paramBufferSize,                   \
               &(value), sizeof(value));                        \
        paramBufferSize += sizeof(value);                       \
    } while (0)

int i;
ADD_TO_PARAM_BUFFER(i, __alignof(i));
float4 f4;
ADD_TO_PARAM_BUFFER(f4, 16); // float4的对齐方式是16
char c;
ADD_TO_PARAM_BUFFER(c, __alignof(c));
float f;
ADD_TO_PARAM_BUFFER(f, __alignof(f));
CUdeviceptr devPtr;
ADD_TO_PARAM_BUFFER(devPtr, __alignof(devPtr));
float2 f2;
ADD_TO_PARAM_BUFFER(f2, 8); // float2的对齐方式是8

void* extra[] = {
    CU_LAUNCH_PARAM_BUFFER_POINTER, paramBuffer,
    CU_LAUNCH_PARAM_BUFFER_SIZE,    &paramBufferSize,
    CU_LAUNCH_PARAM_END
};
cuLaunchKernel(cuFunction,
               blockWidth, blockHeight, blockDepth,
               gridWidth, gridHeight, gridDepth,
               0, 0, 0, extra);

结构体的对齐要求等于其字段的对齐要求的最大值。包含内置向量类型的结构的对齐要求， CUdeviceptr，或不对齐 double 或 long long，因此设备代码和主机代码之间可能有所不同。这样的结构也可以被不同地填充。例如，以下结构在主机代码中根本没有填充，但在设备代码中填充了字段后的 12 个字节 f 由于字段的对齐要求 f4 is 16.

typedef struct {
    float  f;
    float4 f4;
} myStruct;

3.3.4. 运行时和驱动程序 API 之间的互操作性#

应用程序可以将运行时 API 代码与驱动程序 API 代码混合。

如果通过驱动程序 API 创建了上下文并将其设置为当前上下文，则后续运行时调用将使用此上下文，而不是创建新上下文。

如果运行时已初始化， cuCtxGetCurrent() 可用于检索初始化期间创建的上下文。此上下文可供后续驱动程序 API 调用使用。

从运行时隐式创建的上下文称为主上下文（请参阅 运行时初始化）。它可以通过驱动程序 API 进行管理 主要上下文管理 functions.

可以使用任一 API 分配和释放设备内存。 CUdeviceptr 可以转换为常规指针，反之亦然：

CUdeviceptr devPtr;
float* d_data;

// 使用驱动程序 API 进行分配
cuMemAlloc(&devPtr, size);
d_data = (float*)devPtr;

// 使用运行时 API 进行分配
cudaMalloc(&d_data, size);
devPtr = (CUdeviceptr)d_data;

特别是，这意味着使用驱动程序 API 编写的应用程序可以调用使用运行时 API 编写的库（例如 cuFFT、cuBLAS 等）。

参考手册的设备和版本管理部分中的所有功能都可以互换使用。
