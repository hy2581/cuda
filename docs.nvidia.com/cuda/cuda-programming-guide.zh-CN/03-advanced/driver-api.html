3.3. CUDA 驱动程序 API#

本指南前面几节已经介绍了 CUDA 运行时。如 CUDA 运行时 API 和 CUDA 驱动程序 API 中所述，CUDA 运行时构建在更底层的 CUDA 驱动程序 API 之上。本节介绍 CUDA 运行时与驱动程序 API 的一些差异，以及如何混合使用二者。大多数应用无须直接与 CUDA 驱动程序 API 交互，也能以完整性能运行。不过，有些新接口会先在驱动程序 API 中出现，晚于此才进入运行时 API；还有一些高级接口，例如 虚拟内存管理，只在驱动程序 API 中公开。

驱动程序 API 由 cuda 动态库（cuda.dll 或 cuda.so）实现，该库会在安装设备驱动程序时复制到系统中。它的所有入口点都以 cu 为前缀。

这是一个基于句柄的命令式 API：大多数对象都通过不透明句柄引用，函数通过这些句柄来操作对应对象。

驱动程序 API 中可用的对象汇总见 表 6。

在调用驱动程序 API 中的任何函数之前，必须先使用 cuInit() 初始化驱动程序 API。随后必须创建一个 CUDA 上下文，并将该上下文附加到特定设备，同时设为调用方主机线程的当前上下文，详见 上下文。

在 CUDA 上下文中，主机代码会将内核显式加载为 PTX 或二进制对象，如 模块 中所述。因此，用 C++ 编写的内核必须单独编译为 PTX 或二进制对象。内核通过 API 入口点启动，如 内核执行 中所述。

任何希望在未来设备架构上运行的应用，都必须加载 PTX，而不是二进制代码。这是因为二进制代码是架构专用的，因此与未来架构不兼容；而 PTX 代码会在加载时由设备驱动程序编译成二进制代码。

下面是 内核 示例用驱动程序 API 编写后的主机代码：

int main()
{
    int N = ...;
    size_t size = N * sizeof(float);

    // 在主机内存中分配输入向量 h_A 和 h_B
    float* h_A = (float*)malloc(size);
    float* h_B = (float*)malloc(size);

    // 初始化输入向量
    ...

    // 初始化
    cuInit(0);

    // 获取支持CUDA的设备数量
    int deviceCount = 0;
    cuDeviceGetCount(&deviceCount);
    if (deviceCount == 0) {
        printf("There is no device supporting CUDA.\n");
        exit (0);
    }

    // 获取设备0的句柄
    CUdevice cuDevice;
    cuDeviceGet(&cuDevice, 0);

    // 创建上下文
    CUcontext cuContext;
    cuCtxCreate(&cuContext, 0, cuDevice);

    // 从二进制文件创建模块
    CUmodule cuModule;
    cuModuleLoad(&cuModule, "VecAdd.ptx");

    // 在设备内存中分配向量
    CUdeviceptr d_A;
    cuMemAlloc(&d_A, size);
    CUdeviceptr d_B;
    cuMemAlloc(&d_B, size);
    CUdeviceptr d_C;
    cuMemAlloc(&d_C, size);

    // 将向量从主机内存复制到设备内存
    cuMemcpyHtoD(d_A, h_A, size);
    cuMemcpyHtoD(d_B, h_B, size);

    // 从模块获取函数句柄
    CUfunction vecAdd;
    cuModuleGetFunction(&vecAdd, cuModule, "VecAdd");

    // 调用内核
    int threadsPerBlock = 256;
    int blocksPerGrid =
            (N + threadsPerBlock - 1) / threadsPerBlock;
    void* args[] = { &d_A, &d_B, &d_C, &N };
    cuLaunchKernel(vecAdd,
                   blocksPerGrid, 1, 1, threadsPerBlock, 1, 1,
                   0, 0, args, 0);

    ...
}

完整代码可在 CUDA 示例 vectorAddDrv 中找到。

3.3.1. 上下文#

CUDA 上下文类似于 CPU 进程。驱动程序 API 中使用的所有资源和执行的所有操作，都封装在 CUDA 上下文内；当上下文被销毁时，系统会自动清理这些资源。除了模块、纹理引用或表面引用等对象之外，每个上下文都有自己独立的地址空间。因此，来自不同上下文的 CUdeviceptr 值会引用不同的内存位置。

一个主机线程同一时间只能有一个当前设备上下文。使用 cuCtxCreate() 创建上下文时，该上下文会成为调用方主机线程的当前上下文。在上下文中运行的 CUDA 函数（大多数不涉及设备枚举或上下文管理的函数），如果发现线程没有当前有效上下文，就会返回 CUDA_ERROR_INVALID_CONTEXT。

每个主机线程都有一个当前上下文栈。cuCtxCreate() 会把新上下文压入栈顶。可以调用 cuCtxPopCurrent() 将上下文从主机线程分离。分离后，上下文处于“浮动”状态，可以被压入任何主机线程并成为其当前上下文。cuCtxPopCurrent() 还会恢复先前的当前上下文（如果存在）。

每个上下文还维护一个使用计数。cuCtxCreate() 会创建一个使用计数为 1 的上下文。cuCtxAttach() 会增加使用计数，cuCtxDetach() 会减少使用计数。当调用 cuCtxDetach() 或 cuCtxDestroy() 使使用计数降为 0 时，上下文会被销毁。

驱动程序 API 可与运行时互操作，并且可以通过 cuDevicePrimaryCtxRetain()，从驱动程序 API 访问由运行时管理的主上下文（参见 运行时初始化）。

使用计数有助于同一上下文中由第三方编写的代码相互协作。例如，如果加载三个库并让它们使用同一个上下文，每个库都会调用 cuCtxAttach() 增加使用计数，并在不再使用该上下文时调用 cuCtxDetach() 减少使用计数。对于大多数库，预期应用会在加载或初始化库之前创建上下文；这样应用可以根据自己的启发式策略创建上下文，而库只需要操作传入的上下文即可。某些库希望自行创建上下文（其 API 客户端可能不知道这一点，也可能已经创建或尚未创建自己的上下文），这类库会使用 cuCtxPushCurrent() 或 cuCtxPopCurrent()，如下图所示。

3.3.2. 模块#

模块是可动态加载的设备代码和数据包，类似于 Windows 中的 DLL，由 nvcc 输出（参见 使用 NVCC 编译）。所有符号名称（包括函数、全局变量、纹理引用或表面引用）都在模块作用域内维护，使独立第三方编写的模块可以在同一 CUDA 上下文中互操作。

此代码示例加载模块并检索某个内核的句柄：

CUmodule cuModule;
cuModuleLoad(&cuModule, "myModule.ptx");
CUfunction myKernel;
cuModuleGetFunction(&myKernel, cuModule, "MyKernel");

以下代码示例从 PTX 代码编译并加载新模块，同时解析编译错误：

#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[3];
void* values[3];
char* PTXCode = "some PTX code";
char error_log[BUFFER_SIZE];
int err;
options[0] = CU_JIT_ERROR_LOG_BUFFER;
values[0]  = (void*)error_log;
options[1] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[1]  = (void*)BUFFER_SIZE;
options[2] = CU_JIT_TARGET_FROM_CUCONTEXT;
values[2]  = 0;
err = cuModuleLoadDataEx(&cuModule, PTXCode, 3, options, values);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);

以下代码示例从多段 PTX 代码编译、链接并加载新模块，同时解析链接和编译错误：

#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[6];
void* values[6];
float walltime;
char error_log[BUFFER_SIZE], info_log[BUFFER_SIZE];
char* PTXCode0 = "some PTX code";
char* PTXCode1 = "some other PTX code";
CUlinkState linkState;
int err;
void* cubin;
size_t cubinSize;
options[0] = CU_JIT_WALL_TIME;
values[0] = (void*)&walltime;
options[1] = CU_JIT_INFO_LOG_BUFFER;
values[1] = (void*)info_log;
options[2] = CU_JIT_INFO_LOG_BUFFER_SIZE_BYTES;
values[2] = (void*)BUFFER_SIZE;
options[3] = CU_JIT_ERROR_LOG_BUFFER;
values[3] = (void*)error_log;
options[4] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[4] = (void*)BUFFER_SIZE;
options[5] = CU_JIT_LOG_VERBOSE;
values[5] = (void*)1;
cuLinkCreate(6, options, values, &linkState);
err = cuLinkAddData(linkState, CU_JIT_INPUT_PTX,
                    (void*)PTXCode0, strlen(PTXCode0) + 1, 0, 0, 0, 0);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);
err = cuLinkAddData(linkState, CU_JIT_INPUT_PTX,
                    (void*)PTXCode1, strlen(PTXCode1) + 1, 0, 0, 0, 0);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);
cuLinkComplete(linkState, &cubin, &cubinSize);
printf("Link completed in %fms. Linker Output:\n%s\n", walltime, info_log);
cuModuleLoadData(cuModule, cubin);
cuLinkDestroy(linkState);

使用多线程可以加速模块链接/加载过程中的某些部分，包括加载 cubin。下面的代码示例使用 CU_JIT_BINARY_LOADER_THREAD_COUNT 来加快模块加载速度。

#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[3];
void* values[3];
char* cubinCode = "some cubin code";
char error_log[BUFFER_SIZE];
int err;
options[0] = CU_JIT_ERROR_LOG_BUFFER;
values[0]  = (void*)error_log;
options[1] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[1]  = (void*)BUFFER_SIZE;
options[2] = CU_JIT_BINARY_LOADER_THREAD_COUNT;
values[2]  = 0; // 使用与机器上的 CPU 数量一样多的线程
err = cuModuleLoadDataEx(&cuModule, cubinCode, 3, options, values);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);

完整代码可在 CUDA 示例 ptxjit 中找到。

3.3.3. 内核执行#

cuLaunchKernel() 使用给定的执行配置启动内核。

参数可以用两种方式传递：一种是作为指针数组传入（即 cuLaunchKernel() 的倒数第二个参数），其中第 n 个指针对应第 n 个参数，并指向要从中复制该参数的内存区域；另一种是作为额外选项之一传入（即 cuLaunchKernel() 的最后一个参数）。

当参数作为额外选项传递时（使用 CU_LAUNCH_PARAM_BUFFER_POINTER 选项），它们会以指向单个缓冲区的指针形式传递。该缓冲区中的参数需要根据设备代码中各参数类型的对齐要求，彼此保持正确偏移。

内置向量类型在设备代码中的对齐要求列于 表 42。对于所有其他基本类型，设备代码中的对齐要求与主机代码中的对齐要求一致，因此可以使用 __alignof() 获得。唯一例外是主机编译器把 double 或 long long（以及 64 位系统上的 long）按单字边界而不是双字边界对齐时（例如使用 gcc 编译标志 -mno-align-double），因为这些类型在设备代码中总是按双字边界对齐。

CUdeviceptr 是一个整数，但表示指针，因此它的对齐要求是 __alignof(void*)。

下面的代码示例使用宏 ALIGN_UP() 调整每个参数的偏移量，以满足该参数的对齐要求；并使用另一个宏 ADD_TO_PARAM_BUFFER()，把每个参数添加到传给 CU_LAUNCH_PARAM_BUFFER_POINTER 选项的参数缓冲区中。

#define ALIGN_UP(offset, alignment) \
      (offset) = ((offset) + (alignment) - 1) & ~((alignment) - 1)

char paramBuffer[1024];
size_t paramBufferSize = 0;

#define ADD_TO_PARAM_BUFFER(value, alignment)                   \
    do {                                                        \
        paramBufferSize = ALIGN_UP(paramBufferSize, alignment); \
        memcpy(paramBuffer + paramBufferSize,                   \
               &(value), sizeof(value));                        \
        paramBufferSize += sizeof(value);                       \
    } while (0)

int i;
ADD_TO_PARAM_BUFFER(i, __alignof(i));
float4 f4;
ADD_TO_PARAM_BUFFER(f4, 16); // float4 的对齐方式是 16
char c;
ADD_TO_PARAM_BUFFER(c, __alignof(c));
float f;
ADD_TO_PARAM_BUFFER(f, __alignof(f));
CUdeviceptr devPtr;
ADD_TO_PARAM_BUFFER(devPtr, __alignof(devPtr));
float2 f2;
ADD_TO_PARAM_BUFFER(f2, 8); // float2 的对齐方式是 8

void* extra[] = {
    CU_LAUNCH_PARAM_BUFFER_POINTER, paramBuffer,
    CU_LAUNCH_PARAM_BUFFER_SIZE,    &paramBufferSize,
    CU_LAUNCH_PARAM_END
};
cuLaunchKernel(cuFunction,
               blockWidth, blockHeight, blockDepth,
               gridWidth, gridHeight, gridDepth,
               0, 0, 0, extra);

结构体的对齐要求等于其各字段对齐要求中的最大值。因此，包含内置向量类型、CUdeviceptr，或未按双字边界对齐的 double、long long 的结构体，其对齐要求在设备代码和主机代码之间可能不同。这类结构体的填充方式也可能不同。例如，以下结构体在主机代码中完全没有填充，但在设备代码中，由于字段 f4 的对齐要求为 16，会在字段 f 之后填充 12 个字节。

typedef struct {
    float  f;
    float4 f4;
} myStruct;

3.3.4. 运行时和驱动程序 API 之间的互操作性#

应用可以混合使用运行时 API 代码和驱动程序 API 代码。

如果通过驱动程序 API 创建上下文并将其设为当前上下文，后续运行时调用会使用这个上下文，而不是创建新上下文。

如果运行时已经初始化，可以使用 cuCtxGetCurrent() 取回初始化期间创建的上下文。这个上下文可供后续驱动程序 API 调用使用。

由运行时隐式创建的上下文称为主上下文（参见 运行时初始化）。可以通过驱动程序 API 的 主上下文管理 函数对其进行管理。

设备内存可以使用任一 API 分配和释放。CUdeviceptr 可以转换为普通指针，反之亦然：

CUdeviceptr devPtr;
float* d_data;

// 使用驱动程序 API 进行分配
cuMemAlloc(&devPtr, size);
d_data = (float*)devPtr;

// 使用运行时 API 进行分配
cudaMalloc(&d_data, size);
devPtr = (CUdeviceptr)d_data;

特别地，这意味着使用驱动程序 API 编写的应用，可以调用使用运行时 API 编写的库（例如 cuFFT、cuBLAS 等）。

参考手册中设备管理和版本管理部分的所有函数，都可以在两种 API 间互换使用。
