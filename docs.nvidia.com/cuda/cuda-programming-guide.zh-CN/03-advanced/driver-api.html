3.3. CUDA 驱动 API#

本指南前文已介绍 CUDA 运行时。正如CUDA Runtime API 与 CUDA Driver API所述，CUDA 运行时构建在更底层的 CUDA 驱动 API 之上。本节将说明运行时 API 与驱动 API 的一些差异，以及二者如何混合使用。大多数应用无需直接操作 CUDA 驱动 API 也能获得完整性能。但有时新接口会先在驱动 API 中提供，而某些高级接口（如虚拟内存管理）仅在驱动 API 中开放。

驱动 API 由 cuda 动态库（cuda.dll 或 cuda.so）实现，该库会在安装设备驱动时复制到系统中。其所有入口点均以 cu 为前缀。

它是一个基于句柄的命令式 API：大多数对象通过不透明句柄引用，并将该句柄传给函数以操作对象。

驱动 API 中可用对象汇总见表 6。

在调用任何驱动 API 函数前，必须先使用 cuInit() 初始化驱动 API。随后需要创建一个绑定到特定设备的 CUDA 上下文，并将其设为调用该函数的主机线程的当前上下文，详见上下文。

在 CUDA 上下文内，内核需由主机代码显式加载为 PTX 或二进制对象，见模块。因此，以 C++ 编写的内核需要单独编译为 PTX 或二进制对象。内核通过 API 入口点启动，见内核执行。

任何希望在未来设备架构上运行的应用都应加载 PTX，而非仅加载二进制代码。因为二进制代码与架构强相关，无法兼容未来架构；而 PTX 代码会在加载时由设备驱动编译为对应架构的二进制代码。

下面给出使用驱动 API 重写内核示例的主机端代码：

int main()
{
    int N = ...;
    size_t size = N * sizeof(float);

    // Allocate input vectors h_A and h_B in host memory
    float* h_A = (float*)malloc(size);
    float* h_B = (float*)malloc(size);

    // Initialize input vectors
    ...

    // Initialize
    cuInit(0);

    // Get number of devices supporting CUDA
    int deviceCount = 0;
    cuDeviceGetCount(&deviceCount);
    if (deviceCount == 0) {
        printf("There is no device supporting CUDA.\n");
        exit (0);
    }

    // Get handle for device 0
    CUdevice cuDevice;
    cuDeviceGet(&cuDevice, 0);

    // Create context
    CUcontext cuContext;
    cuCtxCreate(&cuContext, 0, cuDevice);

    // Create module from binary file
    CUmodule cuModule;
    cuModuleLoad(&cuModule, "VecAdd.ptx");

    // Allocate vectors in device memory
    CUdeviceptr d_A;
    cuMemAlloc(&d_A, size);
    CUdeviceptr d_B;
    cuMemAlloc(&d_B, size);
    CUdeviceptr d_C;
    cuMemAlloc(&d_C, size);

    // Copy vectors from host memory to device memory
    cuMemcpyHtoD(d_A, h_A, size);
    cuMemcpyHtoD(d_B, h_B, size);

    // Get function handle from module
    CUfunction vecAdd;
    cuModuleGetFunction(&vecAdd, cuModule, "VecAdd");

    // Invoke kernel
    int threadsPerBlock = 256;
    int blocksPerGrid =
            (N + threadsPerBlock - 1) / threadsPerBlock;
    void* args[] = { &d_A, &d_B, &d_C, &N };
    cuLaunchKernel(vecAdd,
                   blocksPerGrid, 1, 1, threadsPerBlock, 1, 1,
                   0, 0, args, 0);

    ...
}

完整代码可见 CUDA 示例 vectorAddDrv。

3.3.1. 上下文#

CUDA 上下文可类比为 CPU 进程。驱动 API 中执行的所有资源操作都封装在某个 CUDA 上下文内，并在上下文销毁时由系统自动清理。除模块、纹理/表面引用等对象外，每个上下文还拥有独立地址空间。因此，不同上下文中的 CUdeviceptr 值指向不同内存位置。

一个主机线程在同一时刻最多只有一个当前设备上下文。使用 cuCtxCreate() 创建上下文时，该上下文会成为调用线程的当前上下文。若线程当前没有有效上下文，则在上下文内运行的大多数 CUDA 函数（除设备枚举和上下文管理类函数外）会返回 CUDA_ERROR_INVALID_CONTEXT。

每个主机线程都维护一个“当前上下文”栈。cuCtxCreate() 会将新上下文压栈到栈顶。可调用 cuCtxPopCurrent() 将上下文从当前主机线程解绑；该上下文随后处于“浮动”状态，可被任意主机线程再次压栈为当前上下文。cuCtxPopCurrent() 还会恢复先前的当前上下文（若存在）。

每个上下文还维护一个使用计数。cuCtxCreate() 创建上下文时计数为 1；cuCtxAttach() 增加计数，cuCtxDetach() 减少计数。调用 cuCtxDetach() 或 cuCtxDestroy() 时，若计数降为 0，上下文将被销毁。

驱动 API 与运行时 API 可互操作。可通过 cuDevicePrimaryCtxRetain() 从驱动 API 访问由运行时管理的主上下文（见运行时初始化）。

使用计数有助于同一上下文中不同第三方代码的互操作。例如，若有三个库共享同一上下文，每个库在使用前都可调用 cuCtxAttach() 增加计数，并在使用结束时调用 cuCtxDetach() 减少计数。对大多数库而言，通常假定应用在加载或初始化库之前就已创建上下文；这样应用可按自身策略创建上下文，而库仅在该上下文中运行。对于希望自行创建上下文（且其 API 调用方未必知道或未必已创建上下文）的库，可使用 cuCtxPushCurrent() 与 cuCtxPopCurrent()，如下图所示。

3.3.2. 模块#

模块是可动态加载的设备代码与数据包，类似于 Windows 中的 DLL，由 nvcc 产出（见使用 NVCC 编译）。所有符号（包括函数、全局变量、纹理/表面引用）的命名都维护在模块作用域内，以便不同第三方编写的模块在同一 CUDA 上下文中互操作。

下面的代码示例加载一个模块并获取某个内核的句柄：

CUmodule cuModule;
cuModuleLoad(&cuModule, "myModule.ptx");
CUfunction myKernel;
cuModuleGetFunction(&myKernel, cuModule, "MyKernel");

下面的代码示例从 PTX 代码编译并加载新模块，同时解析编译错误：

#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[3];
void* values[3];
char* PTXCode = "some PTX code";
char error_log[BUFFER_SIZE];
int err;
options[0] = CU_JIT_ERROR_LOG_BUFFER;
values[0]  = (void*)error_log;
options[1] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[1]  = (void*)BUFFER_SIZE;
options[2] = CU_JIT_TARGET_FROM_CUCONTEXT;
values[2]  = 0;
err = cuModuleLoadDataEx(&cuModule, PTXCode, 3, options, values);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);

下面的代码示例从多个 PTX 代码编译、链接并加载新模块，同时解析链接与编译错误：

#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[6];
void* values[6];
float walltime;
char error_log[BUFFER_SIZE], info_log[BUFFER_SIZE];
char* PTXCode0 = "some PTX code";
char* PTXCode1 = "some other PTX code";
CUlinkState linkState;
int err;
void* cubin;
size_t cubinSize;
options[0] = CU_JIT_WALL_TIME;
values[0] = (void*)&walltime;
options[1] = CU_JIT_INFO_LOG_BUFFER;
values[1] = (void*)info_log;
options[2] = CU_JIT_INFO_LOG_BUFFER_SIZE_BYTES;
values[2] = (void*)BUFFER_SIZE;
options[3] = CU_JIT_ERROR_LOG_BUFFER;
values[3] = (void*)error_log;
options[4] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[4] = (void*)BUFFER_SIZE;
options[5] = CU_JIT_LOG_VERBOSE;
values[5] = (void*)1;
cuLinkCreate(6, options, values, &linkState);
err = cuLinkAddData(linkState, CU_JIT_INPUT_PTX,
                    (void*)PTXCode0, strlen(PTXCode0) + 1, 0, 0, 0, 0);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);
err = cuLinkAddData(linkState, CU_JIT_INPUT_PTX,
                    (void*)PTXCode1, strlen(PTXCode1) + 1, 0, 0, 0, 0);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);
cuLinkComplete(linkState, &cubin, &cubinSize);
printf("Link completed in %fms. Linker Output:\n%s\n", walltime, info_log);
cuModuleLoadData(cuModule, cubin);
cuLinkDestroy(linkState);

模块链接/加载流程中的某些阶段可通过多线程加速（包括加载 cubin 时）。下面代码示例使用 CU_JIT_BINARY_LOADER_THREAD_COUNT 提升模块加载速度。

#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[3];
void* values[3];
char* cubinCode = "some cubin code";
char error_log[BUFFER_SIZE];
int err;
options[0] = CU_JIT_ERROR_LOG_BUFFER;
values[0]  = (void*)error_log;
options[1] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[1]  = (void*)BUFFER_SIZE;
options[2] = CU_JIT_BINARY_LOADER_THREAD_COUNT;
values[2]  = 0; // Use as many threads as CPUs on the machine
err = cuModuleLoadDataEx(&cuModule, cubinCode, 3, options, values);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);

完整代码可见 CUDA 示例 ptxjit。

3.3.3. 内核执行#

cuLaunchKernel() 使用给定的执行配置启动一个内核。

参数可通过两种方式传递：其一是指针数组（cuLaunchKernel() 的倒数第二个参数），其中第 n 个指针对应第 n 个形参并指向用于拷贝该参数的内存区域；其二是通过额外选项（cuLaunchKernel() 的最后一个参数）传递。

当参数通过额外选项（CU_LAUNCH_PARAM_BUFFER_POINTER）传递时，它们会以“单一缓冲区指针”的形式传入。该缓冲区内各参数必须按设备代码中对应参数类型的对齐要求进行正确偏移。

设备代码中内建向量类型的对齐要求见 表 42。对于其他基础类型，设备代码中的对齐要求与主机代码一致，因此可通过 __alignof() 获取。唯一例外是主机编译器将 double 与 long long（以及 64 位系统上的 long）按单字边界而非双字边界对齐时（例如使用 gcc 编译参数 -mno-align-double）。而在设备代码中，这些类型始终按双字边界对齐。

CUdeviceptr 本质是整数类型，但语义上表示指针，因此其对齐要求为 __alignof(void*)。

下例使用宏 ALIGN_UP() 调整每个参数的偏移以满足对齐要求，并使用另一个宏 ADD_TO_PARAM_BUFFER() 将参数加入传给 CU_LAUNCH_PARAM_BUFFER_POINTER 选项的参数缓冲区。

#define ALIGN_UP(offset, alignment) \
      (offset) = ((offset) + (alignment) - 1) & ~((alignment) - 1)

char paramBuffer[1024];
size_t paramBufferSize = 0;

#define ADD_TO_PARAM_BUFFER(value, alignment)                   \
    do {                                                        \
        paramBufferSize = ALIGN_UP(paramBufferSize, alignment); \
        memcpy(paramBuffer + paramBufferSize,                   \
               &(value), sizeof(value));                        \
        paramBufferSize += sizeof(value);                       \
    } while (0)

int i;
ADD_TO_PARAM_BUFFER(i, __alignof(i));
float4 f4;
ADD_TO_PARAM_BUFFER(f4, 16); // float4's alignment is 16
char c;
ADD_TO_PARAM_BUFFER(c, __alignof(c));
float f;
ADD_TO_PARAM_BUFFER(f, __alignof(f));
CUdeviceptr devPtr;
ADD_TO_PARAM_BUFFER(devPtr, __alignof(devPtr));
float2 f2;
ADD_TO_PARAM_BUFFER(f2, 8); // float2's alignment is 8

void* extra[] = {
    CU_LAUNCH_PARAM_BUFFER_POINTER, paramBuffer,
    CU_LAUNCH_PARAM_BUFFER_SIZE,    &paramBufferSize,
    CU_LAUNCH_PARAM_END
};
cuLaunchKernel(cuFunction,
               blockWidth, blockHeight, blockDepth,
               gridWidth, gridHeight, gridDepth,
               0, 0, 0, extra);

结构体的对齐要求等于其所有字段对齐要求的最大值。因此，若结构体包含内建向量类型、CUdeviceptr，或未按标准对齐的 double/long long，其在设备代码与主机代码中的对齐与填充方式可能不同。例如，下面这个结构体在主机代码中完全不填充，但在设备代码中会在字段 f 之后填充 12 字节，因为字段 f4 的对齐要求为 16。

typedef struct {
    float  f;
    float4 f4;
} myStruct;

3.3.4. 运行时 API 与驱动 API 互操作#

应用程序可以混合使用运行时 API 与驱动 API 代码。

若上下文由驱动 API 创建并设为当前上下文，后续运行时调用会复用该上下文，而不会新建上下文。

如果运行时已初始化，可通过 cuCtxGetCurrent() 获取初始化时创建的上下文，该上下文可供后续驱动 API 调用使用。

运行时隐式创建的上下文称为主上下文（见运行时初始化）。可通过驱动 API 的 主上下文管理函数进行管理。

设备内存可通过任一 API 进行分配与释放。CUdeviceptr 可与普通指针互相转换：

CUdeviceptr devPtr;
float* d_data;

// Allocation using driver API
cuMemAlloc(&devPtr, size);
d_data = (float*)devPtr;

// Allocation using runtime API
cudaMalloc(&d_data, size);
devPtr = (CUdeviceptr)d_data;

这尤其意味着：使用驱动 API 编写的应用可以调用使用运行时 API 编写的库（如 cuFFT、cuBLAS 等）。

参考手册中设备管理与版本管理章节的所有函数都可以交替使用。
