3.4. 多 GPU 系统编程#

多 GPU 编程让应用程序能够处理更大规模的问题，并利用多 GPU 系统提供的更高聚合算术性能、更大内存容量和更高内存带宽，达到单个 GPU 难以实现的性能水平。

CUDA 通过主机 API、驱动程序基础设施以及配套的 GPU 硬件技术来支持多 GPU 编程：

  • 主机线程中的 CUDA 上下文管理

  • 面向系统中所有处理器的统一内存寻址

  • GPU 之间的点对点批量内存传输

  • 细粒度的点对点 GPU 加载/存储内存访问

  • 更高层抽象和配套系统软件，例如 CUDA 进程间通信、使用 NCCL 执行并行归约，以及借助 NVLink 和/或 GPU-Direct RDMA 通过 NVSHMEM、MPI 等 API 进行通信

从最基本的层面看，多 GPU 编程要求应用程序同时管理多个活动 CUDA 上下文，将数据分发到各个 GPU，在 GPU 上启动内核完成计算，并通信或收集结果，以便应用程序继续处理。具体如何组织这些工作，取决于怎样把应用程序算法、可用并行性以及现有代码结构最有效地映射到合适的多 GPU 编程方式。常见的多 GPU 编程方式包括：

  • 由单个主机线程驱动多个 GPU

  • 由多个主机线程分别驱动各自的 GPU

  • 由多个单线程主机进程分别驱动各自的 GPU

  • 由多个包含多线程的主机进程驱动 GPU，其中每个线程负责自己的 GPU

  • 多节点 NVLink 互连集群，其中 GPU 由分布在集群节点多个操作系统实例中的线程和进程驱动

GPU 可以通过设备内存之间的内存传输和对等访问相互通信，这适用于上面列出的各种多设备工作分配方式。通过查询并启用点对点 GPU 内存访问，并利用 NVLink 实现高带宽传输以及设备之间更细粒度的加载/存储操作，应用程序可以获得高性能、低延迟的 GPU 通信。

CUDA 统一虚拟寻址允许同一主机进程内的多个 GPU 进行通信；应用程序只需少量额外步骤，即可查询并启用高性能点对点内存访问和传输，例如通过 NVLink 进行通信。

如果多个 GPU 由不同的主机进程管理，则可以通过进程间通信 (IPC) 和虚拟内存管理 (VMM) API 支持它们之间的通信。高级 IPC 概念以及节点内 CUDA IPC API 的介绍见 进程间通信 一节。高级虚拟内存管理 (VMM) API 支持节点内和多节点 IPC，可在 Linux 和 Windows 操作系统上使用，并允许按分配粒度控制是否通过 IPC 共享内存缓冲区，详见 虚拟内存管理。

CUDA 本身提供了在一组 GPU（可能还包括主机）内部实现集合操作所需的 API，但并不直接提供高级多 GPU 集合通信 API。多 GPU 集合通信由更高层抽象的 CUDA 通信库提供，例如 NCCL 和 NVSHMEM。

3.4.1. 多设备上下文和执行管理#

应用程序使用多个 GPU 时，首先需要枚举可用的 GPU 设备，根据硬件属性、CPU 亲和性以及与对等设备的连接情况，从可用设备中作出合适选择，并为应用程序将使用的每个设备创建 CUDA 上下文。

3.4.1.1. 设备枚举#

以下代码示例展示了如何查询支持 CUDA 的设备数量、枚举每个设备，并查询这些设备的属性。

int deviceCount;
cudaGetDeviceCount(&deviceCount);
int device;
for (device = 0; device < deviceCount; ++device) {
    cudaDeviceProp deviceProp;
    cudaGetDeviceProperties(&deviceProp, device);
    printf("Device %d has compute capability %d.%d.\n",
           device, deviceProp.major, deviceProp.minor);
}

3.4.1.2. 设备选择#

主机线程可以随时调用 cudaSetDevice() 来设置当前操作的设备。 设备内存分配和内核启动是在当前设备上进行的；流和事件是与当前设置的设备关联创建的。 在主机线程调用 cudaSetDevice() 之前，当前设备默认是设备 0。

以下代码示例说明了设置当前设备会如何影响后续内存分配和内核执行操作。

size_t size = 1024 * sizeof(float);
cudaSetDevice(0);            // 将设备 0 设置为当前设备
float* p0;
cudaMalloc(&p0, size);       // 在设备 0 上分配内存
MyKernel<<<1000, 128>>>(p0); // 在设备 0 上启动内核

cudaSetDevice(1);            // 将设备 1 设置为当前设备
float* p1;
cudaMalloc(&p1, size);       // 在设备 1 上分配内存
MyKernel<<<1000, 128>>>(p1); // 在设备 1 上启动内核

3.4.1.3. 多设备流、事件和内存拷贝行为#

如果把内核启动提交到一个并非关联当前设备的流，启动将会失败，如以下代码示例所示。

cudaSetDevice(0);               // 将设备 0 设置为当前设备
cudaStream_t s0;
cudaStreamCreate(&s0);          // 在设备 0 上创建流 s0
MyKernel<<<100, 64, 0, s0>>>(); // 在 s0 中的设备 0 上启动内核

cudaSetDevice(1);               // 将设备 1 设置为当前设备
cudaStream_t s1;
cudaStreamCreate(&s1);          // 在设备 1 上创建流 s1
MyKernel<<<100, 64, 0, s1>>>(); // 在 s1 中的设备 1 上启动内核

// 此内核启动将失败，因为流 s0 未与设备 1 关联：
MyKernel<<<100, 64, 0, s0>>>(); // 在 s0 中的设备 1 上启动内核

即使内存拷贝被提交到一个并非关联当前设备的流，它也会成功。

如果输入事件和输入流关联到不同设备，cudaEventRecord() 会失败。

如果两个输入事件关联到不同设备，cudaEventElapsedTime() 会失败。

即使输入事件关联到的设备不同于当前设备，cudaEventSynchronize() 和 cudaEventQuery() 也会成功。

即使输入流和输入事件关联到不同设备，cudaStreamWaitEvent() 也会成功。因此，cudaStreamWaitEvent() 可用于在多个设备之间进行同步。

每个设备都有自己的 默认流，因此提交到某个设备默认流的命令，相对于提交到其他任意设备默认流的命令，可能乱序执行，也可能并发执行。

3.4.2. 多设备点对点传输和内存访问#

3.4.2.1. 点对点内存传输#

CUDA 可以在设备之间执行内存传输；当能够使用点对点内存访问时，它会利用专用拷贝引擎和 NVLink 硬件来最大化性能。

cudaMemcpy 可与 cudaMemcpyDeviceToDevice 或 cudaMemcpyDefault 拷贝类型配合使用。

否则，必须使用 cudaMemcpyPeer()、cudaMemcpyPeerAsync()、cudaMemcpy3DPeer() 或 cudaMemcpy3DPeerAsync() 执行拷贝，如以下代码示例所示。

cudaSetDevice(0);                   // 将设备 0 设置为当前设备
float* p0;
size_t size = 1024 * sizeof(float);
cudaMalloc(&p0, size);              // 在设备 0 上分配内存

cudaSetDevice(1);                   // 将设备 1 设置为当前设备
float* p1;
cudaMalloc(&p1, size);              // 在设备 1 上分配内存

cudaSetDevice(0);                   // 将设备 0 设置为当前设备
MyKernel<<<1000, 128>>>(p0);        // 在设备 0 上启动内核

cudaSetDevice(1);                   // 将设备 1 设置为当前设备
cudaMemcpyPeer(p1, 1, p0, 0, size); // 将 p0 复制到 p1
MyKernel<<<1000, 128>>>(p1);        // 在设备 1 上启动内核

两个不同设备内存之间的拷贝（在隐式 NULL 流中）：

  • 要等到此前提交到任一设备的所有命令都完成后才会开始；并且

  • 会在拷贝之后提交到任一设备的任何命令（见 异步执行）开始之前运行完成。

与流的正常行为一致，两个设备内存之间的异步拷贝可以与另一个流中的拷贝或内核重叠。

如果在两个设备之间启用了点对点访问，例如 点对点内存访问 中所述，那么这两个设备之间的点对点内存拷贝不再需要经由主机中转，因此速度更快。

3.4.2.2. 点对点内存访问#

取决于系统属性，尤其是 PCIe 和/或 NVLink 拓扑，设备可以寻址彼此的内存（也就是说，在一个设备上执行的内核可以解引用指向另一个设备内存的指针）。如果 cudaDeviceCanAccessPeer() 对指定设备返回 true，则这两个设备之间支持点对点内存访问。

必须调用 cudaDeviceEnablePeerAccess() 才能在两个设备之间启用点对点内存访问，如以下代码示例所示。在未启用 NVSwitch 的系统上，每个设备在系统范围内最多支持八个对等连接。

两个设备使用统一虚拟地址空间（见 统一虚拟地址空间），因此可用同一个指针寻址来自两个设备的内存，如下面的代码示例所示。

cudaSetDevice(0);                   // 将设备 0 设置为当前设备
float* p0;
size_t size = 1024 * sizeof(float);
cudaMalloc(&p0, size);              // 在设备 0 上分配内存
MyKernel<<<1000, 128>>>(p0);        // 在设备 0 上启动内核

cudaSetDevice(1);                   // 将设备 1 设置为当前设备
cudaDeviceEnablePeerAccess(0, 0);   // 启用点对点访问
                                    // 使用设备 0

// 在设备 1 上启动内核
// 此内核启动可以访问设备 0 上地址 p0 处的内存
MyKernel<<<1000, 128>>>(p0);

注

使用 cudaDeviceEnablePeerAccess() 启用对等内存访问，会全局作用于对等设备上此前以及此后所有 GPU 内存分配。 通过 cudaDeviceEnablePeerAccess() 为某个设备启用对等访问后，该对等设备上的设备内存分配操作会增加运行时成本，因为这些分配必须立即对当前设备以及其他同样拥有访问权限的对等设备可见。这会带来随对等设备数量扩展的乘法开销。

比为所有设备内存分配启用对等内存访问更具可扩展性的做法，是使用 CUDA 虚拟内存管理 API，在分配时只按需显式分配可由对等设备访问的内存区域。 通过在内存分配期间显式请求对等可访问性，不会让不可由对等设备访问的分配承担额外运行时成本，同时可正确限定对等可访问数据结构的作用范围，从而改进软件调试和可靠性（见 虚拟内存管理）。

3.4.2.3. 点对点内存一致性#

必须使用同步操作来强制规定内存访问的顺序，并保证分布在多个设备上的网格中并发执行线程的内存访问正确性。 跨设备同步的线程在 thread_scope_system 同步作用域 下运行。 类似地，内存操作也落在 thread_scope_system 内存同步域 内。

当只有单个 GPU 访问某个对象时，CUDA 原子函数 可以对位于对等设备内存中的该对象执行读取-修改-写入操作。 对等原子性的要求和限制在 CUDA 内存模型的 原子性要求 讨论中说明。

3.4.2.4. 多设备管理内存#

托管内存可用于支持点对点访问的多 GPU 系统。 并发多设备托管内存访问的详细要求，以及用于让 GPU 独占访问托管内存的 API，见 多 GPU。

3.4.2.5. 主机 IOMMU 硬件、PCI 访问控制服务和虚拟机#

特别是在 Linux 上，CUDA 和显示驱动程序不支持在启用 IOMMU 的裸机环境中执行 PCIe 点对点内存传输。 不过，CUDA 和显示驱动程序支持通过虚拟机直通使用 IOMMU。 在裸机系统上运行 Linux 时，必须禁用 IOMMU，以防静默设备内存损坏。 相反，对于虚拟机的 PCIe 直通，应启用 IOMMU 并使用 VFIO 驱动程序。

在 Windows 上不存在上述 IOMMU 限制。

另请参阅 在 64 位平台上分配 DMA 缓冲区。

此外，在支持 IOMMU 的系统上可以启用 PCI 访问控制服务 (ACS)。 PCI ACS 特性会通过 CPU 根复合体重定向所有 PCI 点对点流量；由于整体对分带宽降低，这可能造成显著的性能损失。
