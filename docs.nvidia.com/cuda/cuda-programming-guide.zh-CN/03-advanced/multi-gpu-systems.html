3.4. 多 GPU 系统编程#

多 GPU 编程可让应用通过利用多 GPU 系统提供的更高总体算力、更大内存容量和更高内存带宽，处理单 GPU 难以胜任的问题规模并达到更高性能水平。

CUDA 通过主机 API、驱动基础设施与配套 GPU 硬件技术支持多 GPU 编程：

  • 主机线程 CUDA 上下文管理

  • 系统内所有处理器的统一内存寻址

  • GPU 间点对点批量内存传输

  • 细粒度 GPU 点对点 load/store 内存访问

  • 更高层抽象与配套系统软件，例如 CUDA 进程间通信、使用 NCCL 进行并行归约，以及通过 NVSHMEM、MPI 等 API 利用 NVLink 和/或 GPU-Direct RDMA 进行通信

在最基本层面，多 GPU 编程要求应用能够并发管理多个活动 CUDA 上下文、将数据分发到各 GPU、在 GPU 上启动内核完成计算，并进行结果通信或汇聚，以便应用后续处理。 具体实现细节取决于如何将应用算法、可用并行性与现有代码结构高效映射到合适的多 GPU 编程方案。 常见多 GPU 编程方式包括：

  • 单个主机线程驱动多个 GPU

  • 多个主机线程分别驱动各自 GPU

  • 多个单线程主机进程分别驱动各自 GPU

  • 多个包含多线程的主机进程分别驱动各自 GPU

  • 多节点 NVLink 互连集群，GPU 由跨节点多个操作系统实例中的线程与进程共同驱动

GPU 之间可通过设备内存间的数据传输与点对点访问进行通信， 覆盖上文列出的各种多设备任务分配方式。 通过查询并启用 GPU 点对点内存访问，再结合 NVLink， 可以实现高带宽传输以及设备间更细粒度的 load/store 操作， 从而获得高性能、低时延的 GPU 通信能力。

CUDA 统一虚拟寻址允许同一主机进程内的多个 GPU 进行通信， 只需极少额外步骤即可查询并启用高性能点对点内存访问与传输（例如经由 NVLink）。

由不同主机进程管理的多个 GPU 之间通信，可通过进程间通信（IPC）与虚拟内存管理（VMM）API 实现。 高层 IPC 概念及节点内 CUDA IPC API 的介绍见进程间通信章节。 高级虚拟内存管理（VMM）API 同时支持节点内与多节点 IPC，可用于 Linux 与 Windows，并可按分配粒度控制内存缓冲区的 IPC 共享，详见虚拟内存管理。

CUDA 本身提供了在一组 GPU（以及可能包含主机）内实现集合通信所需的 API， 但并不直接提供高层多 GPU 集合通信 API。 多 GPU 集合通信通常由更高抽象层的 CUDA 通信库提供，例如 NCCL 和 NVSHMEM。

3.4.1. 多设备上下文与执行管理#

应用使用多 GPU 的第一步通常是：枚举可用 GPU 设备； 根据硬件属性、CPU 亲和性及与其他设备的互连关系选择合适设备； 并为应用将使用的每个设备创建 CUDA 上下文。

3.4.1.1. 设备枚举#

以下代码示例展示如何查询支持 CUDA 的设备数量、遍历各设备并读取其属性。

int deviceCount;
cudaGetDeviceCount(&deviceCount);
int device;
for (device = 0; device < deviceCount; ++device) {
    cudaDeviceProp deviceProp;
    cudaGetDeviceProperties(&deviceProp, device);
    printf("Device %d has compute capability %d.%d.\n",
           device, deviceProp.major, deviceProp.minor);
}

3.4.1.2. 设备选择#

主机线程可在任意时刻调用 cudaSetDevice() 设置当前操作设备。 设备内存分配与内核启动均发生在当前设备上；流和事件也与当前设置的设备关联。 在主机线程首次调用 cudaSetDevice() 之前，当前设备默认为设备 0。

以下代码示例说明设置当前设备后，后续内存分配与内核执行行为如何受到影响。

size_t size = 1024 * sizeof(float);
cudaSetDevice(0);            // Set device 0 as current
float* p0;
cudaMalloc(&p0, size);       // Allocate memory on device 0
MyKernel<<<1000, 128>>>(p0); // Launch kernel on device 0

cudaSetDevice(1);            // Set device 1 as current
float* p1;
cudaMalloc(&p1, size);       // Allocate memory on device 1
MyKernel<<<1000, 128>>>(p1); // Launch kernel on device 1

3.4.1.3. 多设备流、事件与内存拷贝行为#

如果将内核启动提交到与当前设备无关联的流中，启动会失败，如下代码示例所示。

cudaSetDevice(0);               // Set device 0 as current
cudaStream_t s0;
cudaStreamCreate(&s0);          // Create stream s0 on device 0
MyKernel<<<100, 64, 0, s0>>>(); // Launch kernel on device 0 in s0

cudaSetDevice(1);               // Set device 1 as current
cudaStream_t s1;
cudaStreamCreate(&s1);          // Create stream s1 on device 1
MyKernel<<<100, 64, 0, s1>>>(); // Launch kernel on device 1 in s1

// This kernel launch will fail, since stream s0 is not associated to device 1:
MyKernel<<<100, 64, 0, s0>>>(); // Launch kernel on device 1 in s0

即使内存拷贝提交到与当前设备无关联的流中，也会成功。

cudaEventRecord() will fail if the input event and input stream are associated to different devices.

cudaEventElapsedTime() will fail if the two input events are associated to different devices.

cudaEventSynchronize() and cudaEventQuery() will succeed even if the input event is associated to a device that is different from the current device.

cudaStreamWaitEvent() will succeed even if the input stream and input event are associated to different devices. cudaStreamWaitEvent() can therefore be used to synchronize multiple devices with each other.

每个设备都有自己的默认流，因此某设备默认流上的命令相对于其他设备默认流上的命令，可能乱序执行或并发执行。

3.4.2. 多设备点对点传输与内存访问#

3.4.2.1. 点对点内存传输#

CUDA 可以执行设备间内存传输；在可进行点对点内存访问时，会利用专用拷贝引擎与 NVLink 硬件以最大化性能。

cudaMemcpy can be used with the copy type cudaMemcpyDeviceToDevice or cudaMemcpyDefault.

否则，应使用 cudaMemcpyPeer()、cudaMemcpyPeerAsync()、cudaMemcpy3DPeer() 或 cudaMemcpy3DPeerAsync() 进行拷贝，如下代码示例所示。

cudaSetDevice(0);                   // Set device 0 as current
float* p0;
size_t size = 1024 * sizeof(float);
cudaMalloc(&p0, size);              // Allocate memory on device 0

cudaSetDevice(1);                   // Set device 1 as current
float* p1;
cudaMalloc(&p1, size);              // Allocate memory on device 1

cudaSetDevice(0);                   // Set device 0 as current
MyKernel<<<1000, 128>>>(p0);        // Launch kernel on device 0

cudaSetDevice(1);                   // Set device 1 as current
cudaMemcpyPeer(p1, 1, p0, 0, size); // Copy p0 to p1
MyKernel<<<1000, 128>>>(p1);        // Launch kernel on device 1

两个不同设备内存之间的拷贝（在隐式 NULL 流中）具有如下行为：

  • 在任一设备上此前提交的所有命令完成之前不会开始；并且

  • 会先于拷贝后提交到任一设备的任何命令（参见异步执行）执行完毕。

与流的常规行为一致，两个设备内存间的异步拷贝可以与其他流中的拷贝或内核重叠执行。

若两个设备间已启用点对点访问（例如按点对点内存访问所述），两者之间的点对点内存拷贝无需再经主机中转，因此速度更快。

3.4.2.2. 点对点内存访问#

根据系统属性，尤其是 PCIe 和/或 NVLink 拓扑，不同设备可能能够互相寻址对方内存（即在一个设备上执行的内核可解引用指向另一设备内存的指针）。 当 cudaDeviceCanAccessPeer() 对指定设备返回 true 时，这两个设备支持点对点内存访问。

两个设备间的点对点内存访问必须通过调用 cudaDeviceEnablePeerAccess() 启用，如下代码示例所示。在未启用 NVSwitch 的系统上，每个设备在全系统范围最多支持 8 个对等连接。

两个设备使用统一虚拟地址空间（见统一虚拟地址空间），因此如下面代码所示，可用同一指针访问两侧设备内存。

cudaSetDevice(0);                   // Set device 0 as current
float* p0;
size_t size = 1024 * sizeof(float);
cudaMalloc(&p0, size);              // Allocate memory on device 0
MyKernel<<<1000, 128>>>(p0);        // Launch kernel on device 0

cudaSetDevice(1);                   // Set device 1 as current
cudaDeviceEnablePeerAccess(0, 0);   // Enable peer-to-peer access
                                    // with device 0

// Launch kernel on device 1
// This kernel launch can access memory on device 0 at address p0
MyKernel<<<1000, 128>>>(p0);

注意

使用 cudaDeviceEnablePeerAccess() 启用点对点内存访问时，其作用范围覆盖该对等设备过去与未来的所有 GPU 内存分配。 通过 cudaDeviceEnablePeerAccess() 启用设备对等访问，会给该对等设备上的内存分配带来额外运行时开销，因为这些分配需要立即对当前设备及其他已获访问权限的设备可见，且该开销会随对等设备数量增加而放大。

相比对所有设备内存分配统一启用点对点访问，更可扩展的做法是使用 CUDA 虚拟内存管理 API，在分配时按需显式创建可对等访问的内存区域。 通过在分配阶段显式声明对等可访问性，不需要对等访问的分配不会承担额外运行时开销，同时可对对等可访问数据结构进行更准确作用域管理，从而提升软件调试性与可靠性（见 ref::virtual-memory-management）。

3.4.2.3. 点对点内存一致性#

必须使用同步操作来保证跨多个设备分布执行的网格中并发线程的内存访问顺序与正确性。 跨设备同步的线程在 thread_scope_system 同步作用域内工作。 同样，相关内存操作也属于 thread_scope_system 内存同步域。

CUDA ref::atomic-functions 可以在仅有单个 GPU 访问该对象时，对对等设备内存中的对象执行读-改-写操作。 关于对等原子性的要求与限制，请参见 CUDA 内存模型中关于原子性要求的讨论。

3.4.2.4. 多设备托管内存#

在支持点对点访问的多 GPU 系统上可使用托管内存。 关于并发多设备托管内存访问的详细要求，以及 GPU 独占访问托管内存的 API，请参见 多 GPU。

3.4.2.5. 主机 IOMMU 硬件、PCI ACS 与虚拟机#

在 Linux 上，CUDA 与显示驱动不支持启用 IOMMU 的裸机 PCIe 点对点内存传输。 但 CUDA 与显示驱动支持通过虚拟机直通方式使用 IOMMU。 在裸机 Linux 系统上必须禁用 IOMMU，以防止设备内存发生静默损坏。 相应地，在虚拟机 PCIe 直通场景中应启用 IOMMU 并使用 VFIO 驱动。

在 Windows 上，不存在上述 IOMMU 限制。

另见：64 位平台上的 DMA 缓冲区分配。

此外，在支持 IOMMU 的系统上还可能启用 PCI Access Control Services（ACS）。 PCI ACS 会将所有 PCI 点对点流量重定向到 CPU 根复合体，这会因整体双向带宽下降而导致显著性能损失。
