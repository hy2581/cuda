3.4. 多 GPU 系统编程#

多 GPU 编程允许应用程序解决问题规模 并实现超越单个 GPU 所能达到的性能水平 通过利用更大的聚合算术性能， 多 GPU 系统提供的内存容量和内存带宽。

CUDA 通过主机 API 实现多 GPU 编程， 驱动程序基础架构和支持 GPU 硬件技术：

  • 宿主线程 CUDA 上下文管理

  • 系统中所有处理器的统一内存寻址

  • GPU 之间的点对点批量内存传输

  • 细粒度的点对点 GPU 加载/存储内存访问

  • 更高级别的抽象和支持系统软件，例如 CUDA 进程间通信、使用并行缩减 NCCL，以及使用 NVLink 和/或 GPU-Direct RDMA 与 API 进行通信，例如 NVSHMEM 和MPI

在最基本的层面上，多 GPU 编程需要应用程序 同时管理多个活动的 CUDA 上下文， 将数据分配给 GPU， 在 GPU 上启动内核来完成其工作， 并传达或收集结果，以便采取行动 通过应用程序。 如何完成此操作的细节因最有效的方法而异 应用程序算法的映射、可用的并行性、 和现有的代码结构到合适的多 GPU 编程方法。 一些最常见的多 GPU 编程方法包括：

  • 单个主机线程驱动多个 GPU

  • 多个主机线程，每个线程驱动自己的 GPU

  • 多个单线程主机进程，每个进程驱动自己的 GPU

  • 包含多个线程的多个主机进程，每个线程驱动自己的 GPU

  • 多节点 NVLink 连接集群，GPU 由跨集群节点的多个操作系统实例中运行的线程和进程驱动

GPU之间可以相互通信 通过设备内存之间的内存传输和对等访问， 涵盖上面列出的每种多设备工作分配方法。 支持高性能、低延迟的GPU通信 通过查询并启用对等 GPU 内存访问， 并利用 NVLink 实现高带宽传输和 设备之间更细粒度的加载/存储操作。

CUDA统一虚拟寻址允许多个GPU之间的通信 在同一主机进程中，只需最少的额外步骤即可查询和启用 使用高性能点对点内存访问和传输， 例如，通过 NVLink。

由不同主机进程管理的多个 GPU 之间的通信 通过使用进程间通信 (IPC) 来支持，并且 虚拟内存管理 (VMM) API。 高级 IPC 概念和节点内 CUDA IPC API 简介 中讨论了 进程间通信 部分。 高级虚拟内存管理 (VMM) API 支持节点内和 多节点IPC，Linux和Windows均可使用 操作系统，并允许按分配粒度控制 通过 IPC 共享内存缓冲区，如中所述 虚拟内存管理.

CUDA本身提供了实现集体操作所需的API 在一组 GPU 内，可能包括主机，但它不 本身提供高级多 GPU 集体 API。 多 GPU 集合由更高抽象的 CUDA 通信提供 图书馆如 NCCL、NVSHMEM.

3.4.1. 多设备上下文和执行管理#

应用程序使用多个 GPU 所需的首要步骤 是枚举可用的 GPU 设备， 根据设备的实际情况，在可用设备中进行适当选择 硬件属性、CPU 关联性以及与对等点的连接性， 并为应用程序将使用的每个设备创建 CUDA 上下文。

3.4.1.1. 设备枚举#

以下代码示例展示了如何查询启用 CUDA 的设备的数量， 枚举每个设备并查询它们的属性。

int deviceCount;
cudaGetDeviceCount(&deviceCount);
int device;
for (device = 0; device < deviceCount; ++device) {
    cudaDeviceProp deviceProp;
    cudaGetDeviceProperties(&deviceProp, device);
    printf("Device %d has compute capability %d.%d.\n",
           device, deviceProp.major, deviceProp.minor);
}

3.4.1.2. 设备选择#

主机线程可以通过调用随时设置当前正在操作的设备 cudaSetDevice()。 设备内存分配和内核启动是在当前设备上进行的；流和事件是与当前设置的设备关联创建的。 直到接到电话 cudaSetDevice() 由主机线程创建，当前设备默认为设备0。

以下代码示例说明了设置当前设备如何影响后续内存分配和内核执行操作。

size_t size = 1024 * sizeof(float);
cudaSetDevice(0);            // 将设备 0 设置为当前设备
float* p0;
cudaMalloc(&p0, size);       // 在设备0上分配内存
MyKernel<<<1000, 128>>>(p0); // 在设备 0 上启动内核

cudaSetDevice(1);            // 将设备 1 设置为当前设备
float* p1;
cudaMalloc(&p1, size);       // 在设备1上分配内存
MyKernel<<<1000, 128>>>(p1); // 在设备 1 上启动内核

3.4.1.3. 多设备流、事件和内存复制行为#

如果将内核发布到与当前设备不关联的流，则内核启动将会失败，如以下代码示例所示。

cudaSetDevice(0);               // 将设备 0 设置为当前设备
cudaStream_t s0;
cudaStreamCreate(&s0);          // 在设备0上创建流s0
MyKernel<<<100, 64, 0, s0>>>(); // 在 s0 中的设备 0 上启动内核

cudaSetDevice(1);               // 将设备 1 设置为当前设备
cudaStream_t s1;
cudaStreamCreate(&s1);          // 在设备1上创建流s1
MyKernel<<<100, 64, 0, s1>>>(); // 在 s1 中的设备 1 上启动内核

// 此内核启动将失败，因为流 s0 未与设备 1 关联：
MyKernel<<<100, 64, 0, s0>>>(); // 在 s0 中的设备 1 上启动内核

即使内存复制被发送到与当前设备不关联的流，它也会成功。

cudaEventRecord() 如果输入事件和输入流关联到不同的设备，则会失败。

cudaEventElapsedTime() 如果两个输入事件关联到不同的设备，则会失败。

cudaEventSynchronize() 或 cudaEventQuery() 即使输入事件关联到与当前设备不同的设备，也会成功。

cudaStreamWaitEvent() 即使输入流和输入事件关联到不同的设备也会成功。 cudaStreamWaitEvent() 因此可用于使多个设备相互同步。

每个设备都有自己的 默认流，因此向设备的默认流发出的命令可能会乱序执行，或者相对于向任何其他设备的默认流发出的命令同时执行。

3.4.2. 多设备点对点传输和内存访问#

3.4.2.1. 点对点内存传输#

CUDA 可以在设备之间执行内存传输，并将利用 专用复制引擎和 NVLink 硬件以最大限度地提高性能 当可以进行点对点内存访问时。

cudaMemcpy 可与复制类型一起使用 cudaMemcpyDeviceToDevice 或 cudaMemcpyDefault.

否则，必须使用以下方式执行复制 cudaMemcpyPeer(), cudaMemcpyPeerAsync(), cudaMemcpy3DPeer(), or cudaMemcpy3DPeerAsync() 如以下代码示例所示。

cudaSetDevice(0);                   // 将设备 0 设置为当前设备
float* p0;
size_t size = 1024 * sizeof(float);
cudaMalloc(&p0, size);              // 在设备0上分配内存

cudaSetDevice(1);                   // 将设备 1 设置为当前设备
float* p1;
cudaMalloc(&p1, size);              // 在设备1上分配内存

cudaSetDevice(0);                   // 将设备 0 设置为当前设备
MyKernel<<<1000, 128>>>(p0);        // 在设备 0 上启动内核

cudaSetDevice(1);                   // 将设备 1 设置为当前设备
cudaMemcpyPeer(p1, 1, p0, 0, size); // 将 p0 复制到 p1
MyKernel<<<1000, 128>>>(p1);        // 在设备 1 上启动内核

副本（隐式 NULL 两个不同设备的内存之间的流）：

  • 直到之前向任一设备发出的所有命令都已完成并且

  • 在执行任何命令之前运行完成（请参阅 异步执行）发出后，可以开始复制到任一设备。

与流的正常行为一致，两个设备内存之间的异步副本可能与另一个流中的副本或内核重叠。

如果在两个设备之间启用了对等访问，例如，如中所述 点对点内存访问，这两个设备之间的点对点内存复制不再需要通过主机进行，因此速度更快。

3.4.2.2. 点对点内存访问#

根据系统属性，特别是 PCIe 和/或 NVLink 拓扑，设备能够寻址彼此的内存（即，在一个设备上执行的内核可以取消引用指向另一设备内存的指针）。 两个设备之间支持点对点内存访问，如果 cudaDeviceCanAccessPeer() 对于指定设备返回 true。

必须通过调用在两个设备之间启用对等内存访问 cudaDeviceEnablePeerAccess() 如以下代码示例所示。在未启用 NVSwitch 的系统上，每个设备最多可支持系统范围内的八个对等连接。

两个设备都使用统一的虚拟地址空间（请参阅 统一虚拟地址空间），因此可以使用相同的指针来寻址两个设备的内存，如下面的代码示例所示。

cudaSetDevice(0);                   // 将设备 0 设置为当前设备
float* p0;
size_t size = 1024 * sizeof(float);
cudaMalloc(&p0, size);              // 在设备0上分配内存
MyKernel<<<1000, 128>>>(p0);        // 在设备 0 上启动内核

cudaSetDevice(1);                   // 将设备 1 设置为当前设备
cudaDeviceEnablePeerAccess(0, 0);   // 启用点对点访问
                                    // 使用设备 0

// 在设备 1 上启动内核
// 此内核启动可以访问设备 0 上地址 p0 处的内存
MyKernel<<<1000, 128>>>(p0);

注

使用 cudaDeviceEnablePeerAccess() 启用对等内存访问可在对等设备上的所有先前和后续 GPU 内存分配上进行全局操作。 通过以下方式启用对设备的对等访问 cudaDeviceEnablePeerAccess() 由于需要使当前设备和也具有访问权限的任何其他对等方立即访问分配，因此会增加该对等方上的设备内存分配操作的运行时成本，从而增加随对等设备数量扩展的乘法开销。

为所有设备内存分配启用对等内存访问的更具可扩展性的替代方案是利用 CUDA 虚拟内存管理 API 在分配时仅根据需要显式分配对等可访问内存区域。 通过在内存分配期间显式请求对等可访问性，内存分配的运行时成本不会因对等无法访问的分配而受到损害，并且对等可访问数据结构的范围被正确确定，以改进软件调试和可靠性（请参阅参考文献：：virtual-memory-management).

3.4.2.3. 点对点内存一致性#

必须使用同步操作来强制排序和 通过网格中并发执行线程来保证内存访问的正确性 分布在多个设备上。 跨设备同步的线程在 thread_scope_system 同步范围。 同样，内存操作也属于 的 thread_scope_system 内存同步域.

CUDA 参考::atomic-functions 可以执行读-修改-写操作 当只有一个 GPU 时，在对等设备内存中的对象上 访问该对象。 CUDA 内存模型中描述了对等原子性的要求和限制 原子性要求 discussion.

3.4.2.4. 多设备管理内存#

托管内存可用于具有点对点支持的多 GPU 系统。 并发多设备托管内存访问的详细要求 用于 GPU 独占访问托管内存的 API 描述于 多 GPU.

3.4.2.5. 主机 IOMMU 硬件、PCI 访问控制服务和 VM#

特别是在 Linux 上，CUDA 和显示驱动程序不支持启用 IOMMU 的裸机 PCIe 对等内存传输。 但是，CUDA 和显示驱动程序确实通过虚拟机直通支持 IOMMU。 在裸机系统上运行 Linux 时，必须禁用 IOMMU，以防止静默设备内存损坏。 相反，应启用 IOMMU 并将 VFIO 驱动程序用于虚拟机的 PCIe 直通。

在 Windows 上，上述 IOMMU 限制不存在。

另请参阅 在 64 位平台上分配 DMA 缓冲区.

此外，还可以在支持 IOMMU 的系统上启用 PCI 访问控制服务 (ACS)。 PCI ACS 功能通过 CPU 根复合体重定向所有 PCI 点对点流量，这可能会由于总体平分带宽的减少而导致显着的性能损失。
