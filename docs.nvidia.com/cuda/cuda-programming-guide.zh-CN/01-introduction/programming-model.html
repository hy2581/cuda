1.2. 编程模型#

本章从语言无关的角度，对 CUDA 编程模型进行高层介绍。这里引入的术语与概念适用于 CUDA 支持的所有编程语言。后续章节会使用 C++ 对这些概念进行说明。

1.2.1. 异构系统#

CUDA 编程模型假定系统是异构计算系统，也就是同时包含 GPU 和 CPU。CPU 及其直连内存分别称为 主机（host） 和 主机内存（host memory）；GPU 及其直连内存分别称为 设备（device） 和 设备内存（device memory）。在某些片上系统（SoC）中，它们可能集成在同一封装内；在更大型的系统中，则可能包含多个 CPU 或多个 GPU。

CUDA 应用会将部分代码放在 GPU 上执行，但程序总是从 CPU 端开始运行。运行在 CPU 上的主机代码可通过 CUDA API 在主机内存与设备内存间复制数据、启动 GPU 代码执行，并等待数据传输或 GPU 代码完成。CPU 与 GPU 可以并行执行代码，通常通过同时提高两者利用率来获得最佳性能。

应用在 GPU 上执行的代码称为 设备代码（device code）；出于历史原因，被调用到 GPU 上执行的函数称为 内核（kernel）。启动一个内核运行的动作称为 启动（launch） 内核。可以把一次内核启动理解为：在 GPU 上启动大量线程，让这些线程并行执行同一段内核代码。GPU 线程与 CPU 线程在概念上相似，但在正确性和性能相关的行为上存在一些重要差异，后文会继续介绍（见 第 3.2.2.1.1 节）。

1.2.2. GPU 硬件模型#

与任何编程模型一样，CUDA 也依赖于一个对底层硬件的概念模型。对 CUDA 编程而言，可以把 GPU 看作由多个 流式多处理器（SM）组成；这些 SM 又被组织到称为 图形处理簇（GPC）的组中。每个 SM 都包含本地寄存器文件、统一数据缓存，以及若干执行计算的功能单元。统一数据缓存为 共享内存 和 L1 缓存提供物理资源，并且可以在运行时配置这部分资源在 L1 与共享内存之间的分配比例。不同 GPU 架构中，各类内存的大小以及每个 SM 内功能单元的数量都可能不同。

注意

GPU 的实际硬件布局以及底层执行编程模型的物理方式可能因架构而异。但这些差异不应影响按 CUDA 编程模型编写软件的正确性。

1.2.2.1. 线程块与网格#

应用启动内核时，通常会一次启动大量线程，很多情况下可达数百万个。这些线程会被组织成块；一个线程组成的块称为 线程块（thread block）。线程块再组织成 网格（grid）。同一网格中的所有线程块具有相同的大小和维度。图 3 展示了线程块网格的结构。

线程块和网格都可以是一维、二维或三维结构，这些维度有助于将单个线程映射到具体工作单元或数据元素。

内核会使用特定的 执行配置 启动；执行配置指定网格维度和线程块维度。执行配置还可以包含一些可选参数，例如簇大小、流以及 SM 配置设置，这些内容会在后续章节介绍。

每个正在执行内核的线程都可以通过内置变量确定自己在线程块内的位置，以及所属线程块在网格内的位置。线程也可以通过这些内置变量获取线程块和网格的维度。这使每个线程在执行该内核的全部线程中都有唯一身份，而这个身份通常用于决定该线程负责处理哪些数据或执行哪些操作。

同一线程块内的所有线程都在同一个 SM 上执行，因此块内线程可以高效通信与同步。线程块内的所有线程都可访问片上共享内存，该内存可用于线程间交换信息。

网格可能由数百万个线程块组成，而执行网格的 GPU 可能只有数十或数百个 SM。线程块的所有线程都由单个 SM 执行，并且在大多数情况下 [1]，会在该 SM 上运行到完成。线程块之间没有调度顺序保证，因此线程块不能依赖其他线程块的结果，因为其他线程块可能要等到当前线程块完成后才能被调度。图 4 展示了如何将网格中的线程块分配给 SM 的示例。

CUDA 编程模型允许任意大的网格运行在任意规模的 GPU 上，无论 GPU 只有一个 SM 还是有数千个 SM。为做到这一点，除少数例外情况外，CUDA 编程模型要求不同线程块中的线程之间不存在数据依赖。换言之，一个线程不应依赖同一网格中其他线程块内线程的结果，也不应与这些线程同步。线程块内的所有线程会同时运行在同一个 SM 上，而网格内的不同线程块会被调度到可用 SM 上，并且可能以任意顺序执行。简而言之，CUDA 编程模型要求线程块可以按任意顺序执行，可以并行执行，也可以串行执行。

1.2.2.1.1. 线程块簇#

除了线程块之外，计算能力 9.0 及更高版本的 GPU 还提供一个可选的分组层级，称为 簇（cluster）。簇由一组线程块组成，并且和线程块、网格一样，可以按一维、二维或三维布局。图 5 展示了一个同时按簇组织的线程块网格。指定簇并不会改变网格维度，也不会改变线程块在网格内的索引。

指定簇会把相邻线程块归为同一组，并在簇级别提供额外的同步和通信能力。具体来说，同一簇中的所有线程块都会在单个 GPC 中执行。图 6 展示了指定簇时，线程块如何被调度到 GPC 内的 SM 上。由于这些线程块会在同一个 GPC 内同时调度，因此同一簇中不同线程块内的线程可以借助 Cooperative Groups 提供的软件接口相互通信和同步。簇内线程还可以访问该簇所有线程块的共享内存，这称为 分布式共享内存。簇的最大大小取决于硬件，并因设备而异。

图 6 展示了簇内线程块如何在一个 GPC 内的 SM 上同时调度。簇内的线程块在网格中始终彼此相邻。

1.2.2.2. Warp 与 SIMT#

在线程块内部，线程按每 32 个一组组织，这样的一组称为 warp。warp 以 单指令多线程（SIMT）模式执行内核代码。在 SIMT 中，warp 内所有线程执行同一份内核代码，但每个线程可以在代码中走不同的分支。也就是说，程序中的所有线程虽然执行同一份代码，却不必遵循完全相同的执行路径。

线程由 warp 执行时，会被分配一个 warp lane。warp lane 的编号为 0 到 31；线程块中的线程会以可预测的方式分配到各个 warp 中，详情见 硬件多线程。

warp 中的所有线程会同时执行同一条指令。如果 warp 内的一部分线程在执行时进入某个控制流分支，而其他线程没有进入该分支，则在执行进入分支的线程时，未进入该分支的线程会被屏蔽。例如，如果某个条件只对 warp 中一半线程为真，那么活动线程执行这些指令时，warp 中另一半线程会被屏蔽。这种情况如 图 7 所示。当 warp 中不同线程走不同代码路径时，通常称为 warp 发散。因此，当 warp 内线程遵循相同控制流路径时，GPU 利用率通常最高。

在 SIMT 模型中，warp 内所有线程以锁步方式推进内核执行。实际硬件执行方式可能有所不同；关于这种区别在哪些地方重要，请参阅 独立线程执行。不建议程序依赖 warp 执行在真实硬件上的具体映射方式。CUDA 编程模型和 SIMT 模型表达的是：warp 中的所有线程共同推进代码执行。只要程序遵循编程模型，硬件就可以用对程序透明的方式优化被屏蔽的 lane。如果程序违反该模型，可能产生未定义行为，而且这种行为可能在不同 GPU 硬件上表现不同。

编写 CUDA 代码时并不总需要显式考虑 warp，但理解 warp 执行模型有助于理解 全局内存合并访问、共享内存 bank 访问模式 等概念。一些高级编程技术会在线程块内使用 warp 专门化，以限制线程发散并最大化利用率。这些优化依赖的正是“线程执行时会被分组为 warp”这一事实。

warp 执行模型带来的一个直接影响是：线程块的线程总数最好设置为 32 的倍数。CUDA 允许使用任意线程数，但当线程总数不是 32 的倍数时，线程块最后一个 warp 中会有一些 lane 在整个执行期间未被使用。这往往会降低该 warp 的功能单元利用率，并导致内存访问效率不理想。

SIMT 经常与单指令多数据（SIMD）并行模式相比较，但二者存在几个重要差异。在 SIMD 中，执行遵循单一控制流路径；而在 SIMT 中，每个线程都可以遵循自己的控制流路径。因此，SIMT 不像 SIMD 那样具有固定的数据宽度。关于 SIMT 的更详细讨论，请参阅 SIMT 执行模型。

1.2.3. GPU 内存#

在现代计算系统中，高效利用内存与充分利用计算功能单元同样重要。异构系统包含多个内存空间，GPU 除缓存外还包含多种可编程片上内存。下文将更详细介绍这些内存空间。

1.2.3.1. 异构系统中的 DRAM 内存#

GPU 和 CPU 都有与自身直接相连的 DRAM。在多 GPU 系统中，每个 GPU 都拥有自己的内存。从设备代码的角度看，连接到 GPU 的 DRAM 称为 全局内存，因为 GPU 中所有 SM 都可以访问它。但这个术语并不意味着它必然能被系统中的所有位置访问。连接到 CPU 的 DRAM 称为 系统内存 或 主机内存。

和 CPU 一样，GPU 使用虚拟内存寻址。在当前支持的所有系统上，CPU 和 GPU 使用统一的虚拟内存空间。这意味着系统中每个 GPU 的虚拟内存地址范围都是唯一的，并且不同于 CPU 以及系统中的其他 GPU。给定一个虚拟内存地址，系统可以判断该地址位于 GPU 内存还是系统内存；在多 GPU 系统中，也可以判断它位于哪一个 GPU 的内存中。

CUDA API 可用于分配 GPU 内存和 CPU 内存，也可用于在 CPU 与 GPU 的分配之间、同一 GPU 内部，或多 GPU 系统中的不同 GPU 之间复制数据。需要时，应用可以显式控制数据的局部性。下文讨论的 统一内存 则允许 CUDA 运行时或系统硬件自动处理内存放置。

1.2.3.2. GPU 片上内存#

除全局内存外，每个 GPU 还包含一些片上内存。每个 SM 都有自己的寄存器文件和共享内存。这些内存属于 SM 的一部分，SM 内正在执行的线程可以极快地访问它们，但运行在其他 SM 上的线程无法访问。

寄存器文件用于存放线程局部变量，这些变量通常由编译器分配。共享内存可由同一线程块或同一簇内的所有线程访问，可用于在线程块或簇内线程之间交换数据。

SM 中寄存器文件和统一数据缓存的大小都是有限的。SM 寄存器文件的大小、统一数据缓存大小，以及统一数据缓存如何在 L1 与共享内存之间配置平衡，可参见 每个计算能力的内存信息。寄存器文件、共享内存空间和 L1 缓存由线程块中的所有线程共享。

要把一个线程块调度到某个 SM 上，每个线程所需寄存器数乘以线程块中的线程数，必须小于或等于该 SM 可用寄存器数。如果线程块所需寄存器数量超过寄存器文件大小，该内核就无法启动；此时必须减少线程块中的线程数量，才能使线程块可启动。

共享内存按线程块级别分配。也就是说，与按线程分配的寄存器不同，共享内存分配对整个线程块是共同的。

1.2.3.2.1. 缓存#

除了可编程内存之外，GPU 还具有 L1 和 L2 缓存。每个 SM 都有一个 L1 缓存，它是统一数据缓存的一部分。更大的 L2 缓存由 GPU 内所有 SM 共享，这一点可在 图 2 的 GPU 框图中看到。每个 SM 还具有单独的 常量缓存，用于缓存全局内存中声明为在内核生命周期内保持不变的值。编译器也可以将内核参数放入常量内存。这样内核参数就可以在 SM 中独立于 L1 数据缓存进行缓存，从而提升内核性能。

1.2.3.3. 统一内存#

当应用在 GPU 或 CPU 上显式分配内存时，该内存只能由运行在对应设备上的代码访问。也就是说，CPU 内存只能由 CPU 代码访问，而 GPU 内存只能由运行在 GPU 上的内核访问[2]。用于在 CPU 与 GPU 之间复制内存的 CUDA API，需要在合适的时间把数据显式复制到正确的内存中。

CUDA 的 统一内存 功能允许应用分配 CPU 和 GPU 都可访问的内存。CUDA 运行时或底层硬件会在需要时启用访问，或把数据迁移到正确位置。即便使用统一内存，想获得最佳性能，也仍应尽量减少内存迁移，并尽可能让数据由与其所在内存直接相连的处理器访问。

系统的硬件特性决定了不同内存空间之间如何访问和交换数据。统一内存 一节介绍了统一内存系统的不同类别。统一内存 一章则提供了各种情况下统一内存用法与行为的更多细节。

[1]

在某些情况下，例如使用 CUDA 动态并行性 时，线程块可能会被挂起到内存中。这意味着 SM 的状态会保存到 GPU 内存中由系统管理的区域，随后该 SM 可被释放出来执行其他线程块。这类似于 CPU 上的上下文切换，但并不常见。

[2]

一个例外是 映射内存，它是带有可由 GPU 直接访问这一属性的 CPU 内存。不过，映射访问会通过 PCIe 或 NVLINK 连接进行。GPU 无法完全用并行性掩盖这种访问的较高延迟和较低带宽，因此映射内存不能作为统一内存或合理放置数据的高性能替代方案。
