1.2. 编程模型#

本章从语言无关的角度，对 CUDA 编程模型进行高层介绍。这里引入的术语与概念适用于 CUDA 支持的所有编程语言。后续章节会使用 C++ 对这些概念进行说明。

1.2.1. 异构系统#

CUDA 编程模型基于异构计算系统，即系统同时包含 GPU 与 CPU。CPU 及其直连内存分别称为 主机（主机） 与 主机内存（主机内存）。GPU 及其直连内存分别称为 设备（device） 与 设备内存（设备内存）。在某些 SoC 系统中，它们可能集成在同一封装内；在更大型系统中，则可能包含多个 CPU 或 GPU。

CUDA 应用会将部分代码放在 GPU 上执行，但程序总是从 CPU 端开始运行。运行在 CPU 上的主机代码可通过 CUDA API 在主机内存与设备内存间复制数据、启动 GPU 代码执行，并等待数据传输或 GPU 代码完成。CPU 与 GPU 可以并行执行代码，通常通过同时提高两者利用率来获得最佳性能。

应用在 GPU 上执行的代码称为 设备代码（设备代码）；出于历史原因，在 GPU 上执行的函数称为 内核（kernel）。启动内核执行这一动作称为内核 launch（启动）。可以把一次内核启动理解为：在 GPU 上并行启动大量线程来执行该内核代码。GPU 线程与 CPU 线程在形式上相似，但在正确性与性能相关行为上存在重要差异，后文会详细说明（见 第 3.2.2.1.1 节）。

1.2.2. GPU 硬件模型#

与任何编程模型一样，CUDA 依赖于底层硬件的概念模型。出于 CUDA 编程的目的，GPU 可以被认为是一个集合 流式多处理器 （SM）被组织成称为 图形处理集群 （GPC）。每个SM包含一个本地寄存器文件、一个统一的数据缓存和许多执行计算的功能单元。统一的数据缓存提供物理资源 共享内存 和L1缓存。统一数据缓存到 L1 和共享内存的分配可以在运行时配置。不同类型内存的大小以及 SM 内功能单元的数量可能因 GPU 架构而异。

注意

GPU 的实际硬件布局以及底层执行编程模型的物理方式可能因架构而异。但这些差异不应影响按 CUDA 编程模型编写软件的正确性。

1.2.2.1. 线程块与网格#

当应用启动内核时，通常会同时启动大量线程，很多情况下可达到数百万个。这些线程会被组织为多个块，一个线程块称为 线程块。线程块进一步组成 grid（网格）。同一网格中的所有线程块具有相同的大小与维度。 图3 显示了线程块网格的图示。

线程块和网格都可以是一维、二维或三维结构，这些维度有助于将单个线程映射到具体工作单元或数据元素。

当内核启动时，它是使用特定的 执行配置 它指定网格和线程块尺寸。执行配置还可能包括可选参数，例如集群大小、流和 SM 配置设置，这些将在后面的部分中介绍。

使用内置变量，执行内核的每个线程都可以确定其在其包含块内的位置以及其块在包含网格内的位置。线程还可以使用这些内置变量来确定线程块的尺寸以及启动内核的网格。这为每个线程在运行内核的所有线程中提供了唯一的标识。此标识经常用于确定线程负责哪些数据或操作。

同一线程块内的所有线程都在同一个 SM 上执行，因此块内线程可以高效通信与同步。线程块内的所有线程都可访问片上共享内存，该内存可用于线程间交换信息。

网格可能由数百万个线程块组成，而执行网格的 GPU 可能只有数十或数百个 SM。线程块的所有线程都由单个 SM 执行，并且在大多数情况下 [1]，在该 SM 上运行完成。无法保证线程块之间的调度，因此线程块不能依赖其他线程块的结果，因为在该线程块完成之前它们可能无法被调度。 图4 显示了如何将网格中的线程块分配给 SM 的示例。

CUDA 编程模型使任意大的网格能够在任何大小的 GPU 上运行，无论它只有一个 SM 还是数千个 SM。为了实现这一点，除了一些例外，CUDA 编程模型要求不同线程块中的线程之间不存在数据依赖关系。也就是说，线程不应依赖于同一网格的不同线程块中的线程的结果或与其同步。线程块内的所有线程同时在同一个 SM 上运行。网格内的不同线程块在可用的SM之间进行调度，并且可以以任何顺序执行。简而言之，CUDA 编程模型要求能够以任何顺序（并行或串行）执行线程块。

1.2.2.1.1. 线程块簇#

除了线程块之外，计算能力 9.0 及更高版本的 GPU 还具有一个可选的分组级别，称为 clusters。集群是一组线程块，与线程块和网格一样，可以按 1、2 或 3 维布局。 图5 说明了也组织成簇的线程块网格。指定簇不会更改网格尺寸或网格内线程块的索引。

指定集群将相邻的线程块分组为集群，并为集群级别的同步和通信提供一些额外的机会。具体来说，集群中的所有线程块都在单个 GPC 中执行。 图6 显示指定集群时如何将线程块调度到 GPC 中的 SM。由于线程块是在单个 GPC 内同时调度的，因此同一集群内不同块中的线程可以使用以下提供的软件接口相互通信和同步： 合作团体。集群中的线程可以访问集群中所有块的共享内存，称为 分布式共享内存集群的最大大小取决于硬件，并且因设备而异。

图6 说明了如何在 GPC 内的 SM 上同时调度集群内的线程块。集群内的线程块在网格内始终彼此相邻。

1.2.2.2. Warp 与 SIMT#

在线程块内部，线程按 32 个一组组织，称为 warp。它们按 单指令多线程（SIMT）方式执行内核代码。在SIMT中，warp 中的所有线程都执行相同的内核代码，但每个线程可能遵循不同的代码分支。也就是说，虽然程序的所有线程都执行相同的代码，但线程不需要遵循相同的执行路径。

当线程由 warp 执行时，它们会被分配一个 warp 通道。warp 通道编号为 0 到 31，线程块中的线程以可预测的方式分配给 warp，详细信息请参见 硬件多线程.

warp 中的所有线程同时执行相同的指令。如果 warp 中的某些线程在执行时遵循控制流分支，而其他线程则不遵循，则在执行遵循该分支的线程时，不遵循该分支的线程将被屏蔽。例如，如果条件仅对 warp 中的一半线程为真，则在活动线程执行这些指令时，warp 的另一半将被屏蔽。这种情况如图所示 图7。当 warp 中的不同线程遵循不同的代码路径时，有时称为warp 发散。由此可见，当 warp 内的线程遵循相同的控制流路径时，GPU 的利用率就会最大化。

在 SIMT 模型中，warp 中的所有线程都以锁步方式通过内核。 硬件执行可能有所不同。请参阅以下部分 独立线程执行 了解有关这种区别在哪些方面很重要的更多信息。不鼓励利用关于warp 执行如何实际映射到真实硬件的知识。 CUDA 编程模型和 SIMT 表示，warp 中的所有线程一起执行代码。只要遵循编程模型，硬件就可以以对程序透明的方式优化屏蔽通道。如果程序违反此模型，可能会导致未定义的行为，这些行为在不同的 GPU 硬件中可能会有所不同。

虽然在编写 CUDA 代码时不必考虑warp，但了解warp 执行模型有助于理解以下概念： 全局内存合并 和 共享存储体访问模式。一些高级编程技术使用线程块内的warp 专门化来限制线程发散并最大化利用率。此优化和其他优化利用了线程在执行时被分组为warp 的知识。

Warp 执行的一个含义是，线程块最好指定线程总数为 32 的倍数。使用任意数量的线程是合法的，但当总数不是 32 的倍数时，线程块的最后一个 Warp 将有一些在整个执行过程中未使用的通道。这可能会导致该 warp 的功能单元利用率和内存访问不理想。

SIMT 通常与单指令多数据 (SIMD) 并行性进行比较，但两者之间存在一些重要差异。在 SIMD 中，执行遵循单个控制流路径，而在 SIMT 中，允许每个线程遵循其自己的控制流路径。因此，SIMT 不像 SIMD 那样具有固定的数据宽度。 SIMT 的更详细讨论可以在 SIMT执行模型.

1.2.3. GPU内存#

在现代计算系统中，高效利用内存与充分利用计算功能单元同样重要。异构系统包含多个内存空间，GPU 除缓存外还包含多种可编程片上内存。下文将更详细介绍这些内存空间。

1.2.3.1. 异构系统中的 DRAM 内存#

每个 GPU 与 CPU 均连接有各自的 DRAM。在多 GPU 系统中，GPU 都拥有自身独立的内存。从设备代码的角度来看，GPU 所挂接的 DRAM 称为 全局内存，因为 GPU 中的所有 SM 都可以访问它。该术语并不意味着它必须在系统内的任何地方都可以访问。连接到 CPU 的 DRAM 称为 系统内存 或 主机内存.

与 CPU 一样，GPU 使用虚拟内存寻址。在当前支持的所有系统上，CPU 和 GPU 使用单个统一的虚拟内存空间。这意味着系统中每个 GPU 的虚拟内存地址范围都是唯一的，并且与系统中的 CPU 和每个其他 GPU 不同。对于给定的虚拟内存地址，可以确定该地址是在 GPU 内存还是系统内存中，并且在具有多个 GPU 的系统上，可以确定哪个 GPU 内存包含该地址。

CUDA API 可用于分配 GPU 内存、CPU 内存，以及在 CPU 和 GPU 上的分配之间、GPU 内或多 GPU 系统中的 GPU 之间进行复制。需要时可以显式控制数据的局部性。 统一内存如下所述，允许 CUDA 运行时或系统硬件自动处理内存的放置。

1.2.3.2. GPU 片上内存#

除全局内存外，每个GPU还包含片上内存。每个SM都有自己的寄存器文件和共享内存。这些内存是SM的一部分，可以从SM内执行的线程非常快速地访问，但其他SM中运行的线程无法访问它们。

寄存器文件存储通常由编译器分配的线程局部变量。共享内存可由线程块或集群中的所有线程访问。共享内存可用于在线程块或集群的线程之间交换数据。

SM 中的寄存器文件和统一数据缓存的大小是有限的。 SM寄存器文件的大小、统一数据缓存以及如何为L1和共享内存平衡配置统一数据缓存可以在 每个计算能力的内存信息。寄存器文件、共享内存空间和L1缓存在线程块中的所有线程之间共享。

要将线程块调度到 SM，每个线程所需的寄存器总数乘以线程块中的线程数必须小于或等于 SM 中的可用寄存器。如果线程块所需的寄存器数量超过寄存器文件的大小，则内核不可启动，并且必须减少线程块中的线程数量以使线程块可启动。

共享内存分配是在线程块级别完成的。也就是说，与每个线程的寄存器分配不同，共享内存的分配对于整个线程块是公共的。

1.2.3.2.1. 缓存#

除了可编程内存之外，GPU 还具有 L1 和 L2 缓存。每个 SM 都有一个 L1 缓存，它是统一数据缓存的一部分。更大的 L2 缓存由 GPU 内的所有 SM 共享。这可以在 GPU 框图中看到 图2。每个SM也有一个单独的 常量缓存，它用于缓存全局内存中已声明为在内核生命周期内恒定的值。编译器也可以将内核参数放入常量内存中。这可以通过允许内核参数与 L1 数据缓存分开缓存在 SM 中来提高内核性能。

1.2.3.3. 统一内存#

当应用程序在 GPU 或 CPU 上显式分配内存时，该内存只能由该设备上运行的代码访问。也就是说，CPU 内存只能从 CPU 代码访问，GPU 内存只能从 GPU 上运行的内核访问[2]。用于在 CPU 和 GPU 之间复制内存的 CUDA API 用于在正确的时间将数据显式复制到正确的内存。

CUDA的 统一内存 功能允许应用分配可同时被 CPU 和 GPU 访问的内存。 CUDA 运行时或底层硬件可以在需要时启用访问或将数据重新定位到正确的位置。即使使用统一内存，也可以通过将内存迁移保持在最低限度并尽可能从直接连接到数据所在内存的处理器访问数据来获得最佳性能。

系统的硬件特性决定了如何实现存储空间之间的数据访问和交换。部分 统一内存 介绍统一存储系统的不同类别。部分 统一内存 包含有关所有情况下统一内存的使用和行为的更多详细信息。

[1]

在某些情况下，当使用诸如 CUDA 动态并行性，线程块可能会被挂起到内存中。这意味着 SM 的状态存储到 GPU 内存的系统管理区域，并且 SM 被释放以执行其他线程块。这类似于 CPU 上的上下文交换。这并不常见。

[2]

一个例外是 映射内存，这是分配有使其可以从 GPU 直接访问的属性的 CPU 内存。但是，映射访问是通过 PCIe 或 NVLINK 连接进行的。 GPU 无法隐藏并行性背后的较高延迟和较低带宽，因此映射内存不能替代统一内存或将数据放置在适当的内存空间中。
