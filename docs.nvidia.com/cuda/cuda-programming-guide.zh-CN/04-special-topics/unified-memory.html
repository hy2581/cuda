4.1. 统一内存#

本节解释了可用的统一内存的每种不同范例的详细行为和使用。 前面关于统一内存的部分 展示了如何确定应用哪种统一内存范式并简要介绍了每种范式。

如前所述，统一内存编程有四种范例：

  • 完全支持显式托管内存分配

  • 完全支持所有具有软件一致性的分配

  • 完全支持所有具有硬件一致性的分配

  • 有限的统一内存支持

涉及完全统一内存支持的前三个范例具有非常相似的行为和编程模型，并在 具有完整 CUDA 统一内存支持的设备上的统一内存 并突出显示任何差异。

最后一个范例，其中统一内存支持是有限的，详细讨论在 Windows、WSL 和 Tegra 上的统一内存.

4.1.1. 具有完整 CUDA 统一内存支持的设备上的统一内存#

这些系统包括硬件一致性内存系统，例如 NVIDIA Grace Hopper 和启用了异构内存管理 (HMM) 的现代 Linux 系统。 HMM 是一种基于软件的内存管理系统，提供与硬件一致性内存系统相同的编程模型。

Linux HMM 需要 Linux 内核版本 6.1.24+、6.2.11+ 或 6.3+、计算能力为 7.5 或更高的设备以及安装的 CUDA 驱动程序版本 535+ 开放内核模块.

注

我们将具有 CPU 和 GPU 组合页表的系统称为 硬件 连贯的 系统。 CPU 和 GPU 具有单独页表的系统 称为 software-coherent.

硬件一致性系统（例如 NVIDIA Grace Hopper）为 CPU 和 GPU 提供逻辑组合的页表，请参阅 CPU 和 GPU 页表：硬件一致性与软件一致性。 以下部分仅适用于硬件一致性系统：

  • 访问计数器迁移

4.1.1.1. 统一内存：深入示例#

具有完整 CUDA 统一内存支持的系统，请参见表 统一内存范式概述, 允许设备访问与设备交互的主机进程拥有的任何内存。

本节展示了一些高级用例，使用简单打印的内核 输入字符数组的前 8 个字符发送到标准输出流：

__global__ void kernel(const char* type, const char* data) {
  static const int n_char = 8;
  printf("%s - first %d characters: '", type, n_char);
  for (int i = 0; i < n_char; ++i) printf("%c", data[i]);
  printf("'\n");
}

请注意，对于 extern 变量，它可以由第三方库声明及其内存拥有和管理，该第三方库根本不与 CUDA 交互。

另请注意，堆栈变量以及文件范围和全局范围变量只能由 GPU 通过指针访问。在这个特定的示例中，这很方便，因为字符数组已经声明为指针： const char*。但是，请考虑以下具有全局范围整数的示例：

// 该变量是在全局范围内声明的
int global_variable;

__global__ void kernel_uncompilable() {
  // 这会导致编译错误：全局（__host__）变量不能
  // 从 __device__ / __global__ 代码访问
  printf("%d\n", global_variable);
}

// 在 pageableMemoryAccess 设置为 1 的系统上，我们可以访问该地址
// 的全局变量。下面的内核将该地址作为参数
__global__ void kernel(int* global_variable_addr) {
  printf("%d\n", *global_variable_addr);
}
int main() {
  kernel<<<1, 1>>>(&global_variable);
  ...
  return 0;
}

在上面的例子中，我们需要确保传递一个 pointer 将全局变量传给内核，而不是直接访问内核中的全局变量。这是因为没有全局变量 __managed__ 说明符声明为 __host__-仅默认情况下，因此大多数编译器目前不允许在设备代码中直接使用这些变量。

4.1.1.1.1. 文件支持的统一内存#

由于具有完整 CUDA 统一内存支持的系统允许设备访问主机进程拥有的任何内存，因此它们可以直接访问文件支持的内存。

在这里，我们展示了上一节中所示初始示例的修改版本，以使用文件支持的内存来从 GPU 打印字符串，直接从输入文件读取。在以下示例中，内存由物理文件支持，但该示例也适用于内存支持的文件。

__global__ void kernel(const char* type, const char* data) {
  static const int n_char = 8;
  printf("%s - first %d characters: '", type, n_char);
  for (int i = 0; i < n_char; ++i) printf("%c", data[i]);
  printf("'\n");
}

void test_file_backed() {
  int fd = open(INPUT_FILE_NAME, O_RDONLY);
  ASSERT(fd >= 0, "Invalid file handle");
  struct stat file_stat;
  int status = fstat(fd, &file_stat);
  ASSERT(status >= 0, "Invalid file stats");
  char* mapped = (char*)mmap(0, file_stat.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
  ASSERT(mapped != MAP_FAILED, "Cannot map file into memory");
  kernel<<<1, 1>>>("file-backed", mapped);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
  ASSERT(munmap(mapped, file_stat.st_size) == 0, "Cannot unmap file");
  ASSERT(close(fd) == 0, "Cannot close file");
}

请注意，在没有 hostNativeAtomicSupported 财产（见 主机本机原子），包括启用了 Linux HMM 的系统，不支持对文件支持内存的原子访问。

4.1.1.1.2. 具有统一内存的进程间通信 (IPC)#

注

截至目前，使用具有统一内存的 IPC 可能会对性能产生重大影响。

许多应用程序更喜欢每个进程管理一个 GPU，但仍然需要使用统一内存， 例如超额订阅，并从多个 GPU 访问它。

CUDA IPC（参见 进程间通信）不支持托管内存：此类内存的句柄可能无法通过共享 本节讨论的任何机制。 在具有完整 CUDA 统一内存支持的系统上，系统分配的内存支持 IPC。 一旦与其他进程共享对系统分配内存的访问， 适用相同的编程模型，类似于 文件支持的统一内存.

有关各种创建方法的更多信息，请参阅以下参考资料 Linux下支持IPC的系统分配内存：

  • mmap 与 MAP_SHARED

  • POSIX IPC API

  • Linux memfd_create。

请注意，使用此技术不可能在不同主机及其设备之间共享内存。

4.1.1.2. 性能调优#

为了通过统一内存获得良好的性能，重要的是：

  • 了解分页在系统上的工作原理，以及如何避免不必要的页面错误

  • 了解允许您将数据保存在访问处理器本地的各种机制

  • 考虑调整您的应用程序以适应系统内存传输的粒度。

作为一般建议，性能提示（请参阅 性能提示） 可能会提高性能，但使用不当可能会降低性能 与默认行为相比。 另请注意，任何提示都会在主机上产生与其相关的性能成本， 因此，有用的提示至少必须提高性能足以克服这种成本。

4.1.1.2.1. 内存分页和页面大小#

为了更好地理解统一内存的性能影响，了解虚拟寻址非常重要， 内存页和页大小。 本小节尝试定义所有必要的术语并解释为什么分页对性能很重要。

目前所有支持统一内存的系统都使用虚拟地址空间： 这意味着应用程序使用的内存地址代表一个 virtual 位置 这可能是 mapped 到内存实际所在的物理位置。

所有当前支持的处理器（包括 CPU 和 GPU）另外使用 内存 paging。由于所有系统都使用虚拟地址空间，因此有两种类型 内存页数：

  • 虚拟页：这表示虚拟内存的固定大小的连续块 操作系统跟踪的每个进程，可以是 mapped 进入物理内存。 请注意，虚拟页面链接到 mapping: 例如，单个 虚拟地址可以使用不同的页面大小映射到物理内存。

  • 物理页：这代表固定大小的连续内存块 处理器的主内存管理单元（MMU）支持并进入其中 可以映射虚拟页。

目前，所有 x86_64 CPU 均使用 4KiB 的默认物理页大小。 Arm CPU 支持多种物理页面大小 - 4KiB、16KiB、32KiB 和 64KiB - 取决于具体的 CPU。 最后，NVIDIA GPU 支持多种物理页大小，但更喜欢 2MiB 或更大的物理页。 请注意，这些尺寸可能会在未来的硬件中发生变化。

虚拟页的默认页大小通常对应于物理页大小， 但应用程序可以使用不同的页面大小，只要它们受到支持 操作系统和硬件。通常，支持的虚拟页面大小必须是 2 的幂和物理页大小的倍数。

跟踪虚拟页到物理页的映射的逻辑实体将被称为 页表, 具有给定虚拟大小的给定虚拟页到物理页的每个映射称为 页表条目 (PTE)。 所有支持的处理器都为页表提供特定的缓存，以加速页表的转换 虚拟地址到物理地址。这些缓存被称为 转换后备缓冲区 (TLB).

应用程序的性能调优有两个重要方面：

  • 虚拟页面大小的选择，

  • 系统是否提供 CPU 和 GPU 使用的组合页表， 或分别为每个 CPU 和 GPU 提供单独的页表。

4.1.1.2.1.1. 选择正确的页面尺寸#

一般来说，较小的页面大小会导致较少的（虚拟）内存碎片，但会导致更多的 TLB 未命中， 而较大的页面大小会导致更多的内存碎片，但 TLB 未命中的情况会更少。 此外，与较大的页面大小相比，内存迁移通常更昂贵 较小的页面大小，因为我们通常迁移完整的内存页面。这可能会导致 使用大页面大小的应用程序中的延迟峰值更大。另请参阅下一节 有关页面错误的更多详细信息。

性能调优的一个重要方面是 TLB 未命中通常是 与 CPU 相比，GPU 上的成本要高得多。这意味着 如果 GPU 线程频繁访问统一内存映射的随机位置 使用足够小的页面大小，与 使用足够大的页面大小映射的统一内存的相同访问。 虽然 CPU 线程随机访问大数据可能会出现类似的效果 使用小页面大小映射的内存区域，速度减慢不太明显， 这意味着应用程序可能想要权衡这种减速 具有较少的内存碎片。

请注意，一般来说，应用程序不应将其性能调整为 给定处理器的物理页大小，因为物理页大小受限制 根据硬件而改变。上述建议仅适用于虚拟 页面大小。

4.1.1.2.1.2. CPU 和 GPU 页表：硬件一致性与软件一致性#

NVIDIA Grace Hopper 等硬件一致性系统提供了逻辑组合 CPU 和 GPU 的页表。 这很重要，因为为了从 GPU 访问系统分配的内存， GPU 使用 CPU 为请求的内存创建的页表条目。 如果该页表条目使用默认的 CPU 页大小 4KiB 或 64KiB， 对大虚拟内存区域的访问将导致严重的 TLB 未命中， 从而显着放缓。

另一方面，在软件一致性系统中，CPU 和 GPU 都有自己的逻辑 页表，应考虑不同的性能调优方面： 为了保证一致性，这些系统 通常使用 页面错误 如果处理器访问映射的内存地址 到不同处理器的物理内存中。这种页面错误意味着：

  • 需要确保当前拥有的处理器（物理页当前所在的位置） 无法再访问该页，无论是删除页表项还是更新它。

  • 需要保证请求访问的处理器可以访问该页面， 通过创建新的页表条目或更新现有条目，这样 它变得有效/活跃。

  • 支持该虚拟页面的物理页面必须移动/迁移到处理器 请求访问：这可能是一项昂贵的操作，并且工作量 与页面大小成正比。

总体而言，硬件一致性系统提供了显着的性能优势 与频繁并发访问的软件一致性系统相比 CPU 和 GPU 线程都创建到同一内存页面：

  • 更少的页面错误：这些系统不需要使用页面错误来模拟一致性或迁移内存，

  • 更少的争用：这些系统在缓存行粒度而不是页面大小粒度上是一致的，即 当缓存行中存在来自多个处理器的争用时，仅交换比最小页面大小小得多的缓存行， 当不同的处理器访问页面内的不同高速缓存行时，就不会发生争用。

这会影响以下场景的性能：

  • CPU 和 GPU 同时对同一地址进行原子更新

  • 从 CPU 线程向 GPU 线程发出信号，反之亦然。

4.1.1.2.2. 从主机直接统一内存访问#

某些设备具有对一致性读取、存储和原子访问的硬件支持 来自 GPU 驻留统一内存上的主机。 这些设备具有以下属性 cudaDevAttrDirectManagedMemAccessFromHost 设置为 1。 请注意，所有硬件一致性系统都为 NVLink 连接的设备设置了此属性。 在这些系统上，主机可以直接访问 GPU 驻留内存，而不会出现页面错误 数据迁移。请注意，对于 CUDA 托管内存， cudaMemAdviseSetAccessedBy 带有位置类型的提示 cudaMemLocationTypeHost 是必要的 要启用这种直接访问而不会出现页面错误，请参见下面的示例。

__global__ void write(int *ret, int a, int b) {
  ret[threadIdx.x] = a + b + threadIdx.x;
}

__global__ void append(int *ret, int a, int b) {
  ret[threadIdx.x] += a + b + threadIdx.x;
}

void test_malloc() {
  int *ret = (int*)malloc(1000 * sizeof(int));
  // 对于共享页表系统，以下提示不是必需的
  cudaMemLocation location = {.type = cudaMemLocationTypeHost};
  cudaMemAdvise(ret, 1000 * sizeof(int), cudaMemAdviseSetAccessedBy, location);

  write<<< 1, 1000 >>>(ret, 10, 100);            // GPU内存中填充的页面
  cudaDeviceSynchronize();
  for(int i = 0; i < 1000; i++)
      printf("%d: A+B = %d\n", i, ret[i]);        // directManagedMemAccessFromHost=1：CPU直接访问GPU内存，无需迁移
                                                  // directManagedMemAccessFromHost=0：CPU故障并触发设备到主机的迁移
  append<<< 1, 1000 >>>(ret, 10, 100);            // directManagedMemAccessFromHost=1：GPU 无需迁移即可访问 GPU 内存
  cudaDeviceSynchronize();                        // directManagedMemAccessFromHost=0：GPU 故障并触发主机到设备的迁移
  free(ret);
}

__global__ void write(int *ret, int a, int b) {
  ret[threadIdx.x] = a + b + threadIdx.x;
}

__global__ void append(int *ret, int a, int b) {
  ret[threadIdx.x] += a + b + threadIdx.x;
}

void test_managed() {
  int *ret;
  cudaMallocManaged(&ret, 1000 * sizeof(int));
  cudaMemLocation location = {.type = cudaMemLocationTypeHost};
  cudaMemAdvise(ret, 1000 * sizeof(int), cudaMemAdviseSetAccessedBy, location);  // 设置直接访问提示

  write<<< 1, 1000 >>>(ret, 10, 100);            // GPU内存中填充的页面
  cudaDeviceSynchronize();
  for(int i = 0; i < 1000; i++)
      printf("%d: A+B = %d\n", i, ret[i]);        // directManagedMemAccessFromHost=1：CPU直接访问GPU内存，无需迁移
                                                  // directManagedMemAccessFromHost=0：CPU故障并触发设备到主机的迁移
  append<<< 1, 1000 >>>(ret, 10, 100);            // directManagedMemAccessFromHost=1：GPU 无需迁移即可访问 GPU 内存
  cudaDeviceSynchronize();                        // directManagedMemAccessFromHost=0：GPU 故障并触发主机到设备的迁移
  cudaFree(ret);

After write 内核完成， ret 将在 GPU 内存中创建并初始化。 接下来，CPU将访问 ret 随后 append 内核使用相同的 ret 再次内存。 根据系统架构和硬件一致性的支持，此代码将显示不同的行为：

  • 在系统上 directManagedMemAccessFromHost=1: CPU对托管缓冲区的访问不会触发任何迁移； 数据将保留在 GPU 内存和任何后续 GPU 内核中 可以继续直接访问它而不会造成故障或迁移

  • 在系统上 directManagedMemAccessFromHost=0: CPU访问托管缓冲区会出现页错误并发起数据迁移； 任何第一次尝试访问相同数据的 GPU 内核都会出现页面错误，并且 将页面迁移回 GPU 内存。

4.1.1.2.3. 主机本机原子#

某些设备（包括硬件一致性系统的 NVLink 连接设备）支持对 CPU 驻留内存的硬件加速原子访问。这意味着对主机内存的原子访问不必通过页面错误来模拟。对于这些设备，属性 cudaDevAttrHostNativeAtomicSupported 设置为 1。

4.1.1.2.4. 原子访问和同步原语#

CUDA 统一内存支持主机和设备线程可用的所有原子操作，使所有线程能够通过并发访问同一共享内存位置来进行协作。的 libcu++ 库提供了许多针对主机和设备线程之间并发使用而调整的异构同步原语，包括 cuda::atomic, cuda::atomic_ref, cuda::barrier, cuda::semaphore等等。

在软件一致性系统上，不支持从设备到文件支持的主机内存的原子访问。以下示例代码在硬件一致性系统上有效，但在其他系统上表现出未定义的行为：

#include <cuda/atomic>

#include <cstdio>
#include <fcntl.h>
#include <sys/mman.h>

#define ERR(msg, ...) { fprintf(stderr, msg, ##__VA_ARGS__); return EXIT_FAILURE; }

__global__ void kernel(int* ptr) {
  cuda::atomic_ref{*ptr}.store(2);
}

int main() {
  // 退出时默认关闭/删除
  FILE* tmp_file = tmpfile64();
  // 需要在文件中分配空间，我们在这里使用 posix_fallocate 来完成此操作
  int status = posix_fallocate(fileno(tmp_file), 0, 4096);
  if (status != 0) ERR("Failed to allocate space in temp file\n");
  int* ptr = (int*)mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_PRIVATE, fileno(tmp_file), 0);
  if (ptr == MAP_FAILED) ERR("Failed to map temp file\n");

  // 初始化文件支持的内存中的值
  *ptr = 1;
  printf("Atom value: %d\n", *ptr);

  // 设备和主机线程使用 cuda::atomic_ref 同时访问 ptr
  kernel<<<1, 1>>>(ptr);
  while (cuda::atomic_ref{*ptr}.load() != 2);
  // 这将永远是 2
  printf("Atom value: %d\n", *ptr);

  return EXIT_SUCCESS;
}

在软件一致性系统上，对统一内存的原子访问可能会导致页面错误，从而导致显着的延迟。请注意，并非这些系统上的所有 GPU 原子到 CPU 内存的情况都是如此：列出的操作 nvidia-smi -q | grep "Atomic Caps Outbound" 可以避免页面错误。

在硬件一致性系统上，主机和设备之间的原子不需要页面错误，但仍可能因其他原因而导致任何内存访问错误。

4.1.1.2.5. 统一内存的 Memcpy()/Memset() 行为#

cudaMemcpy*() 或 cudaMemset*() 接受任何统一内存指针作为参数。

For cudaMemcpy*()，方向指定为 cudaMemcpyKind 是一个性能提示，如果任何参数是统一的内存指针，则可能会产生更高的性能影响。

因此，建议遵循以下性能建议：

  • 当统一内存的物理位置已知时，使用准确的 cudaMemcpyKind hint.

  • Prefer cudaMemcpyDefault 超过一个不准确的 cudaMemcpyKind hint.

  • 始终使用已填充（已初始化）的缓冲区：避免使用这些 API 来初始化内存。

  • 避免使用 cudaMemcpy*() 如果两个指针都指向系统分配的内存： 启动内核或使用 CPU 内存复制算法，例如 std::memcpy instead.

4.1.1.2.7. 访问计数器迁移#

在硬件一致性系统上，访问计数器功能会跟踪 GPU 对其他处理器上的内存进行访问的频率。这是为了确保内存页面被移动到最频繁访问页面的处理器的物理内存中所必需的。它可以指导 CPU 和 GPU 之间以及对等 GPU 之间的迁移，这个过程称为访问计数器迁移。

从 CUDA 12.4 开始，访问计数器受支持的系统分配内存。请注意，文件支持的内存不会根据访问进行迁移。对于系统分配的内存，可以使用以下命令打开访问计数器迁移 cudaMemAdviseSetAccessedBy 提示具有相应设备 ID 的设备。如果访问计数器打开，则可以使用 cudaMemAdviseSetPreferredLocation 设置为主机以防止迁移。 默认情况下 cudaMallocManaged 基于故障和迁移机制进行迁移。 [7]

驱动程序还可以使用访问计数器来更有效地缓解抖动或内存超额订阅场景。

[7]

当设置了访问设备提示时，当前系统允许使用托管内存的访问计数器迁移。这是一个实现细节，不应依赖于未来的兼容性。

4.1.1.2.8. 避免从 CPU 频繁写入 GPU 驻留内存#

如果主机访问统一内存，缓存未命中可能会在主机和设备之间引入比预期更多的流量。许多 CPU 架构要求所有内存操作都经过高速缓存层次结构，包括写入。如果系统内存驻留在 GPU 上，这意味着 CPU 频繁写入该内存可能会导致缓存未命中，因此首先将数据从 GPU 传输到 CPU，然后再将实际值写入请求的内存范围。在软件一致性系统上，这可能会引入额外的页面错误，而在硬件一致性系统上，可能会导致 CPU 操作之间的延迟更高。因此，为了与设备共享主机生成的数据，请考虑写入 CPU 驻留内存并直接从设备读取值。下面的代码展示了如何使用统一内存来实现这一点。

  size_t data_size = sizeof(int);
  int* data = (int*)malloc(data_size);
  // 确保数据保留在主机本地并避免故障
  cudaMemLocation location = {.type = cudaMemLocationTypeHost};
  cudaMemAdvise(data, data_size, cudaMemAdviseSetPreferredLocation, location);
  cudaMemAdvise(data, data_size, cudaMemAdviseSetAccessedBy, location);

  // 频繁交换小数据：如果CPU写入CPU常驻内存，
  // GPU直接访问该数据，我们可以避免CPU缓存重新加载
  // 数据（如果在写入之间被逐出）
  for (int i = 0; i < 10; ++i) {
    *data = 42 + i;
    kernel<<<1, 1>>>(data);
    cudaDeviceSynchronize();
    // CPU 缓存可能会逐出此处的数据
  }
  free(data);

  int* data;
  size_t data_size = sizeof(int);
  cudaMallocManaged(&data, data_size);
  // 确保数据保留在主机本地并避免故障
  cudaMemLocation location = {.type = cudaMemLocationTypeHost};
  cudaMemAdvise(data, data_size, cudaMemAdviseSetPreferredLocation, location);
  cudaMemAdvise(data, data_size, cudaMemAdviseSetAccessedBy, location);

  // 频繁交换小数据：如果CPU写入CPU常驻内存，
  // GPU直接访问该数据，我们可以避免CPU缓存重新加载
  // 数据（如果在写入之间被逐出）
  for (int i = 0; i < 10; ++i) {
    *data = 42 + i;
    kernel<<<1, 1>>>(data);
    cudaDeviceSynchronize();
    // CPU 缓存可能会逐出此处的数据
  }
  cudaFree(data);

4.1.1.2.9. 利用对系统内存的异步访问#

如果应用程序需要与主机共享设备上的工作结果，有几种可能的选择：

  1. 设备将其结果写入 GPU 驻留内存，结果使用 cudaMemcpy*，主机读取传输的数据。

  2. 设备直接将其结果写入CPU驻留内存，主机读取该数据。

  3. 设备写入 GPU 驻留内存，主机直接访问该数据。

如果可以在设备上安排独立工作，同时由主机传输/访问结果，则首选选项 1 或 3。如果设备在主机访问结果之前一直处于饥饿状态，则选项 2 可能是首选。这是因为设备写入的带宽通常高于主机读取的带宽，除非使用许多主机线程来读取数据。

void exchange_explicit_copy(cudaStream_t stream) {
  int* data, *host_data;
  size_t n_bytes = sizeof(int) * 16;
  // 分配接收缓冲区
  host_data = (int*)malloc(n_bytes);
  // 由于我们首先接触设备，分配将驻留在 GPU 上
  cudaMallocManaged(&data, n_bytes);
  kernel<<<1, 16, 0, stream>>>(data);
  // 在设备上启动独立工作
  // other_kernel<<<1024, 256, 0, 流>>>(other_data, ...);
  // 转移到主机
  cudaMemcpyAsync(host_data, data, n_bytes, cudaMemcpyDeviceToHost, stream);
  // 同步流以确保数据已传输
  cudaStreamSynchronize(stream);
  // 读取传输的数据
  printf("Got values %d - %d from GPU\n", host_data[0], host_data[15]);
  cudaFree(data);
  free(host_data);
}

void exchange_device_direct_write(cudaStream_t stream) {
  int* data;
  size_t n_bytes = sizeof(int) * 16;
  // 分配接收缓冲区
  cudaMallocManaged(&data, n_bytes);
  // 确保数据已映射并驻留在主机上
  cudaMemLocation location = {.type = cudaMemLocationTypeHost};
  cudaMemAdvise(data, n_bytes, cudaMemAdviseSetPreferredLocation, location);
  cudaMemAdvise(data, n_bytes, cudaMemAdviseSetAccessedBy, location);
  kernel<<<1, 16, 0, stream>>>(data);
  // 同步流以确保数据已传输
  cudaStreamSynchronize(stream);
  // 读取传输的数据
  printf("Got values %d - %d from GPU\n", data[0], data[15]);
  cudaFree(data);
}

void exchange_host_direct_read(cudaStream_t stream) {
  int* data;
  size_t n_bytes = sizeof(int) * 16;
  // 分配接收缓冲区
  cudaMallocManaged(&data, n_bytes);
  // 确保数据已映射并驻留在设备上
  cudaMemLocation device_loc = {};
  cudaGetDevice(&device_loc.id);
  device_loc.type = cudaMemLocationTypeDevice;
  cudaMemAdvise(data, n_bytes, cudaMemAdviseSetPreferredLocation, device_loc);
  cudaMemAdvise(data, n_bytes, cudaMemAdviseSetAccessedBy, device_loc);
  kernel<<<1, 16, 0, stream>>>(data);
  // 在GPU上启动独立工作
  // other_kernel<<<1024, 256, 0, 流>>>(other_data, ...);
  // 同步流以确保数据可以被访问（已由设备写入）
  cudaStreamSynchronize(stream);
  // 直接从主机读取数据
  printf("Got values %d - %d from GPU\n", data[0], data[15]);
  cudaFree(data);

最后，在上面的显式复制示例中，而不是使用 cudaMemcpy* 为了传输数据，可以使用主机或设备内核来显式执行此传输。对于连续数据，首选使用 CUDA 复制引擎，因为复制引擎执行的操作可能与主机和设备上的工作重叠。复制引擎可能用于 cudaMemcpy* 或 cudaMemPrefetchAsync API，但没有保证。复制引擎与 cudaMemcpy* API 调用。出于同样的原因，对于足够大的数据，显式复制优于直接主机读取：如果主机和设备执行的工作没有使各自的内存系统饱和，则复制引擎可以与主机和设备执行的工作同时执行传输。

复制引擎通常用于主机和设备之间以及 NVLink 连接系统内对等设备之间的传输。 由于复制引擎总数有限，某些系统的带宽可能较低 cudaMemcpy* 与使用设备显式执行传输相比。 在这种情况下，如果传输位于应用程序的关键路径中，则可能优选使用显式的基于设备的传输。

4.1.3. Windows、WSL 和 Tegra 上的统一内存#

注

本节仅关注计算能力低于 6.0 或 Windows 平台的设备、 concurrentManagedAccess 属性设置为 0。

计算能力低于6.0或Windows平台的设备、 concurrentManagedAccess 属性设置为 0，请参阅 统一内存范式概述，支持 CUDA 托管内存，但有以下限制：

  • 数据迁移和一致性：不支持将托管数据按需细粒度移动到 GPU。每当 GPU 内核启动时，所有托管内存通常都必须转移到 GPU 内存，以避免内存访问出错。仅 CPU 端支持页面错误。

  • GPU 内存超额认购：它们无法分配比 GPU 内存物理大小更多的托管内存。

  • 一致性和并发性：无法同时访问托管内存，因为如果 CPU 在 GPU 内核处于活动状态时访问统一的内存分配，则由于缺少 GPU 页面错误机制，无法保证一致性。

4.1.3.1. 多 GPU#

在计算能力低于 6.0 的设备的系统或 Windows 平台上，托管分配通过 GPU 的对等功能自动对系统中的所有 GPU 可见。托管内存分配的行为与使用分配的非托管内存类似 cudaMalloc()：当前活动设备是物理分配的所在地，但系统中的其他 GPU 将通过 PCIe 总线以减少的带宽访问内存。

在 Linux 上，只要程序正在使用的所有 GPU 都具有对等支持，托管内存就会在 GPU 内存中分配。如果应用程序在任何时候开始使用的 GPU 与任何其他具有托管分配的 GPU 不具有对等支持，则驱动程序会将所有托管分配迁移到系统内存。在这种情况下，所有 GPU 都会受到 PCIe 带宽限制。

在 Windows 上，如果对等映射不可用（例如，不同架构的 GPU 之间），则系统将自动回退到使用映射内存，无论两个 GPU 是否实际被程序使用。如果实际只使用一个GPU，则需要设置 CUDA_VISIBLE_DEVICES 启动程序之前的环境变量。这限制了哪些 GPU 是可见的，并允许在 GPU 内存中分配托管内存。

或者，在 Windows 上用户也可以设置 CUDA_MANAGED_FORCE_DEVICE_ALLOC 为非零值以强制驱动程序始终使用设备内存进行物理存储。当此环境变量设置为非零值时，该进程中使用的支持托管内存的所有设备都必须彼此点对点兼容。 错误 ::cudaErrorInvalidDevice 如果使用支持托管内存的设备，并且该设备与之前在该进程中使用的任何其他托管内存支持设备不点对点兼容，则将返回，即使 ::cudaDeviceReset 已在这些设备上被调用。这些环境变量的描述见 CUDA 环境变量.

4.1.3.2. 一致性和并发性#

为了确保一致性，统一内存编程模型在 CPU 和 GPU 并发执行时对数据访问施加限制。实际上，GPU 对所有托管数据具有独占访问权，并且不允许 CPU 访问它， 当任何内核操作正在执行时，无论特定内核是否正在主动使用数据。 并发 CPU/GPU 访问，即使是不同的托管内存分配，也会导致分段错误，因为 CPU 认为该页面无法访问。

例如，由于 GPU 页面错误功能解除了对同时访问的所有限制，以下代码在计算能力 6.x 的设备上成功运行 但在 6.x 之前的架构和 Windows 平台上失败，因为当 CPU 接触时 GPU 程序内核仍然处于活动状态 y:

__device__ __managed__ int x, y=2;
__global__  void  kernel() {
    x = 10;
}
int main() {
    kernel<<< 1, 1 >>>();
    y = 20;            // GPU 不支持并发访问时出现错误

    cudaDeviceSynchronize();
    return  0;
}

程序在访问之前必须显式地与GPU同步 y （无论GPU内核是否实际触及 y （或任何托管数据）：

__device__ __managed__ int x, y=2;
__global__  void  kernel() {
    x = 10;
}
int main() {
    kernel<<< 1, 1 >>>();
    cudaDeviceSynchronize();
    y = 20;            // 在不支持并发访问的 GPU 上取得成功
    return  0;
}

请注意，任何逻辑上保证 GPU 完成其工作的函数调用都是有效的，以确保逻辑上 GPU 工作完成，请参阅 显式同步.

请注意，如果内存是动态分配的 cudaMallocManaged() 或 cuMemAllocManaged() 当 GPU 处于活动状态时，内存的行为是不确定的，直到启动其他工作或同步 GPU。 在此期间尝试访问 CPU 上的内存可能会也可能不会导致分段错误。这不适用于使用标志分配的内存 cudaMemAttachHost 或 CU_MEM_ATTACH_HOST.

4.1.3.3. 流关联统一内存#

CUDA 编程模型提供流作为程序的机制来指示内核启动之间的依赖性和独立性。启动到同一流中的内核保证连续执行， 而启动到不同流中的内核允许同时执行。 参见部分 CUDA 流.

4.1.3.3.1. 流回调#

如果 GPU 上没有其他可能访问托管数据的流处于活动状态，那么 CPU 从流回调中访问托管数据是合法的。此外，后面没有任何设备工作的回调可用于同步：例如，通过从回调内部发出条件变量信号；否则，CPU 访问仅在回调期间有效。 有几个重要的注意点：

  1. 当 GPU 处于活动状态时，始终允许 CPU 访问非托管映射内存数据。

  2. 当 GPU 运行任何内核时，它被认为是活动的，即使该内核不使用托管数据。如果内核可能使用数据，则禁止访问

  3. 除了适用于非托管内存的多 GPU 访问的限制之外，托管内存的并发 GPU 间访问没有任何限制。

  4. 并发 GPU 内核访问托管数据没有任何限制。

请注意最后一点如何允许 GPU 内核之间的竞争，就像当前非托管 GPU 内存的情况一样。从GPU的角度来看，托管内存功能与非托管内存相同。 以下代码示例说明了这些要点：

int main() {
    cudaStream_t stream1, stream2;
    cudaStreamCreate(&stream1);
    cudaStreamCreate(&stream2);
    int *non_managed, *managed, *also_managed;
    cudaMallocHost(&non_managed, 4);    // 非托管、CPU 可访问的内存
    cudaMallocManaged(&managed, 4);
    cudaMallocManaged(&also_managed, 4);
    // 第1点：CPU可以访问非托管数据。
    kernel<<< 1, 1, 0, stream1 >>>(managed);
    *non_managed = 1;
    // 第 2 点：当 GPU 繁忙时，CPU 无法访问任何托管数据，
    // 除非并发管理访问 = 1
    // 请注意，我们尚未同步，因此“内核”仍然处于活动状态。
    *also_managed = 2;      // 会出现分段错误
    // 第3点：并发GPU内核可以访问相同的数据。
    kernel<<< 1, 1, 0, stream2 >>>(managed);
    // 第4点：也允许多GPU并发访问。
    cudaSetDevice(1);
    kernel<<< 1, 1 >>>(managed);
    return  0;
}

4.1.3.3.2. 与流关联的托管内存允许更细粒度的控制#

统一内存建立在流独立模型的基础上，允许 CUDA 程序将托管分配与 CUDA 流显式关联。 通过这种方式，程序员可以根据内核是否启动到指定的流来指示内核对数据的使用。这使得基于特定于程序的数据访问模式的并发机会成为可能。 控制这种行为的函数是：

cudaError_t cudaStreamAttachMemAsync(cudaStream_t stream,
                                     void *ptr,
                                     size_t length=0,
                                     unsigned int flags=0);

cudaStreamAttachMemAsync() 函数将从 ptr 开始的内存长度字节与指定的流相关联。只要流中的所有操作都已完成，CPU 就可以访问该内存区域，无论其他流是否处于活动状态。 实际上，这将活动 GPU 对托管内存区域的独占所有权限制为每个流活动，而不是整个 GPU 活动。 最重要的是，如果分配不与特定流关联，则它对于所有正在运行的内核都是可见的，无论其流如何。 这是默认可见性 cudaMallocManaged() 分配或 __managed__ 变量；因此，简单情况规则是，当任何内核运行时，CPU 都不得接触数据。

注

通过将分配与特定流相关联，程序可以保证只有启动到该流中的内核才会接触该数据。统一存储系统不执行错误检查。

注

除了允许更大的并发性之外，还可以使用 cudaStreamAttachMemAsync() 可以在统一内存系统内实现数据传输优化，这可能会影响延迟和其他开销。

以下示例展示了如何显式关联 y 具有主机可访问性，从而可以随时从 CPU 进行访问。 （注意没有 cudaDeviceSynchronize() 在内核调用之后。）访问 y GPU 运行内核现在将产生未定义的结果。

__device__ __managed__ int x, y=2;
__global__  void  kernel() {
    x = 10;
}
int main() {
    cudaStream_t stream1;
    cudaStreamCreate(&stream1);
    cudaStreamAttachMemAsync(stream1, &y, 0, cudaMemAttachHost);
    cudaDeviceSynchronize();          // 等待主机连接发生。
    kernel<<< 1, 1, 0, stream1 >>>(); // 注意：启动到stream1。
    y = 20;                           // 成功 – 内核正在运行，但“y”
                                      // 已与任何流关联。
    return  0;
}

4.1.3.3.3. 关于多线程主机程序的更详细的示例#

主要用途为 cudaStreamAttachMemAsync() 是使用CPU线程启用独立任务并行性。通常在这样的程序中，CPU 线程为其生成的所有工作创建自己的流，因为使用 CUDA 的 NULL 流会导致线程之间的依赖关系。 托管数据对任何 GPU 流的默认全局可见性可能会导致难以避免多线程程序中 CPU 线程之间的交互。功能 cudaStreamAttachMemAsync() 因此，用于将线程的托管分配与该线程自己的流关联起来，并且该关联通常在线程的生命周期内不会更改。 这样的程序只需添加一个调用 cudaStreamAttachMemAsync() 使用统一内存进行数据访问：

// 该函数在其自己的私有流中执行一些任务，并且可以并行运行
void run_task(int *in, int *out, int length) {
    // 创建一个流供我们使用。
    cudaStream_t stream;
    cudaStreamCreate(&stream);
    // 分配一些托管数据并与我们的流关联。
    // 请注意 cudaMallocManaged() 中主机附加标志的使用；
    // 然后我们将分配与我们的流相关联，以便
    // 我们的 GPU 内核启动可以访问它。
    int *data;
    cudaMallocManaged((void **)&data, length, cudaMemAttachHost);
    cudaStreamAttachMemAsync(stream, data);
    cudaStreamSynchronize(stream);
    // 使用主机和设备以某种方式迭代数据。
    for(int i=0; i<N; i++) {
        transform<<< 100, 256, 0, stream >>>(in, data, length);
        cudaStreamSynchronize(stream);
        host_process(data, length);    // CPU 使用托管数据。
        convert<<< 100, 256, 0, stream >>>(out, data, length);
    }
    cudaStreamSynchronize(stream);
    cudaStreamDestroy(stream);
    cudaFree(data);
}

在此示例中，分配流关联仅建立一次，然后数据由主机和设备重复使用。结果是比在主机和设备之间显式复制数据所产生的代码简单得多，尽管结果是相同的。

功能 cudaMallocManaged() 指定 cudaMemAttachHost 标志，该标志创建最初对设备端执行不可见的分配。 （默认分配对所有流上的所有 GPU 内核都是可见的。） 这确保了在数据分配和为特定流获取数据之间的时间间隔内不会与另一个线程的执行发生意外交互。

如果没有此标志，如果另一个线程启动的内核恰好正在运行，则新的分配将被视为正在 GPU 上使用。 这可能会影响线程在能够显式地将其附加到私有流之前从 CPU 访问新分配的数据的能力。因此，为了实现线程之间的安全独立，应该在分配时指定此标志。

另一种方法是在分配附加到流后在所有线程之间放置进程范围的屏障。这将确保所有线程在启动任何内核之前完成其数据/流关联，从而避免危险。 在流被销毁之前需要第二个屏障，因为流销毁会导致分配恢复为其默认可见性。的 cudaMemAttachHost 标志的存在既是为了简化此过程，也是因为并不总是可以在需要时插入全局屏障。

4.1.3.3.4. 流关联统一内存的数据移动#

与流相关的统一内存的 Memcpy()/Memset() 在设备上的行为有所不同 concurrentManagedAccess 未设置，则适用以下规则：

If cudaMemcpyHostTo* 指定且源数据为统一内存，则如果复制流中主机可以一致访问，则从主机访问 (1);否则将从设备访问它。类似的规则适用于以下情况的目的地： cudaMemcpy*ToHost 已指定且目的地是统一内存。

If cudaMemcpyDeviceTo* 指定且源数据为统一内存，则从设备访问。源必须可从复制流中的设备连贯地访问 (2);否则，返回错误。类似的规则适用于以下情况的目的地： cudaMemcpy*ToDevice 已指定且目的地是统一内存。

If cudaMemcpyDefault 指定后，如果无法从复制流中的设备连贯地访问统一内存，则将从主机访问统一内存 (2) 或者如果数据的首选位置是 cudaCpuDeviceId 并且可以从复制流中的主机连贯地访问 (1);否则，将从设备访问它。

使用时 cudaMemset*() 使用统一内存，数据必须能够从用于数据流的设备中一致地访问。 cudaMemset() operation (2);否则，返回错误。

当从设备访问数据时 cudaMemcpy* 或 cudaMemset*，操作流被认为在 GPU 上处于活动状态。在此期间，如果 GPU 的设备属性值为零，则任何与该流关联的数据或具有全局可见性的数据的 CPU 访问都将导致分段错误 concurrentManagedAccess。程序必须适当同步，以确保在从 CPU 访问任何关联数据之前操作已完成。

  1. 在给定流中从主机一致地访问意味着存储器既不具有全局可见性也不与给定流关联。

  1. 在给定的流中从设备一致地访问意味着存储器具有全局可见性或者与给定的流相关联。

4.1.4.1. 数据预取#

cudaMemPrefetchAsync API 是异步流排序 API，可以将数据迁移到更靠近指定处理器的位置。 数据可以在预取时被访问。 直到流中的所有先前操作完成后，迁移才会开始， 并在流中的任何后续操作之前完成。

cudaError_t cudaMemPrefetchAsync(const void *devPtr,
                                 size_t count,
                                 struct cudaMemLocation location,
                                 unsigned int flags,
                                 cudaStream_t stream=0);

一个内存区域包含 [devPtr, devPtr + count) 可能会迁移到 目标设备 location.id if location.type is cudaMemLocationTypeDevice，或 CPU，如果 location.type is cudaMemLocationTypeHost, 当预取任务在给定的时间内执行时 stream。有关详细信息 flags，查看当前 CUDA 运行时 API 文档.

考虑下面的简单代码示例：

void test_prefetch_sam(const cudaStream_t& s) {
  // 初始化CPU上的数据
  char *data = (char*)malloc(dataSizeBytes);
  init_data(data, dataSizeBytes);                                     
  cudaMemLocation location = {.type = cudaMemLocationTypeDevice, .id = myGpuId};

  // 鼓励数据在使用前转移到 GPU
  const unsigned int flags = 0;
  cudaMemPrefetchAsync(data, dataSizeBytes, location, flags, s);      

  // 使用 GPU 上的数据
  const unsigned num_blocks = (dataSizeBytes + threadsPerBlock - 1) / threadsPerBlock;
  mykernel<<<num_blocks, threadsPerBlock, 0, s>>>(data, dataSizeBytes);  

  // 鼓励数据移回CPU
  location = {.type = cudaMemLocationTypeHost};
  cudaMemPrefetchAsync(data, dataSizeBytes, location, flags, s);      
  
  cudaStreamSynchronize(s);

  // 使用CPU上的数据
  use_data(data, dataSizeBytes);                                      
  free(data);
}

void test_prefetch_managed(const cudaStream_t& s) {
  // 初始化CPU上的数据
  char *data;
  cudaMallocManaged(&data, dataSizeBytes);
  init_data(data, dataSizeBytes);                                     
  cudaMemLocation location = {.type = cudaMemLocationTypeDevice, .id = myGpuId};

  // 鼓励数据在使用前转移到 GPU
  const unsigned int flags = 0;
  cudaMemPrefetchAsync(data, dataSizeBytes, location, flags, s);

  // 使用 GPU 上的数据
  const uinsigned num_blocks = (dataSizeBytes + threadsPerBlock - 1) / threadsPerBlock;
  mykernel<<<num_blocks, threadsPerBlock, 0, s>>>(data, dataSizeBytes); 

  // 鼓励数据移回CPU
  location = {.type = cudaMemLocationTypeHost};
  cudaMemPrefetchAsync(data, dataSizeBytes, location, flags, s); 

  cudaStreamSynchronize(s);

  // 使用CPU上的数据
  use_data(data, dataSizeBytes);
  cudaFree(data);
}

4.1.4.3. 内存丢弃#

cudaMemDiscardBatchAsync API 允许应用程序通知 CUDA 运行时内容 指定的内存范围不再有用。统一内存驱动程序执行自动内存 由于基于故障的迁移或内存驱逐而进行的传输，以支持设备内存超额订阅。 这些自动内存传输有时可能是冗余的，这会严重降低性能。 将地址范围标记为“丢弃”将通知统一内存驱动程序应用程序已 消耗了范围内的内容，并且无需在预取或页面驱逐时迁移此数据 以便为其他分配腾出空间。读取废弃页而无需后续写入访问 或预取将产生不确定的值。而丢弃操作后的任何新写入都得到保证 通过后续的读取访问可以看到。对被丢弃的地址范围的并发访问或预取 将导致未定义的行为。

cudaError_t cudaMemDiscardBatchAsync(void **dptrs,
                                    size_t *sizes,
                                    size_t count,
                                    unsigned long long flags,
                                    cudaStream_t stream);

该函数在指定的地址范围上执行一批内存丢弃 dptrs 或 sizes 数组。 两个数组的长度必须相同 count。每个内存范围必须引用 管理内存分配通过 cudaMallocManaged 或通过声明 __managed__ variables.

cudaMemDiscardAndPrefetchBatchAsync API 结合了丢弃和预取操作。呼唤 cudaMemDiscardAndPrefetchBatchAsync 在语义上等同于调用 cudaMemDiscardBatchAsync 随后 cudaMemPrefetchBatchAsync，但更优化。当应用程序需要时这很有用 内存位于目标位置，但不需要内存的内容。

cudaError_t cudaMemDiscardAndPrefetchBatchAsync(void **dptrs,
                                               size_t *sizes,
                                               size_t count,
                                               struct cudaMemLocation *prefetchLocs,
                                               size_t *prefetchLocIdxs,
                                               size_t numPrefetchLocs,
                                               unsigned long long flags,
                                               cudaStream_t stream);

prefetchLocs array 指定预取的目的地，而 prefetchLocIdxs 指示每个预取位置适用于哪些操作。例如，如果一个批次有 10 个操作 前 6 个应预取到一个位置，而其余 4 个应预取到另一个位置，然后 numPrefetchLocs 将为 2, prefetchLocIdxs 将是 {0, 6}，并且 prefetchLocs 会 包含两个目标位置。

重要考虑因素：

  • 从丢弃的范围中读取而不进行后续写入或预取将返回不确定的值

  • 可以通过写入范围或通过预取来撤消丢弃操作 cudaMemPrefetchAsync

  • 与丢弃操作同时发生的任何读取、写入或预取都会导致未定义的行为

  • 所有设备都必须具有非零值 cudaDevAttrConcurrentManagedAccess

4.1.4.4. 查询托管内存数据使用属性#

程序可以查询通过分配的内存范围属性 cudaMemAdvise cudaMemPrefetchAsync 使用以下 API 在 CUDA 托管内存上：

cudaMemRangeGetAttribute(void *data,
                         size_t dataSize,
                         enum cudaMemRangeAttribute attribute,
                         const void *devPtr,
                         size_t count);

该函数查询从以下位置开始的内存范围的属性 devPtr 大小为 count 字节。 内存范围必须引用通过分配的托管内存 cudaMallocManaged 或 通过声明 __managed__ 变量。可以查询以下属性：

  • cudaMemRangeAttributeReadMostly：如果整个内存范围都有，则返回 1 cudaMemAdviseSetReadMostly 属性集，否则为 0。

  • cudaMemRangeAttributePreferredLocation：返回的结果将是 GPU 设备 id 或 cudaCpuDeviceId 如果整个内存范围都有相应的处理器作为首选位置，否则 cudaInvalidDeviceId 将被退回。 应用程序可以使用此查询 API 根据托管指针的首选位置属性来决定通过 CPU 或 GPU 暂存数据。 请注意，查询时内存范围的实际位置可能与首选位置不同。

  • cudaMemRangeAttributeAccessedBy：将返回为该内存范围设置建议的设备列表。

  • cudaMemRangeAttributeLastPrefetchLocation：将返回显式预取内存范围的最后一个位置 cudaMemPrefetchAsync。请注意，这只是返回应用程序请求预取内存范围的最后一个位置。它没有指示对该位置的预取操作是否已完成甚至开始。

  • cudaMemRangeAttributePreferredLocationType：它返回首选位置的位置类型，具有以下值：

    • cudaMemLocationTypeDevice：如果内存范围内的所有页面都将相同的 GPU 作为其首选位置，

    • cudaMemLocationTypeHost：如果内存范围内的所有页面都将CPU作为其首选位置，

    • cudaMemLocationTypeHostNuma：如果内存范围内的所有页面都具有相同的主机 NUMA 节点 ID 作为其首选位置，

    • cudaMemLocationTypeInvalid：如果所有页面没有相同的首选位置，或者某些页面根本没有首选位置。

  • cudaMemRangeAttributePreferredLocationId：返回设备序号，如果 cudaMemRangeAttributePreferredLocationType 查询相同地址范围返回 cudaMemLocationTypeDevice。如果首选位置类型是主机 NUMA 节点，则返回主机 NUMA 节点 ID。否则，该 id 应该被忽略。

  • cudaMemRangeAttributeLastPrefetchLocationType：返回内存范围中所有页面通过显式预取的最后一个位置类型 cudaMemPrefetchAsync。返回以下值：

    • cudaMemLocationTypeDevice：如果内存范围内的所有页面都预取到同一个 GPU，

    • cudaMemLocationTypeHost：如果内存范围内的所有页面都被预取到CPU，

    • cudaMemLocationTypeHostNuma：如果内存范围内的所有页面都预取到同一主机NUMA节点ID，

    • cudaMemLocationTypeInvalid：如果所有页面都没有预取到同一位置，或者某些页面根本没有预取。

  • cudaMemRangeAttributeLastPrefetchLocationId：如果 cudaMemRangeAttributeLastPrefetchLocationType 查询相同地址范围返回 cudaMemLocationTypeDevice，它将是一个有效的设备序号，或者如果它返回 cudaMemLocationTypeHostNuma，它将是有效的主机 NUMA 节点 ID。否则，该 id 应该被忽略。

此外，还可以通过使用相应的属性来查询多个属性 cudaMemRangeGetAttributes function.

4.1.4.5. GPU 内存超额认购#

统一内存使应用程序能够 oversubscribe 任何单个处理器的内存： 换句话说，他们可以分配和共享大于 系统中任何单个处理器的内存容量， 允许对不适合的数据集进行核心外处理 单个 GPU，不会显着增加编程模型的复杂性。

此外，还可以通过使用相应的属性来查询多个属性 cudaMemRangeGetAttributes function.
