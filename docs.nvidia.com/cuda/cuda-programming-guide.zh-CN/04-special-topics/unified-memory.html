4.1. 统一内存#

本节说明各种可用统一内存范式的详细行为和用法。前面的统一内存章节 已经展示了如何确定适用哪一种统一内存范式，并对每种范式作了简要介绍。

如前所述，统一内存编程有四种范例：

  • 完全支持显式托管内存分配

  • 完全支持所有具有软件一致性的分配

  • 完全支持所有具有硬件一致性的分配

  • 有限的统一内存支持

前三种范式都提供完整的统一内存支持，行为和编程模型非常相似，因此会在 具有完整 CUDA 统一内存支持的设备上的统一内存 中统一介绍，并突出说明它们之间的差异。

最后一种范式只提供有限的统一内存支持，详见 Windows、WSL 和 Tegra 上的统一内存。

4.1.1. 具有完整 CUDA 统一内存支持的设备上的统一内存#

这类系统包括硬件一致性内存系统，例如 NVIDIA Grace Hopper，也包括启用了异构内存管理 (HMM) 的现代 Linux 系统。 HMM 是一种基于软件的内存管理系统，提供与硬件一致性内存系统相同的编程模型。

Linux HMM 需要 Linux 内核版本 6.1.24+、6.2.11+ 或 6.3+，需要计算能力 7.5 或更高的设备，并且需要安装带有 开放内核模块 的 CUDA 535+ 驱动程序。

注

我们把 CPU 和 GPU 共用组合页表的系统称为 硬件一致性 系统。CPU 和 GPU 分别使用独立页表的系统称为 软件一致性 系统。

NVIDIA Grace Hopper 等硬件一致性系统为 CPU 和 GPU 提供逻辑上的组合页表，见 CPU 和 GPU 页表：硬件一致性与软件一致性。 以下部分仅适用于硬件一致性系统：

  • 访问计数器迁移

4.1.1.1. 统一内存：深入示例#

具有完整 CUDA 统一内存支持的系统（见 统一内存范式概述 表）允许设备访问与该设备交互的主机进程所拥有的任意内存。

本节展示几个高级用例，使用的内核很简单：它会把输入字符数组的前 8 个字符打印到标准输出流：

__global__ void kernel(const char* type, const char* data) {
  static const int n_char = 8;
  printf("%s - first %d characters: '", type, n_char);
  for (int i = 0; i < n_char; ++i) printf("%c", data[i]);
  printf("'\n");
}

以下选项卡展示了使用系统分配内存调用该内核的几种方式：

void test_malloc() {
  const char test_string[] = "Hello World";
  char* heap_data = (char*)malloc(sizeof(test_string));
  strncpy(heap_data, test_string, sizeof(test_string));
  kernel<<<1, 1>>>("malloc", heap_data);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
  free(heap_data);
}

void test_managed() {
  const char test_string[] = "Hello World";
  char* data;
  cudaMallocManaged(&data, sizeof(test_string));
  strncpy(data, test_string, sizeof(test_string));
  kernel<<<1, 1>>>("managed", data);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
  cudaFree(data);
}

void test_stack() {
  const char test_string[] = "Hello World";
  kernel<<<1, 1>>>("stack", test_string);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
}

void test_static() {
  static const char test_string[] = "Hello World";
  kernel<<<1, 1>>>("static", test_string);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));

const char global_string[] = "Hello World";

void test_global() {

  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
}

// 在单独的文件中声明，见下文
extern char* ext_data;

/* 这可能是非 CUDA 文件 */
char* ext_data;
static const char global_string[] = "Hello World";

void __attribute__ ((constructor)) setup(void) {
  ext_data = (char*)malloc(sizeof(global_string));
  strncpy(ext_data, global_string, sizeof(global_string));
}

void __attribute__ ((destructor)) tear_down(void) {
  free(ext_data);
}

请注意，对于 extern 变量，它可以由第三方库声明及其内存拥有和管理，该第三方库根本不与 CUDA 交互。

另请注意，堆栈变量以及文件范围和全局范围变量只能由 GPU 通过指针访问。在这个特定的示例中，这很方便，因为字符数组已经声明为指针： const char*。但是，请考虑以下具有全局范围整数的示例：

// 该变量是在全局范围内声明的
int global_variable;

__global__ void kernel_uncompilable() {
  // 这会导致编译错误：全局（__host__）变量不能
  // 从 __device__ / __global__ 代码访问
  printf("%d\n", global_variable);
}

// 在 pageableMemoryAccess 设置为 1 的系统上，可以访问全局变量的地址。
// 下面的内核将该地址作为参数。
__global__ void kernel(int* global_variable_addr) {
  printf("%d\n", *global_variable_addr);
}
int main() {
  kernel<<<1, 1>>>(&global_variable);
  ...
  return 0;
}

在上面的示例中，需要确保把指向全局变量的 指针 传给内核，而不是在内核中直接访问该全局变量。这是因为没有使用 __managed__ 说明符的全局变量默认声明为仅 __host__ 可用，因此目前大多数编译器都不允许在设备代码中直接使用这些变量。

4.1.1.1.1. 文件支持的统一内存#

由于具有完整 CUDA 统一内存支持的系统允许设备访问主机进程拥有的任意内存，因此设备也可以直接访问文件支持的内存。

这里展示上一节初始示例的一个修改版本：它使用文件支持的内存，从 GPU 打印一个直接从输入文件读取的字符串。以下示例中的内存由物理文件作为后备，但该示例也适用于内存支持的文件。

__global__ void kernel(const char* type, const char* data) {
  static const int n_char = 8;
  printf("%s - first %d characters: '", type, n_char);
  for (int i = 0; i < n_char; ++i) printf("%c", data[i]);
  printf("'\n");
}

void test_file_backed() {
  int fd = open(INPUT_FILE_NAME, O_RDONLY);
  ASSERT(fd >= 0, "Invalid file handle");
  struct stat file_stat;
  int status = fstat(fd, &file_stat);
  ASSERT(status >= 0, "Invalid file stats");
  char* mapped = (char*)mmap(0, file_stat.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
  ASSERT(mapped != MAP_FAILED, "Cannot map file into memory");
  kernel<<<1, 1>>>("file-backed", mapped);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
  ASSERT(munmap(mapped, file_stat.st_size) == 0, "Cannot unmap file");
  ASSERT(close(fd) == 0, "Cannot close file");
}

请注意，在没有 hostNativeAtomicSupported 属性的系统上（见 主机本机原子），包括启用了 Linux HMM 的系统，都不支持对文件支持内存执行原子访问。

4.1.1.1.2. 具有统一内存的进程间通信 (IPC)#

注

截至目前，使用具有统一内存的 IPC 可能会对性能产生重大影响。

许多应用程序倾向于让每个进程管理一个 GPU，但仍然需要使用统一内存，例如用于超额订阅，并从多个 GPU 访问这些内存。

CUDA IPC（见 进程间通信）不支持托管内存：这类内存的句柄不能通过本节讨论的任何机制共享。 在具有完整 CUDA 统一内存支持的系统上，系统分配的内存具备 IPC 能力。 一旦系统分配内存的访问权共享给其他进程，就适用同样的编程模型，类似于 文件支持的统一内存。

关于在 Linux 下创建支持 IPC 的系统分配内存的各种方式，请参阅以下参考资料：

  • mmap 与 MAP_SHARED

  • POSIX IPC API

  • Linux memfd_create。

请注意，使用这种技术无法在不同主机及其设备之间共享内存。

4.1.1.2. 性能调优#

为了让统一内存获得良好性能，需要做到：

  • 了解分页在系统上的工作方式，以及如何避免不必要的页面错误

  • 了解各种可让数据保持在访问处理器本地的机制

  • 考虑根据系统内存传输的粒度来调优应用程序。

一般来说，性能提示（见 性能提示） 可能会提升性能，但使用不当也可能让性能低于默认行为。 还要注意，任何提示都会在主机端带来相关性能成本，因此有用的提示至少必须带来足以抵消这部分成本的性能提升。

4.1.1.2.1. 内存分页和页面大小#

为了更好地理解统一内存的性能影响，需要先理解虚拟寻址、内存页和页大小。 本小节会定义必要术语，并解释为什么分页会影响性能。

当前所有支持统一内存的系统都使用虚拟地址空间： 这意味着应用程序使用的内存地址代表一个 虚拟 位置， 该位置可以 映射 到内存实际所在的物理位置。

当前支持的所有处理器（包括 CPU 和 GPU）还会使用内存 分页。 由于所有系统都使用虚拟地址空间，因此内存页有两种类型：

  • 虚拟页：表示操作系统按进程跟踪的一段固定大小、连续的虚拟内存，可被 映射 到物理内存。 请注意，虚拟页与 映射 相关：例如，同一个虚拟地址可以使用不同页大小映射到物理内存。

  • 物理页：表示处理器主内存管理单元 (MMU) 支持的一段固定大小、连续的内存，虚拟页可以映射到其中。

目前，所有 x86_64 CPU 均使用 4KiB 的默认物理页大小。 Arm CPU 支持多种物理页大小，包括 4KiB、16KiB、32KiB 和 64KiB，具体取决于 CPU。 最后，NVIDIA GPU 支持多种物理页大小，但更喜欢 2MiB 或更大的物理页。 请注意，这些大小未来可能会随硬件变化。

虚拟页的默认页大小通常与物理页大小对应， 但只要操作系统和硬件支持，应用程序也可以使用不同页大小。通常，受支持的虚拟页大小必须是 2 的幂，并且是物理页大小的倍数。

用于跟踪虚拟页到物理页映射关系的逻辑实体称为 页表。 给定虚拟页以给定虚拟大小到物理页的每个映射，称为 页表条目 (PTE)。 所有支持的处理器都会为页表提供专门缓存，以加速从虚拟地址到物理地址的转换。这些缓存称为 转换后备缓冲区 (TLB)。

应用程序性能调优有两个重要方面：

  • 虚拟页大小的选择，

  • 系统是提供 CPU 和 GPU 共用的组合页表，还是为每个 CPU 和 GPU 分别提供独立页表。

4.1.1.2.1.1. 选择合适的页大小#

一般来说，较小的页大小会带来更少的（虚拟）内存碎片，但会导致更多 TLB 未命中； 较大的页大小会带来更多内存碎片，但 TLB 未命中更少。 此外，较大页大小下的内存迁移通常比小页更昂贵，因为通常会迁移完整的内存页。这可能让使用大页大小的应用程序出现更大的延迟尖峰。有关页面错误的更多细节，另请参阅下一节。

性能调优中的一个重要点是：与 CPU 相比，TLB 未命中在 GPU 上通常昂贵得多。 这意味着，如果 GPU 线程频繁随机访问使用较小页大小映射的统一内存位置，那么这些访问可能显著慢于同样访问使用足够大页大小映射的统一内存。 CPU 线程随机访问使用小页映射的大块内存区域时也可能出现类似效果，但减速不那么明显，因此应用程序可能需要在这种减速和较少内存碎片之间作权衡。

请注意，一般来说，应用程序不应针对某个处理器的物理页大小做性能调优，因为物理页大小可能随硬件变化。上述建议只适用于虚拟页大小。

4.1.1.2.1.2. CPU 和 GPU 页表：硬件一致性与软件一致性#

NVIDIA Grace Hopper 等硬件一致性系统为 CPU 和 GPU 提供逻辑上的组合页表。 这很重要，因为 GPU 要访问系统分配的内存时，会使用 CPU 为所请求内存创建的页表条目。 如果该页表条目使用默认 CPU 页大小 4KiB 或 64KiB，那么访问较大的虚拟内存区域就会导致大量 TLB 未命中，从而显著减速。

另一方面，在软件一致性系统中，CPU 和 GPU 各自拥有自己的逻辑页表，因此需要考虑不同的性能调优因素。 为了保证一致性，当某个处理器访问的内存地址映射到另一个处理器的物理内存中时，这类系统通常会使用 页面错误。这种页面错误意味着：

  • 必须确保当前拥有该页的处理器（也就是物理页当前所在位置）不再能访问该页，方式可以是删除页表条目或更新该条目。

  • 必须确保请求访问的处理器能够访问该页，方式可以是创建新的页表条目，或更新现有条目，使其变为有效/活动状态。

  • 支撑该虚拟页的物理页必须移动/迁移到请求访问的处理器上：这可能是一项昂贵操作，工作量与页大小成正比。

总体而言，当 CPU 和 GPU 线程频繁并发访问同一内存页时，相比软件一致性系统，硬件一致性系统能提供显著性能优势：

  • 页面错误更少：这类系统不需要使用页面错误来模拟一致性或迁移内存；

  • 争用更少：这类系统在缓存行粒度而不是页大小粒度上保持一致性。也就是说，当多个处理器在某个缓存行内发生争用时，只交换比最小页大小小得多的缓存行；当不同处理器访问同一页中的不同缓存行时，则不会发生争用。

这会影响以下场景的性能：

  • CPU 和 GPU 同时对同一地址执行原子更新

  • CPU 线程向 GPU 线程发信号，或反向发信号。

4.1.1.2.2. 从主机直接统一内存访问#

某些设备提供硬件支持，允许主机对驻留在 GPU 上的统一内存执行一致性的读取、存储和原子访问。 这类设备的 cudaDevAttrDirectManagedMemAccessFromHost 属性会被设置为 1。 请注意，所有硬件一致性系统都为 NVLink 连接的设备设置了此属性。 在这些系统上，主机可以直接访问 GPU 驻留内存，而不会触发页面错误和数据迁移。请注意，对于 CUDA 托管内存，需要使用位置类型为 cudaMemLocationTypeHost 的 cudaMemAdviseSetAccessedBy 提示，才能启用这种不会触发页面错误的直接访问，见下面的示例。

__global__ void write(int *ret, int a, int b) {
  ret[threadIdx.x] = a + b + threadIdx.x;
}

__global__ void append(int *ret, int a, int b) {
  ret[threadIdx.x] += a + b + threadIdx.x;
}

void test_malloc() {
  int *ret = (int*)malloc(1000 * sizeof(int));
  // 对于共享页表系统，以下提示不是必需的
  cudaMemLocation location = {.type = cudaMemLocationTypeHost};
  cudaMemAdvise(ret, 1000 * sizeof(int), cudaMemAdviseSetAccessedBy, location);

  write<<< 1, 1000 >>>(ret, 10, 100);            // 页面填充到 GPU 内存中
  cudaDeviceSynchronize();
  for(int i = 0; i < 1000; i++)
      printf("%d: A+B = %d\n", i, ret[i]);        // directManagedMemAccessFromHost=1：CPU 直接访问 GPU 内存，无需迁移
                                                  // directManagedMemAccessFromHost=0：CPU 发生故障并触发设备到主机迁移
  append<<< 1, 1000 >>>(ret, 10, 100);            // directManagedMemAccessFromHost=1：GPU 无需迁移即可访问 GPU 内存
  cudaDeviceSynchronize();                        // directManagedMemAccessFromHost=0：GPU 发生故障并触发主机到设备迁移
  free(ret);
}

__global__ void write(int *ret, int a, int b) {
  ret[threadIdx.x] = a + b + threadIdx.x;
}

__global__ void append(int *ret, int a, int b) {
  ret[threadIdx.x] += a + b + threadIdx.x;
}

void test_managed() {
  int *ret;
  cudaMallocManaged(&ret, 1000 * sizeof(int));
  cudaMemLocation location = {.type = cudaMemLocationTypeHost};
  cudaMemAdvise(ret, 1000 * sizeof(int), cudaMemAdviseSetAccessedBy, location);  // 设置直接访问提示

  write<<< 1, 1000 >>>(ret, 10, 100);            // 页面填充到 GPU 内存中
  cudaDeviceSynchronize();
  for(int i = 0; i < 1000; i++)
      printf("%d: A+B = %d\n", i, ret[i]);        // directManagedMemAccessFromHost=1：CPU 直接访问 GPU 内存，无需迁移
                                                  // directManagedMemAccessFromHost=0：CPU 发生故障并触发设备到主机迁移
  append<<< 1, 1000 >>>(ret, 10, 100);            // directManagedMemAccessFromHost=1：GPU 无需迁移即可访问 GPU 内存
  cudaDeviceSynchronize();                        // directManagedMemAccessFromHost=0：GPU 发生故障并触发主机到设备迁移
  cudaFree(ret);

write 内核完成后，ret 会在 GPU 内存中创建并初始化。 接下来，CPU 会访问 ret，随后 append 内核会再次使用同一块 ret 内存。 根据系统架构以及对硬件一致性的支持情况，这段代码会表现出不同的行为：

  • 在 directManagedMemAccessFromHost=1 的系统上： CPU 对托管缓冲区的访问不会触发任何迁移；数据会继续驻留在 GPU 内存中，后续 GPU 内核也可以继续直接访问它，而不会触发故障或迁移。

  • 在 directManagedMemAccessFromHost=0 的系统上： CPU 访问托管缓冲区会触发页面错误并发起数据迁移；任何首次尝试访问同一数据的 GPU 内核都会触发页面错误，并把页面迁移回 GPU 内存。

4.1.1.2.3. 主机本机原子#

某些设备（包括硬件一致性系统中通过 NVLink 连接的设备）支持对 CPU 驻留内存执行硬件加速的原子访问。这意味着对主机内存的原子访问不必通过页面错误来模拟。对于这些设备，cudaDevAttrHostNativeAtomicSupported 属性会被设置为 1。

4.1.1.2.4. 原子访问和同步原语#

CUDA 统一内存支持主机线程和设备线程可用的所有原子操作，让所有线程能够通过并发访问同一个共享内存位置进行协作。libcu++ 库提供了许多异构同步原语，专门面向主机线程和设备线程之间的并发使用进行调优，包括 cuda::atomic、cuda::atomic_ref、cuda::barrier、cuda::semaphore 等。

在软件一致性系统上，不支持从设备对文件支持的主机内存执行原子访问。以下示例代码在硬件一致性系统上有效，但在其他系统上会表现出未定义行为：

#include <cuda/atomic>

#include <cstdio>
#include <fcntl.h>
#include <sys/mman.h>

#define ERR(msg, ...) { fprintf(stderr, msg, ##__VA_ARGS__); return EXIT_FAILURE; }

__global__ void kernel(int* ptr) {
  cuda::atomic_ref{*ptr}.store(2);
}

int main() {
  // 退出时默认关闭/删除
  FILE* tmp_file = tmpfile64();
  // 需要在文件中分配空间，我们在这里使用 posix_fallocate 来完成此操作
  int status = posix_fallocate(fileno(tmp_file), 0, 4096);
  if (status != 0) ERR("Failed to allocate space in temp file\n");
  int* ptr = (int*)mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_PRIVATE, fileno(tmp_file), 0);
  if (ptr == MAP_FAILED) ERR("Failed to map temp file\n");

  // 初始化文件支持的内存中的值
  *ptr = 1;
  printf("Atom value: %d\n", *ptr);

  // 设备和主机线程使用 cuda::atomic_ref 同时访问 ptr
  kernel<<<1, 1>>>(ptr);
  while (cuda::atomic_ref{*ptr}.load() != 2);
  // 这将永远是 2
  printf("Atom value: %d\n", *ptr);

  return EXIT_SUCCESS;
}

在软件一致性系统上，对统一内存执行原子访问可能会触发页面错误，从而造成显著延迟。请注意，在这类系统上，并非所有 GPU 对 CPU 内存的原子操作都会如此：由 nvidia-smi -q | grep "Atomic Caps Outbound" 列出的操作可以避免页面错误。

在硬件一致性系统上，主机和设备之间的原子操作不需要页面错误，但仍然可能因为其他原因遭遇任何内存访问都会遇到的错误。

4.1.1.2.5. 统一内存的 Memcpy()/Memset() 行为#

cudaMemcpy*() 或 cudaMemset*() 可以接受任意统一内存指针作为参数。

对于 cudaMemcpy*()，通过 cudaMemcpyKind 指定的方向是一项性能提示；如果任一参数是统一内存指针，该提示可能带来更高的性能影响。

因此，建议遵循以下性能建议：

  • 当统一内存的物理位置已知时，使用准确的 cudaMemcpyKind 提示。

  • 相比不准确的 cudaMemcpyKind 提示，应优先使用 cudaMemcpyDefault。

  • 始终使用已填充（已初始化）的缓冲区：避免使用这些 API 来初始化内存。

  • 如果两个指针都指向系统分配的内存，应避免使用 cudaMemcpy*()： 改为启动内核，或使用 std::memcpy 等 CPU 内存拷贝算法。

4.1.1.2.7. 访问计数器迁移#

在硬件一致性系统上，访问计数器功能会跟踪 GPU 访问其他处理器上内存的频率。这是为了确保内存页被移动到最频繁访问这些页的处理器物理内存中。它可以引导 CPU 与 GPU 之间以及对等 GPU 之间的迁移，这个过程称为访问计数器迁移。

从 CUDA 12.4 开始，系统分配内存支持访问计数器。请注意，文件支持的内存不会根据访问进行迁移。对于系统分配内存，可以通过对相应设备 ID 的设备使用 cudaMemAdviseSetAccessedBy 提示来开启访问计数器迁移。如果开启了访问计数器，则可以把 cudaMemAdviseSetPreferredLocation 设置为主机以防止迁移。默认情况下，cudaMallocManaged 基于“故障并迁移”机制进行迁移。[7]

驱动程序也可以使用访问计数器，更高效地缓解颠簸或处理内存超额订阅场景。

[7]

设置 accessed-by 设备提示后，当前系统允许对托管内存使用访问计数器迁移。这是实现细节，不应依赖它来保证未来兼容性。

4.1.1.2.8. 避免从 CPU 频繁写入 GPU 驻留内存#

如果主机访问统一内存，缓存未命中可能会在主机和设备之间引入比预期更多的流量。许多 CPU 架构要求所有内存操作（包括写入）都经过缓存层次结构。如果系统内存驻留在 GPU 上，这意味着 CPU 频繁写入该内存可能导致缓存未命中，从而先把数据从 GPU 传输到 CPU，再把实际值写入所请求的内存范围。在软件一致性系统上，这可能引入额外页面错误；在硬件一致性系统上，则可能导致 CPU 操作之间的延迟升高。因此，如果要与设备共享主机生成的数据，可以考虑写入 CPU 驻留内存，并从设备直接读取这些值。下面的代码展示了如何用统一内存实现这一点。

  size_t data_size = sizeof(int);
  int* data = (int*)malloc(data_size);
  // 确保数据保持在主机本地并避免故障
  cudaMemLocation location = {.type = cudaMemLocationTypeHost};
  cudaMemAdvise(data, data_size, cudaMemAdviseSetPreferredLocation, location);
  cudaMemAdvise(data, data_size, cudaMemAdviseSetAccessedBy, location);

  // 频繁交换小数据：如果 CPU 写入 CPU 驻留内存，
  // 而 GPU 直接访问该数据，就可以避免 CPU 缓存重新加载
  // 两次写入之间可能已被逐出的数据
  for (int i = 0; i < 10; ++i) {
    *data = 42 + i;
    kernel<<<1, 1>>>(data);
    cudaDeviceSynchronize();
    // CPU 缓存可能会逐出此处的数据
  }
  free(data);

  int* data;
  size_t data_size = sizeof(int);
  cudaMallocManaged(&data, data_size);
  // 确保数据保持在主机本地并避免故障
  cudaMemLocation location = {.type = cudaMemLocationTypeHost};
  cudaMemAdvise(data, data_size, cudaMemAdviseSetPreferredLocation, location);
  cudaMemAdvise(data, data_size, cudaMemAdviseSetAccessedBy, location);

  // 频繁交换小数据：如果 CPU 写入 CPU 驻留内存，
  // 而 GPU 直接访问该数据，就可以避免 CPU 缓存重新加载
  // 两次写入之间可能已被逐出的数据
  for (int i = 0; i < 10; ++i) {
    *data = 42 + i;
    kernel<<<1, 1>>>(data);
    cudaDeviceSynchronize();
    // CPU 缓存可能会逐出此处的数据
  }
  cudaFree(data);

4.1.1.2.9. 利用对系统内存的异步访问#

如果应用程序需要把设备端工作的结果共享给主机，可以有几种选择：

  1. 设备把结果写入 GPU 驻留内存，再使用 cudaMemcpy* 传输结果，主机读取传输后的数据。

  2. 设备把结果直接写入 CPU 驻留内存，主机读取该数据。

  3. 设备写入 GPU 驻留内存，主机直接访问该数据。

如果结果由主机传输或访问的同时，还能在设备上调度独立工作，则优先选择方案 1 或 3。如果设备必须等到主机访问完结果后才有工作可做，则方案 2 可能更合适。这是因为一般情况下设备写入带宽高于主机读取带宽，除非使用大量主机线程读取数据。

void exchange_explicit_copy(cudaStream_t stream) {
  int* data, *host_data;
  size_t n_bytes = sizeof(int) * 16;
  // 分配接收缓冲区
  host_data = (int*)malloc(n_bytes);
  // 分配后首先由设备访问，因此会驻留在 GPU 上
  cudaMallocManaged(&data, n_bytes);
  kernel<<<1, 16, 0, stream>>>(data);
  // 在设备上启动独立工作
  // other_kernel<<<1024, 256, 0, stream>>>(other_data, ...);
  // 传输到主机
  cudaMemcpyAsync(host_data, data, n_bytes, cudaMemcpyDeviceToHost, stream);
  // 同步流以确保数据已传输
  cudaStreamSynchronize(stream);
  // 读取已传输的数据
  printf("Got values %d - %d from GPU\n", host_data[0], host_data[15]);
  cudaFree(data);
  free(host_data);
}

void exchange_device_direct_write(cudaStream_t stream) {
  int* data;
  size_t n_bytes = sizeof(int) * 16;
  // 分配接收缓冲区
  cudaMallocManaged(&data, n_bytes);
  // 确保数据已映射并驻留在主机上
  cudaMemLocation location = {.type = cudaMemLocationTypeHost};
  cudaMemAdvise(data, n_bytes, cudaMemAdviseSetPreferredLocation, location);
  cudaMemAdvise(data, n_bytes, cudaMemAdviseSetAccessedBy, location);
  kernel<<<1, 16, 0, stream>>>(data);
  // 同步流以确保数据已经由设备写入
  cudaStreamSynchronize(stream);
  // 读取设备写入的数据
  printf("Got values %d - %d from GPU\n", data[0], data[15]);
  cudaFree(data);
}

void exchange_host_direct_read(cudaStream_t stream) {
  int* data;
  size_t n_bytes = sizeof(int) * 16;
  // 分配接收缓冲区
  cudaMallocManaged(&data, n_bytes);
  // 确保数据已映射并驻留在设备上
  cudaMemLocation device_loc = {};
  cudaGetDevice(&device_loc.id);
  device_loc.type = cudaMemLocationTypeDevice;
  cudaMemAdvise(data, n_bytes, cudaMemAdviseSetPreferredLocation, device_loc);
  cudaMemAdvise(data, n_bytes, cudaMemAdviseSetAccessedBy, device_loc);
  kernel<<<1, 16, 0, stream>>>(data);
  // 在 GPU 上启动独立工作
  // other_kernel<<<1024, 256, 0, stream>>>(other_data, ...);
  // 同步流以确保数据可以被访问（已由设备写入）
  cudaStreamSynchronize(stream);
  // 直接从主机读取数据
  printf("Got values %d - %d from GPU\n", data[0], data[15]);
  cudaFree(data);

最后，在上面的“显式拷贝”示例中，也可以不用 cudaMemcpy* 传输数据，而是使用主机或设备内核显式执行传输。对于连续数据，通常更适合使用 CUDA 拷贝引擎，因为拷贝引擎执行的操作可以与主机和设备上的工作重叠。cudaMemcpy* 和 cudaMemPrefetchAsync API 可能会使用拷贝引擎，但并不保证 cudaMemcpy* API 调用一定使用拷贝引擎。基于同样原因，对于足够大的数据，显式拷贝通常优于主机直接读取：如果主机和设备上的工作都没有使各自的内存系统饱和，拷贝引擎就可以与主机和设备执行的工作并发完成传输。

拷贝引擎通常用于主机与设备之间的传输，也用于 NVLink 互连系统内对等设备之间的传输。由于拷贝引擎总数有限，在某些系统上，cudaMemcpy* 的带宽可能低于使用设备显式执行传输的带宽。在这种情况下，如果传输位于应用程序关键路径上，可能更适合使用显式的设备端传输。

4.1.3. Windows、WSL 和 Tegra 上的统一内存#

注

本节只讨论计算能力低于 6.0 的设备，或 Windows 平台上 concurrentManagedAccess 属性为 0 的设备。

计算能力低于 6.0 的设备，或 Windows 平台上 concurrentManagedAccess 属性为 0 的设备（见 统一内存范式概述），支持 CUDA 托管内存，但存在以下限制：

  • 数据迁移和一致性：不支持按需把托管数据细粒度地移动到 GPU。每次启动 GPU 内核时，通常都必须把所有托管内存传输到 GPU 内存，以避免内存访问触发错误。只有 CPU 端支持页面错误。

  • GPU 内存超额订阅：不能分配超过 GPU 物理内存大小的托管内存。

  • 一致性和并发性：不能同时访问托管内存，因为缺少 GPU 页面错误机制；如果 GPU 内核处于活动状态时 CPU 访问统一内存分配，就无法保证一致性。

4.1.3.1. 多 GPU#

在包含计算能力低于 6.0 的设备的系统上，或在 Windows 平台上，托管分配会通过 GPU 的对等功能自动对系统中的所有 GPU 可见。托管内存分配的行为类似于使用 cudaMalloc() 分配的非托管内存：当前活动设备是物理分配的主位置，但系统中的其他 GPU 会通过 PCIe 总线以较低带宽访问该内存。

在 Linux 上，只要程序正在使用的所有 GPU 都支持对等访问，托管内存就会分配在 GPU 内存中。如果应用程序在任何时候开始使用一个 GPU，而该 GPU 与已有托管分配所在的任何其他 GPU 不支持对等访问，驱动程序就会把所有托管分配迁移到系统内存。在这种情况下，所有 GPU 都会受到 PCIe 带宽限制。

在 Windows 上，如果对等映射不可用（例如在不同架构的 GPU 之间），系统会自动回退到使用映射内存，无论程序是否实际使用了这两个 GPU。如果程序实际只使用一个 GPU，则需要在启动程序前设置 CUDA_VISIBLE_DEVICES 环境变量。该变量会限制哪些 GPU 可见，从而允许在 GPU 内存中分配托管内存。

或者，Windows 用户也可以把 CUDA_MANAGED_FORCE_DEVICE_ALLOC 设置为非零值，强制驱动程序始终使用设备内存作为物理存储。当该环境变量设置为非零值时，进程中使用的所有支持托管内存的设备都必须彼此点对点兼容。 如果使用了支持托管内存的设备，但该设备与此前在该进程中使用过的任何其他支持托管内存的设备不点对点兼容，即使已经对那些设备调用过 ::cudaDeviceReset，也会返回错误 ::cudaErrorInvalidDevice。这些环境变量在 CUDA 环境变量 中说明。

4.1.3.2. 一致性和并发性#

为了确保一致性，统一内存编程模型会在 CPU 和 GPU 并发执行时限制数据访问。实际效果是：只要有任何内核操作正在执行，GPU 就拥有所有托管数据的独占访问权，CPU 不允许访问这些数据，不论该内核是否正在主动使用这些数据。 CPU/GPU 并发访问即使发生在不同的托管内存分配上，也会导致分段错误，因为相关页面会被视为 CPU 不可访问。

例如，得益于 GPU 页面错误能力，下面的代码可以在计算能力 6.x 的设备上成功运行；这种能力解除了对同时访问的所有限制。 但在 6.x 之前的架构和 Windows 平台上，代码会失败，因为 CPU 访问 y 时 GPU 程序内核仍处于活动状态：

__device__ __managed__ int x, y=2;
__global__  void  kernel() {
    x = 10;
}
int main() {
    kernel<<< 1, 1 >>>();
    y = 20;            // GPU 不支持并发访问时出现错误

    cudaDeviceSynchronize();
    return  0;
}

程序在访问 y 之前，必须显式与 GPU 同步（无论 GPU 内核是否实际访问 y，甚至是否访问任何托管数据）：

__device__ __managed__ int x, y=2;
__global__  void  kernel() {
    x = 10;
}
int main() {
    kernel<<< 1, 1 >>>();
    cudaDeviceSynchronize();
    y = 20;            // 在不支持并发访问的 GPU 上取得成功
    return  0;
}

请注意，只要某个函数调用在逻辑上能够保证 GPU 已完成其工作，就可以用来确保 GPU 工作完成；参见 显式同步。

还要注意，如果在 GPU 处于活动状态时使用 cudaMallocManaged() 或 cuMemAllocManaged() 动态分配内存，则在启动额外工作或同步 GPU 之前，该内存的行为未指定。 在此期间尝试从 CPU 访问该内存，可能会导致分段错误，也可能不会。使用 cudaMemAttachHost 或 CU_MEM_ATTACH_HOST 标志分配的内存不受此规则影响。

4.1.3.3. 流关联统一内存#

CUDA 编程模型提供流，作为程序表达内核启动之间依赖性和独立性的机制。启动到同一流中的内核保证按顺序执行， 而启动到不同流中的内核允许并发执行。参见 CUDA 流。

4.1.3.3.1. 流回调#

如果 GPU 上没有其他可能访问托管数据的流处于活动状态，CPU 就可以在流回调内部访问托管数据。此外，如果某个回调后面没有任何设备工作，也可以把该回调用于同步，例如在回调内部发出条件变量信号；否则，CPU 访问只在回调执行期间有效。 需要注意以下几点：

  1. 当 GPU 处于活动状态时，始终允许 CPU 访问非托管映射内存数据。

  2. 只要 GPU 正在运行任何内核，就会被视为活动状态，即使该内核并未使用托管数据。如果某个内核可能使用托管数据，则禁止 CPU 访问。

  3. 除了适用于非托管内存的多 GPU 访问的限制之外，托管内存的并发 GPU 间访问没有任何限制。

  4. 并发 GPU 内核访问托管数据没有任何限制。

请注意最后一点允许 GPU 内核之间出现竞争，这与当前非托管 GPU 内存的情况相同。从 GPU 的角度看，托管内存的功能与非托管内存相同。 以下代码示例说明了这些要点：

int main() {
    cudaStream_t stream1, stream2;
    cudaStreamCreate(&stream1);
    cudaStreamCreate(&stream2);
    int *non_managed, *managed, *also_managed;
    cudaMallocHost(&non_managed, 4);    // 非托管、CPU 可访问的内存
    cudaMallocManaged(&managed, 4);
    cudaMallocManaged(&also_managed, 4);
    // 第 1 点：CPU 可以访问非托管数据。
    kernel<<< 1, 1, 0, stream1 >>>(managed);
    *non_managed = 1;
    // 第 2 点：当 GPU 繁忙时，CPU 无法访问任何托管数据，
    // 除非 concurrentManagedAccess = 1
    // 请注意，我们尚未同步，因此“内核”仍然处于活动状态。
    *also_managed = 2;      // 会出现分段错误
    // 第 3 点：并发 GPU 内核可以访问相同的数据。
    kernel<<< 1, 1, 0, stream2 >>>(managed);
    // 第 4 点：也允许多 GPU 并发访问。
    cudaSetDevice(1);
    kernel<<< 1, 1 >>>(managed);
    return  0;
}

4.1.3.3.2. 与流关联的托管内存允许更细粒度的控制#

统一内存建立在流独立模型之上，允许 CUDA 程序把托管分配显式关联到 CUDA 流。 通过这种方式，程序员可以根据内核是否启动到指定流中来说明内核对数据的使用情况。这让程序能够利用自身数据访问模式中的并发机会。 控制这种行为的函数是：

cudaError_t cudaStreamAttachMemAsync(cudaStream_t stream,
                                     void *ptr,
                                     size_t length=0,
                                     unsigned int flags=0);

cudaStreamAttachMemAsync() 函数会把从 ptr 开始的 length 字节内存与指定流关联起来。只要该流中的所有操作都已完成，CPU 就可以访问该内存区域，无论其他流是否处于活动状态。 实际效果是，活动 GPU 对该托管内存区域的独占所有权被限制到每个流的活动范围内，而不是整个 GPU 的活动范围。 最重要的是，如果某个分配未与特定流关联，它就会对所有正在运行的内核可见，而不论这些内核属于哪个流。 这正是 cudaMallocManaged() 分配或 __managed__ 变量的默认可见性；因此，简单情形下的规则是：只要任何内核正在运行，CPU 就不得访问数据。

注

通过把分配与特定流关联起来，程序承诺只有启动到该流中的内核才会访问该数据。统一内存系统不会执行错误检查。

注

除了允许更高并发性之外，使用 cudaStreamAttachMemAsync() 还可能在统一内存系统内部启用数据传输优化，从而影响延迟和其他开销。

下面的示例展示了如何显式把 y 关联为主机可访问，从而允许 CPU 随时访问它。（注意内核调用之后没有 cudaDeviceSynchronize()。）此时，正在运行内核的 GPU 对 y 的访问会产生未定义结果。

__device__ __managed__ int x, y=2;
__global__  void  kernel() {
    x = 10;
}
int main() {
    cudaStream_t stream1;
    cudaStreamCreate(&stream1);
    cudaStreamAttachMemAsync(stream1, &y, 0, cudaMemAttachHost);
    cudaDeviceSynchronize();          // 等待主机关联完成。
    kernel<<< 1, 1, 0, stream1 >>>(); // 注意：启动到 stream1。
    y = 20;                           // 成功 – 内核正在运行，但“y”
                                      // 未与任何流关联。
    return  0;
}

4.1.3.3.3. 关于多线程主机程序的更详细的示例#

cudaStreamAttachMemAsync() 的主要用途，是通过 CPU 线程启用独立任务并行。通常，在这种程序中，每个 CPU 线程都会为自己生成的所有工作创建专用流，因为使用 CUDA 的 NULL 流会在线程之间引入依赖关系。 托管数据默认对任何 GPU 流都具有全局可见性，这会让多线程程序很难避免 CPU 线程之间的相互影响。因此，cudaStreamAttachMemAsync() 可用于把某个线程的托管分配与该线程自己的流关联起来，并且该关联通常在线程生命周期内保持不变。 这样的程序只需增加一次 cudaStreamAttachMemAsync() 调用，就可以使用统一内存进行数据访问：

// 该函数在其自己的私有流中执行一些任务，并且可以并行运行
void run_task(int *in, int *out, int length) {
    // 创建一个供当前任务使用的流。
    cudaStream_t stream;
    cudaStreamCreate(&stream);
    // 分配一些托管数据并与当前流关联。
    // 注意这里为 cudaMallocManaged() 使用主机关联标志；
    // 随后把该分配与当前流关联起来，
    // 使当前流中启动的 GPU 内核可以访问它。
    int *data;
    cudaMallocManaged((void **)&data, length, cudaMemAttachHost);
    cudaStreamAttachMemAsync(stream, data);
    cudaStreamSynchronize(stream);
    // 使用主机和设备以某种方式反复处理数据。
    for(int i=0; i<N; i++) {
        transform<<< 100, 256, 0, stream >>>(in, data, length);
        cudaStreamSynchronize(stream);
        host_process(data, length);    // CPU 使用托管数据。
        convert<<< 100, 256, 0, stream >>>(out, data, length);
    }
    cudaStreamSynchronize(stream);
    cudaStreamDestroy(stream);
    cudaFree(data);
}

在此示例中，分配与流的关联只建立一次，随后主机和设备会反复使用这份数据。虽然结果相同，但相比在主机和设备之间显式拷贝数据，这样的代码要简单得多。

cudaMallocManaged() 函数指定了 cudaMemAttachHost 标志，从而创建一个最初对设备端执行不可见的分配。（默认分配会对所有流上的所有 GPU 内核可见。） 这可确保从数据分配完成到数据被某个特定流获取之间，不会意外影响另一个线程的执行。

如果没有这个标志，当另一个线程启动的内核恰好正在运行时，新分配会被视为正在 GPU 上使用。 这可能会影响该线程在能够把新分配显式附加到私有流之前，从 CPU 访问这块新分配数据的能力。因此，为了在线程之间实现安全独立，分配时应指定此标志。

另一种做法是在分配附加到流之后，在所有线程之间设置一个进程范围屏障。这样可以确保所有线程都在启动任何内核之前完成各自的数据/流关联，从而避免风险。 在销毁流之前还需要第二个屏障，因为销毁流会使分配恢复默认可见性。cudaMemAttachHost 标志既用于简化这一过程，也因为并非总能在需要的位置插入全局屏障。

4.1.3.3.4. 流关联统一内存的数据移动#

在未设置 concurrentManagedAccess 的设备上，Memcpy()/Memset() 与流关联统一内存配合使用时行为不同，适用以下规则：

如果指定了 cudaMemcpyHostTo* 且源数据是统一内存，那么只要在拷贝流中主机能够一致地访问该数据 (1)，就会从主机访问它；否则会从设备访问它。当指定 cudaMemcpy*ToHost 且目标是统一内存时，目标数据也遵循类似规则。

如果指定了 cudaMemcpyDeviceTo* 且源数据是统一内存，那么会从设备访问它。源数据必须能够在拷贝流中由设备一致地访问 (2)；否则会返回错误。当指定 cudaMemcpy*ToDevice 且目标是统一内存时，目标数据也遵循类似规则。

如果指定了 cudaMemcpyDefault，则在以下任一情况下会从主机访问统一内存：它无法在拷贝流中由设备一致地访问 (2)；或者数据首选位置为 cudaCpuDeviceId，且在拷贝流中主机能够一致地访问它 (1)。否则，会从设备访问它。

对统一内存使用 cudaMemset*() 时，数据必须能够在执行 cudaMemset() 操作所用的流中由设备一致地访问 (2)；否则会返回错误。

当 cudaMemcpy* 或 cudaMemset* 从设备访问数据时，执行该操作的流会被视为在 GPU 上处于活动状态。在此期间，如果 GPU 的 concurrentManagedAccess 设备属性值为 0，那么 CPU 访问与该流关联的数据，或访问具有全局可见性的数据，都会导致分段错误。程序必须进行适当同步，确保操作完成后再由 CPU 访问任何关联数据。

  1. “在给定流中可由主机一致访问”意味着该内存既没有全局可见性，也未与该给定流关联。

  1. “在给定流中可由设备一致访问”意味着该内存具有全局可见性，或者已与该给定流关联。

4.1.4. 性能提示#

性能提示允许程序员向 CUDA 提供更多关于统一内存使用方式的信息。 CUDA 会利用这些提示更高效地管理内存，并提升应用程序性能。 性能提示不会影响应用程序的正确性，只会影响性能。

注

应用程序只有在性能确实得到改善时，才应使用统一内存性能提示。

性能提示可用于任何统一内存分配，包括 CUDA 托管内存。 在具有完整 CUDA 统一内存支持的系统上，性能提示也可应用于所有系统分配内存。

4.1.4.1. 数据预取#

cudaMemPrefetchAsync API 是一种异步、按流排序的 API，可将数据迁移到更靠近指定处理器的位置。 数据可以在预取时被访问。 迁移会等到该流中所有先前操作完成后才开始， 并且会在该流中的任何后续操作开始前完成。

cudaError_t cudaMemPrefetchAsync(const void *devPtr,
                                 size_t count,
                                 struct cudaMemLocation location,
                                 unsigned int flags,
                                 cudaStream_t stream=0);

当预取任务在给定 stream 中执行时，包含 [devPtr, devPtr + count) 的内存区域可能会被迁移： 如果 location.type 为 cudaMemLocationTypeDevice，则迁移到目标设备 location.id；如果 location.type 为 cudaMemLocationTypeHost，则迁移到 CPU。有关 flags 的详细信息，请参阅当前 CUDA 运行时 API 文档。

考虑下面的简单代码示例：

void test_prefetch_sam(const cudaStream_t& s) {
  // 初始化 CPU 上的数据
  char *data = (char*)malloc(dataSizeBytes);
  init_data(data, dataSizeBytes);                                     
  cudaMemLocation location = {.type = cudaMemLocationTypeDevice, .id = myGpuId};

  // 鼓励数据在使用前转移到 GPU
  const unsigned int flags = 0;
  cudaMemPrefetchAsync(data, dataSizeBytes, location, flags, s);      

  // 使用 GPU 上的数据
  const unsigned num_blocks = (dataSizeBytes + threadsPerBlock - 1) / threadsPerBlock;
  mykernel<<<num_blocks, threadsPerBlock, 0, s>>>(data, dataSizeBytes);  

  // 鼓励数据移回 CPU
  location = {.type = cudaMemLocationTypeHost};
  cudaMemPrefetchAsync(data, dataSizeBytes, location, flags, s);      
  
  cudaStreamSynchronize(s);

  // 使用 CPU 上的数据
  use_data(data, dataSizeBytes);                                      
  free(data);
}

void test_prefetch_managed(const cudaStream_t& s) {
  // 初始化 CPU 上的数据
  char *data;
  cudaMallocManaged(&data, dataSizeBytes);
  init_data(data, dataSizeBytes);                                     
  cudaMemLocation location = {.type = cudaMemLocationTypeDevice, .id = myGpuId};

  // 鼓励数据在使用前转移到 GPU

4.1.4.3. 内存丢弃#

cudaMemDiscardBatchAsync API 允许应用程序通知 CUDA 运行时：指定内存范围中的内容已经不再有用。统一内存驱动程序会执行自动内存传输，以通过基于错误的迁移或内存逐出支持设备内存超额订阅。 这些自动内存传输有时可能是冗余的，从而严重降低性能。 把某个地址范围标记为“丢弃”会通知统一内存驱动程序：应用程序已经消费了该范围内的内容，在预取或为其他分配腾出空间而逐出页面时，无需再迁移这些数据。读取被丢弃的页面，且之后没有写入访问或预取，会得到不确定的值。丢弃操作之后的任何新写入，都保证可被后续读取访问看到。对正在丢弃的地址范围进行并发访问或预取会导致未定义行为。

cudaError_t cudaMemDiscardBatchAsync(void **dptrs,
                                    size_t *sizes,
                                    size_t count,
                                    unsigned long long flags,
                                    cudaStream_t stream);

该函数会对 dptrs 和 sizes 数组指定的地址范围执行一批内存丢弃操作。 两个数组的长度都必须等于 count。每个内存范围都必须引用 通过 cudaMallocManaged 分配的托管内存，或通过 __managed__ 声明的变量。

cudaMemDiscardAndPrefetchBatchAsync API 结合了丢弃和预取操作。调用 cudaMemDiscardAndPrefetchBatchAsync 在语义上等同于先调用 cudaMemDiscardBatchAsync 再调用 cudaMemPrefetchBatchAsync，但实现更优化。当应用程序需要内存位于目标位置、但不需要保留内存内容时，这很有用。

cudaError_t cudaMemDiscardAndPrefetchBatchAsync(void **dptrs,
                                               size_t *sizes,
                                               size_t count,
                                               struct cudaMemLocation *prefetchLocs,
                                               size_t *prefetchLocIdxs,
                                               size_t numPrefetchLocs,
                                               unsigned long long flags,
                                               cudaStream_t stream);

prefetchLocs 数组指定预取目标位置，而 prefetchLocIdxs 指示每个预取位置适用于哪些操作。例如，如果一个批次有 10 个操作， 前 6 个应预取到一个位置，其余 4 个应预取到另一个位置，那么 numPrefetchLocs 将为 2，prefetchLocIdxs 将为 {0, 6}，prefetchLocs 则会 包含两个目标位置。

重要考虑因素：

  • 在没有后续写入或预取的情况下读取被丢弃的范围，会返回不确定的值。

  • 可以通过写入该范围，或通过 cudaMemPrefetchAsync 预取该范围，来撤销丢弃操作。

  • 任何与丢弃操作同时发生的读取、写入或预取，都会导致未定义行为。

  • 所有设备的 cudaDevAttrConcurrentManagedAccess 值都必须非零。

4.1.4.4. 查询托管内存数据使用属性#

程序可以使用以下 API，查询通过 cudaMemAdvise 或 cudaMemPrefetchAsync 分配给 CUDA 托管内存的内存范围属性：

cudaMemRangeGetAttribute(void *data,
                         size_t dataSize,
                         enum cudaMemRangeAttribute attribute,
                         const void *devPtr,
                         size_t count);

该函数查询从 devPtr 开始、大小为 count 字节的内存范围属性。 该内存范围必须引用通过 cudaMallocManaged 分配的托管内存，或 通过 __managed__ 声明的变量。可以查询以下属性：

  • cudaMemRangeAttributeReadMostly：如果整个内存范围都设置了 cudaMemAdviseSetReadMostly 属性，则返回 1；否则返回 0。

  • cudaMemRangeAttributePreferredLocation：如果整个内存范围都把相应处理器作为首选位置，返回结果将是 GPU 设备 ID 或 cudaCpuDeviceId；否则返回 cudaInvalidDeviceId。 应用程序可以使用此查询 API，根据托管指针的首选位置属性来决定通过 CPU 还是 GPU 暂存数据。 请注意，查询时内存范围的实际位置可能与首选位置不同。

  • cudaMemRangeAttributeAccessedBy：返回为该内存范围设置了访问建议的设备列表。

  • cudaMemRangeAttributeLastPrefetchLocation：返回该内存范围通过 cudaMemPrefetchAsync 显式预取到的最后一个位置。请注意，这只表示应用程序请求把该内存范围预取到的最后一个位置，并不说明到该位置的预取操作是否已完成，甚至是否已经开始。

  • cudaMemRangeAttributePreferredLocationType：返回首选位置的位置类型，取值如下：

    • cudaMemLocationTypeDevice：内存范围内所有页面都把同一个 GPU 作为首选位置；

    • cudaMemLocationTypeHost：内存范围内所有页面都把 CPU 作为首选位置；

    • cudaMemLocationTypeHostNuma：内存范围内所有页面都把同一个主机 NUMA 节点 ID 作为首选位置；

    • cudaMemLocationTypeInvalid：所有页面没有相同的首选位置，或某些页面根本没有首选位置。

  • cudaMemRangeAttributePreferredLocationId：如果针对相同地址范围查询 cudaMemRangeAttributePreferredLocationType 返回 cudaMemLocationTypeDevice，则返回设备序号。如果首选位置类型是主机 NUMA 节点，则返回主机 NUMA 节点 ID。否则，应忽略该 ID。

  • cudaMemRangeAttributeLastPrefetchLocationType：返回内存范围中所有页面通过 cudaMemPrefetchAsync 显式预取到的最后一个位置类型。返回以下值：

    • cudaMemLocationTypeDevice：内存范围内所有页面都预取到同一个 GPU；

    • cudaMemLocationTypeHost：内存范围内所有页面都预取到 CPU；

    • cudaMemLocationTypeHostNuma：内存范围内所有页面都预取到同一个主机 NUMA 节点 ID；

    • cudaMemLocationTypeInvalid：所有页面并未预取到同一位置，或某些页面根本没有预取。

  • cudaMemRangeAttributeLastPrefetchLocationId：如果针对相同地址范围查询 cudaMemRangeAttributeLastPrefetchLocationType 返回 cudaMemLocationTypeDevice，则它是有效的设备序号；如果返回 cudaMemLocationTypeHostNuma，则它是有效的主机 NUMA 节点 ID。否则，应忽略该 ID。

此外，也可以使用对应的 cudaMemRangeGetAttributes 函数一次查询多个属性。

4.1.4.5. GPU 内存超额订阅#

统一内存允许应用程序 oversubscribe 任何单个处理器的内存： 换言之，应用程序可以分配并共享大于系统中任何单个处理器内存容量的数组， 从而支持处理无法放入单个 GPU 的数据集等核外处理场景， 同时不会显著增加编程模型复杂度。

此外，也可以使用对应的 cudaMemRangeGetAttributes 函数一次查询多个属性。
