4.3. 流有序内存分配器#

4.3.1. 引言#

使用管理内存分配 cudaMalloc 或 cudaFree 导致GPU 同步所有正在执行的 CUDA 流。流序内存 分配器使应用程序能够排序内存分配和释放 与启动到 CUDA 流中的其他工作一起使用，例如内核启动和 异步副本。这通过利用 流排序语义以重用内存分配。分配器还 允许应用程序控制分配器的内存缓存行为。当 设置适当的释放阈值，缓存行为允许 分配器以避免在应用程序指示时对操作系统进行昂贵的调用 它愿意接受更大的内存占用。分配器还支持 进程之间轻松安全的分配共享。

流排序内存分配器：

  • 减少了对自定义内存管理抽象的需求，并使其 更轻松地创建高性能自定义内存管理 需要它的应用程序。

  • 使多个库能够共享由管理的公共内存池 司机。这可以减少过多的内存消耗。

  • 允许驾驶员根据其对情况的认识来执行优化 分配器和其他流管理 API。

注

Nsight Compute 和下一代 CUDA 调试器可以识别分配器 从 CUDA 11.3 开始。

4.3.2. 内存管理#

cudaMallocAsync 或 cudaFreeAsync 是启用流排序内存管理的 API。 cudaMallocAsync 返回分配并 cudaFreeAsync 释放一个 分配。两个 API 都接受流参数来定义何时分配 将变得可用并停止可用。 这些函数允许将内存操作绑定到特定的 CUDA 流， 使它们能够在不阻塞主机或其他设备的情况下发生 流。 可以通过避免潜在的问题来提高应用程序性能 昂贵的同步 cudaMalloc 或 cudaFree.

这些 API 可用于进一步的性能优化 内存池，管理和重用大内存块以提高效率 分配和解除分配。内存池有助于减少开销并防止 碎片化，提高内存频繁场景下的性能 分配操作。

4.3.2.1. 分配内存#

cudaMallocAsync 函数触发异步内存分配 GPU，链接到特定的 CUDA 流。 cudaMallocAsync 允许内存 分配发生而不妨碍主机或其他 流，消除了昂贵的同步的需要。

注

cudaMallocAsync 确定位置时忽略当前设备/上下文 分配将驻留。相反， cudaMallocAsync 决定了 基于指定的内存池或提供的流的适当设备。

下面的列表说明了一个基本的使用模式：内存是 分配、使用，然后释放回同一个流中。

void *ptr;
size_t size = 512;
cudaMallocAsync(&ptr, size, cudaStreamPerThread);
// 使用分配进行工作
kernel<<<..., cudaStreamPerThread>>>(ptr, ...);
// 可以在不同步cpu和GPU的情况下指定异步free
cudaFreeAsync(ptr, cudaStreamPerThread);

注

当从进行分配的流以外的流访问分配时， 用户必须保证访问发生在分配之后 操作，否则行为未定义。

4.3.2.2. 释放内存#

cudaFreeAsync() 以流顺序异步释放设备内存 时尚，意味着内存释放被分配给特定的 CUDA 流 并且不会阻塞主机或其他流。

用户必须保证分配后发生空闲操作 操作和分配的任何用途。任何分配的使用 自由操作开始后会导致未定义的行为。

应使用事件和/或流同步操作来保证任何 在释放操作之前完成对其他流的分配的访问 开始，如以下示例所示。

cudaMallocAsync(&ptr, size, stream1);
cudaEventRecord(event1, stream1);
// Stream2 必须等待分配准备好才能访问
cudaStreamWaitEvent(stream2, event1);
kernel<<<..., stream2>>>(ptr, ...);
cudaEventRecord(event2, stream2);
// Stream3 必须等待 Stream2 完成对分配的访问
// 释放分配
cudaStreamWaitEvent(stream3, event2);
cudaFreeAsync(ptr, stream3);

内存分配为 cudaMalloc() 可以通过 with 释放 cudaFreeAsync()。如上所述，所有对内存的访问都必须是 在自由操作开始之前完成。

cudaMalloc(&ptr, size);
kernel<<<..., stream>>>(ptr, ...);
cudaFreeAsync(ptr, stream);

同样，分配的内存 cudaMallocAsync 可以通过释放 cudaFree()。当通过释放此类分配时 cudaFree() 应用程序编程接口， 驱动程序假定对分配的所有访问均已完成并且 不执行进一步的同步。用户可以使用 cudaStreamQuery / cudaStreamSynchronize / cudaEventQuery / cudaEventSynchronize / cudaDeviceSynchronize 以保证适当的异步工作 已完成并且 GPU 不会尝试访问该分配。

cudaMallocAsync(&ptr, size,stream);
kernel<<<..., stream>>>(ptr, ...);
// 需要同步以避免过早释放内存
cudaStreamSynchronize(stream);
cudaFree(ptr);

4.3.3. 内存池#

内存池封装了虚拟地址和物理内存资源， 根据池属性和特性进行分配和管理。 内存池的主要方面是内存的类型和位置 管理。

所有来电 cudaMallocAsync 使用内存池中的资源。如果 未指定内存池， cudaMallocAsync 使用当前的 提供的流设备的内存池。当前内存池为 设备可以设置为 cudaDeviceSetMempool 并查询 cudaDeviceGetMempool。每个设备都有一个默认的内存池，即 活跃如果 cudaDeviceSetMempool 还没有被调用。

应用程序编程接口 cudaMallocFromPoolAsync 和 C++ 重载 cudaMalloc异步 允许用户指定用于分配的池而无需设置 将其作为当前池。 API cudaDeviceGetDefaultMempool 或 cudaMemPoolCreate 返回内存池的句柄。 cudaMemPoolSetAttribute cudaMemPoolGetAttribute 控制内存池的属性。

注

设备当前的内存池将是该设备的本地内存池。所以分配 不指定内存池将始终产生本地分配 流的设备。

4.3.3.1. 默认/隐式池#

可以通过调用来检索设备的默认内存池 cudaDeviceGetDefaultMempool。从默认内存池分配 设备的分配是位于该设备上的不可迁移设备分配。这些 分配始终可以从该设备访问。的可达性 可以修改默认内存池 cudaMemPoolSetAccess 和 查询与 cudaMemPoolGetAccess。由于默认池不需要 由于显式创建，它们有时被称为隐式池。的 设备默认内存池不支持IPC。

4.3.3.2. 显式池#

cudaMemPoolCreate 创建一个显式池。这允许 应用程序请求超出其分配范围的属性 由默认/隐式池提供。其中包括 IPC 等属性 能力、最大池大小、驻留在特定 CPU NUMA 上的分配 支持的平台上的节点等。

// 在设备 0 上创建一个类似于隐式池的池

cudaMemPoolProps poolProps = { };
poolProps.allocType = cudaMemAllocationTypePinned;
poolProps.location.id = device;
poolProps.location.type = cudaMemLocationTypeDevice;

cudaMemPoolCreate(&memPool, &poolProps));

以下代码片段说明了创建具有 IPC 功能的示例 有效 CPU NUMA 节点上的内存池。

// 创建一个驻留在能够进行 IPC 共享（通过文件描述符）的 CPU NUMA 节点上的池。
int cpu_numa_id = 0;
cudaMemPoolProps poolProps = { };
poolProps.allocType = cudaMemAllocationTypePinned;
poolProps.location.id = cpu_numa_id;

cudaMemPoolCreate(&ipcMemPool, &poolProps));

4.3.3.3. 多 GPU 支持的设备可访问性#

就像通过虚拟内存控制的分配可访问性一样 管理 API，内存池分配可访问性不遵循 cudaDeviceEnablePeerAccess 或 cuCtxEnablePeerAccess。对于内存池，API cudaMemPoolSetAccess 修改哪些设备可以访问分配 池。默认情况下，只能从分配的设备访问分配 分配位于。此访问权限无法撤销。要启用来自以下位置的访问： 其他设备，访问设备必须与内存具有对等能力 池的设备。这可以通过以下方式验证 cudaDeviceCanAccessPeer。如果对等能力 未选中，设置访问可能会失败 cudaErrorInvalidDevice。然而，如果没有 已从资金池中进行了拨款， cudaMemPoolSetAccess 打电话可能 即使设备不具备对等能力，也能成功。在这种情况下，下一步 从池中分配将失败。

值得注意的是 cudaMemPoolSetAccess 影响所有分配 内存池，而不仅仅是未来的内存池。同样，报告的可访问性 cudaMemPoolGetAccess 适用于池中的所有分配，而不仅仅是 未来的。更改池的辅助功能设置 不建议频繁使用 GPU。也就是说，一旦可以从 给定 GPU，它应该在该 GPU 的生命周期内保持可访问性 池。

// 显示 cudaMemPoolSetAccess 用法的片段：
cudaError_t setAccessOnDevice(cudaMemPool_t memPool, int residentDevice,
              int accessingDevice) {
    cudaMemAccessDesc accessDesc = {};
    accessDesc.location.type = cudaMemLocationTypeDevice;
    accessDesc.location.id = accessingDevice;
    accessDesc.flags = cudaMemAccessFlagsProtReadWrite;

    int canAccess = 0;
    cudaError_t error = cudaDeviceCanAccessPeer(&canAccess, accessingDevice,
              residentDevice);
    if (error != cudaSuccess) {
        return error;
    } else if (canAccess == 0) {
        return cudaErrorPeerAccessUnsupported;
    }

    // 使地址可访问
    return cudaMemPoolSetAccess(memPool, &accessDesc, 1);
}

4.3.3.4. 为 IPC 启用内存池#

可以启用内存池进行进程间通信 (IPC) 允许轻松、高效且安全地共享 GPU 进程之间的内存。 CUDA 的 IPC 内存池提供相同的安全性 CUDA 的优势 虚拟内存管理 API.

使用内存池在进程之间共享内存有两个步骤： 进程首先需要共享对池的访问，然后共享特定的 从该池中分配。第一步建立并加强安全性。 第二步协调每个进程使用什么虚拟地址 以及何时映射需要在导入过程中有效。

4.3.3.4.1. 创建和共享IPC内存池#

共享对池的访问涉及检索池的操作系统本机句柄 与 cudaMemPoolExportToShareableHandle()，转移 使用操作系统本机 IPC 机制处理导入过程，然后 创建一个导入的内存池 cudaMemPoolImportFromShareableHandle() API。对于 cudaMemPoolExportToShareableHandle 要成功，内存池必须是 使用池属性中指定的请求句柄类型创建 结构。

请参考 samples 适当的 IPC 机制 在进程之间传输操作系统本机句柄。其余程序可以 可以在下面的代码片段中找到。

// 在出口过程中
// 在设备 0 上创建可导出的 IPC 功能池

poolProps.location.id = 0;
poolProps.location.type = cudaMemLocationTypeDevice;

// 将 handleTypes 设置为非零值将使池可导出（支持 IPC）
poolProps.handleTypes = CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR;

cudaMemPoolCreate(&memPool, &poolProps));

// 基于 FD 的句柄是整数类型
int fdHandle = 0;


// 检索池的操作系统本机句柄。
// 注意这里传入的是一个指向句柄内存的指针。
cudaMemPoolExportToShareableHandle(&fdHandle,
             memPool,
             CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR,
             0);

// 必须使用适当的处理将句柄发送到导入进程
// 特定于操作系统的 API。

// 导入过程中
 int fdHandle;
// 需要使用以下命令从导出过程中检索句柄
// 适当的特定于操作系统的 API。
// 从可共享句柄创建导入池。
// 请注意，此处句柄是按值传递的。
cudaMemPoolImportFromShareableHandle(&importedMemPool,
          (void*)fdHandle,
          CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR,
          0);

4.3.3.4.2. 在导入过程中设置访问权限#

导入的内存池最初只能从其驻留内存池访问 设备。导入的内存池不会继承任何由内存池设置的可访问性 导出过程。导入过程需要启用访问 cudaMemPoolSetAccess 从任何它计划访问内存的 GPU。

如果导入的内存池属于导入不可见的设备 过程中，用户必须使用 cudaMemPoolSetAccess 用于启用访问的 API 来自将使用分配的 GPU。 （参见 多 GPU 支持的设备可访问性)

4.3.3.4.3. 从导出的池创建和共享分配#

一旦池被共享，分配就用 cudaMallocAsync() 导出进程中的池中的内容可以与以下进程共享 已导入池。由于矿池的安全策略已经建立并且 在池级别进行验证，操作系统不需要额外的簿记来提供 特定池分配的安全性。换句话说，不透明的 cudaMemPoolPtrExportData 可能会发送导入池分配所需的信息 使用任何机制进行导入过程。

虽然可以在不同步的情况下导出和导入分配 以任何方式分配流，导入过程必须遵循相同的 规则作为访问分配时的导出过程。具体来说，访问 分配必须在分配之后发生 分配流中的操作执行。下面的两个代码片段显示 cudaMemPoolExportPointer() 或 cudaMemPoolImportPointer() 分享 带有 IPC 事件的分配用于保证分配不会 在分配准备好之前在导入过程中访问。

// 在出口过程中准备分配
cudaMemPoolPtrExportData exportData;
cudaEvent_t readyIpcEvent;
cudaIpcEventHandle_t readyIpcEventHandle;

// 用于协调进程之间的 ipc 事件
// cudaEventInterprocess 标志使事件成为 ipc 事件
// cudaEventDisableTiming 出于性能原因而设置

cudaEventCreate(&readyIpcEvent, cudaEventDisableTiming | cudaEventInterprocess)

// 从导出内存池分配
cudaMallocAsync(&ptr, size,exportMemPool, stream);

// 分配准备就绪时共享的事件。
cudaEventRecord(readyIpcEvent, stream);
cudaMemPoolExportPointer(&exportData, ptr);
cudaIpcGetEventHandle(&readyIpcEventHandle, readyIpcEvent);

// 使用以下命令与导入进程共享 IPC 事件和指针导出数据
// 任何机制。这里我们将数据复制到共享内存中
shmem->ptrData = exportData;
shmem->readyIpcEventHandle = readyIpcEventHandle;
// 向消费者发出数据准备就绪的信号

// 导入分配
cudaMemPoolPtrExportData *importData = &shmem->prtData;
cudaEvent_t readyIpcEvent;
cudaIpcEventHandle_t *readyIpcEventHandle = &shmem->readyIpcEventHandle;

// 需要从以下位置检索 ipc 事件句柄和导出数据
// 使用任何机制的导出过程。  这里我们使用 shmem 并且只是
// 需要同步以确保共享内存已填充。

cudaIpcOpenEventHandle(&readyIpcEvent, readyIpcEventHandle);

// 导入分配。该操作不会在分配准备就绪时阻塞。
cudaMemPoolImportPointer(&ptr, importedMemPool, importData);

// 等待分配流中先前的流操作完成之前
// 在导入过程中使用分配。
cudaStreamWaitEvent(stream, readyIpcEvent);
kernel<<<..., stream>>>(ptr, ...);

释放分配时，必须在导入时释放分配 在导出过程中释放之前进行处理。下面的代码 代码片段演示了如何使用 CUDA IPC 事件来提供所需的 之间的同步 cudaFreeAsync 两个进程中的操作。 从导入过程获取分配显然受到以下限制 进口流程端自由操作。值得注意的是 cudaFree 可用于释放两个进程中的分配，并且 可以使用其他流同步 API 来代替 CUDA IPC 事件。

// 释放必须在导入过程中发生在导出过程之前
kernel<<<..., stream>>>(ptr, ...);

// 导入过程中的最后一次访问
cudaFreeAsync(ptr, stream);

// 免费后导入过程中不允许访问
cudaIpcEventRecord(finishedIpcEvent, stream);

// 出口流程
// 导出过程需要将其自由度与流顺序协调
// 导入过程是免费的。
cudaStreamWaitEvent(stream, finishedIpcEvent);
kernel<<<..., stream>>>(ptrInExportingProcess, ...);

// 导入过程中的免费并不会停止导出过程
// 使用分配。
cudFreeAsync(ptrInExportingProcess,stream);

4.3.4. 最佳实践和调整#

4.3.4.1. 查询支持#

应用程序可以确定设备是否支持流排序 通过调用内存分配器 cudaDeviceGetAttribute() （见 开发者博客） 与设备属性 cudaDevAttrMemoryPoolsSupported.

IPC内存池支持可以通过以下命令查询 cudaDevAttrMemoryPoolSupportedHandleTypes 设备属性。该属性已添加 在 CUDA 11.3 中，老司机将回归 cudaErrorInvalidValue 当这个属性 被查询。

int driverVersion = 0;
int deviceSupportsMemoryPools = 0;
int poolSupportedHandleTypes = 0;
cudaDriverGetVersion(&driverVersion);
if (driverVersion >= 11020) {
    cudaDeviceGetAttribute(&deviceSupportsMemoryPools,
                           cudaDevAttrMemoryPoolsSupported, device);
}
if (deviceSupportsMemoryPools != 0) {
    // `device` 支持流排序内存分配器
}

if (driverVersion >= 11030) {
    cudaDeviceGetAttribute(&poolSupportedHandleTypes,
              cudaDevAttrMemoryPoolSupportedHandleTypes, device);
}
if (poolSupportedHandleTypes & cudaMemHandleTypePosixFileDescriptor) {
   // 指定设备上的池可以使用基于 posix 文件描述符的 IPC 创建
}

在查询之前执行驱动程序版本检查可以避免遇到问题 cudaErrorInvalidValue 尚未提供该属性的驱动程序上出现错误 定义的。一个可以用 cudaGetLastError 清除错误而不是 避免它。

4.3.4.2. 物理页面缓存行为#

默认情况下，分配器尝试最小化分配器拥有的物理内存。 池。为了最大限度地减少分配和释放物理内存的操作系统调用， 应用程序必须为每个池配置内存占用量。应用程序可以 使用释放阈值属性执行此操作 （cudaMemPoolAttrReleaseThreshold).

释放阈值是池应保留的内存量（以字节为单位） 在尝试将内存释放回操作系统之前。当超过释放 内存池持有的内存阈值字节，分配器将尝试 在下次调用流、事件或设备时将内存释放回操作系统 同步。将释放阈值设置为 UINT64_MAX 将防止 驱动程序在每次同步后尝试收缩池。

Cuuint64_t setVal = UINT64_MAX;
cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrReleaseThreshold, &setVal);

设置的应用程序 cudaMemPoolAttrReleaseThreshold 足够高到 有效禁用内存池收缩可能希望显式收缩 内存池的内存占用。 cudaMemPoolTrimTo 允许应用程序 这样做。当修剪内存池的占用空间时， minBytesToKeep 参数允许应用程序保留指定数量的内存， 例如，在后续执行阶段预计需要的金额。

Cuuint64_t setVal = UINT64_MAX;
cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrReleaseThreshold, &setVal);

// 应用程序阶段需要来自流排序分配器的大量内存
for (i=0; i<10; i++) {
    for (j=0; j<10; j++) {
        cudaMallocAsync(&ptrs[j],size[j], stream);
    }
    kernel<<<...,stream>>>(ptrs,...);
    for (j=0; j<10; j++) {
        cudaFreeAsync(ptrs[j], stream);
    }
}

// 进程不需要为下一阶段提供那么多内存。
// 同步，以便修剪操作知道分配没有
// 使用时间更长。
cudaStreamSynchronize(stream);
cudaMemPoolTrimTo(mempool, 0);

// 其他一些进程/分配机制现在可以使用物理内存
// 由修剪操作释放。

4.3.4.3. 资源使用统计#

查询 cudaMemPoolAttrReservedMemCurrent 池报告的属性 池当前消耗的总物理 GPU 内存。查询 cudaMemPoolAttrUsedMemCurrent 池的返回所有池的总大小 从池中分配且不可重用的内存。

cudaMemPoolAttr*MemHigh 属性记录相应 cudaMemPoolAttr*MemCurrent 属性自上次重置以来达到的最大高水位值。 可以使用 cudaMemPoolSetAttribute API 将这些值重置为当前值。

// 用于批量获取使用情况统计信息的示例辅助函数
struct usageStatistics {
    cuuint64_t reserved;
    cuuint64_t reservedHigh;
    cuuint64_t used;
    cuuint64_t usedHigh;
};

void getUsageStatistics(cudaMemoryPool_t memPool, struct usageStatistics *statistics)
{
    cudaMemPoolGetAttribute(memPool, cudaMemPoolAttrReservedMemCurrent, statistics->reserved);
    cudaMemPoolGetAttribute(memPool, cudaMemPoolAttrReservedMemHigh, statistics->reservedHigh);
    cudaMemPoolGetAttribute(memPool, cudaMemPoolAttrUsedMemCurrent, statistics->used);
    cudaMemPoolGetAttribute(memPool, cudaMemPoolAttrUsedMemHigh, statistics->usedHigh);
}


// 重置水印将使它们呈现当前值。
void resetStatistics(cudaMemoryPool_t memPool)
{
    cuuint64_t value = 0;
    cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrReservedMemHigh, &value);
    cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrUsedMemHigh, &value);
}

4.3.4.4. 内存重用策略#

为了服务分配请求，驱动程序尝试重用内存 之前通过释放 cudaFreeAsync() 在尝试之前 从操作系统分配更多内存。例如，流中释放的内存可以 立即在同一流上的后续分配请求中重用。 当流与 CPU 同步时，所占用的内存 先前在该流中释放的内容可重新用于分配 在任何流中。 重用策略可以应用于默认内存池和显式内存池。

流排序分配器有一些可控的分配策略。的 池属性 cudaMemPoolReuseFollowEventDependencies, cudaMemPoolReuseAllowOpportunistic, 和 cudaMemPoolReuseAllowInternalDependencies 控制这些政策，详情如下。 这些策略可以通过调用来启用或禁用 cudaMemPoolSetAttribute。 升级到较新的 CUDA 驱动程序可能会更改、增强、增强和/或重新排序 重用策略的枚举。

4.3.4.4.1. cudaMemPoolReuseFollowEventDependencies#

在分配更多物理 GPU 内存之前，分配器会检查依赖关系 由 CUDA 事件建立的信息并尝试从释放的内存中分配 在另一个流中。

cudaMallocAsync(&ptr, size, originalStream);
kernel<<<..., originalStream>>>(ptr, ...);
cudaFreeAsync(ptr, originalStream);
cudaEventRecord(event,originalStream);

// 等待捕获另一个流中的空闲事件
// 允许分配器重用内存以满足
// 另一个流中的新分配请求时
// cudaMemPoolReuseFollowEventDependency 已启用。
cudaStreamWaitEvent(otherStream, event);
cudaMallocAsync(&ptr2, size, otherStream);

4.3.4.4.2. cudaMemPoolReuseAllowOpportunistic#

当 cudaMemPoolReuseAllowOpportunistic 策略已启用，分配器 检查释放的分配以查看自由操作流顺序语义是否已被 满足，例如流已经通过了由 自由操作。当禁用此策略时，分配器仍将重用分配的内存 当流与 CPU 同步时可用。禁用此策略 并没有停止 cudaMemPoolReuseFollowEventDependencies 从申请。

cudaMallocAsync(&ptr, size, originalStream);
kernel<<<..., originalStream>>>(ptr, ...);
cudaFreeAsync(ptr, originalStream);


// 一段时间后，内核完成运行
wait(10);

// 当启用 cudaMemPoolReuseAllowOpportunistic 时，此分配请求
// 可以根据originalStream的进度提前分配来完成。
cudaMallocAsync(&ptr2, size, otherStream);

4.3.4.4.3. cudaMemPoolReuseAllowInternalDependencies#

如果无法从操作系统分配和映射更多物理内存，驱动程序将 查找其可用性取决于另一个流的待处理内存 进步。如果找到这样的内存，驱动程序将插入所需的内存 依赖于分配流并重用内存。

cudaMallocAsync(&ptr, size, originalStream);
kernel<<<..., originalStream>>>(ptr, ...);
cudaFreeAsync(ptr, originalStream);

// 当启用 cudaMemPoolReuseAllowInternalDependencies 时
// 并且驱动程序无法分配更多物理内存，驱动程序可能会
// 在分配流中有效执行 cudaStreamWaitEvent
// 确保‘otherStream’中的未来工作发生在工作之后
// 在原始流中将被允许访问原始分配。
cudaMallocAsync(&ptr2, size, otherStream);

4.3.4.4.4. 禁用重用策略#

虽然可控重用策略可以提高内存重用，但用户可能希望 禁用它们。允许机会性重用（例如 cudaMemPoolReuseAllowOpportunistic) 引入了运行间方差 基于 CPU 和 GPU 执行交错的分配模式。 内部依赖插入（例如 cudaMemPoolReuseAllowInternalDependencies) 可以将工作序列化 当用户愿意时，意外且可能不确定的方式 在分配失败时显式同步事件或流。

4.3.4.5. 同步 API 操作#

分配器作为 CUDA 的一部分带来的优化之一 驱动程序与同步 API 集成。当用户请求时 CUDA驱动程序同步，驱动程序等待异步工作 完成。返回之前，驾驶员将确定什么可以释放 同步保证完成。这些分配是 无论指定流或禁用分配如何，都可用于分配 政策。司机还检查 cudaMemPoolAttrReleaseThreshold 这里和 尽可能释放任何多余的物理内存。

4.3.5. 补充说明#

4.3.5.1. cudaMemcpyAsync 当前上下文/设备敏感度#

在当前的 CUDA 驱动程序中，任何异步 memcpy 涉及内存 cudaMallocAsync 应该使用指定流的上下文作为 调用线程的当前上下文。这对于以下情况来说是不必要的： cudaMemcpyPeerAsync，作为 API 中指定的设备主要上下文 被引用而不是当前上下文。

4.3.5.2. cudaPointerGetAttributes 查询#

Invoking cudaPointerGetAttributes 调用后的分配 cudaFreeAsync 它会导致未定义的行为。具体来说，它确实 如果仍然可以从给定流访问分配并不重要： 行为仍然未定义。

4.3.5.3. cudaGraphAddMemsetNode#

cudaGraphAddMemsetNode 不适用于通过流分配的内存 有序分配器。然而，分配的内存集可以被流捕获。

4.3.5.4. 指针属性#

cudaPointerGetAttributes 查询适用于流排序分配。 由于流排序分配与上下文无关，因此查询 CU_POINTER_ATTRIBUTE_CONTEXT 将成功但返回 NULL *data。 属性 CU_POINTER_ATTRIBUTE_DEVICE_ORDINAL 可以用来确定 分配的位置：这在选择上下文时很有用 用于制作 p2h2p 副本 cudaMemcpyPeerAsync。属性 CU_POINTER_ATTRIBUTE_MEMPOOL_HANDLE 已在 CUDA 11.3 中添加，可以 对于调试和确认分配来自哪个池很有用 在做IPC之前。

4.3.5.5. CPU虚拟内存#

使用 CUDA 流排序内存分配器 API 时，请避免使用“ulimit -v”设置 VRAM 限制，因为不支持此设置。
