4.3. 流有序内存分配器#

4.3.1. 引言#

使用 cudaMalloc 和 cudaFree 管理内存分配会导致 GPU 在所有正在执行的 CUDA 流之间进行同步。流有序内存分配器允许应用程序把内存分配和释放与启动到 CUDA 流中的其他工作排序在一起，例如内核启动和异步拷贝。这样可以利用流有序语义重用内存分配，从而改善应用程序的内存使用情况。分配器还允许应用程序控制内存缓存行为；设置合适的释放阈值后，如果应用程序表示可以接受更大的内存占用，分配器就可以避免对操作系统发起代价较高的调用。该分配器还支持在进程之间方便而安全地共享分配。

流有序内存分配器：

  • 减少对自定义内存管理抽象的需求，并让确实需要这类抽象的应用程序更容易构建高性能的自定义内存管理。

  • 允许多个库共享由驱动程序管理的公共内存池，从而减少多余的内存消耗。

  • 允许驱动程序基于对分配器和其他流管理 API 的了解来执行优化。

注

从 CUDA 11.3 开始，Nsight Compute 和下一代 CUDA 调试器可以识别该分配器。

4.3.2. 内存管理#

cudaMallocAsync 和 cudaFreeAsync 是启用流有序内存管理的 API。cudaMallocAsync 返回一段分配，cudaFreeAsync 释放一段分配。这两个 API 都接受流参数，用于定义该分配何时变为可用、何时停止可用。这些函数允许把内存操作绑定到特定 CUDA 流中，使其能够在不阻塞主机或其他流的情况下发生。通过避免 cudaMalloc 和 cudaFree 可能带来的高成本同步，应用程序性能可以得到提升。

这些 API 还可以结合内存池进一步优化性能。内存池会管理并重用大块内存，让分配和释放更高效。内存池有助于降低开销并避免碎片化，从而提升频繁执行内存分配操作场景中的性能。

4.3.2.1. 分配内存#

cudaMallocAsync 函数会在 GPU 上触发异步内存分配，并将该分配关联到特定 CUDA 流。cudaMallocAsync 允许内存分配在不阻塞主机或其他流的情况下发生，从而消除高成本同步的需要。

注

cudaMallocAsync 在确定分配驻留位置时会忽略当前设备/上下文。它会根据指定的内存池或传入的流来确定合适的设备。

下面的代码展示了一种基本用法：先分配内存，随后使用这段内存，最后在同一个流中释放它。

void *ptr;
size_t size = 512;
cudaMallocAsync(&ptr, size, cudaStreamPerThread);
// 使用这段分配执行工作
kernel<<<..., cudaStreamPerThread>>>(ptr, ...);
// 可以在不同步 CPU 和 GPU 的情况下指定异步释放
cudaFreeAsync(ptr, cudaStreamPerThread);

注

如果从执行分配的流之外的其他流访问该分配，用户必须保证访问发生在分配操作之后，否则行为未定义。

4.3.2.2. 释放内存#

cudaFreeAsync() 会以流有序方式异步释放设备内存。这意味着内存释放被分配到特定 CUDA 流中，并且不会阻塞主机或其他流。

用户必须保证释放操作发生在分配操作以及该分配的所有使用之后。如果在释放操作开始后继续使用该分配，会导致未定义行为。

应使用事件和/或流同步操作来保证来自其他流的任何分配访问都在释放操作开始之前完成，如下面的示例所示。

cudaMallocAsync(&ptr, size, stream1);
cudaEventRecord(event1, stream1);
// stream2 必须等待分配准备好后才能访问
cudaStreamWaitEvent(stream2, event1);
kernel<<<..., stream2>>>(ptr, ...);
cudaEventRecord(event2, stream2);
// stream3 必须等待 stream2 完成对该分配的访问后
// 才能释放该分配
cudaStreamWaitEvent(stream3, event2);
cudaFreeAsync(ptr, stream3);

使用 cudaMalloc() 分配的内存可以通过 cudaFreeAsync() 释放。和上文一样，对这段内存的所有访问都必须在释放操作开始之前完成。

cudaMalloc(&ptr, size);
kernel<<<..., stream>>>(ptr, ...);
cudaFreeAsync(ptr, stream);

类似地，使用 cudaMallocAsync 分配的内存也可以通过 cudaFree() 释放。当通过 cudaFree() API 释放这类分配时，驱动程序会假定对该分配的所有访问都已经完成，并且不会再执行额外同步。用户可以使用 cudaStreamQuery / cudaStreamSynchronize / cudaEventQuery / cudaEventSynchronize / cudaDeviceSynchronize 来保证相应异步工作已经完成，并且 GPU 不会尝试访问该分配。

cudaMallocAsync(&ptr, size,stream);
kernel<<<..., stream>>>(ptr, ...);
// 需要同步，以避免过早释放内存
cudaStreamSynchronize(stream);
cudaFree(ptr);

4.3.3. 内存池#

内存池封装了虚拟地址和物理内存资源；这些资源会根据池的属性和特性进行分配和管理。内存池最核心的属性，是它所管理内存的类型和位置。

所有 cudaMallocAsync 调用都会使用内存池中的资源。如果没有指定内存池，cudaMallocAsync 会使用传入流所在设备的当前内存池。设备的当前内存池可以通过 cudaDeviceSetMempool 设置，并通过 cudaDeviceGetMempool 查询。每个设备都有一个默认内存池；如果尚未调用 cudaDeviceSetMempool，该默认池就是活动池。

cudaMallocFromPoolAsync API 和 cudaMallocAsync 的 C++ 重载 允许用户为某次分配指定要使用的池，而不必把它设置为当前池。cudaDeviceGetDefaultMempool 和 cudaMemPoolCreate API 会返回内存池句柄。cudaMemPoolSetAttribute 和 cudaMemPoolGetAttribute 用于控制内存池的属性。

注

设备的当前内存池是该设备的本地池。因此，在不指定内存池的情况下进行分配，总是会得到相对于该流所在设备本地的分配。

4.3.3.1. 默认/隐式池#

可以调用 cudaDeviceGetDefaultMempool 获取设备的默认内存池。从某个设备的默认内存池分配出的内存，是位于该设备上的不可迁移设备分配。这些分配始终可以从该设备访问。默认内存池的可访问性可以通过 cudaMemPoolSetAccess 修改，并通过 cudaMemPoolGetAccess 查询。由于默认池不需要显式创建，它们有时也称为隐式池。设备的默认内存池不支持 IPC。

4.3.3.2. 显式池#

cudaMemPoolCreate 会创建显式池。这允许应用程序为分配请求默认/隐式池之外的属性，包括 IPC 能力、最大池大小、在支持平台上驻留于特定 CPU NUMA 节点的分配等。

// 在设备 0 上创建一个类似于隐式池的池
int device = 0;
cudaMemPoolProps poolProps = { };
poolProps.allocType = cudaMemAllocationTypePinned;
poolProps.location.id = device;
poolProps.location.type = cudaMemLocationTypeDevice;

cudaMemPoolCreate(&memPool, &poolProps));

下面的代码片段展示了如何在有效的 CPU NUMA 节点上创建支持 IPC 的内存池。

// 创建一个驻留在能够进行 IPC 共享（通过文件描述符）的 CPU NUMA 节点上的池。
int cpu_numa_id = 0;
cudaMemPoolProps poolProps = { };
poolProps.allocType = cudaMemAllocationTypePinned;
poolProps.location.id = cpu_numa_id;
poolProps.location.type = cudaMemLocationTypeHostNuma;
poolProps.handleType = cudaMemHandleTypePosixFileDescriptor;

cudaMemPoolCreate(&ipcMemPool, &poolProps));

4.3.3.3. 多 GPU 支持的设备可访问性#

与通过虚拟内存管理 API 控制的分配可访问性一样，内存池分配的可访问性并不遵循 cudaDeviceEnablePeerAccess 或 cuCtxEnablePeerAccess。对于内存池，cudaMemPoolSetAccess API 会修改哪些设备可以访问池中的分配。默认情况下，分配只能从其所在设备访问；这种访问权限无法撤销。若要允许其他设备访问，访问设备必须与内存池所在设备具备对等访问能力。可以使用 cudaDeviceCanAccessPeer 验证这一点。如果未检查对等能力，设置访问权限可能会以 cudaErrorInvalidDevice 失败。不过，如果还没有从该池中分配过内存，即使设备不具备对等能力，cudaMemPoolSetAccess 调用也可能成功；在这种情况下，下一次从该池分配内存会失败。

值得注意的是，cudaMemPoolSetAccess 会影响该内存池中的所有分配，而不仅仅是未来的分配。同样，cudaMemPoolGetAccess 报告的可访问性也适用于池中的所有分配，而不仅仅是未来的分配。不建议频繁更改某个池相对于给定 GPU 的可访问性设置。也就是说，一旦某个池可以从给定 GPU 访问，它就应在该池的生命周期内保持可从该 GPU 访问。

// 显示 cudaMemPoolSetAccess 用法的片段：
cudaError_t setAccessOnDevice(cudaMemPool_t memPool, int residentDevice,
              int accessingDevice) {
    cudaMemAccessDesc accessDesc = {};
    accessDesc.location.type = cudaMemLocationTypeDevice;
    accessDesc.location.id = accessingDevice;
    accessDesc.flags = cudaMemAccessFlagsProtReadWrite;

    int canAccess = 0;
    cudaError_t error = cudaDeviceCanAccessPeer(&canAccess, accessingDevice,
              residentDevice);
    if (error != cudaSuccess) {
        return error;
    } else if (canAccess == 0) {
        return cudaErrorPeerAccessUnsupported;
    }

    // 使地址可访问
    return cudaMemPoolSetAccess(memPool, &accessDesc, 1);
}

4.3.3.4. 为 IPC 启用内存池#

可以为内存池启用进程间通信 (IPC)，以便在进程之间方便、高效且安全地共享 GPU 内存。CUDA 的 IPC 内存池提供的安全性优势与 CUDA 的 虚拟内存管理 API 相同。

使用内存池在进程之间共享内存分为两步：各进程首先需要共享对池的访问权限，然后再共享该池中的具体分配。第一步用于建立并实施安全策略。第二步用于协调每个进程中使用哪些虚拟地址，以及映射何时需要在导入进程中保持有效。

4.3.3.4.1. 创建和共享 IPC 内存池#

共享对池的访问权限，需要先用 cudaMemPoolExportToShareableHandle() 获取该池的操作系统原生句柄，再使用操作系统原生 IPC 机制把该句柄传给导入进程，然后通过 cudaMemPoolImportFromShareableHandle() API 创建导入的内存池。若要 cudaMemPoolExportToShareableHandle 成功，创建内存池时必须在池属性结构中指定所请求的句柄类型。

有关在进程之间传输操作系统原生句柄所需的 IPC 机制，请参考 示例。其余过程可见下面的代码片段。

// 在导出进程中
// 在设备 0 上创建可导出的 IPC 功能池
cudaMemPoolProps poolProps = { };
poolProps.allocType = cudaMemAllocationTypePinned;
poolProps.location.id = 0;
poolProps.location.type = cudaMemLocationTypeDevice;

// 将 handleTypes 设置为非零值将使池可导出（支持 IPC）
poolProps.handleTypes = CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR;

cudaMemPoolCreate(&memPool, &poolProps));

// 基于 FD 的句柄是整数类型
int fdHandle = 0;


// 检索池的操作系统本机句柄。
// 注意这里传入的是一个指向句柄内存的指针。
cudaMemPoolExportToShareableHandle(&fdHandle,
             memPool,
             CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR,
             0);

// 必须使用合适的操作系统特定 API
// 将句柄发送给导入进程。

// 在导入进程中
 int fdHandle;
// 需要使用合适的操作系统特定 API
// 从导出进程取回该句柄。
// 从可共享句柄创建导入池。
// 请注意，此处句柄是按值传递的。
cudaMemPoolImportFromShareableHandle(&importedMemPool,
          (void*)fdHandle,
          CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR,
          0);

4.3.3.4.2. 在导入进程中设置访问权限#

导入的内存池最初只能从其驻留设备访问。导入的内存池不会继承导出进程设置的任何可访问性。导入进程如果计划从某个 GPU 访问该内存，就需要使用 cudaMemPoolSetAccess 为该 GPU 启用访问权限。

如果导入的内存池属于导入进程不可见的设备，用户必须使用 cudaMemPoolSetAccess API，为将使用这些分配的 GPU 启用访问权限。（参见 多 GPU 支持的设备可访问性）

4.3.3.4.3. 从导出的池创建和共享分配#

共享池之后，在导出进程中使用 cudaMallocAsync() 从该池创建的分配，可以与已经导入该池的进程共享。由于池的安全策略已经在池级别建立并验证，操作系统不需要额外记录账目来为特定池分配提供安全性。换言之，导入池分配所需的不透明 cudaMemPoolPtrExportData 可以通过任何机制发送给导入进程。

虽然导出和导入分配时无需以任何方式与分配流同步，但导入进程访问该分配时，必须遵循与导出进程相同的规则。具体来说，对分配的访问必须发生在分配流中的分配操作执行之后。下面两个代码片段展示了如何使用 cudaMemPoolExportPointer() 和 cudaMemPoolImportPointer() 共享分配，并配合 IPC 事件保证导入进程不会在分配准备好之前访问它。

// 在导出进程中准备分配
cudaMemPoolPtrExportData exportData;
cudaEvent_t readyIpcEvent;
cudaIpcEventHandle_t readyIpcEventHandle;

// 用于在进程之间协调的 IPC 事件
// cudaEventInterprocess 标志使事件成为 IPC 事件
// 出于性能原因设置 cudaEventDisableTiming

cudaEventCreate(&readyIpcEvent, cudaEventDisableTiming | cudaEventInterprocess)

// 从导出内存池分配
cudaMallocAsync(&ptr, size,exportMemPool, stream);

// 用于在分配准备就绪时共享的事件。
cudaEventRecord(readyIpcEvent, stream);
cudaMemPoolExportPointer(&exportData, ptr);
cudaIpcGetEventHandle(&readyIpcEventHandle, readyIpcEvent);

// 使用任何机制与导入进程共享 IPC 事件和指针导出数据。
// 这里我们把数据复制到共享内存中。
shmem->ptrData = exportData;
shmem->readyIpcEventHandle = readyIpcEventHandle;
// 通知使用方数据已准备就绪

// 导入一个分配
cudaMemPoolPtrExportData *importData = &shmem->prtData;
cudaEvent_t readyIpcEvent;
cudaIpcEventHandle_t *readyIpcEventHandle = &shmem->readyIpcEventHandle;

// 需要使用任意机制从导出进程取回 IPC 事件句柄
// 和导出数据。这里我们使用 shmem，只需要同步以确保
// 共享内存已经填充。

cudaIpcOpenEventHandle(&readyIpcEvent, readyIpcEventHandle);

// 导入分配。该操作不会阻塞等待分配准备就绪。
cudaMemPoolImportPointer(&ptr, importedMemPool, importData);

// 在导入进程中使用该分配之前，等待分配流中
// 更早的流操作完成。
cudaStreamWaitEvent(stream, readyIpcEvent);
kernel<<<..., stream>>>(ptr, ...);

释放分配时，导入进程必须先于导出进程释放该分配。下面的代码片段展示了如何使用 CUDA IPC 事件，为两个进程中的 cudaFreeAsync 操作提供所需同步。导入进程对该分配的访问显然会受到导入进程侧释放操作的限制。值得注意的是，也可以在两个进程中使用 cudaFree 释放该分配，并且可以使用其他流同步 API 代替 CUDA IPC 事件。

// 释放必须先在导入进程中发生，然后才能在导出进程中发生
kernel<<<..., stream>>>(ptr, ...);

// 导入进程中的最后一次访问
cudaFreeAsync(ptr, stream);

// 释放后，导入进程中不允许再访问
cudaIpcEventRecord(finishedIpcEvent, stream);

// 导出进程
// 导出进程需要把自己的释放操作与导入进程释放操作
// 的流顺序协调起来。
cudaStreamWaitEvent(stream, finishedIpcEvent);
kernel<<<..., stream>>>(ptrInExportingProcess, ...);

// 导入进程中的释放不会阻止导出进程
// 使用该分配。
cudFreeAsync(ptrInExportingProcess,stream);

4.3.3.4.4. IPC 导出池限制#

IPC 池目前不支持把物理块释放回操作系统。因此，cudaMemPoolTrimTo API 不会产生效果，cudaMemPoolAttrReleaseThreshold 实际上也会被忽略。该行为由驱动程序控制，而不是由运行时控制，并且可能在未来的驱动程序更新中改变。

4.3.3.4.5. IPC 导入池限制#

不允许从导入池中分配；具体来说，导入池不能设置为当前池，也不能用于 cudaMallocFromPoolAsync API。因此，分配重用策略属性对这些池没有意义。

与 IPC 导出池一样，IPC 导入池目前也不支持把物理块释放回操作系统。

资源使用统计属性查询只反映导入到该进程中的分配及其关联的物理内存。

4.3.4. 最佳实践和调整#

4.3.4.1. 查询支持#

应用程序可以调用 cudaDeviceGetAttribute()（参见 开发者博客）并查询 cudaDevAttrMemoryPoolsSupported 设备属性，来判断某个设备是否支持流有序内存分配器。

可以通过 cudaDevAttrMemoryPoolSupportedHandleTypes 设备属性查询 IPC 内存池支持情况。该属性在 CUDA 11.3 中加入；旧版驱动程序在查询该属性时会返回 cudaErrorInvalidValue。

int driverVersion = 0;
int deviceSupportsMemoryPools = 0;
int poolSupportedHandleTypes = 0;
cudaDriverGetVersion(&driverVersion);
if (driverVersion >= 11020) {
    cudaDeviceGetAttribute(&deviceSupportsMemoryPools,
                           cudaDevAttrMemoryPoolsSupported, device);
}
if (deviceSupportsMemoryPools != 0) {
    // `device` 支持流有序内存分配器
}

if (driverVersion >= 11030) {
    cudaDeviceGetAttribute(&poolSupportedHandleTypes,
              cudaDevAttrMemoryPoolSupportedHandleTypes, device);
}
if (poolSupportedHandleTypes & cudaMemHandleTypePosixFileDescriptor) {
   // 指定设备上的池可以使用基于 POSIX 文件描述符的 IPC 创建
}

在查询之前检查驱动程序版本，可以避免在尚未定义该属性的驱动程序上遇到 cudaErrorInvalidValue 错误。也可以使用 cudaGetLastError 清除该错误，而不是预先避免它。

4.3.4.2. 物理页面缓存行为#

默认情况下，分配器会尽量减少内存池拥有的物理内存。为了尽量减少分配和释放物理内存时发生的操作系统调用，应用程序必须为每个池配置内存占用量。应用程序可以通过释放阈值属性（cudaMemPoolAttrReleaseThreshold）完成这项配置。

释放阈值表示内存池在尝试把内存释放回操作系统之前应保留的字节数。当内存池持有的内存超过释放阈值时，分配器会在下一次流、事件或设备同步时尝试把内存释放回操作系统。将释放阈值设置为 UINT64_MAX 可以阻止驱动程序在每次同步后都尝试收缩内存池。

Cuuint64_t setVal = UINT64_MAX;
cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrReleaseThreshold, &setVal);

如果应用程序把 cudaMemPoolAttrReleaseThreshold 设置得足够高，从而实际上禁用了内存池收缩，那么它可能需要显式缩减内存池的内存占用。cudaMemPoolTrimTo 允许应用程序完成这项操作。在修剪内存池占用量时，minBytesToKeep 参数允许应用程序保留指定数量的内存，例如后续执行阶段预计会用到的数量。

Cuuint64_t setVal = UINT64_MAX;
cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrReleaseThreshold, &setVal);

// 应用程序的某个阶段需要从流有序分配器获得大量内存
for (i=0; i<10; i++) {
    for (j=0; j<10; j++) {
        cudaMallocAsync(&ptrs[j],size[j], stream);
    }
    kernel<<<...,stream>>>(ptrs,...);
    for (j=0; j<10; j++) {
        cudaFreeAsync(ptrs[j], stream);
    }
}

// 下一阶段中，该进程不再需要这么多内存。
// 执行同步，使修剪操作能够知道这些分配
// 已经不再使用。
cudaStreamSynchronize(stream);
cudaMemPoolTrimTo(mempool, 0);

// 其他进程或分配机制现在可以使用
// 修剪操作释放出的物理内存。

4.3.4.3. 资源使用统计#

查询内存池的 cudaMemPoolAttrReservedMemCurrent 属性，会报告该池当前消耗的 GPU 物理内存总量。查询内存池的 cudaMemPoolAttrUsedMemCurrent 属性，会返回已经从池中分配且当前不可重用的内存总大小。

cudaMemPoolAttr*MemHigh 属性会记录对应 cudaMemPoolAttr*MemCurrent 属性自上次重置以来达到的最大高水位值。可以使用 cudaMemPoolSetAttribute API 将这些值重置为当前值。

// 用于批量获取使用情况统计信息的示例辅助函数
struct usageStatistics {
    cuuint64_t reserved;
    cuuint64_t reservedHigh;
    cuuint64_t used;
    cuuint64_t usedHigh;
};

void getUsageStatistics(cudaMemoryPool_t memPool, struct usageStatistics *statistics)
{
    cudaMemPoolGetAttribute(memPool, cudaMemPoolAttrReservedMemCurrent, statistics->reserved);
    cudaMemPoolGetAttribute(memPool, cudaMemPoolAttrReservedMemHigh, statistics->reservedHigh);
    cudaMemPoolGetAttribute(memPool, cudaMemPoolAttrUsedMemCurrent, statistics->used);
    cudaMemPoolGetAttribute(memPool, cudaMemPoolAttrUsedMemHigh, statistics->usedHigh);
}


// 重置高水位值会让它们采用当前值。
void resetStatistics(cudaMemoryPool_t memPool)
{
    cuuint64_t value = 0;
    cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrReservedMemHigh, &value);
    cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrUsedMemHigh, &value);
}

4.3.4.4. 内存重用策略#

为了满足分配请求，驱动程序会先尝试重用先前通过 cudaFreeAsync() 释放的内存，然后才会尝试从操作系统分配更多内存。例如，在某个流中释放的内存，可以立即被同一流上的后续分配请求重用。当某个流与 CPU 同步后，先前在该流中释放的内存就可以被任意流中的分配重用。重用策略既适用于默认内存池，也适用于显式内存池。

流有序分配器提供若干可控的分配策略。内存池属性 cudaMemPoolReuseFollowEventDependencies、cudaMemPoolReuseAllowOpportunistic 和 cudaMemPoolReuseAllowInternalDependencies 控制这些策略，详情如下。可以通过调用 cudaMemPoolSetAttribute 启用或禁用这些策略。升级到较新的 CUDA 驱动程序可能会改变、增强、扩展和/或重新排序重用策略的枚举。

4.3.4.4.1. cudaMemPoolReuseFollowEventDependencies#

在分配更多 GPU 物理内存之前，分配器会检查由 CUDA 事件建立的依赖信息，并尝试从另一个流中释放的内存进行分配。

cudaMallocAsync(&ptr, size, originalStream);
kernel<<<..., originalStream>>>(ptr, ...);
cudaFreeAsync(ptr, originalStream);
cudaEventRecord(event,originalStream);

// 等待在另一个流中捕获释放操作的事件，
// 会在启用 cudaMemPoolReuseFollowEventDependencies 时，
// 允许分配器重用这段内存来满足另一个流中的新分配请求。
cudaStreamWaitEvent(otherStream, event);
cudaMallocAsync(&ptr2, size, otherStream);

4.3.4.4.2. cudaMemPoolReuseAllowOpportunistic#

启用 cudaMemPoolReuseAllowOpportunistic 策略后，分配器会检查已经释放的分配，判断释放操作的流有序语义是否已经满足，例如该流是否已经执行到释放操作所指示的执行点之后。禁用该策略时，当某个流与 CPU 同步后，分配器仍会重用由此变为可用的内存。禁用该策略并不会阻止 cudaMemPoolReuseFollowEventDependencies 生效。

cudaMallocAsync(&ptr, size, originalStream);
kernel<<<..., originalStream>>>(ptr, ...);
cudaFreeAsync(ptr, originalStream);


// 一段时间后，内核完成运行
wait(10);

// 启用 cudaMemPoolReuseAllowOpportunistic 时，
// 此分配请求可以根据 originalStream 的进度，
// 使用之前的分配来满足。
cudaMallocAsync(&ptr2, size, otherStream);

4.3.4.4.3. cudaMemPoolReuseAllowInternalDependencies#

如果无法从操作系统分配并映射更多物理内存，驱动程序会查找可用性取决于另一个流待推进度的内存。如果找到这样的内存，驱动程序会把所需依赖插入执行分配的流中，并重用该内存。

cudaMallocAsync(&ptr, size, originalStream);
kernel<<<..., originalStream>>>(ptr, ...);
cudaFreeAsync(ptr, originalStream);

// 启用 cudaMemPoolReuseAllowInternalDependencies 且
// 驱动程序无法分配更多物理内存时，驱动程序可能会
// 在执行分配的流中等效地执行 cudaStreamWaitEvent，
// 以确保 otherStream 中的未来工作发生在原始流中
// 允许访问原始分配的工作之后。
cudaMallocAsync(&ptr2, size, otherStream);

4.3.4.4.4. 禁用重用策略#

虽然可控重用策略可以改善内存重用，用户也可能希望禁用它们。允许机会性重用（例如 cudaMemPoolReuseAllowOpportunistic）会根据 CPU 和 GPU 执行交错情况，在不同运行之间引入分配模式差异。内部依赖插入（例如 cudaMemPoolReuseAllowInternalDependencies）可能以意外且潜在非确定性的方式串行化工作；而用户在分配失败时可能更希望显式同步事件或流。

4.3.4.5. 同步 API 操作#

分配器成为 CUDA 驱动程序一部分后带来的优化之一，是它能够与同步 API 集成。当用户请求 CUDA 驱动程序同步时，驱动程序会等待异步工作完成。返回之前，驱动程序会确定该同步保证哪些释放操作已经完成。无论指定的流是什么，也无论哪些分配策略已被禁用，这些分配都会变为可再次分配。驱动程序还会在这里检查 cudaMemPoolAttrReleaseThreshold，并尽可能释放多余的物理内存。

4.3.5. 补充说明#

4.3.5.1. cudaMemcpyAsync 当前上下文/设备敏感度#

在当前 CUDA 驱动程序中，任何涉及 cudaMallocAsync 内存的异步 memcpy，都应在调用线程的当前上下文中使用指定流的上下文来执行。对 cudaMemcpyPeerAsync 则不需要这样，因为 API 中指定设备的主上下文会被引用，而不是当前上下文。

4.3.5.2. cudaPointerGetAttributes 查询#

在某个分配上调用 cudaFreeAsync 之后，再对该分配调用 cudaPointerGetAttributes 会导致未定义行为。具体而言，即使某个给定流仍可访问该分配也不例外；行为仍然未定义。

4.3.5.3. cudaGraphAddMemsetNode#

cudaGraphAddMemsetNode 不适用于通过流有序分配器分配的内存。不过，对这些分配执行的 memset 可以被流捕获。

4.3.5.4. 指针属性#

cudaPointerGetAttributes 查询适用于流有序分配。由于流有序分配不与上下文关联，查询 CU_POINTER_ATTRIBUTE_CONTEXT 会成功，但会在 *data 中返回 NULL。CU_POINTER_ATTRIBUTE_DEVICE_ORDINAL 属性可用于确定分配所在位置；这在选择用于通过 cudaMemcpyPeerAsync 执行 p2h2p 拷贝的上下文时很有用。CU_POINTER_ATTRIBUTE_MEMPOOL_HANDLE 属性在 CUDA 11.3 中加入，可用于调试，以及在执行 IPC 之前确认某个分配来自哪个池。

4.3.5.5. CPU 虚拟内存#

使用 CUDA 流有序内存分配器 API 时，请避免用 ulimit -v 设置虚拟内存限制，因为不支持这种设置。
