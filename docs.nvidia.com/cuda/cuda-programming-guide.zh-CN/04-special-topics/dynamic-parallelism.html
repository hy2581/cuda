4.18. CUDA 动态并行#

4.18.1. 引言#

4.18.1.1. 概述#

CUDA 动态并行性（通常缩写为 CDP）是 CUDA 编程模型的一项功能，它使在 GPU 上运行的代码能够创建新的 GPU 工作。也就是说，新工作可以以从 GPU 上运行的设备代码启动额外内核的形式添加到 GPU。此功能可以减少在主机和设备之间传输执行控制和数据的需要，因为启动配置决策可以由在设备上执行的线程在运行时做出。

数据相关的并行工作可以由内核在运行时生成。在将 CDP 添加到 CUDA 之前，需要修改一些算法和编程模式，以消除递归、不规则循环结构或其他不适合平面、单级并行性的构造。使用 CUDA 动态并行性可以更自然地表达这些程序结构。

注

本节介绍 CUDA 动态并行性的更新版本，有时称为 CDP2，它是 CUDA 12.0 及更高版本中的默认版本。 CDP2 是 CC 9.0 及更高版本设备上可用的唯一 CUDA 动态并行版本。对于低于 9.0 的 CC 设备，开发人员仍然可以通过编译器参数选择使用旧版 CUDA 动态并行机制 CDP1 -DCUDA_FORCE_CDP1_IF_SUPPORTED。 CDP1 文档可以在以下位置找到 旧版本的 CUDA 编程指南。 CDP1 预计会从 CUDA 的未来版本中删除。

4.18.2. 执行环境#

CUDA 中的动态并行性允许 GPU 线程配置、启动和隐式同步新网格。网格是内核启动的一个实例，包括线程块的具体形状和线程块的网格。在以下各节中，需要重点注意内核函数本身和该内核的特定调用（即网格）之间的区别。

4.18.2.1. 父子网格#

配置和启动新网格的设备线程属于父网格。通过调用创建的新网格称为子网格。

子网格的调用和完成是正确嵌套的，这意味着父网格在其线程创建的所有子网格都完成之前才被视为完成，并且运行时保证父网格和子网格之间的隐式同步。

4.18.2.2. CUDA 基元的范围#

CUDA 动态并行性依赖于 CUDA 设备运行时，它允许调用一组有限的 API，这些 API 在语法上类似于 CUDA 运行时 API，但在设备代码中可用。设备运行时 API 的行为与其主机对应的 API 类似，但也存在一些差异。这些差异在章节中的表格中得到了体现 API参考.

在主机和设备上，CUDA 运行时都提供了一个 API，用于启动内核并通过流和事件跟踪启动之间的依赖关系。在设备上，启动的内核和 CUDA 对象对于调用网格中的所有线程都是可见的。例如，这意味着流可以由一个线程创建并由同一网格中的任何其他线程使用。但是，由设备 API 调用创建的 CUDA 对象（例如流和事件）仅在创建它们的网格内有效。

4.18.2.3. 直播和活动#

CUDA Streams 或 事件 允许控制内核启动之间的依赖关系：启动到同一流中的内核按顺序执行，并且事件可用于创建流之间的依赖关系。在设备上创建的流和事件具有完全相同的目的。

在网格内创建的流和事件存在于网格范围内，但在创建它们的网格之外使用时具有未定义的行为。如上所述，当网格退出时，网格启动的所有工作都会隐式同步；启动到流中的工作包含在其中，所有依赖项都得到了适当的解决。在网格范围之外修改的流上的操作的行为是未定义的。

在主机上创建的流和事件在任何内核中使用时都具有未定义的行为，就像父网格创建的流和事件在子网格中使用时具有未定义的行为一样。

4.18.2.4. 排序和并发#

从设备运行时启动内核的顺序遵循 CUDA Stream 排序语义。在网格内，所有内核都启动到同一个流中（除了 即发即忘流）按顺序执行。当同一网格中的多个线程启动到同一流中时，流内的排序取决于网格内的线程调度，这可以通过同步原语进行控制，例如 __syncthreads().

请注意，虽然命名流由网格内的所有线程共享，但隐式 NULL 流仅由线程块内的所有线程共享。如果线程块中的多个线程启动到隐式流中，则这些启动将按顺序执行。如果不同线程块中的线程启动到隐式流中，则这些启动可以并发执行。如果需要从线程块内的多个线程启动并发，则应使用显式命名流。

设备运行时在 CUDA 执行模型中没有引入新的并发保证。也就是说，不能保证设备上任意数量的不同线程块之间的并发执行。

缺乏并发保证扩展到父网格及其子网格。当父网格启动子网格时，一旦满足流依赖性并且硬件资源可用，子网格就可以开始执行，但不保证在父网格到达隐式同步点之前开始执行。

并发性可能因设备配置、应用程序工作负载和运行时调度而异。因此，依赖不同线程块之间的任何并发性都是不安全的。

4.18.3. 内存相干性与一致性#

4.18.3.1. 全局内存#

父网格和子网格可以一致地访问全局内存，而子网格和父网格之间的一致性保证很弱。在子网格的执行过程中，只有一个时间点其内存视图与父线程完全一致：即子网格被父网格调用时。

在子网格调用之前父线程中的所有全局内存操作对于子网格都是可见的。随着去除 cudaDeviceSynchronize()，不再可能从父网格访问子网格中的线程所做的修改。在父网格退出之前访问子网格中线程所做的修改的唯一方法是通过启动到子网格中的内核 cudaStreamTailLaunch stream.

在下面的示例中，子网格执行 child_launch 只保证看到修改 data 在子网格启动之前制作。由于父线程 0 正在执行启动，因此子线程将与父线程 0 看到的内存保持一致。由于第一个 __syncthreads() 打电话，孩子就会看到 data[0]=0, data[1]=1, …, data[255]=255 （没有 __syncthreads() 打电话，仅 data[0]=0 保证能被孩子看到）。仅保证子网格在隐式同步时返回。这意味着子网格中的线程所做的修改永远不能保证对父网格可用。访问所做的修改 child_launch, a tail_launch 内核被启动到 cudaStreamTailLaunch stream.

__global__ void tail_launch(int *data) {
   data[threadIdx.x] = data[threadIdx.x]+1;
}

__global__ void child_launch(int *data) {
   data[threadIdx.x] = data[threadIdx.x]+1;
}

__global__ void parent_launch(int *data) {
   data[threadIdx.x] = threadIdx.x;

   __syncthreads();

   if (threadIdx.x == 0) {
       child_launch<<< 1, 256 >>>(data);
       tail_launch<<< 1, 256, 0, cudaStreamTailLaunch >>>(data);
   }
}

void host_launch(int *data) {
    parent_launch<<< 1, 256 >>>(data);
}

4.18.3.2. 映射内存#

映射的系统内存具有与全局内存相同的一致性和一致性保证，并遵循上面详述的语义。内核不能分配或释放映射内存，但可以使用从主机程序传入的指向映射内存的指针。

4.18.3.3. 共享内存和本地内存#

共享内存和本地内存分别是线程块或线程私有的，并且在父级和子级之间不可见或不一致。当这些位置之一的对象在其所属范围之外被引用时，行为是未定义的，并且可能会导致错误。

NVIDIA 编译器将尝试警告是否可以检测到指向本地或共享内存的指针正在作为参数传递给内核启动。在运行时，程序员可以使用 __isGlobal() 内部确定指针是否引用全局内存，因此可以安全地传递给子启动。

致电 cudaMemcpy*Async() 或 cudaMemset*Async() 可以调用设备上的新子内核以保留流语义。因此，将共享或本地内存指针传递给这些 API 是非法的，并且会返回错误。

4.18.3.4. 本地内存#

本地内存是执行线程的私有存储，在该线程外部不可见。启动子内核时，将指向本地内存的指针作为启动参数传递是非法的。从子网格取消引用此类本地内存指针的结果是未定义的。

例如，以下内容是非法的，如果存在未定义的行为 x_array 访问者是 child_launch:

int x_array[10];       // 在父级的本地内存中创建 x_array
child_launch<<< 1, 1 >>>(x_array);

有时，程序员很难意识到编译器何时将变量放入本地内存。作为一般规则，传递给子内核的所有存储都应该从全局内存堆中显式分配，或者使用 cudaMalloc(), new() 或者通过声明 __device__ 全局范围内的存储。例如：

// 正确 - “值”是全局存储
__device__ int value;
__device__ void x() {
    value = 5;
    child<<< 1, 1 >>>(&value);
}

// 无效 - “值”是本地存储
__device__ void y() {
    int value = 5;
    child<<< 1, 1 >>>(&value);
}

4.18.3.4.1. 纹理内存#

对映射纹理的全局内存区域的写入与纹理访问是不一致的。纹理内存的一致性是在调用子网格时以及子网格完成时强制执行的。这意味着在子内核启动之前对内存的写入会反映在子内核的纹理内存访问中。与上面的全局内存类似，子进程对内存的写入永远不能保证反映在父进程的纹理内存访问中。在父网格退出之前访问子网格中线程所做的修改的唯一方法是通过启动到子网格中的内核 cudaStreamTailLaunch 流。父级和子级的并发访问可能会导致数据不一致。

4.18.4. 编程接口#

4.18.4.1. 基础#

下面的例子展示了一个简单的 你好世界 结合动态并行性的程序：

#include <stdio.h>

__global__ void childKernel()
{
    printf("Hello ");
}

__global__ void tailKernel()
{
    printf("World!\n");
}

__global__ void parentKernel()
{
    // 发射孩子
    childKernel<<<1,1>>>();
    if (cudaSuccess != cudaGetLastError()) {
        return;
    }

    // 将 tail 启动到 cudaStreamTailLaunch 流中
    // 隐式同步：等待子进程完成
    tailKernel<<<1,1,0,cudaStreamTailLaunch>>>();

}

int main(int argc, char *argv[])
{
    // 启动父级
    parentKernel<<<1,1>>>();
    if (cudaSuccess != cudaGetLastError()) {
        return 1;
    }

    // 等待父级完成
    if (cudaSuccess != cudaDeviceSynchronize()) {
        return 2;
    }

    return 0;
}

该程序可以通过命令行一步构建，如下所示：

$ nvcc -arch=sm_75 -rdc=true hello_world.cu -o hello -lcudadevrt

4.18.4.2. CDP 的 C++ 语言接口#

使用 CUDA C++ 实现动态并行性的 CUDA 内核可用的语言接口和 API 称为 CUDA 设备运行时.

在可能的情况下，保留了 CUDA 运行时 API 的语法和语义，以便于轻松重用可在主机或设备环境中运行的例程的代码。

与 CUDA C++ 中的所有代码一样，此处概述的 API 和代码是每线程代码。这使得每个线程能够就下一步执行哪个内核或操作做出独特的动态决策。块内的线程之间没有同步要求来执行任何提供的设备运行时 API，这使得可以在任意不同的内核代码中调用设备运行时 API 函数，而不会出现死锁。

4.18.4.2.1. 设备端内核启动#

可以使用标准 CUDA <<< >>> 语法从设备启动内核：

kernel_name<<< Dg, Db, Ns, S >>>([kernel arguments]);

  • Dg 属于类型 dim3 并指定网格的尺寸和大小

  • Db 属于类型 dim3 并指定每个线程块的尺寸和大小

  • Ns 属于类型 size_t 并指定除了静态分配的内存之外，为此调用为每个线程块动态分配的共享内存的字节数。 Ns 是一个可选参数，默认为 0。

  • S 属于类型 cudaStream_t 并指定与此调用关联的流。该流必须已分配在进行调用的同一网格中。 S 是一个可选参数，默认为 NULL 流。

4.18.4.2.1.1. 启动是异步的#

与主机端启动相同，所有设备端内核启动相对于启动线程都是异步的。也就是说， <<<>>> launch 命令将立即返回，并且启动线程将继续执行，直到它到达隐式启动同步点，例如在启动到 cudaStreamTailLaunch 流（尾部发射流）。子网格可以在启动后的任何时间开始执行，但不保证在启动线程到达隐式启动同步点之前开始执行。

与主机端启动类似，启动到单独流中的工作可能会同时运行，但不能保证实际的并发性。依赖于子内核之间并发的程序不受 CUDA 编程模型支持，并且将具有未定义的行为。

4.18.4.2.1.2. 启动环境配置#

所有全局设备配置设置（例如，从 cudaDeviceGetCacheConfig()，以及从返回的设备限制 cudaDeviceGetLimit()）将从父级继承。同样，设备限制（例如堆栈大小）将保持配置状态。

对于主机启动的内核，主机设置的每内核配置将优先于全局设置。从设备启动内核时也会使用这些配置。无法从设备重新配置内核环境。

4.18.4.2.2. 事件#

仅支持 CUDA 事件的流间同步功能。这意味着 cudaStreamWaitEvent() 是支持的，但是 cudaEventSynchronize(), cudaEventElapsedTime(), 和 cudaEventQuery() 不是。作为 cudaEventElapsedTime() 不支持，cudaEvents 必须通过创建 cudaEventCreateWithFlags()，通过 cudaEventDisableTiming 标志。

与流一样，事件对象可以在创建它们的网格内的所有线程之间共享，但对于该网格来说是本地的，并且不能传递到其他内核。不保证事件句柄在网格之间是唯一的，因此在未创建事件句柄的网格中使用事件句柄将导致未定义的行为。

4.18.4.2.3. 同步#

如果调用线程旨在与从其他线程调用的子网格同步，则由程序执行足够的线程间同步，例如通过 CUDA 事件。

由于无法从父线程显式同步子工作，因此无法保证子网格中发生的更改对于父网格内的线程可见。

4.18.4.2.4. 设备管理#

只有运行内核的设备才能从该内核控制。这意味着设备 API，例如 cudaSetDevice() 设备运行时不支持。从 GPU 看到的活动设备（从 cudaGetDevice()）将具有与主机系统中看到的相同的设备号。的 cudaDeviceGetAttribute() 调用可能会请求有关另一个设备的信息，因为此 API 允许指定设备 ID 作为调用的参数。请注意，包罗万象 cudaGetDeviceProperties() 设备运行时不提供 API - 必须单独查询属性。

4.18.5. 编程指南#

4.18.5.1. 性能#

4.18.5.1.1. 支持动态并行的内核开销#

在控制动态启动时处于活动状态的系统软件可能会对当时正在运行的任何内核施加开销，无论它是否调用自己的内核启动。这种开销由设备运行时的执行跟踪和管理软件产生，可能会导致性能下降。一般来说，这种开销是由链接到设备运行时库的应用程序产生的。

4.18.5.2. 实施限制和限制#

动态并行保证了本文档中描述的所有语义，但是，某些硬件和软件资源依赖于实现，并限制了使用设备运行时的程序的规模、性能和其他属性。

4.18.5.2.1. 运行时#

4.18.5.2.1.1. 内存占用#

设备运行时系统软件保留用于各种管理目的的存储器，特别是用于跟踪待处理的网格启动的保留。配置控件可用于减少此预留的大小，以换取某些启动限制。参见 配置选项，如下，了解详细信息。

4.18.5.2.1.2. 等待内核发布#

当内核启动时，所有关联的配置和参数数据都会被跟踪，直到内核完成。该数据存储在系统管理的启动池中。

固定大小启动池的大小可通过调用进行配置 cudaDeviceSetLimit() 来自主机并指定 cudaLimitDevRuntimePendingLaunchCount.

4.18.5.3. 兼容性和互操作性#

CDP2 是默认值。函数可以用以下方式编译 -DCUDA_FORCE_CDP1_IF_SUPPORTED 选择不在计算能力低于 9.0 的设备上使用 CDP2。

使用 CUDA 12.0 及更高版本的函数编译器（默认）

使用 CDP1 和 CDP2 的函数可以在同一上下文中同时加载和运行。 CDP1 函数能够使用 CDP1 特定的功能（例如 cudaDeviceSynchronize）和 CDP2 函数能够使用 CDP2 特定的功能（例如尾部启动和即发即忘启动）。

本文档不包含旧版 CDP1 的行为。有关 CDP1 的信息，请参阅 旧版 CUDA 编程指南

4.18.6. 从 PTX 设备端启动#

前面几节已经讨论了使用 CUDA 设备运行时 实现动态并行。动态并行也可以从 PTX 执行。对于目标为以下目标的编程语言和编译器实现者 并行线程执行 (PTX) 并计划支持 动态并行性 用他们的语言，本节提供了与支持 PTX 级别的内核启动相关的底层细节。

4.18.6.1. 内核启动 API#

设备端内核启动可以使用以下两个可从 PTX 访问的 API 来实现： cudaLaunchDevice() 或 cudaGetParameterBuffer(). cudaLaunchDevice() 使用通过调用获得的参数缓冲区启动指定的内核 cudaGetParameterBuffer() 并填充启动内核的参数。参数buffer可以为NULL，即不需要调用 cudaGetParameterBuffer()，如果启动的内核不带任何参数。

4.18.6.1.1. cudaLaunchDevice#

在 PTX 级别， cudaLaunchDevice()在使用之前需要以下面所示的两种形式之一进行声明。

// 当 .address_size 为 64 时 cudaLaunchDevice() 的 PTX 级声明
.extern .func(.param .b32 func_retval0) cudaLaunchDevice
(
  .param .b64 func,
  .param .b64 parameterBuffer,
  .param .align 4 .b8 gridDimension[12],
  .param .align 4 .b8 blockDimension[12],
  .param .b32 sharedMemSize,
  .param .b64 stream
)
;

下面的 CUDA 级别声明映射到上述 PTX 级别声明之一，并可在系统头文件中找到 cuda_device_runtime_api.h。该函数定义在 cudadevrt 系统库，必须与程序链接才能使用设备端内核启动功能。

// cudaLaunchDevice() 的 CUDA 级声明
extern "C" __device__
cudaError_t cudaLaunchDevice(void *func, void *parameterBuffer,
                             dim3 gridDimension, dim3 blockDimension,
                             unsigned int sharedMemSize,
                             cudaStream_t stream);

第一个参数是指向要启动的内核的指针，第二个参数是保存启动内核的实际参数的参数缓冲区。参数缓冲区的布局解释如下 参数缓冲区布局，如下。其他参数指定启动配置，即网格尺寸、块尺寸、共享内存大小以及与启动相关的流（请参阅 内核配置 有关启动配置的详细说明。

4.18.6.1.2. cudaGetParameterBuffer#

cudaGetParameterBuffer() 使用前需要在 PTX 级别声明。 PTX 级声明必须采用下面给出的两种形式之一，具体取决于地址大小：

// .address_size 为 64 时 cudaGetParameterBuffer() 的 PTX 级声明
.extern .func(.param .b64 func_retval0) cudaGetParameterBuffer
(
  .param .b64 alignment,
  .param .b64 size
)
;

以下 CUDA 级别声明 cudaGetParameterBuffer() 映射到前面提到的 PTX 级声明：

// cudaGetParameterBuffer() 的 CUDA 级声明
extern "C" __device__
void *cudaGetParameterBuffer(size_t alignment, size_t size);

第一个参数指定参数缓冲区的对齐要求，第二个参数指定大小要求（以字节为单位）。在当前的实现中，返回的参数缓冲区 cudaGetParameterBuffer() 始终保证 64 字节对齐，并且忽略对齐要求参数。但是，建议将正确的对齐要求值（这是要放置在参数缓冲区中的任何参数的最大对齐方式）传递给 cudaGetParameterBuffer() 以确保将来的可移植性。

4.18.6.2. 参数缓冲区布局#

禁止参数缓冲区中的参数重新排序，并且放置在参数缓冲区中的每个单独的参数都需要对齐。也就是说，每个参数必须放在 nth 参数缓冲区中的字节，其中 n 是参数大小的最小倍数，且该参数大小大于前一个参数所取的最后一个字节的偏移量。参数缓冲区的最大大小为 4KB。

有关 CUDA 编译器生成的 PTX 代码的更详细说明，请参阅 PTX-3.5 规范。
