4.16. 虚拟内存管理#

在CUDA编程模型中，内存分配调用（例如 cudaMalloc()）返回 GPU 内存中的内存地址。 该地址可与任何 CUDA API 一起使用或在设备内部使用 内核。 开发人员可以启用对等设备访问该内存 通过使用分配 cudaEnablePeerAccess。通过这样做， 不同设备上的内核可以访问相同的数据。然而， 所有过去和未来的用户分配也会映射到目标对等设备。 这可能会导致用户无意中支付运行时成本 映射所有 cudaMalloc 分配给对等设备。在大多数 在某些情况下，应用程序通过仅共享少量分配来进行通信 另一个设备。通常不需要将所有分配映射到所有 设备。此外，将此方法扩展到多节点设置变得 本质上是困难的。

CUDA 提供了 虚拟内存管理 (VMM) API 为开发人员提供了对此过程的显式低级控制。

虚拟内存分配，由操作系统管理的复杂过程 和内存管理单元（MMU），工作在两个关键阶段。一、操作系统 为程序保留连续的虚拟地址范围，而无需 分配任何物理内存。然后，当程序尝试使用该 第一次内存时，操作系统提交虚拟地址，分配 根据需要将物理存储转移到虚拟页面。

CUDA 的 VMM API 为 GPU 内存管理带来了类似的概念，允许 开发人员显式保留虚拟地址范围，然后映射它 到物理 GPU 内存。借助VMM，应用程序可以专门选择 其他设备可以访问某些分配。

VMM API 允许管理复杂的应用程序 跨多个 GPU（和 CPU 核心）更有效地存储。通过启用 手动控制内存预留、映射和访问权限， VMM API 支持细粒度数据共享、零复制等先进技术 传输和自定义内存分配器。 CUDA VMM API 公开细粒度 用户可以控制管理应用程序中的 GPU 内存。

开发人员可以通过以下几个关键方式从 VMM API 中受益：

  • 对虚拟和物理内存管理的细粒度控制，允许 非连续物理内存块的分配和映射 连续的虚拟地址空间。这有助于减少 GPU 内存 碎片并提高内存利用率，特别是对于大型 深度神经网络训练等工作负载。

  • 通过分离预留实现高效的内存分配和释放 物理内存分配中的虚拟地址空间。开发商 可以保留大的虚拟内存区域并按需映射物理内存 无需昂贵的内存复制或重新分配，从而提高性能 动态数据结构和可变大小内存的改进 分配。

  • 无需动态增加 GPU 内存分配的能力 复制并重新分配所有数据，类似于 realloc 或 std::vector 作品 在CPU内存管理中。这支持更灵活、更高效的 GPU 内存使用模式。

  • 提高开发人员的工作效率和应用程序性能 提供低级 API，允许构建复杂的内存 分配器和缓存管理系统，例如动态管理 大型语言模型中的键值缓存，提高吞吐量 延迟。

  • CUDA VMM API 在分布式多 GPU 设置中非常有价值，因为 它可以实现跨多个 GPU 的高效内存共享和访问。由 API 允许将虚拟地址与物理内存解耦 开发人员创建一个统一的虚拟地址空间，数据可以在其中存储 动态映射到不同的 GPU。这优化了内存使用 减少数据传输开销。例如，NVIDIA 的库如 NCCL、 NVShmem 积极使用 VMM。

总之，CUDA VMM API 为开发人员提供了高级工具来进行微调、 超越传统的高效、灵活且可扩展的 GPU 内存管理 类似 malloc 的抽象，这对于高性能和 大内存应用

注

本节中描述的 API 套件需要一个系统 支持长波紫外线。参见 虚拟内存管理 API.

4.16.1. 预备知识#

4.16.1.1. 定义#

织物内存： 结构存储器是指可通过高速访问的存储器 互连结构，例如 NVIDIA 的 NVLink 和 NVSwitch。这种面料提供 多个之间的内存一致性和高带宽通信层 GPU 或节点，使它们能够有效地共享内存，就好像内存是 连接到统一的结构而不是隔离在各个设备上。

CUDA 12.4 及更高版本具有 VMM 分配句柄类型 CU_MEM_HANDLE_TYPE_FABRIC。在支持的平台上并提供 NVIDIA IMEX 守护进程正在运行，此分配句柄类型启用共享分配 不仅是具有任何通信机制的节点内，例如MPI，也是节点间的。 这允许多节点 NVLink 系统中的 GPU 映射所有节点的内存 其他 GPU 属于同一 NVLink 结构，即使它们位于不同的节点中。

内存句柄： 在VMM中，句柄是代表物理内存的不透明标识符 分配。这些句柄对于管理低级内存至关重要 CUDA VMM API。它们可以灵活地控制物理内存对象 可以映射到虚拟地址空间。 句柄唯一标识物理内存分配。 句柄用作对内存资源的抽象引用，而不暴露 直接指针。句柄允许诸如导出和导入内存之类的操作 跨进程或设备，促进内存共享和虚拟化。

IMEX 频道： IMEX 这个名称代表 节点间内存交换 并且是 NVIDIA 的一部分 跨不同节点的 GPU 到 GPU 通信的解决方案。 IMEX 通道是一项 GPU 驱动程序功能，可提供基于用户的内存 IMEX 域内多用户或多节点环境中的隔离。 IMEX 通道充当安全和隔离机制。

IMEX 通道与结构句柄直接相关并且必须启用 在多节点GPU通信中。当GPU分配 内存并希望使其可供不同节点上的 GPU 访问，它首先 需要导出该内存的句柄。 IMEX 通道用于 此导出过程生成一个安全的结构句柄，该句柄只能 由具有正确通道访问权限的远程进程导入。

单播内存访问： VMM API 上下文中的单播内存访问指的是 物理内存到唯一虚拟内存的受控、直接映射和访问 特定设备或进程的地址范围。而不是广播访问 对于多个设备，单播内存访问意味着特定的 GPU 设备 被授予对保留虚拟地址范围的显式读/写权限 映射到物理内存分配。

多播内存访问： VMM API 上下文中的多播内存访问指的是以下功能 用于要映射的单个物理内存分配或区域 使用多播同时连接到多个设备的虚拟地址空间 机制。这允许以一对多的方式有效地共享数据 跨多个 GPU，减少冗余数据传输 提高沟通效率。 NVIDIA 的 CUDA VMM API 支持创建绑定在一起的多播对象 来自多个设备的物理内存分配。

4.16.1.2. 查询支持#

应用程序应在尝试使用之前查询功能支持 它们的可用性可能因 GPU 架构、驱动程序而异 版本以及正在使用的特定软件库。以下部分 详细说明如何以编程方式检查必要的支持。

VMM支持 在尝试使用 VMM API 之前，应用程序必须 确保他们想要使用的设备支持 CUDA 虚拟内存 管理。以下代码示例显示了查询 VMM 支持：

int deviceSupportsVmm;
CUresult result = cuDeviceGetAttribute(&deviceSupportsVmm, CU_DEVICE_ATTRIBUTE_VIRTUAL_MEMORY_MANAGEMENT_SUPPORTED, device);
if (deviceSupportsVmm != 0) {
    // `device` 支持虚拟内存管理
}

结构内存支持： 在尝试使用结构内存之前，应用程序必须确保 他们想要使用支持结构内存的设备。下面的代码 示例显示了查询结构内存支持：

int deviceSupportsFabricMem;
CUresult result = cuDeviceGetAttribute(&deviceSupportsFabricMem, CU_DEVICE_ATTRIBUTE_HANDLE_TYPE_FABRIC_SUPPORTED, device);
if (deviceSupportsFabricMem != 0) {
    // `device` 支持 Fabric 内存
}

除了使用 CU_MEM_HANDLE_TYPE_FABRIC 作为句柄类型而不是 需要操作系统本机机制进行进程间通信以进行交换 可共享句柄，与使用结构内存相比没有区别 其他分配句柄类型。

IMEX 通道支持 在 IMEX 域内，IMEX 通道可实现安全内存共享 多用户环境。 NVIDIA 驱动程序通过创建一个 字符设备， nvidia-caps-imex-channels。使用基于织物手柄的 共享时，用户应该验证两件事：

  • 首先，应用程序必须验证该设备是否存在于 /proc/devices:

# cat /proc/devices | grep nvidia
195 nvidia
195 nvidiactl
234 nvidia-caps-imex-channels
509 nvidia-nvswitch

The nvidia-caps-imex-channels device should have a major number (e.g., 234).

  • 其次，对于两个 CUDA 进程（导出器和导入器）共享内存， 它们必须都有权访问相同的 IMEX 通道文件。这些文件，例如 作为 /dev/nvidia-caps-imex-channels/channel0, 是代表的节点 单独的 IMEX 通道。系统管理员必须创建这些文件，以便 例如，使用 马克诺德（） command.

# mknod /dev/nvidia-caps-imex-channels/channelN c <major_number> 0

This command creates channelN using the major number obtained from
/proc/devices.

注

默认情况下，驱动程序可以创建channel0 如果 NVreg_CreateImexChannel0 指定模块参数。

多播对象支持： 在尝试使用多播对象之前，应用程序必须确保 他们想要使用的设备支持他们。以下代码示例 显示查询多播对象支持：

int deviceSupportsMultiCast;
CUresult result = cuDeviceGetAttribute(&deviceSupportsMultiCast, CU_DEVICE_ATTRIBUTE_MULTICAST_SUPPORTED, device);
if (deviceSupportsMultiCast != 0) {
    // `device` 支持多播对象
}

4.16.2. API概述#

VMM API 为开发人员提供 对虚拟内存管理进行精细控制。 VMM 是一个非常低级的 API， 需要使用 CUDA驱动程序API 直接。 这种多功能 API 可用于单节点和多节点 环境。

为了有效地使用 VMM， 开发人员必须牢牢掌握内存管理中的几个关键概念： - 了解操作系统的虚拟内存基础知识，包括它如何处理页面和地址空间 - 需要了解内存层次结构和硬件特性 - 熟悉进程间通信（IPC）方法，例如套接字或消息传递， - 内存访问权限安全的基本知识

VMM API 工作流程涉及一系列内存管理步骤，其中 重点关注不同设备或进程之间共享内存。 最初，开发人员必须在源设备上分配物理内存。至 为了便于共享，VMM API 利用句柄来传达必要的信息 向目标设备或进程发送信息。用户必须导出句柄 共享，可以是特定于操作系统的句柄或特定于结构的 手柄。操作系统特定的句柄仅限于进程间通信 单节点，而特定于结构的手柄提供了更大的多功能性，并且可以 可用于单节点和多节点环境。重要的是 请注意，使用特定于结构的句柄需要启用 IMEX 渠道。

一旦句柄被导出，它必须与接收进程共享或 使用进程间通信协议的进程，可以选择 方法留给开发人员。然后接收进程使用VMM API 导入句柄。句柄成功导出、共享后， 导入时，源进程和目标进程都必须保留虚拟 将映射分配的物理内存的地址空间。决赛 步骤是设置每个设备的内存访问权限，确保正确 权限已建立。这整个过程，包括两个句柄 方法，在附图中进一步详细说明。

4.16.3. 单播内存共享#

共享 GPU 内存可以发生在一台具有多个 GPU 的机器上，也可以发生在多个 GPU 上 机器网络。该过程遵循以下步骤：

  • 分配和导出：一个 GPU 上的 CUDA 程序分配内存并获取 它的可共享句柄。

  • 共享和导入：然后将句柄发送到节点上的其他程序 使用IPC、MPI或NCCL等。在接收GPU中，CUDA驱动程序导入 句柄，创建必要的内存对象

  • 保留和映射：驱动程序从程序的虚拟创建映射 GPU 的地址 (VA) 其网络结构的物理地址 (PA) 地址（FA）。

  • 访问权限：设置分配的访问权限。

  • 释放内存：程序结束执行时释放所有分配的内存。

4.16.3.1. 分配和导出#

分配物理内存 使用虚拟内存管理 API 进行内存分配的第一步是 创建一个物理内存块，为分配提供支持。 为了分配物理内存，应用程序必须使用 cuMemCreate API。该函数创建的分配没有任何 设备或主机映射。函数参数 CUmemGenericAllocationHandle 描述了存储器的属性 allocate 比如分配的位置，如果分配是要 共享给另一个进程（或图形 API），或物理 要分配的内存的属性。用户必须确保所要求的 分配的大小与适当的粒度对齐。信息 关于分配的粒度要求可以使用以下方式查询 cuMemGetAllocationGranularity.

CUmemGenericAllocationHandle allocatePhysicalMemory(int device, size_t size) {
    CUmemAllocationHandleType handleType = CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR;
    CUmemAllocationProp prop = {};
    prop.type = CU_MEM_ALLOCATION_TYPE_PINNED;
    prop.location.type = CU_MEM_LOCATION_TYPE_DEVICE;
    prop.location.id = device;
    prop.requestedHandleType = handleType;

    size_t granularity = 0;
    cuMemGetAllocationGranularity(&granularity, &prop, CU_MEM_ALLOC_GRANULARITY_MINIMUM);

    // 确保大小符合分配的粒度要求
    size_t padded_size = ROUND_UP(size, granularity);

    // 分配物理内存
    CUmemGenericAllocationHandle allocHandle;
    cuMemCreate(&allocHandle, padded_size, &prop, 0);

    return allocHandle;
}

CUmemGenericAllocationHandle allocatePhysicalMemory(int device, size_t size) {
    CUmemAllocationHandleType handleType = CU_MEM_HANDLE_TYPE_FABRIC;
    CUmemAllocationProp prop = {};
    prop.type = CU_MEM_ALLOCATION_TYPE_PINNED;
    prop.location.type = CU_MEM_LOCATION_TYPE_DEVICE;
    prop.location.id = device;
    prop.requestedHandleType = handleType;

    size_t granularity = 0;
    cuMemGetAllocationGranularity(&granularity, &prop, CU_MEM_ALLOC_GRANULARITY_MINIMUM);

    // 确保大小符合分配的粒度要求
    size_t padded_size = ROUND_UP(size, granularity);

    // 分配物理内存
    CUmemGenericAllocationHandle allocHandle;
    cuMemCreate(&allocHandle, padded_size, &prop, 0);

    return allocHandle;
}

注

分配的内存由 cuMemCreate 被引用的是 CUmemGenericAllocationHandle 它返回。请注意，此参考文献是 不是指针，它的内存还无法访问。

注

可以使用以下命令查询分配句柄的属性 cuMemGetAllocationPropertiesFromHandle.

导出内存句柄 CUDA 虚拟内存管理 API 公开了一种新的进程间机制 使用句柄进行通信，以交换有关对象的必要信息 分配和物理地址空间。可以导出特定于操作系统的句柄 IPC 或特定于结构的 IPC。操作系统特定的 IPC 句柄只能在 单节点设置。织物专用手柄可用于单个或多个 节点设置。

CUmemAllocationHandleType handleType = CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR;
CUmemGenericAllocationHandle handle = allocatePhysicalMemory(0, 1<<21);
int fd;
cuMemExportToShareableHandle(&fd, handle, handleType, 0);

CUmemAllocationHandleType handleType = CU_MEM_HANDLE_TYPE_FABRIC;
CUmemGenericAllocationHandle handle = allocatePhysicalMemory(0, 1<<21);
CUmemFabricHandle fh;
cuMemExportToShareableHandle(&fh, handle, handleType, 0);

注

特定于操作系统的句柄要求所有进程都属于同一操作系统。

注

特定于结构的句柄需要系统管理员启用 IMEX 通道。

memMapIpcDrv 示例可以用作将 IPC 与 VMM 分配结合使用的示例。

4.16.3.2. 共享和导入#

共享内存句柄 一旦句柄被导出，它必须与接收进程共享或 使用进程间通信协议的进程。开发商可以自由 使用任何方法来共享句柄。具体使用的IPC方法取决于 应用程序的设计和环境。常见方法包括特定于操作系统的方法 进程间套接字和分布式消息传递。使用特定于操作系统的 IPC 提供高性能传输，但仅限于进程 同一台机器，不便携。特定于Fabric的IPC更简单、更多 便携式。然而，特定于结构的 IPC 需要系统级支持。所选择的 方法必须安全可靠地将句柄数据传输到目标 进程，因此它可用于导入内存并建立有效的映射。 选择 IPC 方法的灵活性允许集成 VMM API 广泛的系统架构，从单节点应用程序到 分布式、多节点设置。在下面的代码片段中，我们将提供 使用套接字编程和接收句柄的示例 MPI。

int ipcSendShareableHandle(int socket, int fd, pid_t process) {
    struct msghdr msg;
    struct iovec iov[1];

    union {
        struct cmsghdr cm;
        char* control;
    } control_un;

    size_t sizeof_control = CMSG_SPACE(sizeof(int)) * sizeof(char);
    control_un.control = (char*) malloc(sizeof_control);

    struct cmsghdr *cmptr;
    ssize_t readResult;
    struct sockaddr_un cliaddr;
    socklen_t len = sizeof(cliaddr);

    // 构造客户端地址以将此 SShareable 句柄发送到
    memset(&cliaddr, 0, sizeof(cliaddr));
    cliaddr.sun_family = AF_UNIX;
    char temp[20];
    sprintf(temp, "%s%u", "/tmp/", process);
    strcpy(cliaddr.sun_path, temp);
    len = sizeof(cliaddr);

    // 发送对应的共享句柄给客户端
    int sendfd = fd;

    msg.msg_control = control_un.control;
    msg.msg_controllen = sizeof_control;

    cmptr = CMSG_FIRSTHDR(&msg);
    cmptr->cmsg_len = CMSG_LEN(sizeof(int));
    cmptr->cmsg_level = SOL_SOCKET;
    cmptr->cmsg_type = SCM_RIGHTS;

    memmove(CMSG_DATA(cmptr), &sendfd, sizeof(sendfd));

    msg.msg_name = (void *)&cliaddr;
    msg.msg_namelen = sizeof(struct sockaddr_un);

    iov[0].iov_base = (void *)"";
    iov[0].iov_len = 1;

    msg.msg_iovlen = 1;

        return -1;

}

int ipcRecvShareableHandle(int socket, int* fd) {

        // 字符控制[CMSG_SPACE(sizeof(int))]
        char* control;
    } control_un;

    control_un.control = (char*) malloc(sizeof_control);
    struct cmsghdr *cmptr;
    ssize_t n;

    char dummy_buffer[1];
    ssize_t sendResult;

    msg.msg_controllen = sizeof_control;

    iov[0].iov_len = sizeof(dummy_buffer);

    msg.msg_iov = iov;
    msg.msg_iovlen = 1;
    if ((n = recvmsg(socket, &msg, 0)) <= 0) {
        perror("IPC failure: Receiving data over socket failed");
        free(control_un.control);
        return -1;
    }

    if (((cmptr = CMSG_FIRSTHDR(&msg)) != NULL) &&
        (cmptr->cmsg_len == CMSG_LEN(sizeof(int)))) {
        if ((cmptr->cmsg_level != SOL_SOCKET) || (cmptr->cmsg_type != SCM_RIGHTS)) {
        free(control_un.control);
        return -1;
        }

        memmove(&receivedfd, CMSG_DATA(cmptr), sizeof(receivedfd));
        *fd = receivedfd;
    } else {
        free(control_un.control);
        return -1;
    }

    free(control_un.control);
    return 0;
}

4.16.3.3. 保护区和地图#

保留虚拟地址范围

由于地址和内存的概念在 VMM 中是不同的， 应用程序必须划分出一个可以容纳的地址范围 内存分配由 cuMemCreate。保留的地址范围必须是 至少与所有物理内存大小的总和一样大 用户计划在其中放置的分配。

应用程序可以通过传递适当的地址来保留虚拟地址范围 参数为 cuMemAddressReserve。获取到的地址范围不会 有与其关联的任何设备或主机物理内存。保留的 虚拟地址范围可以映射到属于任何设备的内存块 在系统中，从而为应用提供连续的 VA 范围支持和 由属于不同设备的内存映射。预计应用程序 使用以下命令将虚拟地址范围返回给 CUDA cuMemAddressFree。 用户在调用之前必须确保整个 VA 范围未映射 cuMemAddressFree。这些函数在概念上类似于 mmap 或 munmap 在 Linux 或 VirtualAlloc AND VirtualFree 在 Windows 上。以下 代码片段说明了该函数的用法：

CUdeviceptr ptr;
// `ptr` 保存返回的保留虚拟地址范围的开始。
CUresult result = cuMemAddressReserve(&ptr, size, 0, 0, 0); // 对齐 = 0 表示默认对齐

映射内存

分配的物理内存和划分的虚拟地址空间 前面两节分别代表内存和地址的区别 由 VMM API 引入。对于分配的内存 为了可用，用户必须将内存映射到地址空间。的 地址范围获取自 cuMemAddressReserve 和身体上的 分配获得自 cuMemCreate 或 cuMemImportFromShareableHandle 必须通过使用相互关联 cuMemMap.

用户可以将多个设备的分配关联起来以驻留在连续的位置 虚拟地址范围只要它们已经划分出足够的地址空间。 为了解耦物理分配和地址范围，用户必须 取消映射映射的地址 cuMemUnmap。用户可以绘制地图并 取消内存映射到相同的地址范围可以任意多次，只要 他们确保不会尝试在 VA 范围上创建映射 已映射的预订。下面的代码片段说明了 该函数的用法：

CUdeviceptr ptr;
// `ptr`：之前由 cuMemAddressReserve 保留的地址范围内的地址。
// `allocHandle`：通过先前调用 cuMemCreate 获得的 CUmemGenericAllocationHandle。
CUresult result = cuMemMap(ptr, size, 0, allocHandle, 0);

4.16.3.4. 访问权#

CUDA 的虚拟内存管理 API 使应用程序能够显式保护 他们的 VA 范围具有访问控制机制。将分配映射到 地址范围的区域使用 cuMemMap 不提供地址 可访问，如果由 CUDA 内核访问，将导致程序崩溃。 用户必须使用以下命令专门选择访问控制 cuMemSetAccess 在源设备和访问设备上运行。这允许或限制访问 特定设备到映射的地址范围。下面的代码片段 说明了该函数的用法：

void setAccessOnDevice(int device, CUdeviceptr ptr, size_t size) {
    CUmemAccessDesc accessDesc = {};
    accessDesc.location.type = CU_MEM_LOCATION_TYPE_DEVICE;
    accessDesc.location.id = device;
    accessDesc.flags = CU_MEM_ACCESS_FLAGS_PROT_READWRITE;

    // 使地址可访问
    cuMemSetAccess(ptr, size, &accessDesc, 1);
}

VMM 公开的访问控制机制允许 用户明确他们想要与其他人共享哪些分配 系统上的对等设备。如前所述， cudaEnablePeerAccess 强制所有先前和未来的分配 cudaMalloc 被映射到 目标对等设备。这在许多情况下很方便，因为用户没有 担心跟踪每个分配到每个设备的映射状态 在系统中。但是 这种方法 对性能有影响。 通过分配粒度的访问控制，VMM 允许以最小的开销进行对等映射。

vectorAddMMAP sample 可以作为使用虚拟的示例 内存管理 API。

4.16.3.5. 释放内存#

为了释放分配的内存和地址空间，源和目标都 流程应该使用 cuMemUnmap, cuMemRelease, 和 cuMemAddressFree 功能 按这个顺序。的 cuMemUnmap 函数取消映射先前映射的内存 从地址范围中分离出区域，有效地将物理内存从 保留的虚拟地址空间。接下来， cuMemRelease 解除分配 先前创建的物理内存，将其返回给系统。 最后， cuMemAddressFree 释放以前的虚拟地址范围 保留，以供将来使用。这个特定的顺序确保了 物理内存和虚拟内存的干净且完整的释放 地址空间。

cuMemUnmap(ptr, size);
cuMemRelease(handle);
cuMemAddressFree(ptr, size);

4.16.4. 组播内存共享#

组播对象管理 API 为应用程序提供一种创建多播对象的方法，并结合 虚拟内存管理 API 如上所述，允许应用程序在与 NVSwitch 连接的支持的 NVLink 连接 GPU 上利用 NVLink SHARP。 NVLink夏普 允许 CUDA 应用程序利用结构内计算来加速诸如广播之类的操作以及连接到 GPU 之间的减少操作 NV 开关。为此，多个 NVLink 连接的 GPU 形成一个多播组，并且该组中的每个 GPU 都使用以下命令备份多播对象： 物理内存。因此，由 N 个 GPU 组成的多播团队拥有多播对象的 N 个物理副本，每个副本都位于一个参与 GPU 的本地。 的 多媒体 PTX 指令 使用多播对象的映射可处理多播对象的所有副本。

要使用多播对象，应用程序需要

  • 查询组播支持

  • 创建多播句柄 cuMulticastCreate.

  • 与控制应参与多播组的 GPU 的所有进程共享多播句柄。这适用于 cuMemExportToShareableHandle 如上所述。

  • 添加应参与多播组的所有 GPU cuMulticastAddDevice.

  • 对于每个参与的 GPU，绑定分配的物理内存 cuMemCreate 如上所述的多播句柄。在任何设备上绑定内存之前，需要将所有设备添加到多播组中。

  • 保留地址范围、映射多播句柄并设置访问权限，如上面针对常规单播映射所述。单播和多播映射到同一物理内存是可能的。请参阅 虚拟别名支持 上面的部分介绍了如何确保到同一物理内存的多个映射之间的一致性。

  • 使用 多媒体 PTX 指令 与多播映射。

multi_node_p2p 中的示例 多 GPU 编程模型 GitHub 存储库包含一个使用结构内存（包括多播对象）来利用 NVLink SHARP 的完整示例。请注意，这个例子是 适用于 NCCL 或 NVSHMEM 等库的开发人员。它展示了 NVSHMEM 等高级编程模型如何在（多节点）内部工作 NVLink 域。应用程序开发人员通常应使用更高级别的 MPI、NCCL 或 NVSHMEM 接口，而不是此 API。

4.16.4.1. 分配组播对象#

可以使用以下命令创建多播对象 cuMulticastCreate:

CUmemGenericAllocationHandle createMCHandle(int numDevices, size_t size) {
    CUmemAllocationProp mcProp = {};
    mcProp.numDevices = numDevices;
    mcProp.handleTypes = CU_MEM_HANDLE_TYPE_FABRIC; // 或在单节点 CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR 上

    size_t granularity = 0;
    cuMulticastGetGranularity(&granularity, &mcProp, CU_MEM_ALLOC_GRANULARITY_MINIMUM);

    // 确保大小符合分配的粒度要求
    size_t padded_size = ROUND_UP(size, granularity);

    mcProp.size = padded_size;

    // 创建多播对象，该对象还没有关联的设备和物理内存
    CUmemGenericAllocationHandle mcHandle;
    cuMulticastCreate(&mcHandle, &mcProp);

    return mcHandle;
}

要在 CUDA C++ 中使用多播映射，需要使用 多媒体 PTX 指令 使用内联 PTX：

__global__ void all_reduce_norm_barrier_kernel(float* l2_norm,
                                               float* partial_l2_norm_mc,
                                               unsigned int* arrival_counter_uc, unsigned int* arrival_counter_mc,
                                               const unsigned int expected_count) {
    assert( 1 == blockDim.x * blockDim.y * blockDim.z * gridDim.x * gridDim.y * gridDim.z );
    float l2_norm_sum = 0.0;
#if __CUDA_ARCH__ >= 900

    // 原子减少到所有副本
    // 这在概念上可以被认为是 __threadfence_system(); atomicAdd_system(arrival_counter_mc, 1);
    cuda::ptx::multimem_red(cuda::ptx::release_t, cuda::ptx::scope_sys_t, cuda::ptx::op_add_t, arrival_counter_mc, n);

    // 需要在多播 (mc) 和单播 (uc) 访问同一内存 `arrival_counter_uc` 和 `arrival_counter_mc` 之间建立栅栏：
    // - fence.proxy 指令在可能通过不同代理发生的内存访问之间建立顺序
    // - .proxykind 限定符的值 .alias 是指使用虚拟别名地址对同一内存位置执行的内存访问。
    // 来自https://docs.nvidia.com/cuda/parallel-thread-execution/#parallel-synchronization-and-communication-instructions-membar
    cuda::ptx::fence_proxy_alias();

    // 自旋等待并在 UC 映射上获取排序，直到所有对等点都已到达本次迭代
    // 注意：所有等级都需要到达该内核之后的另一个屏障，这样屏障就不可能被一个
    // 如果其他某个等级很慢，则下一次迭代的等级到达。
    cuda::atomic_ref<unsigned int,cuda::thread_scope_system> ac(arrival_counter_uc);
    while (expected_count > ac.load(cuda::memory_order_acquire));

    // 所有副本的原子负载减少。它不提供排序，所以可以放心。
    asm volatile ("multimem.ld_reduce.relaxed.sys.global.add.f32 %0, [%1];" : "=f"(l2_norm_sum) : "l"(partial_l2_norm_mc) : "memory");

#else
    #error "ERROR: multimem instructions require compute capability 9.0 or larger."
#endif

    *l2_norm = std::sqrt(l2_norm_sum);
}

4.16.5. 高级配置#

4.16.5.1. 内存类型#

VMM 还为应用程序提供了一种分配特殊类型内存的机制， 某些设备可能支持。与 cuMemCreate, 应用程序可以使用指定内存类型要求 CUmemAllocationProp::allocFlags 选择特定的内存功能。 应用程序必须确保所请求的内存类型受支持 设备。

4.16.5.2. 可压缩内存#

可压缩内存可用于加速数据访问 非结构化稀疏性和其他可压缩数据模式。压缩即可 根据数据节省 DRAM 带宽、L2 读取带宽和 L2 容量。 想要分配可压缩内存的应用程序 支持计算数据压缩的设备可以通过设置来实现 CUmemAllocationProp::allocFlags::compressionType 或 CU_MEM_ALLOCATION_COMP_GENERIC。用户必须询问设备是否支持 使用计算数据压缩 CU_DEVICE_ATTRIBUTE_GENERIC_COMPRESSION_SUPPORTED。下面的代码 片段说明了查询可压缩内存支持 cuDeviceGetAttribute.

int compressionSupported = 0;
cuDeviceGetAttribute(&compressionSupported, CU_DEVICE_ATTRIBUTE_GENERIC_COMPRESSION_SUPPORTED, device);

在支持计算数据压缩的设备上，用户必须选择加入 分配时间如下图：

prop.allocFlags.compressionType = CU_MEM_ALLOCATION_COMP_GENERIC;

由于硬件资源有限等多种原因，可能无法分配 具有压缩属性。为了验证标志是否有效，用户查询属性 分配的内存使用 cuMemGetAllocationPropertiesFromHandle.

CUmemAllocationProp allocationProp = {};
cuMemGetAllocationPropertiesFromHandle(&allocationProp, allocationHandle);

if (allocationProp.allocFlags.compressionType == CU_MEM_ALLOCATION_COMP_GENERIC)
{
    // 获得可压缩内存分配
}

4.16.5.3. 虚拟别名支持#

虚拟内存管理 API 提供了一种创建多个虚拟内存的方法 使用多次调用将内存映射或“代理”到同一分配 cuMemMap 具有不同的虚拟地址。这称为虚拟别名。 除非 PTX ISA 中另有说明，否则写入分配的一个代理 被认为与相同的任何其他代理不一致和不连贯 内存直到写入设备操作（grid launch、memcpy、memset 等） 上）完成。在写入设备操作之前 GPU 上存在的网格 但也考虑写入设备操作完成后的读取 拥有不一致和不连贯的代理。

例如，以下代码片段被视为未定义，假设设备 指针 A 和 B 是同一内存分配的虚拟别名：

__global__ void foo(char *A, char *B) {
  *A = 0x1;
  printf("%d\n", *B);    // 未定义的行为！  *B 可以承担其中任何一个
// 先前的值或中间的某个值。
}

以下是定义的行为，假设这两个内核是有序的 单调地（通过流或事件）。

__global__ void foo1(char *A) {
  *A = 0x1;
}

__global__ void foo2(char *B) {
  printf("%d\n", *B);    // *B == *A == 0x1 假设 foo2 等待 foo1
// 在启动之前完成
}

cudaMemcpyAsync(B, input, size, stream1);    // 允许使用别名
// 操作边界
foo1<<<1,1,0,stream1>>>(A);                  // 允许 foo1 访问 A。
cudaEventRecord(event, stream1);
cudaStreamWaitEvent(stream2, event);
foo2<<<1,1,0,stream2>>>(B);
cudaStreamWaitEvent(stream3, event);
cudaMemcpyAsync(output, B, size, stream3);  // foo2 和
                                            // cudaMemcpy（两者
                                            // 读取）等待 foo1（写入）
                                            // 在继续之前完成

如果需要通过不同的“代理”访问相同的分配 相同的内核， fence.proxy.alias 可以在两个访问之间使用。的 因此，使用内联 PTX 汇编可以使上面的示例合法化：

__global__ void foo(char *A, char *B) {
  *A = 0x1;
  cuda::ptx::fence_proxy_alias();
  printf("%d\n", *B);    // *B == *A == 0x1
}
