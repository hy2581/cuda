4.20. 驱动入口点访问#

4.20.1. 引言#

Driver Entry Point Access APIs 提供一种检索 CUDA 驱动程序函数地址的方法。从 CUDA 11.3 开始，用户可以使用从这些 API 获取的函数指针来调用可用的 CUDA 驱动程序 API。

这些 API 提供的功能类似于 POSIX 平台上的 dlsym 和 Windows 上的 GetProcAddress。提供的 API 将允许用户：

  • 使用以下命令检索驱动程序函数的地址 CUDA Driver API.

  • 使用以下命令检索驱动程序函数的地址 CUDA 运行时 API.

  • 请求 CUDA 驱动程序函数的 每线程默认流 版本。有关更多详细信息，请参阅 检索每线程默认流版本。

  • 使用较旧的工具包但使用较新的驱动程序访问新的 CUDA 功能。

4.20.2. 驱动程序函数类型定义#

为了帮助检索 CUDA 驱动程序 API 入口点，CUDA 工具包提供对包含所有 CUDA 驱动程序 API 的函数指针定义的标头的访问。这些标头随 CUDA 工具包一起安装，并在工具包的 include/ 目录。下表总结了包含以下内容的头文件 typedefs 对于每个 CUDA API 头文件。

上面的头文件本身并没有定义实际的函数指针；它们定义了函数指针的 typedef。例如， cudaTypedefs.h 具有以下驱动程序 API 的 typedef cuMemAlloc:

typedef CUresult (CUDAAPI *PFN_cuMemAlloc_v3020)(CUdeviceptr_v2 *dptr, size_t bytesize);
typedef CUresult (CUDAAPI *PFN_cuMemAlloc_v2000)(CUdeviceptr_v1 *dptr, unsigned int bytesize);

CUDA 驱动程序符号具有基于版本的命名方案，其中 _v* 除第一个版本外，其名称中包含扩展名。当特定 CUDA 驱动程序 API 的签名或语义发生变化时，我们会增加相应驱动程序符号的版本号。在这种情况下 cuMemAlloc 驱动程序 API，第一个驱动程序符号名称是 cuMemAlloc 下一个符号名称是 cuMemAlloc_v2。 CUDA 2.0 (2000) 中引入的第一个版本的 typedef 是 PFN_cuMemAlloc_v2000。 CUDA 3.2 (3020) 中引入的下一个版本的 typedef 是 PFN_cuMemAlloc_v3020.

typedefs 可用于更轻松地在代码中定义适当类型的函数指针：

PFN_cuMemAlloc_v3020 pfn_cuMemAlloc_v2;
PFN_cuMemAlloc_v2000 pfn_cuMemAlloc_v1;

如果用户对特定版本的 API 感兴趣，则更适合使用上述方法。此外，标头还为已安装的 CUDA 工具包发布时可用的所有驱动程序符号的最新版本预定义了宏；这些 typedef 没有 _v* 后缀。对于 CUDA 11.3 工具包， cuMemAlloc_v2 是最新版本，所以我们也可以定义它的函数指针，如下所示：

PFN_cuMemAlloc pfn_cuMemAlloc;

4.20.3. 驱动程序功能检索#

使用驱动程序入口点访问 API 和适当的 typedef，我们可以获得指向任何 CUDA 驱动程序 API 的函数指针。

4.20.3.1. 使用驱动程序 API#

驱动程序 API 需要 CUDA 版本作为参数来获取所请求的驱动程序符号的 ABI 兼容版本。 CUDA 驱动程序 API 有一个按功能 ABI，用 _v* 扩展。例如，考虑以下版本 cuStreamBeginCapture 以及他们对应的 typedefs from cudaTypedefs.h:

// CUDA.h
CUresult CUDAAPI cuStreamBeginCapture(CUstream hStream);
CUresult CUDAAPI cuStreamBeginCapture_v2(CUstream hStream, CUstreamCaptureMode mode);

// cudaTypedefs.h
typedef CUresult (CUDAAPI *PFN_cuStreamBeginCapture_v10000)(CUstream hStream);
typedef CUresult (CUDAAPI *PFN_cuStreamBeginCapture_v10010)(CUstream hStream, CUstreamCaptureMode mode);

从上面 typedefs 在代码片段中，版本后缀 _v10000 或 _v10010 表明上述API分别在CUDA 10.0和 CUDA 10.1中引入。

#include <cudaTypedefs.h>

// 声明 cuStreamBeginCapture 的入口点
PFN_cuStreamBeginCapture_v10000 pfn_cuStreamBeginCapture_v1;
PFN_cuStreamBeginCapture_v10010 pfn_cuStreamBeginCapture_v2;

// 获取指向 cuStreamBeginCapture 驱动程序符号的函数指针
cuGetProcAddress("cuStreamBeginCapture", &pfn_cuStreamBeginCapture_v1, 10000, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);
// 获取指向 cuStreamBeginCapture_v2 驱动程序符号的函数指针
cuGetProcAddress("cuStreamBeginCapture", &pfn_cuStreamBeginCapture_v2, 10010, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);

参考上面的代码片段，检索地址 _v1 驱动程序 API 的版本 cuStreamBeginCapture，CUDA 版本参数应该正好是 10.0 (10000)。同样，用于检索地址的 CUDA 版本 _v2 API 的版本应为 10.1 (10010)。指定更高的 CUDA 版本来检索特定版本的驱动程序 API 可能并不总是可移植的。例如，在这里使用 11030 仍然会返回 _v2 符号，但如果是一个假设 _v3 版本在 CUDA 11.3 中发布， cuGetProcAddress API 将开始返回较新的 _v3 与 CUDA 11.3 驱动程序配对时改为使用符号。由于 ABI 和函数签名 _v2 或 _v3 符号可能会有所不同，调用 _v3 函数使用 _v10010 typedef 旨在用于 _v2 符号将表现出未定义的行为。

要检索给定 CUDA 工具包的驱动程序 API 的最新版本，我们还可以指定 CUDA_VERSION 作为 version 参数并使用无版本的 typedef 来定义函数指针。自从 _v2 是最新版本的驱动程序API cuStreamBeginCapture 在 CUDA 11.3 中，以下代码片段显示了检索它的不同方法。

// 假设我们使用 CUDA 11.3 Toolkit

#include <cudaTypedefs.h>

// 声明入口点
PFN_cuStreamBeginCapture pfn_cuStreamBeginCapture_latest;

// 初始化入口点。指定 CUDA_VERSION 将使函数指针指向
// cuStreamBeginCapture_v2 符号，因为它是 CUDA 11.3 上的最新版本。
cuGetProcAddress("cuStreamBeginCapture", &pfn_cuStreamBeginCapture_latest, CUDA_VERSION, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);

请注意，请求具有无效 CUDA 版本的驱动程序 API 将返回错误 CUDA_ERROR_NOT_FOUND。在上面的代码示例中，传入小于 10000 (CUDA 10.0) 的版本将是无效的。

4.20.3.2. 使用运行时 API#

运行时 API cudaGetDriverEntryPoint 使用 CUDA 运行时版本来获取所请求的驱动程序符号的 ABI 兼容版本。在下面的代码片段中，所需的最低 CUDA 运行时版本为 CUDA 11.2，如下所示 cuMemAllocAsync 当时就被介绍了。

#include <cudaTypedefs.h>

// 声明入口点
PFN_cuMemAllocAsync pfn_cuMemAllocAsync;

// 初始化入口点。假设 CUDA 运行时版本 >= 11.2
cudaGetDriverEntryPoint("cuMemAllocAsync", &pfn_cuMemAllocAsync, cudaEnableDefault, &driverStatus);

// 调用入口点
if(driverStatus == cudaDriverEntryPointSuccess && pfn_cuMemAllocAsync) {
    pfn_cuMemAllocAsync(...);
}

运行时 API cudaGetDriverEntryPointByVersion 使用用户提供的 CUDA 版本来获取所请求的驱动程序符号的 ABI 兼容版本。这允许对请求的 ABI 版本进行更具体的控制。

4.20.3.3. 检索每线程默认流版本#

一些 CUDA 驱动程序 API 可以配置为 默认流 或 每个线程默认流 语义。驱动程序 API 具有 每个线程默认流 语义后缀为 _ptsz 或 _ptds 以他们的名义。例如， cuLaunchKernel 有一个 每个线程默认流 变体命名为 cuLaunchKernel_ptsz。通过驱动程序入口点访问 API，用户可以请求 每个线程默认流 驱动程序 API 的版本 cuLaunchKernel 而不是 默认流 版本。配置 CUDA 驱动程序 API 默认流 或 每个线程默认流 语义影响同步行为。可以找到更多详细信息 here.

默认流 或 每个线程默认流 可以通过以下方式之一获取驱动程序 API 的版本：

  • 使用编译标志 --default-stream per-thread 或者定义宏 CUDA_API_PER_THREAD_DEFAULT_STREAM 得到 每个线程默认流 behavior.

  • Force 默认流 或 每个线程默认流 使用标志的行为 CU_GET_PROC_ADDRESS_LEGACY_STREAM/cudaEnableLegacyStream 或 CU_GET_PROC_ADDRESS_PER_THREAD_DEFAULT_STREAM/cudaEnablePerThreadDefaultStream respectively.

4.20.3.4. 访问新的 CUDA 功能#

始终建议安装最新的 CUDA 工具包来访问新的 CUDA 驱动程序功能，但如果由于某种原因，用户不想更新或无法访问最新的工具包，则只需更新 CUDA 驱动程序即可使用 API 来访问新的 CUDA 功能。为了便于讨论，我们假设用户使用 CUDA 11.3 并且想要使用新的驱动程序 API cuFoo 在 CUDA 12.0 驱动程序中可用。下面的代码片段说明了这个用例：

int main()
{
    // 假设我们安装了 CUDA 12.0 驱动程序。

    // 手动将原型定义为 cudaTypedefs.h 在 CUDA 11.3 中没有 cuFoo typedef
    typedef CUresult (CUDAAPI *PFN_cuFoo)(...);
    PFN_cuFoo pfn_cuFoo = NULL;
    CUdriverProcAddressQueryResult driverStatus;

    // 使用 cuGetProcAddress 获取 cuFoo API 的地址。指定 CUDA 版本为
    // 12000 自 cuFoo 推出以来或动态获取驱动程序版本
    // 使用 cuDriverGetVersion
    int driverVersion;
    cuDriverGetVersion(&driverVersion);
    CUresult status = cuGetProcAddress("cuFoo", &pfn_cuFoo, driverVersion, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);

    if (status == CUDA_SUCCESS && pfn_cuFoo) {
        pfn_cuFoo(...);
    }
    else {
        printf("Cannot retrieve the address to cuFoo - driverStatus = %d. Check if the latest driver for CUDA 12.0 is installed.\n", driverStatus);
        assert(0);
    }

    // 其余代码在这里

}

4.20.4. cuGetProcAddress 的潜在影响#

以下是一组潜在问题的具体和理论示例 cuGetProcAddress 或 cudaGetDriverEntryPoint.

4.20.4.1. cuGetProcAddress 与隐式链接的影响#

cuDeviceGetUuid 在 CUDA 9.2 中引入。此 API 有较新的修订版（cuDeviceGetUuid_v2）在 CUDA 11.4 中引入。为了保持次要版本兼容性， cuDeviceGetUuid 不会被版本撞到 cuDeviceGetUuid_v2 在 cuda.h 中，直到 CUDA 12.0。这意味着通过获取指向它的函数指针来调用它 cuGetProcAddress 可能有不同的行为。直接使用 API 的示例：

#include <cuda.h>

CUuuid uuid;
CUdevice dev;
CUresult status;

status = cuDeviceGet(&dev, 0); // 获取设备0
// 处理状态

status = cuDeviceGetUuid(&uuid, dev) // 获取设备0的uuid

在此示例中，假设用户使用 CUDA 11.4 进行编译。请注意，这将执行以下行为 cuDeviceGetUuid，不是 _v2 版本。现在是一个使用的例子 cuGetProcAddress:

#include <cudaTypedefs.h>

CUuuid uuid;
CUdevice dev;
CUresult status;
CUdriverProcAddressQueryResult driverStatus;

status = cuDeviceGet(&dev, 0); // 获取设备0
// 处理状态

PFN_cuDeviceGetUuid pfn_cuDeviceGetUuid;
status = cuGetProcAddress("cuDeviceGetUuid", &pfn_cuDeviceGetUuid, CUDA_VERSION, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);
if(CUDA_SUCCESS == status && pfn_cuDeviceGetUuid) {
    // pfn_cuDeviceGetUuid 指向跳转到此标题
}

在此示例中，假设用户使用 CUDA 11.4 进行编译。这将得到函数指针 cuDeviceGetUuid_v2。调用函数指针之后会调用新的_v2函数，不一样 cuDeviceGetUuid 如前面的示例所示。

4.20.4.2. cuGetProcAddress 中的编译时与运行时版本用法#

让我们以同样的问题做一点小小的调整。最后一个示例使用 CUDA_VERSION 的编译时常量来确定要获取哪个函数指针。如果用户使用动态查询驱动程序版本，则会出现更多复杂情况 cuDriverGetVersion 或 cudaDriverGetVersion 传递给 cuGetProcAddress。示例：

#include <cudaTypedefs.h>

CUuuid uuid;
CUdevice dev;
CUresult status;
int cudaVersion;
CUdriverProcAddressQueryResult driverStatus;

status = cuDeviceGet(&dev, 0); // 获取设备0
// 处理状态

status = cuDriverGetVersion(&cudaVersion);
// 处理状态

PFN_cuDeviceGetUuid pfn_cuDeviceGetUuid;
status = cuGetProcAddress("cuDeviceGetUuid", &pfn_cuDeviceGetUuid, cudaVersion, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);
if(CUDA_SUCCESS == status && pfn_cuDeviceGetUuid) {
    // pfn_cuDeviceGetUuid 指向跳转到此标题
}

在此示例中，假设用户使用 CUDA 11.3 进行编译。用户将使用已知的行为来调试、测试和部署该应用程序 cuDeviceGetUuid （不是 _v2 版本）。由于 CUDA 保证了次要版本之间的 ABI 兼容性，因此在驱动程序升级到 CUDA 11.4（无需更新工具包和运行时）后，该应用程序预计可以运行，而无需重新编译。但这将具有未定义的行为，因为现在的 typedef PFN_cuDeviceGetUuid 仍将是原始版本的签名，但因为 cudaVersion 现在是 11040 (CUDA 11.4)， cuGetProcAddress 将返回指向 _v2 版本的函数指针，这意味着调用它可能具有未定义的行为。

请注意，在这种情况下，原始（不是 _v2 版本）typedef 如下所示：

typedef CUresult (CUDAAPI *PFN_cuDeviceGetUuid_v9020)(CUuuid *uuid, CUdevice_v1 dev);

但 _v2 版本的 typedef 看起来像：

typedef CUresult (CUDAAPI *PFN_cuDeviceGetUuid_v11040)(CUuuid *uuid, CUdevice_v1 dev);

因此，在这种情况下，API/ABI 将是相同的，并且运行时 API 调用可能不会导致问题 - 只是可能会返回未知的 uuid。在 对 API/ABI 的影响，我们讨论 API/ABI 兼容性问题较多的情况。

4.20.4.3. 通过显式版本检查实现 API 版本更新#

以上，是一个具体的具体例子。现在，让我们使用一个理论示例，该示例仍然存在跨驱动程序版本的兼容性问题。示例：

CUresult cuFoo(int bar); // CUDA 11.4 中引入
CUresult cuFoo_v2(int bar); // CUDA 11.5 中引入
CUresult cuFoo_v3(int bar, void* jazz); // CUDA 11.6 中引入

typedef CUresult (CUDAAPI *PFN_cuFoo_v11040)(int bar);
typedef CUresult (CUDAAPI *PFN_cuFoo_v11050)(int bar);
typedef CUresult (CUDAAPI *PFN_cuFoo_v11060)(int bar, void* jazz);

请注意，自 CUDA 11.4 中最初创建以来，该 API 已被修改两次，最新的 CUDA 11.6 还修改了该函数的 API/ABI 接口。针对 CUDA 11.5 编译的用户代码中的用法是：

#include <cuda.h>
#include <cudaTypedefs.h>

CUresult status;
int cudaVersion;
CUdriverProcAddressQueryResult driverStatus;

status = cuDriverGetVersion(&cudaVersion);
// 处理状态

PFN_cuFoo_v11040 pfn_cuFoo_v11040;
PFN_cuFoo_v11050 pfn_cuFoo_v11050;
if(cudaVersion < 11050 ) {
    // 我们知道要获取 CUDA 11.4 版本
    status = cuGetProcAddress("cuFoo", &pfn_cuFoo_v11040, cudaVersion, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);
    // 处理状态并验证 pfn_cuFoo_v11040
}
else {
    // 假设 >= CUDA 11.5 版本我们可以使用第二个版本
    status = cuGetProcAddress("cuFoo", &pfn_cuFoo_v11050, cudaVersion, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);
    // 处理状态并验证 pfn_cuFoo_v11050
}

在此示例中，如果不更新 CUDA 11.6 中的新 typedef 并使用这些新 typedef 和案例处理重新编译应用程序，应用程序将返回 cuFoo_v3 函数指针，并且对该函数的任何使用都会导致未定义的行为。这个例子的目的是说明即使是显式版本也会检查 cuGetProcAddress 可能无法安全地覆盖 CUDA 主要版本中的次要版本变更。

4.20.4.4. 运行时 API 使用问题#

上面的示例重点关注使用驱动程序 API 来获取驱动程序 API 的函数指针的问题。现在我们将讨论运行时 API 使用的潜在问题 cudaApiGetDriverEntryPoint.

我们将首先使用与上面类似的运行时 API。

#include <cuda.h>
#include <cudaTypedefs.h>
#include <cuda_runtime.h>

CUresult status;
cudaError_t error;
int driverVersion, runtimeVersion;
CUdriverProcAddressQueryResult driverStatus;

// 向运行时询问该函数
PFN_cuDeviceGetUuid pfn_cuDeviceGetUuidRuntime;
error = cudaGetDriverEntryPoint ("cuDeviceGetUuid", &pfn_cuDeviceGetUuidRuntime, cudaEnableDefault, &driverStatus);
if(cudaSuccess == error && pfn_cuDeviceGetUuidRuntime) {
    // pfn_cuDeviceGetUuid 指向跳转到此标题
}

此示例中的函数指针甚至比上面仅包含驱动程序的示例更复杂，因为无法控制要获取哪个版本的函数；它将始终获取当前 CUDA 运行时版本的 API。请参阅下表了解更多信息：

表中的问题出现在较新的 CUDA 11.4 运行时和工具包以及较旧的驱动程序 (CUDA 11.3) 组合中，在上面标记为 v1x。这种组合将使驱动程序返回指向旧函数（非 _v2）的指针，但应用程序中使用的 typedef 将用于新函数指针。

4.20.4.5. 运行时 API 和动态版本控制问题#

当我们考虑编译应用程序的 CUDA 版本、CUDA 运行时版本和应用程序动态链接的 CUDA 驱动程序版本的不同组合时，会出现更多复杂情况。

#include <cuda.h>
#include <cudaTypedefs.h>
#include <cuda_runtime.h>

CUresult status;
cudaError_t error;
int driverVersion, runtimeVersion;
CUdriverProcAddressQueryResult driverStatus;
enum cudaDriverEntryPointQueryResult runtimeStatus;

PFN_cuDeviceGetUuid pfn_cuDeviceGetUuidDriver;
status = cuGetProcAddress("cuDeviceGetUuid", &pfn_cuDeviceGetUuidDriver, CUDA_VERSION, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);
if(CUDA_SUCCESS == status && pfn_cuDeviceGetUuidDriver) {
    // pfn_cuDeviceGetUuidDriver 指向跳转到此标题
}

// 向运行时询问该函数
PFN_cuDeviceGetUuid pfn_cuDeviceGetUuidRuntime;
error = cudaGetDriverEntryPoint ("cuDeviceGetUuid", &pfn_cuDeviceGetUuidRuntime, cudaEnableDefault, &runtimeStatus);
if(cudaSuccess == error && pfn_cuDeviceGetUuidRuntime) {
    // pfn_cuDeviceGetUuidRuntime 指向跳转到此标题
}

// 根据驱动版本向驱动询问该功能（通过runtime获取）
error = cudaDriverGetVersion(&driverVersion);
PFN_cuDeviceGetUuid pfn_cuDeviceGetUuidDriverDriverVer;
status = cuGetProcAddress ("cuDeviceGetUuid", &pfn_cuDeviceGetUuidDriverDriverVer, driverVersion, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);
if(CUDA_SUCCESS == status && pfn_cuDeviceGetUuidDriverDriverVer) {
    // pfn_cuDeviceGetUuidDriverDriverVer 指向跳转到此标题
}

4.20.4.6. 允许 CUDA 版本的运行时 API 存在问题#

除非另有指定，否则 CUDA 运行时 API cudaGetDriverEntryPointByVersion 将具有与驱动程序入口点类似的含义 cuGetProcAddress 因为它允许用户请求特定的 CUDA 驱动程序版本。

4.20.4.7. 对 API/ABI 的影响#

在上面的例子中使用 cuDeviceGetUuid，不匹配的 API 的影响很小，并且许多用户可能不会完全注意到，因为添加 _v2 是为了支持多实例 GPU (MIG) 模式。因此，在没有 MIG 的系统上，用户甚至可能没有意识到他们正在获取不同的 API。

更成问题的是 API 会更改其应用程序签名（以及 ABI），例如 cuCtxCreate。目前默认使用 CUDA 3.2 中引入的 _v2 版本 cuCtxCreate 使用时 cuda.h 但现在 CUDA 11.4 中引入了更新版本（cuCtxCreate_v3）。 API 签名也已修改，现在需要额外的参数。因此，在上述某些情况下，如果函数指针的 typedef 与返回的函数指针不匹配，则可能会出现不明显的 ABI 不兼容性，从而导致未定义的行为。

例如，假设针对安装了 CUDA 11.4 驱动程序的 CUDA 11.3 工具包编译以下代码：

PFN_cuCtxCreate cuUnknown;
CUdriverProcAddressQueryResult driverStatus;

status = cuGetProcAddress("cuCtxCreate", (void**)&cuUnknown, cudaVersion, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);
if(CUDA_SUCCESS == status && cuUnknown) {
    status = cuUnknown(&ctx, 0, dev);
}

在哪里运行此代码 cudaVersion 设置为任何 >=11040（表示 CUDA 11.4）可能会出现未定义的行为，因为没有充分提供 _v3 版本所需的所有参数 cuCtxCreate_v3 API。

4.20.5. 确定 cuGetProcAddress 失败原因#

cuGetProcAddress 有两种类型的错误。这些是 (1) API/使用错误和 (2) 无法找到所请求的驱动程序 API。第一个错误类型将通过 CUresult 返回值从 API 返回错误代码。诸如传递 NULL 作为 pfn 变量或传递无效 flags.

第二个错误类型编码在 CUdriverProcAddressQueryResult *symbolStatus 并可用于帮助区分驱动程序无法找到所请求的符号的潜在问题。举个例子：

// cuDeviceGetExecAffinitySupport 在 CUDA 11.4 版本中引入
#include <cuda.h>
CUdriverProcAddressQueryResult driverStatus;
cudaVersion = ...;
status = cuGetProcAddress("cuDeviceGetExecAffinitySupport", &pfn, cudaVersion, 0, &driverStatus);
if (CUDA_SUCCESS == status) {
    if (CU_GET_PROC_ADDRESS_VERSION_NOT_SUFFICIENT == driverStatus) {
        printf("We can use the new feature when you upgrade cudaVersion to 11.4, but CUDA driver is good to go!\n");
        // 指示 cudaVersion < 11.4 但针对 CUDA 驱动程序 >= 11.4 运行
    }
    else if (CU_GET_PROC_ADDRESS_SYMBOL_NOT_FOUND == driverStatus) {
        printf("Please update both CUDA driver and cudaVersion to at least 11.4 to use the new feature!\n");
        // 由于未找到字符串，指示驱动程序 < 11.4，无论 cudaVersion 是什么
    }
    else if (CU_GET_PROC_ADDRESS_SUCCESS == driverStatus && pfn) {
        printf("You're using cudaVersion and CUDA driver >= 11.4, using new feature!\n");
        pfn();
    }
}

第一种情况有返回码 CU_GET_PROC_ADDRESS_VERSION_NOT_SUFFICIENT 表明 symbol 在CUDA驱动中搜索时发现，但添加时间晚于 cudaVersion 提供。在示例中，指定 cudaVersion 作为 11030 或更少的值，并且当针对 CUDA 驱动程序 >= CUDA 11.4 运行时，会给出以下结果 CU_GET_PROC_ADDRESS_VERSION_NOT_SUFFICIENT。这是因为 cuDeviceGetExecAffinitySupport 已在 CUDA 11.4 (11040) 中添加。

第二种情况有返回码 CU_GET_PROC_ADDRESS_SYMBOL_NOT_FOUND 表明 symbol 在 CUDA 驱动程序中搜索时未找到。这可能是由于多种原因造成的，例如由于较旧的驱动程序导致不支持 CUDA 功能以及拼写错误。在后者中，类似于上一个示例，如果用户输入了 symbol as CUDeviceGetExecAffinitySupport - 注意大写 CU 以开始字符串 - cuGetProcAddress 由于字符串不匹配，将无法找到 API。在前一种情况下，一个示例可能是用户针对支持新 API 的 CUDA 驱动程序开发应用程序，并针对旧的 CUDA 驱动程序部署该应用程序。使用最后一个示例，如果开发人员针对 CUDA 11.4 或更高版本进行开发，但针对 CUDA 11.3 驱动程序进行部署，则在开发过程中他们可能已经成功 cuGetProcAddress，但是当部署针对 CUDA 11.3 驱动程序运行的应用程序时，该调用将不再适用于 CU_GET_PROC_ADDRESS_SYMBOL_NOT_FOUND 返回于 driverStatus.
