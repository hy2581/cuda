4.2. CUDA 图#

CUDA 图为 CUDA 中的工作提交提供了另一种模型。图由一系列操作组成，例如内核启动、数据移动等；这些操作通过依赖关系连接起来，并且图的定义与执行彼此分离。这样一来，图可以只定义一次，然后反复启动。把图的定义与执行分开可以带来多种优化：首先，相比流，CPU 端启动成本更低，因为大量设置工作已经提前完成；其次，把整个工作流程呈现给 CUDA，可以让 CUDA 执行一些基于流的分段工作提交机制无法实现的优化。

要理解图能够带来的优化，可以先看看流中的情况：当把内核放入流中时，主机驱动程序会执行一系列操作，为内核在 GPU 上执行做准备。这些用于设置和启动内核的操作属于开销，每发布一个内核都必须支付一次。对于执行时间较短的 GPU 内核，这部分开销可能占端到端总执行时间的很大比例。通过创建一个包含会被多次启动的工作流的 CUDA 图，可以在实例化期间为整个图一次性支付这些开销，之后就能以很低的开销反复启动该图。

4.2.1. 图结构#

每个操作都会形成图中的一个节点。操作之间的依赖关系就是边；这些依赖关系约束着操作的执行顺序。

只要某个操作所依赖的节点已经完成，该操作就可以在任意时刻被调度执行。具体调度由 CUDA 系统决定。

4.2.1.1. 节点类型#

图节点可以是以下类型之一：

  • 内核

  • CPU 函数调用

  • 内存拷贝

  • memset

  • 空节点

  • 等待一个 CUDA 事件

  • 记录一个 CUDA 事件

  • 发出 外部信号量 信号

  • 等待一个 外部信号量

  • 条件节点

  • 图内存节点

  • 子图：执行单独的嵌套图，如下图所示。

4.2.1.2. 边数据#

CUDA 12.3 为 CUDA 图引入了边数据。目前，非默认边数据的唯一用途是启用 程序化依赖启动.

一般来说，边数据会修改由边指定的依赖关系，由三部分组成：传出端口、传入端口和类型。传出端口指定关联边何时触发。传入端口指定节点的哪一部分依赖于关联边。类型则修改两个端点之间的关系。

端口值取决于节点类型和方向，边类型也可能只适用于特定节点类型。在所有情况下，零初始化的边数据都表示默认行为。传出端口 0 会等待整个任务，传入端口 0 会阻塞整个任务，边类型 0 表示具有内存同步行为的完整依赖关系。

边数据可以通过与节点关联的并行数组，在各种图 API 中选择性指定。如果作为输入参数省略，则使用零初始化数据。如果作为输出（查询）参数省略，则 API 会接受这些参数，但被省略的边数据都会被初始化为零；如果调用会丢弃信息，则返回 cudaErrorLossyQuery。

边数据也可用于某些流捕获 API：cudaStreamBeginCaptureToGraph()、cudaStreamGetCaptureInfo() 和 cudaStreamUpdateCaptureDependencies()。在这些情况下，下游节点尚不存在。这些数据会关联到悬空边（半边），半边会连接到后续捕获的节点，或在流捕获结束时被丢弃。请注意，某些边类型不会等待上游节点完全完成。在判断流捕获是否已经完全重新汇入原始流、以及捕获结束时是否可以丢弃它时，需要考虑这一点。参见 流捕获.

没有任何节点类型定义额外的传入端口，只有内核节点定义额外的传出端口。只有一种非默认依赖类型：cudaGraphDependencyTypeProgrammatic，用于在两个内核节点之间启用 程序化依赖启动。

4.2.2. 构建和运行图#

使用图的工作提交分为三个不同的阶段：定义、实例化和执行。

  • 在定义和创建阶段，程序会创建图中各项操作的描述，以及这些操作之间的依赖关系。

  • 实例化会对图模板拍摄快照、验证它，并执行大部分设置和初始化工作，目标是尽量减少启动时需要完成的工作。生成的实例称为可执行图。

  • 可执行图可以像其他 CUDA 工作一样启动到流中。它可以启动任意多次，而无需重复实例化。

4.2.2.1. 图创建#

可以通过两种机制创建图：使用显式图 API 和通过流捕获。

4.2.2.1.1. 图 API#

下面的示例会创建下图所示的图（省略了声明和其他样板代码）。注意示例使用 cudaGraphCreate() 创建图，并使用 cudaGraphAddNode() 添加内核节点及其依赖关系。CUDA 运行时 API 文档 列出了可用于添加节点和依赖关系的所有函数。

// 创建图，它一开始为空
cudaGraphCreate(&graph, 0);

// 创建节点及其依赖关系
cudaGraphNode_t nodes[4];
cudaGraphNodeParams kParams = { cudaGraphNodeTypeKernel };
kParams.kernel.func         = (void *)kernelName;
kParams.kernel.gridDim.x    = kParams.kernel.gridDim.y  = kParams.kernel.gridDim.z  = 1;
kParams.kernel.blockDim.x   = kParams.kernel.blockDim.y = kParams.kernel.blockDim.z = 1;

cudaGraphAddNode(&nodes[0], graph, NULL, NULL, 0, &kParams);
cudaGraphAddNode(&nodes[1], graph, &nodes[0], NULL, 1, &kParams);
cudaGraphAddNode(&nodes[2], graph, &nodes[0], NULL, 1, &kParams);
cudaGraphAddNode(&nodes[3], graph, &nodes[1], NULL, 2, &kParams);

上面的示例展示了四个内核节点之间的依赖关系，用于说明如何创建一个非常简单的图。在典型用户应用程序中，还需要添加执行内存操作的节点，例如 cudaGraphAddMemcpyNode() 等。有关添加节点的所有图 API 函数的完整参考，请参阅 CUDA 运行时 API 文档。

4.2.2.1.2. 流捕获#

流捕获提供了一种从现有的基于流的 API 创建图的机制。把工作启动到流中的代码片段（包括现有代码）可以包在一对 cudaStreamBeginCapture() 和 cudaStreamEndCapture() 调用之间，如下所示。

cudaGraph_t graph;

cudaStreamBeginCapture(stream);

kernel_A<<< ..., stream >>>(...);
kernel_B<<< ..., stream >>>(...);
libraryCall(stream);
kernel_C<<< ..., stream >>>(...);

cudaStreamEndCapture(stream, &graph);

调用 cudaStreamBeginCapture() 会使流进入捕获模式。捕获流时，启动到该流中的工作不会排队执行，而是附加到一个逐步构建的内部图中。随后调用 cudaStreamEndCapture() 会返回该图，并结束该流的捕获模式。通过流捕获主动构建的图称为捕获图。

流捕获可用于除 cudaStreamLegacy（“NULL 流”）之外的任何 CUDA 流。请注意，它可以用于 cudaStreamPerThread。如果程序正在使用遗留流，可以把流 0 重新定义为每线程流，而无需改变功能。参见 阻塞流和非阻塞流以及默认流。

可以使用 cudaStreamIsCapturing() 查询某个流是否正在被捕获。

可以使用 cudaStreamBeginCaptureToGraph() 把工作捕获到现有图中。此时，工作不会捕获到内部图，而是捕获到用户提供的图中。

4.2.2.1.2.1. 跨流依赖关系和事件#

流捕获可以处理由 cudaEventRecord() 和 cudaStreamWaitEvent() 表示的跨流依赖关系，前提是被等待的事件也记录在同一个捕获图中。

当事件记录到处于捕获模式的流中时，会得到一个捕获事件。捕获事件表示捕获图中的一组节点。

当某个流等待捕获事件时，如果该流尚未处于捕获模式，它会进入捕获模式，并且该流中的下一项工作会额外依赖于捕获事件中的节点。随后，这两个流会被捕获到同一个捕获图中。

当流捕获中存在跨流依赖关系时，仍必须在调用 cudaStreamBeginCapture() 的同一个流中调用 cudaStreamEndCapture()；该流称为原始流。由于存在基于事件的依赖关系，被捕获到同一捕获图中的任何其他流也必须重新连接回原始流，如下图所示。调用 cudaStreamEndCapture() 后，捕获到同一捕获图中的所有流都会退出捕获模式。未能重新汇入原始流会导致整个捕获操作失败。

// stream1 是原始流
cudaStreamBeginCapture(stream1);

kernel_A<<< ..., stream1 >>>(...);

// 分叉到 stream2
cudaEventRecord(event1, stream1);
cudaStreamWaitEvent(stream2, event1);

kernel_B<<< ..., stream1 >>>(...);
kernel_C<<< ..., stream2 >>>(...);

// 将 stream2 连接回原始流 (stream1)
cudaEventRecord(event2, stream2);
cudaStreamWaitEvent(stream1, event2);

kernel_D<<< ..., stream1 >>>(...);

// 结束原始流中的捕获
cudaStreamEndCapture(stream1, &graph);

// stream1 和 stream2 不再处于捕获模式

注

当流退出捕获模式时，流中的下一个非捕获项（如果有）仍会依赖于最近的前一个非捕获项，即使中间捕获项已被移除。

4.2.2.1.2.2. 禁止和未处理的操作#

同步或查询正在捕获的流、或捕获事件的执行状态是无效的，因为它们并不表示已调度执行的项。当任何关联流处于捕获模式时，查询包含活动流捕获的更大范围句柄（例如设备或上下文句柄）的执行状态，或同步这类句柄，也都是无效的。

当同一上下文中的任何流正在被捕获，并且该流不是用 cudaStreamNonBlocking 创建时，任何使用遗留流的尝试都是无效的。这是因为遗留流句柄始终包含这些其他流；向遗留流排队工作会创建对正在捕获的流的依赖关系，而查询或同步遗留流也会查询或同步正在捕获的流。

因此，在这种情况下调用同步 API 也是无效的。同步 API 的一个示例是 cudaMemcpy()，它会把工作排入遗留流，并在返回前同步该流。

注

一般来说，当依赖关系会把捕获内容与未捕获内容连接起来并排队执行时，CUDA 更倾向于返回错误，而不是忽略依赖关系。让流进入或退出捕获模式是一个例外；这一操作会切断模式转换前后添加到流中的项之间的依赖关系。

通过等待来自正在捕获的流的捕获事件来合并两个单独捕获图是无效的，因为该流关联到与该事件不同的捕获图。在未指定 cudaEventWaitExternal 标志的情况下，等待来自非捕获流的非捕获事件也是无效的。

目前，少数会把异步操作排队到流中的 API 在图中不受支持；如果用正在捕获的流调用它们，会返回错误，例如 cudaStreamAttachMemAsync()。

4.2.2.1.2.3. 失效#

如果在流捕获期间尝试无效操作，任何关联的捕获图都会失效。捕获图失效后，继续使用任何正在捕获的流、或使用与该图关联的捕获事件，都是无效的，并会返回错误，直到通过 cudaStreamEndCapture() 结束流捕获。该调用会使关联流退出捕获模式，但也会返回错误值和 NULL 图。

4.2.2.1.2.4. 捕获内省#

可以使用 cudaStreamGetCaptureInfo() 检查活动流捕获操作。该函数允许用户获取捕获状态、捕获的唯一（每进程）ID、底层图对象，以及流中将要捕获的下一个节点的依赖关系/边数据。这些依赖关系信息可用于获取流中最后捕获节点的句柄。

4.2.2.1.3. 综合示例#

图22 中的示例很简单，主要用于从概念上展示一个小型图。在实际使用 CUDA 图的应用程序中，无论使用图 API 还是流捕获，都会有更多细节。下面的代码片段并排比较了图 API 和流捕获两种写法，创建一个用于执行简单两阶段归约算法的 CUDA 图。

图23 展示了这个 CUDA 图。该图由 cudaGraphDebugDotPrint 函数作用于下面的代码生成，并为可读性做了少量调整，然后使用 Graphviz 渲染。

void cudaGraphsManual(float  *inputVec_h,
                      float  *inputVec_d,
                      double *outputVec_d,
                      double *result_d,
                      size_t  inputSize,
                      size_t  numOfBlocks)
{
   cudaStream_t                 streamForGraph;
   cudaGraph_t                  graph;
   std::vector<cudaGraphNode_t> nodeDependencies;
   cudaGraphNode_t              memcpyNode, kernelNode, memsetNode;
   double                       result_h = 0.0;

   cudaStreamCreate(&streamForGraph));

   cudaKernelNodeParams kernelNodeParams = {0};
   cudaMemcpy3DParms    memcpyParams     = {0};
   cudaMemsetParams     memsetParams     = {0};

   memcpyParams.srcArray = NULL;
   memcpyParams.srcPos   = make_cudaPos(0, 0, 0);
   memcpyParams.srcPtr   = make_cudaPitchedPtr(inputVec_h, sizeof(float) * inputSize, inputSize, 1);
   memcpyParams.dstArray = NULL;
   memcpyParams.dstPos   = make_cudaPos(0, 0, 0);
   memcpyParams.dstPtr   = make_cudaPitchedPtr(inputVec_d, sizeof(float) * inputSize, inputSize, 1);
   memcpyParams.extent   = make_cudaExtent(sizeof(float) * inputSize, 1, 1);
   memcpyParams.kind     = cudaMemcpyHostToDevice;

   memsetParams.dst         = (void *)outputVec_d;
   memsetParams.value       = 0;
   memsetParams.pitch       = 0;
   memsetParams.elementSize = sizeof(float); // elementSize 最大可为 4 个字节
   memsetParams.width       = numOfBlocks * 2;
   memsetParams.height      = 1;

   cudaGraphCreate(&graph, 0);
   cudaGraphAddMemcpyNode(&memcpyNode, graph, NULL, 0, &memcpyParams);
   cudaGraphAddMemsetNode(&memsetNode, graph, NULL, 0, &memsetParams);

   nodeDependencies.push_back(memsetNode);
   nodeDependencies.push_back(memcpyNode);

   void *kernelArgs[4] = {(void *)&inputVec_d, (void *)&outputVec_d, &inputSize, &numOfBlocks};

   kernelNodeParams.func           = (void *)reduce;
   kernelNodeParams.gridDim        = dim3(numOfBlocks, 1, 1);
   kernelNodeParams.blockDim       = dim3(THREADS_PER_BLOCK, 1, 1);
   kernelNodeParams.sharedMemBytes = 0;
   kernelNodeParams.kernelParams   = (void **)kernelArgs;
   kernelNodeParams.extra          = NULL;

   cudaGraphAddKernelNode(
      &kernelNode, graph, nodeDependencies.data(), nodeDependencies.size(), &kernelNodeParams);

   nodeDependencies.clear();
   nodeDependencies.push_back(kernelNode);

   memset(&memsetParams, 0, sizeof(memsetParams));
   memsetParams.dst         = result_d;
   memsetParams.value       = 0;
   memsetParams.elementSize = sizeof(float);
   memsetParams.width       = 2;
   memsetParams.height      = 1;
   cudaGraphAddMemsetNode(&memsetNode, graph, NULL, 0, &memsetParams);

   nodeDependencies.push_back(memsetNode);

   memset(&kernelNodeParams, 0, sizeof(kernelNodeParams));
   kernelNodeParams.func           = (void *)reduceFinal;
   kernelNodeParams.gridDim        = dim3(1, 1, 1);
   kernelNodeParams.blockDim       = dim3(THREADS_PER_BLOCK, 1, 1);
   kernelNodeParams.sharedMemBytes = 0;
   void *kernelArgs2[3]            = {(void *)&outputVec_d, (void *)&result_d, &numOfBlocks};
   kernelNodeParams.kernelParams   = kernelArgs2;
   kernelNodeParams.extra          = NULL;

   cudaGraphAddKernelNode(
      &kernelNode, graph, nodeDependencies.data(), nodeDependencies.size(), &kernelNodeParams);

   nodeDependencies.clear();
   nodeDependencies.push_back(kernelNode);

   memset(&memcpyParams, 0, sizeof(memcpyParams));

   memcpyParams.srcArray = NULL;
   memcpyParams.srcPos   = make_cudaPos(0, 0, 0);
   memcpyParams.srcPtr   = make_cudaPitchedPtr(result_d, sizeof(double), 1, 1);
   memcpyParams.dstArray = NULL;
   memcpyParams.dstPos   = make_cudaPos(0, 0, 0);
   memcpyParams.dstPtr   = make_cudaPitchedPtr(&result_h, sizeof(double), 1, 1);
   memcpyParams.extent   = make_cudaExtent(sizeof(double), 1, 1);
   memcpyParams.kind     = cudaMemcpyDeviceToHost;

   cudaGraphAddMemcpyNode(&memcpyNode, graph, nodeDependencies.data(), nodeDependencies.size(), &memcpyParams);
   nodeDependencies.clear();
   nodeDependencies.push_back(memcpyNode);

   cudaGraphNode_t    hostNode;
   cudaHostNodeParams hostParams = {0};
   hostParams.fn                 = myHostNodeCallback;
   callBackData_t hostFnData;
   hostFnData.data     = &result_h;
   hostFnData.fn_name  = "cudaGraphsManual";
   hostParams.userData = &hostFnData;

   cudaGraphAddHostNode(&hostNode, graph, nodeDependencies.data(), nodeDependencies.size(), &hostParams);
}

void cudaGraphsUsingStreamCapture(float  *inputVec_h,
                      float  *inputVec_d,
                      double *outputVec_d,
                      double *result_d,
                      size_t  inputSize,
                      size_t  numOfBlocks)
{
   cudaStream_t stream1, stream2, stream3, streamForGraph;
   cudaEvent_t  forkStreamEvent, memsetEvent1, memsetEvent2;
   cudaGraph_t  graph;
   double       result_h = 0.0;

   cudaStreamCreate(&stream1);
   cudaStreamCreate(&stream2);
   cudaStreamCreate(&stream3);
   cudaStreamCreate(&streamForGraph);

   cudaEventCreate(&forkStreamEvent);
   cudaEventCreate(&memsetEvent1);
   cudaEventCreate(&memsetEvent2);

   cudaStreamBeginCapture(stream1, cudaStreamCaptureModeGlobal);

   cudaEventRecord(forkStreamEvent, stream1);
   cudaStreamWaitEvent(stream2, forkStreamEvent, 0);
   cudaStreamWaitEvent(stream3, forkStreamEvent, 0);

   cudaMemcpyAsync(inputVec_d, inputVec_h, sizeof(float) * inputSize, cudaMemcpyDefault, stream1);

   cudaMemsetAsync(outputVec_d, 0, sizeof(double) * numOfBlocks, stream2);

   cudaEventRecord(memsetEvent1, stream2);

   cudaMemsetAsync(result_d, 0, sizeof(double), stream3);
   cudaEventRecord(memsetEvent2, stream3);

   cudaStreamWaitEvent(stream1, memsetEvent1, 0);

   reduce<<<numOfBlocks, THREADS_PER_BLOCK, 0, stream1>>>(inputVec_d, outputVec_d, inputSize, numOfBlocks);

   cudaStreamWaitEvent(stream1, memsetEvent2, 0);

   reduceFinal<<<1, THREADS_PER_BLOCK, 0, stream1>>>(outputVec_d, result_d, numOfBlocks);
   cudaMemcpyAsync(&result_h, result_d, sizeof(double), cudaMemcpyDefault, stream1);

   callBackData_t hostFnData = {0};
   hostFnData.data           = &result_h;
   hostFnData.fn_name        = "cudaGraphsUsingStreamCapture";
   cudaHostFn_t fn           = myHostNodeCallback;
   cudaLaunchHostFunc(stream1, fn, &hostFnData);
   cudaStreamEndCapture(stream1, &graph);
}

4.2.2.2. 图实例化#

通过图 API 或流捕获创建图之后，必须先将图实例化，生成可启动的可执行图。假设 cudaGraph_t graph 已经成功创建，下面的代码会实例化该图，并创建可执行图 cudaGraphExec_t graphExec：

cudaGraphExec_t graphExec;
cudaGraphInstantiate(&graphExec, graph, NULL, NULL, 0);

4.2.2.3. 图执行#

图创建完成并实例化为可执行图之后，就可以启动它。假设 cudaGraphExec_t graphExec 已经成功创建，下面的代码片段会把该图启动到指定流中：

cudaGraphLaunch(graphExec, stream);

把这些步骤结合起来，并使用 第 4.2.2.1.2 节 中的流捕获示例，下面的代码片段会创建一个图、实例化它并启动它：

cudaGraph_t graph;

cudaStreamBeginCapture(stream);

kernel_A<<< ..., stream >>>(...);
kernel_B<<< ..., stream >>>(...);
libraryCall(stream);
kernel_C<<< ..., stream >>>(...);

cudaStreamEndCapture(stream, &graph);

cudaGraphExec_t graphExec;
cudaGraphInstantiate(&graphExec, graph, NULL, NULL, 0);
cudaGraphLaunch(graphExec, stream);

4.2.3. 更新实例化图#

当工作流发生变化时，图会变得过时，因此必须修改。图结构（例如拓扑或节点类型）的重大变化需要重新实例化，因为必须重新应用与拓扑相关的优化。不过，更常见的情况是只有节点参数（例如内核参数和内存地址）发生变化，而图拓扑保持不变。针对这种情况，CUDA 提供了一种轻量级的“图更新”机制，允许就地修改某些节点参数，而无需重建整个图；这比重新实例化高效得多。

更新会在图下次启动时生效，因此不会影响之前的图启动，即使那些启动在更新发生时仍在运行。图可以反复更新并重新启动，因此可以在流上排队多个更新/启动。

CUDA 提供了两种更新实例化图参数的机制：全图更新和单个节点更新。全图更新允许用户提供一个拓扑相同、但节点中包含更新后参数的 cudaGraph_t 对象。单个节点更新允许用户显式更新各个节点的参数。当需要更新大量节点，或者调用者不知道图拓扑（例如该图来自某个库调用的流捕获）时，使用更新后的 cudaGraph_t 更方便。当改动数量较少，并且用户持有需要更新的节点句柄时，更适合使用单个节点更新。单个节点更新会跳过未改变节点的拓扑检查和比较，因此在许多情况下效率更高。

CUDA 还提供了一种启用和禁用各个节点而不影响其当前参数的机制。

以下部分更详细地解释了每种方法。

4.2.3.1. 全图更新#

cudaGraphExecUpdate() 允许使用一个拓扑相同的图（“更新图”）中的参数，更新已经实例化的图（“原始图”）。更新图的拓扑必须与用于实例化 cudaGraphExec_t 的原始图相同。此外，指定依赖关系的顺序也必须匹配。最后，CUDA 需要以一致的方式对汇点节点（没有依赖节点的节点）排序。CUDA 依赖特定 API 调用的顺序来实现一致的汇点节点排序。

更明确地说，遵循以下规则可以让 cudaGraphExecUpdate() 以确定性的方式配对原始图和更新图中的节点：

  1. 对于任何正在捕获的流，作用于该流的 API 调用必须以相同顺序发出，包括事件等待以及其他不直接对应于节点创建的 API 调用。

  2. 直接操作某个图节点传入边的 API 调用（包括捕获流 API、节点添加 API，以及边添加/删除 API）必须以相同顺序发出。此外，如果这些 API 通过数组指定依赖关系，数组内部指定依赖关系的顺序也必须匹配。

  3. 汇点节点的顺序必须一致。汇点节点是指在调用 cudaGraphExecUpdate() 时，最终图中没有依赖节点/传出边的节点。以下操作（如果存在）会影响汇点节点排序，因此作为一个整体也必须以相同顺序发出：

    • 产生汇点节点的节点添加 API。

    • 导致节点成为汇点节点的边删除操作。

    • cudaStreamUpdateCaptureDependencies()，如果它会从捕获流的依赖集合中删除某个汇点节点。

    • cudaStreamEndCapture()。

以下示例展示了如何使用 API 来更新实例化图：

cudaGraphExec_t graphExec = NULL;

for (int i = 0; i < 10; i++) {
    cudaGraph_t graph;
    cudaGraphExecUpdateResult updateResult;
    cudaGraphNode_t errorNode;

    // 在此示例中，我们使用流捕获来创建图。
    // 也可以使用图 API 生成图。
    cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);

    // 例如，调用用户定义的、基于流的工作负载
    do_cuda_work(stream);

    cudaStreamEndCapture(stream, &graph);

    // 如果已经实例化了图，则尝试直接更新它
    // 并避免实例化开销
    if (graphExec != NULL) {
        // 如果图更新失败，errorNode 将被设置为
        // 导致失败的节点和 updateResult 将被设置为
        // 原因代码。
        cudaGraphExecUpdate(graphExec, graph, &errorNode, &updateResult);
    }

    // 在第一次迭代期间或每当更新时实例化
    // 因任何原因失败
    if (graphExec == NULL || updateResult != cudaGraphExecUpdateSuccess) {

        // 如果之前的更新失败，则销毁 cudaGraphExec_t
        // 在重新实例化之前
        if (graphExec != NULL) {
            cudaGraphExecDestroy(graphExec);
        }
        // 从 graph 实例化 graphExec。错误节点和
        // 此处未使用错误消息参数。
        cudaGraphInstantiate(&graphExec, graph, NULL, NULL, 0);
    }

    cudaGraphDestroy(graph);
    cudaGraphLaunch(graphExec, stream);
    cudaStreamSynchronize(stream);
}

典型工作流程是先使用流捕获或图 API 创建初始 cudaGraph_t。随后照常实例化并启动该 cudaGraph_t。首次启动之后，使用与初始图相同的方法创建新的 cudaGraph_t，并调用 cudaGraphExecUpdate()。如果图更新成功（由上例中的 updateResult 参数指示），就启动更新后的 cudaGraphExec_t。如果更新因任何原因失败，则调用 cudaGraphExecDestroy() 和 cudaGraphInstantiate()，销毁原来的 cudaGraphExec_t 并实例化新的可执行图。

也可以直接更新 cudaGraph_t 节点（例如使用 cudaGraphKernelNodeSetParams()），随后再更新 cudaGraphExec_t；不过，使用下一节介绍的显式节点更新 API 会更高效。

条件句柄标志和默认值会作为图更新的一部分同步更新。

有关用法和当前限制的更多信息，请参阅 图 API。

4.2.3.3. 单个节点启用#

可以使用 cudaGraphNodeSetEnabled() API 启用或禁用实例化图中的内核、memset 和 memcpy 节点。这允许创建一个包含所需功能超集的图，并在每次启动时按需定制。可以使用 cudaGraphNodeGetEnabled() API 查询节点的启用状态。

禁用的节点在功能上等价于空节点，直到重新启用为止。启用或禁用节点不会影响节点参数。启用状态不会受到单个节点更新或通过 cudaGraphExecUpdate() 进行的全图更新影响。节点处于禁用状态时进行的参数更新，会在节点重新启用时生效。

有关用法和当前限制的更多信息，请参阅 图 API。

4.2.3.4. 图更新限制#

内核节点：

  • 函数的所属上下文不能更改。

  • 原本不使用 CUDA 动态并行功能的节点，不能更新为使用 CUDA 动态并行功能的节点。

cudaMemset 和 cudaMemcpy 节点：

  • 分配/映射操作数的 CUDA 设备无法更改。

  • 源/目标内存必须从与原始源/目标内存相同的上下文中分配。

  • 只能更改一维 cudaMemset/cudaMemcpy 节点。

其他 memcpy 节点限制：

  • 不支持更改源内存或目标内存的类型（例如 cudaPitchedPtr、cudaArray_t 等），也不支持更改传输类型（例如 cudaMemcpyKind）。

外部信号量等待节点和记录节点：

  • 不支持更改信号量的数量。

条件节点：

  • 图之间句柄创建和分配的顺序必须匹配。

  • 不支持更改节点参数（例如条件、节点上下文中的图数量等）。

  • 更改条件体图中节点的参数须遵守上述规则。

内存节点：

  • 如果某个 cudaGraph_t 当前已经实例化为另一个不同的 cudaGraphExec_t，则不能用它来更新某个 cudaGraphExec_t。

对主机节点、事件记录节点或事件等待节点的更新没有限制。

4.2.4. 条件图节点#

条件节点允许对包含在条件节点中的图进行条件执行和循环执行。这样一来，动态和迭代式工作流可以完整地表示在图中，同时释放主机 CPU 去并行执行其他工作。

当条件节点的依赖关系满足后，会在设备上求值条件值。条件节点可以是以下类型之一：

  • 条件 IF 节点：如果执行节点时条件值非零，则执行一次其主体图。也可以提供可选的第二个主体图；如果执行节点时条件值为零，则执行该主体图一次。

  • 条件 WHILE 节点：如果执行节点时条件值非零，则执行其主体图，并持续执行该主体图，直到条件值变为零。

  • 条件 SWITCH 节点：如果条件值等于 n，则执行一次从零开始计数的第 n 个主体图。如果条件值没有对应的主体图，则不会启动任何主体图。

条件值通过条件句柄访问，该句柄必须先于节点创建。设备代码可以使用 cudaGraphSetConditional() 设置条件值。创建句柄时，也可以指定一个应用于每次图启动的默认值。

创建条件节点时，会创建一个空图并把句柄返回给用户，以便用户填充该图。这个条件主体图可以使用 图 API 或 cudaStreamBeginCaptureToGraph() 填充。

条件节点可以嵌套。

4.2.4.1. 条件句柄#

条件值由 cudaGraphConditionalHandle 表示，并通过 cudaGraphConditionalHandleCreate() 创建。

该句柄必须与单个条件节点关联。句柄不能销毁，因此无需额外跟踪它们。

如果在创建句柄时指定 cudaGraphCondAssignDefault，则条件值会在每次图执行开始时初始化为指定的默认值。如果未提供此标志，则每次图执行开始时条件值未定义，代码不应假设条件值会跨执行保留。

与句柄关联的默认值和标志会在全图更新期间更新。

4.2.4.2. 条件节点主体图要求#

一般要求：

  • 图的所有节点都必须驻留在单个设备上。

  • 该图只能包含内核节点、空节点、memcpy 节点、memset 节点、子图节点和条件节点。

内核节点：

  • 不允许图中的内核使用 CUDA 动态并行功能或设备图启动。

  • 只要未使用 MPS，就允许协作启动。

Memcpy/Memset 节点：

  • 只允许涉及设备内存和/或固定的设备映射主机内存的拷贝/memset。

  • 不允许涉及 CUDA 数组的拷贝/memset。

  • 实例化时，两个操作数都必须可从当前设备访问。请注意，即使目标是另一个设备上的内存，拷贝操作也会从图所在的设备执行。

4.2.4.4. 条件 WHILE 节点#

只要条件非零，WHILE 节点的主体图就会执行。条件会在节点执行时求值，并在主体图完成后再次求值。下图描绘了一个 3 节点图，其中中间节点 B 是条件节点：

以下代码说明了如何创建包含 WHILE 条件节点的图。这里使用 cudaGraphCondAssignDefault 创建句柄，从而避免需要上游内核。条件主体使用 图 API 填充。

__global__ void loopKernel(cudaGraphConditionalHandle handle, char *dPtr)
{
   // 一旦 dPtr 为 0，则递减 dPtr 的值并将条件值设置为 0
   if (--(*dPtr) == 0) {
      cudaGraphSetConditional(handle, 0);
   }
}

void graphSetup() {
    cudaGraph_t graph;
    cudaGraphExec_t graphExec;
    cudaGraphNode_t node;
    void *kernelArgs[2];

    // 分配一个字节的设备内存用作输入
    char *dPtr;
    cudaMalloc((void **)&dPtr, 1);

    // 创建图
    cudaGraphCreate(&graph, 0);

    // 创建条件句柄，默认值为 1
    cudaGraphConditionalHandle handle;
    cudaGraphConditionalHandleCreate(&handle, graph, 1, cudaGraphCondAssignDefault);

    // 创建并添加 WHILE 条件节点
    cudaGraphNodeParams cParams = { cudaGraphNodeTypeConditional };
    cParams.conditional.handle = handle;
    cParams.conditional.type   = cudaGraphCondTypeWhile;
    cParams.conditional.size   = 1;
    cudaGraphAddNode(&node, graph, NULL, 0, &cParams);

    // 获取条件节点的主体图
    cudaGraph_t bodyGraph = cParams.conditional.phGraph_out[0];

    // 填充条件节点的主体图
    cudaGraphNodeParams params = { cudaGraphNodeTypeKernel };
    params.kernel.func = (void *)loopKernel;
    params.kernel.gridDim.x = params.kernel.gridDim.y = params.kernel.gridDim.z = 1;
    params.kernel.blockDim.x = params.kernel.blockDim.y = params.kernel.blockDim.z = 1;
    params.kernel.kernelParams = kernelArgs;
    kernelArgs[0] = &handle;
    kernelArgs[1] = &dPtr;
    cudaGraphAddNode(&node, bodyGraph, NULL, 0, &params);

    // 初始化设备内存、实例化并启动图
    cudaMemset(dPtr, 10, 1); // 将 dPtr 设置为 10；循环将运行直到 dPtr 为 0
    cudaGraphInstantiate(&graphExec, graph, NULL, NULL, 0);
    cudaGraphLaunch(graphExec, 0);
    cudaDeviceSynchronize();

    // 清理
    cudaGraphExecDestroy(graphExec);
    cudaGraphDestroy(graph);
    cudaFree(dPtr);
}

    // 实例化并启动图
    cudaGraphInstantiate(&graphExec, graph, NULL, NULL, 0);
    cudaGraphLaunch(graphExec, 0);
    cudaDeviceSynchronize();

    // 清理
    cudaGraphExecDestroy(graphExec);
    cudaGraphDestroy(graph);
}

4.2.5. 图内存节点#

4.2.5.1. 引言#

图内存节点允许图创建并拥有内存分配。图内存节点具有 GPU 有序的生命周期语义，用于规定何时允许在设备上访问这段内存。这些 GPU 有序生命周期语义支持由驱动程序管理的内存重用，并且与流有序分配 API cudaMallocAsync 和 cudaFreeAsync 的语义相匹配；这些 API 也可以在创建图时被捕获。

图分配在图的生命周期内具有固定地址，包括反复实例化和启动期间都是如此。这样，即使 CUDA 改变了背后的物理内存，图中的其他操作也可以直接引用这段内存，而无需更新图。在同一个图中，如果两个分配的图有序生命周期不重叠，它们可以使用相同的底层物理内存。

CUDA 可以在多个图的分配之间重用同一块物理内存，并根据 GPU 有序生命周期语义对虚拟地址映射进行别名处理。例如，当不同图被启动到同一个流中时，CUDA 可以把同一块物理内存虚拟别名到不同地址，以满足只有单图生命周期的分配需求。

4.2.5.2. API 基础知识#

图内存节点是表示内存分配或释放操作的图节点。为简洁起见，分配内存的节点称为分配节点，释放内存的节点称为释放节点。由分配节点创建的分配称为图分配。CUDA 会在创建节点时为图分配指定虚拟地址。虽然这些虚拟地址在分配节点的生命周期内固定不变，但分配的内容在释放操作之后并不会持久保留，并且可能被引用另一个分配的访问覆盖。

每次图运行时，图分配都视为重新创建。图分配的生命周期不同于节点生命周期：它从 GPU 执行到达分配图节点时开始，并在发生以下情况之一时结束：

  • GPU 执行到达释放图节点；

  • GPU 执行到达执行释放的 cudaFreeAsync() 流调用；

  • 调用 cudaFree() 执行释放时立即结束。

注

即使销毁图会结束分配节点的生命周期，也不会自动释放任何仍然存活的图分配内存。随后必须在另一个图中释放该分配，或者使用 cudaFreeAsync()/cudaFree() 释放。

与其他图结构一样，图内存节点在图中通过依赖边排序。程序必须保证访问图内存的操作：

  • 排序在分配节点之后；

  • 排序在释放该内存的操作之前。

图分配生命周期通常根据 GPU 执行开始和结束，而不是根据 API 调用开始和结束。GPU 顺序指的是工作在 GPU 上实际运行的顺序，而不是工作入队或被描述的顺序。因此，图分配被视为“GPU 有序”。

4.2.5.2.1. 图节点 API#

可以使用节点创建 API cudaGraphAddNode 显式创建图内存节点。添加 cudaGraphNodeTypeMemAlloc 节点时分配的地址，会通过传入的 cudaGraphNodeParams 结构体中的 alloc::dptr 字段返回给用户。分配图中所有使用图分配的操作都必须排序在分配节点之后。类似地，所有释放节点都必须排序在图内该分配的所有使用之后。释放节点同样使用 cudaGraphAddNode 创建，节点类型为 cudaGraphNodeTypeMemFree。

下图给出了一个包含分配节点和释放节点的示例图。内核节点 a、b 和 c 排序在分配节点之后、释放节点之前，因此这些内核可以访问该分配。内核节点 e 未排序在分配节点之后，因此不能安全访问该内存。内核节点 d 未排序在释放节点之前，因此也不能安全访问该内存。

以下代码片段建立了图中所示的图：

// 创建图，它一开始为空
cudaGraphCreate(&graph, 0);

// 分配的基本参数
cudaGraphNodeParams params = { cudaGraphNodeTypeMemAlloc };
params.alloc.poolProps.allocType = cudaMemAllocationTypePinned;
params.alloc.poolProps.location.type = cudaMemLocationTypeDevice;
// 指定设备 0 为驻留设备
params.alloc.poolProps.location.id = 0;
params.alloc.bytesize = size;

cudaGraphAddNode(&allocNode, graph, NULL, NULL, 0, &params);

// 创建一个使用图分配的内核节点
cudaGraphNodeParams nodeParams = { cudaGraphNodeTypeKernel };
nodeParams.kernel.kernelParams[0] = params.alloc.dptr;
// ...设置其他内核节点参数...

// 将内核节点添加到图中
cudaGraphAddNode(&a, graph, &allocNode, 1, NULL, &nodeParams);
cudaGraphAddNode(&b, graph, &a, 1, NULL, &nodeParams);
cudaGraphAddNode(&c, graph, &a, 1, NULL, &nodeParams);
cudaGraphNode_t dependencies[2];
// 内核节点 b 和 c 正在使用图分配，因此释放节点必须依赖于它们。由于节点 b 对节点 a 的依赖已经建立了间接依赖，释放节点不需要显式依赖节点 a。
dependencies[0] = b;
dependencies[1] = c;
cudaGraphNodeParams freeNodeParams = { cudaGraphNodeTypeMemFree };
freeNodeParams.free.dptr = params.alloc.dptr;
cudaGraphAddNode(&freeNode, graph, dependencies, NULL, 2, freeNodeParams);
// 释放节点不依赖于内核节点 d，因此 d 不能访问已释放的图分配。
cudaGraphAddNode(&d, graph, &c, NULL, 1, &nodeParams);

// 节点 e 不依赖于分配节点，因此它不能访问分配。  即使 freeNode 依赖于内核节点 e，情况也是如此。
cudaGraphAddNode(&e, graph, NULL, NULL, 0, &nodeParams);

4.2.5.2.2. 流捕获#

可以通过捕获对应的流有序分配和释放调用 cudaMallocAsync 与 cudaFreeAsync 来创建图内存节点。在这种情况下，捕获到的分配 API 返回的虚拟地址可以由图内其他操作使用。由于流有序依赖关系会被捕获到图中，因此对于正确编写的流代码，流有序分配 API 的排序要求会保证图内存节点相对于捕获到的流操作正确排序。

为清楚起见，忽略内核节点 d 和 e，以下代码片段展示了如何使用流捕获创建上一张图中的图：

cudaMallocAsync(&dptr, size, stream1);
kernel_A<<< ..., stream1 >>>(dptr, ...);

// 分叉到 stream2
cudaEventRecord(event1, stream1);
cudaStreamWaitEvent(stream2, event1);

kernel_B<<< ..., stream1 >>>(dptr, ...);
// 事件依赖关系会转换为图依赖关系，因此捕获 kernel_C 创建的内核节点将依赖捕获 cudaMallocAsync 调用创建的分配节点。
kernel_C<<< ..., stream2 >>>(dptr, ...);

// 将 stream2 连接回原始流 (stream1)
cudaEventRecord(event2, stream2);
cudaStreamWaitEvent(stream1, event2);

// 释放操作依赖于所有访问该内存的工作。
cudaFreeAsync(dptr, stream1);

// 结束原始流中的捕获
cudaStreamEndCapture(stream1, &graph);

4.2.5.2.3. 在分配图之外访问和释放图内存#

图分配不一定要由创建该分配的图释放。当某个图没有释放其分配时，该分配会在图执行结束后继续存在，并可由后续 CUDA 操作访问。只要访问操作通过 CUDA 事件和其他流排序机制排序在分配之后，就可以在另一个图中访问这些分配，也可以直接通过流操作访问。随后，可以通过常规 cudaFree、cudaFreeAsync 调用释放该分配，也可以启动另一个具有相应释放节点的图来释放，或再次启动分配图来释放（如果该图使用 cudaGraphInstantiateFlagAutoFreeOnLaunch 标志实例化）。内存释放后再访问是非法的：释放操作必须通过图依赖关系、CUDA 事件和其他流排序机制，排序在所有访问该内存的操作之后。

注

由于图分配可能共享底层物理内存，释放操作必须排序在所有设备操作完成之后。带外同步（例如计算内核内基于内存的同步）不足以建立内存写入与释放操作之间的顺序。有关一致性和相干性规则，请参阅虚拟别名支持。

以下三个代码片段演示了如何在分配图之外访问图分配，并分别通过单个流、流之间的事件，以及嵌入到分配图和释放图中的事件正确建立排序。

首先，使用单个流建立排序：

// 分配图的内容
void *dptr;
cudaGraphNodeParams params = { cudaGraphNodeTypeMemAlloc };
params.alloc.poolProps.allocType = cudaMemAllocationTypePinned;
params.alloc.poolProps.location.type = cudaMemLocationTypeDevice;
params.alloc.bytesize = size;
cudaGraphAddNode(&allocNode, allocGraph, NULL, NULL, 0, &params);
dptr = params.alloc.dptr;

cudaGraphInstantiate(&allocGraphExec, allocGraph, NULL, NULL, 0);

cudaGraphLaunch(allocGraphExec, stream);
kernel<<< ..., stream >>>(dptr, ...);
cudaFreeAsync(dptr, stream);

其次，通过记录和等待 CUDA 事件来建立排序：

// 分配图的内容
void *dptr;

// 分配图的内容
cudaGraphAddNode(&allocNode, allocGraph, NULL, NULL, 0, &allocNodeParams);
dptr = allocNodeParams.alloc.dptr;

// 消费/释放图的内容
kernelNodeParams.kernel.kernelParams[0] = allocNodeParams.alloc.dptr;
cudaGraphAddNode(&freeNode, freeGraph, NULL, NULL, 1, dptr);

cudaGraphInstantiate(&allocGraphExec, allocGraph, NULL, NULL, 0);
cudaGraphInstantiate(&freeGraphExec, freeGraph, NULL, NULL, 0);

cudaGraphLaunch(allocGraphExec, allocStream);

// 建立 stream2 对分配节点的依赖关系
// 注意：依赖关系也可以通过流同步操作建立
cudaEventRecord(allocEvent, allocStream);
cudaStreamWaitEvent(stream2, allocEvent);

kernel<<< ..., stream2 >>> (dptr, ...);

// 建立流 3 和分配使用之间的依赖关系
cudaStreamRecordEvent(streamUseDoneEvent, stream2);
cudaStreamWaitEvent(stream3, streamUseDoneEvent);

// 现在可以安全地启动释放图，它也可以访问内存
cudaGraphLaunch(freeGraphExec, stream3);

第三，使用图外部事件节点建立排序：

// 分配图的内容
void *dptr;
cudaEvent_t allocEvent; // 指示分配何时可供使用的事件。
cudaEvent_t streamUseDoneEvent; // 指示流操作何时完成分配的事件。

// 事件记录节点分配图内容
cudaGraphAddNode(&allocNode, allocGraph, NULL, NULL, 0, &allocNodeParams);
dptr = allocNodeParams.alloc.dptr;
// 注意：该事件记录节点依赖于alloc节点

cudaGraphNodeParams allocEventNodeParams = { cudaGraphNodeTypeEventRecord };
allocEventParams.eventRecord.event = allocEvent;
cudaGraphAddNode(&recordNode, allocGraph, &allocNode, NULL, 1, allocEventNodeParams);
cudaGraphInstantiate(&allocGraphExec, allocGraph, NULL, NULL, 0);

// 带有事件等待节点的消费/释放图的内容
cudaGraphNodeParams streamWaitEventNodeParams = { cudaGraphNodeTypeEventWait };
streamWaitEventNodeParams.eventWait.event = streamUseDoneEvent;
cudaGraphAddNode(&streamUseDoneEventNode, waitAndFreeGraph, NULL, NULL, 0, streamWaitEventNodeParams);

cudaGraphNodeParams allocWaitEventNodeParams = { cudaGraphNodeTypeEventWait };
allocWaitEventNodeParams.eventWait.event = allocEvent;
cudaGraphAddNode(&allocReadyEventNode, waitAndFreeGraph, NULL, NULL, 0, allocWaitEventNodeParams);

kernelNodeParams->kernelParams[0] = allocNodeParams.alloc.dptr;

// allocReadyEventNode 提供了在消费图中使用的 alloc 节点的排序。
cudaGraphAddNode(&kernelNode, waitAndFreeGraph, &allocReadyEventNode, NULL, 1, &kernelNodeParams);

// 释放节点必须排序在外部和内部使用者之后。
// 因此，该节点必须同时依赖 kernelNode 和 streamUseDoneEventNode。
dependencies[0] = kernelNode;
dependencies[1] = streamUseDoneEventNode;

cudaGraphNodeParams freeNodeParams = { cudaGraphNodeTypeMemFree };
freeNodeParams.free.dptr = dptr;
cudaGraphAddNode(&freeNode, waitAndFreeGraph, &dependencies, NULL, 2, freeNodeParams);
cudaGraphInstantiate(&waitAndFreeGraphExec, waitAndFreeGraph, NULL, NULL, 0);

cudaGraphLaunch(allocGraphExec, allocStream);

// 建立 stream2 对事件节点的依赖关系，以满足排序要求
cudaStreamWaitEvent(stream2, allocEvent);
kernel<<< ..., stream2 >>> (dptr, ...);
cudaStreamRecordEvent(streamUseDoneEvent, stream2);

// waitAndFreeGraphExec 中的事件等待节点建立对“readyForFreeEvent”的依赖关系，防止 stream2 中运行的内核在执行顺序上晚于释放节点时仍访问该分配。
cudaGraphLaunch(waitAndFreeGraphExec, stream3);

4.2.5.2.4. cudaGraphInstantiateFlagAutoFreeOnLaunch#

正常情况下，如果图中还有未释放的内存分配，CUDA 会阻止重新启动该图，因为在同一地址进行多次分配会造成内存泄漏。使用 cudaGraphInstantiateFlagAutoFreeOnLaunch 标志实例化图，可以允许图在仍有未释放分配时重新启动。在这种情况下，启动会自动插入对未释放分配的异步释放。

启动时自动释放对单生产者、多消费者算法很有用。在每次迭代中，生产者图创建若干分配；根据运行时条件，不同的消费者集合会访问这些分配。这类可变执行序列意味着消费者不能释放分配，因为后续消费者可能仍需要访问。启动时自动释放让启动循环不必跟踪生产者的分配；这些信息可以只保留在生产者的创建和销毁逻辑中。总体而言，启动时自动释放可以简化原本必须在每次重新启动前释放图所拥有全部分配的算法。

注

cudaGraphInstantiateFlagAutoFreeOnLaunch 标志不会改变图销毁的行为。即使图使用该标志实例化，应用程序仍必须显式释放未释放的内存，以避免内存泄漏。下面的代码展示了如何使用 cudaGraphInstantiateFlagAutoFreeOnLaunch 简化单生产者/多消费者算法：

// 创建生产者图，分配内存并用数据填充它
cudaStreamBeginCapture(cudaStreamPerThread, cudaStreamCaptureModeGlobal);
cudaMallocAsync(&data1, blocks * threads, cudaStreamPerThread);
cudaMallocAsync(&data2, blocks * threads, cudaStreamPerThread);
produce<<<blocks, threads, 0, cudaStreamPerThread>>>(data1, data2);
...
cudaStreamEndCapture(cudaStreamPerThread, &graph);
cudaGraphInstantiateWithFlags(&producer,
                              graph,
                              cudaGraphInstantiateFlagAutoFreeOnLaunch);
cudaGraphDestroy(graph);

// 通过捕获异步库调用创建第一个消费者图
cudaStreamBeginCapture(cudaStreamPerThread, cudaStreamCaptureModeGlobal);
consumerFromLibrary(data1, cudaStreamPerThread);
cudaStreamEndCapture(cudaStreamPerThread, &graph);
cudaGraphInstantiateWithFlags(&consumer1, graph, 0); // 常规实例化
cudaGraphDestroy(graph);

// 创建第二个消费者图
cudaStreamBeginCapture(cudaStreamPerThread, cudaStreamCaptureModeGlobal);
consume2<<<blocks, threads, 0, cudaStreamPerThread>>>(data2);
...
cudaStreamEndCapture(cudaStreamPerThread, &graph);
cudaGraphInstantiateWithFlags(&consumer2, graph, 0);
cudaGraphDestroy(graph);

// 循环启动
bool launchConsumer2 = false;
do {
    cudaGraphLaunch(producer, myStream);
    cudaGraphLaunch(consumer1, myStream);
    if (launchConsumer2) {
        cudaGraphLaunch(consumer2, myStream);
    }
} while (determineAction(&launchConsumer2));

cudaFreeAsync(data1, myStream);
cudaFreeAsync(data2, myStream);

cudaGraphExecDestroy(producer);
cudaGraphExecDestroy(consumer1);
cudaGraphExecDestroy(consumer2);

4.2.5.2.5. 子图中的内存节点#

CUDA 12.9 引入了把子图所有权移动到父图的能力。移动到父图之后，子图可以包含内存分配节点和释放节点。这样，包含分配或释放节点的子图就可以在加入父图之前独立构建。

子图被移动之后，适用以下限制：

  • 不能独立实例化或销毁。

  • 不能再作为子图添加到另一个父图中。

  • 不能用作 cuGraphExecUpdate 的参数。

  • 不能再添加额外的内存分配节点或释放节点。

// 创建子图
cudaGraphCreate(&child, 0);

// 基本分配的参数
cudaGraphNodeParams allocNodeParams = { cudaGraphNodeTypeMemAlloc };
allocNodeParams.alloc.poolProps.allocType = cudaMemAllocationTypePinned;
allocNodeParams.alloc.poolProps.location.type = cudaMemLocationTypeDevice;
// 指定设备 0 为驻留设备
allocNodeParams.alloc.poolProps.location.id = 0;
allocNodeParams.alloc.bytesize = size;

cudaGraphAddNode(&allocNode, graph, NULL, NULL, 0, &allocNodeParams);
// 可以在此处添加使用分配的其他节点
cudaGraphNodeParams freeNodeParams = { cudaGraphNodeTypeMemFree };
freeNodeParams.free.dptr = allocNodeParams.alloc.dptr;
cudaGraphAddNode(&freeNode, graph, &allocNode, NULL, 1, freeNodeParams);

// 创建父图
cudaGraphCreate(&parent, 0);

// 将子图移至父图
cudaGraphNodeParams childNodeParams = { cudaGraphNodeTypeGraph };
childNodeParams.graph.graph = child;
childNodeParams.graph.ownership = cudaGraphChildGraphOwnershipMove;
cudaGraphAddNode(&parentNode, parent, NULL, NULL, 0, &childNodeParams);

4.2.5.3. 优化内存重用#

CUDA 以两种方式重用内存：

  • 图内的虚拟内存和物理内存重用基于虚拟地址分配，这与流有序分配器中的行为类似。

  • 图之间的物理内存重用通过虚拟别名完成：不同图可以把同一块物理内存映射到各自唯一的虚拟地址。

4.2.5.3.1. 图内地址重用#

CUDA 可以通过把相同的虚拟地址范围分配给生命周期不重叠的不同分配，在图内重用内存。由于虚拟地址可以重用，指向不同分配的指针即使生命周期互不重叠，也不保证一定唯一。

下图展示了添加一个新的分配节点 (2)，该节点可以重用依赖节点 (1) 释放的地址。

4.2.5.3.2. 物理内存管理与共享#

CUDA 负责在 GPU 顺序到达分配节点之前，把物理内存映射到虚拟地址。作为对内存占用和映射开销的优化，如果多个图不会同时运行，它们可以使用相同的物理内存来满足不同分配；但是，如果物理页同时绑定到多个正在执行的图，或绑定到尚未释放的图分配，就不能重用这些物理页。

CUDA 可以在图实例化、启动或执行期间随时更新物理内存映射。CUDA 也可能在未来的图启动之间引入同步，以防止仍然存活的图分配引用同一块物理内存。和任何“分配-释放-分配”模式一样，如果程序在某个分配的生命周期之外访问指针，错误访问可能会悄悄读取或写入另一个分配拥有的存活数据，即使该分配的虚拟地址是唯一的。使用 Compute Sanitizer 工具可以捕获这类错误。

下图展示了在同一流中顺序启动的图。在此示例中，每个图都会释放自己分配的所有内存。由于同一流中的图不会并发运行，CUDA 可以，也应该，使用同一块物理内存来满足所有分配。

4.2.5.4. 性能考虑因素#

当多个图启动到同一个流中时，CUDA 会尝试为它们分配相同的物理内存，因为这些图的执行不会重叠。作为一种优化，图的物理映射会在多次启动之间保留，以避免重新映射成本。如果稍后某个图以可能与其他图重叠的方式启动（例如启动到不同流中），CUDA 就必须执行一些重新映射，因为并发图需要不同的内存来避免数据损坏。

一般来说，CUDA 中图内存发生重新映射，可能由以下操作引起：

  • 更改图启动到的流；

  • 对图内存池执行 trim 操作，显式释放未使用的内存（见物理内存占用）；

  • 当另一个图的未释放分配映射到同一块内存时，重新启动图会导致在重新启动前重新映射内存。

重新映射必须按执行顺序进行，但也必须等该图的任何先前执行完成之后才能进行，否则仍在使用的内存可能会被取消映射。由于这种顺序依赖关系，并且映射操作属于操作系统调用，映射操作可能相对昂贵。应用程序可以通过始终把包含分配内存节点的图启动到同一个流中，来避免这类成本。

4.2.5.4.1. 首次启动 / cudaGraphUpload#

图实例化期间无法分配或映射物理内存，因为此时尚不知道图将在哪个流中执行。映射会在图启动期间完成。调用 cudaGraphUpload 可以立即执行该图的所有映射，并把图与上传流关联起来，从而把分配成本从启动路径中分离出来。如果随后把图启动到同一流中，该图启动时就不需要任何额外的重新映射。

图上传和图启动使用不同流时，其行为类似于切换流，可能会导致重新映射操作。此外，不相关的内存池管理操作允许从空闲流中回收内存，这可能抵消上传带来的效果。

4.2.5.5. 物理内存占用#

异步分配的池管理行为意味着，销毁包含内存节点的图不会立即把物理内存返还给操作系统供其他进程使用，即使这些分配已经释放也是如此。要显式地把内存释放回操作系统，应用程序应使用 cudaDeviceGraphMemTrim API。

cudaDeviceGraphMemTrim 会取消映射并释放由图内存节点保留、但当前未被主动使用的任何物理内存。尚未释放的分配，以及已调度或正在运行的图，都视为正在主动使用物理内存，因此不会受到影响。使用 trim API 会让物理内存可供其他分配 API、应用程序或进程使用，但也会导致 CUDA 在被 trim 的图下次启动时重新分配并重新映射内存。请注意，cudaDeviceGraphMemTrim 操作的池不同于 cudaMemPoolTrimTo()。图内存池不会暴露给流有序内存分配器。CUDA 允许应用程序通过 cudaDeviceGetGraphMemAttribute API 查询图内存占用。查询 cudaGraphMemAttrReservedMemCurrent 属性会返回驱动程序为当前进程中的图分配保留的物理内存量。查询 cudaGraphMemAttrUsedMemCurrent 会返回当前至少被一个图映射的物理内存量。这两个属性都可以用于跟踪 CUDA 何时为了分配图而获取新的物理内存，也都有助于检查共享机制节省了多少内存。

4.2.5.6. 对等访问#

图分配可以配置为允许多个 GPU 访问。在这种情况下，CUDA 会按需把分配映射到对等 GPU。CUDA 允许需要不同映射的图分配重用同一段虚拟地址。发生这种情况时，该地址范围会被映射到不同分配所需的所有 GPU。这意味着某个分配有时可能允许比创建时请求的更多对等访问；不过，依赖这些额外映射仍然是错误的。

4.2.5.6.1. 使用图节点 API 进行对等访问#

cudaGraphAddNode API 通过分配节点参数结构中的 accessDescs 数组字段接受映射请求。嵌入的 poolProps.location 结构会指定分配的驻留设备。分配所在 GPU 默认被认为需要访问该分配，因此应用程序不需要在 accessDescs 数组中为驻留设备指定条目。

cudaGraphNodeParams allocNodeParams = { cudaGraphNodeTypeMemAlloc };
allocNodeParams.alloc.poolProps.allocType = cudaMemAllocationTypePinned;
allocNodeParams.alloc.poolProps.location.type = cudaMemLocationTypeDevice;
// 指定设备 1 为驻留设备
allocNodeParams.alloc.poolProps.location.id = 1;
allocNodeParams.alloc.bytesize = size;

// 分配驻留在设备 1 上的分配，可从设备 1 访问
cudaGraphAddNode(&allocNode, graph, NULL, NULL, 0, &allocNodeParams);

accessDescs[2];
// 访问描述符样板代码（添加节点 API 仅支持读写和设备访问）
accessDescs[0].flags = cudaMemAccessFlagsProtReadWrite;
accessDescs[0].location.type = cudaMemLocationTypeDevice;
accessDescs[1].flags = cudaMemAccessFlagsProtReadWrite;
accessDescs[1].location.type = cudaMemLocationTypeDevice;

// 设备 0 和 2 正在请求访问。设备 1 的访问要求是隐式的。
accessDescs[0].location.id = 0;
accessDescs[1].location.id = 2;

// 访问请求数组有 2 个条目。
allocNodeParams.accessDescCount = 2;
allocNodeParams.accessDescs = accessDescs;

// 分配驻留在设备 1 上的分配，可从设备 0、1 和 2 访问。（0 和 2 来自描述符，1 来自描述符，1 是驻留设备）。
cudaGraphAddNode(&allocNode, graph, NULL, NULL, 0, &allocNodeParams);

4.2.5.6.2. 通过流捕获进行对等访问#

对于流捕获，分配节点会记录捕获时分配池的对等可访问性。在捕获 cudaMallocFromPoolAsync 调用之后再更改分配池的对等可访问性，不会影响图为该分配建立的映射。

// 访问描述符样板代码（添加节点 API 仅支持读写和设备访问）
accessDesc.flags = cudaMemAccessFlagsProtReadWrite;
accessDesc.location.type = cudaMemLocationTypeDevice;
accessDesc.location.id = 1;

// 让 memPool 驻留在设备 0 上并可访问

cudaStreamBeginCapture(stream);
cudaMallocAsync(&dptr1, size, memPool, stream);
cudaStreamEndCapture(stream, &graph1);

cudaMemPoolSetAccess(memPool, &accessDesc, 1);

cudaStreamBeginCapture(stream);
cudaMallocAsync(&dptr2, size, memPool, stream);
cudaStreamEndCapture(stream, &graph2);

// 即使 memPool 现在可从设备 1 访问，分配 dptr1 的图节点仍然只具有设备 0 的可访问性。
// 分配 dptr2 的图节点将具有设备 0 和设备 1 的可访问性，因为这是调用 cudaMallocAsync 时的池可访问性。

4.2.6. 设备图启动#

许多工作流需要在运行时根据数据做出决策，并据此执行不同操作。用户可能希望在设备上完成这类决策，而不是把决策过程交给主机处理，因为后者可能需要在设备和主机之间往返。为此，CUDA 提供了从设备启动图的机制。

设备图启动提供了一种从设备执行动态控制流的便捷方式，无论是简单循环，还是复杂的设备端工作调度器，都可以使用。

下文把可以从设备启动的图称为设备图，把不能从设备启动的图称为主机图。

设备图既可以从主机启动，也可以从设备启动；主机图只能从主机启动。与主机启动不同，如果先前启动的图仍在运行，又从设备启动同一个设备图，会返回 cudaErrorInvalidValue 错误。因此，设备图不能同时从设备启动两次。同时从主机和设备启动设备图会导致未定义行为。

4.2.6.1. 设备图创建#

要从设备启动图，必须显式地为设备启动实例化该图。做法是在调用 cudaGraphInstantiate() 时传入 cudaGraphInstantiateFlagDeviceLaunch 标志。与主机图一样，设备图结构在实例化时固定，若不重新实例化便无法更新；实例化也只能在主机上执行。若要实例化为可从设备启动的图，该图必须满足若干要求。

4.2.6.1.1. 设备图要求#

一般要求：

  • 图的节点必须全部驻留在同一个设备上。

  • 该图只能包含内核节点、memcpy 节点、memset 节点和子图节点。

内核节点：

  • 不允许图中的内核使用 CUDA 动态并行性。

  • 只要未使用 MPS，就允许协作启动。

Memcpy 节点：

  • 仅允许涉及设备内存和/或固定的设备映射主机内存的拷贝。

  • 不允许涉及 CUDA 数组的拷贝。

  • 实例化时，两个操作数都必须能从当前设备访问。请注意，拷贝操作会从图所在的设备执行，即使它的目标是另一个设备上的内存。

4.2.6.1.2. 设备图上传#

要在设备上启动图，必须先把图上传到设备，以填充必要的设备资源。这可以通过两种方式完成。

第一种方式是显式上传图：可以调用 cudaGraphUpload()，也可以通过 cudaGraphInstantiateWithParams() 请求把上传作为实例化的一部分。

另一种方式是先从主机启动该图，主机启动会在启动过程中隐式执行这个上传步骤。

下面给出了三种方法的示例：

// 实例化后显式上传
cudaGraphInstantiate(&deviceGraphExec1, deviceGraph1, cudaGraphInstantiateFlagDeviceLaunch);
cudaGraphUpload(deviceGraphExec1, stream);

// 作为实例化的一部分显式上传
cudaGraphInstantiateParams instantiateParams = {0};
instantiateParams.flags = cudaGraphInstantiateFlagDeviceLaunch | cudaGraphInstantiateFlagUpload;
instantiateParams.uploadStream = stream;
cudaGraphInstantiateWithParams(&deviceGraphExec2, deviceGraph2, &instantiateParams);

// 通过主机启动隐式上传
cudaGraphInstantiate(&deviceGraphExec3, deviceGraph3, cudaGraphInstantiateFlagDeviceLaunch);
cudaGraphLaunch(deviceGraphExec3, stream);

4.2.6.1.3. 设备图更新#

设备图只能从主机更新，并且在可执行图更新后必须重新上传到设备，更新才会生效。可以使用 设备图上传 一节中介绍的相同方法完成重新上传。与主机图不同，如果在更新生效期间从设备启动设备图，会导致未定义行为。

4.2.6.2. 设备启动#

设备图可以通过 cudaGraphLaunch() 从主机和设备两端启动；该函数在设备端与主机端具有相同签名。主机端和设备端使用同一个句柄来启动设备图。从设备端启动时，设备图必须由另一个图启动。

设备端图启动按线程进行，不同线程可能同时发起多个启动，因此用户需要选择一个线程来启动给定图。

与主机启动不同，设备图不能启动到普通 CUDA 流中，只能启动到若干具名流中；每个具名流都表示一种特定的启动模式。下表列出了可用的启动模式。

4.2.6.2.1. 即发即忘启动#

顾名思义，即发即忘启动会立即提交给 GPU，并且独立于启动图运行。在“即发即忘”场景中，启动图是父图，启动图是子图。

上图可以通过下面的示例代码生成：

__global__ void launchFireAndForgetGraph(cudaGraphExec_t graph) {
    cudaGraphLaunch(graph, cudaStreamGraphFireAndForget);
}

void graphSetup() {
    cudaGraphExec_t gExec1, gExec2;
    cudaGraph_t g1, g2;

    // 创建、实例化和上传设备图。
    create_graph(&g2);
    cudaGraphInstantiate(&gExec2, g2, cudaGraphInstantiateFlagDeviceLaunch);
    cudaGraphUpload(gExec2, stream);

    // 创建并实例化启动图。
    cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);
    launchFireAndForgetGraph<<<1, 1, 0, stream>>>(gExec2);
    cudaStreamEndCapture(stream, &g1);
    cudaGraphInstantiate(&gExec1, g1);

    // 启动主机图，主机图将依次启动设备图。
    cudaGraphLaunch(gExec1, stream);
}

在一次执行过程中，一个图最多可以生成 120 个即发即忘图。这个计数会在同一个父图的两次启动之间重置。

4.2.6.2.1.1. 图执行环境#

为了充分理解设备端同步模型，首先需要理解执行环境的概念。

当从设备启动图时，它会启动到自己的执行环境中。给定图的执行环境封装了图中的所有工作以及所有生成的即发即忘工作。当该图已完成执行并且所有生成的子工作都已完成时，可以认为该图已完成。

下图展示了上一节中即发即忘示例代码会生成的环境封装关系。

这些环境也具有层级结构，因此一个图环境可以包含由即发即忘启动产生的多级子环境。

当从主机启动图时，会存在一个流环境，它是所启动图的执行环境的父环境。流环境封装了整个启动过程中生成的全部工作。当整个流环境被标记为完成时，流启动才算完成，也就是下游依赖工作可以开始运行。

4.2.6.2.2. 尾部启动#

与主机端不同，在 GPU 上无法通过 cudaDeviceSynchronize() 或 cudaStreamSynchronize() 等传统方法与设备图同步。因此，为了表达串行工作依赖关系，CUDA 提供了另一种启动模式，也就是尾部启动，用来提供类似功能。

当某个图的环境被认为完成时，尾部启动才会执行；换言之，要等该图及其所有子图都完成。当一个图完成时，尾部启动列表中下一个图的环境会替换这个已完成的环境，成为父环境的子环境。与即发即忘启动类似，一个图可以排队多个等待尾部启动的图。

上述执行流程可以通过以下代码生成：

__global__ void launchTailGraph(cudaGraphExec_t graph) {
    cudaGraphLaunch(graph, cudaStreamGraphTailLaunch);
}

void graphSetup() {
    cudaGraphExec_t gExec1, gExec2;
    cudaGraph_t g1, g2;

    // 创建、实例化和上传设备图。
    create_graph(&g2);
    cudaGraphInstantiate(&gExec2, g2, cudaGraphInstantiateFlagDeviceLaunch);
    cudaGraphUpload(gExec2, stream);

    // 创建并实例化启动图。
    cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);
    launchTailGraph<<<1, 1, 0, stream>>>(gExec2);
    cudaStreamEndCapture(stream, &g1);
    cudaGraphInstantiate(&gExec1, g1);

    // 启动主机图，主机图将依次启动设备图。
    cudaGraphLaunch(gExec1, stream);
}

由给定图排队的尾部启动将按照排队时间一次执行一个。因此，第一个排队图将首先运行，然后是第二个，依此类推。

由尾部图排队的尾部启动，会先于尾部启动列表中更早图所排队的尾部启动执行。这些新的尾部启动仍会按照各自入队顺序执行。

一个图最多可以有 255 个待处理的尾部启动。

4.2.6.2.2.1. 尾部自启动#

设备图可以把自身加入尾部启动队列，不过给定图在同一时间只能有一个自启动入队。为了查询当前正在运行的设备图，以便重新启动它，CUDA 添加了一个新的设备端函数：

cudaGraphExec_t cudaGetCurrentGraphExec();

如果当前运行的图是设备图，此函数会返回该图的句柄。如果当前执行的内核不是设备图中的节点，则该函数会返回 NULL。

下面的示例代码显示了此函数在重新启动循环中的用法：

__device__ int relaunchCount = 0;

__global__ void relaunchSelf() {
    int relaunchMax = 100;

    if (threadIdx.x == 0) {
        if (relaunchCount < relaunchMax) {
            cudaGraphLaunch(cudaGetCurrentGraphExec(), cudaStreamGraphTailLaunch);
        }

        relaunchCount++;
    }
}

4.2.6.2.3. 兄弟启动#

兄弟启动是即发即忘启动的一种变体：被启动的图不会作为启动图执行环境的子环境启动，而是作为启动图父环境的子环境启动。兄弟启动等价于从启动图的父环境发起一次即发即忘启动。

上图可以通过下面的示例代码生成：

__global__ void launchSiblingGraph(cudaGraphExec_t graph) {
    cudaGraphLaunch(graph, cudaStreamGraphFireAndForgetAsSibling);
}

void graphSetup() {
    cudaGraphExec_t gExec1, gExec2;
    cudaGraph_t g1, g2;

    // 创建、实例化和上传设备图。
    create_graph(&g2);
    cudaGraphInstantiate(&gExec2, g2, cudaGraphInstantiateFlagDeviceLaunch);
    cudaGraphUpload(gExec2, stream);

    // 创建并实例化启动图。
    cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);
    launchSiblingGraph<<<1, 1, 0, stream>>>(gExec2);
    cudaStreamEndCapture(stream, &g1);
    cudaGraphInstantiate(&gExec1, g1);

    // 启动主机图，主机图将依次启动设备图。
    cudaGraphLaunch(gExec1, stream);
}

由于兄弟启动不会进入启动图的执行环境，因此它们不会阻塞由启动图排队的尾部启动。

4.2.7. 使用图 API#

cudaGraph_t 对象不是线程安全的。用户有责任确保多个线程不会并发访问同一个 cudaGraph_t。

cudaGraphExec_t 不能与自身并发运行。启动某个 cudaGraphExec_t 时，它会排序在同一个可执行图先前启动之后。

图执行会在流中完成，以便与其他异步工作排序。不过，该流只用于排序；它不会限制图内部的并行性，也不会影响图节点的执行位置。

更多信息请参阅 图 API。

4.2.8. CUDA 用户对象#

CUDA 用户对象可用于帮助管理 CUDA 中异步工作所使用资源的生命周期。该功能尤其适用于 CUDA 图 和 流捕获。

一些资源管理方案并不兼容 CUDA 图。例如，可以考虑基于事件的池，或者“同步创建、异步销毁”的方案。

// 具有池分配功能的库 API
void libraryWork(cudaStream_t stream) {
    auto &resource = pool.claimTemporaryResource();
    resource.waitOnReadyEventInStream(stream);
    launchWork(stream, resource);
    resource.recordReadyEvent(stream);
}

// 具有异步资源删除功能的库 API
void libraryWork(cudaStream_t stream) {
    Resource *resource = new Resource(...);
    launchWork(stream, resource);
    cudaLaunchHostFunc(
        stream,
        [](void *resource) {
            delete static_cast<Resource *>(resource);
        },
        resource,
        0);
    // 未显示错误处理注意事项
}

这些方案在 CUDA 图中很难处理：资源的指针或句柄并不固定，因此需要间接访问或更新图；每次提交工作时还需要执行同步的 CPU 代码。如果这些细节对库调用者隐藏起来，它们也无法与流捕获配合使用，原因既包括捕获期间使用了不允许的 API，也包括调用者无法处理这些资源管理要求。解决办法有多种，例如把资源暴露给调用者。CUDA 用户对象提供了另一种路径。

CUDA 用户对象会把用户指定的析构函数回调与内部引用计数关联起来，类似于 C++ shared_ptr。引用可以由 CPU 上的用户代码拥有，也可以由 CUDA 图拥有。需要注意的是，对于用户拥有的引用，与 C++ 智能指针不同，并不存在一个表示该引用的对象；用户必须手动跟踪这些用户拥有的引用。一个典型用法是在创建用户对象后，立即把唯一的用户拥有引用移动到 CUDA 图中。

当引用与 CUDA 图关联后，CUDA 会自动管理图操作。克隆得到的 cudaGraph_t 会保留源 cudaGraph_t 所拥有每个引用的副本，并保持相同的重数。实例化得到的 cudaGraphExec_t 会保留源 cudaGraph_t 中每个引用的副本。如果某个 cudaGraphExec_t 在未同步的情况下被销毁，这些引用会一直保留到执行完成。

下面是一个用法示例。

cudaGraph_t graph;  // 已存在的图

Object *object = new Object;  // 析构函数可能并不平凡的 C++ 对象
cudaUserObject_t cuObject;
cudaUserObjectCreate(
    &cuObject,
    object,  // 这里我们使用 CUDA 提供的模板包装器来实现此 API，
             // 它提供了删除 C++ 对象指针的回调
    1,  // 初始引用计数
    cudaUserObjectNoDestructorSync  // 确认无法通过 CUDA
                                    // 等待该回调
);
cudaGraphRetainUserObject(
    graph,
    cuObject,
    1,  // 引用数量
    cudaGraphUserObjectMove  // 转移调用者拥有的引用（不会
                             // 修改总引用计数）
);
// 此线程不再拥有任何引用；无需调用 release API
cudaGraphExec_t graphExec;
cudaGraphInstantiate(&graphExec, graph, nullptr, nullptr, 0);  // 会保留一个
                                                               // 新引用
cudaGraphDestroy(graph);  // graphExec 仍然拥有一个引用
cudaGraphLaunch(graphExec, 0);  // 异步启动可以访问用户对象
cudaGraphExecDestroy(graphExec);  // 启动不会被同步；如有需要，
                                  // 释放会被延后
cudaStreamSynchronize(0);  // 启动同步之后，剩余
                           // 引用会被释放，析构函数将
                           // 执行。注意这会异步发生。
// 如果析构函数回调已经发出同步对象信号，
// 此时就可以安全地等待该对象。

子图节点中的图所拥有的引用与子图关联，而不是与父图关联。如果子图被更新或删除，引用也会相应变化。如果使用 cudaGraphExecUpdate 或 cudaGraphExecChildGraphNodeSetParams 更新可执行图或子图，新源图中的引用会被克隆，并替换目标图中的引用。在这两种情况下，如果先前启动尚未同步，任何原本要释放的引用都会保留到这些启动执行完成为止。

目前还没有通过 CUDA API 等待用户对象析构函数的机制。用户可以在析构函数代码中手动发出同步对象信号。另外，与 cudaLaunchHostFunc 的限制类似，不能从析构函数中调用 CUDA API。这是为了避免阻塞 CUDA 内部共享线程，从而阻碍继续推进。如果依赖关系是单向的，并且执行 API 调用的线程不会阻塞 CUDA 工作的继续推进，那么可以通知另一个线程来执行该 API 调用。

用户对象通过 cudaUserObjectCreate 创建；浏览相关 API 时，这是一个很好的起点。
