4.6. 绿色上下文#

绿色上下文 (GC) 是一种轻量级上下文，从创建之日起就与一组特定的 GPU 资源相关联。 用户可以在创建绿色上下文期间对 GPU 资源、当前流式多处理器 (SM) 和工作队列 (WQ) 进行分区，以便针对绿色上下文的 GPU 工作只能使用其预配置的 SM 和工作队列。 这样做有利于减少或更好地控制由于使用公共资源而产生的干扰。 一个应用程序可以有多个绿色上下文。

使用绿色上下文不需要任何 GPU 代码（内核）更改，只需进行小的主机端更改（例如，绿色上下文创建和为此绿色上下文创建流）。 绿色上下文功能在各种场景中都很有用。例如，它可以帮助确保某些 SM 始终可供延迟敏感的内核开始执行，假设没有其他 SM 约束，或者提供一种快速方法来测试使用较少 SM 的效果，而无需任何内核修改。

绿色上下文支持首先通过 CUDA驱动程序API。 从 CUDA 13.1 开始，上下文通过执行上下文 (EC) 抽象在 CUDA 运行时中公开。 目前，执行上下文可以对应于主上下文（上下文运行时 API 用户始终隐式与之交互）或绿色上下文。 本节将使用术语 执行上下文 或 绿色背景 当提到绿色上下文时可以互换使用。

随着绿色上下文的运行时暴露，强烈建议直接使用 CUDA 运行时 API。本节也将仅使用 CUDA 运行时 API。

本节的其余部分组织如下： 第 4.6.1 节 提供了一个激励人心的例子， 第 4.6.2 节 突出易用性，以及 第 4.6.3 节 提供设备资源和资源描述符结构。 第 4.6.4 节 解释如何创建绿色上下文， 第 4.6.5 节 如何启动针对它的工作， 和 第 4.6.6 节 重点介绍了一些额外的绿色上下文 API。最后， 第 4.6.7 节 最后举一个例子。

4.6.1. 动机/何时使用#

启动 CUDA 内核时，用户无法直接控制内核将在其上执行的 SM 数量。人们只能间接影响这一点 通过更改内核的启动几何结构或任何可能影响内核每个 SM 的最大活动线程块数的内容。 此外，当多个内核在 GPU 上并行执行时（内核在不同的 CUDA 流上运行或作为 CUDA 图的一部分运行），它们可能会 同样争夺SM资源。

然而，在某些用例中，用户需要确保始终有 GPU 资源可用于延迟敏感的工作，以便尽快启动并完成。 绿色上下文提供了一种通过划分 SM 资源来实现这一目标的方法，因此给定的绿色上下文只能使用特定的 SM（在其创建期间配置的 SM）。

图42 说明了这样一个例子。 假设有一个应用程序，其中两个独立的内核 A 和 B 在两个不同的非阻塞 CUDA 流上运行。 内核A首先启动并开始执行，占用所有可用的SM资源。当稍后启动对延迟敏感的内核 B 时，没有可用的 SM 资源。 因此，只有当内核 A 减速时，即内核 A 的线程阻塞完成执行后，内核 B 才能开始执行。 第一张图说明了关键工作 B 被延迟的情况。 y 轴显示 SM 被占用的百分比，x 轴表示时间。

使用绿色上下文，可以对 GPU 的 SM 进行分区，以便以内核 A 为目标的绿色上下文 A 可以访问 GPU 的一些 SM，而以内核 B 为目标的绿色上下文 B 可以访问其余的 SM。 在此设置中，内核 A 只能使用为绿色上下文 A 提供的 SM，无论其启动配置如何。因此，当关键内核 B 启动时，可以保证有可用的 SM 供其立即开始执行，而不受任何其他资源限制。作为第二张图 图42 如图所示，即使内核 A 的持续时间可能增加，延迟敏感的工作 B 将不再因 SM 不可用而被延迟。出于说明目的，该图显示绿色上下文 A 配备了相当于 GPU 80% SM 的 SM 计数。

这一行为无需对内核 A 和 B 进行任何代码修改即可实现。只需确保它们在属于适当绿色上下文的 CUDA 流上启动即可。每个绿色上下文可以访问的 SM 数量应由用户在绿色上下文创建期间根据具体情况决定。

工作队列:

流式多处理器是一种可以为绿色上下文配置的资源类型。 另一种资源类型是工作队列。 将工作队列视为黑盒资源抽象，它还会影响 GPU 工作执行并发性以及其他因素。 如果独立的 GPU 工作任务（例如，在不同 CUDA 流上提交的内核）映射到同一工作队列，则可能会在这些任务之间引入错误的依赖关系， 这可能导致它们的序列化执行。 用户可以通过以下方式影响 GPU 上工作队列的上限 CUDA_DEVICE_MAX_CONNECTIONS 环境变量（参见 第 5.2 节, 第 3.1 节).

在上一个示例的基础上，假设工作 B 映射到与工作 A 相同的工作队列。 在这种情况下，即使 SM 资源可用（绿色上下文情况），工作 B 可能仍然需要等待工作 A 完全完成。 与 SM 类似，用户无法直接控制可能在后台使用的特定工作队列。 但绿色上下文允许用户根据并发流排序工作负载的预期数量来表达他们期望的最大并发性。 然后，驱动程序可以使用该值作为提示，尝试阻止来自不同执行上下文的工作使用相同的工作队列，从而防止执行上下文之间出现不必要的干扰。

Attention

即使每个绿色上下文配置不同的 SM 资源和工作队列，也无法保证独立 GPU 工作的并发执行。 最好考虑下面描述的所有技术 绿色上下文 部分删除可能阻止并发执行的因素（即减少潜在的干扰）。

绿色上下文与 MIG 或 MPS

为了完整起见，本节简要比较绿色上下文与其他两种资源分区机制： MIG（多实例 GPU） 和 MPS（多进程服务）.

MIG 将 MIG 支持的 GPU 静态分区为多个 MIG 实例（“较小的 GPU”）。 这种分区必须在应用程序启动之前进行，并且不同的应用程序可以使用不同的 MIG 实例。 对于应用程序始终未充分利用可用 GPU 资源的用户来说，使用 MIG 可能是有益的；一个问题 随着 GPU 变得越来越大，这一点更加明显。通过MIG，用户可以在不同的MIG实例上运行这些不同的应用程序，从而提高GPU利用率。 MIG 对云服务提供商 (CSP) 具有吸引力，不仅因为此类应用程序可以提高 GPU 利用率，还因为 它可以为运行在不同 MIG 实例上的客户端提供服务质量 (QoS) 和隔离。请参阅上面链接的 MIG 文档了解更多详细信息。

但使用 MIG 无法解决前面描述的有问题的场景，即关键工作 B 被延迟，因为所有 SM 资源都被来自同一应用程序的其他 GPU 工作占用。 对于在单个 MIG 实例上运行的应用程序，此问题仍然可能存在。 为了解决这个问题，可以将绿色上下文与 MIG 结合使用。在这种情况下，可用于分区的 SM 资源将是给定 MIG 实例的资源。

MPS 主要针对不同的进程（例如 MPI 程序），允许它们同时在 GPU 上运行，而无需时间切片。 它要求在应用程序启动之前运行 MPS 守护程序。 默认情况下，MPS 客户端将争夺 GPU 或它们正在运行的 MIG 实例的所有可用 SM 资源。 在这种多客户端进程设置中，MPS 可以支持 SM 资源的动态分区，使用 活跃线程百分比 选项，它对 MPS 客户端进程可以使用的 SM 百分比设置上限。 与绿色上下文不同，活动线程百分比分区是在进程级别使用 MPS 进行的，并且该百分比通常在应用程序启动之前由环境变量指定。 MPS 活动线程百分比表示给定的客户端应用程序不能使用超过 x% GPU 的 SM 数，设为 N 个 SM。然而，这些 SM 可以 any GPU 的 N 个 SM，也会随时间变化。 另一方面，在其创建期间配置有N个SM的绿色上下文只能使用这些特定的N个SM。

从 CUDA 13.1 开始，如果在启动 MPS 控制守护进程时显式启用静态分区，MPS 还支持静态分区。对于静态分区，用户必须在启动应用程序时指定 MPS 客户端进程可以使用的静态分区。在这种情况下，具有活动线程百分比的动态共享不再适用。 静态分区模式下的 MPS 和绿色上下文之间的主要区别在于 MPS 针对不同的进程，而绿色上下文也适用于单个进程。 此外，与绿色上下文相反，具有静态分区的 MPS 不允许超额订阅 SM 资源。

借助 MPS，对于通过以下方式创建的 CUDA 上下文，也可以对 SM 资源进行编程分区： cuCtxCreate 驱动程序 API，具有执行亲和力。 这一编程分区允许来自一个或多个进程的不同客户端 CUDA 上下文每次使用最多指定数量的 SM。 与活动线程百分比分区一样，这些 SM 可以是 any GPU 的 SM 可以随时间变化，这与绿色上下文的情况不同。 即使存在静态 MPS 分区，此选项也是可能的。 请注意，与 MPS 上下文相比，创建绿色上下文要轻量得多，因为许多底层结构归主上下文所有，因此是共享的。

cudaStream_t strm1, strm2;
CUDA_CHECK(cudaStreamCreateWithFlags(&strm1, cudaStreamNonBlocking));
CUDA_CHECK(cudaStreamCreateWithFlags(&strm2, cudaStreamNonBlocking));

// 无法控制每个流上运行的 SM 内核数量
code_that_launches_kernels_on_streams(strm1, strm2); // 该函数中抽象的内容+内核是代码的绝大多数

cudaDevResource initial_GPU_SM_resources {};

cudaDevSmResource result[2] {{}, {}};
cudaDevSmResourceGroupParams group_params[2] =  {

CUDA_CHECK(cudaDevSmResourceSplit(&result[0], 2, &initial_GPU_SM_resources, nullptr, 0, &group_params[0]));

// 为每个资源生成资源描述符
cudaDevResourceDesc_t resource_desc1 {};
cudaDevResourceDesc_t resource_desc2 {};

CUDA_CHECK(cudaDevResourceGenerateDesc(&resource_desc2, &result[1], 1));

// 创造绿色环境
cudaExecutionContext_t my_green_ctx1 {};
cudaExecutionContext_t my_green_ctx2 {};
CUDA_CHECK(cudaGreenCtxCreate(&my_green_ctx1, resource_desc1, gpu_device_index, 0));
CUDA_CHECK(cudaGreenCtxCreate(&my_green_ctx2, resource_desc2, gpu_device_index, 0));

/* ------------------ 修改后的代码 -------------------------- */

// 您只需要使用不同的 CUDA API 来创建流
cudaStream_t strm1, strm2;
CUDA_CHECK(cudaExecutionCtxStreamCreate(&strm1, my_green_ctx1, cudaStreamDefault, 0));

4.6.3. 绿色上下文：设备资源和资源描述符#

绿色上下文的核心是设备资源（cudaDevResource）绑定到特定的 GPU 设备。 资源可以组合并封装到描述符中（cudaDevResourceDesc_t）。 绿色上下文只能访问封装到用于其创建的描述符中的资源。

目前 cudaDevResource 数据结构定义为：

struct {
     enum cudaDevResourceType type;
     union {
         struct cudaDevSmResource sm;
         struct cudaDevWorkqueueConfigResource wqConfig;
         struct cudaDevWorkqueueResource wq;
     };
 };

支持的有效资源类型是 cudaDevResourceTypeSm, cudaDevResourceTypeWorkqueueConfig 或 cudaDevResourceTypeWorkqueue，同时 cudaDevResourceTypeInvalid 标识无效的资源类型。

有效的设备资源可以与：

  • 一组特定的流式多处理器 (SM)（资源类型 cudaDevResourceTypeSm),

  • 特定的工作队列配置（资源类型 cudaDevResourceTypeWorkqueueConfig) or

  • 预先存在的工作队列资源（资源类型 cudaDevResourceTypeWorkqueue).

可以查询给定的执行上下文或 CUDA 流是否与 cudaDevResource 给定类型的资源， 使用 cudaExecutionCtxGetDevResource 或 cudaStreamGetDevResource 分别是API。 对于执行上下文来说，也可以与不同类型的设备资源（例如 SM 和工作队列）相关联， 而流只能关联SM类型的资源。

默认情况下，给定的 GPU 设备具有所有三种设备资源类型：包含 GPU 的所有 SM 的 SM 类型资源、包含所有可用工作队列的工作队列配置资源 及其相应的工作队列资源。这些资源可以通过 cudaDeviceGetDevResource API。

相关设备资源结构概述

不同的资源类型结构具有由用户或相关 CUDA API 调用显式设置的字段。 建议对所有设备资源结构进行零初始化。

  • SM类型的设备资源（cudaDevSmResource) 具有以下相关字段：

    • unsigned int smCount：该资源中可用的 SM 数量

    • unsigned int minSmPartitionSize：分区该资源所需的最小 SM 数量

    • unsigned int smCoscheduledAlignment：资源中保证在同一 GPU 处理集群上共同调度的 SM 数量，这与线程块集群相关。 smCount 是该值的倍数，当 flags 为零。

    • unsigned int flags：支持的标志为 0（默认）和 cudaDevSmResourceGroupBackfill （见 cudaDevSmResourceGroup 标志）。

    上述字段将通过适当的 split API (cudaDevSmResourceSplitByCount 或 cudaDevSmResourceSplit）用于创建此 SM 类型资源或将由 cudaDeviceGetDevResource 用于检索给定 GPU 设备的 SM 资源的 API。这些字段不应该由用户直接设置。请参阅下一节了解更多详细信息。

  • 工作队列配置设备资源（cudaDevWorkqueueConfigResource) 具有以下相关字段：

    • int device：工作队列资源可用的设备

    • unsigned int wqConcurrencyLimit：预期避免错误依赖的流排序工作负载的数量

    • enum cudaDevWorkqueueConfigScope sharingScope：工作队列资源的共享范围。支持的值为： cudaDevWorkqueueConfigScopeDeviceCtx （默认）和 cudaDevWorkqueueConfigScopeGreenCtxBalanced。使用默认选项，所有工作队列资源在所有上下文中共享，而使用平衡选项时，驱动程序尝试尽可能使用用户指定的跨绿色上下文使用非重叠工作队列资源 wqConcurrencyLimit 作为提示。

    这些字段需要由用户设置。没有类似于 split API 的 CUDA API 生成工作队列配置资源，除了由 cudaDeviceGetDevResource API。该 API 可以检索给定 GPU 设备的工作队列配置资源。

  • 最后，一个预先存在的工作队列资源（cudaDevResourceTypeWorkqueue) 没有可由用户设置的字段。与其他资源类型一样， cudaDevGetDevResource 可以检索给定 GPU 设备预先存在的工作队列资源。

4.6.4. 绿色上下文创建示例#

绿色上下文创建涉及四个主要步骤：

  • 步骤 1：从一组初始资源开始，例如获取 GPU 的可用资源

  • 第 2 步：将 SM 资源划分为一个或多个分区（使用可用的拆分 API 之一）。

  • 步骤 3：创建一个资源描述符（如果需要）组合不同的资源

  • 步骤 4：从描述符创建绿色上下文，配置其资源

创建绿色上下文后，您可以创建属于该绿色上下文的 CUDA 流。 GPU 工作随后在此类流上启动，例如通过以下方式启动的内核 <<< >>>，只能访问此绿色上下文的配置资源。 图书馆还可以轻松利用绿色上下文，只要用户将属于绿色上下文的流传递给它们即可。 参见 绿色上下文 - 启动工作 了解更多详情。

4.6.4.1. 第 1 步：获取可用 GPU 资源#

创建绿色上下文的第一步是获取可用的设备资源并填充 cudaDevResource 结构。 目前存在三个可能的起点：设备、执行上下文或 CUDA 流。

下面列出了相关的 CUDA 运行时 API 函数签名：

  • 对于一个 device: cudaError_t cudaDeviceGetDevResource(int device, cudaDevResource* resource, cudaDevResourceType type)

  • 对于一个 执行上下文: cudaError_t cudaExecutionCtxGetDevResource(cudaExecutionContext_t ctx, cudaDevResource* resource, cudaDevResourceType type)

  • 对于一个 stream: cudaError_t cudaStreamGetDevResource(cudaStream_t hStream, cudaDevResource* resource, cudaDevResourceType type)

全部有效 cudaDevResourceType 这些 API 中的每一个都允许使用类型，但以下情况除外 cudaStreamGetDevResource 只支持SM类型的资源。

通常，起点是 GPU 设备。下面的代码片段展示了如何获取给定 GPU 设备的可用 SM 资源。 成功后 cudaDeviceGetDevResource 呼叫后，用户可以查看该资源中可用的短信数量。

4.6.4.2. 步骤2：对SM资源进行分区#

创建绿色上下文的第二步是静态分割可用的 cudaDevResource SM 资源划分为一个或多个分区，并有可能 一些 SM 残留在 remaining 分区。这种分区可以使用 cudaDevSmResourceSplitByCount() 或 cudaDevSmResourceSplit() API。 的 cudaDevSmResourceSplitByCount() API只能创建一个或多个 homogeneous 分区，加上一个潜在的 remaining 分区， 而 cudaDevSmResourceSplit() API还可以创建 heterogeneous 分区，加上潜力 remaining 一。 后续部分详细描述了这两个 API 的功能。这两个API仅适用于SM类型的设备资源。

cudaDevSmResourceSplitByCount API

cudaDevSmResourceSplitByCount 运行时 API 签名为：

cudaError_t cudaDevSmResourceSplitByCount(cudaDevResource* result, unsigned int* nbGroups, const cudaDevResource* input, cudaDevResource* remaining, unsigned int useFlags, unsigned int minCount)

As 图43 突出显示，用户请求拆分 input SM型设备资源分为 *nbGroups 同质群体 minCount 每个短信。 然而，最终结果将包含一个可能更新的 *nbGroups 同质组的数量 N 每个短信。 可能更新的 *nbGroups 将小于或等于最初请求的组号，而 N 将等于或大于 minCount。 这些调整可能是由于某些特定于架构的粒度和对齐要求而发生的。

cudaDevSmResourceSplit API

如前所述，单个 cudaDevSmResourceSplitByCount API调用只能创建同构分区，即具有相同数量SM的分区加上剩余的分区。 这可能会限制异构工作负载，其中在不同绿色上下文上运行的工作具有不同的 SM 计数要求。 要使用按计数拆分 API 实现异构分区，通常需要通过重复步骤 1-4（多次）来对现有资源进行重新分区。或者，在某些情况下，作为步骤 2 的一部分，可以创建同质分区，每个分区的 SM 计数等于所有异构分区的 GCD（最大公约数），然后作为步骤 3 的一部分将所需数量的它们合并在一起。 不过，不建议使用最后一种方法，因为如果预先请求更大的大小，CUDA 驱动程序可能能够创建更好的分区。

cudaDevSmResourceSplit API 旨在通过允许用户在单次调用中创建不重叠的异构分区来解决这些限制。 的 cudaDevSmResourceSplit 运行时 API 签名为：

cudaError_t cudaDevSmResourceSplit(cudaDevResource* result, unsigned int nbGroups, const cudaDevResource* input, cudaDevResource* remainder, unsigned int flags, cudaDevSmResourceGroupParams* groupParams)

该 API 将尝试对 input SM型资源成 nbGroups 放置在的有效设备资源（组） result 数组基于为每个指定的要求 groupParams 数组。还可以创建可选的剩余分区。 成功分割后，如图 图44, 中的每个资源 result 可以有不同数量的 SM，但 SM 不能为零。

当请求异构分裂时，需要指定SM数量（smCount 相关领域 groupParams 条目）中的每个资源 result。此 SM 计数应始终是 2 的倍数。 对于上图中的场景， groupParams[0].smCount 会是 X, groupParams[1].smCount Y等 但是，如果应用程序使用，仅指定 SM 计数是不够的 线程块簇。 由于集群的所有线程块都保证被共同调度，因此用户还需要指定给定资源组应支持的最大支持集群大小（如果有）。这可以通过 coscheduledSmCount 相关领域 groupParams 条目。 对于计算能力为 10.0 及以上 (CC 10.0+) 的 GPU，集群还可以有一个首选维度，该维度是其默认集群维度的倍数。 在受支持的系统上启动单个内核期间，尽可能使用较大的首选集群维度（如果有的话），并使用较小的默认集群维度 否则。用户可以通过以下方式表达此首选簇维度提示 preferredCoscheduledSmCount 相关领域 groupParams 条目。 最后，在某些情况下，用户可能希望放宽 SM 数量要求，并在给定组中引入更多可用的 SM；用户可以通过设置来表达此回填选项 flags 相关领域 groupParams 进入其非默认标志值。

为了提供更大的灵活性， cudaDevSmResourceSplit API还有一个 discovery 模式，当提前不知道一组或多组的准确 SM 计数时使用。 例如，用户可能希望创建具有尽可能多的 SM 的设备资源，同时满足一些协同调度要求（例如，允许大小为 4 的集群）。 要执行此发现模式，用户可以设置 smCount 相关领域 groupParams 条目（或条目）为零。 成功后 cudaDevSmResourceSplit 呼叫, 的 smCount 的领域 groupParams 将填充有效的非零值；我们将此称为 actual smCount 值。 如果 result 不为空（因此这不是一次预演），那么相关组 result 也会有它的 smCount 设置为相同的值。 订单 nbGroups groupParams 条目是指定的事项，因为它们是从左（索引 0）到右（索引 nbGroups-1）进行评估的。

smCount:

  • 控制结果中相应组的 SM 数量。

  • Values：0（发现模式）或有效的非零值（非发现模式）

coscheduledSmCount:

  • 控制分组在一起（“共同调度”）的 SM 数量，以支持在计算能力 9.0+ 上启动不同的集群。因此，它会影响生成的组中 SM 的数量以及它们可以支持的集群大小。

  • Values：0（当前架构的默认值）或有效的非零值

    • 有效的非零值要求： (multiple of 2) 达到最大限制

  • 使用案例：对集群使用默认值或手动选择的值，请记住最大值。给定架构上的可移植集群大小。如果您的代码不使用集群，则可以使用支持的最小值 2 或默认值。

  • 注：当使用默认值时，以实际情况为准 coscheduledSmCount成功拆分调用后，也将满足有效的非零值要求。如果 flags 不为零，则生成的 smCount 将 >= coscheduledSmCount。将 coscheduledSmCount 视为向有效结果组提供一些有保证的底层“结构”（即，在最坏的情况下，该组可以运行至少一个 coscheduledSmCount 大小的集群）。此类结构担保不适用于其余组；在那里，用户可以探索可以启动的集群大小。

preferredCoscheduledSmCount:

  • 提示驱动程序尝试合并实际的组 coscheduledSmCount SM 分成更大的组 preferredCoscheduledSmCount 如果可能的话。这样做可以允许代码利用具有计算能力 (CC) 10.0 及以上的设备上可用的首选集群维度功能。参见 cudaLaunchAttributeValue::preferredClusterDim.

  • Values：0（当前架构的默认值）或有效的非零值

    • 有效的非零值要求： (multiple of actual coscheduledSmCount)

  • 使用案例：如果您使用首选集群并且位于计算能力 10.0 (Blackwell) 或更高版本的设备上，请使用手动选择的大于 2 的值。如果您不使用集群，请选择与以下相同的值 coscheduledSmCount：选择支持的最小值 2 或两者都使用 0

  • 注：当使用默认值时，以实际情况为准 preferredCoscheduledSmCount成功拆分调用后，也将满足有效的非零值要求。

flags:

  • 控制组的最终 SM 计数是否是实际协同调度的 SM 计数的倍数（默认），或者 SM 是否可以回填到该组中（回填）。在回填情况下，得到的 SM 计数（result[i].sm.smCount）将大于或等于指定的 groupParams[i].smCount.

  • Values：0（默认）或 cudaDevSmResourceGroupBackfill

  • 使用案例：使用零（默认），因此生成的组具有支持 coScheduledSmCount 大小的多个集群的保证灵活性。如果您希望在组中获得尽可能多的 SM，并且其中一些 SM（回填的 SM）不提供任何协同调度保证，请使用回填选项。

split_result[1].wqConfig.sharingScope = cudaDevWorkqueueConfigScopeGreenCtxBalanced;
split_result[1].wqConfig.wqConcurrencyLimit = 4;

四个工作队列并发限制向驱动程序提示用户期望最多四个并发流排序工作负载。 如果可能的话，驱动程序将尝试尊重此提示来分配工作队列。

4.6.4.4. 第 3 步：创建资源描述符#

资源分割后，下一步是使用以下内容生成资源描述符： cudaDevResourceGenerateDesc 应用程序编程接口， 预期可用于绿色上下文的所有资源。

相关的 CUDA 运行时 API 函数签名为：

cudaError_t cudaDevResourceGenerateDesc(cudaDevResourceDesc_t *phDesc, cudaDevResource *resources, unsigned int nbResources)

可以组合多个 cudaDevResource 资源。例如，下面的代码片段展示了如何生成封装三组资源的资源描述符。 您只需要确保这些资源都在连续分配 resources array.

cudaDevResource actual_split_result[5] = {};
// 未显示填充actual_split_result的代码

// 生成资源描述。封装3个资源：actual_split_result[2]到[4]
cudaDevResourceDesc_t resource_desc;
CUDA_CHECK(cudaDevResourceGenerateDesc(&resource_desc, &actual_split_result[2], 3));

还支持组合不同类型的资源。例如，可以生成具有 SM 和工作队列资源的描述符。

对于一个 cudaDevResourceGenerateDesc 调用成功：

  • All nbResources 资源应该属于同一个GPU设备。

  • 如果组合多个 SM 类型资源，则它们应由同一个拆分 API 调用生成，并具有相同的属性 coscheduledSmCount 值（如果不是余数的一部分）

  • 只能存在单个工作队列配置或工作队列类型资源。

4.6.4.5. 第四步：创造绿色上下文#

最后一步是使用资源描述符创建绿色上下文 cudaGreenCtxCreate API。 该绿色上下文只能访问其创建期间指定的资源描述符中封装的资源（例如，SM、工作队列）。 这些资源将在此步骤中配置。

相关的 CUDA 运行时 API 函数签名为：

cudaError_t cudaGreenCtxCreate(cudaExecutionContext_t *phCtx, cudaDevResourceDesc_t desc, int device, unsigned int flags)

flags 参数应设置为 0。 还建议在创建绿色上下文之前显式初始化设备的主上下文 通过任一 cudaInitDevice API 或 cudaSetDevice API，它还将主上下文设置为调用线程的当前上下文。 这样做可以确保在绿色上下文创建期间不会产生额外的主上下文初始化开销。

请参阅下面的代码片段。

int current_device = 0; // 假设单 GPU
CUDA_CHECK(cudaSetDevice(current_device)); // 或者 cudaInitDevice

cudaDevResourceDesc_t resource_desc {};
// 生成resource_desc的代码未显示

// 使用 current_device ID 在 GPU 上创建 green_ctx，并可以访问 resource_desc 中的资源
cudaExecutionContext_t green_ctx {};
CUDA_CHECK(cudaGreenCtxCreate(&green_ctx, resource_desc, current_device, 0));

成功创建绿色上下文后，用户可以通过调用来验证其资源 cudaExecutionCtxGetDevResource 在那 每种资源类型的执行上下文。

创造多重绿色上下文

一个应用程序可以有多个绿色上下文，在这种情况下，应重复上述某些步骤。 对于大多数用例，这些绿色上下文将各自具有一组单独的、不重叠的已配置 SM。 例如，对于五个同质的情况 cudaDevResource 组（actual_split_result 数组），一个绿色上下文的描述符可以封装 actual_split_result[2]到[4]资源，而另一个绿色上下文的描述符可以封装actual_split_result[0]到[1]。 在这种情况下，将仅为应用程序的两个绿色上下文之一提供特定的 SM。

但SM超额认购也是可能的，并且可以在某些情况下使用。 例如，让第二个绿色上下文的描述符将actual_split_result[0]封装到[2]是可以接受的。 在这种情况下，actual_split_resource[2]的所有SM cudaDevResource 将被超额认购，即为绿色上下文提供， 而资源actual_split_resource[0]到[1]和actual_split_resource[3]到[4]只能由两个绿色上下文之一使用。 SM 超额认购应根据具体情况明智地使用。

4.6.5. 绿色上下文 - 启动工作#

要启动针对使用前面的步骤创建的绿色上下文的内核，您首先需要使用以下命令为该绿色上下文创建一个流： cudaExecutionCtxStreamCreate API。 使用以下命令在该流上启动内核 <<< >>> 或 cudaLaunchKernel API，将确保内核只能通过其执行上下文使用该流可用的资源（SM、工作队列）。 例如：

// 为之前创建的 green_ctx 绿色上下文创建 green_ctx_stream CUDA 流
cudaStream_t green_ctx_stream;
int priority = 0;
CUDA_CHECK(cudaExecutionCtxStreamCreate(&green_ctx_stream,
                                        green_ctx,
                                        cudaStreamDefault,
                                        priority));

// 内核 my_kernel 将仅使用 green_ctx_stream 执行上下文可用的资源（SM、工作队列，如适用）
my_kernel<<<grid_dim, block_dim, 0, green_ctx_stream>>>();
CUDA_CHECK(cudaGetLastError());

传递给上面的流创建 API 的默认流创建标志相当于 cudaStreamNonBlocking given green_ctx 是一个绿色的背景。

CUDA 图表

对于作为 CUDA 图的一部分启动的内核（请参阅 CUDA 图形），还有一些微妙之处。 与内核不同，启动 CUDA 图的 CUDA 流确实 not 确定使用的 SM 资源，因为该流仅用于依赖性跟踪。

内核节点（和其他适用的节点类型）将在其上执行的执行上下文是在节点创建期间设置的。 如果使用流捕获创建 CUDA 图，则捕获中涉及的流的执行上下文将确定相关图节点的执行上下文。 如果使用图形 API 创建图形，则用户应显式设置每个相关节点的执行上下文。 例如，要添加内核节点，用户应该使用多态 cudaGraphAddNode API 与 cudaGraphNodeTypeKernel 类型并明确指定 .ctx 的领域 cudaKernelNodeParamsV2 结构下 .kernel。的 cudaGraphAddKernelNode 不允许用户指定执行上下文，因此应该避免。 请注意，图中的不同图节点可能属于不同的执行上下文。

出于验证目的，可以在节点跟踪模式下使用 Nsight Systems（--cuda-graph-trace node）以观察特定图形节点将在其上执行的绿色上下文。 请注意，在默认情况下 graph 跟踪模式下，整个图将显示在启动它的流的绿色上下文下，但是，如前所述，这不提供有关各个图节点的执行上下文的任何信息。

要以编程方式进行验证，可以使用 CUDA 驱动程序 API cuGraphKernelNodeGetParams(graph_node, &node_params) 并比较 node_params.ctx 上下文句柄字段，其中包含该图节点的预期上下文句柄。可以使用驱动程序 API CUgraphNode 或 cudaGraphNode_t 可以互换使用，但用户需要包括相关的 cuda.h 标头 并直接与驱动程序链接（-lcuda).

线程块簇

具有线程块簇的内核（参见 第 1.2.2.1.1 节）也可以像任何其他内核一样在绿色上下文流上启动，从而使用该绿色上下文的配置资源。 第 4.6.4.2 节 展示了如何指定设备资源拆分时需要协同调度的 SM 数量，以方便集群。 但与任何使用集群的内核一样，用户应该利用相关的占用 API 来确定内核的最大潜在集群大小（通过 cudaOccupancyMaxPotentialClusterSize） 并且，如果需要，活动集群的最大数量（cudaOccupancyMaxActiveClusters）。 如果用户指定绿色上下文流作为 stream 相关领域 cudaLaunchConfig，那么 这些占用 API 将考虑为该绿色上下文配置的 SM 资源。 此用例尤其适用于可能获得用户传递给它们的绿色上下文 CUDA 流的库，以及从剩余设备资源创建绿色上下文的情况。

下面的代码片段显示了如何使用这些 API。

// 假设 cudaStream_t gc_stream 已经创建并且存在 __global__ void cluster_kernel。

// 如果可能的话，取消注释以支持不可移植的簇大小
// CUDA_CHECK(cudaFuncSetAttribute(cluster_kernel, cudaFuncAttributeNonPortableClusterSizeAllowed, 1))

cudaLaunchConfig_t config = {0};
config.gridDim          = grid_dim; // 必须是 cluster dim 的倍数。
config.blockDim         = block_dim;
config.dynamicSmemBytes = expected_dynamic_shared_mem;

cudaLaunchAttribute attribute[1];
attribute[0].id = cudaLaunchAttributeClusterDimension;
attribute[0].val.clusterDim.x = 1;
attribute[0].val.clusterDim.y = 1;
attribute[0].val.clusterDim.z = 1;
config.attrs = attribute;
config.numAttrs = 1;

config.stream=gc_stream; // 需要传递将用于该内核的 CUDA 流

int max_potential_cluster_size = 0;
// 下一个调用将忽略启动配置中的集群暗淡
CUDA_CHECK(cudaOccupancyMaxPotentialClusterSize(&max_potential_cluster_size, cluster_kernel, &config));
std::cout << "max potential cluster size is " << max_potential_cluster_size << " for CUDA stream gc_stream" << std::endl;

// 可以选择使用 max_potial_cluster_size 更新启动配置的 clusterDim。
// 这样做将导致对相同内核和启动配置的 cudaLaunchKernelEx 调用成功。

int num_clusters= 0;
CUDA_CHECK(cudaOccupancyMaxActiveClusters(&num_clusters, cluster_kernel, &config));
std::cout << "Potential max. active clusters count is " << num_clusters << std::endl;

验证绿色上下文的使用

除了由于绿色上下文配置而影响内核执行时间的经验观察之外， 用户可以利用 夜视系统 和 Nsight计算 CUDA 开发人员工具可在某种程度上验证绿色上下文的正确使用。

例如，在属于不同绿色上下文的 CUDA 流上启动的内核将出现在不同的环境下 绿色背景 CUDA 硬件时间轴部分下的行 夜视系统 report. Nsight计算 提供了一个 绿色上下文资源 其会话页面中的概述以及更新 # 短信 根据 发射统计 的 Details 部分。 前者提供所配置资源的可视位掩码。如果应用程序使用不同的绿色上下文，这特别有用，因为用户可以确认预期的重叠 GC（如果 SM 超额认购，则没有重叠或预期非零重叠）。

图45 描述了这些资源的示例，其中两个绿色上下文分别配备了 112 个和 16 个 SM，并且它们之间没有 SM 重叠。 提供的视图可以帮助用户验证每个绿色上下文所配置的 SM 资源计数。它还有助于确认没有 SM 被超额认购，因为 在两个绿色上下文中，没有框被标记为绿色（为该 GC 配置）。

发射统计 部分还明确列出了为此绿色上下文配置的 SM 数量，因此可由该内核使用。 请注意，这些是给定内核在其执行期间可以访问的 SM，而不是内核运行的实际 SM 数量。这同样适用于前面显示的资源概述。 内核使用的 SM 的实际数量可能取决于多种因素，包括内核本身（启动几何结构等）、GPU 上同时运行的其他工作等。

4.6.6. 附加执行上下文 API#

本节涉及一些额外的绿色上下文 API。完整列表请参考相关的 CUDA 运行时 API 章节。

对于使用 CUDA 事件进行同步，可以利用 cudaError_t cudaExecutionCtxRecordEvent(cudaExecutionContext_t ctx, cudaEvent_t event) 或 cudaError_t cudaExecutionCtxWaitEvent(cudaExecutionCtxWaitEvent(cudaExecutionContext_t ctx, cudaEvent_t event) APIs. cudaExecutionCtxRecordEvent 记录一个 CUDA 事件，捕获调用时指定执行上下文的所有工作/活动，同时 cudaExecutionCtxWaitEvent 使提交到执行上下文的所有未来工作等待在指定事件中捕获的工作。

Using cudaExecutionCtxRecordEvent 比 cudaEventRecord 如果执行上下文有多个 CUDA 流。 要在没有此执行上下文 API 的情况下实现等效行为，需要通过以下方式记录单独的 CUDA 事件 cudaEventRecord 在每个执行上下文流上 然后让相关工作分别等待所有这些事件。 同样， cudaExecutionCtxWaitEvent 比 cudaStreamWaitEvent，如果需要所有执行上下文流等待事件完成。另一种选择是 一个单独的 cudaStreamWaitEvent 对于此执行上下文中的每个流。

对于 CPU 端的阻塞同步，可以使用 cudaError_t cudaExecutionCtxSynchronize(cudaExecutionContext_t ctx)。 此调用将阻塞，直到指定的执行上下文完成其所有工作。 如果指定的执行上下文不是通过创建的 cudaGreenCtxCreate，而是通过以下方式获得的 cudaDeviceGetExecutionCtx，因此是设备的主要上下文，调用该函数将 还同步在同一设备上创建的所有绿色上下文。

要检索与给定执行上下文关联的设备，可以使用 cudaExecutionCtxGetDevice。 要检索给定执行上下文的唯一标识符，可以使用 cudaExecutionCtxGetId.

最后，可以通过以下方式销毁显式创建的执行上下文 cudaError_t cudaExecutionCtxDestroy(cudaExecutionContext_t ctx) API。

4.6.7. 绿色上下文示例#

本节说明绿色上下文如何使关键工作能够更快地开始和完成。 类似于中使用的场景 第 4.6.1 节，该应用程序有两个内核，将在两个不同的非阻塞 CUDA 流上运行。 从CPU方面来看，时间线如下。 一个长时间运行的内核（delay_kernel_us），在全 GPU 上进行多波处理，首先在 CUDA 流上启动 strm1。然后经过短暂的等待时间（小于内核持续时间）， 一个更短但关键的内核（critical_kernel）已上线 strm2。 测量两个内核的 GPU 持续时间和从 CPU 启动到完成的时间。

作为长时间运行内核的代理，使用延迟内核，其中每个线程块运行固定的微秒数，并且线程块的数量超过 GPU 的可用 SM。

最初，不使用绿色上下文，但关键内核在 CUDA 流上启动，其优先级高于长时间运行的内核。 由于其高优先级流，关键内核可以在长时间运行的内核的某些线程块完成后立即开始执行。然而，它仍然需要 等待一些可能长时间运行的线程块完成，这将延迟其执行开始。

图46 Nsight Systems 报告中展示了这一场景。 长时间运行的内核在流 13 上启动，而短但关键的内核在流 14 上启动，流 14 具有更高的流优先级。 如图中突出显示的那样，关键内核在开始执行之前会等待 0.9 毫秒（在本例中）。如果两个流具有相同的优先级，则关键内核将执行得更晚。

为了利用绿色上下文功能，创建了两个绿色上下文，每个绿色上下文都配备了一组不同的不重叠的 SM。 出于说明目的，在本例中为具有 132 个 SM 的 H100 选择了精确的 SM 分割，即 16 个 SM 用于关键内核（绿色上下文 3），112 个 SM 用于长时间运行的内核（绿色上下文 2）。 作为 图47 表明，关键内核现在几乎可以立即启动，因为只有 Green Context 3 可以使用 SM。

与单独运行时的持续时间相比，短内核的持续时间可能会增加，因为现在它可以使用的 SM 数量受到限制。 对于长时间运行的内核来说也是如此，它不能再使用 GPU 的所有 SM，而是受到其绿色上下文所配置资源的限制。 然而，关键的结果是关键的内核工作现在可以比以前更快地开始和完成。 这排除了任何其他限制，因为如前所述，无法保证并行执行。

在所有情况下，确切的 SM 分割应在实验后根据具体情况决定。
