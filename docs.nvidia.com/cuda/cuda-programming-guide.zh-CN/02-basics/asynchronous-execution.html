2.3. 异步执行#

2.3.1. 什么是异步并发执行？#

CUDA 允许多个任务并发（即重叠）执行，具体包括：

  • 主机端计算

  • 设备端计算

  • 从主机到设备的内存传输

  • 从设备到主机的内存传输

  • 同一设备内存空间内的数据传输

  • 设备之间的数据传输

这种并发性通过异步接口来表达：调度函数调用或内核启动会立即返回。异步调用通常会在所派发操作完成前返回，甚至可能在异步操作真正开始前就返回。应用程序因此可以在原始操作执行期间并行处理其他任务。当需要最初派发操作的最终结果时，应用必须通过某种同步手段确保该操作已经完成。一个典型的并发执行模式是将主机与设备之间的数据传输和计算重叠，从而降低或消除传输开销。

通常，异步接口一般提供三种与已派发操作同步的主要方式：

  • 阻塞方式：应用调用会阻塞（等待）直到操作完成的函数

  • 非阻塞方式（轮询方式）：应用调用立即返回的函数，并获取操作状态信息

  • 回调方式：当操作完成时执行预先注册的函数。

虽然编程接口是异步的，但硬件能否真正并发执行各类操作还取决于 CUDA 版本和所用硬件的计算能力。相关细节将在本指南后续章节说明（见 计算能力）。

在 CPU 与 GPU 同步 一节中，我们介绍了 CUDA 运行时函数 cudaDeviceSynchronize()。这是一个阻塞调用，会等待此前发出的所有工作完成。之所以需要调用 cudaDeviceSynchronize()，是因为内核启动本身是异步且立即返回的。CUDA 提供了阻塞和非阻塞两类同步 API，并支持主机侧回调函数。

CUDA 中异步执行的核心 API 组件是 CUDA 流 与 CUDA 事件。 在本节其余部分中，我们将说明如何利用这些机制来表达 CUDA 异步执行。

另一个相关主题是 CUDA 图（CUDA Graphs）。它允许预先定义异步操作图，并以很小开销重复执行。我们会在 2.3.9.2 通过流捕获入门 CUDA 图 中做入门介绍，更完整的讨论见 4.1 CUDA 图。

2.3.2. CUDA 流#

在最基础层面，CUDA 流是一种抽象，用于让程序员表达一串按顺序操作。流的操作就像一个工作队列，程序可以向其中添加要按顺序执行的操作，例如内存复制或内核启动。位于队列前端的操作会先执行，随后出队，让下一个排队操作到达前端并等待执行。一个流中的操作按入队顺序串行执行。

应用程序可以同时使用多个流。在这种情况下，运行时会根据 GPU 资源状态，从有待执行任务的流中选择任务执行。流可设置优先级，用作影响调度的提示，但不保证严格的执行顺序。

在某个流中执行的 API 调用与内核启动相对主机线程都是异步的。应用程序可以等待流中的任务清空来与该流同步，也可以在设备级别进行同步。

CUDA 有一个默认流。未显式指定流的操作和内核启动都会进入默认流。未注明流的示例代码都隐式使用该默认流。默认流具有一些特殊语义，详见子节 阻塞与非阻塞流及默认流。

2.3.2.1. 创建与销毁 CUDA 流#

可使用 cudaStreamCreate() 创建 CUDA 流。该调用会初始化流句柄，供后续函数调用中标识此流。

cudaStream_t stream;        // 流句柄
cudaStreamCreate(&stream);  // 创建一个新流

// 基于流的操作...

cudaStreamDestroy(stream);  // 销毁流

如果应用调用 cudaStreamDestroy() 时，设备仍在流 stream 中执行任务，则该流会先完成其中所有任务，再被销毁。

2.3.2.2. 在 CUDA 流中启动内核#

通常用于启动内核的三尖括号语法同样可将内核发射到指定流中。做法是在内核启动参数中额外传入流。如下示例中，名为 kernel 的内核被发射到句柄为 stream 的流中；该句柄类型为 cudaStream_t，并假定已事先创建。

kernel<<<grid, block, shared_mem_size, stream>>>(...);

内核启动是异步的，函数调用会立即返回。若内核成功发射，它将在流 stream 中执行；与此同时，应用可以在 CPU 上或 GPU 的其他流中并行执行其他任务。

2.3.2.3. 在 CUDA 流中发起内存传输#

若要把内存传输发起到某个流中，可使用 cudaMemcpyAsync()。它与 cudaMemcpy() 类似，但多了一个参数用于指定传输所使用的流。下面代码将 src 指向的主机内存中的 size 字节复制到流 stream 中 dst 指向的设备内存。

// 将“size”字节从流“stream”中的“src”复制到“dst”
cudaMemcpyAsync(dst, src, size, cudaMemcpyHostToDevice, stream);

与其他异步函数调用一样，该调用会立即返回；而 cudaMemcpy() 会阻塞直到传输完成。要安全访问传输结果，应用必须通过某种同步手段确认该操作已经结束。

其他 CUDA 内存传输函数（如 cudaMemcpy2D()）也有对应的异步版本。

注意

若要让涉及 CPU 内存的拷贝真正异步执行，主机缓冲区必须是固定页内存（pinned/page-locked）。若主机内存不是固定页，cudaMemcpyAsync() 虽能正常工作，但会退化为同步行为，无法与其他任务重叠，从而削弱异步传输的性能收益。建议使用 cudaMallocHost() 分配用于与 GPU 收发数据的缓冲区。

2.3.2.4. 流同步#

与流同步最简单的方法，是等待该流中的任务全部清空。这可以通过两种方式完成：cudaStreamSynchronize() 或 cudaStreamQuery()。

cudaStreamSynchronize() 会阻塞，直到该流中的所有工作完成。

// 等待流清空任务
cudaStreamSynchronize(stream);

// 至此流就完成了
// 我们可以安全地访问流操作的结果

如果不希望阻塞，只想快速检查流是否为空，可使用 cudaStreamQuery()。

// 看看流
// 如果流为空则返回 cudaSuccess
// 如果流不为空，则返回 cudaErrorNotReady
cudaError_t status = cudaStreamQuery(stream);

switch (status) {
    case cudaSuccess:
        // 流是空的
        std::cout << "The stream is empty" << std::endl;
        break;
    case cudaErrorNotReady:
        // 流不为空
        std::cout << "The stream is not empty" << std::endl;
        break;
    default:
        // 发生错误 - 我们应该处理这个问题
        break;
};

2.3.3. CUDA 事件#

CUDA 事件是一种向 CUDA 流中插入标记点的机制，可用于跟踪流中任务进度。设想向一个流中启动两个内核；若没有这类事件，我们只能判断流是否为空。若某个操作依赖第一个内核输出，那么在确认流为空之前无法安全启动该操作，而此时两个内核往往都已完成。

使用 CUDA 事件可以做得更好。若在第一个内核之后、第二个内核之前向流中插入一个事件，我们可以等待该事件到达流前端。这样就能在确认第一个内核完成、但第二个内核尚未开始时，安全启动依赖操作。按此方式使用事件，可构建操作与流之间的依赖图，这与后文讨论的 CUDA 图 直接对应。

CUDA 流还会保留时间信息，可用于测量内核启动和内存传输耗时。

2.3.3.1. 创建与销毁 CUDA 事件#

可使用 cudaEventCreate() 与 cudaEventDestroy() 创建和销毁 CUDA 事件。

cudaEvent_t event;

// 创建事件
cudaEventCreate(&event);

// 做一些涉及事件的工作

// 一旦工作完成并且不再需要该事件
// 我们可以毁掉这个事件
cudaEventDestroy(event);

事件不再需要时，应由应用负责销毁。

2.3.3.2. 向 CUDA 流中插入事件#

可通过 cudaEventRecord() 将 CUDA 事件插入流中。

cudaEvent_t event;
cudaStream_t stream;

// 创建事件
cudaEventCreate(&event);

// 将事件插入流中
cudaEventRecord(event, stream);

2.3.3.3. 对 CUDA 流中的操作计时#

CUDA 事件可用于计时流中的各类操作（包括内核）。当事件到达流前端时会记录时间戳。像下方示例这样在同一流中用两个事件包围一个内核，即可准确测得该内核执行时长。

cudaStream_t stream;
cudaStreamCreate(&stream);

cudaEvent_t start;
cudaEvent_t stop;

// 创建事件
cudaEventCreate(&start);
cudaEventCreate(&stop);

 // 记录开始事件
cudaEventRecord(start, stream);

// 启动内核
kernel<<<grid, block, 0, stream>>>(...);

// 记录停止事件
cudaEventRecord(stop, stream);

// 等待流完成
// 两个事件都会被触发
cudaStreamSynchronize(stream);

// 掌握时机
float elapsedTime;
cudaEventElapsedTime(&elapsedTime, start, stop);
std::cout << "Kernel execution time: " << elapsedTime << " ms" << std::endl;

// 清理
cudaEventDestroy(start);
cudaEventDestroy(stop);
cudaStreamDestroy(stream);

2.3.3.4. 检查 CUDA 事件状态#

与检查流状态类似，事件状态也可用阻塞或非阻塞两种方式检查。

cudaEventSynchronize() 会阻塞直到事件完成。下方示例先向流中发射一个内核，再记录事件，再发射第二个内核。我们可以通过 cudaEventSynchronize() 等待第一个内核后的事件完成，从而在理论上可立即启动依赖任务，且可能早于 kernel2 结束。

cudaEvent_t event;
cudaStream_t stream;

// 创建流
cudaStreamCreate(&stream);

// 创建事件
cudaEventCreate(&event);

// 将内核启动到流中
kernel<<<grid, block, 0, stream>>>(...);

// 记录事件
cudaEventRecord(event, stream);

// 将内核启动到流中
kernel2<<<grid, block, 0, stream>>>(...);

// 等待活动完成
// 内核 1 将保证已完成
// 我们可以启动依赖任务。
cudaEventSynchronize(event);
dependentCPUtask();

// 等待流为空
// 内核 2 保证已完成
cudaStreamSynchronize(stream);

// 销毁事件
cudaEventDestroy(event);

// 销毁流
cudaStreamDestroy(stream);

可使用 cudaEventQuery() 以非阻塞方式检查 CUDA 事件是否完成。下例中我们向一个流发射两个内核。第一个内核 kernel1 生成了希望拷回主机的数据，同时 CPU 侧还有其他工作要做。代码中先把 kernel1、事件（event）和 kernel2 依次入队到 stream1。随后进入 CPU 工作循环，并偶尔检查事件是否完成（即 kernel1 是否结束）。若完成，则在 stream2 中发起设备到主机拷贝。这样可以实现 CPU 工作、GPU 内核执行与设备到主机传输之间的重叠。

cudaEvent_t event;
cudaStream_t stream1;
cudaStream_t stream2;

size_t size = LARGE_NUMBER;
float *d_data;

// 创建一些数据
cudaMalloc(&d_data, size);
float *h_data = (float *)malloc(size);

// 创建流
cudaStreamCreate(&stream1);   // 处理流
cudaStreamCreate(&stream2);   // 复制流
bool copyStarted = false;

// 创建事件
cudaEventCreate(&event);

// 将 kernel1 启动到流中
kernel1<<<grid, block, 0, stream1>>>(d_data, size);
// 将事件放入 kernel1 之后的队列中
cudaEventRecord(event, stream1);

// 将 kernel2 启动到流中
kernel2<<<grid, block, 0, stream1>>>();

// 当内核运行时，CPU 会做一些工作
// 但检查 kernel1 是否已完成，因为那时我们将开始
// 用于在 Stream2 中托管副本的设备
while ( not allCPUWorkDone() || not copyStarted ) {
    doNextChunkOfCPUWork();

    // 查看内核 1 是否已完成
    // 如果是这样，将非阻塞副本排队到stream2中
    if ( not copyStarted ) {
        if( cudaEventQuery(event) == cudaSuccess ) {
            cudaMemcpyAsync(h_data, d_data, size, cudaMemcpyDeviceToHost, stream2);
            copyStarted = true;
        }
    }
}

// 等待两个流完成
cudaStreamSynchronize(stream1);
cudaStreamSynchronize(stream2);

// 销毁事件
cudaEventDestroy(event);

// 销毁流并释放数据
cudaStreamDestroy(stream1);
cudaStreamDestroy(stream2);
cudaFree(d_data);
free(h_data);

2.3.4. 来自流的回调函数#

CUDA 提供了一种机制，可在流内部触发主机侧函数。当前可用的函数有两个：cudaLaunchHostFunc() 和 cudaAddCallback()。但 cudaAddCallback() 已计划弃用，因此应用应使用 cudaLaunchHostFunc()。

使用 cudaLaunchHostFunc()

cudaLaunchHostFunc() 的函数签名如下：

cudaError_t cudaLaunchHostFunc(cudaStream_t stream, void (*func)(void *), void *data);

其中：

  • stream：要将回调函数放入的流。

  • func：要执行的回调函数。

  • data：传给回调函数的数据指针。

主机函数本身是一个简单的 C 函数，签名如下：

void hostFunction(void *data);

其中 data 参数指向用户定义的数据结构，函数可自行解释该结构。使用这类回调函数时有一些注意事项：尤其是，主机函数内部不得调用任何 CUDA API。

在统一内存语义下，系统提供如下执行保证： - 函数执行期间，该流被视为空闲状态。因此函数可始终使用其入队流所附加的内存。 - 函数开始执行的效果，等价于同步同一流中紧邻其前的一个事件，因此会同步此前“汇合”的流。 - 在所有前序主机函数和流回调执行完之前，向任何流加入设备工作都不会使该流变为活跃。 - 除上述情况外，函数完成本身不会使流变为活跃。若后续没有设备工作，该流将保持空闲；连续主机函数/回调之间若无设备工作，流也保持空闲。

2.3.4.1. 使用 cudaStreamAddCallback()#

注意

cudaStreamAddCallback() 已计划弃用并移除。此处仅为完整性与兼容存量代码而说明。应用应使用或迁移到 cudaLaunchHostFunc()。

cudaStreamAddCallback() 的函数签名如下：

cudaError_t cudaStreamAddCallback(cudaStream_t stream, cudaStreamCallback_t callback, void* userData, unsigned int flags);

其中：

  • stream：要将回调函数放入的流。

  • callback：要执行的回调函数。

  • userData：传入回调函数的数据指针。

  • flags：当前必须设为 0，以保证未来兼容性。

callback 的签名与 cudaLaunchHostFunc() 使用的主机函数签名略有不同。 在本例中，回调函数是一个具有以下签名的 C 函数：

void callbackFunction(cudaStream_t stream, cudaError_t status, void *userData);

此时该函数会接收：

  • stream：启动回调函数的流句柄。

  • status：触发回调的流操作的状态。

  • userData：指向传递给回调函数的数据的指针。

特别是 status 参数将包含流的当前错误状态，该状态可能已由之前的操作设置。 类似地 cudaLaunchHostFunc() func 情况下，在主机函数完成之前，流不会处于活动状态并前进到任务，并且不能从回调函数中调用任何 CUDA 函数。

2.3.4.2. 异步错误处理#

在 CUDA 流中，错误可能来自流内任一操作（包括内核启动和内存传输）。这类错误在运行时可能要等到流被同步后（例如等待事件或调用 cudaStreamSynchronize()）才会反馈给用户。排查流内错误通常有两种方式。

  • 使用 cudaGetLastError()：返回并清除当前上下文中任意流遇到的最后一个错误。若两次调用间无新错误，紧接着第二次调用会返回 cudaSuccess。

  • 使用 cudaPeekAtLastError()：返回当前上下文的最后一个错误，但不会清除它。

两者都以 cudaError_t 返回错误值。可通过 cudaGetErrorName() 与 cudaGetErrorString() 获取可读错误名称和描述。

下面给出这些函数的使用示例：

代码清单 1 使用 cudaGetLastError() 和 cudaPeekAtLastError() 的示例#
// 有些工作发生在流中。
cudaStreamSynchronize(stream);

// 查看最后一个错误但不清除它
cudaError_t err = cudaPeekAtLastError();
if (err != cudaSuccess) {
    printf("Error with name: %s\n", cudaGetErrorName(err));
    printf("Error description: %s\n", cudaGetErrorString(err));
}

// 查看最后一个错误并将其清除
cudaError_t err2 = cudaGetLastError();
if (err2 != cudaSuccess) {
    printf("Error with name: %s\n", cudaGetErrorName(err2));
    printf("Error description: %s\n", cudaGetErrorString(err2));
}

if (err2 != err) {
    printf("As expected, cudaPeekAtLastError() did not clear the error\n");
}

// 再次检查
cudaError_t err3 = cudaGetLastError();
if (err3 == cudaSuccess) {
    printf("As expected, cudaGetLastError() cleared the error\n");
}

提示

当错误在同步点暴露出来时（尤其在包含大量操作的流中），通常很难定位具体出错位置。一个实用调试技巧是设置环境变量 CUDA_LAUNCH_BLOCKING=1 后再运行程序。该变量会让每次内核启动后都执行同步，有助于定位是哪一次内核或传输导致错误。需要注意，同步代价较高，启用该变量后程序可能明显变慢。

2.3.5. CUDA 流的顺序语义#

在了解了流、事件与回调函数的基础机制后，我们还需关注流中异步操作的顺序语义。这些语义让应用开发者能够以安全方式推理流内操作顺序。在某些性能优化场景下，这些语义会被适当放宽，例如 程序化依赖内核启动 场景可借助特定属性与启动机制让两个内核重叠执行；又如使用 cudaMemcpyBatchAsync() 批量传输时，运行时可并发执行互不重叠的批拷贝。相关优化将在后文讨论。

最关键的是，CUDA 流属于“按序流（in-order stream）”。这意味着流中操作的执行顺序与其入队顺序一致，后续操作不能“插队”越过前序操作。内存操作（如拷贝）会由运行时跟踪，并保证在后续操作执行前完成，以确保依赖内核能安全访问正在传输的数据。

2.3.6. 阻塞/非阻塞流与默认流#

在 CUDA 中，流分为阻塞流与非阻塞流两类。这个命名容易误解，因为其语义仅指这些流与默认流之间的同步关系。默认情况下，使用 cudaStreamCreate() 创建的是阻塞流。若要创建非阻塞流，需使用 cudaStreamCreateWithFlags() 并传入 cudaStreamNonBlocking 标志：

cudaStream_t stream;
cudaStreamCreateWithFlags(&stream, cudaStreamNonBlocking);

非阻塞流可按常规方式通过 cudaStreamDestroy() 销毁。

2.3.6.1. 传统默认流#

阻塞流与非阻塞流的关键差异在于它们如何与默认流同步。CUDA 提供传统默认流（又称 NULL 流或流 ID 0），当内核启动未指定流或调用阻塞式 cudaMemcpy() 时会使用它。该默认流由所有主机线程共享，且属于阻塞流。当操作被发射到该默认流时，它会与所有其他阻塞流同步，即需等待其他阻塞流完成后才能执行。

cudaStream_t stream1, stream2;
cudaStreamCreate(&stream1);
cudaStreamCreate(&stream2);

kernel1<<<grid, block, 0, stream1>>>(...);
kernel2<<<grid, block>>>(...);
kernel3<<<grid, block, 0, stream2>>>(...);

cudaDeviceSynchronize();

上述默认流行为意味着：在前面的代码中，kernel2 会等待 kernel1，而 kernel3 会等待 kernel2，即便理论上三者可并发执行。通过创建非阻塞流可避免这种同步。在下方示例中我们创建两个非阻塞流，默认流将不再与它们同步，因此三者原则上可并发执行。也因此不能再假设三者存在固定顺序，需使用显式同步（例如较为“重”的 cudaDeviceSynchronize()）来保证内核完成。

cudaStream_t stream1, stream2;
cudaStreamCreateWithFlags(&stream1, cudaStreamNonBlocking);
cudaStreamCreateWithFlags(&stream2, cudaStreamNonBlocking);

kernel1<<<grid, block, 0, stream1>>>(...);
kernel2<<<grid, block>>>(...);
kernel3<<<grid, block, 0, stream2>>>(...);

cudaDeviceSynchronize();

2.3.6.2. 每线程默认流#

从 CUDA 7 开始，CUDA 支持“每个主机线程拥有独立默认流”，而不再必须共享传统默认流。要启用该行为，可使用 nvcc 选项 --default-stream per-thread，或定义预处理宏 CUDA_API_PER_THREAD_DEFAULT_STREAM。启用后，每个主机线程的默认流彼此独立，不再按传统默认流方式与其他流同步。在这种情况下，传统默认流示例 将表现出与 非阻塞流示例 相同的同步特性。

2.3.7. 显式同步#

流之间可以通过多种方式进行显式同步。

cudaDeviceSynchronize() 等待直到所有主机线程的所有流中的所有先前命令都完成。

cudaStreamSynchronize()将流作为参数并等待，直到给定流中的所有先前命令都完成。它可用于将主机与特定流同步，从而允许其他流继续在设备上执行。

cudaStreamWaitEvent()接受一个流和一个事件作为参数（参见 CUDA 活动 事件的描述）并使所有命令在调用后添加到给定流 cudaStreamWaitEvent()延迟执行直到给定事件完成。

cudaStreamQuery()为应用程序提供了一种方法来了解流中所有前面的命令是否已完成。

2.3.8. 隐式同步#

如果提交了 NULL 流上的任何 CUDA 操作，则来自不同流的两个操作不能同时运行 在它们之间，除非流是非阻塞流（使用 cudaStreamNonBlocking 旗）。

为提升内核并发执行潜力，应用应遵循以下原则：

  • 先发出彼此独立的操作，再发出存在依赖关系的操作；

  • 尽可能推迟各类同步操作的发生时机。

2.3.9. 杂项与高级主题#

2.3.9.1. 流优先级#

如前所述，开发者可以为 CUDA 流分配优先级。优先级流需要通过 cudaStreamCreateWithPriority() 创建；该函数接收两个关键参数：流创建标志和优先级。 通常，数值越低表示优先级越高。给定设备和上下文支持的优先级范围 可通过 cudaDeviceGetStreamPriorityRange() 查询。流的默认优先级为 0。

int minPriority, maxPriority;

// 查询设备的优先级范围
cudaDeviceGetStreamPriorityRange(&minPriority, &maxPriority);

// 创建两个具有不同优先级的流
// cudaStreamDefault 指示应使用默认标志创建流
// 换句话说，它们将阻塞相对于旧版默认流的流
// 还可以在此处使用选项“cudaStreamNonBlocking”来创建非阻塞流
cudaStream_t stream1, stream2;
cudaStreamCreateWithPriority(&stream1, cudaStreamDefault, minPriority);  // 最低优先级
cudaStreamCreateWithPriority(&stream2, cudaStreamDefault, maxPriority);  // 最高优先级

需要注意，流优先级只是给运行时的提示，通常主要作用于内核发射，对内存传输未必生效。流优先级不会抢占已在执行的工作，也不保证特定执行顺序。

2.3.9.2. 通过流捕获入门 CUDA 图#

CUDA 流允许程序按顺序指定一系列操作（如内核或内存拷贝）。借助多流与 cudaStreamWaitEvent 跨流依赖，应用可描述完整的有向无环图（DAG）操作流。有些应用在运行期间需要反复执行同一序列或 DAG。

针对这种场景，CUDA 提供了 CUDA 图。本节介绍 CUDA 图及其一种构建机制——流捕获。更详细内容见 CUDA 图。捕获或创建图可减少主机线程重复调用同一 API 链带来的延迟与 CPU 开销：图定义一次，之后可重复执行多次。

CUDA 图的一般工作流程如下：

  1. 应用先对图进行捕获（通常在首次执行时完成）；也可通过 CUDA Graph API 手工构建图。

  2. 随后对图进行实例化（一次性步骤）。该步骤会建立执行图所需的运行时结构，以尽可能加快各组件启动。

  3. 之后按需反复执行已实例化图。由于运行时结构已就绪，图执行的 CPU 开销可显著降低。

代码清单 2 使用 CUDA 图对简单线性图执行“捕获-实例化-执行”阶段（摘自 CUDA 开发者技术博客，A.灰色，2019）#
#define N 500000 // 调整内核需要几微秒

// 一个非常轻量级的内核
__global__ void shortKernel(float * out_d, float * in_d){
    int idx=blockIdx.x*blockDim.x+threadIdx.x;
    if(idx<N) out_d[idx]=1.23*in_d[idx];
}

bool graphCreated=false;
cudaGraph_t graph;
cudaGraphExec_t instance;

// 该图将执行 NSTEP 次
for(int istep=0; istep<NSTEP; istep++){
    if(!graphCreated){
        // 捕获图
        cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);

        // 启动 NKERNEL 内核
        for(int ikrnl=0; ikrnl<NKERNEL; ikrnl++){
            shortKernel<<<blocks, threads, 0, stream>>>(out_d, in_d);
        }

        // 结束捕获
        cudaStreamEndCapture(stream, &graph);

        // 实例化图
        cudaGraphInstantiate(&instance, graph, NULL, NULL, 0);
        graphCreated=true;
    }

    // 启动图
    cudaGraphLaunch(instance, stream);

    // 同步流
    cudaStreamSynchronize(stream);
}

关于 CUDA 图的更多细节请参见 CUDA 图。

2.3.10. 异步执行总结#

本节要点如下：

  • 异步 API 使我们能够表达任务并发执行与操作重叠；实际并发度取决于可用硬件资源与计算能力。

  • CUDA 异步执行的关键抽象是：流、事件与回调函数。

  • 可在事件级、流级与设备级进行同步。

  • 默认流属于阻塞流，会与其他阻塞流同步，但不会与非阻塞流同步。

  • 可通过编译选项 --default-stream per-thread 或雕塑宏 CUDA_API_PER_THREAD_DEFAULT_STREAM 启用每线程默认流，苏格兰传统默认流行为。

  • 流可配置不同优先级，但这只是对运行时的提示，对内存传输不一定生效。

  • CUDA 提供了用于降低或重叠内核启动与内存传输开销的 API，例如 CUDA 图、批量内存传输和程序化依赖内核启动。
