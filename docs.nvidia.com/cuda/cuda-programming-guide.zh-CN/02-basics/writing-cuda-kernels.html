2.2. 编写 CUDA SIMT 内核#

需要确定的是，CUDA C++ 内核在编写方式上与传统 CPU 代码总体相似。但 GPU 具备一些突出特性问题，可用于提升性能。此外，对 GPU 上的线程如何调度、它们如何访问内存以及它们的执行过程如何进行的一些了解可以帮助开发人员编写能够最大限度地利用可用计算资源的内核。

2.2.1. SIMT基础#

从开发者视角看，CUDA 线程是并行执行的基本单位。 Warp 与 SIMT 描述了 GPU 执行的基本 SIMT 模型 SIMT执行模型 提供 SIMT 模型的更多详细信息。 SIMT 模型允许每个线程维护自己的状态和控制流。从功能角度来看，每个线程可以执行单独的代码路径。 然而，通过注意内核代码最大限度地减少同一warp 中的线程采用不同代码路径的情况，可以实现显着的性能改进。

2.2.2. 线程层次结构#

网格可以是 1、2 或 3 维，网格的大小可以在内核中通过以下方式查询： gridDim 内置变量。 线程块也可以是 1、2 或 3 维的。可以使用以下命令在内核内部查询线程块的大小 blockDim 内置变量。可以使用以下命令查询线程块的索引 blockIdx 内置变量。 在线程块内，线程的索引是通过以下方式获得的： threadIdx 内置变量。 这些内置变量用于计算每个线程的唯一全局线程索引，从而使每个线程能够从全局内存加载/存储特定数据，并根据需要执行唯一的代码路径。

  • gridDim.[x|y|z]: 中网格的大小 x, y 或 z 分别为维度。 这些值是在内核启动时设置的。

  • blockDim.[x|y|z]：块的大小 x, y 或 z 分别为维度。 这些值是在内核启动时设置的。

  • blockIdx.[x|y|z]：块中的索引 x, y 或 z 分别为维度。 这些值根据正在执行的块而变化。

  • threadIdx.[x|y|z]：线程中的索引 x, y 或 z 分别为维度。 这些值根据正在执行的线程而变化。

使用多维线程块和网格只是为了方便，并不影响性能。块的线程可预测地线性化：第一个索引 x 移动速度最快，其次是 y 然后 z。 这意味着在线程索引的线性化中，连续的值 threadIdx.x 表示连续的线程， threadIdx.y 有一个步幅 blockDim.x, 和 threadIdx.z 有一个步幅 blockDim.x * blockDim.y。这会影响线程分配给 warp 的方式，详见 硬件多线程.

2.2.3.1. 全局内存#

全局内存（也称设备内存）是存放内核中所有线程可访问数据的主要内存空间。 其作用类似于 CPU 系统中的 RAM。运行在 GPU 上的内核可直接访问全局内存，就像 CPU 代码可直接访问系统内存一样。

全局内存是持久的。也就是说，在全局内存中进行的分配以及存储在其中的数据将持续存在，直到分配被释放或应用程序终止为止。 cudaDeviceReset 还释放所有分配。

全局内存通过 CUDA API 调用进行分配，例如 cudaMalloc 或 cudaMallocManaged。可以使用 CUDA 运行时 API 调用将数据从 CPU 内存复制到全局内存，例如 cudaMemcpy。 使用 CUDA API 进行的全局内存分配通过以下方式释放 cudaFree.

在内核启动之前，全局内存由 CUDA API 调用分配和初始化。在内核执行期间，CUDA 线程可以读取全局内存中的数据，并且 CUDA 线程执行的操作结果可以写回全局内存。一旦内核完成执行，它写入全局内存的结果就可以复制回主机或由 GPU 上的其他内核使用。

由于网格中的所有线程都可以访问全局内存，因此必须注意避免线程之间的数据竞争。 由于从主机启动的 CUDA 内核具有返回类型 void，将内核计算的数值结果返回到主机的唯一方法是将这些结果写入全局内存。

说明全局内存使用的一个简单示例是 vecAdd 下面的内核，其中三个数组 A, B, 和 C 位于全局内存中，并由该向量加法内核访问。

2.2.3.2. 共享内存#

共享内存是同一线程块内所有线程都可访问的内存空间。它物理上位于各个 SM 上，与 L1 缓存共享同一片统一数据缓存资源。共享内存中的数据在内核执行期间保持有效。可将其视为由用户管理、供内核执行阶段使用的暂存区。尽管容量小于全局内存，但由于其位于 SM 本地，访问带宽更高、延迟更低。

由于共享内存可由线程块中的所有线程访问，因此必须注意避免同一线程块中的线程之间的数据竞争。 同一线程块中的线程之间的同步可以使用 __syncthreads() 功能。 该函数阻塞线程块中的所有线程，直到所有线程都到达对 __syncthreads().

// 假设 blockDim.x 是 128
__global__ void example_syncthreads(int* input_data, int* output_data) {
    __shared__ int shared_data[128];
    // 每个线程写入“shared_data”的不同元素：
    shared_data[threadIdx.x] = input_data[threadIdx.x];

    // 所有线程同步，保证对“shared_data”的所有写入都是有序的 
    // 在任何线程从“__syncthreads()”解除阻塞之前：
    __syncthreads();

    // 单个线程安全地读取“shared_data”：
    if (threadIdx.x == 0) {
        int sum = 0;
        for (int i = 0; i < blockDim.x; ++i) {
            sum += shared_data[i];
        }
        output_data[blockIdx.x] = sum;
    }
}

共享内存的大小根据所使用的 GPU 架构而有所不同。 由于共享内存和 L1 缓存共享相同的物理空间，因此使用共享内存会减少内核可用的 L1 缓存的大小。 此外，如果内核没有使用共享内存，则整个物理空间将被 L1 缓存使用。 CUDA运行时API提供了在每个SM和每个线程块的基础上查询共享内存大小的函数，使用 cudaGetDeviceProperties 功能并调查 cudaDeviceProp.sharedMemPerMultiprocessor 或 cudaDeviceProp.sharedMemPerBlock 设备属性。

CUDA运行时API提供了一个函数 cudaFuncSetCacheConfig 告诉运行时是否为共享内存分配更多空间，或为 L1 缓存分配更多空间。 此函数指定对运行时的偏好，但不保证得到尊重。 运行时可以根据可用资源和内核的需求自由做出决策。

共享内存可以静态和动态分配。

2.2.3.2.1. 共享内存的静态分配#

要静态分配共享内存，程序员必须使用以下方法在内核中声明一个变量： __shared__ 说明符。 该变量将分配在共享内存中，并在内核执行期间持续存在。 以这种方式声明的共享内存的大小必须在编译时指定。 例如，以下代码片段位于内核主体中，声明了一个类型为的共享内存数组 float 有 1024 个元素。

__shared__ float sharedArray[1024];

声明后，线程块中的所有线程都可以访问该共享内存数组。 必须小心避免同一线程块中线程之间的数据竞争，通常使用 __syncthreads().

2.2.3.2.2. 共享内存的动态分配#

要动态分配共享内存，程序员可以以三重 V 形符号指定每个线程块所需的共享内存量（以字节为单位）作为内核启动的第三个（也是可选的）参数，如下所示 functionName<<<grid, block, sharedMemoryBytes>>>().

然后，在内核内部，程序员可以使用 extern __shared__ 说明符来声明将在内核启动时动态分配的变量。

extern __shared__ float sharedArray[];

需要注意的是，如果需要多个动态分配的共享内存阵列，则单个 extern __shared__ 必须使用指针算术手动分区。 例如，如果有人想要以下等价的内容，

short array0[128];
float array1[64];
int   array2[256];

在动态分配的共享内存中，可以通过以下方式声明和初始化数组：

extern __shared__ float array[];

short* array0 = (short*)array;
float* array1 = (float*)&array0[128];
int*   array2 =   (int*)&array1[64];

请注意，指针需要与它们指向的类型对齐，因此以下代码不起作用，因为 array1 未与 4 字节对齐。

extern __shared__ float array[];
short* array0 = (short*)array;
float* array1 = (float*)&array0[127];

2.2.3.3. 寄存器#

寄存器位于 SM 上，作用域为线程本地。寄存器使用由编译器管理，并在内核运行期间用于线程局部存储。可通过 GPU 设备属性 regsPerMultiprocessor 与 regsPerBlock 查询每个 SM 与每个线程块可用的寄存器数量。

NVCC 允许开发商 指定最大寄存器数 由内核通过 -maxrregcount 选项。 使用此选项来减少内核可以使用的寄存器数量可能会导致在 SM 上同时调度更多线程块，但也可能导致更多寄存器溢出。

2.2.3.4. 本地内存#

本地内存与寄存器一样是线程本地存储，由 NVCC 管理，但其物理位置位于全局内存空间。这里的“local”指的是逻辑作用域，而非物理位置。本地内存在内核执行期间用于线程局部存储。编译器通常会将以下自动变量放入本地内存：

  • 无法确定它们是否使用常量索引的数组，

  • 大型结构或数组会消耗太多寄存器空间，

  • 如果内核使用的寄存器多于可用的任何变量，则称为寄存器溢出。

由于本地内存空间驻留在设备内存中，因此本地内存访问具有与全局内存访问相同的延迟和带宽，并且受到与内存合并相同的要求，如 合并全局内存访问。然而，本地存储器的组织方式使得连续的 32 位字可以由连续的线程 ID 访问。因此，只要 warp 中的所有线程访问相同的相对地址（例如数组变量中的相同索引或结构变量中的相同成员），访问就会完全合并。

2.2.3.5. 常量内存#

常量内存作用域为网格，在应用生命周期内可访问。常量内存驻留于设备端，对内核是只读的。因此必须在主机端、函数外通过 __constant__ 说明符进行声明与初始化。

__constant__ 内存空间说明符声明一个变量：

  • 驻留在恒定的内存空间中，

  • 具有创建它的 CUDA 上下文的生命周期，

  • 每个设备都有一个不同的对象，

  • 可通过运行时库从网格内的所有线程以及主机访问（cudaGetSymbolAddress() / cudaGetSymbolSize() / cudaMemcpyToSymbol() / cudaMemcpyFromSymbol()).

常量内存总量可以通过以下命令查询 totalConstMem 设备属性元素。

常量内存对于每个线程以只读方式使用的少量数据很有用。 相对于其他存储器，恒定存储器较小，通常每个设备 64KB。

下面是声明和使用常量内存的示例片段。

// 在您的 .cu 文件中
__constant__ float coeffs[4];

__global__ void compute(float *out) {
    int idx = threadIdx.x;
    out[idx] = coeffs[0] * idx + coeffs[1];
}

// 在你的主机代码中
float h_coeffs[4] = {1.0f, 2.0f, 3.0f, 4.0f};
cudaMemcpyToSymbol(coeffs, h_coeffs, sizeof(h_coeffs));
compute<<<1, 10>>>(device_out);

2.2.3.6. 缓存#

GPU设备具有多级缓存结构，包括L2和L1缓存。

L2 缓存位于设备上并在所有 SM 之间共享。 L2缓存的大小可以通过以下命令查询 l2CacheSize 函数中的设备属性元素 cudaGetDeviceProperties.

正如上面所描述的 共享内存，L1 缓存物理上位于每个 SM 上，并且与共享内存使用的物理空间相同。 如果内核没有使用共享内存，则整个物理空间将由 L1 缓存使用。

L2 和 L1 缓存可以通过允许开发人员指定各种缓存行为的函数进行控制。 这些功能的详细信息可以在 配置 L1/共享内存平衡, L2 缓存控制, 和 低级加载和存储函数.

如果不使用这些提示，编译器和运行时将尽力有效地利用缓存。

2.2.3.7. 纹理与表面内存#

注意

一些较旧的 CUDA 代码可能会使用纹理内存，因为在较旧的 NVIDIA GPU 中，这样做在某些情况下可以提供性能优势。在所有当前支持的 GPU 上，可以使用直接加载和存储指令来处理这些场景，并且使用纹理和表面内存指令不再提供任何性能优势。

GPU 可能具有专门的指令，用于从图像加载数据以用作 3D 渲染中的纹理。 CUDA 公开了这些指令以及在以下环境中使用它们的机制： texture object API 和 表面对象API.

本指南不会进一步讨论纹理和表面内存，因为在任何当前支持的 NVIDIA GPU 上的 CUDA 中使用它们没有任何优势。 CUDA 开发人员应该随意忽略这些 API。对于仍在使用现有代码库的开发人员来说，仍然可以在旧版中找到这些 API 的解释 CUDA C++ 编程指南.

2.2.3.8. 分布式共享内存#

线程块簇 计算能力 9.0 中引入并由 合作团体，为线程块集群中的线程提供访问该集群中所有参与线程块的共享内存的能力。这个分区共享内存称为 分布式共享内存，对应的地址空间称为分布式共享内存地址空间。属于线程块簇的线程可以在分布式地址空间中读取、写入或执行原子操作，无论该地址属于本地线程块还是远程线程块。无论内核是否使用分布式共享内存，共享内存大小规范（静态或动态）仍然是每个线程块。分布式共享内存的大小就是每个集群的线程块数量乘以每个线程块的共享内存大小。

访问分布式共享内存中的数据需要所有线程块都存在。用户可以保证所有线程块都已开始执行 cluster.sync() from class cluster_group。用户还需要确保所有分布式共享内存操作都发生在线程块退出之前，例如，如果远程线程块正在尝试读取给定线程块的共享内存，则程序需要确保远程线程块读取的共享内存在退出之前完成。

让我们看一下简单的直方图计算以及如何使用线程块集群在 GPU 上对其进行优化。计算直方图的标准方法是在每个线程块的共享内存中执行计算，然后执行全局内存原子。这种方法的一个限制是共享内存容量。一旦直方图箱不再适合共享内存，用户就需要直接计算直方图，从而计算全局内存中的原子。通过分布式共享内存，CUDA 提供了一个中间步骤，根据直方图箱的大小，可以直接在共享内存、分布式共享内存或全局内存中计算直方图。

下面的 CUDA 内核示例展示了如何根据直方图箱的数量计算共享内存或分布式共享内存中的直方图。

#include <cooperative_groups.h>

// 分布式共享内存直方图内核
__global__ void clusterHist_kernel(int *bins, const int nbins, const int bins_per_block, const int *__restrict__ input,
                                   size_t array_size)
{
  extern __shared__ int smem[];
  namespace cg = cooperative_groups;
  int tid = cg::this_grid().thread_rank();

  // 集群初始化、大小和计算本地 bin 偏移量。
  cg::cluster_group cluster = cg::this_cluster();
  unsigned int clusterBlockRank = cluster.block_rank();
  int cluster_size = cluster.dim_blocks().x;

  for (int i = threadIdx.x; i < bins_per_block; i += blockDim.x)
  {
    smem[i] = 0; // 将共享内存直方图初始化为零
  }

  // 集群同步确保共享内存初始化为零
  // 集群中的所有线程块。它还确保所有线程都阻塞
  // 已经开始执行并且它们同时存在。
  cluster.sync();

  for (int i = tid; i < array_size; i += blockDim.x * gridDim.x)
  {
    int ldata = input[i];

    // 找到正确的直方图箱。
    int binid = ldata;
    if (ldata < 0)
      binid = 0;
    else if (ldata >= nbins)
      binid = nbins - 1;

    // 查找目标块排名和偏移量以进行计算
    // 分布式共享内存直方图
    int dst_block_rank = (int)(binid / bins_per_block);
    int dst_offset = binid % bins_per_block;

    // 指向目标块共享内存的指针
    int *dst_smem = cluster.map_shared_rank(smem, dst_block_rank);

    // 执行直方图 bin 的原子更新
    atomicAdd(dst_smem + dst_offset, 1);
  }

  // 需要集群同步，保证所有分布式共享
  // 内存操作完成并且没有线程块退出
  // 其他线程块仍在访问分布式共享内存
  cluster.sync();

  // 使用本地分布式内存直方图执行全局内存直方图
  int *lbins = bins + cluster.block_rank() * bins_per_block;
  for (int i = threadIdx.x; i < bins_per_block; i += blockDim.x)
  {
    atomicAdd(&lbins[i], smem[i]);
  }
}

上述内核可以在运行时启动，其集群大小取决于所需的分布式共享内存的数量。如果直方图小到足以容纳一个块的共享内存，则用户可以启动集群大小为 1 的内核。下面的代码片段显示了如何根据共享内存需求动态启动集群内核。

// 通过可扩展启动启动
{
  cudaLaunchConfig_t config = {0};
  config.gridDim = array_size / threads_per_block;
  config.blockDim = threads_per_block;

  // cluster_size 取决于直方图大小。
  // ( cluster_size == 1 ) 意味着没有分布式共享内存，只是线程块本地共享内存
  int cluster_size = 2; // 尺寸 2 是此处的示例
  int nbins_per_block = nbins / cluster_size;

  // 动态共享内存大小是每个块的。
  // 分布式共享内存大小 = cluster_size * nbins_per_block * sizeof(int)
  config.dynamicSmemBytes = nbins_per_block * sizeof(int);

  CUDA_CHECK(::cudaFuncSetAttribute((void *)clusterHist_kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, config.dynamicSmemBytes));

  cudaLaunchAttribute attribute[1];
  attribute[0].id = cudaLaunchAttributeClusterDimension;
  attribute[0].val.clusterDim.x = cluster_size;
  attribute[0].val.clusterDim.y = 1;
  attribute[0].val.clusterDim.z = 1;

  config.numAttrs = 1;
  config.attrs = attribute;

  cudaLaunchKernelEx(&config, clusterHist_kernel, bins, nbins, nbins_per_block, input, array_size);
}

2.2.4. 内存性能#

合理使用内存是 CUDA 内核获得高性能的关键。本节讨论在 CUDA 内核中实现高内存吞吐量的一些一般原则和示例。

2.2.4.1. 全局内存合并访问#

全局内存通过 32 字节内存事务进行访问。 当 CUDA 线程从全局内存请求一个数据字时，相关的 warp 会将来自该 warp 中所有线程的内存请求合并为满足请求所需的内存事务数量，具体取决于每个线程访问的字的大小以及跨线程的内存地址的分布。 例如，如果线程请求 4 字节字，则 warp 将生成到全局内存的实际内存事务总共为 32 字节。 为了最有效地使用内存系统，warp 应使用在单个内存事务中获取的所有内存。 也就是说，如果一个线程正在从全局内存请求 4 字节字，并且事务大小为 32 字节，如果该 warp 中的其他线程可以使用该 32 字节请求中的其他 4 字节字数据，这将导致内存系统的最有效使用。

举个简单的例子，如果 warp 中的连续线程请求内存中的连续 4 字节字，则 warp 将请求总共 128 字节的内存，并且所需的 128 字节将在四个 32 字节内存事务中获取。 这导致内存系统的利用率为 100%。 也就是说，100% 的内存流量被 warp 使用。 图10 说明了这个完美合并内存访问的示例。

相反，最糟糕的情况是连续线程访问内存中彼此相距 32 字节或更多的数据元素。 在这种情况下，warp 将被迫为每个线程发出 32 字节的内存事务，内存流量的总字节数将为 32 字节乘以 32 个线程/warp = 1024 字节。 然而，使用的内存量仅为 128 字节（warp 中每个线程 4 字节），因此内存利用率仅为 128 / 1024 = 12.5%。 这是对内存系统的非常低效的使用。 图11 说明了这个未合并内存访问的示例。

实现合并内存访问的最直接方法是连续线程访问内存中的连续元素。 例如，对于使用 1d 线程块启动的内核，以下内容 VecAdd 内核将实现合并内存访问。 Notice how thread workIndex 访问三个数组和连续的线程（由连续的值表示） workIndex) 访问数组中的连续元素。

__global__ void vecAdd(float* A, float* B, float* C, int vectorLength)
{
    int workIndex = threadIdx.x + blockIdx.x*blockDim.x;
    if(workIndex < vectorLength)
    {
        C[workIndex] = A[workIndex] + B[workIndex];

不要求连续的线程访问连续的内存元素来实现合并内存访问，这只是实现合并的典型方式。如果 warp 中的所有线程以某种线性或排列方式访问来自相同 32 字节内存段的元素，就会发生合并内存访问。 换句话说，实现合并内存访问的最佳方法是最大化已用字节与传输字节的比率。

注意

确保全局内存访问的正确合并是编写高性能 CUDA 内核的最重要的性能考虑因素之一。 应用程序必须尽可能高效地使用内存系统。

2.2.4.1.1. 使用全局内存的矩阵转置示例#

作为一个简单的示例，考虑一个异地矩阵转置内核，该内核转置大小为 N x N 的 32 位浮点方阵，从矩阵 a 到矩阵 c。 此示例使用 2d 网格，并假设启动大小为 32 x 32 线程的 2d 线程块，即 blockDim.x = 32 或 blockDim.y = 32，因此每个 2d 线程块将在矩阵的 32 x 32 分块上运行。 每个线程都对矩阵的唯一元素进行操作，因此不需要线程的显式同步。 图12 说明了该矩阵转置运算。 内核源代码如图所示。

/* 用于以行优先顺序索引具有 2D 索引的 1D 内存数组的宏 */
/* ld 是主维度，即矩阵中的列数 */

#define INDX( row, col, ld ) ( ( (row) * (ld) ) + (col) )

/* 用于朴素矩阵转置的 CUDA 内核 */

__global__ void naive_cuda_transpose(int m, float *a, float *c )
{
    int myCol = blockDim.x * blockIdx.x + threadIdx.x;
    int myRow = blockDim.y * blockIdx.y + threadIdx.y;

    if( myRow < m && myCol < m )
    {
        c[INDX( myCol, myRow, m )] = a[INDX( myRow, myCol, m )];
    } /* 结束如果 */
    return;
} /* 结束 naive_cuda_transpose */

为了确定该内核是否实现了合并内存访问，需要确定连续的线程是否正在访问连续的内存元素。 在 2d 线程块中， x 索引移动最快，因此连续值 threadIdx.x 应该访问内存的连续元素。 threadIdx.x 出现在 myCol，并且可以观察到，当 myCol 是第二个参数 INDX 宏，连续的线程正在读取连续的值 a，所以读到 a 是完美结合的。

然而，写作 c 不合并，因为连续值 threadIdx.x （再次检查 myCol) 正在将元素写入 c 那是 ld （主维）元素彼此分开。 观察到这一点是因为现在 myCol 是第一个参数 INDX 宏，并作为第一个参数 INDX 每增加1，内存位置改变 ld。 当 ld 大于 32（每当矩阵大小大于 32 时就会发生），这相当于中所示的病态情况 图11.

为了减轻这些未合并的写入，可以使用共享内存，这将在下一节中描述。

2.2.4.2. 共享内存访问模式#

共享内存有 32 个存储体，这些存储体的组织方式使得连续的 32 位字映射到连续的存储体。每个存储体每个时钟周期的带宽为 32 位。

当同一 warp 中的多个线程尝试访问同一存储体中的不同元素时，就会发生存储体冲突。 在这种情况下，对该存储体中的数据的访问将被串行化，直到该存储体中的数据被所有请求它的线程获取为止。 这种访问的序列化会导致性能损失。

当同一 warp 中的多个线程访问（读取或写入）同一共享内存位置时，会发生此场景的两个例外。 对于读访问，该字被广播到请求线程。 对于写访问，每个共享内存地址仅由一个线程写入（哪个线程执行写入未定义）。

图13 显示了跨步访问的一些示例。 库内的红色框表示共享内存中的唯一位置。

图14 显示了涉及广播机制的内存读取访问的一些示例。 库内的红色框表示共享内存中的唯一位置。 如果多个箭头指向同一位置，则数据将广播到请求它的所有线程。

注意

避免存储体冲突是编写使用共享内存的高性能 CUDA 内核的重要性能考虑因素。

2.2.4.2.1. 使用共享内存的矩阵转置示例#

在前面的使用全局内存的矩阵转置示例中，我们展示了一个功能正确但较为朴素的实现：由于对 c 矩阵的写入未正确合并，因此全局内存利用并不高效。本示例将把共享内存作为用户管理缓存，用于暂存全局内存的读写，从而使读写两侧都获得更好的全局内存合并访问效果。

此示例中说明的基本性能优化是确保在访问全局内存时，内存访问正确合并。 在执行副本之前，每个线程计算其 tileRow 或 tileCol 指数。 这些是将要操作的特定分块的索引，并且这些分块索引基于正在执行的线程块。 同一线程块中的每个线程都有相同的 tileRow 或 tileCol 值，因此可以将其视为该特定线程块将操作的分块的起始位置。

然后，内核继续使用以下语句将每个线程块的 32 x 32 矩阵分块从全局内存复制到共享内存。 由于 warp 的大小为 32 个线程，因此该复制操作将由 32 个 warp 执行，并且不保证 warp 之间的顺序。

smemArray[threadIdx.x][threadIdx.y] = a[INDX( tileRow + threadIdx.y, tileCol + threadIdx.x, m )];

请注意，因为 threadIdx.x 出现在第二个参数中 INDX，连续的线程正在访问内存中的连续元素，并且读取 a 是完美结合的。

内核的下一步是调用 __syncthreads() 功能。这确保了线程块中的所有线程在继续之前已经完成了先前代码的执行，因此写入 a 进入共享内存在下一步之前完成。 这非常重要，因为下一步将涉及线程从共享内存中读取数据。 如果没有 __syncthreads() 调用，读取 a 在某些warp在代码中进一步前进之前，不能保证线程块中的所有warp都能完成进入共享内存。

此时在内核中，对于每个线程块， smemArray 有一个 32 x 32 的矩阵分块，其排列顺序与原始矩阵相同。 为了确保分块内的元素正确调换， threadIdx.x 或 threadIdx.y 当他们阅读时交换 smemArray。 确保整体分块放置在正确的位置 c, 的 tileRow 或 tileCol 写入时索引也会交换 c。 为了确保适当的合并， threadIdx.x 用于第二个参数 INDX，如下面的语句所示。

c[INDX( tileCol + threadIdx.y, tileRow + threadIdx.x, m )] = smemArray[threadIdx.y][threadIdx.x];

该内核说明了共享内存的两种常见用途。

  • 共享内存用于暂存全局内存中的数据，以确保对全局内存的读取和写入都正确合并。

  • 共享内存用于允许同一线程块中的线程之间共享数据。

2.2.4.2.2. 共享内存 Bank 冲突#

In 第2.2.4.2节，描述了共享内存的bank结构。 在前面的矩阵转置示例中，实现了对全局内存的正确合并内存访问，但没有考虑是否存在共享内存组冲突。 考虑以下二维共享内存声明，

__shared__ float smemArray[32][32];

由于一个 warp 有 32 个线程，因此同一个 warp 中的每个线程都有一个固定的值 threadIdx.y 并将有 0 <= threadIdx.x < 32.

左侧面板的 图15 说明了warp 中的线程访问列中的数据时的情况 smemArray。 warp 0 正在访问内存位置 smemArray[0][0] 到 smemArray[31][0]。 在 C++ 多维数组排序中，最后一个索引移动速度最快，因此 warp 0 中的连续线程正在访问相距 32 个元素的内存位置。 如图所示，颜色表示存储体，通过 warp 0 向下访问整个列会导致 32 路存储体冲突。

右侧面板的 图15 说明了warp 中的线程跨行访问数据时的情况 smemArray。 warp 0 正在访问内存位置 smemArray[0][0] 到 smemArray[0][31]。 在这种情况下，warp 0 中的连续线程正在访问相邻的内存位置。 如图所示，颜色表示存储体，并且通过 warp 0 对整个行进行访问不会导致任何存储体冲突。 理想的情况是warp 中的每个线程都访问具有不同颜色的共享内存位置。

回到来自的例子 第2.2.4.2.1节，可以检查共享内存的使用情况以确定是否存在存储体冲突。 共享内存的第一次使用是将全局内存中的数据存储到共享内存时：

smemArray[threadIdx.x][threadIdx.y] = a[INDX( tileRow + threadIdx.y, tileCol + threadIdx.x, m )];

因为 C++ 数组按行优先顺序存储，所以同一warp 中的连续线程，如连续的值所示 threadIdx.x，将访问 smemArray 步幅为 32 个元素，因为 threadIdx.x 是数组中的第一个索引。 这会导致 32 路银行冲突，如左图所示 图15.

共享内存的第二种用法是将共享内存中的数据写回全局内存时：

c[INDX( tileCol + threadIdx.y, tileRow + threadIdx.x, m )] = smemArray[threadIdx.y][threadIdx.x];

在这种情况下，因为 threadIdx.x 是第二个索引 smemArray 数组，同一warp 中的连续线程将访问 smemArray 步幅为 1 个元素。 这不会导致银行冲突，如右图所示 图15.

矩阵转置内核如图所示 第2.2.4.2.1节 具有一种没有存储体冲突的共享内存访问和一种具有 32 路存储体冲突的访问。 避免存储体冲突的常见修复方法是通过向数组的列维度加 1 来填充共享内存，如下所示：

__shared__ float smemArray[THREADS_PER_BLOCK_X][THREADS_PER_BLOCK_Y+1];

此次声明的小幅调整 smemArray 将消除银行冲突。 为了说明这一点，请考虑 图16 其中共享内存数组的大小被声明为 32 x 33。可以观察到，无论同一 warp 中的线程是向下一整列还是跨整行访问共享内存数组，都消除了存储体冲突，即同一 warp 中的线程访问具有不同颜色的位置。

2.2.5. 原子操作#

高性能 CUDA 内核依赖于表达尽可能多的算法并行性。 GPU 内核执行的异步特性要求线程尽可能独立运行。 线程完全独立并不总是可能的，正如我们在 共享内存，存在一种机制可以让同一线程块中的线程交换数据并进行同步。

在整个网格的层面上，没有这样的机制来同步网格中的所有线程。 然而，有一种机制可以通过使用原子函数来提供对全局内存位置的同步访问。 原子函数允许线程获取全局内存位置的锁，并在该位置执行读取-修改-写入操作。 持有锁时，其他线程无法访问同一位置。 CUDA 提供的原子与 C++ 标准库原子具有相同的行为： cuda::std::atomic 或 cuda::std::atomic_ref。 CUDA 还提供扩展的 C++ 原子 cuda::atomic 或 cuda::atomic_ref 允许用户指定 线程范围 的原子操作。 原子函数的详细信息包含在 原子函数.

示例用法 cuda::atomic_ref 执行设备范围的原子加法如下，其中 array 是一个浮点数组，并且 result 是一个指向全局内存中某个位置的浮点指针，该位置是存储数组总和的位置。

__global__ void sumReduction(int n, float *array, float *result) {
   ...
   tid = threadIdx.x + blockIdx.x * blockDim.x;

   cuda::atomic_ref<float, cuda::thread_scope_device> result_ref(result);
   result_ref.fetch_add(array[tid]);
   ...
}

应谨慎使用原子函数，因为它们强制执行可能影响性能的线程同步。

2.2.6. 协作组（Cooperative Groups）#

合作团体 是 CUDA C++ 中提供的软件工具，允许应用程序定义可以相互同步的线程组，即使该线程组跨越多个线程块、单个 GPU 上的多个网格，甚至跨多个 GPU。 CUDA编程模型通常允许线程块或线程块簇内的线程有效地同步，但不提供用于指定小于线程块或簇的线程组的机制。同样，CUDA 编程模型不提供跨线程块同步的机制或保证。

合作团体通过软件提供这两种功能。协作组允许应用程序创建跨越线程块和集群边界的线程组，尽管这样做会带来一些语义限制和性能影响，这些限制和性能影响在 涵盖合作团体的专题部分.

2.2.7. 内核启动与占用率#

当 CUDA 内核启动时，CUDA 线程根据内核启动时指定的执行配置被分组为线程块和网格。 一旦内核启动，调度程序就会将线程块分配给 SM。 应用程序无法控制或查询哪些线程块被调度执行哪些 SM，并且调度程序不提供任何顺序保证，因此程序不能依赖特定的调度顺序或方案来正确执行。

SM 上可调度的块数量取决于给定线程块所需的硬件资源以及 SM 上可用的硬件资源。 当内核首次启动时，调度程序开始将线程块分配给 SM。 只要SM有足够的硬件资源未被其他线程块占用，调度程序就会继续向SM分配线程块。 如果在某个时刻没有 SM 有能力接受另一个线程块，则调度程序将等待，直到 SM 完成先前分配的线程块。 一旦发生这种情况，SM 就可以自由地接受更多的工作，并且调度程序会为它们分配线程块。 这个过程一直持续到所有线程块都被调度并执行为止。

cudaGetDeviceProperties 功能允许应用程序通过查询每个 SM 的限制 设备属性。 请注意，每个 SM 和每个线程块都有限制。

  • maxBlocksPerMultiProcessor：每个 SM 的最大驻留块数。

  • sharedMemPerMultiprocessor：每个 SM 可用的共享内存量（以字节为单位）。

  • regsPerMultiprocessor：每个 SM 可用的 32 位寄存器的数量。

  • maxThreadsPerMultiProcessor：每个SM的最大常驻线程数。

  • sharedMemPerBlock：线程块可以分配的最大共享内存量（以字节为单位）。

  • regsPerBlock：一个线程块可以分配的32位寄存器的最大数量。

  • maxThreadsPerBlock：每个线程块的最大线程数。

CUDA内核的占用率是活动warp数量与SM支持的最大活动warp数量的比率。 一般来说，尽可能高的占用率是一个很好的做法，这样可以隐藏延迟并提高性能。

为了计算占用率，我们需要知道刚才描述的 SM 的资源限制，并且需要知道相关 CUDA 内核需要哪些资源。 要确定每个内核的资源使用情况，在程序编译期间可以使用 --resource-usage option 和 nvcc，它将显示内核所需的寄存器和共享内存的数量。

为了说明这一点，请考虑一个设备，例如计算能力 10.0，其设备属性在 表2.

如果内核启动为 testKernel<<<512, 768>>>()，即每个块 768 个线程，每个 SM 一次只能执行 2 个线程块。 调度程序不能为每个 SM 分配超过 2 个线程块，因为 maxThreadsPerMultiProcessor 是 2048。因此占用率为 (768 * 2) / 2048，即 75%。

如果内核启动为 testKernel<<<512, 32>>>()，即每个块 32 个线程，每个 SM 不会遇到限制 maxThreadsPerMultiProcessor，但自从 maxBlocksPerMultiProcessor 如果是 32，那么调度程序只能为每个 SM 分配 32 个线程块。 由于块中的线程数为 32，因此驻留在 SM 上的线程总数将为 32 个块 * 每块 32 个线程，即总共 1024 个线程。 由于计算能力 10.0 SM 的最大值为每个 SM 2048 个常驻线程，因此本例中的占用率为 1024 / 2048，即 50%。

可以使用共享内存进行相同的分析。 例如，如果内核使用 100KB 共享内存，则调度程序只能为每个 SM 分配 2 个线程块，因为该 SM 上的第三个线程块将需要另外 100KB 共享内存，总共 300KB，这超过了每个 SM 可用的 233472 字节。

每个块的线程数和每个块的共享内存使用量由程序员显式控制，并且可以进行调整以达到所需的占用率。 程序员对寄存器使用的控制有限，因为编译器和运行时将尝试优化寄存器使用。 然而，程序员可以通过以下方式指定每个线程块的最大寄存器数量： --maxrregcount option 和 nvcc。 如果内核需要的寄存器多于这个指定数量，内核可能会溢出到本地内存，这将改变内核的性能特征。 在某些情况下，即使发生溢出，限制寄存器也允许调度更多线程块，这反过来会增加占用率并可能导致性能的净提高。
