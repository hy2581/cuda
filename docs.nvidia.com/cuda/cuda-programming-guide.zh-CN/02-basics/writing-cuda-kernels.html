2.2. 编写 CUDA SIMT 内核#

需要确定的是，CUDA C++ 内核在编写方式上与传统 CPU 代码总体相似。但 GPU 具备一些突出特性问题，可用于提升性能。此外，对 GPU 上的线程如何调度、它们如何访问内存以及它们的执行过程如何进行的一些了解可以帮助开发人员编写能够最大限度地利用可用计算资源的内核。

2.2.1. SIMT 基础#

从开发者视角看，CUDA 线程是并行执行的基本单位。Warp 与 SIMT 描述了 GPU 执行所采用的基本 SIMT 模型；SIMT 执行模型 则提供了更多细节。SIMT 模型允许每个线程维护自己的状态和控制流。从功能角度看，每个线程可以走不同的代码路径。不过，如果在编写内核时尽量减少同一 warp 内线程走向不同代码路径的情况，通常可以显著提升性能。

2.2.2. 线程层次结构#

网格可以是一维、二维或三维的；内核中可以通过内建变量 gridDim 查询网格大小。线程块同样可以是一维、二维或三维的；内核中可通过 blockDim 查询线程块大小，通过 blockIdx 查询线程块索引。在线程块内部，线程索引由内建变量 threadIdx 给出。这些内建变量可用于计算每个线程唯一的全局线程索引，从而让每个线程从全局内存加载或存储特定数据，并在需要时执行特定代码路径。

  • gridDim.[x|y|z]: 中网格的大小 x, y 或 z 分别为维度。 这些值是在内核启动时设置的。

  • blockDim.[x|y|z]：块的大小 x, y 或 z 分别为维度。 这些值是在内核启动时设置的。

  • blockIdx.[x|y|z]：块中的索引 x, y 或 z 分别为维度。 这些值根据正在执行的块而变化。

  • threadIdx.[x|y|z]：线程中的索引 x, y 或 z 分别为维度。 这些值根据正在执行的线程而变化。

使用多维线程块和网格主要是为了方便表达，并不会直接影响性能。线程块中的线程会按可预测方式线性化：x 索引变化最快，其次是 y，再其次是 z。这意味着在线性化后的线程索引中，连续的 threadIdx.x 值对应连续线程；threadIdx.y 的步幅为 blockDim.x；threadIdx.z 的步幅为 blockDim.x * blockDim.y。这会影响线程分配到 warp 的方式，详见 硬件多线程。

图 9 给出了一个使用一维线程块的二维网格示例。

2.2.3.1. 全局内存#

全局内存（也称设备内存）是存放内核中所有线程可访问数据的主要内存空间。 其作用类似于 CPU 系统中的 RAM。运行在 GPU 上的内核可直接访问全局内存，就像 CPU 代码可直接访问系统内存一样。

全局内存是持久的。也就是说，全局内存中的分配以及存放在其中的数据会一直存在，直到该分配被释放或应用程序终止。cudaDeviceReset 也会释放所有分配。

全局内存通过 CUDA API 调用分配，例如 cudaMalloc 或 cudaMallocManaged。也可以使用 CUDA Runtime API（如 cudaMemcpy）把数据从 CPU 内存复制到全局内存。通过 CUDA API 分配的全局内存使用 cudaFree 释放。

在内核启动之前，全局内存由 CUDA API 调用分配和初始化。在内核执行期间，CUDA 线程可以读取全局内存中的数据，并且 CUDA 线程执行的操作结果可以写回全局内存。一旦内核完成执行，它写入全局内存的结果就可以复制回主机或由 GPU 上的其他内核使用。

由于网格中的所有线程都可以访问全局内存，因此必须注意避免线程之间的数据竞争。 由于从主机启动的 CUDA 内核具有返回类型 void，将内核计算的数值结果返回到主机的唯一方法是将这些结果写入全局内存。

下面的 vecAdd 内核是一个使用全局内存的简单示例，其中三个数组 A、B 和 C 都位于全局内存中，并由向量加法内核访问。

2.2.3.2. 共享内存#

共享内存是同一线程块内所有线程都可访问的内存空间。它物理上位于各个 SM 上，与 L1 缓存共享同一片统一数据缓存资源。共享内存中的数据在内核执行期间保持有效。可将其视为由用户管理、供内核执行阶段使用的暂存区。尽管容量小于全局内存，但由于其位于 SM 本地，访问带宽更高、延迟更低。

由于共享内存可由同一线程块中的所有线程访问，因此必须注意避免线程块内部的数据竞争。同一线程块内的线程可使用 __syncthreads() 函数同步。该函数会阻塞线程块中的所有线程，直到所有线程都到达这次 __syncthreads() 调用为止。

// 假设 blockDim.x 是 128
__global__ void example_syncthreads(int* input_data, int* output_data) {
    __shared__ int shared_data[128];
    // 每个线程写入“shared_data”的不同元素：
    shared_data[threadIdx.x] = input_data[threadIdx.x];

    // 所有线程同步，保证对“shared_data”的所有写入都是有序的 
    // 在任何线程从“__syncthreads()”解除阻塞之前：
    __syncthreads();

    // 单个线程安全地读取“shared_data”：
    if (threadIdx.x == 0) {
        int sum = 0;
        for (int i = 0; i < blockDim.x; ++i) {
            sum += shared_data[i];
        }
        output_data[blockIdx.x] = sum;
    }
}

共享内存大小会随所用 GPU 架构而变化。由于共享内存和 L1 缓存共享同一片物理空间，使用共享内存会减少内核可用的 L1 缓存容量。相反，如果内核不使用共享内存，这片物理空间就可以全部用于 L1 缓存。CUDA Runtime API 提供了按 SM 和按线程块查询共享内存大小的能力：可以调用 cudaGetDeviceProperties，并查看设备属性 cudaDeviceProp.sharedMemPerMultiprocessor 或 cudaDeviceProp.sharedMemPerBlock。

CUDA Runtime API 提供了 cudaFuncSetCacheConfig，用于提示运行时应更偏向为共享内存分配空间，还是更偏向为 L1 缓存分配空间。该函数表达的是偏好，并不保证运行时一定遵循；运行时仍可根据可用资源和内核需求自行决策。

共享内存可以静态和动态分配。

2.2.3.2.1. 共享内存的静态分配#

静态分配共享内存时，程序员需要在内核中使用 __shared__ 说明符声明变量。该变量会分配在共享内存中，并在内核执行期间持续存在。以这种方式声明的共享内存大小必须在编译时确定。下面的代码片段位于内核主体中，声明了一个包含 1024 个 float 元素的共享内存数组。

__shared__ float sharedArray[1024];

声明后，线程块中的所有线程都可以访问该共享内存数组。必须小心避免同一线程块内线程之间的数据竞争，通常会使用 __syncthreads() 进行同步。

2.2.3.2.2. 共享内存的动态分配#

要动态分配共享内存，程序员可以在三尖括号语法中把每个线程块所需的共享内存字节数作为内核启动的第三个可选参数传入，如 functionName<<<grid, block, sharedMemoryBytes>>>() 所示。

然后，在内核内部，程序员可以使用 extern __shared__ 说明符来声明将在内核启动时动态分配的变量。

extern __shared__ float sharedArray[];

需要注意，如果需要多个动态分配的共享内存数组，就必须在单个 extern __shared__ 区域中用指针算术手动分区。例如，如果希望得到等价于以下声明的布局：

short array0[128];
float array1[64];
int   array2[256];

在动态分配的共享内存中，可以通过以下方式声明和初始化数组：

extern __shared__ float array[];

short* array0 = (short*)array;
float* array1 = (float*)&array0[128];
int*   array2 =   (int*)&array1[64];

还要注意，指针必须按其目标类型的要求对齐。因此下面的代码是错误的，因为 array1 没有按 4 字节边界对齐。

extern __shared__ float array[];
short* array0 = (short*)array;
float* array1 = (float*)&array0[127];

2.2.3.3. 寄存器#

寄存器位于 SM 上，作用域为线程本地。寄存器使用由编译器管理，并在内核运行期间用于线程局部存储。可通过 GPU 设备属性 regsPerMultiprocessor 与 regsPerBlock 查询每个 SM 与每个线程块可用的寄存器数量。

NVCC 允许开发者通过 -maxrregcount 选项 指定内核可使用的最大寄存器数量。减少内核可用寄存器数量，可能让 SM 同时调度更多线程块，但也可能导致更多寄存器溢出。

2.2.3.4. 本地内存#

本地内存与寄存器一样是线程本地存储，由 NVCC 管理，但其物理位置位于全局内存空间。这里的“local”指的是逻辑作用域，而非物理位置。本地内存在内核执行期间用于线程局部存储。编译器通常会将以下自动变量放入本地内存：

  • 无法确定是否使用常量索引访问的数组，

  • 会消耗过多寄存器空间的大型结构体或数组，

  • 因内核所需寄存器数量超过可用数量而发生寄存器溢出的变量。

由于本地内存空间驻留在设备内存中，本地内存访问具有与全局内存访问相同的延迟和带宽，并且同样受内存合并要求影响，见 全局内存合并访问。不过，本地内存的组织方式使连续线程 ID 可访问连续的 32 位字。因此，只要 warp 中的所有线程访问相同的相对地址，例如数组变量中的相同索引或结构变量中的相同成员，访问就会完全合并。

2.2.3.5. 常量内存#

常量内存作用域为网格，在应用生命周期内可访问。常量内存驻留于设备端，对内核是只读的。因此必须在主机端、函数外通过 __constant__ 说明符进行声明与初始化。

__constant__ 内存空间说明符声明一个变量：

  • 驻留在常量内存空间中，

  • 生命周期与创建它的 CUDA 上下文一致，

  • 每个设备都有各自独立的对象，

  • 可由网格内的所有线程访问，也可通过运行时库从主机端访问（cudaGetSymbolAddress() / cudaGetSymbolSize() / cudaMemcpyToSymbol() / cudaMemcpyFromSymbol()）。

常量内存总量可以通过设备属性中的 totalConstMem 字段查询。

常量内存适合存放每个线程只读访问的少量数据。相对于其他内存空间，常量内存较小，通常每个设备为 64 KB。

下面是声明和使用常量内存的示例片段。

// 在 .cu 文件中
__constant__ float coeffs[4];

__global__ void compute(float *out) {
    int idx = threadIdx.x;
    out[idx] = coeffs[0] * idx + coeffs[1];
}

// 在你的主机代码中
float h_coeffs[4] = {1.0f, 2.0f, 3.0f, 4.0f};
cudaMemcpyToSymbol(coeffs, h_coeffs, sizeof(h_coeffs));
compute<<<1, 10>>>(device_out);

2.2.3.6. 缓存#

GPU 设备具有多级缓存结构，包括 L2 和 L1 缓存。

L2 缓存位于设备上，并由所有 SM 共享。可调用 cudaGetDeviceProperties，通过设备属性中的 l2CacheSize 字段查询 L2 缓存大小。

如上文 共享内存 所述，L1 缓存在物理上位于各个 SM 内，并与共享内存使用同一片物理空间。如果内核没有使用共享内存，则这片物理空间会全部用于 L1 缓存。

L2 和 L1 缓存可通过一些函数进行控制，这些函数允许开发者指定不同的缓存行为。相关细节见 配置 L1/共享内存平衡、L2 缓存控制 和 低级加载和存储函数。

如果不使用这些提示，编译器和运行时将尽力有效地利用缓存。

2.2.3.7. 纹理与表面内存#

注意

一些较旧的 CUDA 代码可能会使用纹理内存，因为在较旧的 NVIDIA GPU 中，这样做在某些情况下可以提供性能优势。在所有当前支持的 GPU 上，可以使用直接加载和存储指令来处理这些场景，并且使用纹理和表面内存指令不再提供任何性能优势。

GPU 可能提供专门指令，用于加载图像数据并在 3D 渲染中作为纹理使用。CUDA 通过 texture object API 和 surface object API 暴露这些指令及其使用机制。

本指南不再进一步讨论纹理和表面内存，因为在当前受支持的 NVIDIA GPU 上，CUDA 使用它们已经没有性能优势。CUDA 开发者通常可以忽略这些 API。仍需维护旧代码库的开发者，可以在旧版 CUDA C++ 编程指南 中找到相关说明。

2.2.3.8. 分布式共享内存#

线程块簇 在计算能力 9.0 中引入，并通过 Cooperative Groups 暴露给程序。它让线程块簇中的线程能够访问该簇内所有参与线程块的共享内存。这片组合后的共享内存称为 分布式共享内存，对应地址空间称为分布式共享内存地址空间。属于线程块簇的线程可以在该分布式地址空间中读取、写入或执行原子操作，不论目标地址属于本地线程块还是远程线程块。无论内核是否使用分布式共享内存，共享内存大小（静态或动态）仍按每个线程块指定。分布式共享内存总大小等于每个簇中的线程块数量乘以每个线程块的共享内存大小。

访问分布式共享内存中的数据时，相关线程块必须全部存在。程序可以通过 class cluster_group 提供的 cluster.sync() 确保所有线程块都已经开始执行。程序还必须保证所有分布式共享内存操作都在线程块退出前完成。例如，如果远程线程块要读取某个线程块的共享内存，就必须确保这次读取在目标线程块退出之前完成。

下面以一个简单的直方图计算为例，说明如何用线程块簇在 GPU 上优化它。计算直方图的标准做法，是先在每个线程块的共享内存中完成局部计算，然后再对全局内存执行原子操作。该方法的限制在于共享内存容量；一旦直方图 bin 无法放入单个线程块的共享内存，用户就需要直接在全局内存中计算直方图并执行原子操作。借助分布式共享内存，CUDA 提供了一个中间选择：根据直方图 bin 的大小，可在普通共享内存、分布式共享内存或全局内存中计算直方图。

下面的 CUDA 内核示例展示了如何根据直方图 bin 的数量，在共享内存或分布式共享内存中计算直方图。

#include <cooperative_groups.h>

// 分布式共享内存直方图内核
__global__ void clusterHist_kernel(int *bins, const int nbins, const int bins_per_block, const int *__restrict__ input,
                                   size_t array_size)
{
  extern __shared__ int smem[];
  namespace cg = cooperative_groups;
  int tid = cg::this_grid().thread_rank();

  // 初始化簇，获取簇大小，并计算本地 bin 偏移量。
  cg::cluster_group cluster = cg::this_cluster();
  unsigned int clusterBlockRank = cluster.block_rank();
  int cluster_size = cluster.dim_blocks().x;

  for (int i = threadIdx.x; i < bins_per_block; i += blockDim.x)
  {
    smem[i] = 0; // 将共享内存直方图初始化为零
  }

  // 簇同步确保簇中所有线程块的共享内存已初始化为 0。
  // 它也会阻塞所有线程，直到它们都已开始执行并同时存在。
  cluster.sync();

  for (int i = tid; i < array_size; i += blockDim.x * gridDim.x)
  {
    int ldata = input[i];

    // 找到正确的直方图 bin。
    int binid = ldata;
    if (ldata < 0)
      binid = 0;
    else if (ldata >= nbins)
      binid = nbins - 1;

    // 查找目标块排名和偏移量以进行计算
    // 分布式共享内存直方图
    int dst_block_rank = (int)(binid / bins_per_block);
    int dst_offset = binid % bins_per_block;

    // 指向目标块共享内存的指针
    int *dst_smem = cluster.map_shared_rank(smem, dst_block_rank);

    // 执行直方图 bin 的原子更新
    atomicAdd(dst_smem + dst_offset, 1);
  }

  // 需要簇同步，保证所有分布式共享内存操作完成，
  // 并确保在线程块退出时，没有其他线程块仍在访问其分布式共享内存。
  cluster.sync();

  // 使用本地分布式内存直方图执行全局内存直方图
  int *lbins = bins + cluster.block_rank() * bins_per_block;
  for (int i = threadIdx.x; i < bins_per_block; i += blockDim.x)
  {
    atomicAdd(&lbins[i], smem[i]);
  }
}

上述内核可以在运行时启动，簇大小取决于所需的分布式共享内存容量。如果直方图足够小，能够放入单个线程块的共享内存，用户也可以用簇大小为 1 启动该内核。下面的代码片段展示了如何根据共享内存需求动态启动簇内核。

// 通过可扩展启动启动
{
  cudaLaunchConfig_t config = {0};
  config.gridDim = array_size / threads_per_block;
  config.blockDim = threads_per_block;

  // cluster_size 取决于直方图大小。
  // ( cluster_size == 1 ) 意味着没有分布式共享内存，只是线程块本地共享内存
  int cluster_size = 2; // 尺寸 2 是此处的示例
  int nbins_per_block = nbins / cluster_size;

  // 动态共享内存大小是每个块的。
  // 分布式共享内存大小 = cluster_size * nbins_per_block * sizeof(int)
  config.dynamicSmemBytes = nbins_per_block * sizeof(int);

  CUDA_CHECK(::cudaFuncSetAttribute((void *)clusterHist_kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, config.dynamicSmemBytes));

  cudaLaunchAttribute attribute[1];
  attribute[0].id = cudaLaunchAttributeClusterDimension;
  attribute[0].val.clusterDim.x = cluster_size;
  attribute[0].val.clusterDim.y = 1;
  attribute[0].val.clusterDim.z = 1;

  config.numAttrs = 1;
  config.attrs = attribute;

  cudaLaunchKernelEx(&config, clusterHist_kernel, bins, nbins, nbins_per_block, input, array_size);
}

2.2.4. 内存性能#

合理使用内存是 CUDA 内核获得高性能的关键。本节讨论在 CUDA 内核中实现高内存吞吐量的一些一般原则和示例。

2.2.4.1. 全局内存合并访问#

全局内存以 32 字节内存事务进行访问。当 CUDA 线程从全局内存请求一个数据字时，相关 warp 会把该 warp 中所有线程的内存请求合并成满足请求所需的内存事务；所需事务数取决于每个线程访问的数据字大小，以及各线程访问地址的分布。例如，如果线程请求 4 字节字，那么 warp 发送到全局内存的实际内存事务大小总计为 32 字节。为了最高效地使用内存系统，warp 应尽量使用单个内存事务中取回的全部数据。换句话说，如果某个线程从全局内存请求一个 4 字节字，而事务大小是 32 字节，那么当同一 warp 中其他线程也能使用该 32 字节请求中的其他 4 字节字时，内存系统利用率最高。

举个简单例子，如果 warp 中的连续线程请求内存中连续的 4 字节字，那么 warp 总共会请求 128 字节内存，所需的 128 字节会通过四个 32 字节内存事务取回。这时内存系统利用率为 100%，也就是 100% 的内存流量都被该 warp 使用。图 10 展示了这种完全合并内存访问的示例。

相反，最糟糕的情况是连续线程访问内存中彼此相隔 32 字节或更远的数据元素。这时，warp 被迫为每个线程发出一个 32 字节内存事务，总内存流量会达到 32 字节乘以每 warp 32 个线程，即 1024 字节。但实际使用的数据只有 128 字节（warp 中每个线程 4 字节），所以内存利用率只有 128 / 1024 = 12.5%。这会非常低效地使用内存系统。图 11 展示了这种非合并内存访问的示例。

实现合并内存访问最直接的方法，是让连续线程访问内存中的连续元素。例如，对于使用一维线程块启动的内核，下面的 VecAdd 内核会实现合并内存访问。注意每个线程会用 workIndex 访问三个数组，而连续线程（即 workIndex 连续的线程）会访问数组中的连续元素。

__global__ void vecAdd(float* A, float* B, float* C, int vectorLength)
{
    int workIndex = threadIdx.x + blockIdx.x*blockDim.x;
    if(workIndex < vectorLength)
    {
        C[workIndex] = A[workIndex] + B[workIndex];

合并内存访问并不要求连续线程一定访问连续内存元素；这只是实现合并的典型方式。只要 warp 中所有线程以某种线性或排列方式访问同一组 32 字节内存段中的元素，就会发生合并内存访问。换句话说，实现合并访问的关键，是最大化“实际使用字节数”与“传输字节数”的比例。

注意

确保全局内存访问正确合并，是编写高性能 CUDA 内核时最重要的性能考虑之一。应用程序必须尽可能高效地使用内存系统。

2.2.4.1.1. 使用全局内存的矩阵转置示例#

作为一个简单示例，考虑一个非原地矩阵转置内核：它把一个大小为 N x N 的 32 位浮点方阵从矩阵 a 转置到矩阵 c。该示例使用二维网格，并假设启动大小为 32 x 32 线程的二维线程块，即 blockDim.x = 32 且 blockDim.y = 32，因此每个二维线程块处理矩阵中的一个 32 x 32 分块。每个线程只操作矩阵中的一个唯一元素，因此不需要显式线程同步。图 12 展示了该矩阵转置操作；内核源代码如下所示。

/* 用于以行优先顺序索引具有 2D 索引的 1D 内存数组的宏 */
/* ld 是主维度，即矩阵中的列数 */

#define INDX( row, col, ld ) ( ( (row) * (ld) ) + (col) )

/* 用于朴素矩阵转置的 CUDA 内核 */

__global__ void naive_cuda_transpose(int m, float *a, float *c )
{
    int myCol = blockDim.x * blockIdx.x + threadIdx.x;
    int myRow = blockDim.y * blockIdx.y + threadIdx.y;

    if( myRow < m && myCol < m )
    {
        c[INDX( myCol, myRow, m )] = a[INDX( myRow, myCol, m )];
    } /* 结束如果 */
    return;
} /* 结束 naive_cuda_transpose */

要判断该内核是否实现了合并内存访问，需要确认连续线程是否访问连续内存元素。在二维线程块中，x 索引变化最快，因此连续的 threadIdx.x 值应当访问内存中的连续元素。threadIdx.x 出现在 myCol 中；可以看到，当 myCol 作为 INDX 宏的第二个参数时，连续线程会读取 a 中的连续值，因此对 a 的读取是完全合并的。

然而，对 c 的写入不是合并的，因为连续的 threadIdx.x 值（也就是连续的 myCol）会把元素写入 c 中彼此相隔 ld（主维度）个元素的位置。原因是此时 myCol 作为 INDX 宏的第一个参数；第一个参数每增加 1，内存位置就变化 ld。当 ld 大于 32 时，也就是矩阵大小大于 32 时，这就相当于 图 11 所示的低效情况。

为了减轻这些未合并的写入，可以使用共享内存，这将在下一节中描述。

2.2.4.2. 共享内存访问模式#

共享内存有 32 个存储体，这些存储体的组织方式使得连续的 32 位字映射到连续的存储体。每个存储体每个时钟周期的带宽为 32 位。

当同一 warp 中的多个线程尝试访问同一存储体中的不同元素时，就会发生存储体冲突。在这种情况下，对该存储体中数据的访问会被串行化，直到请求它的所有线程都取得数据为止。这种串行化会造成性能损失。

同一 warp 中多个线程访问同一个共享内存位置（读取或写入）时，有两个例外。对于读取访问，该字会广播给请求它的线程。对于写入访问，每个共享内存地址只会由一个线程写入，具体由哪个线程执行写入未定义。

图 13 展示了一些跨步访问示例。图中的红色方框表示共享内存中的唯一位置。

图 14 展示了一些涉及广播机制的内存读取访问示例。图中的红色方框表示共享内存中的唯一位置。如果多个箭头指向同一位置，则数据会广播给所有请求它的线程。

注意

避免存储体冲突是编写使用共享内存的高性能 CUDA 内核的重要性能考虑因素。

2.2.4.2.1. 使用共享内存的矩阵转置示例#

在前面的 使用全局内存的矩阵转置示例 中，我们展示了一个结果正确但较为朴素的实现：由于对 c 矩阵的写入未正确合并，因此全局内存利用并不高效。本示例将把共享内存作为用户管理缓存，用于暂存全局内存的读写，从而使读写两侧都获得更好的全局内存合并访问效果。

 1/* X、Y方向线程块尺寸定义 */
 2
 3#define THREADS_PER_BLOCK_X 32
 4#define THREADS_PER_BLOCK_Y 32
 5

10
11/* 用于共享内存矩阵转置的 CUDA 内核 */
12
13__global__ void smem_cuda_transpose(int m, float *a, float *c )
14{

17

19

21

24

29    __syncthreads();

36    } /* 结束如果 */

这个示例体现的基本性能优化，是确保访问全局内存时访问能够正确合并。在执行复制之前，每个线程会计算自己的 tileRow 和 tileCol 索引。它们表示将要操作的特定分块，并由当前执行的线程块决定。同一线程块中的每个线程都有相同的 tileRow 和 tileCol 值，因此可视为该线程块所处理分块的起始位置。

随后，内核使用下面的语句，把每个线程块对应的 32 x 32 矩阵分块从全局内存复制到共享内存。由于 warp 大小为 32 个线程，该复制操作会由 32 个 warp 执行，并且不保证 warp 之间的执行顺序。

smemArray[threadIdx.x][threadIdx.y] = a[INDX( tileRow + threadIdx.y, tileCol + threadIdx.x, m )];

注意，由于 threadIdx.x 出现在 INDX 的第二个参数中，连续线程会访问连续内存元素，因此对 a 的读取是完全合并的。

内核下一步会调用 __syncthreads() 函数。它确保线程块中的所有线程都完成前面代码的执行后才继续，因此，在进入下一步之前，所有线程都已经把 a 中的数据写入共享内存。这很重要，因为下一步会从共享内存读取数据。如果没有 __syncthreads() 调用，当某些 warp 已继续执行到后面的代码时，不能保证线程块中的所有 warp 都已完成向共享内存的写入。

此时，对于每个线程块，smemArray 中都有一个 32 x 32 的矩阵分块，其排列顺序与原始矩阵相同。为了确保分块内部的元素被正确转置，线程在读取 smemArray 时会交换 threadIdx.x 和 threadIdx.y。为了确保整体分块被放到 c 中的正确位置，写入 c 时也会交换 tileRow 和 tileCol 索引。为保证合并访问，threadIdx.x 用作 INDX 的第二个参数，如下语句所示。

c[INDX( tileCol + threadIdx.y, tileRow + threadIdx.x, m )] = smemArray[threadIdx.y][threadIdx.x];

该内核说明了共享内存的两种常见用途。

  • 共享内存用于暂存全局内存中的数据，以确保对全局内存的读取和写入都正确合并。

  • 共享内存用于允许同一线程块中的线程之间共享数据。

2.2.4.2.2. 共享内存 Bank 冲突#

第 2.2.4.2 节 描述了共享内存的 bank 结构。在前面的矩阵转置示例中，全局内存访问已经正确合并，但还没有考虑共享内存 bank 冲突。请看下面这个二维共享内存声明：

__shared__ float smemArray[32][32];

由于一个 warp 有 32 个线程，同一 warp 中每个线程的 threadIdx.y 固定，并且满足 0 <= threadIdx.x < 32。

图 15 左侧展示了 warp 中线程访问 smemArray 一列数据时的情况。warp 0 正在访问从 smemArray[0][0] 到 smemArray[31][0] 的内存位置。在 C++ 多维数组布局中，最后一个索引变化最快，因此 warp 0 中的连续线程访问的是相隔 32 个元素的内存位置。如图中颜色所示，warp 0 向下访问整列会导致 32 路 bank 冲突。

图 15 右侧展示了 warp 中线程横向访问 smemArray 一行数据时的情况。warp 0 正在访问从 smemArray[0][0] 到 smemArray[0][31] 的内存位置。在这种情况下，warp 0 中的连续线程访问相邻内存位置。如颜色所示，warp 0 横向访问整行不会导致 bank 冲突。理想情况下，warp 中每个线程都访问不同颜色的共享内存位置。

回到 第 2.2.4.2.1 节 的示例，可以检查共享内存的使用方式，判断是否存在 bank 冲突。第一次使用共享内存，是把全局内存中的数据存入共享内存：

smemArray[threadIdx.x][threadIdx.y] = a[INDX( tileRow + threadIdx.y, tileCol + threadIdx.x, m )];

由于 C++ 数组按行优先顺序存储，而 threadIdx.x 是数组的第一个索引，因此同一 warp 中连续的 threadIdx.x 值会让连续线程以 32 个元素的步幅访问 smemArray。这会导致 32 路 bank 冲突，如 图 15 左侧所示。

共享内存的第二种用法是将共享内存中的数据写回全局内存时：

c[INDX( tileCol + threadIdx.y, tileRow + threadIdx.x, m )] = smemArray[threadIdx.y][threadIdx.x];

在这种情况下，由于 threadIdx.x 是 smemArray 数组的第二个索引，同一 warp 中的连续线程会以 1 个元素的步幅访问 smemArray。这不会导致 bank 冲突，如 图 15 右侧所示。

第 2.2.4.2.1 节 中的矩阵转置内核包含两种共享内存访问：一种没有 bank 冲突，另一种有 32 路 bank 冲突。避免 bank 冲突的常见修复方法，是在数组列维度上加 1，对共享内存进行填充，如下所示：

__shared__ float smemArray[THREADS_PER_BLOCK_X][THREADS_PER_BLOCK_Y+1];

对 smemArray 声明做这个小调整，就会消除 bank 冲突。为说明这一点，请看 图 16：其中共享内存数组声明为 32 x 33。可以看到，无论同一 warp 中的线程是向下访问整列，还是横向访问整行，共享内存数组中的 bank 冲突都会被消除，也就是同一 warp 中的线程会访问不同颜色的位置。

2.2.5. 原子操作#

高性能 CUDA 内核依赖于表达尽可能多的算法并行性。 GPU 内核执行的异步特性要求线程尽可能独立运行。 线程完全独立并不总是可能的，正如我们在 共享内存，存在一种机制可以让同一线程块中的线程交换数据并进行同步。

在整个网格层面，没有机制可以同步网格中的所有线程。不过，可以通过原子函数为全局内存位置提供同步访问。原子函数允许线程对某个全局内存位置执行读取-修改-写入操作，并保证该操作相对于其他线程是原子的。CUDA 提供与 C++ 标准库原子行为一致的 cuda::std::atomic 和 cuda::std::atomic_ref。此外，CUDA 还提供扩展 C++ 原子 cuda::atomic 和 cuda::atomic_ref，允许用户为原子操作指定 线程作用域。原子函数的详细信息见 原子函数。

下面示例使用 cuda::atomic_ref 执行设备作用域的原子加法。其中 array 是浮点数组，result 是指向全局内存中某个位置的浮点指针，该位置用于存储数组求和结果。

__global__ void sumReduction(int n, float *array, float *result) {
   ...
   tid = threadIdx.x + blockIdx.x * blockDim.x;

   cuda::atomic_ref<float, cuda::thread_scope_device> result_ref(result);
   result_ref.fetch_add(array[tid]);
   ...
}

应谨慎使用原子函数，因为它们强制执行可能影响性能的线程同步。

2.2.6. 协作组（Cooperative Groups）#

Cooperative Groups 是 CUDA C++ 提供的软件工具，允许应用程序定义可相互同步的线程组，即便这些线程组跨越多个线程块、单个 GPU 上的多个网格，甚至跨越多个 GPU。CUDA 编程模型通常允许线程块或线程块簇内的线程高效同步，但不提供指定小于线程块或簇的线程组的机制。同样，CUDA 编程模型也不提供跨线程块同步的机制或保证。

Cooperative Groups 通过软件提供这两类能力。它允许应用程序创建跨越线程块和簇边界的线程组，不过这样做会带来一些语义限制和性能影响；这些限制与影响会在 Cooperative Groups 专题章节 中说明。

2.2.7. 内核启动与占用率#

CUDA 内核启动时，CUDA 线程会根据执行配置组织为线程块和网格。内核启动后，调度器会把线程块分配给各个 SM。应用程序无法控制或查询某个线程块会被调度到哪个 SM，也不能从调度器获得任何顺序保证，因此程序的正确性不能依赖特定调度顺序或调度方案。

一个 SM 上可驻留的线程块数量，取决于单个线程块所需的硬件资源以及该 SM 当前可用的硬件资源。内核启动后，调度器开始向 SM 分配线程块。只要某个 SM 还有足够硬件资源未被其他线程块占用，调度器就可以继续向该 SM 分配线程块。如果暂时没有 SM 能接收新的线程块，调度器就会等待，直到某个 SM 完成先前分配的线程块。随后该 SM 便可接收更多工作，调度器也会继续向其分配线程块。这个过程会持续到所有线程块都被调度并执行完毕。

cudaGetDeviceProperties 允许应用程序通过查询 设备属性 获取每个 SM 的限制。注意，限制既可能按 SM 计，也可能按线程块计。

  • maxBlocksPerMultiProcessor：每个 SM 的最大驻留块数。

  • sharedMemPerMultiprocessor：每个 SM 可用的共享内存量（以字节为单位）。

  • regsPerMultiprocessor：每个 SM 可用的 32 位寄存器的数量。

  • maxThreadsPerMultiProcessor：每个 SM 的最大常驻线程数。

  • sharedMemPerBlock：线程块可以分配的最大共享内存量（以字节为单位）。

  • regsPerBlock：一个线程块可分配的最大 32 位寄存器数量。

  • maxThreadsPerBlock：每个线程块的最大线程数。

CUDA 内核的占用率，是活动 warp 数量与 SM 支持的最大活动 warp 数量之比。一般来说，较高占用率有助于隐藏延迟并提升性能。

计算占用率时，我们既需要知道上面列出的 SM 资源限制，也需要知道目标 CUDA 内核会消耗哪些资源。要确定每个内核的资源使用情况，可在编译时使用 nvcc 的 --resource-usage 选项，它会显示内核所需的寄存器和共享内存数量。

为说明这一点，请考虑一个计算能力为 10.0 的设备，其设备属性见 表 2。

如果内核以 testKernel<<<512, 768>>>() 启动，即每个线程块 768 个线程，那么每个 SM 一次最多只能执行 2 个线程块。调度器不能为每个 SM 分配超过 2 个线程块，因为 maxThreadsPerMultiProcessor 为 2048。因此占用率为 (768 * 2) / 2048，即 75%。

如果内核以 testKernel<<<512, 32>>>() 启动，即每个线程块 32 个线程，则每个 SM 不会触及 maxThreadsPerMultiProcessor 限制。但由于 maxBlocksPerMultiProcessor 为 32，调度器每个 SM 最多只能分配 32 个线程块。每个线程块有 32 个线程，因此驻留在 SM 上的线程总数为 32 个线程块 * 每块 32 个线程，即 1024 个线程。计算能力 10.0 的 SM 每个 SM 最多支持 2048 个常驻线程，所以本例占用率为 1024 / 2048，即 50%。

共享内存也可以按同样方式分析。例如，如果某个内核使用 100 KB 共享内存，调度器每个 SM 最多只能分配 2 个线程块，因为该 SM 上第三个线程块还需要额外 100 KB 共享内存，总计 300 KB，超过了每个 SM 可用的 233472 字节。

每个线程块的线程数和共享内存使用量由程序员显式控制，可通过调节它们来达到期望占用率。程序员对寄存器使用量的控制较有限，因为编译器和运行时会尝试优化寄存器分配。不过，程序员可以通过 nvcc 的 --maxrregcount 选项 指定每个线程可使用的最大寄存器数量。如果内核需要的寄存器超过指定数量，就可能溢出到本地内存，从而改变性能特征。在某些情况下，即使发生溢出，限制寄存器数量也能让调度器安排更多线程块，进而提高占用率并带来净性能收益。
