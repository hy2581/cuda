2.1. CUDA C++ 入门#

本章通过 C++ 示例介绍 CUDA 编程模型中的一些基础概念。

本编程指南主要介绍 CUDA Runtime API。它是 C++ 中最常用的 CUDA 使用方式，并构建在更底层的 CUDA Driver API 之上。

CUDA Runtime API 与 CUDA Driver API 说明了这两套 API 的差异；CUDA Driver API 章节则讨论如何编写混用两套 API 的代码。

本指南假设系统已经安装 CUDA Toolkit 和 NVIDIA Driver，并且配备受支持的 NVIDIA GPU。安装必要 CUDA 组件的步骤，请参阅 CUDA 快速入门指南。

2.1.1. 使用 NVCC 编译#

使用 C++ 编写的 GPU 代码由 NVIDIA CUDA 编译器 nvcc 编译。nvcc 是一个编译器驱动程序，用来简化 C++ 或 PTX 代码的编译流程：它提供简单、熟悉的命令行选项，并通过调用一组工具来完成不同的编译阶段。

本指南中的 nvcc 命令行示例，可用于安装了 CUDA Toolkit 的 Linux 系统、Windows 命令提示符或 PowerShell，也可用于带 CUDA Toolkit 的 Windows Subsystem for Linux。本文档的 NVCC 章节 介绍 nvcc 的常见用法；完整文档见 nvcc 用户手册。

2.1.2. 内核（Kernel）#

如 CUDA 编程模型 中所述，可以从主机端调用、并在 GPU 上执行的函数称为内核（kernel）。内核会由许多并行线程同时运行。

2.1.2.1. 定义内核#

内核代码使用 __global__ 声明说明符来标记。该说明符告诉编译器：这个函数需要为 GPU 编译，并且可以通过一次内核启动来调用。内核启动通常是从 CPU 发起、让内核开始运行的操作。内核函数的返回类型必须是 void。

// 内核定义
__global__ void vecAdd(float* A, float* B, float* C)
{

}

2.1.2.2. 启动内核#

并行执行内核的线程数量会在内核启动时指定，这称为执行配置（execution configuration）。同一个内核的不同调用可以使用不同的执行配置，例如不同数量的线程或线程块。

从 CPU 代码启动内核有两种方式：三尖括号语法 和 cudaLaunchKernelEx。这里先介绍最常见的三尖括号语法。使用 cudaLaunchKernelEx 启动内核的示例，会在 第 3.1.1 节 中详细展示和讨论。

2.1.2.2.1. 三尖括号语法#

三尖括号语法是一项用于启动内核的 CUDA C++ 语言扩展。它之所以叫三尖括号，是因为它用三个尖括号字符包住内核启动的执行配置，即 <<< >>>。执行配置参数以逗号分隔的列表写在尖括号内，形式类似函数调用的参数。下面展示了 vecAdd 内核的启动语法。

 __global__ void vecAdd(float* A, float* B, float* C)
 {

 }

int main()
{
    ...
    // 内核调用
    vecAdd<<<1, 256>>>(A, B, C);
    ...
}

三尖括号语法的前两个参数分别是网格维度和线程块维度。使用一维线程块或网格时，可以直接用整数指定维度。

上面的代码启动了一个包含 256 个线程的线程块。每个线程都会执行同一份内核代码。在 线程与网格索引内建变量 中，我们会展示每个线程如何利用自己在线程块和网格中的索引，选择要处理的数据。

每个线程块中的线程数量有上限，因为同一线程块中的所有线程都驻留在同一个流式多处理器（SM）上，并且必须共享该 SM 的资源。在当前 GPU 上，一个线程块最多可包含 1024 个线程。如果资源允许，一个 SM 可以同时调度多个线程块。

相对于主机线程，内核启动是异步的。也就是说，内核会被提交到 GPU 上执行，但主机代码不会等待内核在 GPU 上完成执行，甚至不会等待它开始执行，就会继续向下运行。因此必须在 GPU 与 CPU 之间使用某种同步机制，才能确定内核已经完成。最基本的方式是同步整个 GPU，见 CPU 与 GPU 同步。更复杂的同步方法见 异步执行。

使用二维或三维网格、线程块时，CUDA 类型 dim3 可作为网格和线程块维度参数。下面的代码片段展示了如何启动 MatAdd 内核：它使用 16 x 16 个线程块构成的网格，每个线程块大小为 8 x 8。

int main()
{
    ...
    dim3 grid(16,16);
    dim3 block(8,8);
    MatAdd<<<grid, block>>>(A, B, C);
    ...
}

2.1.2.3. 线程与网格索引内建变量#

在内核代码中，CUDA 提供了一组内建变量，可访问执行配置参数以及线程/线程块索引。

  • threadIdx 给出线程在其线程块中的索引。线程块中的每个线程都会有不同的索引。

  • blockDim 给出线程块的尺寸，该尺寸在内核启动的执行配置中指定。

  • blockIdx 给出线程块在网格中的索引。每个线程块都会有不同的索引。

  • gridDim 给出网格的尺寸，该尺寸在内核启动时在执行配置中指定。

这些内建变量都是三分量向量，成员包括 .x、.y 和 .z。启动配置中没有指定的维度会默认为 1。 threadIdx 和 blockIdx 都从 0 开始计数。也就是说，threadIdx.x 的取值范围是 0 到 blockDim.x-1，包含两端。.y 和 .z 在各自维度上遵循同样的规则。

类似地，blockIdx.x 的取值范围是 0 到 gridDim.x-1，包含两端；.y 和 .z 维度也是如此。

这些内建变量让每个线程能够识别自己要执行的工作。回到 vecAdd 内核，它接收三个参数，每个参数都是浮点向量。内核对 A 和 B 做逐元素加法，并将结果存入 C。该内核会并行执行，让每个线程完成一次加法；具体计算哪个元素，由线程索引和网格索引共同决定。

__global__ void vecAdd(float* A, float* B, float* C)
{
   // 计算这个线程负责计算哪个元素
   int workIndex = threadIdx.x + blockDim.x * blockIdx.x

   // 执行计算
   C[workIndex] = A[workIndex] + B[workIndex];
}

int main()
{
    ...
    // A、B 和 C 是 1024 个元素的向量
    vecAdd<<<4, 256>>>(A, B, C);
    ...
}

在这个示例中，程序使用 4 个线程块、每块 256 个线程来相加一个包含 1024 个元素的向量。在第一个线程块中，blockIdx.x 为 0，因此每个线程的 workIndex 就等于它的 threadIdx.x。在第二个线程块中，blockIdx.x 为 1，因此 blockDim.x * blockIdx.x 等于 blockDim.x，本例中也就是 256。第二个线程块中每个线程的 workIndex 为 threadIdx.x + 256。第三个线程块中，workIndex 则为 threadIdx.x + 512。

这种 workIndex 计算在一维并行化中很常见。扩展到二维或三维时，通常也会在每个维度上采用类似模式。

2.1.2.3.1. 边界检查#

上面的示例假设向量长度是线程块大小的整数倍，本例中线程块大小为 256。为了让内核能处理任意向量长度，可以像下面这样添加边界检查，确保内存访问不会越过数组边界；这样启动的最后一个线程块中可能会包含一些不执行实际工作的线程。

__global__ void vecAdd(float* A, float* B, float* C, int vectorLength)
{
     // 计算这个线程负责计算哪个元素
     int workIndex = threadIdx.x + blockDim.x * blockIdx.x

     if(workIndex < vectorLength)
     {
         // 执行计算
         C[workIndex] = A[workIndex] + B[workIndex];
     }
}

使用上述内核代码后，可以启动略多于实际需要的线程，而不会造成数组越界访问。当 workIndex 超过 vectorLength 时，该线程会直接退出，不执行任何工作。在线程块内多启动一些不工作的线程通常开销不大，但应避免启动完全没有线程执行有效工作的线程块。这样修改后，内核就可以处理长度不是线程块大小整数倍的向量。

所需线程块数量可以按“所需线程数除以每块线程数并向上取整”来计算，本例中所需线程数就是向量长度。下面给出一种常见写法，它只用一次整数除法表达向上取整。通过在整数除法前加上 threads - 1，该表达式的行为类似上取整函数：只有当向量长度不能被每块线程数整除时，才会额外增加一个线程块。

// vectorLength 是一个整数，存储向量中元素的数量
int threads = 256;
int blocks = (vectorLength + threads-1)/threads;
vecAdd<<<blocks, threads>>>(devA, devB, devC, vectorLength);

CUDA Core Compute Library (CCCL) 提供了方便的工具函数 cuda::ceil_div，可用这种向上取整除法计算内核启动所需的线程块数。包含头文件 <cuda/cmath> 后即可使用该工具。

// vectorLength 是一个整数，存储向量中元素的数量
int threads = 256;
int blocks = cuda::ceil_div(vectorLength, threads);
vecAdd<<<blocks, threads>>>(devA, devB, devC, vectorLength);

这里选择每个线程块 256 个线程只是示例取值，不过它通常是一个不错的起点。

2.1.3. GPU 计算中的内存#

要使用上面的 vecAdd 内核，数组 A、B 和 C 必须位于 GPU 可以访问的内存中。实现方式有多种，这里介绍其中两种。其他方式会在后续 统一内存 章节中说明。GPU 端代码可用的内存空间已在 GPU 内存 中简要介绍，并会在 GPU 设备内存空间 中进一步展开。

2.1.3.1. 统一内存#

统一内存是 CUDA Runtime 的一项功能，可让 NVIDIA Driver 管理主机与设备之间的数据移动。可以使用 cudaMallocManaged API 分配统一内存，也可以在变量声明中使用 __managed__ 说明符。无论 GPU 还是 CPU 试图访问这段内存，NVIDIA Driver 都会确保它在访问方可用。

下面的代码展示了一个完整函数：它启动 vecAdd 内核，并用统一内存存放 GPU 将要使用的输入、输出向量。cudaMallocManaged 分配的缓冲区既可由 CPU 访问，也可由 GPU 访问。这些缓冲区使用 cudaFree 释放。

void unifiedMemExample(int vectorLength)
{
    // 指向内存向量的指针
    float* A = nullptr;
    float* B = nullptr;
    float* C = nullptr;
    float* comparisonResult = (float*)malloc(vectorLength*sizeof(float));

    // 使用统一内存分配缓冲区
    cudaMallocManaged(&A, vectorLength*sizeof(float));
    cudaMallocManaged(&B, vectorLength*sizeof(float));
    cudaMallocManaged(&C, vectorLength*sizeof(float));

    // 在主机上初始化向量
    initArray(A, vectorLength);
    initArray(B, vectorLength);

    // 启动内核。统一内存会确保 GPU
    // 可以访问 A、B 和 C
    int threads = 256;
    int blocks = cuda::ceil_div(vectorLength, threads);
    vecAdd<<<blocks, threads>>>(A, B, C, vectorLength);
    // 等待内核完成执行
    cudaDeviceSynchronize();

    // 在 CPU 上串行执行计算以便比较
    serialVecAdd(A, B, comparisonResult, vectorLength);

    // 确认 CPU 和 GPU 得到相同结果
    if(vectorApproximatelyEqual(C, comparisonResult, vectorLength))
    {
        printf("Unified Memory: CPU and GPU answers match\n");
    }
    else
    {
        printf("Unified Memory: Error - CPU and GPU answers do not match\n");
    }

    // 清理
    cudaFree(A);
    cudaFree(B);
    cudaFree(C);
    free(comparisonResult);

}

CUDA 支持的所有操作系统和 GPU 都支持统一内存，但底层机制和性能可能随系统架构而变化。更多细节见 统一内存。在某些 Linux 系统上，例如支持 地址转换服务 或 异构内存管理 的系统，所有系统内存都会自动成为统一内存，因此无需使用 cudaMallocManaged 或 __managed__ 说明符。

2.1.3.2. 显式内存管理#

显式管理内存分配，以及不同内存空间之间的数据迁移，有助于提升应用程序性能，但代码也会更长。下面的代码使用 cudaMalloc 在 GPU 上显式分配内存。GPU 内存使用 cudaFree 释放，这与前面统一内存示例中使用的 API 相同。

void explicitMemExample(int vectorLength)
{
    // 主机内存指针
    float* A = nullptr;
    float* B = nullptr;
    float* C = nullptr;
    float* comparisonResult = (float*)malloc(vectorLength*sizeof(float));
    
    // 设备内存指针
    float* devA = nullptr;
    float* devB = nullptr;
    float* devC = nullptr;

    // 使用 cudaMallocHost API 分配主机内存。缓冲区将用于
    // CPU 与 GPU 内存之间的数据复制时，这是推荐做法
    cudaMallocHost(&A, vectorLength*sizeof(float));
    cudaMallocHost(&B, vectorLength*sizeof(float));
    cudaMallocHost(&C, vectorLength*sizeof(float));

    // 在主机上初始化向量
    initArray(A, vectorLength);
    initArray(B, vectorLength);

    // 开始分配和复制
    // 在 GPU 上分配内存
    cudaMalloc(&devA, vectorLength*sizeof(float));
    cudaMalloc(&devB, vectorLength*sizeof(float));
    cudaMalloc(&devC, vectorLength*sizeof(float));

    // 将数据复制到 GPU
    cudaMemcpy(devA, A, vectorLength*sizeof(float), cudaMemcpyDefault);
    cudaMemcpy(devB, B, vectorLength*sizeof(float), cudaMemcpyDefault);
    cudaMemset(devC, 0, vectorLength*sizeof(float));
    // 结束分配和复制

    // 启动内核
    int threads = 256;
    int blocks = cuda::ceil_div(vectorLength, threads);
    vecAdd<<<blocks, threads>>>(devA, devB, devC, vectorLength);
    // 等待内核执行完成
    cudaDeviceSynchronize();

    // 将结果复制回主机
    cudaMemcpy(C, devC, vectorLength*sizeof(float), cudaMemcpyDefault);

    // 在 CPU 上串行执行计算以便比较
    serialVecAdd(A, B, comparisonResult, vectorLength);

    // 确认 CPU 和 GPU 得到相同结果
    if(vectorApproximatelyEqual(C, comparisonResult, vectorLength))
    {
        printf("Explicit Memory: CPU and GPU answers match\n");
    }
    else
    {
        printf("Explicit Memory: Error - CPU and GPU answers to not match\n");
    }

    // 清理
    cudaFree(devA);
    cudaFree(devB);
    cudaFree(devC);
    cudaFreeHost(A);
    cudaFreeHost(B);
    cudaFreeHost(C);
    free(comparisonResult);
}

CUDA API cudaMemcpy 用于在 CPU 端缓冲区和 GPU 端缓冲区之间复制数据。除了目标指针、源指针和字节数之外，cudaMemcpy 的最后一个参数是 cudaMemcpyKind_t。它可以取 cudaMemcpyHostToDevice 这样的值，表示从 CPU 复制到 GPU；也可以取 cudaMemcpyDeviceToHost，表示从 GPU 复制到 CPU；还可以取 cudaMemcpyDeviceToDevice，表示在同一 GPU 内部或不同 GPU 之间复制。

在这个示例中，cudaMemcpyDefault 作为最后一个参数传给 cudaMemcpy。这样 CUDA 会根据源指针和目标指针的值自动判断应执行哪种复制。

cudaMemcpy API 是同步的，也就是说，它会等到复制完成后才返回。异步复制会在 在 CUDA 流中启动内存传输 中介绍。

示例代码使用 cudaMallocHost 在 CPU 上分配内存。它会在主机上分配 页锁定内存，这能提升复制性能，并且是进行 异步 内存传输所必需的。一般来说，用于向 GPU 发送数据或从 GPU 接收数据的 CPU 缓冲区，最好使用页锁定内存。不过，如果过多主机内存被页锁定，某些系统上的性能可能会下降；最佳实践是只对确实参与 GPU 数据传输的缓冲区使用页锁定。

2.1.3.3. 内存管理与应用性能#

从上面的示例可以看出，显式内存管理更繁琐，需要程序员明确指定主机与设备之间的数据复制。这既是显式内存管理的缺点，也是它的优点：程序员可以更精确地控制何时在主机和设备之间复制数据、内存驻留在哪里，以及哪些内存在何处被分配。显式内存管理也为控制内存传输、并将传输与其他计算重叠提供了性能优化空间。

使用统一内存时，也有一些 CUDA API 可以向负责管理内存的 NVIDIA Driver 提供提示，相关内容会在 内存建议和预取 中介绍。借助这些提示，统一内存也能获得显式内存管理中的部分性能优势。

2.1.4. CPU 与 GPU 同步#

如 启动内核 一节所述，内核启动相对于发起调用的 CPU 线程是异步的。这意味着 CPU 线程的控制流会在内核完成之前继续向前执行，甚至可能在内核尚未真正启动前就继续执行。若要保证主机端后续代码执行前内核已经完成，就必须使用某种同步机制。

同步 GPU 与主机线程最简单的方法是调用 cudaDeviceSynchronize，它会阻塞主机线程，直到 GPU 上此前提交的所有工作都完成。本章示例中 GPU 只执行单个操作，因此这种方式已经足够。更大的应用可能会有多个 流 同时在 GPU 上执行工作，而 cudaDeviceSynchronize 会等待所有流中的工作完成。在这类应用中，更推荐使用 流同步 API 只同步特定流，或使用 CUDA 事件。这些内容会在 异步执行 一章中介绍。

2.1.5. 整合示例#

下面的清单给出了本章简单向量加法内核的完整代码，包括所有主机端代码，以及用于检查结果是否正确的辅助函数。示例默认使用长度为 1024 的向量，也可以通过可执行文件的命令行参数传入其他向量长度。

#include <cuda_runtime_api.h>
#include <memory.h>
#include <cstdlib>
#include <ctime>
#include <stdio.h>
#include <cuda/cmath>

__global__ void vecAdd(float* A, float* B, float* C, int vectorLength)
{
    int workIndex = threadIdx.x + blockIdx.x*blockDim.x;
    if(workIndex < vectorLength)
    {
        C[workIndex] = A[workIndex] + B[workIndex];
    }
}

void initArray(float* A, int length)
{
     std::srand(std::time({}));
    for(int i=0; i<length; i++)
    {
        A[i] = rand() / (float)RAND_MAX;
    }
}

{
    for(int i=0; i<length; i++)
    {
        C[i] = A[i] + B[i];
    }
}

bool vectorApproximatelyEqual(float* A, float* B, int length, float epsilon=0.00001)
{
    for(int i=0; i<length; i++)
    {
        if(fabs(A[i] -B[i]) > epsilon)
        {
            printf("Index %d mismatch: %f != %f", i, A[i], B[i]);
            return false;
        }
    }
    return true;
}

// 统一内存开始
void unifiedMemExample(int vectorLength)
{
    // 指向内存向量的指针
    float* A = nullptr;
    float* B = nullptr;
    float* C = nullptr;
    float* comparisonResult = (float*)malloc(vectorLength*sizeof(float));

    // 使用统一内存分配缓冲区
    cudaMallocManaged(&A, vectorLength*sizeof(float));
    cudaMallocManaged(&B, vectorLength*sizeof(float));
    cudaMallocManaged(&C, vectorLength*sizeof(float));

    // 在主机上初始化向量
    initArray(A, vectorLength);
    initArray(B, vectorLength);

    // 启动内核。统一内存将确保 A、B 和 C
    // GPU 可以访问
    int threads = 256;
    int blocks = cuda::ceil_div(vectorLength, threads);
    vecAdd<<<blocks, threads>>>(A, B, C, vectorLength);
    // 等待内核完成执行
    cudaDeviceSynchronize();

    // 在CPU上串行执行计算以进行比较
    serialVecAdd(A, B, comparisonResult, vectorLength);

    // 确认 CPU 和 GPU 得到相同结果
    if(vectorApproximatelyEqual(C, comparisonResult, vectorLength))
    {
        printf("Unified Memory: CPU and GPU answers match\n");
    }
    else
    {
        printf("Unified Memory: Error - CPU and GPU answers do not match\n");
    }

    // 清理
    cudaFree(A);
    cudaFree(B);
    cudaFree(C);
    free(comparisonResult);

}

// 显式内存开始
void explicitMemExample(int vectorLength)
{
    // 主机内存指针
    float* A = nullptr;
    float* B = nullptr;
    float* C = nullptr;
    float* comparisonResult = (float*)malloc(vectorLength*sizeof(float));
    
    // 设备内存指针
    float* devA = nullptr;
    float* devB = nullptr;
    float* devC = nullptr;

    // 使用 cudaMallocHost API 分配主机内存。这是最佳实践
    // 何时使用缓冲区在 CPU 和 GPU 内存之间进行复制
    cudaMallocHost(&A, vectorLength*sizeof(float));
    cudaMallocHost(&B, vectorLength*sizeof(float));
    cudaMallocHost(&C, vectorLength*sizeof(float));

    // 在主机上初始化向量
    initArray(A, vectorLength);
    initArray(B, vectorLength);

    // 开始分配和复制
    // 在 GPU 上分配内存
    cudaMalloc(&devA, vectorLength*sizeof(float));
    cudaMalloc(&devB, vectorLength*sizeof(float));
    cudaMalloc(&devC, vectorLength*sizeof(float));

    // 将数据复制到GPU
    cudaMemcpy(devA, A, vectorLength*sizeof(float), cudaMemcpyDefault);
    cudaMemcpy(devB, B, vectorLength*sizeof(float), cudaMemcpyDefault);
    cudaMemset(devC, 0, vectorLength*sizeof(float));
    // 结束分配和复制

    // 启动内核
    int threads = 256;
    int blocks = cuda::ceil_div(vectorLength, threads);
    vecAdd<<<blocks, threads>>>(devA, devB, devC, vectorLength);
    // 等待内核执行完成
    cudaDeviceSynchronize();

    // 将结果复制回主机
    cudaMemcpy(C, devC, vectorLength*sizeof(float), cudaMemcpyDefault);

    // 在CPU上串行执行计算以进行比较
    serialVecAdd(A, B, comparisonResult, vectorLength);

    // 确认 CPU 和 GPU 得到相同结果
    if(vectorApproximatelyEqual(C, comparisonResult, vectorLength))
    {
        printf("Explicit Memory: CPU and GPU answers match\n");
    }
    else
    {
        printf("Explicit Memory: Error - CPU and GPU answers to not match\n");
    }

    // 清理
    cudaFree(devA);
    cudaFree(devB);
    cudaFree(devC);
    cudaFreeHost(A);
    cudaFreeHost(B);
    cudaFreeHost(C);
    free(comparisonResult);
}
// 显式内存结束


int main(int argc, char** argv)
{
    int vectorLength = 1024;
    if(argc >=2)
    {
        vectorLength = std::atoi(argv[1]);
    }
    explicitMemExample(vectorLength);		
    return 0;
}

在这些示例中，所有线程都执行相互独立的工作，不需要彼此协调或同步。但在实际程序中，线程经常需要与其他线程协作、通信才能完成任务。同一线程块内的线程可以通过 共享内存 共享数据，并通过同步来协调内存访问。

块级同步最基本的机制是内建函数 __syncthreads()。它会充当一个屏障：线程块中的所有线程都必须到达该位置后，任何线程才允许继续执行。共享内存 一节给出了使用共享内存的示例。

为了高效协作，共享内存被设计为靠近每个处理器核心的低延迟内存，类似 L1 缓存；__syncthreads() 也被设计为相对轻量。__syncthreads() 只同步单个线程块内的线程。CUDA 编程模型不支持普通线程块之间的同步。Cooperative Groups 提供了设置其他同步域的机制，而不仅限于单个线程块。

通常，将同步限制在线程块内部可以获得最佳性能。线程块仍然可以通过 原子内存函数 协同更新共同结果，后续章节会介绍这一点。

第 3.2.4 节 介绍 CUDA 同步原语，这些原语提供非常细粒度的控制，有助于最大化性能和资源利用率。

2.1.6. 运行时初始化#

CUDA Runtime 会为系统中的每个设备创建一个 CUDA 上下文。这个上下文是该设备的主上下文，会在第一个需要该设备上有活动上下文的 Runtime 函数中初始化。上下文由应用程序的所有主机线程共享。创建上下文时，如有必要，设备代码会被 即时编译，并加载到设备内存中；这些过程对应用程序透明。CUDA Runtime 创建的主上下文也可以通过 Driver API 访问，以实现互操作，见 Runtime API 与 Driver API 的互操作。

从 CUDA 12.0 开始，调用 cudaInitDevice 或 cudaSetDevice 会初始化运行时，以及与指定设备关联的主 上下文。如果在这些调用之前已经发生 Runtime API 请求，运行时会隐式使用设备 0，并按需自初始化来处理这些请求。对 Runtime 函数调用计时，或解释第一次进入 Runtime 调用返回的错误码时，这一点很重要。在 CUDA 12.0 之前，cudaSetDevice 不会初始化运行时。

cudaDeviceReset 会销毁当前设备的主上下文。如果主上下文被销毁后又调用 CUDA Runtime API，系统会为该设备创建新的主上下文。

注

CUDA 接口使用全局状态；该状态会在主机程序启动期间初始化，并在主机程序终止期间销毁。在 main 之外的程序启动或终止阶段，隐式或显式使用这些接口都会导致未定义行为。

从 CUDA 12.0 开始，cudaSetDevice 在切换主机线程的当前设备后，会在运行时尚未初始化时显式初始化运行时。旧版本 CUDA 会把新设备上的运行时初始化推迟到 cudaSetDevice 之后的第一次 Runtime 调用。因此，检查 cudaSetDevice 的返回值以发现初始化错误非常重要。

参考手册中错误处理和版本管理部分的 Runtime 函数不会初始化运行时。

2.1.7. CUDA 中的错误检查#

每个 CUDA API 都会返回一个枚举类型值 cudaError_t。示例代码中常常省略错误检查；但在生产应用中，最佳实践是始终检查并处理每个 CUDA API 调用的返回值。没有错误时，返回值为 cudaSuccess。许多应用会实现类似下面这样的辅助宏。

#define CUDA_CHECK(expr_to_check) do {            \
    cudaError_t result  = expr_to_check;          \
    if(result != cudaSuccess)                     \
    {                                             \
        fprintf(stderr,                           \
                "CUDA Runtime Error: %s:%i:%d = %s\n", \
                __FILE__,                         \
                __LINE__,                         \
                result,\
                cudaGetErrorString(result));      \
    }                                             \
} while(0)

该宏使用 cudaGetErrorString API，后者会返回一个人类可读的字符串，用来描述特定 cudaError_t 值的含义。使用上面的宏时，应用程序可以把 CUDA Runtime API 调用包在 CUDA_CHECK(expression) 中，如下所示：

    CUDA_CHECK(cudaMalloc(&devA, vectorLength*sizeof(float)));
    CUDA_CHECK(cudaMalloc(&devB, vectorLength*sizeof(float)));
    CUDA_CHECK(cudaMalloc(&devC, vectorLength*sizeof(float)));

如果这些调用中的任意一个检测到错误，该宏就会把错误打印到 stderr。这种宏在小型项目中很常见；在大型应用中，也可以改造成接入日志系统或其他错误处理机制的形式。

注

需要注意，任意 CUDA API 调用返回的错误状态，也可能表示此前发出的异步操作发生了错误。异步错误处理 一节会更详细地说明这一点。

2.1.7.1. 错误状态#

CUDA Runtime 会为每个主机线程维护一个 cudaError_t 状态。该值默认为 cudaSuccess，发生错误时会被覆盖。cudaGetLastError 返回当前错误状态，并将其重置为 cudaSuccess。相对地，cudaPeekLastError 会返回错误状态，但不会重置它。

使用 三尖括号语法 启动内核时不会返回 cudaError_t。因此，最好在内核启动后立即检查错误状态，以捕获内核启动本身的即时错误，或捕获内核启动之前已经发生的 异步错误。在内核启动后立刻检查到 cudaSuccess，并不表示内核已经成功执行，甚至不表示它已经开始执行；它只说明传给 Runtime 的启动参数和执行配置没有触发错误，并且错误状态中没有内核启动前遗留的错误或异步错误。

2.1.7.2. 异步错误#

CUDA 内核启动和许多 Runtime API 都是异步的。异步 CUDA Runtime API 会在 异步执行 中详细讨论。每当发生错误时，CUDA 错误状态都会被设置并覆盖。这意味着异步操作执行期间发生的错误，只会在下一次检查错误状态时报告。如前所述，这次检查可能是调用 cudaGetLastError 或 cudaPeekLastError，也可能是任意一个返回 cudaError_t 的 CUDA API。

CUDA Runtime API 函数返回错误时，不会自动清除错误状态。这意味着来自异步错误的错误码，例如内核中的非法内存访问，会被每个 CUDA Runtime API 持续返回，直到调用 cudaGetLastError 清除该错误状态。

    vecAdd<<<blocks, threads>>>(devA, devB, devC);
    // 内核启动后检查错误状态
    CUDA_CHECK(cudaGetLastError());
    // 等待内核执行完成
    // CUDA_CHECK 将报告内核执行期间发生的错误
    CUDA_CHECK(cudaDeviceSynchronize());

注

cudaStreamQuery 或 cudaEventQuery 可能返回 cudaError_t 值 cudaErrorNotReady。该值不视为错误，也不会由 cudaPeekAtLastError 或 cudaGetLastError 报告。

2.1.7.3. CUDA_LOG_FILE#

识别 CUDA 错误的另一种好方法是使用 CUDA_LOG_FILE 环境变量。设置该变量后，CUDA Driver 会把遇到的错误消息写入变量所指定路径的文件。例如，下面这段错误的 CUDA 代码尝试启动一个线程块，其大小超过了任何架构所支持的上限。

__global__ void k()
{ }

int main()
{
        k<<<8192, 4096>>>(); // 块大小无效
        CUDA_CHECK(cudaGetLastError());
        return 0;
}

构建并运行这段代码时，内核启动之后的检查会使用 第 2.1.7 节 中展示的宏检测并报告错误。

$ nvcc errorLogIllustration.cu -o errlog
$ ./errlog
CUDA Runtime Error: /home/cuda/intro-cpp/errorLogIllustration.cu:24:1 = invalid argument

不过，如果运行应用程序时把 CUDA_LOG_FILE 设置为一个文本文件，该文件会包含关于错误的更多信息。

$ env CUDA_LOG_FILE=cudaLog.txt ./errlog
CUDA Runtime Error: /home/cuda/intro-cpp/errorLogIllustration.cu:24:1 = invalid argument
$ cat cudaLog.txt
[12:46:23.854][137216133754880][CUDA][E] One or more of block dimensions of (4096,1,1) exceeds corresponding maximum value of (1024,1024,64)
[12:46:23.854][137216133754880][CUDA][E] Returning 1 (CUDA_ERROR_INVALID_VALUE) from cuLaunchKernel

将 CUDA_LOG_FILE 设置为 stdout 或 stderr 时，日志会分别打印到标准输出或标准错误。借助 CUDA_LOG_FILE 环境变量，即便应用程序没有正确检查 CUDA 返回值，也可以捕获并识别 CUDA 错误。这对调试非常有用，但仅靠环境变量并不能让应用程序在运行时处理 CUDA 错误并从中恢复。CUDA 的 错误日志管理 还允许向驱动注册回调函数；每当检测到错误时，该回调就会被调用。它可用于在运行时捕获和处理错误，也能把 CUDA 错误日志无缝集成到应用程序已有的日志系统中。

第 4.8 节 展示了更多 CUDA 错误日志管理功能示例。错误日志管理和 CUDA_LOG_FILE 适用于 r570 及更高版本的 NVIDIA Driver。

2.1.9. 变量说明符#

CUDA 说明符 可用于静态变量声明，以控制变量的放置位置。

  • __device__ 指定变量存储在 全局内存 中

  • __constant__ 指定变量存储在 常量内存 中

  • __managed__ 指定变量以 统一内存 形式存储

  • __shared__ 指定变量存储在 共享内存 中

如果变量在 __device__ 或 __global__ 函数内部声明且没有使用说明符，那么它会在可能时分配到寄存器中，必要时分配到 本地内存 中。任何在 __device__ 或 __global__ 函数外部声明、且没有使用说明符的变量，都会分配到系统内存中。

2.1.10. 线程块簇#

从计算能力 9.0 开始，CUDA 编程模型加入了一个可选的层次结构，称为线程块簇（thread block cluster），它由多个线程块组成。类似于同一线程块中的线程保证会共同调度到一个流式多处理器上，同一簇中的线程块也保证会共同调度到 GPU 内的一个 GPU Processing Cluster（GPC）上。

与线程块类似，簇也会组织成由线程块簇构成的一维、二维或三维网格，如 图 5 所示。

簇中线程块的数量可由用户定义。在 CUDA 中，最多 8 个线程块的簇大小作为可移植簇大小受到支持。 请注意，如果 GPU 硬件或 MIG 配置小到无法支持 8 个多处理器，则最大簇大小会相应减小。对于这些较小配置，以及支持超过 8 个线程块簇大小的较大配置，相关限制取决于具体架构，可通过 cudaOccupancyMaxPotentialClusterSize API 查询。

簇中的所有线程块都保证会共同调度到单个 GPU Processing Cluster（GPC）上并同时执行，并且簇内线程块可以通过 Cooperative Groups API cluster.sync() 执行硬件支持的同步。cluster group 还提供成员函数，可分别通过 num_threads() 和 num_blocks() 查询簇组中的线程数或线程块数；也可以分别通过 dim_threads() 和 dim_blocks() 查询线程或线程块在簇组中的秩。

属于同一簇的线程块可以访问 分布式共享内存，也就是簇中所有线程块共享内存的组合。簇内线程块能够对分布式共享内存中的任意地址进行读取、写入和原子操作。分布式共享内存 给出了在分布式共享内存中执行直方图的示例。

注

在启用簇支持启动的内核中，出于兼容性考虑，gridDim 变量仍以线程块数量表示网格大小。线程块在簇中的秩可通过 Cooperative Groups API 获取。

2.1.10.1. 用三尖括号语法启动簇#

线程块簇可以通过编译时内核属性 __cluster_dims__(X,Y,Z) 在内核中启用，也可以通过 CUDA 内核启动 API cudaLaunchKernelEx 启用。下面的示例展示了如何使用编译时内核属性启动簇。通过内核属性指定的簇大小在编译时固定；之后即可使用传统的 <<< , >>> 语法启动内核。如果内核使用编译时簇大小，那么启动内核时不能再修改该簇大小。

// 内核定义
// 编译时簇大小在 X 维度为 2，在 Y 和 Z 维度为 1
__global__ void __cluster_dims__(2, 1, 1) cluster_kernel(float *input, float* output)
{

}

int main()
{
    float *input, *output;
    // 具有编译时簇大小的内核调用
    dim3 threadsPerBlock(16, 16);
    dim3 numBlocks(N / threadsPerBlock.x, N / threadsPerBlock.y);

    // 网格维度不受簇启动影响，仍然枚举
    // 使用块数。
    // 网格尺寸必须是簇大小的倍数。
    cluster_kernel<<<numBlocks, threadsPerBlock>>>(input, output);
}
