2.4. 统一内存与系统内存#

异构系统中存在多个可存储数据的物理内存。主机 CPU 连接主机 DRAM，而系统中的每块 GPU 也有各自连接的 DRAM。当数据驻留在访问它的处理器本地内存中时，性能最佳。CUDA 提供了用于显式管理内存放置的 API，但这往往较为冗长并增加软件设计复杂度。CUDA 也提供了多种特性来简化不同物理内存间的数据分配、放置与迁移。

本章旨在介绍并解释这些特性，以及它们对应用开发者在功能和性能层面的意义。统一内存在不同操作系统、驱动版本和 GPU 条件下会呈现不同形态。本章将说明如何判断当前适用的统一内存范式，以及各范式下统一内存的行为。关于统一内存的更深入内容见后续统一内存章节。

本章将定义并解释以下概念：

  • Unified Virtual Address Space - CPU memory and each GPU’s memory have a distinct range within a single virtual address space

  • Unified Memory - A CUDA feature that enables managed memory which can be automatically migrated between CPU and GPUs

    • Limited Unified Memory - A unified memory paradigm with some limitations

    • Full Unified Memory - Full support for unified memory features

    • Full Unified Memory with Hardware Coherency - Full support for unified memory using hardware capabilities

    • Unified memory hints - APIs to guide unified memory behavior for specific allocations

  • Page-locked Host Memory - Non-pageable system memory, which is necessary for some CUDA operations

    • Mapped memory - A mechanism (different from unified memory) for accessing host memory directly from a kernel

此外，本章还会介绍讨论统一内存与系统内存时常见的术语：

  • Heterogeneous Managed Memory (HMM) - A feature of the Linux kernel that enables software coherency for full unified memory

  • Address Translation Services (ATS) - A hardware feature, available when GPUs are connected to the CPU by the NVLink Chip-to-Chip (C2C) interconnect, which provides hardware coherency for full unified memory

2.4.1. 统一虚拟地址空间#

在同一操作系统进程内，系统中所有主机内存与所有 GPU 全局内存共享一个虚拟地址空间。主机端与各设备上的所有分配都位于该空间中。无论通过 CUDA API（如 cudaMalloc、cudaMallocHost）还是系统分配 API（如 new、malloc、mmap）进行分配，均如此。CPU 与每块 GPU 都在该统一虚拟地址空间中拥有各自独立的地址范围。

这意味着：

  • 可通过 cudaPointerGetAttributes() 根据指针值判断任意内存所在位置（CPU 或某块 GPU 的内存）

  • 可将 cudaMemcpy*() 的 cudaMemcpyKind 参数设为 cudaMemcpyDefault，由指针自动判定拷贝类型

2.4.2. 统一内存#

统一内存是 CUDA 的一种内存特性，允许称为托管内存的分配被 CPU 端与 GPU 端代码共同访问。我们已在 CUDA C++ 入门 中展示过统一内存。统一内存在所有 CUDA 支持的系统上均可用。

在某些系统上，托管内存需要显式分配。CUDA 中可通过以下几种方式显式分配托管内存：

  • CUDA API：cudaMallocManaged

  • 在内存池的 allocType 设置为 cudaMemAllocationTypeManaged 时，使用 CUDA API cudaMallocFromPoolAsync

  • 使用 __managed__ 说明符的全局变量（见 内存空间说明符）

在支持 HMM 或 ATS 的系统上，无论系统内存如何分配，都会隐式作为托管内存，无需特殊分配。

2.4.2.1. 统一内存范式#

统一内存的特性与行为会随操作系统、Linux 内核版本、GPU 硬件以及 GPU-CPU 互连方式而变化。可通过 cudaDeviceGetAttribute 查询以下属性来判断可用的统一内存形态：

  • cudaDevAttrConcurrentManagedAccess - 1 for full unified memory support, 0 for limited support

  • cudaDevAttrPageableMemoryAccess - 1 means all system memory is fully-supported unified memory, 0 means only memory explicitly allocated as managed memory is fully-supported unified memory

  • cudaDevAttrPageableMemoryAccessUsesHostPageTables - Indicates the mechanism of CPU/GPU coherence: 1 is hardware, 0 is software.

统一内存共有四种工作范式：

  • Full support for explicit managed memory allocations

  • Full support for all allocations with software coherence

  • Full support for all allocations with hardware coherence

  • Limited unified memory support

当具备完整支持时，可能仍需显式分配，也可能所有系统内存都被隐式视为统一内存。若全部内存都隐式统一，则一致性机制可能由软件或硬件实现。Windows 与部分 Tegra 设备仅支持有限统一内存。

2.4.2.1.1. 统一内存范式：代码示例#

下面的代码示例展示了如何按照 图 18 的逻辑，为系统中的每块 GPU 查询设备属性并判断统一内存范式。

void queryDevices()
{
    int numDevices = 0;
    cudaGetDeviceCount(&numDevices);
    for(int i=0; i<numDevices; i++)
    {
        cudaSetDevice(i);
        cudaInitDevice(0, 0, 0);
        int deviceId = i;

        int concurrentManagedAccess = -1;     
        cudaDeviceGetAttribute (&concurrentManagedAccess, cudaDevAttrConcurrentManagedAccess, deviceId);    
        int pageableMemoryAccess = -1;
        cudaDeviceGetAttribute (&pageableMemoryAccess, cudaDevAttrPageableMemoryAccess, deviceId);
        int pageableMemoryAccessUsesHostPageTables = -1;
        cudaDeviceGetAttribute (&pageableMemoryAccessUsesHostPageTables, cudaDevAttrPageableMemoryAccessUsesHostPageTables, deviceId);

        printf("Device %d has ", deviceId);
        if(concurrentManagedAccess){
            if(pageableMemoryAccess){
                printf("full unified memory support");
                if( pageableMemoryAccessUsesHostPageTables)
                    { printf(" with hardware coherency\n");  }
                else
                    { printf(" with software coherency\n"); }
            }
            else
                { printf("full unified memory support for CUDA-made managed allocations\n"); }
        }
        else
        {   printf("limited unified memory support: Windows, WSL, or Tegra\n");  }
    }
}

2.4.2.2. 完整统一内存特性支持#

多数 Linux 系统支持完整统一内存。若设备属性 cudaDevAttrPageableMemoryAccess 为 1，则无论通过 CUDA API 还是系统 API 分配，所有系统内存都以具备完整特性的统一内存方式运行，其中也包括通过 mmap 创建的文件映射内存。

若 cudaDevAttrPageableMemoryAccess 为 0，则只有通过 CUDA 作为托管内存分配的内存才表现为统一内存。通过系统 API 分配的内存不受托管，也不一定能被 GPU 内核访问。

总体而言，在“完整支持”下，统一内存分配通常具有以下行为：

  • 托管内存通常会分配在“首次访问它”的处理器所在内存空间；

  • 当被当前驻留处理器以外的处理器使用时，托管内存通常会发生迁移；

  • 托管内存以页粒度（软件一致性）或缓存行粒度（硬件一致性）进行迁移或访问；

  • 允许超额订阅：应用可分配超过 GPU 物理可用容量的托管内存。

实际分配与迁移行为也可能偏离上述规则。开发者可通过提示与预取进行影响。关于完整统一内存支持的全面说明见 具备完整 CUDA 统一内存支持的设备上的统一内存。

2.4.2.2.1. 具备硬件一致性的完整统一内存#

在 Grace Hopper、Grace Blackwell 等硬件上，当采用 NVIDIA CPU 且 CPU-GPU 互连为 NVLink Chip-to-Chip（C2C）时，可用地址转换服务（ATS）。当 ATS 可用时，cudaDevAttrPageableMemoryAccessUsesHostPageTables 为 1。

在 ATS 下，除对全部主机分配提供完整统一内存支持外，还具备：

  • CPU 可访问 GPU 分配（如 cudaMalloc），此时 cudaDevAttrDirectManagedMemAccessFromHost 为 1；

  • CPU 与 GPU 间链路支持原生原子操作（cudaDevAttrHostNativeAtomicSupported 为 1）；

  • 硬件一致性通常较软件一致性具有更好的性能。

ATS 覆盖了 HMM 的全部能力。ATS 可用时，HMM 会自动禁用。关于硬件一致性与软件一致性的更多讨论见 CPU 与 GPU 页表：硬件一致性 vs 软件一致性。

2.4.2.2.2. HMM：具备软件一致性的完整统一内存#

Heterogeneous Memory Management (HMM) is a feature available on Linux operating systems (with appropriate kernel versions) which enables software-coherent full unified memory support. Heterogeneous memory management brings some of the capabilities and convenience provided by ATS to PCIe-connected GPUs.

在 Linux 内核版本至少为 6.1.24、6.2.11 或 6.3+ 的系统上，可能支持异构内存管理（HMM）。可用以下命令检查寻址模式是否为 HMM。

$ nvidia-smi -q | grep Addressing
Addressing Mode : HMM

当 HMM 可用时，系统支持完整统一内存，且所有系统分配都被隐式视为统一内存。若系统同时支持 ATS，则会禁用 HMM 并改用 ATS，因为 ATS 能提供 HMM 的全部能力并更进一步。

2.4.2.3. 有限统一内存支持#

在 Windows（含 WSL）及部分 Tegra 系统上，仅提供统一内存的有限子集功能。在这些系统中虽然可用托管内存，但 CPU 与 GPU 间迁移行为有所不同。

  • 托管内存首先分配在 CPU 物理内存中；

  • 托管内存迁移粒度大于虚拟内存页；

  • GPU 开始执行时，托管内存迁移到 GPU；

  • GPU 活跃期间，CPU 不得访问托管内存；

  • GPU 同步时，托管内存迁回 CPU；

  • 不允许 GPU 内存超额订阅；

  • 只有 CUDA 显式分配为托管内存的分配才属于统一内存。

该范式的完整说明见 Windows、WSL 与 Tegra 上的统一内存。

2.4.2.4. 内存建议与预取#

开发者可向管理统一内存的 NVIDIA 驱动提供提示，以帮助最大化应用性能。CUDA API cudaMemAdvise 允许指定分配属性，从而影响其放置位置以及被其他设备访问时是否迁移。

cudaMemPrefetchAsync 允许开发者建议异步启动某个分配到其他位置的迁移。常见用法是在内核启动前预先传输其将使用的数据，从而让数据拷贝与其他 GPU 内核执行重叠。

性能提示一节介绍了可传给 cudaMemAdvise 的不同提示，并给出 cudaMemPrefetchAsync 的示例。

2.4.3. 页锁定主机内存#

在入门示例中，我们使用 cudaMallocHost 在 CPU 端分配内存。这会在主机端分配页锁定（也称 pinned）内存。通过传统机制（如 malloc、new、mmap）得到的主机内存并非页锁定，因此可能被操作系统换出到磁盘或发生物理重定位。

进行CPU 与 GPU 之间的异步拷贝需要页锁定主机内存。页锁定主机内存也能提升同步拷贝性能。此外，页锁定内存可被映射到 GPU，供 GPU 内核直接访问。

CUDA 运行时提供了用于分配页锁定主机内存或对已有分配执行页锁定的 API：

  • cudaMallocHost：分配页锁定主机内存

  • cudaHostAlloc：默认行为与 cudaMallocHost 相同，也可通过标志位指定其他内存参数

  • cudaFreeHost：释放由 cudaMallocHost 或 cudaHostAlloc 分配的内存

  • cudaHostRegister：对 CUDA API 之外（如 malloc、mmap）分配的已有内存区间执行页锁定

cudaHostRegister 使得由第三方库或开发者不可控代码分配的主机内存也可被页锁定，从而可用于异步拷贝或映射访问。

注意

系统中的所有 GPU 都可使用页锁定主机内存进行异步拷贝与映射内存访问。

在非 I/O 一致性的 Tegra 设备上，页锁定主机内存不会被缓存；且这些设备不支持 cudaHostRegister()。

2.4.3.1. 映射内存#

在支持 HMM 或 ATS 的系统上，GPU 可直接通过主机指针访问全部主机内存。若 ATS/HMM 不可用，则可通过将主机内存映射到 GPU 内存空间来实现访问。映射内存始终是页锁定内存。

下面的代码示例将展示如下数组复制内核如何直接在映射主机内存上工作。

__global__ void copyKernel(float* a, float* b)
{
        int idx = threadIdx.x + blockDim.x * blockIdx.x;
        a[idx] = b[idx];
}

在某些无需拷贝到 GPU、但内核仍需访问的数据场景中，映射内存可能有用。然而内核访问映射内存需要跨越 CPU-GPU 互连（PCIe 或 NVLink C2C）进行事务，延迟更高、带宽更低，不如访问设备内存高效。对于内核的大多数内存需求，不应将映射内存视为 统一内存 或 显式内存管理 的高性能替代方案。

2.4.3.1.1. cudaMallocHost 与 cudaHostAlloc#

通过 cudaHostMalloc 或 cudaHostAlloc 分配的主机内存会自动映射。其返回指针可直接在内核代码中访问主机内存；访问路径经过 CPU-GPU 互连。

void usingMallocHost() {
  float* a = nullptr;
  float* b = nullptr;
  
  CUDA_CHECK(cudaMallocHost(&a, vLen*sizeof(float)));
  CUDA_CHECK(cudaMallocHost(&b, vLen*sizeof(float)));

  initVector(b, vLen);
  memset(a, 0, vLen*sizeof(float));

  int threads = 256;
  int blocks = vLen/threads;
  copyKernel<<<blocks, threads>>>(a, b);
  CUDA_CHECK(cudaGetLastError());
  CUDA_CHECK(cudaDeviceSynchronize());

  printf("Using cudaMallocHost: ");
  checkAnswer(a,b);
}

void usingCudaHostAlloc() {
  float* a = nullptr;
  float* b = nullptr;

  CUDA_CHECK(cudaHostAlloc(&a, vLen*sizeof(float), cudaHostAllocMapped));
  CUDA_CHECK(cudaHostAlloc(&b, vLen*sizeof(float), cudaHostAllocMapped));

  initVector(b, vLen);
  memset(a, 0, vLen*sizeof(float));

  int threads = 256;
  int blocks = vLen/threads;
  copyKernel<<<blocks, threads>>>(a, b);
  CUDA_CHECK(cudaGetLastError());
  CUDA_CHECK(cudaDeviceSynchronize());

  printf("Using cudaAllocHost: ");
  checkAnswer(a, b);
}

2.4.3.1.2. cudaHostRegister#

当 ATS 与 HMM 不可用时，仍可通过 cudaHostRegister 将系统分配器分配的内存映射给 GPU 内核直接访问。不同于 CUDA API 直接创建的内存，这类内存不能在内核中直接使用主机指针访问；必须先通过 cudaHostGetDevicePointer() 获取设备地址空间中的指针，并在内核中使用该指针。

void usingRegister() {
  float* a = nullptr;
  float* b = nullptr;
  float* devA = nullptr;
  float* devB = nullptr;

  a = (float*)malloc(vLen*sizeof(float));
  b = (float*)malloc(vLen*sizeof(float));
  CUDA_CHECK(cudaHostRegister(a, vLen*sizeof(float), 0 ));
  CUDA_CHECK(cudaHostRegister(b, vLen*sizeof(float), 0  ));

  CUDA_CHECK(cudaHostGetDevicePointer((void**)&devA, (void*)a, 0));
  CUDA_CHECK(cudaHostGetDevicePointer((void**)&devB, (void*)b, 0));

  initVector(b, vLen);
  memset(a, 0, vLen*sizeof(float));

  int threads = 256;
  int blocks = vLen/threads;
  copyKernel<<<blocks, threads>>>(devA, devB);
  CUDA_CHECK(cudaGetLastError());
  CUDA_CHECK(cudaDeviceSynchronize());

  printf("Using cudaHostRegister: ");
  checkAnswer(a, b);
}

2.4.3.1.3. 统一内存与映射内存对比#

映射内存让 GPU 可以访问 CPU 内存，但并不保证所有访问类型（例如原子操作）在所有系统上都受支持。统一内存则保证所有访问类型均可用。

映射内存始终驻留在 CPU 内存中，这意味着 GPU 的所有访问都必须经过 CPU-GPU 互连（PCIe 或 NVLink）。跨该链路访问的延迟明显高于访问 GPU 内存，且总可用带宽更低。因此，将映射内存用于内核的全部内存访问通常难以充分利用 GPU 计算资源。

统一内存通常会迁移到当前访问它的处理器物理内存中。首次迁移后，内核对同一内存页或缓存行的重复访问可利用完整 GPU 内存带宽。

注意

在以往文档中，映射内存也常被称为 zero-copy（零拷贝）内存。

在所有 CUDA 应用都使用统一虚拟地址空间之前，需要额外 API 才能启用内存映射（cudaSetDeviceFlags 配合 cudaDeviceMapHost）。这些 API 现已不再需要。

对映射主机内存执行的原子函数（见 原子函数）从主机或其他 GPU 视角看不具备原子性。

CUDA 运行时要求：由设备发起并作用于主机内存的 1/2/4/8/16 字节自然对齐读写，从主机和其他设备视角看必须保持为单次访问。在某些平台上，硬件可能将内存原子操作拆分为独立的加载与存储；这些子操作同样需满足自然对齐访问保持要求。CUDA 运行时不支持会拆分 8 字节自然对齐操作的 PCIe 拓扑；NVIDIA 也不了解会拆分 16 字节自然对齐操作的拓扑。

2.4.4. 总结#

  • 在支持异构内存管理（HMM）或地址转换服务（ATS）的 Linux 平台上，所有系统分配内存都属于托管内存；

  • 在不支持 HMM/ATS 的 Linux、Tegra 处理器以及所有 Windows 平台上，托管内存必须通过 CUDA 显式分配：

    • cudaMallocManaged or

    • cudaMallocFromPoolAsync with a pool created with allocType=cudaMemAllocationTypeManaged

    • 使用 __managed__ 说明符的全局变量

  • 在 Windows 与 Tegra 平台上，统一内存存在功能限制；

  • 在具备 ATS 的 NVLINK C2C 系统上，cudaMalloc 分配的设备内存可被 CPU 或其他 GPU 直接访问。
